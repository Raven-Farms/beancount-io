# Apply getLedgerContext's payee limit to its nested vocabulary too

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** backend-v2. **A1 — Agent-native accounting:** an agent requesting a bounded vocabulary should receive that bounded sample throughout the context payload.

## Live reproduction

Production `https://beancount.io`, observed 2026-10-14; local main `1d45a5ea`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed SHA unavailable. Existing designated unpinned QA API key, scopes `ledger.read ledger.write ledger.admin`. Only public synthetic ledgers were read.

Call `getLedgerContext` with:

```json
{"ledger":"open_ledger/example","payeeLimit":1}
```

HTTP 200, successful tool envelope. The result has:

```text
result.payees.length             = 1
result.payeeCount                 = 36
result.attributes.payees.length  = 36
```

A fresh repeat returns the same result. With `payeeLimit: 500`, the top-level list grows to 36, but `attributes.payees` is unchanged. The nested list exactly equals both the full tool payee list and REST `GET /api-gateway/v1/ledgers/open_ledger/example/payees`. REST `/attributes` exactly matches the unmodified nested attributes object.

A second synthetic ledger, `open_ledger/crypto-example`, with `payeeLimit: 1` likewise returns one top-level payee but all 17 payees in `attributes.payees`, with `payeeCount: 17`. These are vocabulary strings from public fixtures, not private customer data. The defect is redundant unbounded context, not incorrect accounting or an authorization issue. Larger-ledger token costs were not measured.

Exact helper pattern:

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file .env call getLedgerContext '{"ledger":"open_ledger/example","payeeLimit":1}'
```

## Root cause and bounded repair

`backend-cluster/backend-v2/src/features/ai-agent/tools/ledger-context-tools.ts`, `executeGetLedgerContext`, returns raw `attributes` from `ledgerData.getAttributes` and separately slices only `payees`. Real attributes contain a full `payees` array. Thus every payee still reaches the agent even when it requests a sample of one.

The published input describes `payeeLimit` as how many payees to return; the tool description promises counts beside truncated lists to avoid flooding context. The original acceptance in `w2/done/m27/done/t003.md` explicitly calls for top-N payees and bounded context. The current unit fixture supplies attributes as `{options: {}}`, so it cannot detect the second copy.

Apply the limit consistently to the context tool's nested payee vocabulary as well as its top-level sample. Preserve the full `payeeCount`, deterministic ordering, existing defaults and bounds, and unrelated attribute fields. Project into a new object rather than mutating the shared service result. Keep the standalone attributes/payees reads complete: REST, GraphQL and MCP vocabulary resources do not accept this context-tool-only limit and should not acquire an unrelated global cap. This is a repair of the MCP convenience aggregate's projection; no new endpoint or protocol exception is needed.

Regression coverage should use realistic attributes containing the same full payee list, assert that both tool lists respect the requested limit, preserve the true count and other attributes, and verify the original service object remains intact. Check the default limit against a fixture above 50 payees and retain complete results below the limit. Exercise the registered MCP tool so its structured and text representations both contain the bounded vocabulary. Run the owning package's typecheck/test/OpenAPI drift checks and preserve the existing zero-debt surface-parity gate.
