# Validate journal pagination before GraphQL reaches array slicing

**Severity:** minor. **Estimate:** 40–55 minutes, including adapter coverage. **Owner:** backend-v2. **A1 — Agent-native accounting:** equivalent API reads must reject invalid pagination consistently instead of silently returning a different page.

## Live reproduction

Production `https://beancount.io`, 2026-10-11; main `c2820a99`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed SHA unavailable. Designated unpinned QA API key with `ledger.read ledger.write ledger.admin`, loaded inside helpers and never recorded. Only the existing synthetic evaluation ledger was read. This is an API-parity finding from MCP QA.

Use a prepared synthetic ledger with two USD accounts (`Assets:Checking`, `Expenses:Food`), two balanced expense transactions, and their opens. Its account journal has three items (one open, two transactions), and its Transaction-only main journal has two items. Send ordinary authenticated GraphQL POSTs to `/api-gateway/`:

```graphql
query {
  getLedgerAccountJournal(
    ledgerId: "qa-owner/qa-book"
    query: { account: "Assets:Checking", limit: -1, offset: 0 }
  ) { total items { entry change balance } }
}
```

Actual on the hosted synthetic fixture, in two fresh requests: HTTP 200 without errors, `total:10`, **nine** returned account items. `limit:-1` means "all except the last" through JavaScript slicing. `limit:1.5` likewise succeeds twice, silently returning one item with `total:10`. `limit:2,offset:-1` succeeds with zero items and `total:10`.

The second affected read is also live:

```graphql
query {
  getLedgerJournal(
    ledgerId: "qa-owner/qa-book"
    query: { directiveTypes: ["Transaction"], limit: -1, offset: 0 }
  ) { total data }
}
```

Two fresh requests succeed with `total:16` and fifteen transactions. On the two-transaction minimal fixture the same negative limit would omit its last transaction.

## Working and rejected controls

- GraphQL `limit:2,offset:0` returns the same two account items, changes, and running balances as MCP/REST. Full reads and successive pages retain correct running balances; this finding does not allege an arithmetic or valid-page defect.
- MCP `resources/read` of `beancount://qa-owner/qa-book/account-journal?account=Assets%3AChecking&limit=1.5` or `limit=-1` returns JSON-RPC `-32602` with `data.code:"BAD_USER_INPUT"` and the named limit validation error, HTTP 200 SSE.
- The identical REST `GET /api-gateway/v1/ledgers/qa-owner/qa-book/account-journal` requests return HTTP 400 with `VALIDATION_FAILED` naming `query.limit`. The main-journal negative-limit controls are also rejected by MCP and REST. Both existing schemas require integer limits in 1–1000 and integer offsets at least zero. Their protocol-specific error envelopes are recorded rather than claimed identical.
- GraphQL `limit:0` additionally succeeds with zero items and the nonzero total. The published REST/MCP lower bound is one; no documented journal count-only or negative-limit exception was found.

## Root cause and correction

GraphQL `JournalQueryInput` and `AccountJournalQueryInput` in `src/features/ledger/api/resolvers/ledger-journal-resolver.query.ts:59–80,134–166` publish pagination as `Number` (Float) and provide no value constraints. Resolvers at lines 186–195 and 234–248 pass the input straight to the shared journal service.

`src/features/ledger/service/ledger-journal-service.ts:161–186,246–275` forwards unchecked limits/offsets to the ledger client. The producer in `backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:597–609,747–760` uses `items.slice(offset,offset+limit)`: fractions truncate, negative values become end-relative indexes, and zero becomes an empty success. REST/MCP stop earlier through `journal-reads.ts` integer/range query schemas; GraphQL bypasses those adapter schemas.

Enforce the existing journal pagination contract in the shared backend-v2 service before the downstream read: optional limit defaults to 20 and must be a safe integer in 1–1000; optional offset defaults to zero and must be a safe nonnegative integer. Reject invalid values with a named `BadUserInputError` so GraphQL receives a useful input error instead of a silently altered page. Preserve valid defaults, filters, total counts, descending order, running balances, source permissions, and published field names/types. Keep REST/MCP rejection behavior and their documented envelopes. No ledger-engine change or cross-package import is needed.

Exercise both journal reads through real GraphQL/REST/MCP adapters for negative/fractional/zero/over-limit pagination, valid omitted/default values, normal pages, and a valid out-of-range empty page. Offset-fraction and over-limit cases are source-derived acceptance cases, not claimed live reproductions here. Run backend-v2 typecheck, tests, and OpenAPI drift generation when implementing.
