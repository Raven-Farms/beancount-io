# Describe an empty BQL result without claiming no postings matched

**Severity:** minor. **Estimate:** 15–25 minutes. **Owner:** backend-v2. **A1 — Agent-native accounting:** MCP text should describe the result it knows, without turning a query limit or aggregate filter into a statement about ledger activity.

## Reproduction and controls

Production `https://beancount.io`, 2026-10-14; local main `ba1ddb80`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed SHA unavailable. Existing designated unpinned QA API key, scopes `ledger.read ledger.write ledger.admin`. Read-only public synthetic `open_ledger/example`.

Call `runBqlQuery` with:

```json
{"ledger":"open_ledger/example","query":"SELECT DISTINCT payee WHERE payee IS NOT NULL ORDER BY payee LIMIT 0"}
```

HTTP 200, successful envelope, empty string result. The text block says **`0 rows — no postings matched`**, including on a fresh repeat. The same query without LIMIT has 36 non-null payees; with LIMIT 5 it returns the first five sorted names. Postings do match the predicate: LIMIT deliberately suppresses the output rows. The count is correct; the claimed cause is false.

`runBqlQueryStructured` and REST `POST /api-gateway/v1/ledgers/open_ledger/example/query` with the same LIMIT-0 query both return an empty table. The structured MCP result states `rowCount: 0`, `truncated: false`, and its text correctly says just `0 rows` before the short JSON payload.

An additional text-tool call, `SELECT payee, COUNT(*) AS postings GROUP BY payee HAVING COUNT(*) > 10000`, also says `no postings matched`. The verified unfiltered grouping has 37 groups covering 3,209 postings; HAVING removes all groups. Empty output alone does not establish that the input stream had no matching postings.

Helper pattern: `node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file .env call runBqlQuery '<JSON above>'`.

## Root cause and bounded repair

`backend-cluster/backend-v2/src/features/ai-agent/api/mcp-result-text.ts`, `renderBqlTable`, returns the fixed phrase whenever canonical row-count metadata equals zero. That metadata counts output rows, not pre-LIMIT/pre-HAVING input postings, so it cannot support the explanation.

Use neutral wording such as `0 rows` or `0 rows — query returned no rows`. Preserve canonical same-query counts, success status, the empty string result, text payloads for nonempty results and all typed data. Do not add a second count query or infer causes by parsing the statement. REST and GraphQL query evaluation/results remain the same; the repair belongs to MCP's additional text summary.

Update the existing text-summary and registered BQL parity tests with genuine empty input and LIMIT-0/HAVING controls, asserting truthful text and unchanged canonical counts. The current literal expectation for `no postings matched` should change rather than preserve the overclaim. Run backend-v2 typecheck/tests and OpenAPI drift checks; retain the zero-debt parity gate.
