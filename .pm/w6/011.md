# Start default quarterly reports in the quarter containing their first activity

**Severity:** minor. **Estimate:** 35–50 minutes. **Owner:** ledger. **A1 — Agent-native accounting:** quarter-grouped reads should describe the selected activity span without inventing an earlier empty reporting quarter.

## Live reproduction

Production `https://beancount.io`, 2026-10-11; main `ef178f5a`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed SHA unavailable. Existing designated unpinned QA API key with `ledger.read ledger.write ledger.admin`; read-only public synthetic demos, no personal ledger data.

Read this URI without a `time` parameter:

```text
beancount://open_ledger/real-estate-example/interval-totals?account=Income%3ARealEstate%3ARent&accountName=Income%3ARealEstate%3ARent&conversion=USD&interval=quarter&shape=fava
```

The independently inspected complete transaction history starts rental income on **2024-04-01**. Two fresh MCP requests return eight quarters, starting with `{"date":"2024-03-31","balance":{},"account_balances":{}}`: a wholly empty Q1 before any selected transaction. Both REST controls return the same eight points. `shape=summary` also exposes the extra first period with total 0 and no accounts. GraphQL `getLedgerIntervalTotals` with the same ledger/account/conversion/interval returns the same eight points, renaming only `account_balances` to `accountBalances`.

Controls:

- Change grouping to `month`: 19 periods begin at `2024-04-30`, with -2400 USD rental income. The quarter and month flow sums agree; this finding is a wrong extra period, not lost money.
- Supply `time=2024-04-01 - 2025-10-01`: seven quarter intervals begin at `2024-06-30`; the explicit-window path does not invent Q1. MCP and REST match.
- Public `open_ledger/crypto-example`, filtered to `Assets:DeFi:Compound:CUSDC` for both `account` and `accountName`, `conversion=at_cost`, `interval=quarter`, `shape=fava`, no time: first selected transaction **2025-07-31**, but the first result is an empty **2025-06-30** Q2.
- Same crypto ledger, `Assets:Crypto:NFT`: first selected transaction **2025-10-05**, but an empty **2025-09-30** Q3 precedes it. Both cases have matching REST controls.

Exact helper pattern: `node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file .env read '<URI above>'`.

## Root cause and bounded repair

`backend-cluster/ledger/src/foundation/rustledger/interval-series.ts`, `INTERVALS.quarter.getPrev`, checks `m > i` for boundary months `[10, 7, 4]`. That floors every April to January, July to April, and October to July. The containing quarter must include its boundary month. `intervalRanges(..., complete=true)` calls this function to round the first activity date; `complete=false` starts directly at the explicit window and explains the working control.

The official [Fava quarter implementation](https://github.com/beancount/fava/blob/main/src/fava/util/date.py#L160) floors the month using `(month - 1) // 3 * 3 + 1`, consistently including April/July/October. Its interval API defines the previous boundary as the start of the containing interval. This is a divergence from the port's stated Fava behavior, not a request for a new reporting policy.

Correct the quarter floor in this ledger package, preserving year/month/week/day behavior, the shared `quarter`/`quarterly` aliases, explicit partial windows, and legitimate empty quarters **inside** a requested span. Do not fix it by dropping all zero periods. Cover all 12 start months, including first/middle/last days in April/July/October, and both aliases. Add a report-level fixture with first activity on 2024-04-01: one -2400 USD rental transaction should yield one June-30 quarter, not an extra March-31 zero quarter. That minimal fixture is a proposed regression control, not a ledger uploaded by this run.

`seriesRanges` feeds both `intervalTotals` and `accountBalanceSeries`; callers include ledger-data's interval/account reports and ledger-finance's overview, statement and net-worth series. Those additional callers are source-traced. The live reproduction covers interval totals and their backend projections across REST/GraphQL/MCP. The domain fix should update all eligible consumers together through the shared implementation; no protocol adapter duplication or exemption is needed. Keep w6/005's separate income-summary `period.from` correction independent.

Acceptance: default April/July/October-start reports begin in the containing quarter, raw and summary interval reads agree, the existing explicit-window and full-history controls stay correct, and native ledger checks pass (`yarn test`, `yarn lint`, `yarn typecheck`, `yarn build`; engine verification where required by the scoped guide).
