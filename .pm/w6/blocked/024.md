# Adopt hidden ORDER BY keys in subqueries and table groups

**Severity:** minor · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 45–60m after a published fixed WASM artifact.

**A1 — Agent-native accounting.** An agent cannot return just the top customer account names ranked by outstanding balance: a valid query is refused unless it exposes the sort key as another output column.

## Reproduce

Live 2026-10-15, `https://beancount.io/api-gateway/mcp`, documented synthetic `open_ledger/freelancer-invoicing`, designated unpinned API key (ledger.read/write/admin). Last observed handshake: beancount-mcp 1.0.0, protocol 2025-11-25; deployed backend/engine revision unavailable. No ledger mutations.

Use the root `.env` with the QA helper to call `runBqlQueryStructured`:

```json
{"ledger":"open_ledger/freelancer-invoicing","query":"SELECT account FROM (SELECT account, SUM(number) AS outstanding WHERE account ~ '^Assets:Receivable:' AND date < 2026-03-01 GROUP BY account) ORDER BY outstanding DESC LIMIT 2"}
```

Fresh MCP calls both fail with isError true / BAD_USER_INPUT: `Invalid BQL query: Query execution error: column 'outstanding' not found`. Modern REST POST `/api-gateway/v1/ledgers/open_ledger/freelancer-invoicing/query` returns HTTP 400 with the same code/message twice. GraphQL queryShell returns the same BAD_USER_INPUT. This is a shared engine refusal, not inconsistent error envelopes.

Nearby control: change the outer projection to `SELECT account, outstanding`, keeping the inner query and ORDER BY unchanged. MCP/REST succeed with Northwind 6000.00 and Contoso 4500.00 USD. Independent sums from the complete 23-transaction journal as of February 28 are Northwind 6000, Contoso 4500, Fabrikam 3200; the expected account-only result is therefore Northwind then Contoso. The sort key exists in the subquery row; only its omission from the outer output triggers the failure.

Independent valid minimal fixture: open Assets:A, Assets:B, Assets:C and Equity:Opening; one balanced transaction posts 10/20/30 USD to A/B/C and -60 USD to equity. Query `SELECT account FROM (SELECT account, SUM(number) AS outstanding WHERE account ~ '^Assets:' GROUP BY account) ORDER BY outstanding DESC LIMIT 2`. Official Beanquery 0.2.0 returns C then B; installed WASM 0.24.0 reports the same missing-column error. Selecting outstanding as well makes native WASM return C/30 and B/20. Both loaders report zero errors.

## Root cause, adoption and acceptance

Tagged v0.24.0 `crates/rustledger-query/src/executor/execution.rs::execute_select_from_subquery` materializes the outer projection before sorting; its column map cannot resolve an ORDER BY column omitted from that projection. The ordinary SELECT path already adds hidden ORDER BY targets. This is not an unknown input column.

Upstream [05b8588b8cc364ed4b55587173a805d33178526f / PR 2439](https://github.com/rustledger/rustledger/commit/05b8588b8cc364ed4b55587173a805d33178526f) adds the existing hidden-target path to subqueries and grouped table/subquery execution: evaluate hidden keys, deduplicate visible columns, sort, then strip hidden columns before PIVOT/LIMIT. The initial subquery reproduction is complemented by the table-group reproduction below; other cases in that upstream fix still require targeted adoption tests rather than broad hosted claims.

## Additional verified table-group path — 2026-10-15

On synthetic freelancer-invoicing, `SELECT account FROM #postings GROUP BY account ORDER BY COUNT(*) DESC, account LIMIT 3` fails twice through MCP and REST with BAD_USER_INPUT / `ORDER BY expression not found in SELECT: COUNT(*)`; GraphQL reproduces the same refusal. This query asks for the busiest account names, ranking by a count it does not need to print.

Control `SELECT account, COUNT(*) AS posting_count FROM #postings GROUP BY account ORDER BY posting_count DESC, account LIMIT 3` succeeds on MCP/REST. It returns Assets:Bank:Business 14, Assets:Receivable:Contoso 7, Assets:Bank:TaxReserve 6. Independent posting counts from the complete 23-transaction journal match that exact order and counts. Removing only `FROM #postings` from the original account-only query also succeeds on MCP/REST with those three names in that order, isolating the grouped-table execution path.

A valid native fixture with A/B/C assets and equity has posting counts C=2, Equity:Opening=2, A=1, B=1. Installed WASM 0.24.0 fails the account-only table query with the same ORDER BY error; the visible-count-alias control returns C/2, Equity/2, A/1. Official Beanquery over the same fixture returns C, Equity, A using the equivalent default-posting-source query (without the rustledger-specific `FROM #postings` spelling). The official control is not claimed to run that system-table spelling.

The same upstream 05b8588b commit fixes `execute_aggregate_from_table` alongside the subquery path by evaluating hidden ORDER BY targets. Extend actual-artifact regression coverage to this table-group query, non-equal counts and ties, and the working alias control, preserving the three requested output rows and a one-column result. A variant selecting COUNT under an alias but still ordering by the COUNT expression also failed in this pass; only the explicit alias-order control succeeded. Do not claim every alias/expression combination fixed before testing the adopted artifact.
