# Preserve integer arithmetic before type-sensitive BQL operations

**Severity:** minor · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 45–60m after a compatible upstream release.

**A1 — Agent-native accounting.** An agent computing an April-based fiscal-month offset gets negative January–March values instead of 9–11, because integer arithmetic changes the numeric type used by the next operation.

## Live reproduction

2026-10-15, https://beancount.io/api-gateway/mcp, synthetic open_ledger/crypto-example, designated unpinned QA API key (ledger.read/write/admin). Last observed beancount-mcp 1.0.0, protocol 2025-11-25; deployed revision unavailable. No ledger writes.

Call runBqlQueryStructured using the root .env:

```json
{"ledger": "open_ledger/crypto-example", "query": "SELECT DISTINCT MONTH(date) AS calendar_month, (MONTH(date) - 4) % 12 AS fiscal_month_offset ORDER BY calendar_month"}
```

Two fresh MCP/REST requests return 12 rows: January/February/March offsets -3/-2/-1, then April–December 0–8. Expected January–March 9/10/11 and April–December 0–8. GraphQL queryShell returns the same wrong table. All 12 months are present in the complete synthetic journal.

Adding INT around the subtraction, INT(MONTH(date)-4)%12, produces the expected twelve offsets on MCP/REST/GraphQL. This is a working control, not a proposed query rewrite.

Operator isolation:

```sql
SELECT (INT(1) - INT(4)) % INT(12) AS subtraction,
       (INT(-3) + INT(0)) % INT(12) AS addition,
       (INT(-3) * INT(1)) % INT(12) AS multiplication,
       INT(-3) % INT(12) AS integer_control,
       DECIMAL(-3) % INT(12) AS decimal_control LIMIT 1
```

Live MCP/REST/GraphQL return -3/-3/-3/9/-3. Official Beanquery returns 9/9/9/9/-3. Direct integer modulo is already correct, and Decimal remainder intentionally differs. Remainder controls with positive/negative divisors and explicit Decimal operands also agree between engines; the break occurs after integer arithmetic.

Minimal valid fixture:

```beancount
2026-01-01 open Assets:Bank:Business USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "Synthetic opening"
  Assets:Bank:Business 10 USD
  Equity:Opening -10 USD
```

The fiscal query on this identical fixture returns January / 9 in Beanquery 0.2.0, but January / -3 in installed @rustledger/wasm 0.24.0. The isolated operator SELECT has the same three wrong results natively. A separate valid 12-month fixture confirms all twelve rows, with no validation/query errors in WASM. These are actual intermediate-value semantics, not only displayed dtype labels.

## Root cause and repair direction

Tagged [operators.rs](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-query/src/executor/operators.rs), arithmetic_op around line 177, converts Integer/Integer operands into Decimal and always wraps the result as Value::Number. Add/Sub/Mul use that helper. The subsequent modulo_op selects floored integer modulo only for Integer/Integer; it correctly retains truncated remainder for Decimal operands. Promoting the previous integer result therefore routes the composed expression to the wrong rule. Inspected upstream main retains this path. Local ledger src/foundation/rustledger/engine.ts::queryLedgerFilesResultInProcess delegates to native execution; direct valid WASM fixtures remove adapters/cache as prerequisites.

After upstream publishes a compatible correction, adopt it with the ledger package manager and verify actual native computations plus eligible REST/GraphQL/MCP together. Integer-only addition/subtraction/multiplication must retain the integer behavior required by downstream operators, with safe overflow handling. Preserve mixed/explicit Decimal semantics and division's documented behavior. Do not reclassify every whole-valued Decimal as Integer, globally floor Decimal modulo, rewrite customer queries by adding INT, patch result cells, fork upstream or vendor unreleased bytes.

Acceptance: all twelve fiscal offsets match (month-4)%12 using integer arithmetic; all three composed operator controls return 9; direct integer and explicit Decimal remainder controls stay 9/-3. Native-backed tests exercise positive/negative results, mixed operands, zero/null and overflow behavior without introducing panics or weakening the existing range contract. Additional boundaries are acceptance work, not claimed live coverage. Most recent npm check and installed WASM were 0.24.0; no fixed commit identified.
