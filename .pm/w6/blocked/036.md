# Preserve BOOL string truthiness in BQL

**Severity:** minor · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 35–50m after a compatible upstream release.

**A1 — Agent-native accounting.** An agent checking whether string metadata is populated must get the standard BQL truth value, rather than reinterpret text as a boolean token or fail the query.

## Reproduction

Live 2026-10-15, https://beancount.io/api-gateway/mcp, synthetic open_ledger/freelancer-invoicing, designated unpinned QA API key (ledger.read/write/admin). Last observed beancount-mcp 1.0.0, protocol 2025-11-25; deployed revision unavailable. No ledger writes.

Call runBqlQueryStructured using the root .env:

```json
{"ledger": "open_ledger/freelancer-invoicing", "query": "SELECT BOOL('false') AS false_word, BOOL('0') AS zero_word, BOOL('true') AS true_word, BOOL('') AS empty_text, BOOL(0) AS zero_number, BOOL(-1) AS negative_number LIMIT 1"}
```

Two fresh MCP/REST queries and one GraphQL queryShell request return:

```json
[false,false,true,false,false,true]
```

Expected Beanquery-compatible values:

```json
[true,true,true,false,false,true]
```

The nonempty strings false and 0 are truthy; empty text and numeric zero are false. The native result instead interprets the string contents as boolean literals. Numeric negative and true-word controls work. An earlier broad cast query also verifies null propagation, INT(TRUE)=1, DECIMAL(FALSE)=0 and STR(FALSE)=FALSE; those are not defects.

Practical metadata reproduction: SELECT COUNT(*) AS labeled_postings WHERE BOOL(ENTRY_META('invoice')) fails on MCP/REST/GraphQL with BAD_USER_INPUT, `BOOL: cannot parse '2026-001' as boolean`. The explicit IS NOT NULL control succeeds on MCP/REST with 27 postings. The full journal independently contains 27 postings with six nonempty invoice IDs and 23 without invoice metadata; this truthiness query should count 27, not reject those strings. The literal false/0 cases were repeated; the metadata expression was exercised once per surface.

Minimal valid fixture:

```beancount
2026-01-01 open Assets:Bank:Business USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "Synthetic opening"
  invoice: "2026-001"
  Assets:Bank:Business 10 USD
  Equity:Opening -10 USD
```

The exact six-BOOL SELECT above returns the expected row on official Beanquery 0.2.0; installed @rustledger/wasm 0.24.0 Ledger.fromFiles(...).query(...) returns the erroneous row. The metadata presence query returns count 2 in Beanquery and the same native parse error in WASM. Both use the identical valid fixture, with no validation errors.

## Root cause and repair direction

[Beanquery bool_](https://github.com/beancount/beanquery/blob/master/beanquery/query_env.py) converts a non-null value using Python bool, so string truth depends on emptiness. The [tagged native util.rs](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-query/src/executor/functions/util.rs) value_to_bool around line 223 uppercases strings, maps a fixed TRUE/FALSE/YES/NO/1/0 token list, and errors on other text. Fresh upstream main retains that parser. The BOOL dispatch calls it directly. The valid native fixture removes adapters/cache as prerequisites; local ledger src/foundation/rustledger/engine.ts::queryLedgerFilesResultInProcess delegates to native execution.

After upstream publishes a compatible correction, adopt it with the ledger package manager and verify real native BOOL behavior plus eligible REST/GraphQL/MCP together. Empty strings must be false and all nonempty strings true; preserve boolean/numeric values and existing null propagation. This repair concerns BQL BOOL only: preserve the strict parsing of API boolean inputs and the authored types/contents of ledger metadata. Do not rewrite queries, normalize source strings, patch cells, change API schemas, fork upstream or vendor unreleased bytes.

Acceptance: exact false/0/true/empty/numeric controls match the reference, populated invoice-string predicates count the expected postings, null operands stay null, and ordinary nonempty text no longer causes a parse error. Add native-backed adapter regressions, with whitespace-only and mixed-case strings as extra controls; those additional strings were not live-verified here. Latest published and installed WASM checked this session were 0.24.0; no fixed commit identified.
