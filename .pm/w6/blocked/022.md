# Adopt upstream BQL JOURNAL date windows and opening summaries

**Severity:** major · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 45–60m after a published fixed WASM artifact.

**A1 — Agent-native accounting.** An agent requesting February's receivable journal gets January through June and a final zero instead of February's 13,700 USD closing receivables. Boundaries in an accepted BQL statement must constrain its accounting result.

## Reproduction and evidence

Live 2026-10-15, `https://beancount.io/api-gateway/mcp`, public documented synthetic `open_ledger/freelancer-invoicing`, designated unpinned API key with ledger.read/write/admin scopes. Last observed initialize: beancount-mcp 1.0.0, protocol 2025-11-25; deployed backend/engine SHA unavailable. No ledger mutations.

```json
{"tool":"runBqlQueryStructured","arguments":{"ledger":"open_ledger/freelancer-invoicing","query":"JOURNAL 'Assets:Receivable' FROM OPEN ON 2026-02-01 CLOSE ON 2026-03-01"}}
```

Fresh MCP calls both succeed with 13 rows dated January 9 through June 30, ending at an empty inventory (zero). Modern REST POST `/api-gateway/v1/ledgers/open_ledger/freelancer-invoicing/query` repeats the same 13 rows twice; GraphQL `queryShell` returns the identical table. This is shared engine behavior, not an MCP-only adapter defect. Unbounded JOURNAL legitimately returns these 13 rows.

The same date clauses in `SELECT date, account, number FROM OPEN ON 2026-02-01 CLOSE ON 2026-03-01 WHERE account ~ '^Assets:Receivable' ORDER BY date, account` return the four real February postings on MCP/REST, proving that dates and fixture records exist. This SELECT control still lacks opening summaries, another part of the same upstream correction; it is not a complete accounting workaround.

Official installed Beanquery 0.2.0 over a valid in-memory fixture reconstructed from the complete 23-transaction synthetic journal returns six JOURNAL rows: two January 31 S opening summaries totaling 15,500 USD, then February 5/6/11/20 changes, ending at 13,700 USD. No March–June activity belongs in this window. CLOSE ON is exclusive. This does not propose changing same-day endpoint semantics.

Minimal independent valid fixture: open Assets:Test and Equity:Opening on January 1; post +100/-100 USD on January 10, -40/+40 on February 10, -60/+60 on April 10. Installed WASM 0.24.0 returns all three original JOURNAL rows under February's bounds, ending zero; SELECT returns only February's -40. Beanquery instead returns January 31 S +100 and February 10 -40, ending 60. Both loaders report zero errors. No downloaded ledger workspace or production writes are needed.

## Root cause and bounded adoption

Tagged rustledger v0.24.0 `crates/rustledger-query/src/executor/execution.rs::execute_journal` loops over all resolved directives and checks only `from.filter`; it ignores the FROM open/close fields. SELECT has a separate date path and drops pre-open rows without summarizing their balances.

Upstream already corrected both in [1324bc25529870ab529252601548916bbf6a9ca8 / PR 2410](https://github.com/rustledger/rustledger/commit/1324bc25529870ab529252601548916bbf6a9ca8): JOURNAL and SELECT share `window_transactions`, applying OPEN summaries and the [open, close) transaction window. See also [upstream issue 2401](https://github.com/rustledger/rustledger/issues/2401). This finding requests adoption, not a fork or parser/engine reimplementation.

Once published, upgrade the owning ledger package's existing WASM dependency with its package manager, retaining generated lockfile discipline. Verify actual installed WASM behavior for JOURNAL, SELECT and BALANCES: pre-open summaries, in-window changes, post-close exclusion, final balances, no-bound controls and reversed-date refusal. Keep result shapes and credential policy; validate eligible REST/GraphQL/MCP together through backend-v2 query adapters. Coordinate one engine upgrade with blocked 016/017/018; do not duplicate their PRINT, date-subtraction or MIN/MAX fixes. Native total-cost, lots and renamed-root behaviors in the larger upstream change require focused package checks rather than claims based on this USD fixture alone.
