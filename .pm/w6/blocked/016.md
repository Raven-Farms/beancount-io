# Adopt corrected PRINT filtering and cost-preserving rendering

**Severity:** major. **Owner:** ledger. **Estimate:** 45–60 minutes for downstream adoption/verification once a fixed artifact is released. **Status:** blocked on the upstream WASM release. **A1 — Agent-native accounting:** query reads must honor their predicate and preserve the accounting meaning of the directives they render. Both demonstrated PRINT faults are corrected by the same existing upstream commit.

## Live reproduction

Production `https://beancount.io`, 2026-10-15; local main `81cf96c9`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed backend/engine SHA unavailable. The local ledger dependency is `@rustledger/wasm` 0.24.0. Existing designated unpinned QA API key, scopes `ledger.read ledger.write ledger.admin`; public synthetic `open_ledger/example` only.

Call `runBqlQueryStructured`:

```json
{"ledger":"open_ledger/example","query":"PRINT FROM FALSE"}
```

The successful result has **1,000 rows and `truncated: true`**, beginning with `1792-01-01 commodity USD`. REST query and GraphQL queryShell return the full **1,007 directives** for exactly the same statement. A fresh MCP/REST repeat has the same result. The MCP text tool correctly reports 1,007 output rows; this is incorrect predicate evaluation, not a row-count/cap defect.

The full results are exactly all the fixture's non-transaction directives: 10 commodities, 60 opens, 82 balance assertions, nine events and 846 prices. The same 1,007 rows appear for `PRINT FROM type = 'balance'`, although only 82 are balance assertions. All 82 asserted amounts still match the source; the problem is the extra rows, not corrupted assertion values.

Working controls: `SELECT account WHERE FALSE` returns zero rows through MCP and REST. A local **in-memory** Beanquery 0.2.0 control, with a valid five-directive synthetic ledger, returns zero rows for `PRINT FROM FALSE` and only its one Balance for lowercase `type = 'balance'`. Uppercase `type = 'Balance'` returns zero in that control; the initial uppercase probe was not used to establish the expected lowercase result. No hosted-to-local workspace or export workflow was created.

Exact helper:

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file .env call runBqlQueryStructured '{"ledger":"open_ledger/example","query":"PRINT FROM FALSE"}'
```

REST: `POST /api-gateway/v1/ledgers/open_ledger/example/query`, body `{"query":"PRINT FROM FALSE"}`. GraphQL: `queryShell(ledgerId: "open_ledger/example", query: "PRINT FROM FALSE") { resultType table { types { name dtype } rows t } }`.

## Additional rendering failure covered by the same upstream fix

Observed 2026-10-15 at local main `a61ba7cb`, on the same production server/protocol; deployed SHA remains unavailable. On public synthetic `open_ledger/crypto-example`, run:

```sql
PRINT FROM narration = 'Withdraw 0.10 BTC to Ledger hardware wallet'
```

The selected June-30-2025 transaction is present in the MCP result, its fresh repeat, REST and GraphQL. All four captured results render the same six posting accounts and unit amounts, but **omit all four cost specifications**. Source context from `getEntryContext` with canonical hash `65b355ebf0df80511b76e130294ffe6f` retains four structured costs and the original slice. For example, the source's `-0.08 BTC {94,384.59 USD, 2025-04-30}` becomes `-0.08 BTC`; its `-0.02 BTC {105,000.00 USD, 2025-05-31}` likewise loses the cost and date. The destination postings lose the corresponding two costs too.

This is loss of lot cost/acquisition information, not whitespace normalization. The source entries and previously verified account balances are unchanged; only PRINT's returned directive representation is shown to be lossy. No downstream rewrite or valuation from the damaged representation was performed. The unrelated-directive predicate fault also remains in this query; the target transaction itself was isolated from the result for the comparison.

## Root cause and existing upstream fix

The pinned [Rustledger v0.24.0 PRINT executor](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-query/src/executor/execution.rs#L1199) evaluates the FROM filter only inside its Transaction branch. Every other directive bypasses that predicate and is formatted into the result. LedgerShellService delegates to this engine; REST, GraphQL and MCP share the same producer, explaining their identical underlying content. The structured tool's separate 1,000-row cap is working.

Its adjacent `format_directive` transaction branch emits posting accounts and unit amounts without the posting's cost fields, explaining the second case. Both operations are replaced by the upstream correction below, so the downstream work remains one release adoption with acceptance for both observed failures, not a duplicate engine implementation task.

Upstream already corrected this in [3ad34e07 / PR 2530](https://github.com/rustledger/rustledger/commit/3ad34e07cd36fb1ef5e6dfb1c6f87a8e69cefa6a): PRINT filters each entry using its entries-table row and the canonical formatter. The current upstream main source was inspected and retains that correction. The [Beanquery PRINT compiler](https://github.com/beancount/beanquery/blob/master/beanquery/compiler.py) likewise binds the FROM expression to the entries table, matching the local control. The official [BQL PRINT documentation](https://beancount.github.io/docs/beancount_query_language/#print) describes printing the filtered entry stream.

At this observation, both the [latest npm WASM package](https://www.npmjs.com/package/@rustledger/wasm) and the GitHub latest release endpoint identify 0.24.0, whose tagged implementation is affected. This is a known upstream correction awaiting a published dependency artifact, not a request to reimplement its parser or filter in the adapter. No fresh upstream issue or comment was posted.

## Blocked / Unblock

**Blocked by:** the upstream release publisher; the checked latest published WASM package does not contain the corrected PRINT executor.

**Unblock:** publish a supported `@rustledger/wasm` artifact containing 3ad34e07 or equivalent all-entry predicate and cost-preserving PRINT fixes. Then the repository worker updates the existing ledger dependency with the owning package's Yarn command, regenerates its lockfile, and verifies the artifact actually passes the controls below. An upstream main commit alone does not clear this release condition. Preserve the GPL boundary and do not vendor engine bytes or introduce a second BQL parser. Coordinate the version adoption with other engine-blocked findings, including w3/blocked/113, without claiming they are fixed by the same commit. A fresh npm latest check during the cost-rendering controls still reported 0.24.0.

Acceptance after unblock: real WASM cases for PRINT FROM FALSE (no rows), lowercase Balance-only selection, date and has_account entry predicates, ordinary transaction selection, and unfiltered PRINT. Include a cost-bearing transfer and verify that rendered postings retain each cost's amount, currency and acquisition date as well as their unit amounts. Assert actual directive kinds/content, not just status or count. Preserve canonical row counts and the structured cap. Run ledger tests/lint/typecheck/build and engine verification, plus backend query-adapter parity checks for REST/GraphQL/MCP. Recheck the hosted endpoint after its deployment separately; no weakening or bypassing of parity gates.
