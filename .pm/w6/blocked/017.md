# Adopt upstream BQL date subtraction support

**Severity:** minor. **Owner:** ledger. **Estimate:** 35–50 minutes after release. **Status:** blocked on the upstream WASM release. **A1 — Agent-native accounting:** invoice-aging queries written with ordinary Beanquery date subtraction should execute through the remote query surfaces.

## Live reproduction

Production `https://beancount.io`, 2026-10-15; local main `4ba36029`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed backend/engine SHA unavailable. Existing designated unpinned QA API key with scopes `ledger.read ledger.write ledger.admin`. Only the public synthetic `open_ledger/freelancer-invoicing` example was read; its README identifies fictional example clients.

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file .env call runBqlQueryStructured '{"ledger":"open_ledger/freelancer-invoicing","query":"SELECT 2026-02-08 - 2026-01-09 AS days LIMIT 1"}'
```

Actual, including a fresh MCP repeat: `isError: true`, `BAD_USER_INPUT`, `Invalid BQL query: Query execution error: type error: arithmetic requires numeric values`. The equivalent REST query returns HTTP 400 with that message. GraphQL `queryShell` returns the same error. Expected: one integer cell **30**, as in the independent Beanquery 0.2.0 control.

REST: `POST /api-gateway/v1/ledgers/open_ledger/freelancer-invoicing/query`, body `{"query":"SELECT 2026-02-08 - 2026-01-09 AS days LIMIT 1"}`. GraphQL: `queryShell(ledgerId: "open_ledger/freelancer-invoicing", query: "SELECT 2026-02-08 - 2026-01-09 AS days LIMIT 1") { resultType table { types { name dtype } rows t } }`.

The practical invoice query also fails when projecting `ENTRY_META('due') - date`. The metadata itself is intact: projecting `ENTRY_META('due')` returns all six invoice due dates, and replacing subtraction with `DATE_DIFF(ENTRY_META('due'), date)` returns six **30-day** terms through MCP and REST. Independently rebuilding terms from the 23-transaction journal with Python calendar subtraction gives the same six dates and values. Grouping receivable postings by invoice also matches the independently summed journal balances, all six zero after payment/write-off. This is an operator compatibility gap, not lost metadata or incorrect receivable balances.

A valid, entirely in-memory synthetic Beanquery fixture independently returns 30 for both literal date subtraction and `ENTRY_META('due') - date`; the latter has two posting rows, correctly both 30. `DATE_DIFF` likewise returns 30. No hosted ledger was written or exported into a workspace. Initial `META('due')` probes addressed posting metadata and returned no matches; transaction metadata requires `ENTRY_META`, so those initial results are caller errors and do not establish a defect.

## Root cause and existing upstream correction

The local dependency is pinned to `@rustledger/wasm` 0.24.0. Its [operator implementation](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-query/src/executor/operators.rs) reaches the numeric-only arithmetic fallback for Date minus Date. The ledger query service delegates to that engine; the shared producer explains matching failures across REST, GraphQL and MCP. The deployed engine version itself was not observable.

Upstream already fixes these operators in [6972f5ed / PR 2331](https://github.com/rustledger/rustledger/commit/6972f5edd15be5847f22f30b2511b8775a152f13). Its inspected patch implements Date minus Date using the DATE_DIFF rule, and adds date/day-count operators and regression cases. It also intentionally changes fractional `date_add` behavior; downstream adoption must review those release notes rather than treating an upgrade as behavior-free. Only date subtraction was demonstrated failing live here; the other operators are not additional verified findings.

The [latest published npm WASM package](https://www.npmjs.com/package/@rustledger/wasm) still reports 0.24.0 at this check. Current upstream main contains the correction, but no supported fixed artifact was identified on the checked latest channel. Do not implement a second BQL parser or rewrite query strings as a workaround. Users can currently write `DATE_DIFF` explicitly.

## Blocked / Unblock

**Blocked 2026-10-15** — the upstream release publisher has not provided the corrected artifact on the checked latest WASM channel.

**Unblock:** a supported published `@rustledger/wasm` artifact containing 6972f5ed or equivalent date subtraction support. Then a repository worker updates the existing ledger dependency through its owning package manager, regenerates the lockfile, and verifies the actual artifact. Coordinate the dependency adoption with [016](./016.md), which needs a different upstream PRINT fix; neither commit proves the other's behavior. Preserve the GPL boundary and do not vendor upstream engine source. No new upstream issue or comment was posted.

Acceptance after unblock: actual WASM tests for literal and metadata date subtraction, equal and reversed dates, a leap-day boundary, and the working DATE_DIFF control. Verify typed integer results, expected negative differences, and invalid mixed operands remaining errors. Review date_add compatibility changes; run ledger native checks and backend query-adapter parity checks, then separately recheck the hosted deployment. Keep parity gates intact.
