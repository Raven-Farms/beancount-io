# Adopt upstream posting-column FROM filtering in BQL

**Severity:** major · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 35–50m after a published fixed WASM artifact.

**A1 — Agent-native accounting.** A valid income query can report an empty result instead of six actual income postings because the predicate is tested against another posting. An agent should get the same posting selection from equivalent FROM and WHERE forms.

## Live evidence

2026-10-15, `https://beancount.io/api-gateway/mcp`, documented synthetic `open_ledger/freelancer-invoicing`, designated unpinned API key (ledger.read/write/admin). Last observed initialization: beancount-mcp 1.0.0, protocol 2025-11-25; deployed backend/engine SHA unknown. No production writes.

Call `runBqlQueryStructured` with these arguments using the QA helper and root `.env`:

```json
{"ledger":"open_ledger/freelancer-invoicing","query":"SELECT date, account, number FROM account ~ '^Income:' ORDER BY date, account"}
```

MCP returns success with zero rows twice. Modern REST POST `/api-gateway/v1/ledgers/open_ledger/freelancer-invoicing/query` returns the same empty table twice; GraphQL `queryShell` also returns that table. Replace FROM with WHERE: MCP/REST return six rows, January 9/23, February 6/11, April 10/30, with income amounts -6000, -9500, -6000, -3200, -4000 and -792.40 USD. The complete 23-transaction journal independently contains these six income postings. They are not the first posting in their transactions.

Independent minimal fixture: open Assets:Test and Equity:Opening, then three balanced transactions, each with Assets:Test first and Equity:Opening second, units +100/-100, -40/+40, -60/+60 USD. Official Beanquery 0.2.0 with `SELECT date, account, number FROM account ~ '^Equity:' ORDER BY date, account` returns the three equity postings. Installed WASM 0.24.0 accepts the same valid fixture with zero errors but returns zero FROM rows; changing FROM to WHERE returns three. This isolates posting selection from adapters, fixture business rules and date-window behavior.

## Root cause and adoption

Tagged engine `crates/rustledger-query/src/executor/evaluation.rs::evaluate_from_filter` evaluates a generic FROM predicate using `PostingContext` with `posting_index: 0`; the executor then keeps or drops the whole transaction. A predicate on account therefore observes only its first posting. `has_account()` is deliberately a whole-transaction predicate and must keep its current semantics.

Upstream [a2d984d6f96cc438c2c3dea9c12acb3482dd6d6d / PR 2523](https://github.com/rustledger/rustledger/commit/a2d984d6f96cc438c2c3dea9c12acb3482dd6d6d) fixes this: posting-column FROM expressions filter posting rows and combine with WHERE using AND in SELECT, BALANCES and JOURNAL; entry predicates retain whole-transaction behavior. It also rejects posting-column predicates in PRINT, which has no posting rows. Only SELECT's false-empty outcome was reproduced live here; do not claim all upstream follow-up cases were verified on the hosted endpoint.

After a release, upgrade the existing ledger-owned WASM dependency with its package manager. Add actual WASM regression coverage for both first and later posting matches, equivalent FROM/WHERE results and their intersection, plus a has_account whole-entry control. Verify the eligible REST, GraphQL and MCP adapters against those results; preserve existing result envelopes and credential policy. Run owning package checks and coordinate the artifact upgrade with blocked 016/017/018/022. Do not fork, vendor unreleased WASM, recreate an evaluator, or document valid queries as unsupported to hide the bug.
