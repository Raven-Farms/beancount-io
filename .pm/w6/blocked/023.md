# Adopt correct FROM predicate evaluation in BQL

**Severity:** major · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 45–60m after a published fixed WASM artifact.

**A1 — Agent-native accounting.** A valid income query can report an empty result instead of six actual income postings because the predicate is tested against another posting. An agent should get the same posting selection from equivalent FROM and WHERE forms.

## Live evidence

2026-10-15, `https://beancount.io/api-gateway/mcp`, documented synthetic `open_ledger/freelancer-invoicing`, designated unpinned API key (ledger.read/write/admin). Last observed initialization: beancount-mcp 1.0.0, protocol 2025-11-25; deployed backend/engine SHA unknown. No production writes.

Call `runBqlQueryStructured` with these arguments using the QA helper and root `.env`:

```json
{"ledger":"open_ledger/freelancer-invoicing","query":"SELECT date, account, number FROM account ~ '^Income:' ORDER BY date, account"}
```

MCP returns success with zero rows twice. Modern REST POST `/api-gateway/v1/ledgers/open_ledger/freelancer-invoicing/query` returns the same empty table twice; GraphQL `queryShell` also returns that table. Replace FROM with WHERE: MCP/REST return six rows, January 9/23, February 6/11, April 10/30, with income amounts -6000, -9500, -6000, -3200, -4000 and -792.40 USD. The complete 23-transaction journal independently contains these six income postings. They are not the first posting in their transactions.

Independent minimal fixture: open Assets:Test and Equity:Opening, then three balanced transactions, each with Assets:Test first and Equity:Opening second, units +100/-100, -40/+40, -60/+60 USD. Official Beanquery 0.2.0 with `SELECT date, account, number FROM account ~ '^Equity:' ORDER BY date, account` returns the three equity postings. Installed WASM 0.24.0 accepts the same valid fixture with zero errors but returns zero FROM rows; changing FROM to WHERE returns three. This isolates posting selection from adapters, fixture business rules and date-window behavior.

## Root cause and adoption

Tagged engine `crates/rustledger-query/src/executor/evaluation.rs::evaluate_from_filter` evaluates a generic FROM predicate using `PostingContext` with `posting_index: 0`; the executor then keeps or drops the whole transaction. A predicate on account therefore observes only its first posting. `has_account()` is deliberately a whole-transaction predicate and must keep its current semantics.

Upstream [a2d984d6f96cc438c2c3dea9c12acb3482dd6d6d / PR 2523](https://github.com/rustledger/rustledger/commit/a2d984d6f96cc438c2c3dea9c12acb3482dd6d6d) fixes this: posting-column FROM expressions filter posting rows and combine with WHERE using AND in SELECT, BALANCES and JOURNAL; entry predicates retain whole-transaction behavior. It also rejects posting-column predicates in PRINT, which has no posting rows. The initial reproduction covers SELECT's false-empty outcome; verified year/month comparisons are recorded below. Other upstream follow-up cases remain unverified on the hosted endpoint.

After a release, upgrade the existing ledger-owned WASM dependency with its package manager. Add actual WASM regression coverage for both first and later posting matches, equivalent FROM/WHERE results and their intersection, plus a has_account whole-entry control. Verify the eligible REST, GraphQL and MCP adapters against those results; preserve existing result envelopes and credential policy. Run owning package checks and coordinate the artifact upgrade with blocked 016/017/018/022. Do not fork, vendor unreleased WASM, recreate an evaluator, or document valid queries as unsupported to hide the bug.

## Additional verified year/month comparison defect — 2026-10-15

The same evaluator and upstream adoption also own transaction-level comparisons. On synthetic `open_ledger/crypto-example`, `SELECT COUNT(*) FROM year > 2026` succeeds with **174**, twice on MCP and REST; equivalent WHERE returns **0**. `SELECT COUNT(*) FROM month < 2` succeeds with **276**, twice on MCP and REST; equivalent WHERE returns **13**. GraphQL queryShell reproduces both wrong FROM counts. The complete 105-transaction/304-posting journal independently contains no posting after 2026, 174 postings outside 2026, 13 January postings and 276 postings outside February. Thus the wrong counts exactly match `year != 2026` and `month != 2`.

Tagged `evaluate_from_filter` has special YEAR/MONTH arms: it calculates equality, returns that for `Eq`, and returns its negation for every other binary operator. DATE has a proper operator match. A live `SELECT COUNT(*) FROM date > 2026-12-31` control returns 0 on MCP/REST, as the complete journal requires. Only year `>` and month `<` were reproduced live here; other comparison operators need regression coverage, not unverified hosted claims. The already-linked a2d984d6 commit explicitly corrects these special arms as part of its FROM-evaluation fix.

On the same valid three-transaction minimal fixture above, installed WASM returns COUNT 6 for `FROM year > 2027` and COUNT 4 for `FROM month < 2`; official Beanquery instead has no future-year matches and counts the two January postings. Beanquery emits no aggregate row for a completely empty stream, unlike rustledger's COUNT 0; that established empty-aggregate convention is not this defect.

Extend the adoption checks to YEAR and MONTH `<`, `<=`, `=`, `!=`, `>=`, `>` against independently known dates, with matching WHERE controls and one DATE comparison control. Keep entry predicates selecting whole transactions. This is additional evidence for the same dependency-adoption item, not a second board note or a second count for the finding. The 45–60m estimate includes these focused native/adapter checks once the fixed artifact exists.

Additional ignored evidence: oct15-from-comparison-{from-year,where-year,from-month,where-month}, fresh repeat-year/month MCP/REST files, GraphQL from-comparison, and official Python/native WASM controls. No engine changes or upstream messages were made.
