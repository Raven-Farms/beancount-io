# Restore authored BQL source locations through the WASM query binding

**Severity:** minor · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 45–60m after upstream supplies a source-aware published query binding.

**A1 — Agent-native accounting.** A query cannot point an agent to the source file/line of an authored invoice, and adding the known source filename as a filter incorrectly hides that posting.

## Reproduction

Live 2026-10-15, `https://beancount.io/api-gateway/mcp`, documented synthetic `open_ledger/freelancer-invoicing`, designated unpinned QA API key (ledger.read/write/admin). Last observed server beancount-mcp 1.0.0, protocol 2025-11-25; deployed backend/engine revision unavailable. No ledger writes.

Call runBqlQueryStructured with the root `.env`:

```json
{"ledger": "open_ledger/freelancer-invoicing", "query": "SELECT date, account, filename, lineno WHERE date = 2026-01-23 AND account = 'Assets:Receivable:Contoso'"}
```

Two fresh MCP/REST queries succeed with one row: 2026-01-23 / Assets:Receivable:Contoso / empty string / empty string. GraphQL queryShell returns the identical table. The native values are null; the existing wire mapper's empty-string rendering is not the root cause.

Working source control: fresh getEntryContext for canonical hash `36e509162b1eb84dad9efec92f1528f7` returns file `transactions/invoicing.bean`, transaction header line 16 and its source slice. readLedgerFiles lines 16–24 shows that header, invoice/due metadata, and the actual receivable posting at **line 19**. BQL posting lineno should identify the posting's line; it must not simply copy the transaction header's 16. The filename and source are present in the ledger and are readable.

Adding `AND filename ~ 'invoicing'` to the query returns zero rows on MCP/REST/GraphQL, although the unfiltered one-row result is known to come from that file. This is ordinary source-based selection, not a credential or parser refusal. Only the base missing-location query was repeated; the derived filename filter was verified once per surface.

Independent valid native fixture: main.bean opens Assets:Test and Equity:Opening and includes txns.bean; the child file has one balanced transaction with postings on lines 2/3. Ledger.fromFiles(...).query('SELECT account, filename, lineno ORDER BY account') returns both accounts with null filename/lineno and no errors. Official Beanquery on an equivalent single-source in-memory fixture returns a nonempty `<string>` filename and correct posting lines 4/5 after the two Opens. The Python control is not claimed to resolve the two-file virtual include map. No hosted ledger workspace was exported.

## Root cause and external requirement

The repository's ledger-shell-service.ts loads the file map and entry point and passes them through engine.ts::queryLedgerFilesResultInProcess to the published Ledger.fromFiles(...).query(...). A valid direct native reproduction removes the adapters, worker pool and cache as prerequisites for the missing data.

Tagged [WASM parsed_ledger.rs at v0.24.0](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-wasm/src/parsed_ledger.rs) stores booked plain directives, options, errors and an editor cache in Ledger; execute_query expands padding then constructs Executor::new(&expanded), with no SourceMap. The same binding shape was still present in inspected upstream main. The core query executor has a [source-aware constructor](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-query/src/executor/mod.rs) and source-column evaluation that require that mapping. Without it, authored posting spans cannot resolve to filename/line. No public TypeScript query argument currently supplies the missing map.

This requires upstream to retain/wire source locations through the WASM query path, rather than a local cell formatter change. After a compatible artifact is published, adopt it with the ledger package manager and verify actual native included-file locations, posting-versus-header line semantics, fresh/cached behavior and filename predicates. Validate eligible REST/GraphQL/MCP queries together while preserving their envelopes and existing missing-value rendering. Keep true generated entries source-less. Do not reconstruct origins with a second parser, patch query strings, fill cells from guessed transaction headers, vendor unreleased bytes or fork the engine. Existing canonical entry-context/file reads are working controls, not a reason to replace BQL's source columns with a new endpoint.
