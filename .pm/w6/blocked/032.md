# Preserve calendar DATE_BIN origins and boundaries

**Severity:** minor · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 45–60m after a compatible upstream release.

**A1 — Agent-native accounting.** Calendar-month/year bins must preserve the requested origin and contain the source date, including month-end and leap-day origins. Incorrect boundaries silently change the requested grouping.

## Reproduction

Live 2026-10-15, https://beancount.io/api-gateway/mcp, synthetic open_ledger/crypto-example, designated unpinned QA API key (ledger.read/write/admin). Last observed beancount-mcp 1.0.0, protocol 2025-11-25; deployed revision unavailable. Literal-date queries only; no ledger writes.

Call runBqlQueryStructured using the root .env:

```json
{"ledger": "open_ledger/crypto-example", "query": "SELECT DATE_BIN('1 month', 2026-02-15, 2026-01-31) AS before_feb_boundary, DATE_BIN('1 month', 2026-03-15, 2026-01-31) AS before_mar_boundary, DATE_BIN('1 month', 2026-02-15, 2026-01-01) AS first_day_control, DATE_BIN('1 month', 2026-01-31, 2026-01-31) AS origin_control LIMIT 1"}
```

Two fresh MCP and modern REST query requests return:

```json
["2026-02-01","2026-03-01","2026-02-01","2026-01-01"]
```

GraphQL queryShell returns the identical table once. Expected Beanquery-compatible results:

```json
["2026-01-31","2026-02-28","2026-02-01","2026-01-31"]
```

The first-day origin control agrees. The source-equals-origin case should preserve January31, but returns January1. The other cases show that dates before the next anchored boundary are assigned to calendar-month starts instead. All sources are at/after origin; this is not the negative-offset division bug.

Official Beanquery 0.2.0 on this valid in-memory fixture gives the expected row; installed @rustledger/wasm 0.24.0 Ledger.fromFiles(...).query(...) gives the live erroneous row with no validation/query errors:

```beancount
2026-01-01 open Assets:Bank:Business USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "Synthetic opening"
  Assets:Bank:Business 10 USD
  Equity:Opening -10 USD
```

[Beanquery date_bin](https://github.com/beancount/beanquery/blob/master/beanquery/query_env.py) supports month strides and aligns them by stepping from the specified origin. Its month-end clamping accounts for January31 to February28. The source-equals-origin case alone proves origin loss, without relying on ambiguous rounding or exact later-boundary policy.

## Year boundaries and leap-day origins

The same calendar-stride investigation now also covers year bins. Live 2026-10-15 on the same synthetic ledger, call runBqlQueryStructured with:

```json
{"ledger": "open_ledger/crypto-example", "query": "SELECT DATE_BIN('1 year', 2026-01-01, 2025-06-15) AS before_anniversary, DATE_BIN('1 year', 2026-07-01, 2025-06-15) AS after_anniversary, DATE_BIN('1 year', 2025-06-15, 2025-06-15) AS origin_control, DATE_BIN('1 year', 2025-03-01, 2024-02-29) AS leap_origin_next_year, DATE_BIN('1 year', 2024-02-29, 2024-02-29) AS leap_origin_control LIMIT 1"}
```

Two fresh MCP/REST queries and one GraphQL queryShell return:

```json
["2026-06-15","2026-06-15","2025-06-15","2024-02-29","2024-02-29"]
```

Expected Beanquery-compatible results:

```json
["2025-06-15","2026-06-15","2025-06-15","2025-02-28","2024-02-29"]
```

The January 2026 source is assigned a future June 2026 start rather than the June 2025 bin that contains it. The March 2025 source with a February 29, 2024 origin falls back to the original year instead of advancing to February 28, 2025. After-anniversary and both exact-origin controls work. All inputs are at/after their origins, independently separating this from w6/031's negative fixed-day offset division.

On the existing valid minimal fixture above, official Beanquery 0.2.0 returns the expected row and installed WASM 0.24.0 the erroneous row, with no fixture validation errors. Fresh main date.rs still computes years_diff using year fields alone and constructs the origin's original month/day in that year, falling back to origin if the resulting date is invalid. The yearly path therefore also needs correct boundary selection and calendar clamping, not merely retaining month/day. These cases extend the existing calendar-origin adoption record; no new ticket is created.

## Root cause and external requirement

The [v0.24.0 date executor](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-query/src/executor/functions/date.rs) month arm (around line426) computes a bucket using year/month differences and constructs naive_date(year, month, 1), discarding the origin day. Fresh upstream main still constructs day1. This is different from truncating negative fixed-day offsets in w6/031. The direct valid native fixture removes adapters/cache as prerequisites; local ledger src/foundation/rustledger/engine.ts::queryLedgerFilesResultInProcess delegates to that engine.

After upstream publishes a compatible origin-preserving month/year-bin implementation, adopt it with the ledger package manager and verify actual native results and eligible REST/GraphQL/MCP together. Preserve the specified origin and apply calendar-month stepping/clamping consistently with the reference behavior. Do not approximate months by a fixed number of days, merely replace day1 with the origin day without handling shorter months, rewrite user queries, patch result cells, fork upstream or vendor unreleased bytes.

Acceptance: source==origin retains January31; the February15/March15 cases above match the reference, while a January1 origin still gives February1. Add real-native controls for leap/non-leap month ends, day15 origins, multi-month strides and before/at/after actual boundaries; compare reference behavior before choosing an exact-boundary convention. The five year-bin cases above must also match their expected row. API dates and envelopes remain stable. Year-origin/boundary cases are independently verified above. Quarter strides, pre-origin calendar bins, grouped totals and exact later-boundary conventions remain unverified. Latest npm and installed WASM this session were0.24.0; no fixed commit or published repair identified.
