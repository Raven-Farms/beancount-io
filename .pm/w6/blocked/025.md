# Adopt upstream quoted BQL column resolution

**Severity:** major · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 45–60m after a published fixed WASM artifact.

**A1 — Agent-native accounting.** A successful valid BQL projection can return the text `account` and `number` instead of an account name and amount. A caller must receive the selected column values rather than silently fabricated constants.

## Live reproduction

2026-10-15, `https://beancount.io/api-gateway/mcp`; last observed server beancount-mcp 1.0.0, protocol 2025-11-25. Dedicated unpinned QA API key with ledger.read/write/admin scopes, documented synthetic `open_ledger/freelancer-invoicing`. Deployed backend/engine SHA unknown; no ledger writes.

Using the root `.env`, call runBqlQueryStructured with:

```json
{"ledger": "open_ledger/freelancer-invoicing", "query": "SELECT \"account\" AS quoted_account, account AS plain_account, \"number\" AS quoted_number, number AS plain_number LIMIT 3"}
```

The intended JSON query contains ordinary double quotes around account/number. Both fresh MCP requests return success, with rows:

- account / Assets:Bank:Business / number / 12000.00
- account / Assets:Bank:TaxReserve / number / 4500.00
- account / Equity:Opening / number / -16500.00

The first and third fields are literal strings, not the selected account and numeric value. Modern REST POST `/api-gateway/v1/ledgers/open_ledger/freelancer-invoicing/query` repeats the exact wrong table twice; GraphQL queryShell returns the same table. Unquoted columns in the same request are working controls. `SELECT 'account' AS literal_account, 'number' AS literal_number LIMIT 3` correctly returns string literals on MCP/REST and must keep doing so.

Official installed Beanquery 0.2.0 over an independent valid in-memory fixture resolves the double-quoted names as columns: each quoted value equals its unquoted partner, including numeric values. On that same fixture, installed WASM 0.24.0 instead returns account/Assets:A/number/10, account/Assets:B/number/20, account/Assets:C/number/30. Both loaders report zero errors. The fixture has three asset accounts and equity, one balanced transaction +10/+20/+30/-60 USD. The failure is not a query alias or data fixture issue.

## Root cause and bounded adoption

Tagged `crates/rustledger-query/src/executor/evaluation.rs::evaluate_literal` turns a string literal into Value::String without the column-name resolution stage Beanquery performs. Pinned execution does not resolve double-quoted strings naming columns before evaluating the projection.

Upstream [9d3bde866fe59e18e5eb3df6971ba9d26871fac5 / PR 2610](https://github.com/rustledger/rustledger/commit/9d3bde866fe59e18e5eb3df6971ba9d26871fac5) already adds the resolution rule against the active input columns, retaining the source header. It covers multiple clauses and sources; only the SELECT projection is live-proven here. It deliberately preserves JOURNAL's quoted account argument as a pattern, a documented exception that this note must not turn into another bug. No parser fork or adapter query-text rewriting is requested.

After publication, upgrade the ledger-owned existing WASM dependency with the package manager. Verify actual WASM quoted versus unquoted column values, numeric projections/aliases, single-quoted string controls and one non-column double-quoted literal control. Include a focused quoted WHERE/order control and preserve the JOURNAL pattern exception using the adopted engine's documented behavior. Validate eligible REST/GraphQL/MCP query adapters with exact values and existing envelopes, then run owning package checks. Coordinate one artifact upgrade with blocked 016/017/018/022/023/024.
