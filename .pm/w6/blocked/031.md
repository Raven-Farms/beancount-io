# Adopt floor-based DATE_BIN arithmetic before the origin

**Severity:** minor · **Package:** ledger, with backend-v2 parity validation · **Estimate:** 35–50m after a compatible upstream release.

**A1 — Agent-native accounting.** An agent grouping historical postings into weekly bins can receive a bucket start later than the posting date, shifting activity into the wrong interval.

## Reproduction

Live 2026-10-15, https://beancount.io/api-gateway/mcp, synthetic open_ledger/crypto-example, designated unpinned QA API key (ledger.read/write/admin). Last observed beancount-mcp 1.0.0, protocol 2025-11-25; deployed revision unavailable. No ledger writes. This literal-date query does not rely on market quotes or fixture-specific positions.

Call runBqlQueryStructured using the root .env:

```json
{"ledger": "open_ledger/crypto-example", "query": "SELECT DATE_BIN('7 days', 2026-01-01, 2026-01-05) AS four_days_before, DATE_BIN('7 days', 2026-01-04, 2026-01-05) AS one_day_before, DATE_BIN('7 days', 2025-12-28, 2026-01-05) AS eight_days_before, DATE_BIN('7 days', 2025-12-29, 2026-01-05) AS previous_exact_bin, DATE_BIN('7 days', 2026-01-12, 2026-01-05) AS next_exact_bin LIMIT 1"}
```

MCP/REST/GraphQL return one successful row:

```json
["2026-01-05","2026-01-05","2025-12-29","2025-12-29","2026-01-12"]
```

Expected:

```json
["2025-12-29","2025-12-29","2025-12-22","2025-12-29","2026-01-12"]
```

An initial fresh MCP/REST query separately reproduces the January1 case and includes working at-origin/next-bin controls. The expanded query repeats it and verifies one/eight days before origin plus exact previous/next boundaries. For a positive seven-day stride, the bin start must be no later than the source and source must precede bin+7days. The first two actual results violate that containment invariant; the eight-day case is one bin too late. Exact negative/positive multiples work.

Independent integer-day floor arithmetic gives the expected row. Official Beanquery 0.2.0 over this valid minimal in-memory fixture returns that same expected row; installed @rustledger/wasm 0.24.0 Ledger.fromFiles(...).query(...) returns the erroneous live row, with no validation/query errors:

```beancount
2026-01-01 open Assets:Bank:Business USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "Synthetic opening"
  Assets:Bank:Business 10 USD
  Equity:Opening -10 USD
```

The fixed-stride behavior follows [Beanquery date_bin](https://github.com/beancount/beanquery/blob/master/beanquery/query_env.py). A further live SELECT DISTINCT date/DATE_BIN query over all32 actual transaction dates reproduces the wrong bins for 13 dates on MCP/REST. For example, 2025-02-28 maps to 2025-03-03 instead of 2025-02-24. Independent date arithmetic checks every row; grouped totals themselves were not exercised. DATE_ADD leap-day/previous-day/365-day controls return 2024-02-29 / 2024-02-29 / 2025-02-28 correctly in the initial query.

## Root cause and repair direction

Tagged [executor/functions/date.rs](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-query/src/executor/functions/date.rs), date_bin_on_values around line405, computes signed days_diff then uses `days_diff / amount` for day strides. Rust signed integer division truncates toward zero; the interval calculation requires floor division for a positive stride. Fresh upstream main still has the same divisions. A valid direct WASM fixture reproduces without API adapters/cache. Local ledger src/foundation/rustledger/engine.ts::queryLedgerFilesResultInProcess delegates to the native query object.

After upstream publishes a compatible fixed artifact, adopt it with the ledger package manager and verify actual native results plus eligible REST/GraphQL/MCP together. For supported fixed positive day strides, use floor-based signed offset selection so bins contain the source on either side of the origin. Preserve at-origin and exact-boundary results, positive offsets and date arithmetic. Do not patch adapter cells, rewrite user queries, fork upstream or vendor unreleased bytes. Month/year stride rules need their own compatibility analysis; this finding does not claim that changing division alone fixes calendar-month binning.

Acceptance: sources one/four/eight days before an origin yield the expected earlier bins, both exact boundaries remain correct, and a grouping regression places postings into bins that contain their dates. Verify negative/positive offsets and leap/year transitions with real native fixtures; all three API surfaces retain envelopes and dates. Invalid/zero strides, month/year origins and nullable arguments are not live-verified here. Latest npm and installed WASM were 0.24.0; no fixed commit or published repair identified.
