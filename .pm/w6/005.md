# Stop using the first chart bucket's end as the income statement's start

**Severity:** major. **Estimate:** 45–60 minutes for the backend-v2 correction and adapter coverage. **Owner:** backend-v2. **A1 — Agent-native accounting:** an agent must not label a month's financial results as one day's results because of chart granularity.

## Live reproduction

Production `https://beancount.io/api-gateway/mcp`, 2026-10-11. Initial local HEAD `4e83269c`, refreshed main `a8b75aed`; the defect remains in both source versions. The deployed SHA is unavailable. This run's initialization reports `beancount-mcp` 1.0.0, protocol `2025-11-25`. The designated QA API key is unpinned with `ledger.read ledger.write ledger.admin`; its value is never recorded. Only the existing synthetic MCP evaluation ledger was read.

Minimal balanced fixture for an independently prepared QA ledger:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Bank USD
2026-01-01 open Income:Salary USD
2026-01-01 open Expenses:Rent USD
2026-08-01 * "QA salary"
  Assets:Bank       100 USD
  Income:Salary    -100 USD
2026-08-03 * "QA rent"
  Expenses:Rent      25 USD
  Assets:Bank       -25 USD
```

Run from the repo root, loading the credential inside the helper:

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa.env read 'beancount://qa-owner/qa-book/statements/income-statement?time=2026-08'
```

Two fresh live requests return HTTP 200, `Content-Type: text/event-stream`, an `application/json` resource, and a successful summary whose period is `{"from":"2026-08-31","to":"2026-08-31"}`. The hosted synthetic fixture's income is `-4000`, expenses `2095.6`, and net `1904.4`. Those amounts include August 1 salary and August 3 rent; they are not August 31 activity.

Change only `interval=daily`: two fresh requests return `{"from":"2026-08-01","to":"2026-08-31"}` with identical income, expenses, net, currency, and account breakdown. Changing only chart grouping must not redefine which dates the financial results cover.

## Controls and parity

- The equivalent REST route `GET /api-gateway/v1/ledgers/qa-owner/qa-book/statements/income-statement?time=2026-08` reproduces the monthly label twice; its daily control returns the correct month's bounds with the same amounts. This is a shared REST/MCP summary defect.
- `shape=fava` returns `net_profit_data:[{"date":"2026-08-31","balance":{"USD":"-1904.4"}}]`. That date is the chart bucket's inclusive **end**, not the statement's start. The raw payload has no reporting-start metadata.
- GraphQL `getLedgerIncomeStatement(ledgerId:"qa-owner/qa-book",time:"2026-08",interval:"monthly",conversion:"USD") { netProfitData { date balance } incomeData { date balance } expensesData { date balance } }` returns the same correctly dated chart buckets and amounts, HTTP 200 without errors. It does not manufacture a `period.from` field.
- BQL `SELECT date, account, number WHERE year = 2026 AND month = 8 AND account ~ '^(Income|Expenses)' ORDER BY date` independently returns eight postings dated August 1–28, including `Income:Salary -4000` on August 1 and `Expenses:Housing:Rent 1800` on August 3.
- `time=2026` reports `from:"2026-01-31"` despite covering the entire year. An explicit partial range `time=2026-08-15 - 2026-08-31` reports `from:"2026-08-31"` above expenses `193.6` from earlier days in that range. Subtracting a whole month from the first bucket's end would also be wrong for this partial range.
- A single-day selection `time=2026-08-03` correctly reports August 3–3 and expenses 1800. An empty November selection returns zero amounts but still labels the whole month November 30–30; lack of activity does not turn a selected month into a single day.

## Root cause and correction

`src/features/ledger/utils/report-summaries.ts:197–215` assigns `period.from = data.net_profit_data[0]?.date`. The chart producer deliberately emits `range.endInclusive` as every point's `date` (`backend-cluster/ledger/src/foundation/rustledger/interval-series.ts:322–335`). Its `intervalRanges` carries the true `begin` separately and clamps it to the selected window, but the income-statement chart response does not expose that field. The current summary unit fixture unrealistically uses January 1 as its first monthly point and therefore endorses the faulty inference.

The sole production caller of `summarizeIncomeStatement` is `fetchStatement` in `src/features/ledger/api/rest/v1/reports-handler.ts:73–94`. REST and the MCP statement resource share this caller. `ledger-finance-service.ts:79–96` forwards the filters to the chart service; GraphQL `ledger-finance-resolver.query.ts:231–251` maps the raw chart data and bypasses the summary.

Correct the backend-v2 projection so a chart bucket's end never becomes a reporting start. Use authoritative resolved bounds if the existing response supplies them; otherwise return `period.from:null`, which the published summary type already permits. Preserve the exact selected time expression in the summary when needed to communicate unresolved scope. A future canonical bound field may supply the actual August 1 or August 15 start; that wider ledger/IDL work is not required to stop emitting false dates here. Do not add a second Fava time parser, guess month starts from chart ends, infer the period from the first matching transaction, or change the financial amounts. Keep the correctly supported end date and raw chart contract.

Acceptance: monthly and daily reads of the same selection report the same known reporting start, or consistently leave an unavailable start null; neither calls August 31 the start of August's results. Cover full month, year, partial range, single day, empty period, and unresolved relative-time selections through REST/MCP adapters. Preserve all totals, signed account rows, currency choice, and GraphQL/raw chart bucket dates. Run backend-v2 typecheck, tests, and OpenAPI drift generation when implementing.
