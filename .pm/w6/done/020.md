# Preserve JSON null in modern REST value responses

**Minor · backend-v2 · 35–50m · A1 — Agent-native accounting.** A valid lookup with no previous transaction returns an undocumented empty 204 response, so a normal JSON reader throws instead of receiving the declared null result.

Production `https://beancount.io`, 2026-10-15; refreshed local main `22aec290`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed SHA unavailable. Existing designated unpinned QA API key, scopes `ledger.read ledger.write ledger.admin`. Only the public synthetic `open_ledger/freelancer-invoicing` demo was read; no ledger/account mutation or product fix was performed.

GET `/api-gateway/v1/ledgers/open_ledger/freelancer-invoicing/payee-transactions?payee=QA+No+Such+Payee+20261015` with the existing QA credential. Repeat with `/narration-transactions?narration=QA+No+Such+Narration+20261015`.

Actual, including fresh fetches for both routes: **HTTP 204**, no Content-Type, zero body bytes. Calling the response's normal `json()` method throws `SyntaxError: Unexpected end of JSON input`. The live `/api-gateway/v1/openapi.json` declares **200 application/json with nullable:true** for both reads and no 204 response. The route descriptions promise a most-recent transaction or null. Expected: **HTTP 200, application/json, body null**, parseable as the JSON null value. Do not convert this ordinary absence into a missing-ledger error.

Positive control: `payee=Contoso+Ltd` returns HTTP 200, application/json, 273 body bytes, and parses normally to the May-22-2026 payment. Lookup by the exact narration `Workshop facilitation + 8.5% sales tax` succeeds through a percent-encoded MCP path and the REST query string, preserving all three postings. MCP's successful unmatched-resource contents parse as JSON null on two fresh calls per lookup. GraphQL has the separate resolver/non-null defect in [019](./019.md); its failure does not make REST's undocumented empty body conform to its own contract.

Root cause: `src/features/ledger/api/rest/v1/analysis-handler.ts:326–346` declares a JSON 200 response and returns the service's null unchanged. `src/server/rest/v1-route.ts:180` assigns every defined handler result directly to `ctx.body`. The installed Koa `response.body` setter treats null as no-content unless JSON has already been selected; that branch does not set a successful 200 status itself either. The builder supplies neither an explicit JSON-null response nor that status/content-type setup. Assigning an ordinary object works because Koa's non-null branch selects 200/JSON automatically, explaining the control.

Fix the shared value-response boundary to serialize a legitimate null result explicitly as **200 JSON null**, while preserving the separate undefined-handler branch used for responses already written to the context. Use the framework's supported status/content-type/body behavior; do not blindly stringify streams, archives or already-sent responses. Audit the builder's callers (33 feature files currently register v1Route) for deliberate response ownership. Only the two nullable analysis reads above were live-proven affected; no broader list of failures is claimed. Keep their existing OpenAPI 200/nullable contract rather than documenting away the JSON-reader failure. Coordinate with 019 so the complete empty-lookup parity journey works on all three API surfaces.

Acceptance: exercise an actual HTTP route returning null through the shared builder, checking status 200, JSON Content-Type and `response.json() === null`. Include both real lookup aliases, the positive object control, and a handler returning undefined after setting its own response. Preserve custom byte/stream responses and genuine service errors. Check MCP remains successful/null and GraphQL meets 019's nullable-result acceptance. Run backend-v2 typecheck, tests and OpenAPI generation without contract drift when implementing.

Dedupe: searched all board states for null/204, empty REST body, nullable lookup and Koa/v1Route response handling; no overlapping item or landed correction was found. This is not the archive naming/MIME contract issue in w6/done/010.
