# Return an ordinary empty result for unmatched GraphQL transaction lookups

**Minor · backend-v2 · 35–50m · A1 — Agent-native accounting.** A new payee or narration normally has no prior transaction to autocomplete. That condition should produce a nullable result rather than a server failure.

Production `https://beancount.io`, 2026-10-15; refreshed local main `22aec290`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed SHA unavailable. Designated unpinned QA API key with `ledger.read ledger.write ledger.admin`; only public synthetic `open_ledger/freelancer-invoicing` was read. No product fix or ledger mutation was performed.

POST this GraphQL document to `/api-gateway/`:

```graphql
query {
  getLedgerPayeeTransactions(
    ledgerId: "open_ledger/freelancer-invoicing"
    payee: "QA No Such Payee 20261015"
  ) { date payee narration }
}
```

Actual, including a fresh repeat: HTTP 200, `data: null`, error code `INTERNAL_SERVER_ERROR`, message `Internal server error`. `getLedgerNarrationTransactions` with `narration: "QA No Such Narration 20261015"` has the same result. A combined document with a known Contoso lookup under `existing` and the missing payee under `missing` returns **data:null for the entire document**, with the error path `missing`; the otherwise working field is lost through non-null propagation.

Controls: the Contoso lookup alone succeeds with date `2026-05-22`, payee `Contoso Ltd`, narration `Payment — invoice 2026-006`, matching the independently inspected 23-transaction journal. The corresponding MCP resources return successful JSON `null` for both unmatched values, repeated fresh. Their published descriptions explicitly promise one most-recent transaction or null. REST reaches the same null producer but has the separate serialization defect in [020](../020.md). The public demo contains neither sentinel string; these are valid new lookup values, not missing ledgers or invalid inputs.

Root cause: `src/features/ledger/api/resolvers/ledger-data-resolver.query.ts:365–425` declares both fields as non-null `Transaction`, then turns a falsy service result into `InternalServerError`. `LedgerDataService.getPayeeTransactions/getNarrationTransactions` legitimately returns the underlying nullable result; MCP forwards it. The root-level non-null fields explain loss of the combined document's positive field. This is distinct from the REST response-builder cause in 020.

Fix both GraphQL lookups together: declare nullable Transaction results and return null for a normal no-history result. Keep real service failures as failures; do not catch every exception and return null. Preserve positive dates, payees, narrations and posting amounts/commodities/prices. Coordinate with 020 in the API parity change so REST's declared JSON-null contract works too; retain MCP's already-correct null result. Update generated GraphQL artifacts/consumer types where owned by the backend workflow rather than leaving a non-null promise behind.

Acceptance: real adapter tests for both missing values return the respective field:null without errors; a combined positive/missing document retains its positive field. Check both successful lookups, unknown narration, and genuine service failure through the eligible REST/GraphQL/MCP adapters. Preserve existing failure codes for failures. Run backend-v2 typecheck, tests and OpenAPI drift checks when implementing. Only API behavior was exercised; no dashboard/mobile/host-client failure is claimed.

Dedupe: searched all board states for these resolver messages, nullable autocomplete, empty transaction lookup, and lookup null/204 behavior; targeted history still retains these non-null guards. No overlapping open item or landed repair was found. Query-cursor completion is not exposed by the inspected API inventory/source and was not filed as a missing capability.
