# Distinguish BQL output rows from input postings

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** backend-v2. **A1 — Agent-native accounting:** MCP text and schemas should describe output rows without assuming they count input postings. This affects empty-result explanations and advice for grouped queries.

## Reproduction and controls

Production `https://beancount.io`, 2026-10-14; local main `ba1ddb80`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed SHA unavailable. Existing designated unpinned QA API key, scopes `ledger.read ledger.write ledger.admin`. Read-only public synthetic `open_ledger/example`.

Call `runBqlQuery` with:

```json
{"ledger":"open_ledger/example","query":"SELECT DISTINCT payee WHERE payee IS NOT NULL ORDER BY payee LIMIT 0"}
```

HTTP 200, successful envelope, empty string result. The text block says **`0 rows — no postings matched`**, including on a fresh repeat. The same query without LIMIT has 36 non-null payees; with LIMIT 5 it returns the first five sorted names. Postings do match the predicate: LIMIT deliberately suppresses the output rows. The count is correct; the claimed cause is false.

`runBqlQueryStructured` and REST `POST /api-gateway/v1/ledgers/open_ledger/example/query` with the same LIMIT-0 query both return an empty table. The structured MCP result states `rowCount: 0`, `truncated: false`, and its text correctly says just `0 rows` before the short JSON payload.

An additional text-tool call, `SELECT payee, COUNT(*) AS postings GROUP BY payee HAVING COUNT(*) > 10000`, also says `no postings matched`. The verified unfiltered grouping has 37 groups covering 3,209 postings; HAVING removes all groups. Empty output alone does not establish that the input stream had no matching postings.

## The same assumption in published row-count advice

Additional controls were observed at local main `4eda91f8`, on the same production server/protocol above; deployed SHA remains unavailable.

The served `runBqlQueryStructured` output schema describes `rowCount` as **“Rows returned. BQL rows are postings, so this counts postings, not transactions.”** Initialization likewise says LIMIT counts postings. The served `spending-report` prompt tells the agent that BQL rows are postings and LIMIT 5 is five postings.

Live counterexample, with the same public fixture and credential:

```sql
SELECT account, COUNT(*) AS postings
WHERE account ~ '^Expenses:'
GROUP BY account ORDER BY postings DESC, account LIMIT 5
```

It correctly returns `rowCount: 5`, `truncated: false`, and five account groups whose posting counts are 370, 73, 71, 71 and 71: **656 underlying postings**, independently verified against the full journal. REST has the identical table. No result value is wrong; the schema description and generic instructions give the count the wrong meaning. The raw unaggregated-query warning about multiple postings per transaction remains useful, but needs that qualification. GROUP BY and DISTINCT change what a result row represents; LIMIT bounds output rows.

The import playbook's `item_id`, `transactions`, `target_account` and `dry_run` names were checked against the published schema and matched; it is not part of this finding. No bank operation was executed.

Helper pattern: `node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file .env call runBqlQuery '<JSON above>'`.

## Root cause and bounded repair

`backend-cluster/backend-v2/src/features/ai-agent/api/mcp-result-text.ts`, `renderBqlTable`, returns the fixed phrase whenever canonical row-count metadata equals zero. That metadata counts output rows, not pre-LIMIT/pre-HAVING input postings, so it cannot support the explanation.

Use neutral wording such as `0 rows` or `0 rows — query returned no rows`. Preserve canonical same-query counts, success status, the empty string result, text payloads for nonempty results and all typed data. Do not add a second count query or infer causes by parsing the statement. REST and GraphQL query evaluation/results remain the same; the repair belongs to MCP's additional text summary.

Qualify the same assumption in `mcp-context.ts` initialization text, `bql-query-tool.ts`'s raw-query description and rowCount schema description, and `mcp-prompts.ts`'s spending playbook. State that raw, unaggregated entries queries iterate postings, while `rowCount` always counts returned result rows and LIMIT applies to the result. Preserve grouped/unique-value semantics and the distinction from transaction counts. This is a wording/metadata correction, not a request to replace the existing canonical count producer with an input-posting count.

Update the existing text-summary and registered BQL parity tests with genuine empty input, LIMIT-0/HAVING and grouped/distinct controls, asserting truthful text and unchanged canonical counts. Include the served schema/instructions/prompt descriptions. The current literal expectation for `no postings matched` should change rather than preserve the overclaim. Run backend-v2 typecheck/tests and OpenAPI drift checks; retain the zero-debt parity gate.

**Resolved 2026-10-15** — Implemented and shipped in `563cd059` (`backend-cluster/backend-v2`). `renderBqlTable` no longer attaches a cause to a zero-row result. It reads `0 rows`, matching `runBqlQueryStructured`, because the canonical count is of output rows, and LIMIT 0 or a HAVING that drops every group returns nothing from postings that did match. The served `rowCount` description, the server instructions, `runBqlQuery`'s description, and the spending-report playbook now say the same thing. They keep the posting caveat for unaggregated queries (one row per posting, not per transaction), state that GROUP BY and DISTINCT return one row per group or value, and that LIMIT bounds result rows. Canonical same-query counts, success status, the empty-string result, nonempty text payloads, typed data, and REST/GraphQL results are unchanged. No second count query or statement parsing was added. `bql-parity.test.ts` adds LIMIT-0-over-matching-postings, HAVING-removes-every-group, and grouped-top-five (five rows standing for 656 postings) cases through the real service on REST, GraphQL, and MCP. The literal empty-result expectation changed rather than preserving the overclaim. `bql-row-wording.test.ts` reads the tool schema, instructions, and prompt from an MCP client. The old wording fails 5 cases. Native gates pass: 311 suites / 5335 tests, typecheck, lint/dead-code, and OpenAPI generation without drift. Served text updates on deployment; downstream agent decisions were not measured.
