# Preserve event filters in REST and MCP reads

**Minor · backend-v2 · 35–50m · A1 — Agent-native accounting.** An agent cannot retrieve the same filtered Event directives as the existing GraphQL/dashboard read: REST silently ignores the selection, while MCP refuses it.

## Live reproduction

Production `https://beancount.io`, 2026-10-15; local main `a1959a9c`. MCP `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployed SHA unavailable. Existing designated unpinned QA API key, scopes `ledger.read ledger.write ledger.admin`. Only public synthetic `open_ledger/example` was read.

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file .env read 'beancount://open_ledger/example/events?time=2016'
```

Actual, repeated fresh: JSON-RPC -32602, `BAD_USER_INPUT`, `Unknown or repeated resource parameter: time`, with a hint that this resource takes no query parameters. The advertised template is only `beancount://{owner}/{name}/events`.

REST `GET /api-gateway/v1/ledgers/open_ledger/example/events?time=2016` succeeds with **all nine** events, including 2015 and 2017 entries. `time=2010` also returns all nine. Both were repeated fresh. Expected: four 2016 events, and zero events for 2010.

The equivalent GraphQL controls at `POST /api-gateway/` work:

```graphql
query {
  getLedgerEvents(ledgerId: "open_ledger/example", time: "2016") {
    date type description
  }
}
```

This returns exactly April 11, April 19, November 16 and November 29 of 2016, twice. With time:"2010" it returns []; without time it returns all nine. Independent extraction and date sorting of the public fixture's nine source Event directives agrees exactly with these GraphQL results. The unfiltered MCP and REST reads also agree with all nine, so the fault is lost input behavior, not missing/corrupt event data. The documents resource's analogous time-filter read is accepted and returns its legitimate empty array; positive Document coverage is not claimed.

## Root cause and correction

`src/features/ledger/api/rest/v1/vocabulary-handler.ts` registers events in VOCABULARY_READS without a query schema. Its REST handler only forwards ledgerId and identity. `mcp-resources.ts` builds that vocabulary template without query names and likewise omits filters; the shared strict URI matcher correctly rejects a parameter absent from that descriptor. REST's undeclared query is ignored rather than forwarded.

The existing GraphQL `getLedgerEvents` resolver forwards account, filter and time. Backend LedgerDataService.getEvents already accepts FilterParams and passes them to the existing ledger service, which applies the directive filters. No new producer, parser, API authority or ledger-service change is needed.

Make the existing events read use the same shared filtered descriptor mechanism as documents (or an equally narrow extension of the current descriptor). Declare and forward account/filter/time through REST and MCP, advertise the query expansion, and preserve the current URI, resource name, response fields, ordering and unfiltered behavior. Remove the duplicate unfiltered registration if moving the descriptor; do not create a second independent event implementation. Preserve GraphQL's current behavior. Registration in the historical vocabulary family is not a documented protocol/credential-policy exception to the root accepted-input parity requirement. Do not weaken eligibility or change a ratchet to hide the gap.

Acceptance: real adapter cases for unfiltered nine events, 2016's four and 2010's empty selection have identical REST/GraphQL/MCP content and ordering. Cover forwarding of the already-supported account and expression filters as well as time, and keep malformed selections on the producer's normal error path. Update the OpenAPI snapshot and advertised MCP template/docs. Run backend-v2 typecheck, tests, lint and OpenAPI generation. Do not change unrelated vocabulary defaults or the ledger Event-versus-account-lifecycle definition.
