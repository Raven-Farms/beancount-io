# Give tool-only clients a read path to canonical entry hashes

**Severity:** major. **Estimate:** 50–60 minutes for a narrow journal-read tool and adapter coverage. **Owner:** backend-v2. **A1 — Agent-native accounting:** a client that exposes tools but not resources must be able to discover the identifier required to inspect an existing entry.

## Live reproduction

Production `https://beancount.io/api-gateway/mcp`, 2026-10-11; main `63ce8988`. Server `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployment SHA unavailable. Designated unpinned QA API key with `ledger.read ledger.write ledger.admin`, never recorded. Direct JSON-RPC tool calls against the existing synthetic evaluation ledger; no billed host session or write.

On a prepared QA ledger containing an ordinary transaction, try to inspect that existing transaction using tools alone:

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa.env call runBqlQueryStructured '{"ledger":"qa-owner/qa-book","query":"SELECT id, date, narration WHERE account = '\''Assets:Checking'\'' AND date = 2026-08-20"}'
```

Two fresh requests on the hosted fixture return HTTP 200 SSE with a successful typed row `[25,"2026-08-20","Groceries"]`; column `id` has dtype `int`. That is a directive index, not the entry hash accepted by the context tool. Passing `entryHash:"25"` to `getEntryContext` returns `isError:true`, `NOT_FOUND` in two fresh requests, with the normal missing-resource hint. Passing the numeric value directly would not satisfy its published string argument schema.

The two plausible hash-column queries are also refused: `SELECT entry_hash ...` reports `column 'entry_hash' not found`, and `SELECT hash ...` reports `column 'hash' not found`, both `BAD_USER_INPUT`. `SELECT entry_hash() ...` reports no matching function. These are working query errors, not parser defects to repair.

Working control: read the journal resource, select the same transaction's `entry_hash`, and pass that value to the **same** `getEntryContext` tool. It succeeds with the correct August 20 entry, source slice, and checksum. The entry exists and its context is readable; discovery of its canonical identifier is missing from the tool-only path.

## Contract and root cause

[ADR 019 D7](../../docs/adrs/ADR019-backend-v2-mcp-host-compatibility.md#d7--tools-are-the-surface-every-host-can-reach-and-an-identifier-a-tool-needs-must-come-from-a-tool) identifies this as a structural usability requirement that needs no billed agent run. Customer `docs/mcp.md` also states that every identifier required by a tool comes from another tool. Existing-entry context and source editing need `entryHash`; writes returning newly created/updated hashes cannot discover a pre-existing transaction for a read-only client.

The read-tool inventory was inspected live and in `src/features/ai-agent/api/mcp-tools.ts:255–332`:

- BQL tools return native query columns; the gateway/ledger shell mappers do not attach canonical entry hashes.
- `listLedgers` returns ledger metadata, `getLedgerContext` returns vocabulary, and `checkLedger` returns counts/errors/latest-commit metadata. This healthy fixture has no errors furnishing an entry identifier.
- `listLedgerFiles` returns files; `readLedgerFiles` returns raw text and line-range metadata. File/blob hashes are not journal-entry hashes.
- `getEntryContext` itself already requires the missing identifier (`ledger-context-tools.ts:170–195`). It is not an entry-discovery operation.

The journal and account-directives **resources** do return canonical hashes. Those resources use the shared service and its existing full-stream/occurrence-aware IDs. Upstream rustledger 0.24.0's [query evaluator](https://github.com/rustledger/rustledger/blob/v0.24.0/crates/rustledger-query/src/executor/evaluation.rs#L518) explicitly makes `id` an integer directive index; its function dispatcher/utilities contain no canonical-entry-hash function. The installed local WASM version is 0.24.0; deployed dependency version remains unverified, but the observed numeric result is decisive for this deployment.

## Correction and acceptance

Promote the existing journal read as a narrow read-only tool, for example `listLedgerEntries`, returning its existing entry records with `entry_hash`, total, and pagination. Reuse the same journal service as REST `journal` and GraphQL `getLedgerJournal`; accept an explicit ledger plus existing account/time/expression/type filters and bounded pagination so a client can find older entries without enumerating the whole book. Retain the current resource twin. Update `getEntryContext` and `editEntrySource` discovery descriptions to name the read tool that supplies their identifier.

Preserve canonical hash generation, duplicate-occurrence handling, source checksums, target selection, read policy, and existing valid journal semantics. Keep BQL's native numeric `id` unchanged; do not treat mutable indexes as durable hashes, require a client to recreate hashing, or build a generic resource bridge. Update the measured tool inventory/count gate, descriptors, op-class mapping, docs, and parity coverage in the same backend-v2 change. REST/GraphQL already expose the underlying read; their values must remain equivalent.

Acceptance: a real MCP adapter/client restricted to `tools/list` and `tools/call` finds a selected existing transaction, obtains its canonical hash, and successfully calls `getEntryContext` with matching source/checksum, without mutation or `resources/read`. Cover older filtered entries, pagination, empty matches, and occurrence-distinct duplicates using the existing canonical service. Preserve ordinary BQL results and all eligible surface results. Run backend-v2 typecheck, tests, and OpenAPI drift generation when implementing.
