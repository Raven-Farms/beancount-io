# Keep balance-sheet summary totals on one valuation basis

**Severity:** major. **Estimate:** 45–60 minutes for the backend-v2 projection, valuation disclosure, and adapter coverage. **Owner:** backend-v2. **A1 — Agent-native accounting:** a financial snapshot must not report net worth different from its stated assets plus liabilities because it mixes valuations.

## Live reproduction

Production `https://beancount.io/api-gateway/mcp`, 2026-10-11; main `b831767a`. Server `beancount-mcp` 1.0.0, protocol `2025-11-25`; deployment SHA unavailable. Designated unpinned QA API key with `ledger.read ledger.write ledger.admin`, never recorded. The additional target is the public synthetic `open_ledger/crypto-example` demo; only reads were made. Its error resource returns no errors.

```sh
node .agents/skills/qa-shared/scripts/qa-mcp.mjs --credentials-file /path/to/qa.env read 'beancount://open_ledger/crypto-example/statements/balance-sheet?conversion=USD&time=2026-01'
```

The first request returns HTTP 200 SSE and a successful USD summary with:

```json
{"asOf":"2026-01-31","currency":"USD","assets":187687.0180319,"liabilities":0,"netWorth":194880.731731}
```

A fresh request repeats the broken identity: assets `187650.8092319`, liabilities `0`, net worth still `194880.731731`. Latest quote data moved between snapshots, but **each single response** is internally inconsistent. This is not a comparison of totals fetched from different responses. The second summary's net worth exceeds its assets plus liabilities by `7229.9224991 USD`, far beyond JSON-number rounding.

## Controls and parity

- The equivalent REST `GET /api-gateway/v1/ledgers/open_ledger/crypto-example/statements/balance-sheet?conversion=USD&time=2026-01` reproduces the second summary and matches MCP.
- `shape=fava` identifies both sources: its January 31 `net_worth_data` point contains `USD:"194880.731731"`, while the Assets hierarchy's aggregate carries the other amount and Liabilities is empty. The summary combines these distinct views.
- GraphQL `getLedgerBalanceSheet(ledgerId:"open_ledger/crypto-example",time:"2026-01",conversion:"USD") { netWorthData { date balance } assetsHierarchyData { balance balanceChildren } liabilitiesHierarchyData { balance balanceChildren } }` returns the same dated point and latest-valued hierarchy, HTTP 200 without errors. The raw/chart contract itself is not claimed broken by this filing.
- The same historical selection with `conversion=units` gives assets and net worth both `86519.39 USD`; `at_cost` gives both `200642.81326 USD`, with zero liabilities. An unfiltered USD summary also obeys the identity because its last chart valuation and latest-valued tree coincide. These controls isolate the mixed price-date projection.
- Summary `byAccount` values come from the hierarchy, so changing only the reported net-worth number's source does not repair its mismatch with account-derived totals unless that source uses the same valuation basis.

Minimal static fixture for regression coverage: open an `Assets:Broker` account in XYZ and `Equity:Opening` in USD; acquire 2 XYZ at cost 10 USD on January 2 against Equity `-20 USD`; declare January 31 XYZ price 10 USD and February 28 XYZ price 20 USD. The January position window and latest-price tree then differ from the dated January chart point. This fixture description is for implementation coverage, not claimed uploaded or exercised live by QA.

## Root cause and correction

`src/features/ledger/utils/report-summaries.ts:166–193` derives assets/liabilities/equity and account rows from hierarchy nodes, but prefers `last(net_worth_data).balance` for `netWorth`. Its existing `assets + liabilities` fallback runs only when there is no series point.

The producer deliberately has two views. `backend-cluster/ledger/src/foundation/rustledger/account-tree.ts:178–197` values hierarchies at the latest ledger price when its optional date is omitted. `LedgerFinanceService.getBalanceSheet` omits that date for the trees while `accountBalanceSeries` values each chart point at its interval end. A historical position filter therefore exposes the two different valuations. The gateway summary is the layer that incorrectly collapses them into one financial snapshot.

Correct the bounded backend-v2 summary: derive its net worth from the same Assets and Liabilities hierarchy totals it reports, using the existing `assets + liabilities` identity for every snapshot. Keep account rows on that same basis. Explicitly disclose the summary's valuation basis in its result/docs: price-based conversions use the latest ledger quotes for the selected positions; `asOf` describes the position cut-off. Do not present that price policy as historical-date market valuation. Preserve units/cost semantics and the currently documented raw tree/chart pricing behavior.

Do not change the legacy `shape=fava` or GraphQL chart values, reconstruct pricing in the gateway, hardcode a currency, combine different currencies, or add another engine evaluation. True historical-price hierarchy projection would be separate domain/contract work; it is not necessary to stop mixing the two existing projections here.

The sole production summary caller is `fetchStatement` in `src/features/ledger/api/rest/v1/reports-handler.ts:73–94`, shared by REST and MCP. GraphQL bypasses it and exposes both raw views. Keep eligible underlying values and input/default behavior intact while documenting the summary projection. Add real-adapter coverage with deliberately different dated-series/latest-tree values, an explicit historical filter, unfiltered/units/cost controls, nonzero liabilities, and the public invariant `netWorth = assets + liabilities` within the documented numeric precision. Assert that account rows and valuation disclosure agree with that basis and that raw/GraphQL payloads remain unchanged. Run backend-v2 typecheck, tests, and OpenAPI drift generation when implementing.
