## Objective

Stop subscription reads and webhooks from refreshing another customer binding's `currentPeriodEnd`. Fixing the write path prevents old test records from being revived by a live subscription.

## Context

`SubscriptionService.subscriptionStatus()` sorts active subscriptions, takes one period end, and writes it to `customers[0]` irrespective of the subscription owner. `findByUserIdWithActivePeriod()` also returns an arbitrary qualifying row. The read-only synthetic reproduction showed a live Organization renewal being written to an old test row. The webhook and upgrade paths have separate writes that must obey the same ownership rule.

## Steps

1. Replace first-row write selection with exact user/client/Stripe-customer matching and keep each supported binding's period cache scoped to its own subscriptions.
2. Audit `stripe-webhook-handler.ts` and `stripe-service.ts` writes, including upgrade/checkout handlers; signed events must not bypass customer ownership checks or resurrect retired bindings.
3. Scope active-period shortcuts to supported bindings, using narrow model queries where necessary. Do not treat record existence or a copied future date as proof of a recognized plan.
4. Exercise duplicate refreshes, multiple bindings, stale events, cancellation/expiry and Stripe lookup failures. Preserve established period-end cancellation policy; document any pre-existing unrelated lifecycle gap instead of inventing new policy.

## Files

- `backend-cluster/backend-v2/src/features/stripe/service/subscription-service.ts` — status refresh cache writes.
- `backend-cluster/backend-v2/src/features/stripe/service/stripe-service.ts` and `api/stripe-webhook-handler.ts` — lifecycle writes and identity checks.
- `backend-cluster/backend-v2/src/features/stripe/data/paid-customer-model/{postgres-impl,types}.ts` — narrowly scoped queries/updates as required.
- Existing stripe service, webhook and model tests — assert actual row changes.

## Acceptance criteria

- [x] A live subscription refresh changes only its exact binding; a historical test row and an unrelated live customer row remain unchanged.
- [x] Repeated reads/events are idempotent; retired/test events and mismatched customer ownership cannot grant or extend live paid access.
- [x] Active-period fast paths cannot choose a retired binding, and no write relies on `customers[0]` or unspecified database order.
- [x] Focused webhook/service/model tests pass with the existing cancellation behavior preserved.

## Out of scope

- Applying historical data cleanup, changing subscription prices, and widening billing credentials; t004 owns existing corrupted data.
