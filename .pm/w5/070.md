# `list price --on-disk` returns managed-feed prices that no ledger file contains

**Minor · cli · 25–40m · A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`,
checkout `bea 0.3.1`, macOS. `--on-disk` promises the rows written in a ledger
file. In a ledger with a managed price include it also returns every price the
feed supplies, unmarked, so an agent that lists the authored prices before
editing or reconciling them is told the feed's quotes are in the books. No
product fix implemented.

The feed was a **simulation**: a loopback HTTP server allowlisted through the
documented `MANAGED_PRICE_ORIGINS` variable served one synthetic feed; no
Beancount.io endpoint was contacted and no credential was used. The listing
path under test is local and does not depend on the origin.

Feed body served at `http://127.0.0.1:18765/prices/BTC-USD`:

```beancount
; alias: BTC-USD
; commodity: BTC
; quote: USD
2026-01-04 price BTC 53000.50 USD
  observed-at: "2026-10-10T00:00:00Z"
2026-01-05 price BTC 55000 USD
  observed-at: "2026-10-10T18:50:00Z"
```

Disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
include "http://127.0.0.1:18765/prices/BTC-USD"

2026-01-01 open Assets:Cash USD

2026-01-03 price BTC  51000 USD
```

With isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1,
`MANAGED_PRICE_ORIGINS=http://127.0.0.1:18765`, closed stdin, no TTY:

```sh
bea --file /absolute/books/main.bean list price --on-disk
bea --json --file /absolute/books/main.bean list price --on-disk
```

Actual: exit 0 and three rows — `2026-01-03 51000 USD`, `2026-01-04 53000.50
USD`, `2026-01-05 55000 USD`. The JSON rows for the two feed prices carry no
`generated` field. `grep -c 'price BTC' main.bean` prints `1`. Plain
`list price` returns the same three rows with no `SOURCE` column, so the two
kinds are indistinguishable in both modes. Repeated on a second fresh cache.
An independent query shows where the extra rows live:
`SELECT date, meta('filename') FROM #prices` names `main.bean` for the first
row and `<cache>/bea/managed-prices/<hash>/<revision>.effective.<hash>.beancount`
for the other two.

Control: in a ledger using `plugin "beancount.plugins.implicit_prices"`, the
plugin's prices are marked `generated` and `--on-disk` drops them, as
documented. The authored `2026-01-03` row is returned in every case.

Expected: `docs/USAGE.md` Listing directives defines `--on-disk` as "Only
directives written in a ledger file" and says it answers "exactly what `grep`
would find in the file". The same guide calls feed entries read-only and says
"your files are never rewritten to accommodate a feed", and its `add price`
rule counts "only written price directives" as duplicates. A feed price is in
the price cache, not in a ledger file, so `--on-disk` should return the one
authored row, and an unfiltered listing should mark the feed rows so they can
be told apart.

Cause: `cli/src/bea_engine/ledger/reader.py:116-149` (`entry_generated`)
decides "on disk" by reading the entry's `filename`/`lineno` and checking that
the line there declares this directive on this date. A managed price's
metadata points at the cached effective feed file, whose line does declare it,
so the entry passes as written. `cli/src/bea_engine/ledger/listing.py:101-104`
applies only that test. The engine already knows how to recognize such a path:
`managed_price_cache.managed_source_for_path`
(`cli/src/bea_engine/managed_price_cache.py:370`), used by the write boundary
(`ledger/write.py:89-91`) and the price duplicate rule (`ledger/adding.py:565`).

Fix: treat an entry whose source file belongs to the managed price cache as
not on disk, so `--on-disk` drops it, and surface it in unfiltered listings the
way plugin rows are surfaced — the existing `generated` marker and `SOURCE`
column, or a distinct value naming the managed source; pick one and document
it beside the plugin cases. Apply it in `entry_generated` or beside it so every
`list <type>` shares the rule, and keep exported snapshots unaffected: after
`bea price export` the feed is a real local file and its rows are on disk.
No dependency or API change.

Dedupe: board search for `--on-disk`, `generated` and managed prices finds
w3/301, w1/113, w1/114, w1/049 and w3/394 (plugin rows and line-matching
defects, all done) and w1/163 (shadowing by slash-dated prices); none
considers feed entries under `--on-disk`.

Acceptance: on the fixture, `list price --on-disk` returns only the authored
row in text and JSON, the unfiltered listing marks the two feed rows, the
plugin control and a plain plugin-free ledger are unchanged, and an exported
snapshot lists all three as on disk. Regression tests run the real command
against a seeded offline cache. Only macOS and the checkout were exercised,
against a simulated feed.
