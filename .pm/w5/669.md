# `--meta 'qty: -12345678901.123456789012345678'` is written rounded (`-12345678901.12345678901234568`), while the positive twin is written exactly (sibling of w5/263)

**Minor · cli · 10m · A1.** Real CLI QA, 2026-10-16, HEAD `60ea00ea`, checkout `bea 0.3.1`, macOS 26.5.1.
w5/263 made wide negative numbers go on disk exactly (or be refused) for
`--posting`, bulk shorthand and `add balance`. `--meta` values still go through
the stock parser, which applies its 28-digit context to the negation. The
typed digits are changed with exit 0. No product fix implemented.

`main.bean`: two opens.

```sh
bea --json -f /abs/main.bean add transaction --date 2026-02-01 A \
  --meta 'qty: -12345678901.123456789012345678' --meta 'pos: 12345678901.123456789012345678' \
  --meta 'fee: -12345678901.123456789012345678 SHIB' -p 'Assets:Wallet 1 SHIB' -p Equity:Opening
bea -f /abs/main.bean add commodity --date 2026-01-01 --commodity SHIB --meta 'supply: -12345678901.123456789012345678'
```

Actual: exit 0; the file and the JSON answer hold `qty:
-12345678901.12345678901234568`, `fee: -12345678901.12345678901234568 SHIB` and
`supply: -12345678901.12345678901234568`; `pos` is exact.

Control: a bulk row's tagged number (`{"kind": "number", "value":
"-12345678901.123456789012345678"}`) is written exactly; `add custom -v
number:-…` refuses with "would reload as different values".

Expected: the typed digits on disk, or exit 2, as w5/263 decided for other
paths.

Cause: `_parse_metadata` (`cli/src/bea_engine/ledger/adding.py:1111`) uses
`parser.parse_string` instead of `parse_exact`
(`cli/src/bea_engine/amounts.py:49`); callers at `adding.py:782` and `:220`.

Fix: parse with `parse_exact`.

Dedupe: searched `parse_exact`, `28 significant` with meta; w5/263 (done) is
the parent.

Acceptance: the three values are written exactly. A test pins them.
