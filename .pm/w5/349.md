# A Python importer's second same-day trade with the same share count but a different cost is skipped as an "exact duplicate" (exit 0): the generated import-id and the possible-duplicate fingerprint ignore cost and price

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12 with beangulp.
The generated `import-id` hashes the source account's posting units, here
`10 AAPL`. It ignores the cost spec, the price and the cash leg, because
the cash leg is not on the source account. Take two buys on the same day
with the same description and share count but different prices, for
example partial fills, DRIP lots or repeated buys. They get the same id.

When the second trade arrives in a later export, it counts as an exact
duplicate of the first. `--apply` exits 0 with `Wrote 0 entries`, so the
trade and its cash leg are lost with no warning. The SOURCE AMOUNT column
shows `10 AAPL` for both rows, which hides the difference. No product fix
implemented.

Create disposable `/absolute/books/main.bean`:

```beancount

2026-01-01 open Assets:Cash USD,EUR
2026-01-01 open Assets:Broker
2026-01-01 open Equity:Opening
2026-01-02 * "Seed"
  Assets:Cash  10000 USD
  Equity:Opening
```

Create `imp2.py`:

```python
import datetime, os
from decimal import Decimal as D
from beancount.core import data, amount, position
from beangulp import importer

class Imp(importer.Importer):
    def identify(self, filepath):
        return os.path.basename(filepath).startswith("trade")
    def account(self, filepath):
        return "Assets:Broker"
    def extract(self, filepath, existing):
        cost, cash = open(filepath).read().split()
        p1 = data.Posting("Assets:Broker", amount.Amount(D("10"), "AAPL"),
                          position.CostSpec(D(cost), None, "USD", None, None, False), None, None, None)
        p2 = data.Posting("Assets:Cash", amount.Amount(D(cash), "USD"), None, None, None, None)
        return [data.Transaction(data.new_metadata("x", 1), datetime.date(2026, 1, 5), "*",
                                 "Broker", "Buy AAPL", frozenset(), frozenset(), [p1, p2])]

CONFIG = [Imp()]
```

Actual:

- A writes one entry with `import-id: "csv:sha256:fd25259e21688a59"`.
- B's preview shows `0 ready, 1 exact duplicates`, with `Row 1: import-id
  csv:sha256:fd25259e21688a59 is already in the ledger`, and prints the
  existing `{100 USD}` entry.
- B's `--apply` exits 0 with `Wrote 0 entries`.
- Holdings stay at `10 AAPL {100 USD}`, so the 120 USD lot and its
  −1,200 USD cash leg are missing.
- When one export holds both trades, row 2 is flagged as a
  `possible_duplicate` of row 1, and `--apply` exits 4. That case is less
  harmful but has the same cause.

Reproduced by the hunter in two fresh copies and by me in a third.

Control: `tradeC.txt` with 11 shares at 120 USD is `new` and is written.

Expected: `docs/IMPORTING.md` says the generated id "binds the date,
amount, description, and account of the original source row, so a
canonical generated-id hit is a duplicate even if the ledger's date,
amounts, payee, or narration were edited later". An id hit is treated as
proof that this is the same source row. For a posting held at cost, or
priced, the cost or price is part of the source amount. Two buys at
different prices are different rows, so they need different ids and
different fingerprints.

Cause:

- `_hash_import_ids` (`cli/src/bea_engine/importing.py:1166`, `amounts =
  sorted((p.units.number, p.units.currency) for p in
  _source_postings(...))`) hashes units only.
- `_fingerprint` (`importing.py:721-737`) uses the same units-only
  amounts.
- `_source_legs`/`_source_postings` (`:703-718`) keep only postings on
  the exact source account, so the cash leg never contributes when the
  lot sits directly on `account()`.

Per the code (not exercised), the w5/223 layout (`Assets:Broker:AAPL`
plus `Assets:Broker:Cash`) includes the cash leg and avoids the problem.

Fix:

- When a source posting carries a cost (number, currency, date, label) or
  a price, include it in the canonical id base and in `_fingerprint`.
- Keep the units-only digest as a lookup-only legacy key, as the module
  already does for older formats, so existing ids still match.
- Show the cost or price in SOURCE AMOUNT.
- No dependency change.

Blast radius: `import` with Python importers (beangulp or `--config`)
that post lots or priced units directly on their `account()`. CSV rows
carry no cost and are unaffected. The loss is silent and exits 0.

Dedupe: searched `.pm/**`, including `done/`, for import together with
cost, lot or price and duplicate, and for `_fingerprint` and
`_hash_import_ids`. Related notes:

- w5/223: the parent-account importer.
- w5/m10: migrate and transfer ids.
- w1/m27: exact amounts.

None covers cost or price in generated ids or fingerprints.

Acceptance:

- On the fixture, B previews as `new`, and `--apply` writes it. Holdings
  are `10 AAPL {100 USD}` plus `10 AAPL {120 USD}`.
- Re-importing B is then an exact duplicate.
- An entry written before the fix with a units-only id still matches on
  re-import.
- A real-command test covers different-cost trades across two exports and
  within one export.
- Only macOS and the checkout were exercised.
