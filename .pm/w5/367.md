# `bea cloud status` reports a redirect (or any other non-200 status below 400) as a rejected credential: exit 3 with "log in again" or "fix BEA_TOKEN", which cannot help

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1. **Simulation:** the server behaviour comes from a local mock. The defect is in how the CLI handles it.

`cloud status` treats an empty profile as "revoked bearer" and raises an
HTTP-401 auth error. `unwrap_or_none` returns `None` for *any* status
below 400 that the parser did not recognize, so a redirect gets the same
treatment. A redirect is what an `http://` `BEA_API_URL` gets from an
https-only API, or what a proxy or captive portal returns. A 204 is
treated the same way.

The user is told to log in again or to replace `BEA_TOKEN`. That cannot
fix anything, because the same redirect comes back. No product fix
implemented.

Setup: a localhost mock answers every request with `302 Location:
https://127.0.0.1:18751/…`. Use the environment from [366](./366.md),
with either a fake `BEA_TOKEN` or a stored credential file in the
isolated config directory.

```sh
bea cloud status
bea cloud ledger list
```

Actual:

- `cloud status` exits **3** (`auth`).
  - With `BEA_TOKEN`: `Not authorized (the server does not recognize
    this environment credential). BEA_TOKEN is the credential in use … mint
    a new token.`
  - With a stored credential: `… Run 'bea cloud login'.`
- `cloud ledger list` exits 1 with `Empty response (HTTP 302).`
- A 204 behaves the same way.

The hunter reproduced this four times and I reproduced it once. No
redirect was followed, and the token was not sent to the other origin.

Control: a real 401 gives the same auth message with exit 3. A 200 whose
body is null is the case the empty-profile rule was written for.

Expected: `docs/USAGE.md` maps only `401`/`403` to exit 3, and
"everything else … exits **1**". A redirect or unexpected success status
should be an unexpected-response error with exit 1. Ideally it names the
`Location` and suggests checking `BEA_API_URL`, for example `http` vs
`https`.

Cause: `unwrap_or_none` (`cli/src/cli/api/client.py:172-177`) returns
`parsed` (`None`) for any status below 400. `cloud_status`
(`cli/src/cli/commands/cloud/app.py:104-109`) then raises
`error_from_status(401, …)` for `None`.

Fix: apply the revoked-credential rule only to an HTTP 200 with a null
body. Route a 3xx, or any other unexpected status, through
`error_from_status(status)` or an unexpected-response error naming the
redirect target. No dependency change.

Blast radius: `bea cloud status` behind a redirecting proxy, or with a
mistyped `BEA_API_URL` scheme or host. Users are sent to re-authenticate
for nothing.

Dedupe: searched `.pm/**`, including `done/`, for redirect, 302 and
`unwrap_or_none`. w5/012 covers the wording of the auth message, not when
it fires. Nothing covers redirects.

Acceptance: with a 302 and with a 204, `cloud status` exits 1 with an
unexpected-response or redirect message that does not mention login or
`BEA_TOKEN`. A 200 null body still gives the auth error. A
mocked-transport test pins all three.
