# With the cached price blob missing or corrupt, a failing fetch never backs off: every command fetches again (and waits 5 s when the service is slow)

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-16, HEAD `c0267f61`, checkout `bea 0.3.1`, macOS 26.5.1. Synthetic local feed server.
ADR018 §6 and ADR015 §5: a failed fetch sets the next refresh 60 seconds
ahead. The window is honored only when the cached blob reads, or when the
head names no revision. The degraded head written after a failure keeps
naming the missing blob, so the window never applies. Every command then
refetches, and with a slow service every command waits out the 5 s
timeout. A truncated blob, one that fails re-validation after an upgrade
(w5/377, 423), or partial cache cleanup puts a ledger in this state. No
product fix implemented.

A ledger with one managed include. Run `check` once, then delete the cached
`<rev>.beancount` blob (or append a line, so its digest fails); the server
now answers 503.

```sh
bea -f /abs/main.bean check     # run four times
```

Actual: four checks send four requests (each exits 1, "managed price source
unavailable"); `head.json` keeps `revision` pointing at the missing blob with
`next_refresh_at` 60 s ahead. With the server delayed 8 s, each run takes about
5.5 s, every time.

Control: with an intact blob, a lapsed window and a 503, five checks send one
request.

Expected: one request per 60 s after a failure, whatever the blob's state.

Cause: `cli/src/bea_engine/managed_price_cache.py:280` honors the window only
when `previous is not None or head.revision is None`; the degraded head
(`:358`) copies `revision=head.revision`.

Fix: write `revision=previous.revision if previous else None` in the degraded
head (or always honor the window when the head carries `last_error`).

Dedupe: searched `backoff`, `retry window`, `missing blob`. No match.

Acceptance: four checks after deleting the blob send one request. A test pins
it.
