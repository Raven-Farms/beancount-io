# A price refresh deletes the superseded revision's effective file while another `bea` process is loading it, so a concurrent `check` fails and `add` refuses a valid write; racing fetches also leave orphan revisions on disk forever

**Minor · cli · 30–45m · A1.** Real CLI QA, 2026-10-16, HEAD `c0267f61`, checkout `bea 0.3.1`, macOS 26.5.1. Synthetic local feed server that changes the body on every request.
ADR018 §6: a concurrent process "can only ever observe a complete revision",
and the only cost of a race is "a redundant conditional GET". Loads include
the shared cache file `<rev>.effective.<hash>.beancount` in place. A process
that repoints the head immediately deletes the previous revision's blob and
effective files. A reader that has already chosen that revision then fails
to load it. Deletion targets only the revision the refreshing process itself
read, so revisions written by a racing fetcher are never deleted. An agent
running commands alongside an editor plugin or a scheduled refresh hits the
first case. No product fix implemented.

A ledger with a managed include whose feed changes on each fetch, plus about
20,000 small transactions (so a load takes ~2 s); the cache is warm.

```sh
bea -f /abs/main.bean check & sleep 0.1; bea -f /abs/main.bean price refresh; wait
```

Actual: `check` exits 1 with `<load>:0: File glob ".../managed-prices/<hash>/<rev>.effective.<hash>.beancount"
does not match any files`. Against `add balance` the same race exits 1 with
`The ledger already has 1 error(s); nothing was written. Pass --allow-errors to
write anyway.` (misleading). 25 refreshes against 2 × 25 checks gave 3
failures. Two concurrent `price refresh` runs (with a 1.5 s server delay) both
report a change; the first new revision is never deleted, and repeated window
lapses under four parallel `check`s left 16 revisions with one in use.

Control: serial runs (or a 0.5 s gap) pass, and serial refreshes delete the
previous revision.

Expected: a load never fails because another process refreshed; superseded
revisions are removed only when no reader can still be using them.

Cause: `cli/src/bea_engine/managed_price_cache.py:338-344` unlinks the previous
revision's files right after repointing the head; loads write and later parse
the shared effective file (`cli/src/bea_engine/managed_load.py:386-391`, `:434`).

Fix: keep superseded revisions for a grace period and sweep unreferenced
revisions older than the refresh window (also collecting orphans); or stage
each load's effective text beside the ledger rather than including the shared
cache file.

Dedupe: searched `superseded`, `orphan`, `does not match any files` with
effective; w1/076 (done) fixed a temp-file race among parallel fetchers, not a
reader racing a refresh.

Acceptance: a stress test of concurrent `check`/`price refresh` passes, and
the cache keeps a bounded number of revisions.
