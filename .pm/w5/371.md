# `cloud ledger create --clone` creates the remote ledger before checking a local target that is certain to fail (an existing non-empty directory), so a retry conflicts; the printed manual `git clone` remedy also drops `--dir`

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1. **Simulation:** the API came from a localhost mock. The defect is in how the CLI orders its checks.

`create --clone` already refuses before any remote change when git is
missing (`ensure_git_available`, "Fail before a remote mutation"). It
does not check the clone target, `./<name>` or `--dir`, until after
`create_ledger` has run. If that path exists and is not empty, `git
clone` is certain to fail, and by then the ledger exists on the server.

The failure message also prints `Clone it manually with: git clone
<url>` without the chosen target. Run as printed, it clones into
`./<repo>`, not the `--dir` the user asked for. No product fix
implemented.

Setup: the mock from [370](./370.md), and an existing `w/qa-new/notes.txt`
in the working directory. Use the same environment.

```sh
bea cloud ledger create qa-new --clone
bea --json cloud ledger create qa-new --clone
bea cloud ledger create qa-q --clone --dir "x y/q"   # sshUrl points at a missing repo
```

Actual:

- Both `qa-new` runs POST `/api-gateway/v1/ledgers` (mock log), then
  exit 1 with `Ledger 'qa/qa-new' was created but could not be cloned
  (fatal: destination path '…/qa-new' already exists and is not an empty
  directory.)`. The JSON carries `error.result`. `notes.txt` is
  untouched.
- The `--dir` run ends `Clone it manually with: git clone
  git@127.0.0.1:nope.git`, with no target.

Reproduced twice by the hunter. I confirmed the order in the code.

Control: with git missing, `create --clone` exits 2 before any request.

Expected: `docs/USAGE.md` warns that a clone can fail after the ledger is
created, and w3/443 made that case recoverable. A failure that can be
predicted locally should be refused before the remote change, as the git
check already is: exit 2 naming the path, with nothing created. The
manual command should repeat the target, shell-quoted (`git clone <url>
'x y/q'`).

Cause:

- `ledger_create` (`cli/src/cli/commands/cloud/ledger/app.py:64-65`)
  pre-checks only git. The target is resolved at `:84`, after
  `create_ledger` at `:69`.
- `_clone_failure_message` (`app.py:22-37`) leaves out the target.

Fix:

- Before `create_ledger`, resolve `directory or
  manager.default_clone_dir(name)` and refuse an existing file or
  non-empty directory with `UsageError`.
- Pass the target into `_clone_failure_message` and add it,
  `shlex.quote`d, to the manual command.
- No dependency change.

Blast radius: `cloud ledger create --clone` whenever the default or
`--dir` target already holds files. A retry after the first failure
conflicts on the ledger name.

Dedupe: searched `.pm/**`, including `done/`, for "created but could not
be cloned", "Clone it manually" and `--dir`. w3/443 covers keeping the
result when a clone fails, w1/089 covers name and URL safety, and w2/m24
covers other clone work. None covers a check before creation or the
missing target.

Acceptance: with a non-empty `./qa-new`, `create qa-new --clone` exits 2
naming the path and sends no POST. A clone failure after creation prints
`git clone <url> 'x y/q'` when `--dir` was given. A test covers both.
