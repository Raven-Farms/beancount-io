# CSV credit-column decimal inference changes a separate `1,234` debit into `1.234`, silently understating the withdrawal 1000×

**Major · cli · 45–60m · A1/A2.** Real bookkeeping QA, 2026-10-20,
checkout `bea 0.3.1`, HEAD `3c125ca95`, Darwin 25.5.0 arm64, frontend
Python 3.13.3. Reproduced twice from pristine ledgers; three working
controls twice, and automatic header inference twice. No product fix made.

Create `/abs/case/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

`bank.csv` has separate money-out and money-in columns:

```csv
Date,Description,Debit,Credit
2024-02-01,Withdrawal,"1,234",
2024-02-02,Refund,,"0,50"
```

Use cwd `/abs/case`, isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`, closed
stdin/no TTY. Run preview, then apply, then independent reads:

```sh
bea --json --no-input --file /abs/case/main.bean import /abs/case/bank.csv --csv date=Date,narration=Description,debit=Debit,credit=Credit --account Assets:Cash --default-account Expenses:Food
bea --json --no-input --file /abs/case/main.bean import /abs/case/bank.csv --csv date=Date,narration=Description,debit=Debit,credit=Credit --account Assets:Cash --default-account Expenses:Food --apply
bea --json --file /abs/case/main.bean query "SELECT narration, number WHERE account = 'Assets:Cash' ORDER BY narration"
bea --json --file /abs/case/main.bean check
```

Actual: all exit **0**, JSON stderr empty. Preview preserves the ledger;
apply writes two balanced transactions, but the withdrawal is wrong:

```text
Refund       0.50
Withdrawal  -1.234
```

The resulting cash balance is **−0.734 USD**. It should be **−1233.50 USD**:
a 1234 withdrawal and a 0.50 refund. The Debit column's lone `1,234` reads
as grouped thousands on its own; the Credit column's `0,50` reads as a
comma decimal. The independent columns must not change one another's
meaning. Ledger validation stays green because the generated counterposting
carries the same incorrect amount. Source CSV bytes are unchanged.

Controls, each twice from fresh fixtures:

- Change only Credit `0,50` to `0.50`: the identical Debit `1,234` is
  written as **−1234**, and cash is **−1233.50**.
- Change only Debit `1,234` to `1234`: the comma-decimal credit stays
  **0.50**, and cash is **−1233.50**.
- Keep Debit `1,234` and omit the refund row: withdrawal is **−1234**.

Replacing the explicit mapping with `--csv auto` reproduces the wrong
**−0.734** balance twice; its human preview also succeeds with the wrong
amount. This affects the ordinary no-code bank import, not just a custom
mapping. A related refusal is also confirmed twice: Debit `1,234.56` and
Credit `0,50`, each internally consistent in its own column, fail with
`cannot parse amount '0,50' in column 'Credit'` and advice that comma
decimals work when the whole column uses them. That column already does.
Those refusals preserve the ledger and are the same shared-convention cause.

Expected: resolve decimal conventions independently for each mapped amount
column, as `cli/docs/IMPORTING.md:103–115` describes. Preserve the existing
lone-grouped-amount default in Debit and the comma decimal in Credit, or
refuse an unresolved ambiguity before writing. A value in the other column
must never silently rescale the withdrawal. Explicit `decimal=point|comma`
overrides and mixed conventions within one column must retain their current
documented behavior.

Cause: `cli/src/bea_engine/csv_mapper.py:1675–1677` flattens every Debit and
Credit cell into one call to `_resolve_decimal_comma`, setting a single
`self._decimal_comma`. `_parse_decimal` at :1497–1498 uses that same Boolean
for both headers, including `_pair_number` (:1538) and pair-sign validation
(:1601). The Credit cell's comma vote therefore reinterprets Debit's
otherwise-grouped value as a fraction. Dot-ambiguity notes also consult the
same global Boolean. The no-code `CsvImporter` is constructed by
`bea_engine/importing.py`; explicit and inferred mappings share it.

Fix: track the inferred convention per mapped amount header and use it in
all amount parsing, sign validation and ambiguity notes. A supplied decimal
override can still govern all selected columns. Preserve skipped/unposted
row filtering, direction/sign handling, stable IDs and atomic apply; do not
round amounts or merely change the displayed result. No dependency or API
change is needed.
