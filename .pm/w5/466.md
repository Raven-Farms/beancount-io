# A `SIGTERM`/`SIGHUP` to `bea treeify`, `bea doctor` or `bea example` leaves the upstream child running

**Minor · cli · 20–30m · A1.** Split from [300](./done/300.md)'s addendum (CLI QA r80, 2026-10-14). macOS, checkout `bea 0.3.1`.
`capture_native` (`cli/src/cli/engine/launch.py`, `subprocess.run(...,
capture_output=True)`) forwards no signals. When the frontend gets SIGTERM
or SIGHUP, it exits 143 or 129, but a `treeify` child that is blocked
without writing (for example, reading a FIFO) keeps running. A child that
is writing dies of SIGPIPE soon after. The hunter reproduced this twice.
These children only read, so no ledger is changed. The cost is a leftover
process and an open input.

Repro: `mkfifo in.fifo`; `bea treeify in.fifo &`; `kill -TERM $!`. The
frontend exits 143. `pgrep -fl treeify` still lists the child until
something writes to the FIFO.

Expected: as with `run_native` (w5/208), the stop signal is passed on and
the child gets the cleanup grace period, then the frontend dies of the
same signal.

Fix: run captured natives through the same forwarding as
`_run_inherited`'s `stop`/`forward` handlers, using `Popen` plus
`communicate`. No dependency change.

Acceptance: on the FIFO repro, no `treeify` process outlives the grace
period after SIGTERM or SIGHUP to the `bea` PID. A real-command test
covers it.
