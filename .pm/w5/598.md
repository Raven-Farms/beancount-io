# A bank ID from one account dedupes another account's rows through a transfer entry: a real savings deposit is skipped as an "exact duplicate" with exit 0 (or a different row is a false conflict, exit 4), and the result depends on import order

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-16, HEAD `5e09bcc4`, checkout `bea 0.3.1`, macOS 26.5.1.
IMPORTING.md: native IDs are "scoped to the importer's source account" and
"must be stable and unique within that account". OFX FITIDs work the same
way. When an import writes a transfer, the entry carries the source
account's bank ID and also posts to the other account. Importing that other
account later indexes the entry under its own scope, because it has a leg
there. The first account's ID then matches an unrelated row of the second
account. No product fix implemented.

`main.bean`: opens for `Assets:Checking`, `Assets:Savings`,
`Expenses:Groceries`, `Expenses:Uncategorized`, `Income:Salary`,
`Income:Interest` (USD).

`checking.csv`:

```csv
Date,Description,Amount,ID
2026-09-05,ONLINE TRANSFER TO SAVINGS,-500.00,1001
2026-09-06,WHOLE FOODS,-45.00,1002
```

`savings.csv`:

```csv
Date,Description,Amount,ID
2026-09-20,MOBILE DEPOSIT,500.00,1001
2026-09-30,INTEREST PAID,1.25,1002
```

Rules: checking `transfer to savings` → `Assets:Savings`, `whole foods` →
`Expenses:Groceries`; savings `interest` → `Income:Interest`, `deposit` →
`Income:Salary`.

```sh
bea --file /abs/main.bean import checking.csv --csv date=Date,amount=Amount,narration=Description,id=ID --account Assets:Checking --rules chk.toml --apply
bea --file /abs/main.bean import savings.csv  --csv date=Date,amount=Amount,narration=Description,id=ID --account Assets:Savings  --rules sav.toml --apply
bea --file /abs/main.bean balance Assets:Savings
```

Actual: the savings import exits 0 with `1 ready, 1 exact duplicates`, and
reports `Row 1: import-id bank:1001 is already in the ledger.`, matching the
09-05 checking transfer. Savings ends at `501.25 USD`. With a Python OFX
importer where checking's transfer and savings' interest share `FITID 1`,
the savings `--apply` exits 4 (`Stable ID matches an entry with different
transaction data`) and points at the transfer.

Control: savings' `1002` is new (checking's `1002` never posts to savings);
importing savings first, then checking, is correct.

Expected: 500 (transfer) + 500 (deposit) + 1.25 = 1,001.25 USD. A native ID
matches only entries whose source posting is the account that issued it. A
hit that arrives only through a counter posting is at most a possible
duplicate ("matches the other side of a transfer"), which keeps the benefit
for banks that share one reference across both legs.

Cause: the index of written entries includes any entry with a leg on
`--account` (`cli/src/bea_engine/importing.py:317-322`); `_identities`
(`:1011-1032`) keys that entry's `bank_id`/`fitid`/`import-id` under the
current account; `_same_row` (`:1062-1063`) accepts a native-ID hit on equal
amounts at any date.

Fix: scope native IDs to the source posting that wrote them (bea writes it
first) or record the issuing account; downgrade counter-posting hits as
above.

Dedupe: searched `fitid`, `cross-account`, `counter posting`; w3/237, w3/280,
w5/075 and 469 are different.

Acceptance: in both orders savings ends at 1,001.25 USD, and the OFX variant
imports the interest. Tests pin both.
