# Entry metadata named `filename:` or `lineno:` makes a written entry look plugin-made: `list` calls it generated and `--on-disk` hides it, `import` and `add balance` write duplicates, and a non-string value crashes `list`

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-16, HEAD `76c5b63e`, checkout `bea 0.3.1`, macOS 26.5.1.
Beancount stores an entry's source location in `meta["filename"]` and
`meta["lineno"]`, and the parser merges user metadata over them with no
error. `filename: "scan-0042.pdf"` is a natural way to note a receipt, and
`pushmeta filename: …` applies it to a whole block. bea then trusts those
values as the location. Every feature that separates written entries from
generated ones gets the entry wrong, including import's duplicate check.
Bulk input already refuses these keys as "reserved for Beancount source
location" (w3/284), but a ledger that has them passes `check`. No product
fix implemented.

Fixture A:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
2024-01-02 * "Shop" "receipt attached"
  filename: "scan-0042.pdf"
  Expenses:Food  1.00 USD
  Assets:Cash
2024-01-03 * "Shop" "plain"
  Expenses:Food  2.00 USD
  Assets:Cash
```

```sh
bea --file /abs/a.bean check                        # exit 0
bea --file /abs/a.bean list transaction --on-disk
bea --json --file /abs/a.bean list transaction
```

Actual: `--on-disk` lists only "plain". The full listing marks "receipt
attached" as `generated`; `--details` prints `scan-0042.pdf:3 (generated)`;
JSON has `"source": {"filename": "scan-0042.pdf", "lineno": 3}`,
`"generated": true` and `"meta": {}` (the user's value is gone).

Import: an imported entry that also carries `filename: "bank-2024-01.csv"` and
`lineno: 2` (as an importer or a hand edit might add) is not recognized on
re-import: `1 ready, 0 exact duplicates`, `Wrote 1 entry`, and the ledger holds
two entries with the same `import-id`. `add balance` writes a duplicate of an
assertion carrying `filename: "statement-jan.pdf"`.

Crash: `filename: 2024-01-02` (or `TRUE`), or `lineno: 4.5`/`"abc"`, makes `list
transaction` exit 1 with `Error: ValidationError: 1 validation error for
SourceLocation`, with or without `--allow-errors`.

Control: the same entries with `receipt:` or `statement:` instead are on disk,
deduplicated and listed correctly.

Expected: entry-level `filename`/`lineno` metadata (including from
`pushmeta`) is reported by `check` and the read gate as an error naming the
line ("reserved for Beancount's source location"). Until fixed, the reader
recovers the location from the postings' meta (which still holds the real
file and line) or treats it as unknown, and never crashes.

Cause: upstream `beancount/parser/grammar.py` merges entry metadata over the
location with `meta.update`; bea reads it as truth in `entry_generated`
(`cli/src/bea_engine/ledger/reader.py:179-221`), `--on-disk`
(`ledger/listing.py:110`), `SourceLocation` (`reader.py:289`),
`metadata_to_json` (`reader.py:243`), import's written-entry index
(`cli/src/bea_engine/importing.py:327`) and `add balance`
(`ledger/adding.py:473`, `:496`).

Fix: as above.

Dedupe: searched `SourceLocation`, `lineno:`, `filename:` with metadata,
`pushmeta`; w3/284 (done, writes refuse the keys) and w3/394 (done) are
related.

Acceptance: `check` reports the reserved key; `--on-disk`, import dedupe and
`add balance` treat the entry as written; no crash. Tests pin each.
