# `add transactions --partial` reloads the ledger once per row, so the retry the CLI recommends takes minutes

**Major (time, correct result) · cli · 45–60m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`),
checkout `bea 0.3.1`, macOS arm64.
When a batch has one bad row, bea refuses it in half a second and says "Pass
`--partial` to append the N valid rows". Following that advice validates the
batch one row at a time, each with a full staged load and a re-parse of every
row accepted so far: 4 seconds for 250 rows, 14 for 500, 51 for 1,000 on a
two-line ledger, and about 1.3 seconds per row on a 20,000-transaction ledger.
The rows written are correct. No product fix implemented.

Create disposable `/absolute/books/main.bean` and a 500-row batch whose
first row posts to an unopened account:

```sh
printf '2000-01-01 open Assets:Bank USD\n2000-01-01 open Expenses:Food USD\n' > main.bean
python3 -c "import json,sys;K=int(sys.argv[1]);json.dump([{'date':'2024-01-02','narration':f'r{i}','postings':[{'account':'Expenses:Nope' if i==0 else 'Expenses:Food','amount':'1 USD'},{'account':'Assets:Bank'}]} for i in range(K)],open('rows.json','w'))" 500
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bea -f /absolute/books/main.bean add transactions --from /absolute/books/rows.json
bea -f /absolute/books/main.bean add transactions --from /absolute/books/rows.json --partial
```

Actual: the first exits 1 in 0.4 s with `… nothing was written. Pass
--partial to append the 499 valid rows.` The second exits 1 with `Added 499
of 500 transactions; 1 row was rejected.` after 13.7 s; with 250 rows it
takes 4.0 s. A worker's table, each measured twice:

| Ledger | Rows (1 bad) | Refusal | `--partial` |
| --- | --- | --- | --- |
| 2 lines | 250 | 0.4 s | 3.7 s |
| 2 lines | 500 | 0.4 s | 12.9 s |
| 2 lines | 1,000 | 0.5 s | 51.2 s |
| 20k txns | 10 | 3.1 s | 14.5 s |
| 20k txns | 20 | 3.1 s | 27.1 s |
| 20k txns | 40 | 3.1 s | 51.1 s |

The worker also saw 2,000 rows take 125 s and 4,000 rows not finish in 300 s.

Control: an all-valid 500-row batch with `--partial` exits 0 in 0.5 s.

Expected: a bounded number of loads however many rows there are, as w1/167
established for the refusal path ("at most 2 full loads"). An agent batch
with one typo'd account is the ordinary case this flag exists for.

Cause: `cli/src/bea_engine/ledger/adding.py:1091-1094` calls
`write.validate_append(file, [*texts, text], …)` for every row, each a full
staged load, and each call re-parses every already-accepted text in
`require_one_entry_each` (`cli/src/bea_engine/ledger/write.py:1037`). A
worker's profile at 250 rows: 251 validations, 32,127 parses, 11.1 of 11.7 s.

Fix: reuse the mechanism the refusal already has (`_rows_with_errors`,
`adding.py:1132`) to drop the rows the batch error names, validate the
remainder once, and fall back to bisection or per-row trials only if that
still fails. Parse each row once. No dependency or API change.

Dedupe: board search for `--partial` cost finds w1/167 (the non-partial
hint, done), w3/315 and w3/231 (hint wording) and w5/057 (a crash); none
covers per-row loading.

Acceptance: the 1,000-row fixture with one bad row completes in under 3
seconds with the same rows written and the same message, and time on a
20,000-transaction ledger stays within a few loads regardless of row count.
A regression test counts loads. Only macOS and the checkout were exercised.
