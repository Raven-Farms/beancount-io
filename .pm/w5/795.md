# Three path-handling gaps: `--json format` on a symlinked root reports the resolved target (and text `add` names it while its JSON names the link), `init` through a symlink loop or with an illegal byte leaks a raw `OSError`, and `-o /dev/stdout` fails when stdout is a file or closed

**Trivial · cli · 15m · A1.** Real CLI QA, 2026-10-17, HEAD `9b822564b`, checkout `bea 0.3.1`, macOS 26.5.1. Follow-ups to w5/581, 580 and 583 (done).
No product fix implemented.

1. **Symlinked root (gap in w5/581).** `B/real.bean` includes `inc.bean`;
   `A/inc.bean` exists, and `A/main.bean -> ../B/real.bean`. From `A`:
   - `bea --json format --check main.bean` gives `target.files` =
     `[…/A/inc.bean, …/B/real.bean]`. Re-running on `B/real.bean` fails with
     `1 include(s) are missing` (hunter's run).
   - `bea add note -a Assets:Checking -m t --date 2026-01-08` prints `Added 1
     note to …/B/real.bean.`, while `--json add note` reports `{"file":
     "…/A/main.bean", "into": "…/A/main.bean"}`.
   - `check`, `balance`, `list`, `query` and `report` already report `A/main.bean`.
2. **`init` OSErrors (gap in w5/580).** With `ln -s loop loop`, `bea init
   loop/books --currency USD --date 2026-01-01` exits 1 with `OSError: [Errno
   62] Too many levels of symbolic links: '…/loop/books'`. A name with byte
   `\xff` gives `OSError: [Errno 92] Illegal byte sequence` and leaks the
   staging name `.bea-….tmp` (hunter's run). `bea init loop` itself exits 2.
3. **`-o /dev/stdout` (beside w5/583).** USAGE:254-256 says a device
   destination "is written through", and `/dev/stdout` "prints it as `-o -`
   does".
   - `bea treeify bal.txt -o /dev/stdout > out.txt` exits 2 with `[Errno 2] No
     such file or directory: '/dev/fd/.bea-….tmp'`.
   - `bea example -o /dev/stdout > out.bean` exits 4, `Already exists:
     /dev/stdout.`
   - `format g.bean -o /dev/stdout >&-` says `the directory /dev is not
     writable` (hunter's run).
   - Piped stdout works.

Cause:
1. `format` reports `path.resolve()` (`cli/src/cli/commands/format.py`, around
   `:419-457`, `:643-672`), and the text add confirmation prints the engine's
   resolved target.
2. `_make_parent` (`cli/src/bea_engine/initiating.py:134`) catches only three
   `OSError` subclasses.
3. treeify's `atomic_write` and `example._is_written_through` stat
   `/dev/stdout`, which is `S_ISREG` under a file redirect.

Fix:
1. Report the lexical root, and use the `write_target` path in text.
2. Map any other `OSError` to the usage message.
3. Treat `output.STDOUT_PATHS` as stdout in treeify, example and format, as
   query does.

Dedupe: w5/581, 580 and 583 (done) are the parents; w5/613 and 767 (open)
cover other target cases.

Acceptance: each case behaves as its parent promises.
