# A bare JSON float as a bulk metadata value is accepted and written with its binary error (`12345678901234567890.123` becomes `12345678901234567000`, `0.3`-style values keep `0.30000000000000004`), while the same float in a tagged object or an amount is refused

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
bea refuses JSON floats in amounts and in tagged numbers, because "the
float cannot hold the decimal exactly". An untagged float metadata value
goes through a coercion added by w3/230 to stop a printer crash. That
coercion records the float's binary value as a decimal, so large numbers
lose digits silently and fractional ones keep binary noise. Untagged
`NaN` and `Infinity` are refused, but with the misleading "a field holds
a line break or a value that is not one token". No product fix
implemented.

Use any USD ledger with `Expenses:Food` and `Assets:Cash` open. Use
isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, and
closed stdin. Create `in.json`:

```json
[{"date":"2026-01-02","meta":{"rate":12345678901234567890.123,"rr":0.30000000000000004},
  "postings":[{"account":"Expenses:Food","amount":"5 USD"},{"account":"Assets:Cash"}]}]
```

```sh
bea -f /absolute/books/main.bean add transactions --from in.json
```

Actual: exit 0 with `Added 1 transaction`. The ledger gets `rate:
12345678901234567000` and `rr: 0.30000000000000004`. `1e2` becomes
`100.0`, and posting meta behaves the same way. Reproduced twice by the
hunter (text and JSON) and once by me.

Control: `{"kind":"number","value":12345678901234567890.123}` and a float
`units.number` are both refused with `JSON float … cannot represent a
decimal exactly. Send the number as a decimal string`. The tagged string
form is written exactly.

Expected: `docs/USAGE.md` says numeric metadata uses tagged objects, and
that "a JSON float … rejects the row, because the float cannot hold the
decimal exactly". `amounts.py` says accepting a float "would record binary
error as accounting fact". An untagged float metadata value should be
refused with the same field-named remedy, for example `Row 1, meta.rate:
JSON float … send {"kind":"number","value":"…"}`. JSON integers can stay
accepted, since they are exact. NaN and infinities should be named as
non-finite numbers.

Cause:

- The bulk pre-check (`cli/src/bea_engine/ledger/adding.py:1128`) admits
  untagged `int | float`, and `_META_VALUE_HELP` (`:1065`) advertises "a
  number".
- `metadata_for_write` (`cli/src/bea_engine/ledger/write.py:2130-2132`)
  converts with `Decimal(str(value))`.

Fix: refuse untagged `float` values (including non-finite ones) in the
bulk metadata check with the tagged-number remedy, keep `int`, and update
the help text and the USAGE sentence. No dependency change.

Blast radius: bulk `add transactions` rows with numeric metadata produced
by JSON serializers, which emit floats by default. The result is silent
precision loss in recorded metadata.

Dedupe: w3/230 (done) introduced the coercion for a crash, without
considering precision. w3/260 and w1/045 refuse floats in amounts and
tagged meta. w5/335 covers the remedy text for refused floats. None
covers silent rounding of untagged metadata.

Acceptance: on the fixture, the row is refused with a field-named float
message, and nothing is written. An integer `"n": 5` is still written
exactly. A test pins both.
