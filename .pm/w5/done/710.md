# A UTF-8 BOM on line 1 hides a first-line `pushtag`/`pushmeta` and `option "name_*"` from the write checks: an append under `--allow-errors` silently inherits the tag, and adds under a renamed root are refused as "not used" (incomplete fix of w5/464; gap in w5/402)

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-17, HEAD `a7c2762d`, checkout `bea 0.3.1`, macOS 26.5.1. Follow-up to w5/464 and w5/402/462 (done).
USAGE:589 says a BOM-marked ledger "loads like any other". Two write-path
checks scan the raw text, where the BOM sits in front of the first
directive, so a match anchored at the start of line 1 fails. No product fix
implemented.

1. **Inherited tag.** `main.bean` is `include "inc.bean"` followed by opens
   for `Assets:Cash` and `Expenses:Food`. `inc.bean` is the bytes `EF BB BF`
   followed by `pushtag #trip` and one transaction.
   - `bea --file /abs/main.bean add transaction Groceries --date 2026-01-05
     -p "Expenses:Food 10 USD" -p Assets:Cash --into inc.bean` exits 1 with
     `The ledger already has 1 error(s)… Unbalanced pushed tag: 'trip'. Pass
     --allow-errors to write anyway.`
   - With `--allow-errors` it exits 0, and `query "SELECT narration, tags"`
     shows `Groceries  trip`. The JSON echo says `"tags": []`.
   - `pushmeta`, `add note`, `add transactions` and `import --apply` behave
     the same.
   - Control: without the BOM, the write exits 2 with `…ends inside
     \`pushtag #trip\` at line 1, so an entry appended there would silently
     inherit it.`, as w5/464 requires "even under `--allow-errors`".
2. **Renamed roots.** `bom.bean` is `EF BB BF` followed by `option
   "name_expenses" "Aufwand"` and opens for `Assets:Cash` and `Aufwand:Food`.
   - `check` exits 0.
   - `add note -a Aufwand:Food …` and `add open -a Aufwand:X …` exit 2: `Account
     'Aufwand:Food' has root 'Aufwand', which this ledger does not use; its
     roots are Assets, Liabilities, Equity, Income, Expenses…`. `add close`,
     `pad` and `document` behave the same, and `add transaction`'s advice to
     `add open` loops into this refusal.
   - With a BOM root holding `option "name_assets" "Activos"`, `add
     transaction … --into txns/new.bean` exits 1 asking to "Repeat the root's
     options at the top of new.bean", the seed that the no-BOM control writes
     itself.
   - Control: the same files without the BOM succeed.

Expected: a BOM-marked file behaves exactly like the same file without the
BOM in both checks.

Cause:
- `open_pushes(original.decode("utf-8"))` (`cli/src/bea_engine/ledger/write.py:2560`)
  keeps U+FEFF, so the lexer sees `﻿pushtag` as an error token.
- `root_names_of` (`cli/src/bea_engine/ledger/text.py:331-344`, called from
  `ledger/adding.py:89`) and `new_include_seed` (`write.py:2512-2523`) match
  `^option` on text that still has the BOM.

Fix: drop a leading U+FEFF (decode with `utf-8-sig`) before each scan.

Dedupe: searched `pushtag`, `pushmeta`, `name_*` with `BOM`. w5/464, 402 and
462 (done) never mention a BOM; w5/704 is the ingest side.

Acceptance: both fixtures behave like their no-BOM controls. A test pins one
case of each.

Addendum (CLI QA 2026-10-17, HEAD `701764c5a`): a third trigger in `root_names_of`.
When the `option "name_assets"` value is spelled NFD (`Vermögen` with U+0308),
`check` passes, but `add open -a 'Vermögen:Sparbuch' --date 2024-01-02 -c EUR`
(NFC or NFD) exits 2 with `Account 'Vermögen:Sparbuch' has root 'Vermögen',
which this ledger does not use; its roots are Vermögen, Liabilities, …`. That
message contradicts itself. `add close`, `add note`, `add pad` and `add
document` behave the same, while `add transaction`, `add balance` and `import`
accept the account. `root_names_of` keeps the raw NFD option value, and
`parse_account` compares an NFC name against it. Fixing all three triggers
(BOM, invalid value, NFD) the same way, by reading the roots as the loader
does, would close this. w5/766 item 3 is the invalid-value case.

**Resolved 2026-10-18** — Shipped in `d4c6b2fa8a514577100c4180b235fcee3cb084ed` (`cli`). Pushed-context scanning now strips a leading BOM and normalizes NFC before lexing, so a first-line `pushtag` or `pushmeta` cannot evade the append refusal under `--allow-errors`. Root-name prechecks and new-include seeding share a lexer-based extractor with the same BOM/NFC handling and Beancount's own root-name converter: the last valid value wins, an invalid override retains the prior/default root, and comments, quoted text and malformed option lines do not supply root options. Seeding preserves option insertion order and emits the accepted final values without modifying the original root. This also covers the invalid-root-option subcase referenced by w5/766; its other work remains open. The five original/addendum repro triggers are fixed, with source bytes preserved, and newly seeded ledgers pass a fresh check. Added 18 focused option cases and 41 real-command cases spanning transaction, note, bulk, import and raw appends, both pushed contexts, BOM/no-BOM and closed-push controls, five simple directive types, NFC/NFD input, invalid overrides and new-include balances; all passed along with 46 existing focused tests. The initial integration run's two final-query assertions expected text instead of structured JSON inventories; only those assertions were corrected. Reverting both existing production modules made 37 integration cases fail and four controls pass; fixed sources were restored before the full gate. `make check-all` passed (8,859 tests, two skipped, 70 existing forkpty warnings), and two independent reviews accepted the change. Incoming backend/dashboard/other-workstream changes during pull applied cleanly without touching CLI code. Refreshed tracked-content gitleaks was clean; the whole-tree scan retained the same 72 known ignored runtime/build/cache matches with no new fingerprints.
