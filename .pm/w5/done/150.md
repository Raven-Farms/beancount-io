# `--allow-errors` refuses a backdated purchase when the account already has a failing sale

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
A ledger with a sale whose purchases are not all entered yet cannot be
backfilled one purchase at a time. The existing booking error lists the
account's lots in its text; a backdated purchase changes that list, and
`bea` counts the same error on the same line as newly introduced, so
`--allow-errors` refuses. A workaround exists (enter all missing purchases
in one batch that cures the error), so the owner may downgrade. No product
fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Broker "FIFO"
2024-01-01 open Expenses:Fees
2024-01-01 open Income:Gains
2024-01-01 open Equity:Opening

2024-01-02 * "Opening"
  Assets:Cash  100000.00 USD
  Equity:Opening

2024-02-01 * "buy 1"
  Assets:Broker  10 ACME {100 USD}
  Assets:Cash

2024-03-01 * "sell (two purchases still to be entered)"
  Assets:Broker  -30 ACME {} @ 150 USD
  Assets:Cash  4500 USD
  Income:Gains
```

`bea check` reports exactly one error, at line 16.

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean add transaction "buy 2" --date 2024-02-10 -p "Assets:Broker 10 ACME {110 USD}" -p "Assets:Cash" --allow-errors
```

Actual: exit 1, file unchanged.

```text
Error: The change would introduce 1 new ledger error(s); nothing was written.
  /absolute/books/main.bean:16: Not enough lots to reduce "-30 ACME {}": 10 ACME {100 USD, 2024-02-01}, 10 ACME {110 USD, 2024-02-10}
```

Controls, each on a pristine copy with the same flag: the same purchase
dated `2024-03-02` (after the failing sale) exits 0 and repeats the line-16
error as a warning; an unrelated backdated `Expenses:Fees 5 USD` on
`2024-02-10` exits 0. A worker saw the same refusal through `add
transactions --from -`, and for three sibling cases whose message changes
with the write: a pre-existing `Ambiguous matches` in a STRICT account, a
`Too many missing numbers` sale that becomes `Not enough lots`, and a
`Transaction does not balance: (100 USD)` that becomes `(200 USD)`.

Expected: `docs/USAGE.md` says every add command "accepts `--allow-errors`
for a semantic error already in the books… An error the write itself would
introduce … is refused". The ledger has one error at line 16 before and
would have one at line 16 after; nothing new is introduced, so the write
should succeed with the error as a warning. w1/done/135's acceptance says
investment ledgers with a lot-matching error must still accept
`--allow-errors` writes.

Cause: `cli/src/bea_engine/ledger/write.py:878-893` (`_error_key`)
identifies an error by file, line and raw message, with a stable key only
for `Balance` entries. Booking messages embed the account's lots at that
moment, so the key differs after the write and the error is counted as
new.

Fix: an error anchored to a pre-existing line should match a before-error
at the same file and line with the same error class — an append never
alters existing lines. Keep the raw-message key for errors past the
original end of file or without a line. No dependency or API change.

Blast radius: every validating writer (`add *`, `add transactions`,
`import --apply`); only `add transaction` and the bulk form were run.

Dedupe: board search for "Not enough lots", "Ambiguous matches",
`_error_key` and "new ledger error" finds w1/done/135 (same symptom from a
staged path inside the message, fixed) and w5/079, 096 and 144 (false
refusals from line or path shifts); none covers message text that changes
with the write.

Acceptance: the command exits 0, appends the purchase and prints the
line-16 error as a warning; a write that adds a genuinely new error is
still refused. Real-command regression tests cover the four message
variants. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — `--allow-errors` now recognises a pre-existing error that a write only rewords: in `cli/src/bea_engine/ledger/write.py`, an error left unmatched by the exact file, line and message key is matched against a before-error of the same kind on the same pre-existing directive, while errors on appended lines or without a line keep the exact key. Two details go beyond the note's sketch: every booking failure counts as one kind, and a posting-line error is anchored to its transaction's first line, because upstream reports "Too many missing numbers" at the posting under a different class than the "Not enough lots" it becomes. `cli/tests/test_allow_errors_reworded_existing_error.py` runs the four message variants (not enough lots, ambiguous matches, missing numbers becoming not enough lots, a changed residual) through `add transaction` and `add transactions --from -`, with controls for a purchase dated after the sale, an unknown account on the appended entry, a backdated purchase that breaks a different existing sale, and a second error on an already failing line; nine of the twelve cases fail with the fix reverted. `import --apply` shares the same validation path but was not run separately. An existing booking failure that a write turns into a different kind of error on the same entry (for example a sale that then books but does not balance) is still refused as new. Only macOS was exercised. `make check-all` passed. Shipped in `a883317f` (`cli`).
