# `bea add` indents new postings by four spaces after a bulk row with posting metadata (and by one space in a tab-indented file), so a formatted file fails `format --check`

**Minor · cli · 30–45m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
Cosmetic, but it breaks a documented promise and any CI gate on
`format --check`. The append path guesses the file's posting indent from
every indented line, so `bea`'s own four-space posting-metadata lines
outvote real postings and the next entry is written with four-space
postings. In a tab-indented file new postings get one space. Meaning is
never changed. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, no TTY, cwd `/absolute/books`; the first
command reads its JSON on stdin, the rest have stdin closed.

```sh
echo '[{"date":"2026-02-01","narration":"Lunch","postings":[{"account":"Expenses:Food","amount":"12.50 USD","meta":{"receipt":"R-1"}},{"account":"Assets:Cash","meta":{"note":"wallet"}}]}]' | bea -f main.bean add transactions --from -
bea format --check main.bean
bea -f main.bean add transaction Coffee --date 2026-02-02 -p "Expenses:Food 4.50 USD" -p Assets:Cash
bea format --check main.bean
```

Actual: both writes exit 0; the first `format --check` exits 0, the second
exits 1 (`would format: /absolute/books/main.bean`). The file ends:

```beancount
2026-02-01 * "Lunch"
  Expenses:Food  12.50 USD
    receipt: "R-1"
  Assets:Cash
    note: "wallet"

2026-02-02 * "Coffee"
    Expenses:Food   4.50 USD
    Assets:Cash
```

Second trigger: in a ledger whose two existing transactions indent their
postings with a tab, the same `add transaction` appends ` Expenses:Food
4.50 USD` and ` Assets:Cash` with one leading space, where `bea format`
uses two.

Control: the same batch with `receipt` and `note` as transaction-level
`meta` gives a two-space Coffee entry and `format --check` exit 0 after
both writes. The tab fixture rewritten with two-space indents appends at
two spaces. A worker saw a later `format -i` restore the postings to two
spaces but leave the next bulk row's posting metadata at eight, and
`import --apply` follow the one-space style in the tab case.

Expected: `docs/USAGE.md`: "Appended lines are written where `bea format`
would put them given the file's current contents, so a formatted file stays
formatted after an add".

Cause: `cli/src/bea_engine/ledger/write.py:904` (`_destination_indent`)
samples every indented line that looks like `key value…`, so four-space
posting-metadata lines count as posting indents while a posting with no
amount does not; `_indent_block` (`:985`) applies the winner. For tabs,
`write.py:999` hands the draft, existing tab lines included, to the
upstream aligner, which normalises to the most frequent indent length, and
a tab has length one.

Fix: count only posting (account) lines when choosing the indent, and give
the append draft the same two-space posting canonicalisation that
`bea format` applies before alignment. No dependency or API change.

Blast radius: every `add` type that writes indented lines,
`add transactions`, and `import` (preview diff and apply), on files that
contain posting metadata or tab indents.

Dedupe: board search for `_destination_indent`, four-space, "stays
formatted" and tab with indent finds w3/done/267 (`bea format` itself
turning tabs into one space) and w1/done/094 (which introduced four-space
posting-metadata nesting); neither covers appends.

Acceptance: both fixtures append postings at two spaces with posting
metadata at four, and `format --check` stays 0 after `add`, bulk add and
import; a regression test covers each trigger. Only macOS and the checkout
were exercised.

---

**Resolved 2026-10-13** — The append path in `cli/src/bea_engine/ledger/write.py` now chooses the destination's posting indent from posting lines only, found with the same lexer pass `bea format` uses (shared from `cli/src/bea_engine/ledger/formatting.py`), so four-space posting-metadata lines no longer outvote the two-space postings they sit under. The draft handed to the aligner also gives existing postings the indent `bea format` would, so a tab-indented ledger no longer pulls new postings to a single space; existing bytes are still never rewritten. The regression test `cli/tests/test_append_indent_follows_postings.py` covers `add transaction`, `add transactions` and `import` (preview diff and apply) after a bulk row with posting metadata and in a tab-indented ledger, plus the transaction-level-metadata and two-space controls; three of its five cases fail with the fix reverted. A ledger whose postings are consistently indented by four spaces still receives four-space appends, as before, and a tab-indented ledger itself still fails `format --check` until it is formatted, although the appended lines already sit where `bea format` leaves them. Only macOS was exercised. `make check-all` passed. Shipped in `40e22943` (`cli`).
