# `--allow-errors` refuses an ordinary transaction into an account that already has a `onecommodity` violation

**Minor · cli · 30–45m with w5/150 · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
The `onecommodity` plugin attributes its per-account error to the
account's latest posting. A new transaction dated after that posting
becomes the error's source, so the unchanged, pre-existing error is
counted as introduced by the write and `--allow-errors` refuses. Same
function as w5/150; fix together. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
plugin "beancount.plugins.onecommodity"
option "operating_currency" "USD"
2023-01-01 open Assets:Bank USD
2023-01-01 open Assets:Cash
2023-01-01 open Equity:Opening USD
2023-01-01 open Expenses:Food
2023-01-01 open Expenses:Rent

2023-01-02 * "Opening"
  Assets:Bank  1000.00 USD
  Equity:Opening

2023-02-01 * "Lunch"
  Expenses:Food  10.00 USD
  Assets:Bank

2023-02-05 * "Trip lunch"
  Expenses:Food  5.00 EUR
  Assets:Cash
```

`bea check` reports one error, `main.bean:17: More than one currency in
account 'Expenses:Food'`.

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean add transaction --date 2023-03-01 "Dinner" -p 'Expenses:Food 20.00 USD' -p Assets:Bank --allow-errors
```

Actual: exit 1, file unchanged.

```text
Error: The change would introduce 1 new ledger error(s); nothing was written.
  Proposed append (not written): More than one currency in account 'Expenses:Food': EUR,USD
```

Control: the same command posting to `Expenses:Rent` exits 0 and repeats
the line-17 error as a warning. A worker saw the `Expenses:Food` write
succeed when backdated to `2023-02-03`, and the same refusal through `add
transactions --allow-errors` and `import --apply --allow-errors`.

Expected: `docs/USAGE.md` says every add command "accepts `--allow-errors`
for a semantic error already in the books". Appending the transaction by
hand leaves exactly one error with the same message; only the line the
plugin attributes it to moves.

Cause: `cli/src/bea_engine/ledger/write.py:878-893` (`_error_key`)
identifies an error by file, line and message; the plugin's source line
moves to the appended entry, so the key no longer matches the before-set.

Fix: when an after-error does not match on line, fall back to matching on
error class and message against the unconsumed before-errors, at least
for errors sourced in the appended text. Note the message's currency
order (`EUR,USD` / `USD,EUR`) varies between processes, so compare within
one process or normalize. No dependency or API change.

Blast radius: all `add` and `import` writes with `--allow-errors` on
ledgers whose plugin attributes an account-level error to the latest
entry; among stock plugins only `onecommodity` was seen to do so.

Dedupe: w5/150 covers message text that changes on a backdated write;
this is the line that moves on a forward-dated write. w5/079 and 144 are
staging path and line shifts. Board search for `onecommodity` finds
nothing else.

Related case (a worker's observation, 2026-10-11, not re-run): `beancount.plugins.check_commodity`
has the same unstable error text. Its one pre-existing error names the
alphabetically first account using the currency (`Missing Commodity
directive for 'USD' in 'Assets:Bank'`); an `--allow-errors` transaction that
posts USD to an earlier-sorting account changes that text and is refused as
"1 new ledger error(s)". Cover it in the same fix.

Acceptance: the command exits 0, appends the transaction and prints the
one existing error as a warning; a write that makes a second account
multi-currency is still refused. Only macOS and the checkout were
exercised.

---

**Resolved 2026-10-13** — The write validation in cli/src/bea_engine/ledger/write.py now recognises an existing plugin error that an append only re-anchors: after the exact file/line/message match, an unmatched error sourced in the appended text spends an unmatched before-error of the same class whose message has the same words in any order (onecommodity), and an unmatched error reported against no ledger line spends an unmatched before-error of the same class and pseudo-file (check_commodity, whose text names a different account after the write). The before-count still caps how many such errors a write may leave, so a second multi-currency account or a second missing commodity is refused as before. The regression test tests/test_allow_errors_moved_plugin_error.py runs the real command for both plugins, the unaffected-account control and the two still-refused cases; two of its five cases fail with the fix reverted. Deviation from the note: a write that adds a third currency to an already multi-currency account changes the message's currency list and is still refused, since that is the changed-message case w5/150 covers; the bulk and import paths share the same function and were not run separately. Only macOS was exercised. `make check-all` passed. Shipped in `c7e4fdef` (`cli`).
