# Keep stable import IDs anchored to written source facts

**Major · cli · 45–60m · A1.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `21029d403`, Darwin 25.5.0 arm64; frontend Python 3.13.3.
No product fix implemented. Both native-bank-ID and generated-ID CSV cases,
plus the Python importer path, reproduced twice from pristine fixtures.

Create disposable `/abs/books/main.bean`:

```beancount
option "operating_currency" "USD"
option "insert_pythonpath" "TRUE"
plugin "cleared_only"

2024-01-01 open Expenses:Uncategorized
```

`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, and no inherited

```sh

```

Actual: both calls exit 0 with `written: 1`, `duplicates: 0`, row status
`new`. The raw ledger gains two identical transactions, each with
`bank_id: "BANK-123"` and `import-id: "bank:BANK-123"`. Unmatched CSV rows
use `!`, so the plugin omits them from the loaded view; it never removes
their source records. `check` passes.

To inspect the resulting accounting data without altering the original,
copy `main.bean` to disposable `unfiltered.bean` and comment out only its
`plugin "cleared_only"` line. Then:

```sh
bea --json --file /abs/books/unfiltered.bean query "SELECT count(*), sum(number) WHERE account = 'Assets:Checking'"
```

It returns `[[2, "-20.00"]]`, instead of one payment and −10.00 USD. These
duplicate source records become duplicate money when no longer filtered.

Controls and scope:

- A plugin returning `entries, []` writes once, then reports `written: 0`,
  `duplicates: 1`; the unfiltered query is `[[1, "-10.00"]]`.
- Omitting `id=Reference` also double-appends: the identical canonical
  `csv:sha256:…` ID is written twice.
- A controlled Python importer returning the same `!` transaction with
  `meta["bank_id"] = "BANK-123"` behaves identically. CSV and Python paths
  were each repeated twice. The public CSV setup suffices to reproduce.

Expected: a stable ID already present on a real transaction in the ledger's
source files prevents re-importing that source payment, regardless of a
view plugin omitting it from the transformed entries. IMPORTING's Duplicate
decisions section says exact IDs are skipped and the ledger itself is the
dedup database; canonical IDs retain identity even after later edits.
Keep genuinely synthesized forecast/amortization entries out of the index.

Cause: `cli/src/bea_engine/importing.py:205` receives `existing` only from
`managed_load.load_file`, after plugins have run. The stable-ID index at
:425–460 filters/indexes that result as `on_disk`; a source transaction
removed from the view is no longer in that list at all. Its native/generated
IDs never reach `identities`/`dated`, despite remaining in
`snapshot.contents`. The shared `answer` path serves CSV and Python imports.
This is distinct from a plugin deliberately changing IDs or source files.

Fix: retain stable identities of transactions actually written in source
even when their entries do not survive plugin transforms. Build/recover
that source identity evidence without reviving synthesized forecast rows
as duplicates. Preserve native-ID conflict/date rules, generated-ID
semantics, and the existing header-normalizer controls. No dependency or
backend/API change is needed.

Dedupe: searched all board states for plugins filtering/removing source
transactions and stable-ID matching, and scanned open/blocked milestone
scopes. Completed w5/866 (`92a53e4e7`) repairs header rewrites on entries
still returned by the loader; it cannot recover absent entries. w5/662
concerns generated projections. No open item or later repair covers this
filtering case. This is a remaining source-identity gap, not a claim that
w5/866 introduced it.

Acceptance: native-ID CSV, generated-ID CSV and Python-importer variants
write once and skip the repeat, preserving the second-run ledger bytes;
the unfiltered source copy contains one payment and −10.00 USD. No-op,
header-normalizer and forecast/generated-entry controls remain correct.
Pin real import/apply/fresh-query journeys. Windows/Linux and repaired
behavior remain unverified. Sanitized evidence and fixtures are retained
under `.tmp/qa-2026-10-20-cli-loop-pass2-2afc4ed1/`, in
`filtered-ids-*`, `filtered-python-*`, `filtered-generated-csv-*` and

## Also affected: a native-ID price changed only in the loaded view

**Additional minor symptom, reproduced 2026-10-21.** HEAD `9e0aa3543`, same
executable/platform and isolated process setup as above. The standard
`currency_accounts` plugin leaves the written transaction present, but
removes its source price annotation in the loaded view. An unchanged export
then becomes a false native-ID conflict rather than a duplicate. This is the
same requirement to anchor identity checks to source evidence; a fallback
that handles only IDs absent from the view would miss this case.

Create `main.bean`:

```beancount

option "operating_currency" "USD"
2024-01-01 open Assets:CashEUR EUR
2024-01-01 open Assets:CashUSD USD
```

Create a synthetic `bank.txt` containing `1.20` and this `importers.py`:

```python
from pathlib import Path
from decimal import Decimal
from beancount.parser import parser

class Imp:
    def identify(self, file): return str(file).endswith(".txt")
    def account(self, file): return "Assets:CashEUR"
    def extract(self, file, existing_entries=None):
        rate = Decimal(Path(file).read_text().strip())
        text = ('2024-02-01 * "Bank" "FX conversion"\n'
                '  bank_id: "fx-001"\n'
                f'  Assets:CashEUR -100 EUR @ {rate} USD\n'
                f'  Assets:CashUSD {100 * rate} USD\n')
        entries, errors, _ = parser.parse_string(text)
        assert not errors, errors
        return entries

CONFIG = [Imp()]
```

Run twice, from the same fixture directory and child environment:


transaction data`; it tells the user to edit/remove the recorded transaction,
change the bank ID or drop the row. A separate preview exits 0 with one

## Also affected: accepted negative amounts wider than native load precision

**Additional minor symptom, reproduced 2026-10-21.** HEAD `d7a950d7f`, same
executable/platform and isolated process setup as above; CLI sources unchanged
since the preceding capture at `89d178b46`. This case needs no plugin and uses
an ASCII bank reference. An unchanged accepted CSV becomes a false native-ID
conflict because the native loader rounds its negative amount on reload.

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

Create `bank.csv`:

```csv
Date,Description,Amount,Reference
2024-02-01,Wide amount,-12345678901.123456789012345678,wide-1
```

Run twice with closed stdin/no TTY and the isolated environment above:

```sh
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --csv date=Date,narration=Description,amount=Amount,id=Reference,decimal=point --account Assets:Cash --default-account Expenses:Food --apply
```

First: exit 0, writes one transaction, retaining the exact amount literal and
`import-id: "bank:wide-1"`. Second: exit **4**, stdout empty, with `Stable ID
matches an entry with different transaction data`. Preview calls it a conflict;
`--duplicates include` cannot resolve it. The source CSV and recorded transaction
are unchanged. Fresh `check` passes; fresh BQL `SELECT number WHERE
account='Assets:Cash'` returns `-12345678901.12345678901234568`.

The native parser's default 28-digit arithmetic rounds unary minus on this
29-significant-digit literal, while the positive counterposting retains its
digits. That native loaded result is an existing upstream behavior, not the
requested change. The CLI already accepts and deliberately preserves the exact
written literal (completed w5/263 and w3/408). Reimporting that unchanged source
must still be an exact duplicate without altering the ledger or native results.

Controls, twice from fresh fixtures:

- The same negative amount without a native ID correctly skips by its generated
  hash. Positive 29- and 31-digit amounts, both signs at 28 digits, and their
  native/generated-ID variants also skip. Across 24 journeys, only the four
  negative wide-number native-ID cases falsely conflict.
- Actually change the final source digit from `...5678` to `...5679`, keeping
  `wide-1`: this must remain a real conflict. The two different written amounts
  reload to the **same** native number, so rounding incoming amounts to 28
  digits or trusting the native ID alone would hide a genuine source change.
- Four additional human-output journeys reproduce unchanged/changed refusals,
  with fresh checks and queries on both original and deliberately changed
  disposable ledger copies. Rejected repeats preserve ledger bytes.

Further cause: `_same_row` (`importing.py:1754–1775`) fingerprints the loaded
entry through `_fingerprint` / `_legs` (:1451 / :1386), comparing its rounded
units against the exact incoming decimal. The stable ID exists in the index;
the source amount evidence differs solely because of loading. This is another
case of this note's source-fact-versus-loaded-view comparison gap, alongside
the price-stripping plugin above. It is distinct from w5/919's Unicode ID
lookup miss, and no other open wide-number reimport repair was found in the
whole-board search. Completed 263/408 preserve write literals; they do not
repair this repeat-import comparison.

Extend acceptance: identical accepted wide-number exports with native IDs skip
at exit 0, while exact source amount changes still conflict even when their
native loaded numbers coincide. Recover exact written unit facts where needed;
`ledger/reader.py:_spelled_entries` alone still uses the ordinary native parser
and repeats this rounding. Reuse the existing exact-number machinery as
appropriate. Preserve native booked amounts, lot/price matching constraints,
source bytes and generated hashes; do not raise global Decimal precision.

## Also affected: a native-ID amortization template conflicts with its own allocation

`/abs/books/importer.py`:

```python
from pathlib import Path
from beancount.parser import parser
from beancount.core.data import Transaction

USE_NATIVE_ID = True

class Rows:
    def identify(self, file):
        return str(file).endswith(".schedule")
    def account(self, file):
        return "Assets:Prepaid"
    def extract(self, file, existing=None):
        entries, errors, options = parser.parse_string(Path(str(file)).read_text())
        assert not errors, errors
        rows = [entry for entry in entries if isinstance(entry, Transaction)]
        for entry in rows:
            if USE_NATIVE_ID:
                entry.meta["bank_id"] = "insurance-2024"
        return rows

CONFIG = [Rows()]
```

Run after the fixed schedule ends in December 2024, as in the tested
2026-10-21 environment; the plugin deliberately omits allocations after
today. From `/abs/books`, closed stdin/no TTY:

```sh

bea --json --no-input -f /abs/books/main.bean import /abs/books/amortization.schedule --config /abs/books/importer.py
```

authored date/location and reaches the native-ID index in

−1200 and −100 falsely disagree. A canonical generated ID takes its
