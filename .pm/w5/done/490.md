# A no-break space between account and amount in `add -p` becomes part of the account name; the refusal shows it as a plain space and offers to open that account

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-16, HEAD `7334a32b`, checkout `bea 0.3.1`, macOS 26.5.1.
Text copied from a web page, a PDF statement or a chat often carries U+00A0
between words. Beancount's lexer does not treat it as whitespace, so the
amount runs into the account name. bea's refusal prints the no-break space
as an ordinary space and suggests `bea add open --account 'Expenses:Food 5'`.
Running that suggestion creates an account whose name contains an invisible
U+00A0 followed by `5`. No product fix implemented.

Any ledger with `Expenses:Food` and `Assets:Cash` open.

```sh
bea -f /abs/main.bean add transaction X --date 2026-01-05 -p $'Expenses:Food 5 USD' -p 'Assets:Cash -5 USD'
```

Actual: exit 1, `Invalid reference to unknown account 'Expenses:Food 5' Did
you mean Expenses:Food? To create it, use bea add open --account
'Expenses:Food 5' --date YYYY-MM-DD.` Following it succeeds and the next add
lands 5 USD in `Expenses:Food 5`. With `-p 'Assets:Cash'` instead, the
error is the misleading `Only one posting may omit its amount`.

Control: a tab or ordinary space between account and amount works.

Expected: a posting with U+00A0 (or another Unicode space) between account
and amount is refused with exit 2, naming the character (`U+00A0 no-break
space`) and its position, or it is read as the separator. Diagnostics show
invisible characters escaped, as bea already does for control characters.

Cause: U+00A0 is not in `CONTROL_CHARACTERS`
(`cli/src/bea_engine/ledger/text.py:28`), and the account check allows any
non-ASCII character, so neither the frontend nor the engine flags it.

Fix: refuse (or normalize to a space) Unicode space separators in `-p` and
account options before parsing; escape them in error text.

Dedupe: w5/165 (no-break spaces in `format`), w5/242 and w3/256 (CSV import)
are done; nothing covers `add`.

Acceptance: the command exits 2 naming U+00A0 (or writes the posting to
`Expenses:Food`); the suggested `add open` never contains an invisible
character. A test pins it.

---

**Resolved 2026-10-16** — Shipped in `07ea551c` (`cli`). `add transaction` (`_refuse_unicode_space` in `cli/src/bea_engine/ledger/adding.py`) now refuses a `--posting` that holds a Unicode space outside a quoted label, with exit 2: `--posting 1 holds U+00A0 (No-Break Space) at character 14: 'Expenses:Food\xa05 USD'. … Retype it as a space.` The text is shown escaped, and nothing is written. `parse_account` (`cli/src/bea_engine/ledger/text.py`) refuses any whitespace character in an account name and names it, so `add open --account $'Expenses:Food 5'` cannot create the invisible account. A ledger that already opens such an account can no longer name it in `add`; it still loads and checks. `tests/test_add_unicode_space_in_posting.py` pins three Unicode spaces, with and without an elided leg, plus the quoted-label exception and the `add open` refusal; seven fail without the fix.
