# The update check's 3-second limit applies to each socket read, not to the request: a slowly trickling index keeps `upgrade --check` waiting with no upper bound, and the passive notice adds 3 s to every interactive command without ever caching the result

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1. **Simulation:** the index behaviour comes from a localhost mock reached through the existing `BEA_UPDATE_API_URL` hook. The defect is in how the CLI bounds the request.

`_fetch_latest` passes `timeout=TIMEOUT_SECONDS` (3) to `urlopen`. That
limits each socket operation, not the whole request. A response that
keeps arriving slowly, as on a bad link or behind a captive or
inspecting proxy, is therefore never cut off:

- `upgrade --check` waits for the whole body.
- The passive notice behaves worse. `print_notice` stops waiting after
  `thread.join(3)`, and the daemon thread is killed at exit before
  `write_cache` runs. The failure is never cached, so every interactive
  command pays the 3 s again, on every run.

No product fix implemented.

Setup: a localhost mock serves `{"info":{"version":"9.9.9"}}` one byte at
a time with a 1–2 s gap between bytes. Use isolated
BEA_CONFIG_DIR/XDG_CACHE_HOME, `BEA_UPDATE_API_URL=http://127.0.0.1:<port>`,
no inherited BEA_FILE/BEA_TOKEN, and closed stdin.

```sh
bea --json upgrade --check            # 1 s gap
bea upgrade --check                   # 2 s gap
```

For the notice, the hunter used a pipx-layout venv, so that
`current_channel()` is `pipx` and the notifier is active, with
`BEA_NO_UPDATE_NOTIFIER` unset, running `bea engine status` under a PTY.

Actual:

- `--json upgrade --check` takes 29 s and then reports `"latest":
  "9.9.9"`. I measured this myself, and the hunter got 29.4 s.
- With a 2 s gap the text run takes 58.4 s.
- Notice: each of 5 runs took about 3.2 s, printed no notice, and left no
  `update-check.json`. The mock logged one request per run.

Control:

- A server that never responds: the first run takes 3.1 s and writes the
  cache, and later runs take 0.16 s with no request.
- A normal response is cached on the first run.

Expected:

- `docs/USAGE.md` says each outcome is cached "so an offline machine
  waits at most once a day and prints nothing".
- `TIMEOUT_SECONDS` (`cli/src/cli/update.py:41-43`) is documented as "The
  whole budget for the check".
- The `print_notice` docstring says "a hung index costs the timeout once
  a day … because the thread still writes the cache that the next run
  reads".

Cause:

- `_fetch_latest` (`cli/src/cli/update.py:145`): a per-operation
  `urlopen` timeout.
- `print_notice` (`update.py:233`): `thread.join(TIMEOUT_SECONDS)`, after
  which the daemon thread dies before `write_cache` (`:179`).

Fix:

- Enforce a total deadline: read in chunks against a monotonic deadline,
  or run the fetch with an overall cutoff.
- When the join in `print_notice` times out, cache the failure from the
  main thread so the next run skips the check.
- Bound `upgrade --check` the same way.
- No dependency change.

Blast radius: every interactive command (via the notice) and `upgrade
--check` for users on slow or proxied networks, with 3 s added to each
command indefinitely.

Dedupe: searched `.pm/**`, including `done/`, for trickle, deadline,
`TIMEOUT_SECONDS`, and notice together with cache. Related notes:

- w5/321: the cache cannot be written (unwritable directory). Here it is
  writable but never reached.
- w5/322: `--check` reporting `unknown` with exit 0.
- w5/188: a price-feed timeout gap.

None covers the per-read timeout or the thread dying before caching.

Acceptance: against the trickling mock, `upgrade --check` returns within
about 3 s as `unknown`. The first notifier run takes about 3 s and writes
the cache, and the next run makes no request. A test with a slow fake
response pins both.

**Resolved.** `cli/src/cli/update.py` changes in three places:

- `_fetch_latest` now reads the body with `read1` chunks against one `time.monotonic()` deadline of `TIMEOUT_SECONDS`, and raises `TimeoutError` once it passes. The background read therefore also stops soon after the budget.
- `upgrade --check` (`check_latest`) runs the fetch through `_fetch_within_budget`, a daemon thread joined for `TIMEOUT_SECONDS`. The explicit check fails at the budget with `Could not check … for a newer release: no answer within 3 s.` It is reported as a failure (w5/322) rather than `unknown`.
- When `print_notice`'s join times out with the check still running, it writes the failure to the cache from the main thread, because the daemon thread dies at exit before it can. The next run that day asks nothing.

`docs/USAGE.md` says the 3 s budget covers the whole check.

`FakeIndex` gained a `trickle` mode that sends one byte at a time, and the conftest leak guard also waits on the new fetch thread. Two tests use it:

- `test_an_explicit_check_of_a_trickling_index_gives_up_at_the_budget`: with a 0.5 s budget and a 0.2 s/byte trickle, the check fails within 1.5 s.
- `test_a_trickling_index_costs_the_budget_once_and_is_cached`: the first notifier run takes under 2.5 s and writes the cache, and the second run makes no request.

With the fix stashed, both fail.
