# A skill's `SKILL.md` saved as UTF-8 with a BOM is silently never discovered by `bea ask`

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-12, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
An agent skill whose `SKILL.md` starts with a byte-order mark (what Windows
Notepad and some editors write) is skipped without a word: the BOM hides
the opening `---` of the front matter. The documented inspection lists the
BOM-less twin and not this one. `bea` tolerates a BOM on ledgers, CSV
imports and bulk JSON. No product fix implemented.

In a fresh project directory `/absolute/proj`:

```sh
mkdir -p .agents/skills/with-bom .agents/skills/no-bom
printf -- '\xef\xbb\xbf---\nname: with-bom\ndescription: Saved as UTF-8 with BOM.\n---\nbody\n' > .agents/skills/with-bom/SKILL.md
printf -- '---\nname: no-bom\ndescription: Saved as plain UTF-8.\n---\nbody\n' > .agents/skills/no-bom/SKILL.md
```

Use BEA_CONFIG_DIR pointing at an empty disposable directory, no inherited
BEA_FILE/BEA_TOKEN, cwd `/absolute/proj`, and the interpreter of the
environment that holds `bea`. Run the inspection from
`docs/agent-skills.md` (no API call, no model):

```sh
python -c "
from cli.ask.skills import load_skills
for s in load_skills():
    print(f'{s.name}\t{s.path}')
"
```

Actual: exit 0 and one line, `no-bom  /absolute/proj/.agents/skills/no-bom/SKILL.md`.
Nothing on stderr.

Control: `no-bom`, the same file without the three BOM bytes, is listed. A
worker saw a CRLF-terminated `SKILL.md` discovered too.

Expected: `docs/agent-skills.md`: "Every immediate subdirectory that
contains a `SKILL.md` with a `name` and `description` is discovered." The
file has both.

Cause: `cli/src/cli/ask/skills.py:24` loads the file with the default
`utf-8` encoding; the leading U+FEFF stops the front-matter parser from
recognising the fence, the metadata comes back empty, and the loader
returns nothing (`:32`).

Fix: read `SKILL.md` as `utf-8-sig`, and add a regression test beside the
existing skill-loader tests. No dependency or API change.

Blast radius: skill discovery for `bea ask`, in both the project and the
user skill directories.

Dedupe: board search for `load_skills`, "skill discovery" and `SKILL.md`
with BOM finds nothing; nearest are w3/done/257 (BOM on ledgers) and
w5/done/021 (the agent-skills doc).

Acceptance: the inspection lists both skills with the same name,
description and body handling. `bea ask` itself was not run; only macOS
and the checkout were exercised.

---

**Resolved 2026-10-13** — The agent-skill loader in `cli/src/cli/ask/skills.py` now reads `SKILL.md` as `utf-8-sig`, so a leading byte-order mark no longer hides the opening front-matter fence and the skill is discovered like its BOM-less twin. The change covers both the project `.agents/skills/` directory and the user skill directory, since they share the same parser. A parametrized regression test in `cli/tests/test_ask.py` writes a BOM skill beside a plain twin in each directory and asserts both are listed with the same description and body and the right path; both cases fail with the fix reverted. The note's inspection snippet from `docs/agent-skills.md` now lists both skills; `bea ask` itself was not run, and no documentation change was needed because the documented contract already promised discovery. Only macOS was exercised. `make check-all` passed. Shipped in `d4edd750` (`cli`).
