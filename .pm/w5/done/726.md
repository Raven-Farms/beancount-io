# The BQL syntax-error caret is placed by character count, so a query with CJK or other wide characters points two columns short per wide character

**Trivial · cli · 5m · A1.** Real CLI QA, 2026-10-17, HEAD `cc6b52ed`, checkout `bea 0.3.1`, macOS 26.5.1.
No product fix implemented.

```sh
bea -f /abs/main.bean query "SELECT payee WHERE payee = '東京' AND AND"
```

Actual: the caret line has the same number of spaces as for `'ab'`. In a
terminal, `東京` is four columns wide, so the caret lands under `ND` instead
of at the end of the statement. Under an ISO-8859-1 locale, where the
statement is printed escaped, it lands further off (hunter's run).

Expected: the caret uses display width, as table output does.

Cause: `_caret_lines` (`cli/src/bea_engine/query.py:2042`) counts characters.
The width helper already exists (`cli/src/cli/output.py`, around `:277`).

Fix: compute the caret column from the display width of the prefix, after
any escaping.

Dedupe: w5/103, 178 and 276 (done) and 549 (open) cover other caret issues;
none covers width.

Acceptance: the caret sits at the statement end for the CJK query.

**Resolved 2026-10-18** — Shipped in `f3218dd4adb3ec68445bf4baff9c5a50349a9052` (`cli`). `_caret_lines` indents by the display width of the shown prefix instead of its character count, using an engine-side repeat of the frontend `display_width` rule (the frontend cannot be imported across the engine boundary). Reproduced the note's query first (identical caret columns for `'東京'` and `'ab'`), then verified the caret sits at the statement end. New text+json test pins the caret column against the statement's display width; both fail pre-fix while the 10 parents pass both ways. Full suite 9069 passed / 2 skipped; `spec-check` still fails identically on clean HEAD (pre-existing description-only backend drift, recorded under w5/716). No doc change: caret placement is undocumented behavior.
