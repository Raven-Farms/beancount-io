# Bulk `add transactions` now moves every same-day sale after every same-day purchase: a valid sell-then-rebuy batch is refused as "Ambiguous", and under LIFO/FIFO it is written in the wrong order, closing the wrong lot and changing the realized gain (regression from w5/543)

**Major · cli · 15–20m · A1.** Real CLI QA, 2026-10-17, HEAD `eea79d702`, checkout `bea 0.3.1`, macOS 26.5.1. Regression from w5/543 (done, `2b6f0a096`).
w5/543 lets a same-day sale use a purchase listed after it. The fix reorders
unconditionally, so a sale that already books in input order is moved after
an unrelated rebuy. No product fix implemented.

`hold.bean`:

```
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Assets:Brokerage
2026-01-01 open Income:Gains USD
2026-01-01 open Equity:Opening
2026-01-02 * "Deposit"
  Assets:Checking  10000 USD
  Equity:Opening
2026-01-10 * "Buy Jan"
  Assets:Brokerage  10 HOOL {40 USD}
  Assets:Checking  -400 USD
```

`rows.json`, both rows dated 2026-03-05, in this order:
1. "Sell all": `-10 HOOL {} @ 55 USD`, `550 USD` to Checking, rest to
   `Income:Gains`.
2. "Rebuy": `10 HOOL {50 USD}`, `-500 USD` from Checking.

```sh
bea -f /abs/hold.bean add transactions --from rows.json
```

Actual:
- **STRICT (default):** exit 1, `Row 1: Proposed append (not written):
  Ambiguous matches for "-10 HOOL {}": 10 HOOL {40 USD, 2026-01-10}, 10 HOOL
  {50 USD, 2026-03-05}`. Nothing is written.
- **LIFO** (`open Assets:Brokerage "LIFO"`): exit 0, with "Rebuy" written
  before "Sell all". The sale closes the new 50 USD lot: `Income:Gains` totals
  −50 USD, and the January lot stays open. In input order the gain is −150
  USD, with the 50 USD lot left open.
- An intraday buy, sell and buy (hunter's run) is refused under STRICT,
  `--partial` drops the sale, and under FIFO "Sell noon" is written after
  "Buy afternoon".

Control: writing the two rows one at a time exits 0 each, and `check` passes.
Before `2b6f0a096`, the batch was written in input order (hunter's run on the
pre-fix tree). The note's own case (no holding, sale listed first) still
works.

Expected: rows that book in the given order are written in that order. Only a
sale that cannot book is moved after its same-day purchase.

Cause: `_same_day_purchases_first` (`cli/src/bea_engine/ledger/adding.py:1499`,
called at `:1425`) moves every same-day sale of an account and commodity after
every same-day buy, without checking whether input order already books.

Fix: validate in input order first, and reorder only the sales that fail
(or only when the account held no position before the sale).

Dedupe: w5/543 (done) is the parent.

Acceptance: the batch writes in input order under STRICT, LIFO and FIFO with
the −150 USD gain; w5/543's fixture still writes. Tests pin both.

**Resolved 2026-10-19** — Shipped in `6468f1cb2` (`cli`). `_same_day_purchases_first` now moves only sales with no position to book against: a sale stays in input order when the ledger holds the lot through its date or an earlier row bought it (same date listed before it, or any earlier date). Reproduced the note's STRICT refusal first (exit 1, `Ambiguous`), then verified the batch writes in input order under STRICT, LIFO and FIFO with the −150 USD gain plus the hunter's-run control. 8 new tests in `tests/test_bulk_sale_keeps_input_order.py` (all fail pre-fix); w5/543's fixture still reorders and passes unchanged. Full suite 9087 passed / 2 skipped; `spec-check` still fails identically on clean HEAD (pre-existing backend drift).
