# A bulk batch with a same-day sale listed before its purchase is refused ("Too many missing numbers"), though USAGE says "a sale can use a purchase appearing later in the input"

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-16, HEAD `c3c42a48`, checkout `bea 0.3.1`, macOS 26.5.1.
Broker exports, and `bea list` (newest first by default), often put a
same-day sale before the buy it closes. Beancount books same-date entries in
file order, and bulk add appends in input order, so the sale finds no lot.
With an explicit lot, it is booked as a short position instead. USAGE's
sentence holds only for a purchase dated earlier. No product fix
implemented.

`sd.bean`:

```beancount
option "operating_currency" "USD"

2026-01-01 open Assets:Checking USD
2026-01-01 open Assets:Brokerage "FIFO"
2026-01-01 open Income:Gains USD
```

Rows, in this order: a 1,000 USD deposit to `Assets:Checking` dated
2026-01-02; a sale `-10 HOOL {} @ 55 USD` dated 2026-03-05 (550 USD to
checking, remainder to `Income:Gains`); a purchase `10 HOOL {50 USD}` dated
2026-03-05 (-500 USD from checking).

```sh
bea -f /abs/sd.bean add transactions --from j.json
```

Actual: exit 1, `Row 2: Proposed append (not written): Too many missing
numbers for currency group 'USD'`, with "Pass --partial to append the 2 valid
rows".

Control: the sale dated 2026-03-06 writes all three rows (exit 0).

Expected: either bulk add writes same-date rows with augmentations before
reductions (the order Beancount needs; keep input order otherwise), or USAGE
says "a purchase dated earlier, or earlier in the input on the same day".

Cause: rows are appended in input order (`cli/src/bea_engine/ledger/adding.py`
bulk path); USAGE's "The whole batch is tried first so a sale can use a
purchase appearing later in the input" (around line 1334) overstates it.

Fix: the stable reorder is preferable, since it fixes broker-order input. At
minimum, correct the sentence.

Dedupe: no `.pm` match.

Acceptance: the batch writes, or USAGE states the same-day limit. A test
pins whichever is chosen.

---

**Resolved 2026-10-17** — Shipped in `2b6f0a09` (`cli`). The note's preferred fix, the stable reorder: `_same_day_purchases_first` (`cli/src/bea_engine/ledger/adding.py`) runs before the batch is validated. Within one date, a row that sells a commodity at cost which another row buys at cost into the same account that day moves after that date's other rows. Each date keeps the slots it held, and nothing else changes order. Detection is linear (a counter of buyers per date). The note's batch now writes all three rows with the purchase first, and the explicit-lot sale is booked as a reduction (50 USD gain) instead of a short position. `written_rows`/`unwritten_rows` stay sorted input indexes. USAGE states the rule beside "a sale can use a purchase appearing later in the input".

`tests/test_bulk_same_day_sale_order.py` covers:
- both lot forms, checked on file order, booking and gain;
- the control, where a later-dated sale keeps its order;
- partial-write indexes.

The first three fail without the fix.

Caveat: a same-day short sale listed before its cover is reordered too. Each row balances on its own, so with the same cost basis the outcome is equivalent. `make check-all` passed.
