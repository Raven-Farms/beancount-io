# With stderr closed, `bea` writes its warnings and errors into stdout: a `query -f csv` export or a `--json` envelope picks up loader errors and still exits 0

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, Python 3.13.3.
When file descriptor 2 is closed (`2>&-`, which is how some schedulers and
supervisors start jobs), Python sets `sys.stderr` to `None`. Every
`print(..., file=sys.stderr)` then writes to **stdout** instead. As a
result, tolerated loader errors end up inside the command's data, and both
cases below still exit 0:

- A `--allow-errors` CSV export starts with two diagnostic lines.
- A `--json` list is followed by text, so it no longer parses.

Error messages go to stdout too (`Error: …`, or the JSON error object).
[258](./done/258.md) fixed the closed-stdout case and recorded that "other
closed-stderr behaviour was not examined". No product fix implemented.

Create disposable `/absolute/books/bad.bean`:

```beancount
option "operating_currency" "USD"
2026-01-02 * "x"
  Assets:Nope  1 USD
  Equity:Opening
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bea -f /absolute/books/bad.bean query --allow-errors -f csv "SELECT account, number" 2>&- > out.csv
bea -f /absolute/books/bad.bean --json list transaction --allow-errors 2>&- > out.json
python3 -c "import json; json.load(open('out.json'))"
```

Actual: both `bea` runs exit 0. `out.csv` contains:

```text
/absolute/books/bad.bean:2: Invalid reference to unknown account 'Assets:Nope'
/absolute/books/bad.bean:2: Invalid reference to unknown account 'Equity:Opening'
account,number
Assets:Nope,1
Equity:Opening,-1
```

`out.json` is the envelope followed by the same two lines, so `json.load`
fails with `Extra data`. Every failing command tried also writes its error
to stdout, with the correct exit code: `check`, a missing `--file`, a BQL
syntax error, an invalid `add` date, `report -t nonsense` (text and
`--json`), an unknown command, `cloud status`, and `ask`. Reproduced in
three fresh processes.

Control: the same commands with `2>/dev/null` produce a CSV whose first
line is `account,number`, and `out.json` parses.

Expected:

- `docs/USAGE.md`: `--json` "Emit[s] the JSON envelope on stdout and JSON
  errors on stderr"; "a redirected or piped stdout carries only results";
  "In `--json` mode a failure writes nothing to stdout".
- `note()` in `cli/src/cli/output.py` says it writes "on stderr so it
  never contaminates piped stdout".

With stderr closed, diagnostics should be dropped, as `replay` already
does for a closed stream since 258. They should never be redirected into
results.

Cause: `print(..., file=None)` falls back to `sys.stdout`, and the
diagnostic writers pass `file=sys.stderr` without checking for `None`:

- `cli/src/cli/output.py:53` (`flush_warnings`)
- `cli/src/cli/output.py:102` (`note`)
- `cli/src/cli/output.py:149` (JSON error)
- `cli/src/cli/output.py:180-184` (text error, details, trace)
- `cli/src/cli/output.py:837` (`render_ledger_errors`)
- `cli/src/cli/update.py:236,255`
- `cli/src/cli/commands/upgrade.py:172-174`

Fix: route every diagnostic through one helper that writes to `sys.stderr`
only when it is not `None`, and otherwise drops the text, matching
`output.replay`. Exit codes stay the same. No dependency or API change.

Blast radius: every command that prints a tolerated loader warning, plugin
output, a note, or an error while stderr is closed. Data is corrupted with
exit 0 under `--allow-errors` and lenient reads, and by any successful
command that prints a note. Output passed through from native child
processes was not examined.

Dedupe: searched `.pm/**` (including `done/`) for `2>&-`, "closed stderr",
"stderr closed" and `sys.stderr is None`.

- w5/258 covers closed stdout and the `query --source` closed-stderr
  crash, and leaves other closed-stderr behaviour unexamined.
- w1/107 covers a closed-stdout flush crash.
- w3/378 covers a closed pipe reader.

None of these covers diagnostics redirected into stdout.

Acceptance:

- On the fixture with `2>&-`, `out.csv` starts with `account,number` and
  `out.json` parses as a single envelope, both with exit 0.
- `bea --json report balance-sheet -t nonsense 2>&-` writes nothing to
  stdout and exits 2.
- A real-command regression test covers text, CSV and JSON with stderr
  closed, using `2>/dev/null` as the control.

Only macOS and the checkout were exercised.

---

**Resolved 2026-10-15** — `_discard_diagnostics_without_stderr` (`cli/src/cli/main.py`) runs first in the root group's `parse_args`. When `sys.stderr` is `None`, it points descriptor 2 at `/dev/null` and reopens `sys.stderr` on it. Every diagnostic writer, Click's own usage errors and any engine child that inherits fd 2 now drop their text instead of falling back to stdout. Exit codes are unchanged. On the fixture with `2>&-`, `out.csv` starts with `account,number` and `out.json` parses, both with exit 0. `--json report balance-sheet -t nonsense` on a valid ledger writes nothing to stdout and exits 2; on the note's erroring ledger it exits 1, as the `2>/dev/null` control does. USAGE's automation paragraph says so. `cli/tests/test_closed_stderr_keeps_stdout_clean.py` closes fd 2 in the child and covers CSV, JSON and four failing commands, with `/dev/null` controls; 5 of the 6 closed cases fail with the fix reverted. The first gate run hit an unrelated timing flake in `test_candidate_cleanup.py::test_interrupt_during_spawn_reaches_the_isolated_helper`, which uses a fake engine and passed 5/5 alone; the re-run was green. Only macOS was exercised. `make check-all` passed. Shipped in `8b2ef23b` (`cli`).
