# A typo in `option "operating_currency"` (`"usd"`) is never named: `report` asks for `USD → usd` prices, `add` reports a token error, and `import` cites "column None"

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
Beancount accepts any string for `operating_currency`, so `bea check` exits
0 on `"usd"`. Every command that falls back to the operating currency then
fails in its own confusing way, and none of them names the option line or
the fix (`"USD"`):

- `report` treats the typo as missing prices and exits 1.
- `add` with a bare amount reports a token error and exits 2.
- `import` cites `column None` and exits 2.

[w3/427](../w3/done/427.md) fixed exactly this typo for `--conversion usd`,
which now exits 2 with `Did you mean 'USD'?`. The same value coming from the
ledger's own option is not covered. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "usd"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food
2026-01-01 open Equity:Opening
2026-01-02 * "Open"
  Assets:Checking  100.00 USD
  Equity:Opening
```

and `/absolute/books/s.csv` (`Date,Payee,Amount` / `2026-01-06,Cafe,-3.00`).
Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bea -f /absolute/books/main.bean check
bea -f /absolute/books/main.bean report balance-sheet
bea -f /absolute/books/main.bean add transaction Lunch --date 2026-01-07 -p 'Expenses:Food 5' -p Assets:Checking
bea -f /absolute/books/main.bean import s.csv --csv date=Date,payee=Payee,amount=Amount --account Expenses:Food
```

Actual:

- `check` exits 0.
- `report balance-sheet` exits 1 with `Error: Missing prices for USD → usd.
  … Add prices covering the dates below or pass --allow-errors for partial
  balances.` `--json` reports category `validation` with `missing_prices:
  [{"from": "USD", "to": "usd"}]`. `bea balance` behaves the same way.
- `add` exits 2 with `Error: Directive 1 of 1 would be written as 0
  directive(s); a field holds a line break or a value that is not one token
  (Beancount: Invalid token: 'usd'). Nothing was written.`
- `import` exits 2 with `Error: Row 1 (line 2), column None: 'usd' is not
  one commodity; …`.

The ledger is unchanged. Reproduced in three fresh runs, one of them an
independent rerun.

Control: with `option "operating_currency" "USD"`, all four commands work.
`report balance-sheet -x usd` exits 2 with `Invalid --conversion 'usd'. …
Did you mean 'USD'?`.

Expected: invalid report inputs exit 2 and name the problem, and w3/427
established that `usd` is a typo to name, not a currency to price. Whenever
a command falls back to the operating currency, an invalid value should be
refused with exit 2, naming the option, its line, and the suggestion `USD`.
Alternatively, `check` could flag it as a ledger error. It should never
surface as a missing-price instruction, a token error, or `column None`.

Cause:

- `cli/src/bea_engine/report.py:408-409` takes
  `options["operating_currency"][0]` unchecked. The w3/427 validation
  (`a6c0231b`) runs only on the `-x` value.
- `cli/src/bea_engine/ledger/adding.py:725-741` uses `currencies[0]` for a
  bare amount, and the render/reparse guard then rejects it as a token
  problem.
- `cli/src/bea_engine/csv_mapper.py:1089-1102` falls back to the ledger
  currency and formats the error with `columns.get('currency')`, which is
  `None` when no currency column is mapped.

Fix: validate `operating_currency` values with the same lexer check w3/427
uses for `-x`, wherever the default is read. Refuse an invalid value with
exit 2: "`option "operating_currency" "usd"` at main.bean:1 is not a
Beancount currency; did you mean `USD`?". In `csv_mapper`, name where the
currency came from instead of `column None`. No dependency or API change.

Blast radius: on any ledger whose operating currency is not a valid
commodity:

- `report` (all subcommands) and `balance`, which convert to it by default;
- `add transaction` and `add transactions` with bare amounts;
- CSV `import` without a currency column.

`check` and paths with an explicit currency are unaffected.

Dedupe: searched `.pm/**`, including `done/`, for `operating_currency`
together with lowercase, `"usd"`, `→ usd`, "not one commodity" and "column
None". w3/427 covers only the `-x` flag. w3/390, w3/322, w4/163 and w4/164
cover other operating-currency topics. None of them covers a malformed
option value.

Acceptance: on the fixture, the report, `balance`, the bare-amount `add`
and the import each exit 2 naming the option, its line and `USD`, and the
ledger is unchanged. With `"USD"`, all four behave as they do today. A
real-command regression test covers each path. Only macOS and the checkout
were exercised.

---

**Resolved 2026-10-15** — A new `checked_operating_currencies(options)` (`cli/src/bea_engine/ledger/text.py`) refuses an operating currency that is not a Beancount commodity with exit 2. The message names the option line (`at <file>:<line>`, found across the loaded files) and suggests the uppercase spelling, as w3/427 does for `-x`. It is called only where a command falls back to that currency: `report` and `balance` without `--conversion` (`report.py`), a bare `add` amount (`adding.py`), and a CSV import whose rows have no currency column (`importing._row_currency`). An explicit `-x` or a mapped currency column still works on such a ledger. `csv_mapper.py` now names where a bad currency came from (the column, `--csv currency=…`, or the operating currency) instead of `column None`. USAGE's conversion paragraph says so. `cli/tests/test_operating_currency_typo.py` covers the four fallbacks, the explicit-currency controls, and the four paths with `"USD"`; the 4 refusal cases fail with the fix reverted. `check` still accepts the option, as upstream does. Only macOS was exercised. `make check-all` passed. Shipped in `24da97a0` (`cli`).
