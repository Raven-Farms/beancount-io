# A mistyped `--csv encoding=` on a non-UTF-8 export is never named: the file is first decoded as UTF-8, and the refusal tells the user to "Force one with --csv encoding=latin-1"

**Minor · cli · 15–20m · A2.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, Python 3.13.3.
`--csv encoding=` accepts only utf-8, cp1252 and latin-1, plus their
aliases. Plausible values outside that set, such as `iso8859-1`,
`windows1252`, `iso-8859-15`, `sjis` and `shift_jis`, are refused with
`Bad --csv encoding … write utf-8, cp1252, or latin-1.`, but only when the
file happens to be UTF-8.

On the non-UTF-8 export the user was actually trying to fix, the bad value
is silently dropped and delimiter detection decodes the file as UTF-8. The
result is the generic decode refusal, which never mentions the value the
user passed. It tells them to force an encoding, which is what they just
tried. For a Shift_JIS file it also claims `tried utf-8, cp1252, latin-1`,
although latin-1 decodes every byte. No product fix implemented.

Use any valid ledger at `/absolute/books/main.bean`, and
`/absolute/books/sj.csv` written in Shift_JIS:

```text
Date,Payee,Amount
2026-02-03,東京ラーメン,-9.00
```

Also create `/absolute/books/ok.csv`: the same header and an ASCII row, in
UTF-8. Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1,
no inherited BEA_FILE/BEA_TOKEN, closed stdin, and cwd `/absolute/books`.

```sh
bea -f main.bean import sj.csv --csv date=Date,payee=Payee,amount=Amount,encoding=sjis --account Assets:Checking
bea -f main.bean import sj.csv --csv date=Date,payee=Payee,amount=Amount,encoding=bogus --account Assets:Checking
bea -f main.bean import ok.csv --csv date=Date,payee=Payee,amount=Amount,encoding=sjis --account Assets:Checking
```

Actual:

- The first two commands exit 2 with `Error: Cannot decode sj.csv: tried
  utf-8, cp1252, latin-1 (invalid start byte at byte 29). Force one with
  --csv encoding=latin-1.` `iso8859-1`, `windows1252`, `iso-8859-15` and
  `shift_jis` produce the same text.
- The third exits 2 with `Error: Bad --csv encoding 'sjis': write utf-8,
  cp1252, or latin-1.`
- A file that cp1252 can decode, given a bad value, gets `… it decodes as
  cp1252 — pass --csv encoding=cp1252.`, which also ignores the typo.

The ledger is unchanged. Reproduced in three fresh runs, one of them an
independent rerun.

Control: on the UTF-8 `ok.csv`, the same bad values are named correctly. A
supported `encoding=cp1252` on a cp1252 file previews normally.

Expected: `docs/IMPORTING.md` says files are read as UTF-8 "unless `--csv
encoding=` names cp1252 or latin-1", and that the generic decode error is
for runs "Without the key". A key the user passed should be validated
before any read, and refused with the value and the supported set named,
regardless of the file's bytes. The no-candidate message should not list
latin-1 as failed, because latin-1 cannot fail.

Cause:

- `import_entries` (`cli/src/cli/commands/import_.py:564-568`) wraps
  `parse_mapping(csv_request)` in `except UsageError: peek = None`. The bad
  value is dropped, and `csv_encoding` stays `"utf-8"`.
- `detect_delimiter(source, encoding=csv_encoding)` (`import_.py:726-727`)
  then raises `_decode_usage_error` (`cli/src/cli/csv_mapper.py:386-408`)
  before the mapping is parsed for real.
- The last branch of `_decode_usage_error` (`:405-408`) runs when the probe
  falls back to latin-1, so its message describes the working decoding as
  a failure.

Fix: parse the `--csv` spec, or at least its `encoding=` and `delimiter=`
keys, before the first read, and let its `UsageError` propagate. Reword the
latin-1 branch to "decodes only as latin-1 (bytes outside cp1252); pass
`--csv encoding=latin-1` if that is right". No dependency change.

Blast radius: `import` with an explicit `--csv … encoding=<unsupported>` on
any non-UTF-8 export, including a bare `--csv encoding=X` and runs that use
remembered settings.

Dedupe: searched `.pm/**`, including `done/`, for `Bad --csv encoding`,
`tried utf-8, cp1252`, `Force one with`, `sjis` and `iso-8859-15`. Related
notes cover different cases:

- w1/065: UTF-16.
- w5/281: a remembered cp1252 replayed onto a UTF-8 file.
- w3/257: ledger BOM.
- w5/293: `query --source`.

None of them covers this one.

Acceptance: `sj.csv` with `encoding=sjis`, `bogus` or `iso8859-1` exits 2
with `Bad --csv encoding '<value>': write utf-8, cp1252, or latin-1.`,
exactly as `ok.csv` does. The Shift_JIS refusal without the key no longer
claims latin-1 failed. A real-command regression test covers a non-UTF-8
file both with a bad key and without a key. Only macOS and the checkout
were exercised.

---

**Resolved 2026-10-15** — When the early `parse_mapping` peek in `import_entries` (`cli/src/cli/commands/import_.py`) fails, a new `csv_mapper.validate_reading_keys` still checks the spec's `encoding=` and `delimiter=` before the file is read, and its `UsageError` propagates. `sj.csv` with `encoding=sjis`, `bogus` or `iso8859-1` (also as a bare `--csv encoding=…`) now exits 2 with `Bad --csv encoding '<value>': write utf-8, cp1252, or latin-1.`, exactly as on a UTF-8 file. Without the key, the last branch of `_decode_usage_error` (frontend and engine twins) says the file cannot be decoded as UTF-8 or cp1252 and that only latin-1, which reads any byte, accepts it; it no longer lists latin-1 as tried. IMPORTING.md's encoding paragraph says so. `cli/tests/test_csv_bad_encoding_on_non_utf8.py` covers three bad keys on a Shift_JIS export and the keyless refusal; all 4 fail with the fix reverted. `test_csv_encoding_feedback.py` pinned the old "tried" wording and now asserts the new one. Only macOS was exercised. `make check-all` passed. Shipped in `bd0b68a2` (`cli`).
