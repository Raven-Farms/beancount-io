# `bea cloud status` prints a raw `'dict' object has no attribute 'username'` (exit 1, `validation`, request ID lost) when the 200 profile response lacks any required field

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1. **Simulation:** the server behaviour comes from a local mock. The defect is in how the CLI handles it.

The generated `get_user_profile` parser falls back to returning the raw
dict when `from_dict` fails. No exception reaches `call`, so the
documented "Unexpected server response" path never runs, and
`cloud_status` then fails reading an attribute off a dict.

The other hosted reads handle an unreadable body correctly. A partial
body on `cloud ledger list` or `show` gives `Unexpected server response
(HTTP 200).` and keeps the request ID. A version skew in which the
backend renames or omits one profile field turns `cloud status` into an
exception class name. No product fix implemented.

Setup: a localhost mock answers `GET /api-gateway/v1/user-profile` with
200 and `{"id":1,"email":"qa@example.invalid","locale":"en","tier":"free","limits":{},"hasEverSubscribed":false}`.
That is the valid fixture without `username` and `limits.maxDirectives`.
It also sends `X-Request-Id: req-qa-123`. Use isolated
BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1,
`BEA_API_URL=http://127.0.0.1:<port>`, `BEA_DASHBOARD_URL` on localhost,
an obviously fake `BEA_TOKEN`, and closed stdin.

```sh
bea cloud status
bea --json cloud status
```

Actual: both exit 1 with `'dict' object has no attribute 'username'`.
The JSON says category `validation` and has no `request_id`. The hunter
reproduced this four times with two different missing fields (`locale`,
`limits.maxDirectives`), and I reproduced it once.

Control: the full fixture body exits 0 and prints the profile.

Expected: `docs/USAGE.md` says "A successful HTTP response that the
generated parser cannot read exits **1** with `Unexpected server response
(HTTP 200).` … and preserves the request ID when supplied … the CLI does
not expose parser exceptions".

Cause: the generated `get_user_profile._parse_response` returns `cast(…,
data)` when parsing fails. `cloud_status`
(`cli/src/cli/commands/cloud/app.py:102-112`) then reads `user.username`
from a plain dict. w3/m46/t004 guarded only exceptions raised inside
`call`.

Fix: in `unwrap`/`unwrap_or_none`, or in `cloud_status`, treat a parsed
value that is not the expected generated model as `Unexpected server
response (HTTP <status>)`, keeping the request ID. Do not edit the
generated client. Check the other union-typed operations for the same
fallback. No dependency change.

Blast radius: `bea cloud status`, in text and JSON, whenever the profile
response drifts from the schema. That is the first command users run
when something looks wrong.

Dedupe: searched `.pm/**`, including `done/`, for "has no attribute",
`cloud status` together with parser, and "Unexpected server response".
w3/m46/t004 covers parser exceptions at `call`, and w1/055 covers error
bodies. Neither covers the cast fallback.

Acceptance: with a profile body missing a required field, `cloud status`
exits 1 with `Unexpected server response (HTTP 200).` and JSON
`request_id: "req-qa-123"`. The full body still works. A mocked-transport
test pins this.

**Resolved.** `unwrap_or_none` in `cli/src/cli/api/client.py` now takes an optional `model`. On a success status whose parsed value is neither `None` nor an instance of that model, it raises `UnreadableSuccess("Unexpected server response (HTTP <status>).")` with the request ID from the response headers. `bea cloud status` passes `GetUserProfileResponse200Type0`. The generated client is untouched.

I checked the other generated operations: `get_user_profile` is the only one with the `cast(…, data)` fallback. The other raw-JSON operations are untyped `response.json()` successes, so the check is opt-in per call rather than a blanket "dict means unreadable".

`tests/test_cloud_status_unreadable_profile.py` runs against a mocked transport. A profile missing `email`, `locale` or `limits.maxDirectives` exits 1 with that message in text and JSON, and JSON keeps `request_id: "req-qa-123"`. The full body still reads. With the fix stashed, all six missing-field cases fail.

One deviation from the note: `username` is optional in the current schema, so a body missing only `username` now prints `Username: (not set)`. The hunter's body failed because `limits.maxDirectives` was also missing.
