# Two concurrent `add balance` runs both exit 0, bypassing the duplicate and `--force` checks

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-11, HEAD `0227141a` (CLI unchanged since `97600b74`),
checkout `bea 0.3.1`, macOS.
`add balance` decides whether an assertion already exists before it takes
the write lock, and does not carry that decision's snapshot into the write.
Two writers started together therefore both succeed: the ledger ends with two
assertions for the same date, account and currency, which the sequential path
refuses without `--force`. The ledger stays valid. No product fix
implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Equity:Opening USD

2026-01-02 * "Opening"
  Assets:Checking  1000.00 USD
  Equity:Opening  -1000.00 USD
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY. Start both at the same moment:

```sh
bea --json -f /absolute/books/main.bean add balance --date 2026-03-01 --account Assets:Checking --amount "1000 USD" &
bea --json -f /absolute/books/main.bean add balance --date 2026-03-01 --account Assets:Checking --amount "1000.00 USD" &
wait
```

Actual: both exit 0 and the file holds
`2026-03-01 balance Assets:Checking 1000 USD` and
`2026-03-01 balance Assets:Checking 1000.00 USD`. Repeated on two fresh
copies. A worker saw the same with two identical amounts (neither reporting
`"duplicate": true`) and with one writer using `--into` an include.

Controls: run one after the other, the first exits 0 and the second exits 2
with `Assets:Checking already has a 2026-03-01 balance of 1000 USD … Pass
--force to record another assertion`. A worker confirmed two concurrent
identical `add price` runs give one exit 0 and one exit 4, and four
concurrent identical `import --apply` runs give one exit 0 and three exit 4.

Expected: `docs/USAGE.md` says "`add balance` is idempotent the same way:
re-running an identical assertion reports the existing location and writes
nothing, and a different value for the same date, account, and currency needs
`--force`", and treats a ledger that changed between read and write as an
exit-4 conflict. One writer should win; the other should exit 4, or
re-evaluate under the lock and report the duplicate or the refusal.

Cause: `cli/src/bea_engine/ledger/adding.py:264-300`. `_balance` captures
a snapshot and runs its match and conflict checks against it, then appends
(`:300` via `:222-227`) without passing that snapshot, so
`write.append` (`cli/src/bea_engine/ledger/write.py:1217`) captures a
fresh one under the lock and cannot see that the ledger changed since the
decision. `_price` passes `snapshot=snapshot` (`adding.py:596`), which
is why it conflicts correctly.

Fix: pass the pre-check snapshot into the append for the plain balance path,
as `_price` does, so the loser exits 4; or run the match and conflict
checks inside the lock. Check the `--pad-from` branch (`adding.py:310`),
which also appends without a snapshot and was not raced. No dependency or API
change.

Dedupe: board search for `add balance` with idempotent, concurrent and
race finds w3/297 (sequential idempotency, done), w1/137 (precision treated
as duplicate), w1/075 (lock key spelling) and w3/434 (format versus add);
none covers the concurrent bypass.

Acceptance: the two concurrent commands yield one exit 0 and one exit 4 (or
exit 2 with the `--force` message), with one assertion in the file, for
identical amounts, differing precision and `--into`. A regression test
races two real processes. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — `add balance` now writes against the same ledger snapshot it used to decide "already recorded?" and "needs --force?", as `add price` already did, so a writer that lands in between is an exit-4 conflict instead of a second assertion (`cli/src/bea_engine/ledger/adding.py`, with `write_balance` in `writer.py` accepting the snapshot). The `--pad-from` fallback path had the same gap and is covered. Tests race four real processes for identical amounts, differing precision, `--into` and `--pad-from`, and pin the window in-process for the plain, `--into` and `--pad-from` paths; the three in-process cases fail every time with the fix reverted. The losing writer exits 4 and must retry. `make check-all` passed. Only macOS was exercised. Shipped in `8ad77d29` (`cli`).
