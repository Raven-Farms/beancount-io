# `beancount-migrate` turns a split purchase exported as one row per category into separate transactions with separate ids, so the bank's later single row for the total is `new`: the import either fails on the migration's own assertion ("120 too little") or double-books

**Minor · skills · 20–30m · A2.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
`SKILL.md` says "One transaction per non-transfer row". When a source app
exports a split purchase as one row per category, each sharing the date,
account and raw statement description, the migration writes one
transaction and one `import-id` per piece. The bank's own export later
shows the purchase as a single row for the total. Its id and fingerprint
match none of the pieces, so the import treats it as new. Only `qbo.md`
handles splits (`-Split-`). The Mint and Monarch references do not
mention them. No product fix implemented.

Caveat: the fixture assumes that Monarch and Mint export a split as one
row per category. That was not checked against a real export, so this
note is A2.

Monarch-layout `export.csv` (Chase Checking):

```text
"2026-03-05","Paycheck","Paycheck","Chase Checking","ACME CORP PAYROLL","","2500.00",""
"2026-03-12","Costco","Groceries","Chase Checking","COSTCO WHSE #0123","","-80.00",""
"2026-03-12","Costco","Household","Chase Checking","COSTCO WHSE #0123","","-40.00",""
```

Use the environment from [361](./361.md). Follow the skill:

1. Write an opening of 500 and 3 transactions, with ids
   `monarch:sha256:` over `date|amount|Original Statement|Assets:Checking`.
2. Assert `2880.00` on 2026-03-13.
3. Import the bank's CSV, with rows `2026-03-12,COSTCO WHSE
   #0123,-120.00` and one new row, using `--csv
   'date=Date,narration=Description,amount=Amount,sign=bank'`.

Actual:

- The preview shows `2 ready, 0 exact duplicates, 0 possible
  duplicates`, and the Costco −120.00 row is `new`.
- `--apply` exits 1 with `Balance failed … expected 2880.00 USD !=
  accumulated 2760.00 USD (120.00 too little)` and advises "Correct
  missing transactions or edit that assertion". That points away from the
  real cause, a duplicate.
- With the account left unasserted, as the documented conflicting-balance
  path allows, `--apply` exits 0. Checking ends at 2,730.00 instead of
  2,850.00, so Costco is booked twice.

Reproduced twice by the hunter. I checked the skill text myself.

Control: unsplit migrated rows, from Mint and the Monarch overlap
example, dedupe as `duplicate`, including transfers through `import-id-2`.

Expected: `references/mapping.md` promises that "the user's first
`beancount-import` run after migrating won't double-book overlap rows".
When rows share a date, account and raw description but differ in
category, the skill should ask whether they form one split purchase. If
they do, it should write one transaction with one source posting for
the total and one counter-posting per category. The id should be hashed
on the total, which is what the bank row will carry.

Cause: `skills/.claude/skills/beancount-migrate/SKILL.md:54` ("One
transaction per non-transfer row"). `references/mint.md` and
`references/monarch.md` do not mention split rows.

Fix:

- In Identify, detect same-date, same-account, same-description groups
  with differing categories, and ask the user about each group.
- Convert a confirmed split to one multi-posting transaction with one
  `import-id` over the summed amount.
- Add an eval with a split purchase and an overlapping bank row.
- First confirm how the real Mint and Monarch exports represent splits.

Blast radius: migrations from apps where users split purchases (common
for Costco, Amazon and Target), followed by bank imports that overlap the
export period.

Dedupe: searched `.pm/**`, including `done/`, for split together with
migrate, Monarch or Mint. w3/377 is about NFC. w5/m10 covers transfers.
349 is a different cause in bea's importer ids. Nothing covers migrated
split rows.

Acceptance: on the fixture, the migration writes one Costco transaction
for −120.00 with two expense postings, and the later bank import marks
the Costco row `duplicate`. An eval covers it.

**Resolved.** The migrate skill now handles split purchases:

- **Identify** (`SKILL.md`) lists rows that share the date, source account and raw description but have different categories, and asks whether each group is one split purchase.
- **Convert** turns a confirmed group into one transaction: one source posting for the total, one counter-posting per category, and one `import-id` hashed over the total.
- **Verify's** row count counts a split group on the source-row side.
- A new "Split purchases" section in `mapping.md` shows the note's Costco rows and a marked `split-purchase` transaction with its hash input. It also says what to do when the user says the rows are separate.
- `mint.md` and `monarch.md` point at that section.

The new eval9 (`split-purchase-one-transaction`, fixture `eval9_monarch_split.csv`) expects the question, a single −120.00 Costco transaction with two expense postings and one id, the row-count arithmetic, and a 2825.80 assertion.

`test_migrated_split_purchase_is_a_duplicate_of_the_banks_single_row` checks the documented hash input against the transaction. It writes that transaction and runs the `csv-preview` recipe on the bank's single −120.00 row, which comes back `duplicate`. The per-row control (two ids) does not. The test fails without the doc.

The note's caveat still stands: how real Mint and Monarch exports represent splits was not checked. The guidance therefore asks the user rather than merging automatically.

Gate note: run locally, `skills/scripts` resolves `bea` from PATH first. Here that was `/opt/homebrew/bin/bea` 0.1.0, which lacks the migrated-digest matching and returned `new`. With the checkout's `cli/.venv/bin` first on PATH, as CI's `uv run` fallback effectively is, the full skills suite (140 tests) passes. That run re-validated the w5/356–361 changes too.
