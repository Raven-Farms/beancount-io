# A ledger that is not UTF-8 gets the documented decode error from `format` and `add`, but a raw codec message from read commands

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-12, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
For a ledger saved in Latin-1, `bea format` names the file, the byte
offset and the remedy. `list`, `balance`, `query` and `check` instead
report `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in
position 3` as an ordinary ledger error at a line number, and suggest
`--allow-errors`. No product fix implemented.

Create `/absolute/books/latin.bean` with the byte 0xE9 in the payee:

```sh
printf '2026-01-01 open Assets:A\n2026-01-02 * "caf\xe9"\n  Assets:A  1 USD\n  Assets:A  -1 USD\n' > latin.bean
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea --file latin.bean list transaction
bea format latin.bean
```

Actual: the first exits 1:

```text
Error: Ledger has 1 error(s). Pass --allow-errors to report anyway.
  /absolute/books/latin.bean:2: UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 3: unexpected end of data
```

Control: the second exits 1 with `Error: Cannot decode
'/absolute/books/latin.bean' as UTF-8: invalid continuation byte at byte
42. Re-save the file as UTF-8 and retry.` A worker saw `add open` give
that same message, and `balance`, `--json query` and `check` give the raw
one.

Expected: `docs/USAGE.md`: "A file that is not UTF-8 at all fails with its
path, the offending byte offset, and a hint to re-save as UTF-8".

Cause: `format` and `add` map the decode error through
`decode_error_message` (`cli/src/bea_engine/ledger/formatting.py:135`,
`cli/src/cli/commands/format.py:348`); the read path surfaces the upstream
parser's error as a loader error (not traced further).

Fix: read commands and `--json check` report the same path, byte offset
and hint, and do not suggest `--allow-errors` for an undecodable file. No
dependency change.

Blast radius: every read command on a non-UTF-8 ledger or include.

Dedupe: board search for `UnicodeDecodeError`, "not UTF-8" and "Cannot
decode" finds import CSV (w3/done/227), bulk JSON (w3/done/283,
w1/done/112), `format` (w3/done/251, w1/done/166) and stdin BQL (w5/155);
none is the ledger read path.

Acceptance: `list transaction` on the fixture prints the "Cannot decode …
at byte 42. Re-save the file as UTF-8" message; the `format` control is
unchanged. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — The shared ledger load in `cli/src/bea_engine/managed_load.py` now refuses a load whose parser error is a `UnicodeDecodeError` with the same message `format` and `add` give: the file's path, the first undecodable byte offset and the hint to re-save as UTF-8, with no `--allow-errors` suggestion, for the root ledger or an include. That covers `list`, `balance`, `query`, `report`, `price status` and `--json check`; plain `bea check` (`cli/src/cli/commands/check.py`) raises the helper's refusal instead of deferring to bean-check's raw codec line, with or without bean-check options. `tests/test_read_non_utf8_ledger.py` runs the real commands on the note's fixture as a root and as an include, in text and `--json`, plus the `format` control and a Latin-1 byte in a comment that still loads; 15 of its 18 cases fail with the fix reverted. Two deliberate limits: `--allow-errors` no longer reports past an undecodable string (`docs/USAGE.md` now says so), and a file whose non-UTF-8 bytes surface only as `Invalid token` errors (an account name, a UTF-16 file) keeps the parser's own message. Only macOS was exercised. `make check-all` passed. Shipped in `6e568c75` (`cli`).
