# upgrade --check's new version-shape guard still accepts and caches malformed strings such as 0.9banana, 0.9.0.. and 0.9.0+ (incomplete fix of w5/648)

**Trivial · cli · 10–15m · A1.** Real CLI QA, 2026-10-18, HEAD `b7dfbe1bf`, checkout `bea 0.3.1`, macOS 26.5.1. Every response reproduced twice in a fresh child process against a local HTTP stub, isolated config/cache, stdin closed, no TTY. This tests only `--check`; no upgrade or global installation change was run. No product fix implemented.

A loopback server answers `/pypi/beancount-io/json` with one of:

```json
{"info":{"version":"0.9banana"}}
{"info":{"version":"0.9.0.."}}
{"info":{"version":"0.9.0+"}}
```

```sh
BEA_UPDATE_API_URL=http://127.0.0.1:PORT bea --json upgrade --check
```

Actual: each exits 0 with its malformed string in `data.latest`, and the isolated config directory's `update-check.json` stores that string as `version`. These are not valid versions, yet the explicit check records a successful answer.

Controls: `version: null`, `""`, `["0.9.0"]` and `9` now exit 1 with `the index sent an unreadable answer` and create no successful cache entry. `"0.9.0"` exits 0 and caches the real version. Each response used a cleared isolated cache; the nonempty cache evidence was copied before resetting it.

Expected: reject invalid version syntax with the existing unreadable-answer refusal and do not cache it as a successful answer. Preserve any deliberately supported valid prerelease or local-version syntax; this finding does not require changing release-channel policy.

Cause: `_fetch_latest` (`cli/src/cli/update.py:284`) checks `_VERSION.fullmatch`, but `_VERSION` (`:291`) is `\d+(?:\.\d+)+[A-Za-z0-9.+-]*`, which accepts arbitrary suffix letters and punctuation after the initial digits. `check_latest` then caches the accepted answer. This path serves explicit update checks and passive notices; the Homebrew formula parser is separate and was not exercised here.

Fix: use a defined, complete grammar for supported versions, rather than a permissive numeric prefix plus arbitrary suffix. Reuse existing parsing where it represents that policy; no new dependency is necessary for the documented canonical release channel.

Dedupe: whole-board searches for malformed version strings and unreadable index answers found the completed w5/648 (`0f6b26925`) and w5/484/376 parents, with no open coverage for malformed strings that pass the new guard.

Acceptance: the three responses above exit 1 and leave the successful-answer cache absent; canonical `0.9.0` still succeeds. Add valid suffix controls if the supported grammar includes them.

---

**Resolved 2026-10-20** — `_fetch_latest` now accepts an index answer only when it matches PEP 440's own grammar (epoch, release, pre/post/dev segments, local version; the spec's pattern, no new dependency), which PyPI enforces on upload, so `0.9banana`, `0.9.0..` and `0.9.0+` are refused as `the index sent an unreadable answer` with no successful cache entry; `0.9.0`, `1.0.0rc1`, `1.0.0.post2`, `1.0.0.dev3` and `1.0.0+local.1` still read and cache. Release-channel policy is unchanged (`release_parts` still gates the notice on canonical X.Y.Z). `tests/test_message_full_stops_and_index_answers.py` covers both sets. Gate note: `make check-all` had three load-induced managed-price fetch timeouts in `test_price_source_limit.py` (load average ~90); the file passes in isolation. Shipped in `ecba7d95e` (`cli`)
