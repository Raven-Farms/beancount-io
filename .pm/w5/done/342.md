# Ctrl-C during the first ~50 ms of any `bea` run prints a coloured `KeyboardInterrupt` traceback and dies on SIGINT, instead of the documented silent exit 130

**Trivial · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, frontend venv Python 3.13.
The silent-130 interrupt handling lives in the root group's `invoke`. An
interrupt that arrives earlier is not handled:

- while `cli.main` imports its modules;
- while Typer builds the command tree inside `app()`.

Python's default handler then prints a 15–100 line ANSI-coloured
traceback ending in `KeyboardInterrupt`, and the process dies on SIGINT.
A warm `bea --version` takes about 70–80 ms, so the window covers most of
startup, and a cold start (first run after install, slow disk) widens it.
A user who presses Ctrl-C right after a typo in the command line sees a
stack dump. No product fix implemented.

No fixture is needed. Run under a real PTY, with isolated
BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, and no inherited
BEA_FILE/BEA_TOKEN, in an empty directory. A driver forks a PTY, execs
`bea init a --currency USD` (or `bea -f /absolute/books/main.bean list
transaction`), sleeps for a delay, writes `\x03`, and reads the output.

```python
pid, fd = pty.fork()
if pid == 0:
    os.execve(BEA, [BEA, "init", "a", "--currency", "USD"], env)
time.sleep(delay)          # 0.03, 0.045, 0.05, 0.055, 0.2
os.write(fd, b"\x03")
```

Actual:

- At delays of 0.03–0.055 s, most runs end with a coloured traceback and
  `KeyboardInterrupt`, and the process is killed by SIGINT (wait status
  −2).
- The traceback passes through `.venv/bin/bea` → `sys.exit(app())` →
  `typer/main.py` `get_command` → `get_group_from_info` →
  `inspect.get_annotations`, or, at the shortest delays, through `from
  cli.main import app`.
- No file is written.

Reproduced in two rounds by me and in three by the hunter, with `init`
and with `list transaction`.

Control: at 0.2 s, and at any `init` prompt, the run exits 130 with only
`^C` echoed.

Expected: `cli/docs/USAGE.md` says the two signals that mean the run was
ended on purpose are that "`Ctrl-C` still exits 130 and a closed
downstream pipe still exits 141, both without a message." That should hold
from the first instruction `bea` controls, not only once a command
starts.

Cause:

- `_exit_on_interrupt` (`cli/src/cli/main.py:93-114`) is called only from
  `_GuardedGroup.invoke` (`main.py:195-196`).
- The console script is `bea = "cli.main:app"` (`cli/pyproject.toml:32`).
  So a `KeyboardInterrupt` raised while `cli.main` imports its modules
  (`main.py:10-35`) or while `app()` builds its Click group, before
  `invoke`, reaches the interpreter's default handler.

Fix: point `[project.scripts]` at a thin entry point (for example
`cli.__main__:main`) that wraps `from cli.main import app; app()` in
`except KeyboardInterrupt: sys.exit(130)` (and `BrokenPipeError` → 141
for symmetry). Alternatively, install a SIGINT handler before the heavy
imports. Keep the imports lazy so startup time does not regress. No
dependency change.

An interrupt at about 10 ms gives `Fatal Python error: init_import_site`
inside interpreter startup, before any `bea` code runs. That is out of
scope.

Blast radius: every `bea` invocation from an interactive terminal,
whenever Ctrl-C lands during startup. It is cosmetic, but it breaks the
documented exit status for scripts that send SIGINT early.

Dedupe: searched `.pm/**`, including `done/`, for `KeyboardInterrupt` and
for Ctrl-C together with traceback. Related notes cover other stages:

- w3/388 and w5/273: `Aborted!` at prompts and in `check`.
- w5/233: query shell loading.
- w3/440, w5/014 and w1/074: signals during writes.
- w3/449: the `ask` session.

None covers the import or command-build window before `invoke`.

Acceptance: a PTY test that sends SIGINT while `cli.main` is being
imported, and again during command construction, sees exit 130 and no
output beyond `^C`. The later-interrupt and prompt behaviour is unchanged.
Startup time is not measurably slower. Only macOS and the checkout were
exercised.

---

**Resolved 2026-10-15** — `[project.scripts]` (`cli/pyproject.toml`) now points `bea` at a new `cli.entry:main` (`cli/src/cli/entry.py`). It imports `cli.main` and runs `app()` inside `except KeyboardInterrupt: sys.exit(130)` and imports nothing heavy itself, so startup is unchanged. Once a command runs, the existing `invoke` handling applies as before. With the note's PTY driver, Ctrl-C at 0.03, 0.045, 0.055 and 0.2 s gives exit 130 with only `^C` in all 16 runs. The old `cli.main:app` target, driven the same way, died on SIGINT and printed a traceback. `cli/tests/test_entry_startup_interrupt.py` raises `KeyboardInterrupt` deterministically while `cli.main` is imported (a meta-path hook) and while Typer builds the command tree (a patched `get_command`), and asserts a silent 130. The same two scripts against the old target exit −2 with a traceback. It also pins the console-script target. `uv sync` regenerated the venv's `bea`; `uv.lock` is unchanged. The interpreter-startup window before any `bea` code (`init_import_site`) stays out of scope, as the note says. Only macOS was exercised. `make check-all` passed. Shipped in `6cd62642` (`cli`).
