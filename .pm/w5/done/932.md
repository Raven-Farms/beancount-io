# Avoid intermediate year zero in representable fiscal periods

**Minor · cli · 25–40m · A1.** `FY0001` and `FY0001-Q1` refuse valid,
fully representable periods that their calendar spellings report correctly.
The fiscal parser constructs a day in year zero before calculating the
requested start. All four report kinds and `balance` share the failure.
No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `4b8be76ef` (CLI unchanged after pulling
`e65b694f0`), checkout `bea 0.3.1`, macOS 26.5.1 arm64, frontend Python
3.13.3, existing managed Python 3.12.10. Separate subprocesses, closed
stdin/no TTY, isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`.

Create disposable `/abs/books/main.bean`:

```beancount
option "operating_currency" "USD"
0001-01-01 open Assets:Cash USD
0001-01-01 open Income:Salary USD
0001-01-02 * "First salary"
  Assets:Cash 10.00 USD
  Income:Salary -10.00 USD
0002-01-02 * "Second salary"
  Assets:Cash 20.00 USD
  Income:Salary -20.00 USD
```

From `/abs/books`, with the isolated child environment above:

```sh
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean report income-statement --time 0001 --interval quarterly
bea --json -f /abs/books/main.bean report income-statement --time FY0001 --interval quarterly
bea --json -f /abs/books/main.bean report income-statement --time 0001-Q1 --interval quarterly
bea --json -f /abs/books/main.bean report income-statement --time FY0001-Q1 --interval quarterly
bea --json -f /abs/books/main.bean report income-statement --time FY0002 --interval quarterly
```

Actual exits: **0, 0, 2, 0, 2, 0**, with unchanged ledger bytes.
Check passes. Calendar year 0001 reports `[0001-01-01, 0002-01-01)` and
profit 10 USD; calendar Q1 reports `[0001-01-01, 0001-04-01)` and the same
profit. Both fiscal equivalents have empty stdout and a usage envelope on
stderr, for example:

```text
Invalid time filter 'FY0001'. Use month, year, YYYY, YYYY-MM, or a date range such as '2026-01 - 2026-06'. year 0 is out of range
```

FY0002 works and reports profit 20 USD. With no fiscal-year-end declared,
the fiscal year is the calendar year; explicitly adding this valid option
does not change either failure:

```beancount
0001-01-01 custom "fava-option" "fiscal-year-end" "12-31"
```

A quarter can also be fully representable when its whole fiscal year is
not. In a fresh copy, add this option instead:

```beancount
0001-01-01 custom "fava-option" "fiscal-year-end" "06-30"
```

```sh
bea --json -f /abs/books/main.bean report income-statement --time FY0001-Q3 --interval quarterly
```

That Q3 should be `[0001-01-01, 0001-04-01)`, the working calendar Q1,
but also refuses at exit 2 with year zero. This does not require reporting
the unrepresentable preceding July–December or the whole fiscal year.

Reproduced twice from pristine fixtures. The first sweep ran 32 fiscal and
calendar comparisons across years 0001, 0002, 9998 and 9999. A further
64 comparisons covered default, explicit December, June and next-year March
year ends, plus eight direct calls covering overview, balance sheet, trial
balance and balance at FY0001. All eight aliases refuse identically. Valid
`15-31` next-year fiscal periods beginning in year 0001 work; genuine FY0000
remains refused. All source checks pass and all reads preserve bytes.
Upper-limit fiscal failures were recorded too, but are outside this repair:
the existing exclusive-end limitation and explicit calendar recovery policy
from completed w3/407 remain intact.

Cause: `cli/src/fava/util/date.py:get_fiscal_period` (:505–541) constructs
`date(year - 1 + fye.year_offset, month, day) + ONE_DAY` at :525 before
calculating either the requested year or quarter. For default/explicit
December FY0001, it tries `0000-12-31` instead of directly obtaining
`0001-01-01`. June FY0001-Q3 also constructs the unrepresentable whole-year
start before adding its six-month quarter offset. `parse_date` (:465, :470)
passes both fiscal forms here; `TimeFilter` at
`cli/src/fava/core/filters.py:394` calls it, and
`cli/src/bea_engine/report.py:_load` (:456–482) wraps the exception as an
invalid spelling. Calendar parsing uses a different path and reaches the
date-minimum clamp support that completed w5/842 already supplies.

Fix: calculate the requested fiscal period's actual start/end without
materializing a previous-year date that is only an intermediate value.
Return representable year/quarter bounds through the existing filter and
date-minimum handling. Preserve June and next-year fiscal definitions,
leap handling, the no-quarter policy for mid-month year ends, and refusal
when an actual requested bound cannot be represented. No broader maximum
date support, dependency, backend or API change is needed. `parse_date` is
the sole caller of `get_fiscal_period`; its other report caller
`_period_terms` uses the same helper to recognize misplaced period arguments.

Dedupe: searched all board states for fiscal boundary/overflow, FY0001 and

only keyword scope was the unrelated PDF-statement milestone w2/m47.

Acceptance: both default and explicit December FY0001/FY0001-Q1 match

**Resolved 2026-10-22** — fixed: `get_fiscal_period` (`cli/src/fava/util/date.py`) now computes the fiscal start as (year, month, day) arithmetic and builds only the bounds it returns, so `FY0001`, `FY0001-Q1` and a June year end's `FY0001-Q3` report the same representable periods as their calendar spellings. A fiscal year that itself starts in year zero (`FY0000`, June `FY0001`) is still refused, and ordinary, leap-day, next-year and mid-month year ends are unchanged (checked against the old function over 3,000+ combinations). Regression tests in `cli/tests/test_report_fiscal_year_one.py` fail without the fix. Full suite green apart from the known `test_release` smoke timeout, which passes alone. Shipped in this commit (`cli`).
