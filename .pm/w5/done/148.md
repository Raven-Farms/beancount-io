# Bidirectional override characters pass the control-character sanitizer into the import preview and `list` tables

**Minor · cli · 30m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
`bea` escapes ESC and other control characters so imported text "cannot
drive your terminal", but Unicode bidi controls such as U+202E
(right-to-left override) pass through raw, directly before the amount cell
in the import preview, and are stored in the ledger. On a bidi-aware
terminal that can reverse how the rest of the row reads. The raw
pass-through is verified from captured bytes; the visual effect was not
observed. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Uncategorized USD
```

`/absolute/books/bank.csv`, where row 1's description ends with U+202E
(bytes `e2 80 ae`) and row 2 contains a raw ESC (`1b`):

```csv
Date,Amount,Description
2026-02-01,-12.34,Refund <U+202E>
2026-02-02,-5.00,Esc <ESC>[31mred
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean import bank.csv --csv auto --account Assets:Cash
```

Actual: exit 0. Preview rows, shown through Python `ascii()`:

```text
1    new     2026-02-01  Refund \u202e           -12.34 USD     hash  unmatched
2    new     2026-02-02  Esc \\x1b[31mred    -5.00 USD      hash  unmatched
```

U+202E reaches stdout raw (and the proposed entry `"Refund <U+202E>"`),
and row 1 is padded one column short.

Control: the ESC in row 2 is escaped to the visible text `\x1b[31mred`. A
worker saw the character stored by `--apply` and printed raw by `list
transaction`, and U+2028 and U+200B pass the same way.

Expected: `docs/USAGE.md` says control characters are "replaced by a
visible `\xNN` rather than passed through, so text from an untrusted
source such as an imported bank export cannot drive your terminal. That
matters most in the `import` preview". The doc's list (C0, DEL, C1) does
not name bidi controls, so this is a gap in the guarantee, not a
contradiction of its wording.

Cause: `CONTROL_CHARACTERS` at `cli/src/cli/utils.py:18` and its twin in
`cli/src/bea_engine/ledger/text.py` cover `\x00-\x1f` and `\x7f-\x9f`
only; `display_width` in `cli/src/cli/output.py` counts format characters
as one column.

Fix: also escape U+202A–202E, U+2066–2069 and U+2028/2029 (arguably
U+200E/200F/061C) in both sanitizers, and count remaining format
characters as width 0. No dependency or API change.

Blast radius: every table (`import` preview, `list *`, `price status`,
report breakdowns), `list --details`, error details, and engine-side write
sanitising.

Dedupe: board search for bidi, 202e, right-to-left override and U+2028
finds only dashboard RTL items; the nearest CLI notes are w3/392 (ESC from
CSV, done), w1/134, w5/107 and w5/108, all C0/C1.

Acceptance: the preview shows a visible escape for U+202E and the row is
aligned; the written narration carries the escaped form; ordinary
right-to-left text (Arabic, Hebrew letters) is untouched. Only macOS and
the checkout were exercised.

---

**Resolved 2026-10-13** — The control-character sanitizer in `cli/src/cli/utils.py` and its engine twin in `cli/src/bea_engine/ledger/text.py` now also escape the Unicode bidirectional overrides, embeddings and isolates (U+202A–202E, U+2066–2069), written as a visible `\uNNNN`, so the import preview, `list` tables, query tables, diagnostics and the stored narration all carry the escaped form; raw `ask` directive text containing one is refused like any other control character. `display_width` in `cli/src/cli/output.py` counts the remaining format characters (zero-width space and joiner, directional marks) as zero columns, which restores row alignment, and `cli/docs/USAGE.md` names the newly escaped characters. The regression test `cli/tests/test_bidi_controls_are_escaped.py` covers both sanitizers for every escaped code point, the width rule, the import preview's alignment, the applied ledger text, `list transaction` on new and pre-existing ledgers, and the ESC and Hebrew/Arabic controls; 34 of its 55 cases fail with the fix reverted. Two deviations from the note: the line and paragraph separators U+2028 and U+2029 are not escaped, because an earlier decision (w1/136) keeps them exactly as written inside a string and the test pins that, and the directional marks U+200E, U+200F and U+061C, which the note called arguable, are left alone because they occur in ordinary right-to-left text. Only macOS was exercised. `make check-all` passed. Shipped in `f635d130` (`cli`).
