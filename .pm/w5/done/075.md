# Import silently skips a later row that repeats an inferred bank reference, and says it is already in the ledger

**Major (missing transactions, exit 0; identity policy is an owner call) ·
cli · 30–45m · A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS. Header inference adopts a `Reference Number` column
as the stable bank ID without being asked. When two rows of one export share
that value and amount — a monthly autopay — the second is classed an exact
duplicate and dropped, with a reason that is false. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"

2026-01-01 open Assets:Checking USD
2026-01-01 open Liabilities:Card USD
2026-01-01 open Expenses:Food
2026-01-01 open Expenses:Uncategorized
2026-01-01 open Equity:Opening

2026-01-02 * "Opening balance"
  Assets:Checking  1000.00 USD
  Equity:Opening
```

and `/absolute/books/rent.csv`:

```csv
Date,Description,Amount,Reference Number
2026-01-01,Rent January,-1200.00,RENT-AUTOPAY
2026-02-01,Rent February,-1200.00,RENT-AUTOPAY
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`, and
a fresh configuration directory so no mapping is remembered.

```sh
bea -f /absolute/books/main.bean import rent.csv --account Assets:Checking --apply
bea -f /absolute/books/main.bean query "SELECT sum(position) WHERE account='Assets:Checking'"
```

Actual: the import exits 0 with `1 ready, 1 exact duplicates`, row 2
`duplicate`, `Row 2: import-id bank:RENT-AUTOPAY is already in the ledger.`
directly above `Matches row 1 of this import:`, and `Wrote 1 entry`. The
query prints `-200.00 USD`. Independent arithmetic over the export: 1000 −
1200 − 1200 = −1400.00. Nothing in the ledger carried that ID before this
run. Repeated twice.

Control: renaming the header to `Ref`, which inference does not treat as an
ID, imports both rows and the query prints `-1400.00 USD`.

Expected: two rows of one export are two bank lines, so an ID that repeats
across them with a different date is evidence the column is not a unique
transaction ID. `docs/IMPORTING.md` already treats an "ID repeated within one
export with different data" as a conflict that "names the earlier row of the
import", and says the fix "is in the source file rather than the ledger"; a
different date is different data in that sense. The row should need review —
exit 4 under `--apply` — and its reason should name row 1 of this import, not
the ledger. The same guide does say IDs "must be stable and unique" and that
date edits "do not change that identity"; that sentence is about later edits
to ledger entries, which is why the identity policy is the owner's call. The
false reason and the unrequested ID inference are defects either way.

Cause: `cli/src/bea_engine/importing.py:614-615` (`_same_row`) compares
only source amounts for `bank` and `import-id` keys, so a same-amount repeat
is an exact match. The reason text at `:339-341` always says "is already in
the ledger"; only the conflict branch (`:319`) checks whether the match came
from this batch. Inference maps `Reference Number` (with `id`,
`transaction id`, `fitid`, …) to `id` in the frontend mapper.

Fix: when a native-ID hit is a row of the same import and its date or
description differs, classify the row as a conflict (or at least a possible
duplicate) with "Stable ID `X` repeats row N of this import"; for a true
same-data repeat inside one file, say "repeats row N of this import" rather
than naming the ledger. Matches against entries already in the ledger keep
today's rule. Consider stating in the header-inference note that the column
was adopted as a bank ID, so a non-unique reference is visible in the preview.
No dependency or API change.

Dedupe: board search for repeated IDs within one export and reference-number
inference finds w1/168 (wording for the in-batch conflict branch) and w3/280
(ID header synonyms); neither covers a same-amount repeat or the reason text.

Acceptance: the fixture needs review with exit 4, names row 1 of the import,
and writes nothing until the user chooses; with `--duplicates include` both
rows land and the balance is −1400.00 USD; a re-import of an already applied
file still skips every row as a ledger duplicate; the different-amount
conflict is unchanged. Only macOS and the checkout were exercised; Python
importers supplying `bank_id` share the engine path by source reading.

---

**Resolved 2026-10-12** — A native bank ID that repeats an earlier row of the same import on a different date is now a `possible_duplicate` whose reason names that row (`Stable ID bank:RENT-AUTOPAY repeats row 1 of this import on a different date…`). On the fixture `--apply` exits 4 and writes nothing; `--duplicates include` writes both rows and the balance is `-1400.00 USD`; `--duplicates skip` is the explicit way to keep one. A same-day in-batch repeat is still written once, and its reason now reads `Repeats row N of this import.` instead of claiming the ledger already held it. Matches against ledger entries are unchanged, so a re-import of an applied file skips every row as a ledger duplicate, and the different-amount conflict is unchanged. `docs/IMPORTING.md` states the rule. Shipped in `b3e98e7f` (`cli`).

Scope decision, recorded because the note left the identity policy to the owner: the trigger is a different **date** only. A shipped test (`test_repeated_native_id_with_a_cleaner_payee_in_one_export_writes_once`, from `3dd10d5e`) pins that a same-day repeat differing only in its description is one transaction, and this change keeps that. Header inference still adopts `Reference Number` as the ID without a dedicated note; the inferred mapping line already shows `id=Reference Number`. If the owner wants description differences to need review too, or wants inference to stop adopting that column, that is a follow-up.

Real-command regression tests cover the review-and-exit-4 path, include followed by a re-import, skip, identical and tidier-description same-day repeats, and the amount conflict. Three fail with the fix reverted. `make check-all` passed. Python importers supplying `bank_id` share the engine path by source reading only. Only macOS was exercised.
