# Another bea write to an include in a different directory makes `add`/`import --apply` exit 4 "The ledger changed during the operation" instead of queueing (gap in w5/183)

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-17, HEAD `5ac35014`, checkout `bea 0.3.1`, macOS 26.5.1. Gap in w5/183 (done).
USAGE:576-578 says `format -i` "is serialized against every other `bea`
write". USAGE:1103-1106 says "Writers queue rather than refuse one another …
unrelated `bea` writes started together all land". That holds only when
every file is in the root's own directory. No product fix implemented.

`books/main.bean` holds `option "operating_currency" "USD"`, opens for
`Assets:Cash` and `Expenses:Food`, `include "2024/jan.bean"`, and 20,000
generated one-line-each transactions, so validating a write takes about a
second. `books/2024/jan.bean` holds one misaligned transaction (so `format
-i` changes it).

```sh
bea -f /abs/books/main.bean add transaction Coffee --date 2024-02-01 -p "Expenses:Food 3.00 USD" -p Assets:Cash &
sleep 0.5; bea format -i /abs/books/2024/jan.bean; wait
```

Actual: `format -i` exits 0. `add` exits 4 with `Error: The ledger changed
during the operation: …/books/2024/jan.bean. Nothing was written; retry.`.
There was no wait notice, and `main.bean` is unchanged. This happened in 3 of
3 fresh rounds (hunter: 10/10, plus 11/20 at random offsets). `import --apply`
fails the same way. Two roots in different directories that share
`../shared/leaf.bean` also fail: a root write raced by `-f rootB --into
../shared/leaf.bean` failed in 4 of 20 rounds with 2 writers and 9 of 10 with
4 writers (hunter's runs).

Control: the same layout with `include "jan.bean"` beside the root succeeds
3/3 (hunter: 10/10). All-in-one-directory two-root races succeed 40/40.

Expected: the add waits for `format -i` (or the other root's write) and then
lands, as USAGE promises. Exit 4 stays for edits made outside bea
(USAGE:1014-1016).

Cause:
- `write.append` locks only the root and the target. `lock_directories`
  (`cli/src/bea_engine/ledger/write.py:720`) locks only the directories of
  written files.
- `LedgerSnapshot.verify` (`:268`) still refuses a change to any included
  file it read.
- `format -i` locks only its own targets (`cli/src/bea_engine/ledger/formatting.py`,
  around `:122-133`).
- In single-directory layouts the shared directory lock hides the gap.

Fix: also take the lock on every file the snapshot reads (shared for reads,
exclusive for targets), or wait on a changed file's lock and re-validate, so
bea writers queue.

Dedupe: w5/183, 181 and w3/389 (done) cover other lock gaps; none covers
includes in another directory.

Acceptance: the race above lands both writes 10/10. A test pins the
`format -i` case.

**Resolved 2026-10-18** — Shipped in `fe80c70963d37fba1abce284272f7b81c3f89719` (`cli`). New `locked_graph` in `bea_engine/ledger/write.py`: probe the include graph, lock root, target, and every file it holds in one global-ordered pass (releasing and retrying when membership changed mid-probe, so locks never stack out of order), and re-read under the locks. `append` widens to it when outermost (a handed-in snapshot is re-verified; a stale one is adopted fresh when this call still owns validation, and still refuses when the caller pre-validated), and the add deciding lock uses it directly, covering transaction/transactions/balance/price, the simple directives, and raw `bea-engine append`. `format -i` is unchanged: its exclusive target lock is what the other writer queues on. Graphs wider than the descriptor limit keep the old narrow behavior (helper moved from `formatting.py` to `write.py` as `descriptors_allow`). Reproduced the note's race first (add rc=4 naming jan.bean), then verified 5/5 misaligned rounds land with every entry present and the leaf formatted; the hunter's two-root `--into shared/leaf.bean` race went from rc=4s pre-fix to all-land post-fix. 2 new cases in `test_cross_directory_writes_queue.py`: the 5-round race (fails pre-fix with the note's exact error) and the descriptor-fallback unit test. Full suite 9029 passed / 2 skipped; `spec-check` still fails identically on clean HEAD (pre-existing description-only backend drift, recorded under w5/716). Remainder split out: `import --apply` keeps its safe exit-4 refusal (verified: nothing written, no corruption) until its apply path re-decides under the lock — tracked as a w5 follow-up note, since its 690-line extract/dedupe/validate interleave needs its own restructure.
