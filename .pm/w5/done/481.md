# `bea engine status` reports a `BEA_ENGINE_PYTHON` override that cannot run the engine as serving, with features "present", while every local command fails and sends the user back to `engine status`

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-16, HEAD `0864aeed`, checkout `bea 0.3.1`, macOS 26.5.1.
The failure message tells the user to "run 'bea engine status' to see which
engine would serve". Status names the override, exits 0, and shows no sign
that it is unusable, so the round trip explains nothing. No product fix
implemented.

```sh
BEA_ENGINE_PYTHON=/usr/bin/true bea engine status
BEA_ENGINE_PYTHON=/usr/bin/true bea --json engine status
BEA_ENGINE_PYTHON=/usr/bin/true bea -f /abs/main.bean check
```

Actual: status exits 0: `Serving from: BEA_ENGINE_PYTHON override
(/usr/bin/true)`, `beangulp: disabled, present`, `beanprice: disabled,
present`; JSON says `provisioned: true`, `serving.tier: override`. `check`
exits 1 with `BEA_ENGINE_PYTHON=/usr/bin/true names an environment with no
'bean-check' (/usr/bin). Correct or unset BEA_ENGINE_PYTHON, or run 'bea
engine status' to see which engine would serve.` A Python without beancount
(`/usr/bin/python3`) gives the same status.

Expected: status probes the override as it probes the managed engine and
reports it as unusable (the same reason `check` gives), with a failing exit
or a clear `usable: false` in JSON.

Cause: `cli/src/cli/commands/engine.py:41` probes only the `managed` tier;
`provision.py:235` counts any override as provisioned; `provision.py:309`
trusts exit 0 without the sentinel that w5/309 added to
`launch.engine_load_failure`.

Fix: probe the serving interpreter whatever its tier (bean-check present,
`bea_engine` importable, the sentinel), report the failure, and only list
features as present if the probe ran.

Dedupe: w5/269, 309, 320, 412 and 419 cover engine failures elsewhere,
not the status output for an override.

Acceptance: both status forms report the override as unusable with the
reason; a working override still reports as now. A test pins it.

---

**Resolved 2026-10-16** — Shipped in `cb4cb7dd` (`cli`). `bea engine status` (`cli/src/cli/commands/engine.py`) now probes the serving interpreter for the `override` tier too, with `launch.engine_load_failure`. An unusable override prints `Usable: no — it cannot load the engine (<reason>). Correct or unset BEA_ENGINE_PYTHON; local commands fail until then.`, and JSON carries `usable: false` and `unusable: <reason>`. A working override and the managed engine also report `usable: true`; the managed engine keeps its `damaged` key. Status still exits 0, like the damaged managed engine. `_packages_importable` (`cli/src/cli/engine/provision.py`) now requires a printed sentinel, so `/usr/bin/true` no longer reads as having every feature present. A Python too old for `-P` is reported as `Unknown option: -P; the engine needs Python 3.12 or newer`, not its usage hint. `tests/test_engine_status_unusable_override.py` pins `true`, a too-old Python and a working override in text and JSON; all fail without the fix.
