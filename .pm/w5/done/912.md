# Keep child source accounts in parent-importer transaction identity

**Major · cli · 45–60m · A1.** An importer filing under a parent account can
silently omit a real payment to a different child account. The two rows get
one generated ID, and even `--duplicates include` cannot keep the second.
Agents importing separate brokerage statements need each cash posting to
survive. No product fix implemented.

Real CLI QA 2026-10-21, checkout `169bb4fb0` (`cli` unchanged since the
`bcd564706` reproduction), `bea 0.3.1`, Darwin 25.5.0 arm64, frontend Python
3.13.3, managed engine Python 3.12 with existing Beangulp. Reproduced twice
from pristine fixtures, bounded separate processes, closed stdin/no TTY,
isolated absolute BEA_CONFIG_DIR/XDG_CACHE_HOME, updater disabled, and no
inherited BEA_FILE/BEA_TOKEN.

Create `/absolute/qa/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Broker:One USD
2024-01-01 open Assets:Broker:Two USD
2024-01-01 open Income:Interest USD
```

Create `one.txt` containing `One` and `two.txt` containing `Two`, each with a
trailing newline. Put this inspected synthetic importer in `importers.py`:

```python
from pathlib import Path
from beancount.parser import parser

class Imp:
    def identify(self, file):
        return str(file).endswith(".txt")
    def account(self, file):
        return "Assets:Broker"
    def extract(self, file, existing_entries=None):
        child = Path(file).read_text().strip()
        entries, errors, _ = parser.parse_string(
            '2024-02-01 * "Broker" "Interest"\n'
            f'  Assets:Broker:{child} 1.00 USD\n'
            '  Income:Interest -1.00 USD\n'
        )
        assert not errors, errors
        return entries

CONFIG = [Imp()]
```

Run with absolute paths:

```sh
bea --json -f /absolute/qa/main.bean import /absolute/qa/one.txt --config /absolute/qa/importers.py --apply
bea --json -f /absolute/qa/main.bean import /absolute/qa/two.txt --config /absolute/qa/importers.py
bea --json -f /absolute/qa/main.bean import /absolute/qa/two.txt --config /absolute/qa/importers.py --apply --duplicates include
bea --json -f /absolute/qa/main.bean query "SELECT account, sum(number) GROUP BY account ORDER BY account"
bea --json -f /absolute/qa/main.bean check
```

Actual, both repetitions: the first writes 1. The second preview leaves the
ledger unchanged and calls Two's payment an exact duplicate of One's:
`import-id csv:sha256:bfb41b5c36505377 is already in the ledger.` Its proposed
entry posts to `Assets:Broker:Two`, while `match.entry` posts to
`Assets:Broker:One`. Apply exits **0**, writes **0**, and leaves the ledger
byte-identical. BQL shows only One `1.00 USD` and Income `-1.00 USD`; Two's
payment is missing. `check` exits 0. Human apply and reversed child order
reproduce the same omission twice each.

Expected: both payments import once, One and Two each hold `1.00 USD`, and
Income is `-2.00 USD`. Different source child accounts are different cash
postings, even when an importer files their documents under one root.

Controls, twice each: return the exact child from `account()` and both rows
are new and write. Different descriptions or distinct native bank IDs also
let `--duplicates include` write both, although their preview still falsely
flags a possible duplicate across children. A manually written One entry
likewise makes Two a possible duplicate; include keeps it. Reimporting the
same child correctly writes 0. Returning both child rows in one initial file
writes 2 because occurrence numbering distinguishes them; splitting that
file into one-row exports exposes the collision. All fresh checks pass.

Cause: `cli/src/bea_engine/importing.py:1281–1296` correctly selects child
source postings when no exact root posting exists, but `_hash_import_ids`
at 2417–2435 retains only their amounts, commodities and lots. It omits each
posting's account, then hashes the parent `account()` value. `_same_row`
at 1754–1775 trusts a canonical generated-ID hit without content checking.
The adjacent `_legs` at 1386–1391 also drops child names, explaining false
possible duplicates and why a migration cannot merely rename the new hash.
The shared callers cover Python importer row hashing, legacy claims, native
ID content checks and twin matching. Ordinary exact-account CSV imports
cannot select two different source children this way.

Fix: include the actual source-account distribution when identifying rows
selected through a filing parent, in both generated IDs and relevant content
matching. Keep exact-account IDs and counter-account edit behavior stable
where possible. Treat old child-blind IDs as lossy: only match a known child
distribution, or surface ambiguity for review; do not silently consume
another child's payment through a legacy lookup. Preserve normal same-child
reimports, parent brokerage extraction, and valid transfer matching. Owning
package is CLI; no API or dependency change is required.

Dedupe: searched all board states for child/subaccount source identity,
hashing and duplicates, and checked open milestone scopes. Completed
[223](./done/223.md), `99c8145b9`, enabled parent filing roots but tested
different commodity/amount legs. Completed [818](./done/818.md),
`072e42ca4`, fixes those rows being mistaken for the other side of a
transfer. Neither retains child names in generated identity. Open
[897](./897.md)/[899](./899.md) omit lot constraints, and
[900](./900.md) has ambiguous description boundaries; this loses the source
posting account itself. Targeted history contains no later repair.

Acceptance: separate one-row files for the two children each write 1 with
distinct IDs, correct per-child and income totals, then each reimport writes
0. Repeat with child order reversed and with old generated IDs already on
disk; keep the exact-account, same-child and combined-file controls. Content
matching must not call a different child distribution an exact twin.

## Native-ID content checks also lose the child distribution

Additional real CLI QA, 2026-10-21, HEAD `58f8ea575` (CLI sources unchanged
after pulling `bca6a678c`), same checkout executable/environment isolation,
macOS 26.5.1 arm64, frontend Python 3.13.3 and existing managed Python 3.12.
This is another caller of the child-blind `_legs` already identified above,
not another finding or a request to change native-ID scope policy.

With one native bank ID under the same filing parent, the original row posts
One = 1 USD and Two = 2 USD. A corrected row posting One = 2 USD and Two =
1 USD is called an exact duplicate, exit 0/written 0/conflicts 0. The total
and bag of amounts are unchanged, but each child account's source amount has
changed. Native-ID content validation should refuse that correction as a
conflict, as it does when a source amount changes without preserving this bag.
Merely changing generated hashes cannot fix a native-ID hit.

Start another pristine directory `/absolute/qa/native`, using the `main.bean`
fixture above. Create `original.json`:

```json
{"one": 1, "two": 2}
```

Create `corrected.json`:

```json
{"one": 2, "two": 1}
```

Create `native-importers.py`:

```python
import json
from pathlib import Path
from beancount.parser import parser

class Imp:
    def identify(self, file):
        return str(file).endswith(".json")
    def account(self, file):
        return "Assets:Broker"
    def extract(self, file, existing_entries=None):
        row = json.loads(Path(file).read_text())
        a, b = row["one"], row["two"]
        entries, errors, _ = parser.parse_string(
            '2024-02-01 * "Broker" "Interest"\n'
            '  bank_id: "distribution-1"\n'
            f'  Assets:Broker:One {a}.00 USD\n'
            f'  Assets:Broker:Two {b}.00 USD\n'
            f'  Income:Interest -{a+b}.00 USD\n'
        )
        assert not errors, errors
        return entries

CONFIG = [Imp()]
```

From that directory, with the isolated child environment above:

```sh
bea --json --no-input -f /absolute/qa/native/main.bean import /absolute/qa/native/original.json --config /absolute/qa/native/native-importers.py --apply
bea --json --no-input -f /absolute/qa/native/main.bean import /absolute/qa/native/corrected.json --config /absolute/qa/native/native-importers.py
bea --json --no-input -f /absolute/qa/native/main.bean import /absolute/qa/native/corrected.json --config /absolute/qa/native/native-importers.py --apply
bea --json -f /absolute/qa/native/main.bean query "SELECT account,sum(number) GROUP BY account ORDER BY account"
bea --json -f /absolute/qa/native/main.bean check
```

Actual: all five commands exit 0. First apply writes 1. Corrected preview and
apply report one exact duplicate and no conflicts; apply writes 0 and leaves
the ledger unchanged. Fresh BQL still returns One `1.00`, Two `2.00`, Income
`-3.00`. Preview's proposed entry shows the swapped amounts, while its match
shows the original distribution. Both source documents remain byte-identical.

Eight fresh control journeys, two repetitions each: unchanged parent row
correctly skips; swapped child amounts incorrectly skip; changing the source
total to One = 2/Two = 2 correctly conflicts at exit 4; returning the exact
child One from `account()` also correctly conflicts on its 1 → 2 change.
Every native-ID write/refusal/repeat preserves the resulting ledger and passes
a fresh check. The five public commands above were replayed twice separately.

The native key follows `_under_id` / `_same_row` (:1734–1775), which obtains
the existing fingerprint and calls `_legs_agree`. `_legs` (:1386–1391) retains
unit/price/lot data without the posting account, and `_legs_agree` matches
those legs irrespective of their order. It therefore accepts this swap before
`_same_row` returns true for the bank key. Include actual source accounts in
this comparison while preserving booked lot splitting within one account and
ordinary counter-account edits. Acceptance must cover a native-ID correction
whose child amounts swap but whose total and amount multiset do not change:
preview reports a conflict and apply exits 4 with zero writes.

---

**Resolved 2026-10-22** — a source leg now carries the child account it posts to when an importer files rows under a parent (empty for the account itself): `_legs_agree`, the split-lot matching and the content checks only match legs of the same child, and the generated ID writes each child posting's account into the hash input. So separate one-row statements for `Assets:Broker:One` and `:Two` are two payments (any order), a native-ID correction that swaps the children's amounts is a conflict (exit 4, nothing written), and an exact-child importer keeps its IDs. The child-blind spelling stays a lookup-only legacy key whose content check requires the same child distribution, so an older ID cannot consume another child's payment. `cli/tests/test_import_child_source_identity.py` fails for the four defect cases without the fix; the 896 unit fixtures gained the new leg element; shipped in the commit that moves this note (`cli`). Other operating systems are unverified.
