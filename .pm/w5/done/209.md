# An account 492 or more levels deep makes `bea balance` and reports fail with a raw `RecursionError` traceback

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
A contrived limit, found while probing scale: a ledger that stock
`bean-check` and `bea check` accept cannot be reported on once an account
name has 492 components. The failure is "The Beancount engine did not
answer" plus a boxed Python traceback printed without `--debug`. No product
fix implemented.

Generate disposable `/absolute/books/m492.bean` (and `m491.bean` with
`n=491` as the control):

```sh
python3 -c "n=492;a='Expenses:'+':'.join(f'L{k}' for k in range(n-1));open('m492.bean','w').write(f'option \"operating_currency\" \"USD\"\n2000-01-01 open Assets:Bank USD\n2000-01-01 open {a} USD\n2001-02-03 * \"t\"\n  {a}  1.00 USD\n  Assets:Bank\n')"
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f /absolute/books/m492.bean balance
```

Actual: exit 1.

```text
Error: The Beancount engine did not answer 'bea-engine balance --file /absolute/books/m492.bean' (exit 1).
```

followed by a boxed traceback through `protocol.py` ending in
`RecursionError: maximum recursion depth exceeded`.

Control: `m491.bean` exits 0 and prints the full tree. A worker saw
`report trial-balance` and `report income-statement` fail the same way from
492 levels, `report balance-sheet` and `report overview` from 978 levels
(there as a one-line `Error: RecursionError: maximum recursion depth
exceeded`, JSON category `validation`), while `bean-check`, `check`,
`list`, `query`, `add note` and `format --check` handled 20,000 levels in
0.3 s.

Expected: `docs/USAGE.md` lists `--debug` as the option that makes errors
"Include exception tracebacks"; this traceback prints without it, and "did
not answer" reads as a broken engine rather than a property of the ledger.
Either the report renders, or it is refused naming the account depth.

Cause: `cli/src/bea_engine/protocol.py:247` (`_jsonable`) recurses once per
tree level, outside the handler that turns engine exceptions into error
envelopes; the vendored `cli/src/fava/core/tree.py:238` recurses for the
deeper band.

Fix: serialize the tree iteratively, or catch `RecursionError` in the
protocol's answering wrapper and report "account nesting too deep" as an
ordinary error. No dependency or API change.

Blast radius: `bea balance` and the four reports, text and JSON.

Dedupe: board search for `RecursionError`, `recursion` and `levels deep`
finds w1/done/112 (deeply nested JSON on stdin for `add transactions`), a
different input and code path.

Acceptance: `bea balance` on `m492.bean` either exits 0 with the tree or
exits nonzero with a one-line message naming the nesting depth and no
traceback; `m491.bean` is unchanged. Only macOS and the checkout were
exercised.

---

**Resolved 2026-10-13** — The engine's answering wrapper in `cli/src/bea_engine/protocol.py` now turns a `RecursionError` raised while encoding the answer (which happened after the command body returned, so no envelope was published) into an ordinary failure envelope, and `bea balance` and `bea report` register a refusal built by `too_deep` in `cli/src/bea_engine/report.py` that names the deepest account and its depth, for example "Account nesting is too deep to report: 'Expenses:L0:L1:…:L490' is 492 levels deep." The same one-line validation error (exit 1, no traceback, also under `--json`) replaces the bare `RecursionError` from the deeper band where building the tree itself fails; the report is refused rather than rendered, and the depth at which refusal starts is unchanged, so a 491-level ledger still prints its tree. `cli/tests/test_deep_account_nesting_is_refused.py` covers balance and all four reports at 600 and 3000 levels in text and JSON, `--debug`, a 40-level control that still reports, `bea check` on the deep ledger, and the protocol wrapper directly; 13 of its 20 cases fail with the fix reverted. The exact threshold still depends on the interpreter's recursion limit, and a command that registers no refusal gets a generic "nests too deeply" envelope instead. Only macOS was exercised. `make check-all` passed. Shipped in `af169c3a` (`cli`).
