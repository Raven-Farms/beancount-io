# Order same-day bulk trades from the lots that can actually book

**Minor · cli · 45–60m · A1.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `79dc0d7aa`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
Both the on-disk partial-holding case and an earlier-row partial purchase
reproduced twice from pristine fixtures; nearby controls repeated twice.
No product fix implemented.

Create `/abs/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Broker HOOL "FIFO"
2024-01-01 open Equity:Opening USD
2024-01-01 open Income:Gains USD
2024-01-01 * "Cash"
  Assets:Cash 1000 USD
  Equity:Opening -1000 USD
2024-01-02 * "Old lot"
  Assets:Broker 1 HOOL {100 USD}
  Assets:Cash -100 USD
```

Create `/abs/books/batch.json`, with the sale before the same-day buy:

```json
[
  {"date":"2024-02-01","narration":"Sell two","postings":[
    {"account":"Assets:Broker","amount":"-2 HOOL {}"},
    {"account":"Assets:Cash","amount":"300 USD"},
    {"account":"Income:Gains"}
  ]},
  {"date":"2024-02-01","narration":"Buy two","postings":[
    {"account":"Assets:Broker","amount":"2 HOOL {150 USD}"},
    {"account":"Assets:Cash","amount":"-300 USD"}
  ]}
]
```

With cwd `/abs/books`, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, and no inherited
`BEA_FILE`/`BEA_TOKEN`:

```sh
bea --json --file /abs/books/main.bean add transactions --from /abs/books/batch.json
bea --json --file /abs/books/main.bean check
bea --json --file /abs/books/main.bean query 'SELECT account, sum(cost(position)) GROUP BY account ORDER BY account'
```

Actual: add exits 1, stdout empty, with one JSON error on stderr:
`Row 1: Proposed append (not written): Not enough lots to reduce "-2 HOOL
{}": 1 HOOL {100 USD, 2024-01-02}`. It reports zero written and preserves the
ledger bytes. Check passes on that unchanged ledger. The error suggests
`--partial`; a fresh fixture with that flag writes only the purchase,
rejects the sale, exits 1 and accurately reports `written_rows: [1]`.
That partial outcome is documented behavior, not a separate finding or
silent data-loss claim.

Working control: on a pristine copy, swap the two JSON objects so the buy
comes first. Both write, check passes, and a fresh query has broker cost
**150 USD**, cash **900 USD**, opening equity **−1000 USD**, gains
**−50 USD**. FIFO closes the old 100 USD share and one new 150 USD share
against the 300 USD proceeds, leaving one new share. All input amounts and
dates are otherwise identical.

The same hole exists for purchases earlier in the batch: omit `Old lot`
from the root and prepend a February 1 `Buy one first` row posting
`1 HOOL {100 USD}` to Broker and `-100 USD` to Cash. Order
`Buy one first, Sell two, Buy two` refuses Row 2 with only one available
share; `Buy one first, Buy two, Sell two` writes all three and produces the
same correct totals above.

Additional controls, each twice: with no existing holding and just the
original two rows, the CLI moves `Buy two` before `Sell two`, writes both,
and leaves no stock/gain with cash 1000 USD. With **two** old shares instead
of one, it correctly preserves `Sell two` before `Buy two`, closes the old
lot for 100 USD gain, and leaves two new shares at 300 USD cost. Preserve
that input-order behavior from completed w5/730.

Expected: the documented whole-batch handling in `cli/docs/USAGE.md:1585`
lets a sale use a purchase later in the same-date input. Having some shares
is not proof that this sale already books in input order. Reorder only a
sale that needs the later same-day purchase to book, while keeping a sale
that actually books in its original place. Do not return to unconditional
reordering, which changed realized gains in w5/730.

Cause: `_same_day_purchases_first` in
`cli/src/bea_engine/ledger/adding.py:1937–2021`, called only by bulk add at
:1827, tracks purchases as sets of `(account, commodity)`. Its
`file_holds` (:1984–1991) returns true for **any nonzero** summed units, and
its `before` set (:2004–2016) records only whether a prior purchase exists.
Neither proves that the available quantity/lots can satisfy the sale. That
boolean blocks the same-day reorder, and later validation rejects the
otherwise bookable batch. `_held_through` itself is also used by close;
the repair should stay in batch ordering, preserving close's semantics.

Fix: make the ordering decision reflect whether this sale can actually book
against the preceding inventory, including quantities and relevant lot
selection. A booking-aware fallback or quantity-aware dependency check must
retain the sufficient-holding control and input row indexes. Keep atomic
refusal and partial-outcome reporting accurate. No dependency, backend or
API change is needed.

Dedupe: searched all board states for partial/insufficient holdings,
quantities, same-day sales and `Not enough lots`, and reviewed current open
milestones. Completed w5/543 added ordering; w5/730 (`6468f1cb2`) added the
nonzero/set guard and its sufficient-holding controls. The current case is
an uncovered boundary of that fix; its recorded successful controls still
hold. No overlapping open item or later repair was found in targeted
history. w5/150 concerns allowed pre-existing errors, not ordering a new
valid batch.

Acceptance: both partial-holding cases write all supplied rows exactly once
with the required same-day buy before the dependent sale, pass check, and
produce the four expected totals above. Zero-holding reorder and
sufficient-holding input order/gain controls remain correct; rejected
atomic writes and explicit partial outcomes remain truthful. Pin real CLI
coverage. LIFO/STRICT variants, `--into`, cost-selector edge cases and
repaired behavior are unverified. Sanitized fixtures, before snapshots and
captures are under `.tmp/qa-2026-10-20-cli-loop-pass2-2afc4ed1/`, especially
`bulk-holdings-{1,2}-*/` and `captures/bulk-holdings-*.json`.

## Additional lot-dependency cases, 2026-10-20

The same ordering classifier also misses a required cost lot and an inferred
purchase, and reorders a valid short-opening/cover pair into an invalid order.
Each case and its controls reproduced twice from pristine fixtures at HEAD
`badebff53` (CLI unchanged through the subsequent pull), using the executable,
isolated environment, closed stdin and commands above. These extend this
item's booking-aware ordering repair rather than create another task against
the same helper. No product fix implemented.

Start each fixture with:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Broker HOOL "FIFO"
2024-01-01 open Income:Gains USD
```

1. **An existing share is the wrong cost lot.** Append this old purchase:

   ```beancount
   2024-01-02 * "Old lot"
     Assets:Broker 1 HOOL {100 USD}
     Assets:Cash -100 USD
   ```

   Supply two February 1 rows to `add transactions`, in this order:
   - Sell: `Assets:Broker -1 HOOL {200 USD} @ 250 USD`,
     `Assets:Cash 250 USD`, inferred `Income:Gains`.
   - Buy: `Assets:Broker 1 HOOL {200 USD}`, `Assets:Cash -200 USD`.

   Actual: exit 1, zero written, byte-identical ledger, `No position matches
   -1 HOOL {200 USD} in Assets:Broker; it holds (1 HOOL {100 USD,
   2024-01-02})`. Swapping the rows writes both and passes check: broker
   cost **100 USD**, cash **−50 USD**, gain **−50 USD**. Counting available
   shares alone therefore cannot repair the original finding.

2. **The later purchase leaves units for booking to infer.** On the base
   fixture, use this complete `batch.json`:

   ```json
   [
     {"date":"2024-02-01","narration":"Sell","postings":[
       {"account":"Assets:Broker","amount":"-2 HOOL {} @ 150 USD"},
       {"account":"Assets:Cash","amount":"300 USD"},
       {"account":"Income:Gains"}
     ]},
     {"date":"2024-02-01","narration":"Buy","postings":[
       {"account":"Assets:Broker","units":{"number":null,"currency":"HOOL"},
        "cost":{"number":"100","currency":"USD"}},
       {"account":"Assets:Cash","amount":"-200 USD"}
     ]}
   ]
   ```

   Actual: exit 1, zero written, unchanged ledger, Row 1 `Too many missing
   numbers for currency group 'USD'`. With the buy first, both write and
   check passes: zero stock, cash **100 USD**, gain **−100 USD**. Keeping the
   original sale-first order but changing only the purchase's null number
   to `"2"` also writes both with those balances. Native inferred units are
   supported input, as USAGE's investment-posting section documents.

3. **A negative position opens a short; a positive one covers it.** On the
   base fixture, use these February 1 rows, already in valid order:

   ```json
   [
     {"date":"2024-02-01","narration":"Open short","postings":[
       {"account":"Assets:Broker","amount":"-1 HOOL {150 USD}"},
       {"account":"Assets:Cash","amount":"150 USD"}
     ]},
     {"date":"2024-02-01","narration":"Cover short","postings":[
       {"account":"Assets:Broker","amount":"1 HOOL {} @ 100 USD"},
       {"account":"Assets:Cash","amount":"-100 USD"},
       {"account":"Income:Gains"}
     ]}
   ]
   ```

   Actual: exit 1, zero written, unchanged ledger, Row 2 `Too many missing
   numbers for currency group 'USD'`. The classifier moves the negative
   short-opening row behind the positive cover: the cover then has no lot.
   Reversing the JSON objects also refuses. Controls: add the two rows
   individually, short first, or write their equivalent native text in that
   order and run the real `bea check` and BQL query. Both controls pass twice,
   with zero stock, cash **50 USD**, gain **−50 USD**. This is a CLI ordering
   error on an otherwise valid batch, not an unsupported short position.

Further cause: `lots` at `adding.py:1956–1968` discards every null units
number, then calls every negative cost posting a sale and every positive
one a purchase. Its `(account, currency)` keys also omit cost constraints.
The only caller remains bulk add at :1827; single-add controls bypass it.
History `8c6145c01` added the explicit null-number exclusion for w5/801, while
the original ordering rule came from `2b6f0a096` (543). Completed 730's
contract already requires retaining an input order that books; its long-sale
controls do not cover this short-opening case. Whole-board searches for
inferred purchases, short covers and same-day cost-lot dependencies found
no other open repair; current milestone scopes do not own this CLI helper.

Extend acceptance: preserve a valid short-first batch, and recognize these
later cost-lot and inferred-unit dependencies without changing the original
sufficient-holding gain controls. Keep row indexes, atomic byte preservation,
and explicit partial results accurate. A booking-aware decision is needed;
neither unit sign nor nonzero inventory alone establishes a dependency.
Additional sanitized evidence is in
`.tmp/qa-2026-10-20-cli-loop-pass7-9d3acadc/`:
`probe_bulk_lot_dependencies.py`, `control_bulk_lot_dependencies.py`,
`bulk-lot-dependency-results.json`, `bulk-lot-dependency-controls.json`,
and `captures/lot-dependency-*.json`.
