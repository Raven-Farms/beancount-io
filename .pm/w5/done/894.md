# Device login replaces the existing credential and reports success even when the granted expiry makes the next command refuse locally

**Minor · cli · 25–40m · A1/A2.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `ea074ff8e`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
Real PTY device-flow client against an owned loopback simulator; no hosted
authentication or server defect claimed. Three expiry failures reproduced
twice, with four controls twice. No product fix made.

Use cwd `/abs/case`, isolated absolute `BEA_CONFIG_DIR=/abs/case/config`
and `XDG_CACHE_HOME=/abs/case/cache`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited
`BEA_FILE`/`BEA_TOKEN`, and an actual terminal/PTY. Seed a private `0600`
`config/credentials.json` in a `0700` directory with an opaque synthetic
old token and `expireAt: "2099-01-01T00:00:00Z"`. Keep its original bytes.

Set both `BEA_API_URL` and `BEA_DASHBOARD_URL` to an owned loopback server.
Set `BROWSER=/usr/bin/true` **in this child only**, suppressing a real
browser launch. The simulator implements the normal device-flow sequence:

1. `POST /api-gateway/v1/cli-sessions` returns synthetic private/user codes,
   `expiresAt: "2099-01-01T00:00:00Z"`, `pollIntervalSeconds: 1`.
2. `GET /api-gateway/v1/cli-sessions/<private-code>` returns
   `{"status":"AUTHORIZED"}`.
3. `POST .../<private-code>/consume` returns a different opaque synthetic
   token and `expireAt: "not-a-timestamp"` with HTTP 200.
4. A correctly authenticated `GET /api-gateway/v1/ledgers` returns `[]`.

Keep codes, tokens, headers and raw authentication response bodies out of
captures; record only route templates and redacted terminal text. Run:

```sh
bea cloud login                       # real PTY; simulator grants immediately
bea --json cloud ledger list          # fresh process, closed stdin/no TTY
```

Actual: login exits **0**, prints `Logged in successfully.`, and atomically
replaces the old credential with the new token and unusable expiry. The
fresh list command exits **3**, stdout empty, with:

```json
{"error":{"category":"auth","message":"Session expired. Run 'bea cloud login' to re-authenticate.","exit_code":3}}
```

It sends **no** ledger-list request: the newly saved file is already unusable
under the client's own expiry rules. Using timezone-less
`2099-01-01T00:00:00` or already-expired `2000-01-01T00:00:00Z` in the grant
produces the same false success and immediate local refusal. All three
variants reproduced twice from fresh configurations with an existing
future-dated credential. No ledger data was touched.

Controls, each twice: a valid future UTC expiry logs in and a fresh list
exits 0, using the new credential. `DENIED` and `EXPIRED` status responses
exit 3 and preserve the original credential bytes. A malformed initial
session response exits 1 with `Unexpected server response (HTTP 200).`,
preserving the original file. Successful writes keep file/directory modes
0600/0700. All synthetic credential files were removed afterward, and the
owned server stopped; no real browser, account, token or quota was used.

Expected: validate a grant's expiry before replacing local credentials or
printing success. Malformed/timezone-less expiry should be a clear
unexpected-server-response failure; an already-expired grant should be a
clear nonzero authentication refusal. Preserve the existing credential
bytes and any supplied request ID. Keep the current strict expiry checks
on later commands; accepting unusable stored state would only hide the
failed login.

Cause: `cli/src/cli/auth/device_flow.py:71–74` unwraps the grant and calls
`save_credentials` immediately. `credentials.py:62–85` validates the token
but never parses or checks `expire_at` before writing/replacing the file.
Its existing `_parse_expire_at` and `Credentials.is_expired` (:35–59) reject
the exact same values when the next command calls `require_credentials`
(:204–210). The generated grant model merely stores the string; generated
client files should not be hand-edited. Device flow is the sole product
caller of `save_credentials`.

Fix: validate the full grant at the device-flow/persistence boundary before
any replacement, reusing the existing aware-UTC expiry semantics. Retain
HTTP context for a bad server grant and the normal retry/login remedy for
an expired one; keep valid grants and the existing privacy modes. Do not
change backend credential policy or add a dependency for this client fix.

Dedupe: searched all board states and active milestone scopes for login
grants, expiry, `save_credentials` and false success. Completed w5/516
(`3f055ad1`) prevents success when `BEA_TOKEN` shadows a login. w5/297,
589 and 811 handle already-unusable stored files, not validating a new grant
before replacing an existing one. Their deliberate stored-expiry refusal
is the passing downstream behavior here. No matching open repair or later
save-path validation found in targeted history.

Acceptance: real-PTY loopback cases for each bad expiry return nonzero,
do not print success and preserve the seeded file; fresh commands can still
read the seeded credential. Valid future grants still replace privately
and authenticate a fresh command; denied/expired-session/malformed-session
controls remain unchanged. Evidence:
`.tmp/qa-2026-10-20-cli-loop-pass4-515fe144/sweep_device_login.py`,
`device-login-simulation.json`, `device-login-v2-{1,2}-*/` and matching
`captures/device-login-v2-*.json`. An initial simulator forgot to ignore
pagination query parameters on the valid list control; it was corrected
before classifying any product result. Hosted behavior, clock-skew remedies,
other expiry types, other platforms and repaired behavior remain unverified.

---

**Resolved 2026-10-22** — the device flow now validates the consumed grant's expiry with the same aware-UTC rules the stored credential is judged by before `save_credentials` runs: an unreadable or timezone-less expiry is an `Unexpected server response (HTTP 200).` failure carrying the response's request ID, an already-expired grant is a nonzero auth refusal saying the saved login is unchanged, and neither prints success or replaces the existing credential; valid grants save as before. `TestUnusableGrants` in `cli/tests/test_device_flow.py` (HTTP-layer mocks, not a real PTY) fails without the fix; the suite's mock grant moved to a far-future expiry; shipped in the commit that moves this note (`cli`).
