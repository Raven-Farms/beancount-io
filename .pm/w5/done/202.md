# An `include` glob with a decomposed (NFD) non-ASCII name fails in `bea` on a ledger stock `bean-check` accepts

**Major · cli · 45m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, Beancount 3.2.3, macOS (APFS).
A ledger that includes `été-*.bean`, where both the include text and the
file names on disk are in decomposed Unicode, loads in stock Beancount
but fails every `bea` command with "File glob … does not match any
files". `bea` normalizes the whole ledger text to NFC before loading,
including the include pattern, and the glob then no longer matches the
NFD directory entries. Decomposed names are what older macOS volumes,
unzip and rsync from macOS produce. No product fix implemented.

In a new directory `/absolute/D` (`e\xcc\x81` is `e` + U+0301):

```sh
printf 'option "operating_currency" "USD"\n2024-01-01 open Assets:Bank USD\n2024-01-01 open Expenses:Food USD\ninclude "e\xcc\x81te\xcc\x81-*.bean"\n' > main.bean
printf '2024-01-02 * "lunch"\n  Expenses:Food  5.00 USD\n  Assets:Bank\n' > "$(printf 'e\xcc\x81te\xcc\x81-2024.bean')"
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bean-check main.bean        # stock, from the managed engine
bea -f main.bean check
```

Actual: stock `bean-check` exits 0. `bea check` exits 1: `<load>:0: File
glob "été-*.bean" does not match any files` (the name printed in
composed form).

Control: the same fixture with composed text and a composed file name
(`\xc3\xa9t\xc3\xa9-*.bean`) passes in both tools. A worker saw
`balance` and every other loading command fail the same way.

Expected: the ledger loads as it does in stock. `docs/USAGE.md` promises
NFC comparison for account names, search terms and BQL literals, and
that "existing bytes are never renormalised as a side effect"; the
compat shim's own docstring says only account names are meant to merge.

Cause: `cli/src/bea_engine/compat.py:68-69` NFC-normalizes the entire
file text, include strings included. Beancount then globs with the NFC
pattern, and wildcard matching compares directory entries byte for byte.
Literal (non-glob) includes survive on macOS only because APFS lookups
ignore normalization.

Fix: match include globs normalization-insensitively (compare NFC of the
pattern with NFC of each listed name), or leave include targets
un-normalized. No dependency or API change.

Blast radius: every loading command, for any wildcard include whose
matching names contain a decomposable character stored NFD. On
normalization-sensitive filesystems literal includes are likely affected
too (not tested).

Dedupe: board search for "does not match any files" with NFD and glob
finds w5/097 (`--into` string compare) and w5/144 (NFD directory breaks
`--allow-errors`); neither is a load failure. w5/199 is the mirror case
on writes.

Acceptance: `bea check` exits 0 on the NFD fixture and `bea balance`
shows the 5.00 USD expense; the NFC control is unchanged. A real-command
regression test creates the file with an explicit NFD name. Only macOS
and the checkout were exercised.

---

**Resolved 2026-10-13** — The load failure no longer reproduces: the w5/144 fix ("keep include paths out of NFC normalization") already puts each parsed include target back in the spelling the file has it in (`_restore_include_paths` in `cli/src/bea_engine/compat.py`), so a decomposed `include "été-*.bean"` is globbed in decomposed form and finds its decomposed files, while account names are still read as NFC. No test pinned that for a wildcard whose own text is decomposed, so this change is test-only: `cli/tests/test_include_glob_decomposed_name.py` creates the included file with an explicit NFD name, asserts the directory kept that spelling, and runs `bea check`, `bea --json check` and `bea balance` (expecting the 5.00 USD expense) against it and against the composed control. With the include restoration disabled, two of the six cases fail, the NFD `--json check` and the NFD `balance`; plain `bea check` passes either way because it hands this all-ASCII-account closure to native bean-check. No source or documentation changed. Only macOS was exercised. `make check-all` passed. Shipped in `684a78a0` (`cli`).
