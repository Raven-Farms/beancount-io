# `bea import --id-key FITID` (or `''`) silently turns a Python importer's native-ID dedupe off, so a reused bank ID with changed data is written with exit 0

**Minor · cli · 15–25m · A1.** Real CLI QA, 2026-10-16, HEAD `8195088f`, checkout `bea 0.3.1`, macOS 26.5.1. Sibling gap of w5/254.
`FITID` is how OFX and most bank exports spell the field, so it is the
natural thing to type. A metadata key must start lowercase, so `FITID`
names nothing. It still replaces the default list (`bank_id`, `fitid`,
`transaction_id`, `imported_id`), which turns native-ID matching off. Only
`id` is case-folded (w5/254), and the "keeps `bank_id`" guard applies only
to a `--csv … id=` mapping. No product fix implemented.

Disposable `main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized USD

2026-02-01 * "COFFEE"
  fitid: "F1"
  Assets:Checking          -4.50 USD
  Expenses:Uncategorized    4.50 USD
```

`importers.py` beside it: a beangulp importer for `.csv` files, account
`Assets:Checking`. For each row it sets `meta["fitid"] = row["Ref"]` and
posts `Amount` to `Assets:Checking`, with the negation to
`Expenses:Uncategorized`. `s.csv`:

```csv
Date,Description,Amount,Ref
2026-02-01,COFFEE,-9.99,F1
```

Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, closed stdin, pristine ledger each time.

```sh
bea -f /abs/main.bean import s.csv --apply
bea -f /abs/main.bean import s.csv --apply --id-key fitid
bea -f /abs/main.bean import s.csv --apply --id-key FITID
bea -f /abs/main.bean import s.csv --apply --id-key ''
```

Actual: the first two exit 4 with `Row 1 (conflict): Stable ID matches an
entry with different transaction data.`, which is correct. `FITID` and `''`
exit 0 and write the row; the ledger then holds two `fitid: "F1"` entries
with different amounts. Re-importing a file that was imported before also
downgrades its exact duplicates to possible duplicates under these keys.

Expected: `cli/docs/IMPORTING.md` says "`--id-key` never silently disables
bank-ID dedupe" and that a reused native ID with different data is a
conflict. Since a metadata key must begin with a lowercase letter, a key
that cannot be one should be refused (exit 2, naming the legal spelling).
Alternatively, a case-insensitive match for a default key should be folded
(`FITID` → `fitid`), as `ID` already is.

Cause: `_effective_id_keys` (`cli/src/bea_engine/importing.py:95-116`)
aliases only `id` (`:112`) and replaces the defaults with whatever else was
typed; `cli/src/cli/commands/import_.py:771` forwards the values unchecked.
The w5/254 resolution records that refusing illegal keys was not taken.

Fix: refuse an empty `--id-key` or one that is not a legal metadata key, and
fold case for the default keys.

Blast radius: `--id-key` on Python-importer and CSV imports; remembered
import settings if the key is persisted.

Dedupe: searched `FITID`, `id-key`. w5/254 (done) fixed `ID`/`id` for the
CSV path only. w3/237, 326, 184 and 210 are other `--id-key` issues, all done.

Acceptance: `--id-key FITID` either matches `fitid` (exit 4 conflict here)
or is refused with exit 2. `--id-key ''` is refused. A test pins both.

---

**Resolved 2026-10-16** — Shipped in `ac237bd5` (`cli`). `_effective_id_keys` (`cli/src/bea_engine/importing.py`) now folds the default native-ID keys' case, as `ID` already folded to `bank_id`: `--id-key FITID` is `fitid` and keeps the exit-4 conflict. A key that cannot be a metadata key (empty, `Ref`, `9id`) exits 2, naming the legal spelling, before anything is read or written. `tests/test_id_key_folds_and_refuses.py` pins `fitid`/`FITID`/`Fitid` (a conflict) and `''`/`Ref`/`9id` (refused, ledger unchanged); all but the lowercase control fail without the fix. `cli/docs/IMPORTING.md` documents both.
