# `cloud ledger create`/`delete` report a connection that was never made (refused, DNS failure) as exit 4 "The outcome is unknown — check the current state before retrying"

**Trivial · cli · 10–15m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1.
The cloud write commands send every httpx transport error to the
unknown-outcome path (exit 4, `conflict`). That includes `ConnectError`
from a refused connection or a failed DNS lookup. In those cases no
request left the machine, so the outcome is known: nothing happened.

`cloud logout` already draws this line: `ConnectError` gives exit 1 and
only a timeout gives exit 4, pinned by
`cli/tests/test_cloud_transport.py:331`. The reads say `Could not reach
the server`. No product fix implemented.

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, an
obviously fake `BEA_TOKEN`, `BEA_DASHBOARD_URL` on localhost, and closed
stdin.

```sh
BEA_API_URL=http://127.0.0.1:9 bea cloud ledger create qa-z
BEA_API_URL=http://127.0.0.1:9 bea --yes --json cloud ledger delete a/b
BEA_API_URL=http://nonexistent-host.invalid bea --json cloud ledger create qa-z
BEA_API_URL=http://127.0.0.1:9 bea cloud ledger list
```

Actual:

- The three writes exit **4** with `Creating ledger 'qa-z' did not
  complete cleanly (ConnectError). The outcome is unknown — check the
  current state before retrying.` (and the delete equivalent).
- `ledger list` exits 1 with `Could not reach the server
  (ConnectError).`

The hunter reproduced this in three rounds plus the DNS case, and I
reproduced it once.

Expected: `docs/USAGE.md` describes exit 4 as "A write whose outcome the
CLI cannot know (a timeout mid-delete)". A refused connection or a
failed lookup should exit 1 with the "Could not reach the server"
sentence, as `logout` does.

Cause: `except (httpx.TimeoutException, httpx.TransportError)` maps to
`unknown_write_outcome` in two places:

- `cli/src/cli/commands/cloud/ledger/app.py:70`;
- the generated `cli/src/cli/commands/cloud/generated/ledger.py:97`,
  which comes from the template in `cli/scripts/gen_cloud_commands.py:205-210`.

Fix: catch `httpx.ConnectError` and `httpx.ConnectTimeout` first and
send them through `to_bea_error` (exit 1). Keep `ReadTimeout` and other
errors raised after the request was sent at exit 4. Change the generator
template and regenerate. No dependency change.

Blast radius: `cloud ledger create`/`delete` (and any generated write)
when offline or with a wrong `BEA_API_URL`. Scripts that see exit 4 are
told to reconcile state that never changed.

Dedupe: searched `.pm/**`, including `done/`, for "outcome is unknown"
together with cloud, and `ConnectError`. w5/309, w5/320, w5/269 and
w5/252 are engine-side. None covers cloud transport.

Acceptance: the four commands above exit 1 with `Could not reach the
server (ConnectError).`. A read timeout on a write still exits 4. A
transport test covers the connect and timeout cases for create and
delete.

**Resolved.** `cloud ledger create` (`commands/cloud/ledger/app.py`) and the generated-write template (`scripts/gen_cloud_commands.py`) now catch `httpx.ConnectError` and `httpx.ConnectTimeout` first and re-raise them. The usual mapping then exits 1 with `Could not reach the server (ConnectError).`. Other transport errors and an unreadable success still go to `unknown_write_outcome` (exit 4). I regenerated `generated/ledger.py` (delete) with the script; the diff is just the new clause. `docs/USAGE.md` now says a write that never connected exits 1.

`tests/test_cloud_write_connect_failure.py` covers create and delete:

- a refused connection and a connect timeout exit 1 with that message;
- a `ReadTimeout` still exits 4, "The outcome is unknown";
- with the fix stashed, the four connect cases fail.

`tests/test_contract.py::test_4_when_a_write_times_out_with_an_unknown_outcome` used `ConnectTimeout` as its mid-delete timeout. It now uses `ReadTimeout`, the case the exit-4 contract describes.
