# `add transaction --posting` rounds a negative amount wider than 28 significant digits; the positive twin is written exactly

**Minor · cli · 40–60m · A1.** Real CLI QA, 2026-10-12, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
The closed milestone w1/m27 requires that every write path puts the typed
decimal on disk, and w3/done/408 fixed exactly this for CSV import. The
`--posting` flag path still loses a digit: a 29-digit negative amount is
rounded to 28, with exit 0, while the positive posting in the same command
is written in full. Realistic only for 18-decimal tokens held in the tens
of billions; Beancount itself rounds such a number on read, so the defect
is the changed bytes and JSON answer. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking
2026-01-01 open Assets:Wallet
2026-01-01 open Equity:Opening
2026-01-01 commodity SHIB
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean add transaction --date 2026-02-01 -n A -p 'Assets:Wallet 12345678901.123456789012345678 SHIB' -p 'Equity:Opening -12345678901.123456789012345678 SHIB'
bea -f main.bean add transaction --date 2026-02-02 -n B -p 'Assets:Wallet 12345678901.123456789012345678 SHIB' -p 'Equity:Opening'
```

Actual: the first exits 0 and writes

```beancount
  Assets:Wallet   12345678901.123456789012345678 SHIB
  Equity:Opening  -12345678901.12345678901234568 SHIB
```

The second (balancing posting left out) exits 1 with `Error:
InvalidOperation: [<class 'decimal.InvalidOperation'>] Pass --debug before
the command for a traceback.`

Control: the same first command with 28 digits
(`1234567890.123456789012345678`) writes both signs exactly. The 29-digit
pair through bulk JSON (`"amount": "-12345678901.123456789012345678
SHIB"`) writes both postings exactly. A worker saw the rounding also for
the bulk shorthand with a price and for `add balance --amount`, and CSV
import exact.

Expected: w1/m27: every write path "asserts the bytes on disk equal the
input's decimal value"; w3/done/408: "do not … truncate the input". Either
the typed digits are written, or the amount is refused naming the 28-digit
limit; never a different number at exit 0.

Cause: `cli/src/bea_engine/ledger/adding.py:649` parses the posting text
with Beancount's parser, whose unary minus is arithmetic under the default
28-digit decimal context, and `bea` then renders the parsed number. The
same mechanism is at `cli/src/bea_engine/ledger/models.py:189` (bulk
shorthand with cost or price) and `adding.py:502` (balance amount). The
408 fix (`copy_negate` in `cli/src/bea_engine/csv_mapper.py:89-101`)
covers only the CSV mapper.

Fix: on these paths take the number from the source text, or re-apply the
sign without context rounding; otherwise refuse wider input with a usage
error. Turn the uncaught `InvalidOperation` into a usage error naming the
amount. No dependency change.

Blast radius: negative numbers wider than 28 digits in `--posting`, bulk
shorthand fragments, and `add balance --amount`.

Dedupe: board search for `copy_negate`, "28 significant", `InvalidOperation`
and unary finds only closed notes (w3/done/408, w1/done/160, w3/done/309);
nothing open.

Acceptance: the first command writes both 29-digit numbers exactly or
exits 2 naming the limit; the second gives a usage error, not
`InvalidOperation`; the 28-digit and bulk controls are unchanged. Only
macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — `add transaction --posting`, the bulk amount shorthand with a cost or price, and `add balance --amount` now read their text through a new `parse_exact` in `cli/src/bea_engine/amounts.py`, which repeats a parse that rounded under a decimal context wide enough for the text, so a negative number wider than 28 significant digits is written digit for digit like its positive twin; a non-terminating quotient such as `1/3` keeps Beancount's own 28-digit reading. The `InvalidOperation` that Beancount's booking raises when it must infer a balancing amount beside such a number is caught in `validate_candidate` (`cli/src/bea_engine/ledger/write.py`) and reported as a usage error, exit 2, with nothing written. `cli/tests/test_add_negative_amount_keeps_digits.py` covers both signs on the flag path with the JSON answer, the priced flag and bulk shorthands, the balance amount, a wide number beside a repeating quotient, the refusal, and the 28-digit control; six of its seven cases fail with the fix reverted. One deviation from the note: the refusal names the 28-digit limit and the remedy rather than the specific amount, because the failure surfaces inside Beancount's loader. A negative wide number beside an inferred leg still succeeds, since Beancount itself reads that number rounded; the bytes written are the typed ones. Only macOS was exercised. `make check-all` passed. Shipped in `2b3b5697` (`cli`).
