# Writers with different `XDG_CACHE_HOME` do not lock each other: both exit 0 and one write is lost

**Major · cli · 60–90m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
`bea` serializes writers with a lock file under each caller's own cache
directory. Two writers whose `XDG_CACHE_HOME` differs — two OS users on a
shared ledger, containers or agent sandboxes mounting the same books, a
harness that sets the variable — lock different files and are not
serialized. The remaining compare-before-replace check has a window of a
few milliseconds: both writers can print "Added 1 transaction" and exit 0
while only one transaction is in the file. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

Use an isolated BEA_CONFIG_DIR, BEA_NO_UPDATE_NOTIFIER=1, no inherited
BEA_FILE/BEA_TOKEN/CI, closed stdin. Start eight writers at once, each
with its own cache directory and a distinct narration:

```sh
for i in 1 2 3 4 5 6 7 8; do
  XDG_CACHE_HOME=/absolute/books/cache$i bea -f /absolute/books/main.bean add transaction "tx$i" --date 2024-02-01 -p "Expenses:Food $i.00 USD" -p Assets:Cash </dev/null &
done; wait
```

Actual, over 12 such runs (96 writers): 44 exited 0 and 52 exited 4
("The ledger changed during the operation … Nothing was written;
retry"). Of the 44 that exited 0, 29 are not in the ledger. The file
still passes `bean-check`, and no staging file is left.

Control: the same 12 runs with one shared `XDG_CACHE_HOME` — 96 of 96
exit 0 and every transaction is present exactly once. A worker measured
the two-writer case at roughly 1 loss in 10–30 runs, falling to none once
the second writer starts 20 ms later.

Expected: `docs/USAGE.md` says "Concurrent CLI writers use persistent
locks under `$XDG_CACHE_HOME/bea/locks` … The locks coordinate `bea`
writers only: an editor or script that does not take them is caught by
the final compare-before-replace check in most cases". Two `bea` writers
are promised coordination, with no requirement that they share a cache
directory, and "Exit 0 is a promise" that the write happened.

Cause: `cli/src/bea_engine/ledger/write.py:317-339` takes `flock` on a
file under the caller's cache. The fallback, `replace_checked` (around
`:1174-1190`), compares the target and then copies metadata (ownership,
mode, ACLs and extended attributes) before `os.replace`, so the check
and the replace are several milliseconds apart.

Fix: make mutual exclusion independent of the per-user cache — for
example also hold an advisory lock on the target's parent directory (or
the target inode) around compare-and-replace, which creates no file
beside the ledger. At minimum move the metadata copy ahead of the
comparison, and document that writers must share `XDG_CACHE_HOME`.

Blast radius: every writer through the append and format paths (`add
*`, `add transactions`, `import --apply`, `format -i`); only `add
transaction` was raced.

Dedupe: board search for `bea/locks`, lost update and per-user cache
finds w1/done/075 (lock key spelling; kept the per-cache location),
w5/113 (uncreatable lock directory) and w5/115 (`add balance` pre-lock
decision); none covers writers on different cache directories.

Acceptance: with distinct cache directories, every writer that exits 0
has its transaction in the ledger exactly once across 100 runs of 8
writers; the others exit 4 or wait. Only macOS and the checkout were
exercised; real multi-user and container setups were not.

---

**Resolved 2026-10-13** — Every writer now also holds an advisory `flock` on the directory of each file it writes, taken after the per-cache lock files in one global order and deduplicated by device and inode, so writers whose `XDG_CACHE_HOME` differs queue instead of racing the compare-before-replace check; the change is in `cli/src/bea_engine/ledger/write.py` (`lock_files`, `lock_directories`), and a directory this process already holds is kept rather than locked again, matching the re-entrant lock file a deciding command passes on to `append`. `format --in-place` takes the same lock in `cli/src/bea_engine/ledger/formatting.py`, per file and after that file's lock when a run has too many targets to hold every lock at once. No file is created beside the ledger, and `cli/docs/USAGE.md` now states the second lock and its limit: on Windows, on a filesystem without `flock`, or in a directory the writer cannot read, the lock is skipped and writers must still share `XDG_CACHE_HOME` to be serialized. `cli/tests/test_write_lock_across_caches.py` races eight real `bea add transaction` writers on separate caches for three rounds, checks that an append, an in-place format and a bare lock from another cache each wait for the holder and go through once it is released, and guards against a writer waiting on itself when its files share a directory; five of its six cases fail with the fix reverted, and the shared-cache control passes either way. The note's acceptance was also run by hand before the lock protocol was reworked: 100 runs of 8 writers with distinct caches gave 800 exits of 0, none of 4 and no missing transaction. The metadata copy was not moved ahead of the comparison, so the window against an editor or script that takes no lock is unchanged. Only macOS was exercised. `make check-all` passed. Shipped in `e636e474` (`cli`).
