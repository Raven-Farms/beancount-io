# Four query shapes still exit with raw Python errors after w5/562 and w5/563: `ORDER BY` mixed-type metadata (`TypeError: '<' not supported`), `DISTINCT` over a subquery's set column ("cannot use starred expression"), `joinstr(accounts)` (`AttributeError: __mro__`), and `DISTINCT meta FROM entries` (`unhashable type`)

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-17, HEAD `1d0fe90f3`, checkout `bea 0.3.1`, macOS 26.5.1. Follow-up to w5/562 and 563 (done).
w5/562 and w5/563 set the standard: the query answers, or bea refuses it with
exit 2 and a one-line explanation naming the column, with no Python class
names. No product fix implemented.

`q.bean` has two transactions with `ref: "A-12"` and `ref: 5`.

1. `bea --file /abs/q.bean query "SELECT date, entry_meta('ref') AS ref ORDER
   BY ref"` exits 1 (`validation`): `TypeError: '<' not supported between
   instances of 'decimal.Decimal' and 'str'.`. `ORDER BY meta` and `ORDER BY
   entry` fail the same way with `'dict' and 'dict'` (hunter's run). Control:
   `ORDER BY str(entry_meta('ref'))` answers.
2. `query "SELECT DISTINCT o FROM (SELECT other_accounts AS o)"` exits 2 with
   `Beanquery could not compile this BQL query: cannot use starred expression
   here (<string>, line 4).`, followed by the tags/links advice. `SELECT
   DISTINCT other_accounts` gets the new message.
3. `query "SELECT accounts, count(*) GROUP BY accounts"` exits 2 with `BQL
   cannot use DISTINCT or GROUP BY on accounts…`, followed by the `tags` and
   `links` recipes. Adapting them, `SELECT joinstr(accounts), count(*) GROUP
   BY joinstr(accounts)` exits 1 with `AttributeError: __mro__.`.
4. `query "SELECT DISTINCT meta FROM entries"` exits 1 with `TypeError:
   unhashable type: 'ImmutableDictWithDefault'.`. `SELECT meta, count(*) FROM
   entries` gets the explained refusal with a `str(meta)` recipe.

Expected: each shape gets the explained exit-2 refusal (with advice that fits
the column) or an answer.

Cause (`cli/src/bea_engine/query.py`):
- `_null_safe_ordering` (`:173`) only orders NULLs, so mixed types still
  reach `rows.sort`.
- `_set_columns` (`:1988`) recognises only bare targets, and
  `_set_column_advice` (`:1982`) has no `accounts` case. The function-lookup
  failure on its `typing.Set[str]` dtype comes back raw.
- `_ungroupable_columns` (`:1854`) handles "unhashable type" only from
  `execute_select`, not from DISTINCT's hash.

Fix: map each of these to the existing explained refusals, naming the column.
Order mixed types by `str()` or refuse with that recipe, and give `accounts`
its own advice (no function applies to it, per w5/260).

Dedupe: w5/562, 563 and 260 (done) are the parents; w3/358 and w5/313
introduced the set-column refusal.

Acceptance: each query above exits 0 or 2 with no Python error text. Tests pin
each.
