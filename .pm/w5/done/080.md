# `add custom --value account:…` is always refused on a ledger with renamed root accounts

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS. On a ledger that renames its root
accounts with `option "name_*"`, a custom directive carrying an account value
cannot be added: the write is refused as "would not reload as written" although
the rendered line is valid in that ledger. A Fava budget is exactly this
shape. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "name_assets" "Aktiva"
option "name_expenses" "Aufwand"
option "name_equity" "Eigenkapital"
option "operating_currency" "EUR"
2026-01-01 open Aktiva:Bank EUR
2026-01-01 open Aufwand:Essen
2026-01-01 open Eigenkapital:OpeningBalances
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f /absolute/books/main.bean add custom --date 2026-01-01 -t budget -v account:Aufwand:Essen -v text:monthly -v "amount:400 EUR"
```

Actual: exit 2, file unchanged:

```text
Error: The custom directive would not reload as written; nothing was written. Rendered: '2026-01-01 custom "budget" Aufwand:Essen "monthly" 400 EUR'
  Invalid account name: Aufwand:Essen
```

Repeated twice. Appending that exact rendered line by hand, `bea check` exits
0 and `bea list custom` returns `account:Aufwand:Essen text:monthly
amount:400 EUR`.

Controls: on a default-root ledger, the same command with `account:Expenses:Food`
exits 0. On the renamed ledger, `add transaction`, `add open` and `add
balance` with `Aufwand:`/`Aktiva:` accounts all succeed.

Expected: `docs/USAGE.md` Adding directives says of account syntax that
"Unicode letters and configured root names are supported", and the custom
section lists `account` among the supported value kinds. The directive
should be written and listed.

Cause: `cli/src/bea_engine/ledger/writer.py:515-516`
(`_require_custom_roundtrip`) parses the rendered line on its own with
`parser.parse_string`, which uses default options, and treats any parser
error as proof the line would not reload. Under default options `Aufwand` is
not a root, so the parser reports `Invalid account name`. The transaction
path already tolerates exactly that standalone-probe error
(`ledger/adding.py`, the header probe).

Fix: in standalone round-trip probes, either parse with the ledger's own
`name_*` options or disregard `Invalid account name` errors and let the
whole-ledger validation that follows judge the name. Audit the sibling probes
for the same assumption — the raw-text append behind `bea ask` writes
(`ledger/appending.py`), the bulk zero-net guard and the `--meta` value
probe (`ledger/adding.py`) each parse standalone text; engine-level runs
showed the first rejecting all text on this ledger and the second skipping its
guard. No dependency or API change.

Dedupe: board search for "would not reload", renamed roots, `name_assets`
and "Invalid account name" finds w3/430 (the round-trip check for negative
custom values) and w1/157 (import with an unknown root); neither covers
`name_*` options in standalone probes.

Acceptance: the fixture command exits 0, `bea check` passes and `list
custom` shows the three values; a genuinely invalid account value is still
refused with nothing written; an `ask`-style raw append and a zero-net bulk
row behave on the renamed ledger as they do on a default one. Real-command
regression tests use the renamed-root fixture. Only macOS and the checkout
were exercised; the `ask` path was observed at the engine helper, not through
a hosted session.

---

**Resolved 2026-10-12** — Standalone parse probes no longer treat `Invalid account name` as a syntax failure: root names are ledger options, and the whole-ledger validation that follows every write judges them. On the fixture `add custom … -v account:Aufwand:Essen` exits 0, `bea check` passes and `list custom` shows the values. The same helper is applied to the sibling probes the note asked to audit — the raw-text append behind `bea ask`, the bulk zero-net guard, and the `--meta` value probe — and replaces the transaction header probe's own copy of the rule. Shipped in `220f7ed3` (`cli`).

Regression tests run each case on the renamed-root fixture and on a default-root ledger as its control: the custom directive is written and listed; a custom account value under a root the ledger does not use is still refused with nothing written; a raw append through the engine helper is accepted; a bulk row whose inferred leg is zero is refused with the zero-net message; and an account-shaped `--meta` value is written identically on both. The custom, raw-append and zero-net cases fail on the renamed ledger with the fix reverted; the default-root controls and the metadata case pass either way (the metadata probe already fell back to the same quoted string). `make check-all` passed. The `ask` path was exercised at the engine helper, not through a hosted session, and only macOS was tested.
