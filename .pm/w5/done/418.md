# With `BEANCOUNT_LOAD_CACHE_FILENAME` set to a file that is not a ledger file, every read command (`balance`, `list`, `query`, `add`) silently deletes it, with exit 0 and no message

**Minor · cli · 15m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
Before loading, bea removes whatever sits at the resolved load-cache path
unless it wrote that file itself (w5/220). The guard from w5/065 and
w5/067 refuses the variable only when it names a ledger file. Any other
file it names is deleted without a word: a note, a CSV, or a mistyped
path to something important. This is bea's own deletion. The sibling
[417](./417.md) is upstream's deletion through `check --cache-filename`.
No product fix implemented.

Use a minimal ledger `/absolute/w/main.bean` and `/absolute/w/notes.txt`.
Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, and
closed stdin.

```sh
BEANCOUNT_LOAD_CACHE_FILENAME=/absolute/w/notes.txt bea -f /absolute/w/main.bean balance
ls /absolute/w/notes.txt
```

Actual: exit 0, with nothing on stderr, and `notes.txt` is gone. The
ledger is unchanged. `list transaction`, `query 'SELECT 1'` and `add note`
do the same. Reproduced twice by the hunter (`balance`), once for each
other command, and once by me.

Control:

- Without the variable, `notes.txt` survives.
- With the variable naming `main.bean`, the command exits 2 with
  "…Beancount deletes a cache file it cannot read, so this would delete
  the ledger… Nothing was changed."

Expected: `docs/USAGE.md` says a cache path outside the ledger's files
"keeps working" and that "a `bea` command never replaces a file it was
not given". The guard's own message names deletion as the danger. An
existing file that is not a recognisable cache should be refused with
exit 2, naming the variable and the file. It should never be deleted
silently.

Cause:

- `_load_fresh` (`cli/src/bea_engine/managed_load.py:544-547`) runs
  `if cache.is_file() and not _engine_wrote(cache): cache.unlink(...)`
  (from `2ff77650`, w5/220).
- `refuse_cache_over_ledger` (`cli/src/bea_engine/ledger/write.py:383+`)
  checks only the include closure.

Fix: before unlinking, require a pickle-cache header (or upstream's cache
structure), and otherwise refuse with exit 2. Share the check with 417's
`--cache-filename` fix. No dependency change.

Blast radius: every local command when `BEANCOUNT_LOAD_CACHE_FILENAME` is
set (for example in a shell profile) to a path that is, or later
becomes, a user file.

Dedupe: w5/220 and w5/067 cover ledger files, w5/312 covers an `EACCES`
on this line, and 417 covers upstream's deletion through `check`. None
covers bea's own deletion of other files.

Acceptance: on the fixture, `balance` exits 2 naming `notes.txt`, which
survives. A real cache at the path still works. A test pins both.

Addendum (CLI QA r80, 2026-10-14): `BEANCOUNT_LOAD_CACHE_FILENAME` (and
`check --cache-filename`) naming a non-regular file is also mishandled:

- A FIFO hangs the command (twice).
- `/dev/null` or `/dev/zero` exits 0 but prints `ERROR:root:Cache file is
  corrupted: Ran out of input; recomputing.` and `WARNING:root:Could not
  remove picklecache file /dev/null: [Errno 1] Operation not permitted`
  (reproduced by me). Upstream tries to `os.remove` the device, which
  fails for a normal user and would succeed as root.

`/dev/null` is the obvious way to try to disable the cache. The guard
should refuse a cache path that exists and is not a regular file, or map
`/dev/null` to "no cache" and document it. `_load_fresh`
(`managed_load.py:544-547`) tests only `is_file()`.

---

**Resolved 2026-10-15** — both load-cache guards now run
`not_a_load_cache`: `refuse_cache_over_ledger` in
`cli/src/bea_engine/ledger/write.py`, on every engine load, and its
frontend twin in `cli/src/cli/output.py`, before native commands. An
existing file at the resolved cache path must be a regular file that
starts with a pickle header. Otherwise the command exits 2 with
`BEANCOUNT_LOAD_CACHE_FILENAME … names …/notes.txt, which is not a
Beancount load cache, and Beancount deletes a cache file it cannot read.
… Nothing was changed.`, and the file survives. That covers `balance`,
`list`, `query`, `add` and `check`. Per the addendum, `/dev/null` and a
FIFO are refused as "not a regular file" without being opened, so there
is no hang or device read. A real cache at the path is still written and
read. USAGE states the rule. Pinned by
`cli/tests/test_load_cache_env_not_a_cache.py`, which fails without the
fix; the FIFO case was not run unfixed, because it would hang. The
frontend guard also covers `check --cache-filename`, the deletion half of
417; 417's leaked `ERROR:root:` and `WARNING:root:` lines remain.
