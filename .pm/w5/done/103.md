# An invalid regex in a BQL query exits 1 as a ledger validation failure, and only when a row is scanned

**Minor · cli · 30–40m · A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS.
A malformed pattern after `~` is a mistake in the command, but it is reported
with exit 1 and JSON category `validation` — the code that means the ledger
is broken — with a message that names neither the pattern nor the query. The
same malformed query exits 0 when its `FROM` clause happens to select no
rows. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Broker HOOL "FIFO"
2024-01-01 open Expenses:Food
2024-01-04 custom "budget" Expenses:Food "monthly" 400.00 USD TRUE 2024-01-01 -3.5
2024-01-05 * "Grocer" "Refund (partial)" #food #trip #reimbursable
  Expenses:Food  -5.00 USD
  Assets:Cash
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY. The fixture passes
`bea check`.

```sh
bea -f /absolute/books/main.bean query "SELECT date, narration WHERE narration ~ '(partial'"
bea --json -f /absolute/books/main.bean query "SELECT date, narration WHERE narration ~ '(partial'"
bea -f /absolute/books/main.bean query "SELECT date, narration FROM year = 2025 WHERE narration ~ '(partial'"
```

Actual: the first exits 1 with `Error: error: missing ), unterminated
subpattern at position 0 Pass --debug before the command for a traceback.`
The JSON run exits 1 with `"category": "validation"`. The third exits 0 with
`(no rows)`. Repeated twice. A worker saw `'['` and `'*sale'` fail the
same way.

Control: the escaped pattern `'\(partial'` exits 0 and returns the two
matching postings.

Expected: `docs/USAGE.md` reserves exit 2 for bad arguments and exit 1 for
a ledger that fails validation; a BQL syntax error already exits 2 with a
caret. A bad pattern should exit 2 with category `usage`, name the pattern
and the regex error, and do so whether or not any row is scanned. An agent
that reads exit 1 here goes looking for a ledger problem that does not exist.

Cause: `cli/src/bea_engine/query.py:964-1030` (`_compiled`) and
`:929-962` (`_executed`) translate Beanquery, syntax, type, attribute and
parser errors, but not `re.error`. Beanquery compiles the pattern while
evaluating rows, so the exception escapes to the generic wrapper at
`cli/src/cli/engine/launch.py:342`, which reports exit 1.

Fix: catch `re.error` around compilation and execution and raise the usage
error; where the pattern is a constant, validate it before execution so an
empty scan fails identically. No dependency or API change.

Blast radius: every `~` and `!~` in one-shot queries, stored `.run`
queries and the interactive shell. Other evaluation-time errors (date
overflow, `parse_date('x')`) take the same generic path and were not filed.

Dedupe: board search for unterminated, `re.error` and invalid regex finds
w1/018 (`report --account`), w5/061 (treeify) and w1/m16 (import rules),
each treating a bad pattern as a usage error; none covers BQL.

Acceptance: all three commands exit 2 with category `usage` and a message
containing the pattern; the escaped control is unchanged. Real-command
regression tests cover a scanned and an empty window, text and JSON. Only
macOS and the checkout were exercised.

---

**Resolved 2026-10-12** — An invalid regular expression in a BQL query is a usage error: exit 2, category `usage`, with a message that names the pattern and the regex error and details that quote the query. Constant patterns after `~` and `!~` are compiled before the statement runs, so a window with no rows fails identically; a `re.error` raised while evaluating a non-constant pattern is translated the same way. The check sits in the shared compile wrapper, so one-shots, stored `.run` queries and the interactive shell use it. Shipped in `465a88a6` (`cli`).

Real-command regression tests cover three malformed patterns under `~` and `!~`, with rows scanned and with an empty window, in text and JSON; a double-quoted pattern; and three valid queries that must be unchanged — an escaped pattern, two valid patterns in one query, and an equality comparison against the same text. Thirteen fail with the fix reverted. Other evaluation-time errors the note mentions (date overflow, `parse_date('x')`) take the generic path still and were not filed or changed. `make check-all` passed. Only macOS was exercised.
