# A `socks4://`, `socks://` or `socks4a://` proxy (or any other unknown proxy scheme) still fails cloud commands and `ask` as an unexpected error that echoes the proxy URL, and the w5/518 refusal names the wrong variable for mixed-case or duplicate settings (incomplete fix of w5/518)

**Minor · cli · 15m · A1.** Real CLI QA, 2026-10-17, HEAD `733ea312`, checkout `bea 0.3.1`, macOS 26.5.1. Simulation: a local stub API. Follow-up to w5/518 (done, `21e69dbf`).
w5/518 refuses a `socks5://` proxy with exit 2, in bea's own words and without
echoing the value. Other SOCKS spellings, including `socks://`, the form
GNOME and Ubuntu proxy settings export, still fail as before. No product fix
implemented.

1. **Other schemes.**
   - `ALL_PROXY=socks4://alice:s3cret@127.0.0.1:1080 BEA_TOKEN=qa-fake-token
     bea cloud ledger list` exits 1 with `Error: Unknown scheme for proxy URL
     URL('socks4://alice:[secure]@127.0.0.1:1080'). Pass --debug before the
     command for a traceback.`
   - `all_proxy=socks://127.0.0.1:1080/ bea --json cloud status` gives the same
     error, category `validation`.
   - `bea -f main.bean ask -p hi` with `ALL_PROXY=socks4a://…` fails the same way.
   - `HTTPS_PROXY=ftp://…` and a malformed `HTTPS_PROXY='http://[::1'` (`Invalid
     port`) also fail this way.

   The message shows the proxy user name, host and port. No request is sent.
2. **Variable names.**
   - `All_Proxy=socks5://…` (mixed case, which httpx reads) exits 2 with
     `Error: a proxy variable names a SOCKS proxy… (for example ALL_PROXY=
     bea …)`. The sentence starts lower-case and names a variable that is not
     set.
   - With both `ALL_PROXY` and `all_proxy` set, the message reads `ALL_PROXY
     and all_proxy names a SOCKS proxy… (for example ALL_PROXY= bea …)`.
     Following that example exits 2 again, now naming `all_proxy`.
3. **Docs.** No page in `cli/docs` or `cli/README.md` mentions SOCKS.

Control: `ALL_PROXY=socks5://…` and `SOCKS5://…` exit 2 with `ALL_PROXY names
a SOCKS proxy, which bea's HTTP client does not support. Unset it for bea…`.

Expected: every unusable proxy setting exits 2 naming the variable, not its
value. The example clears every variable involved. USAGE's environment
section says SOCKS proxies are refused.

Cause:
- httpx raises `ValueError("Unknown scheme for proxy URL …")` while it builds
  the client. `_httpx_client` (`cli/src/cli/api/client.py:81-92`) and
  `ask.py:84` catch only `ImportError`.
- `socks_proxy_refusal` (`cli/src/cli/errors.py:403-419`) checks six exact
  names (`_PROXY_VARIABLES`, `:400`), and its example uses only `named[0]`.

Fix:
- Also map the proxy `ValueError`/`httpx.InvalidURL` at client construction to
  the refusal.
- Match proxy variable names case-insensitively, and list every named variable
  in the example.
- Document the behavior.

Dedupe: searched `socks4`, `Unknown scheme for proxy`, `socks://`; only w5/518
(done) matches.

Acceptance: the commands above exit 2 without the proxy URL, and the
duplicate case's example works when followed. Tests pin `socks4://` and the
mixed-case name.
