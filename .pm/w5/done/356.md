# The `beancount-close` flag sweep groups by date, payee and narration, so two `!` transactions at the same merchant on the same day count as one and "Flags carried" undercounts

**Minor · skills · 15m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
The close skill's flag-sweep recipe deduplicates the per-posting rows
that BQL returns. It groups by the entry's content (`date, flag, payee,
narration`) instead of the entry's identity. Two different flagged
transactions with the same date and description therefore collapse into
one row.

This is the normal output of `bea import` for two same-day charges at one
merchant. Rows that no rule matches are written `!`, and different
amounts keep them from being possible duplicates. The close report then
undercounts carried flags, which the skill says must never happen.
No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
2026-06-21 ! "WHOLE FOODS" "groceries"
  Expenses:Food 30 USD
  Assets:Checking
2026-06-21 ! "WHOLE FOODS" "groceries"
  Expenses:Food 12 USD
  Assets:Checking
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, and closed stdin. Run the recipe exactly as
`close-checklist.md` gives it:

```sh
bea --json -f /absolute/books/main.bean query "SELECT date, flag, payee, narration WHERE flag = '!' AND date < 2026-07-01 GROUP BY date, flag, payee, narration ORDER BY date"
```

Actual: one row. The hunter got the same result in two fresh directories
built with `bea init` and `bea import` of a two-row CSV (`06/21/2026,WHOLE
FOODS MKT #123,-30.00` and `…,-12.00`). There the import wrote 2 `!`
entries and the sweep returned 1.

Control: `bea --json list transaction --flag '!'` returns both.
Adding `id` to the select and the `GROUP BY` returns one row per
transaction.

Expected: `references/close-checklist.md` says the `GROUP BY` "collapses
the one-row-per-posting duplicates" and "A close can complete with
carried flags; it cannot complete with uncounted ones". `SKILL.md` says
carried flags "all appear in the report with counts". The sweep should
give one row per flagged transaction.

Cause: `skills/.claude/skills/beancount-close/references/close-checklist.md:44`
groups by content, not identity. The recipe is not marked `<!-- recipe:
-->`, so `skills/scripts/test_beancount_skills.py` never runs it.

Fix:

- Add `id` to the select and to the `GROUP BY`, or switch the recipe to
  `bea --json list transaction --flag '!' --to-date <period-end>` with a
  `truncated` check.
- Mark the recipe so it is executed in CI.
- Add a behaviour fixture with two same-day, same-merchant `!` rows.
- No dependency change.

Blast radius: every `beancount-close` run on a period with repeated
same-day flagged charges at one merchant (coffee, transit, split
purchases). The close report's carried-flag count is understated.

Dedupe: searched `.pm/**`, including `done/`, for "flag sweep", `flag =
'!'` and `GROUP BY date, flag`. w2/m5/t001 and t002 created the sweep, and
w1/139 fixed a different grouping (recurring charges). None covers this.

Acceptance: on the fixture, the recipe returns 2 rows. A two-posting
transaction still returns 1 row. The recipe is marked and executed by the
skills CI with that fixture.

**Resolved.** The flag-sweep recipe in `close-checklist.md` now selects and groups by the transaction `id` before `date, flag, payee, narration`. A transaction's per-posting rows still collapse to one row, and two same-day `!` charges at one merchant stay two. The block is marked `<!-- recipe: flag-sweep -->`, and `test_flag_sweep_counts_each_flagged_transaction_once` in `skills/scripts/test_beancount_skills.py` runs it against two same-day WHOLE FOODS flags plus a three-posting flagged transaction and expects three rows. The test fails with the old grouping, which returns one WHOLE FOODS row.
