# `add` refuses accounts that the ledger already opens and that `bea check` and stock Beancount accept

**Minor · cli · 30m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, Beancount 3.2.3, macOS (APFS).
An account whose name contains a combining mark that has no precomposed
form — for example Thai `Expenses:Kค่า` — loads in stock Beancount,
passes `bea check` and shows in reports, but cannot be posted to through
`bea add`: the command exits 2 with "Invalid account". The `add`
validator is stricter than the loader it claims to mirror. No product
fix implemented.

Create `/absolute/books/main.bean` (the account is `Expenses:K` followed
by U+0E04 U+0E48 U+0E32):

```sh
A=$(printf 'Expenses:K\xe0\xb8\x84\xe0\xb9\x88\xe0\xb8\xb2')
printf 'option "operating_currency" "USD"\n2024-01-01 open Assets:Bank USD\n2024-01-01 open %s USD\n2024-01-01 open Expenses:Rent USD\n2024-01-02 * "rent"\n  %s  5.00 USD\n  Assets:Bank\n' "$A" "$A" > main.bean
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY. cwd `/absolute/books`.

```sh
bea -f main.bean check
bea -f main.bean add transaction --date 2024-02-01 -n rent -p "$A 7 USD" -p Assets:Bank
```

Actual: `check` exits 0 (as does stock `bean-check`). `add` exits 2:
`Invalid account 'Expenses:Kค่า'. Account names use colon-separated
segments … Use letters, digits and hyphens within segments.`

Control: the same command with `-p "Expenses:Rent 7 USD"` exits 0. A
worker saw the refusal for `add balance` and `add note`, for a Yoruba
name with a combining grave, and for zero-width and emoji characters
inside a component.

Expected: `docs/USAGE.md` — "Account syntax follows Beancount … Unicode
letters and configured root names are supported." An account the ledger
already opens and `check` accepts should be postable.

Cause: `cli/src/bea_engine/ledger/text.py:228-231` validates with
Beancount's end-anchored account pattern (letters, digits and hyphens
only), whereas the loader accepts anything its lexer tokenizes as an
account; combining marks are neither letters nor digits.

Fix: accept any name the ledger already opens, or validate with the
loader's rule; the strict rule can stay for new names. Name the
offending character in the message. No dependency or API change.

Blast radius: every `add` subcommand that takes an account; import
account options share the validator (not run).

Dedupe: w3/278 and w5/130 are NFD spellings (a different cause); w1/157
is the root check. Board search for combining, Thai and zero-width finds
nothing else.

Acceptance: the `add` command exits 0 and `bea check` still passes; a
genuinely malformed name such as `expenses:food` is still refused. Only
macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — `parse_account` in `cli/src/bea_engine/ledger/text.py` no longer stops at Beancount's end-anchored `is_valid`: a name that pattern refuses is put to the loader's own rule (it must lex as exactly one account token and match the account pattern from the start), so an account such as `Expenses:Kค่า` that the ledger opens and `bea check` accepts can be posted to through every `add` subcommand, bulk rows and the import account options. The rule applies to new names too, so the `bea add open` remedy printed for an unknown account works for the same names; this goes one step past the note, which allowed the strict rule to stay for new names. Control characters and bidirectional overrides remain refused even though the lexer would take them, and the refusal now names the offending character (for example `U+0020 (SPACE)`) when there is one. `docs/USAGE.md` states the wider rule. The regression test `cli/tests/test_add_accepts_loader_valid_accounts.py` drives the real command for Thai, combining-grave, zero-width and emoji names across transaction, note, balance, pad-from, document, custom, close, bulk and import, plus the `Expenses:Rent` control and still-refused names such as `expenses:food`; 17 of its 24 cases fail with the fix reverted. Only macOS was exercised. `make check-all` passed. Shipped in `c9b50f21` (`cli`).
