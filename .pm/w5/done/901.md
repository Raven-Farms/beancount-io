# Preserve the exact equity negation for a wide preset opening balance

**Trivial · cli · 10–15m · A2.** The preset initializer repeats the
29-digit negation bug already fixed in the legacy initializer by
[310](./done/310.md). A negative opening amount is written intact, but
its equity offset is rounded. This concerns stored decimal text; upstream
Beancount still books these wide numbers at its own precision. No larger
bookkeeping-loss claim or product fix is made.

Real CLI QA 2026-10-20, HEAD `69fbacfb6`, checkout `bea 0.3.1`, Darwin
25.5.0 arm64, frontend Python 3.13.3, managed engine Python 3.12. From
an isolated synthetic cwd, use absolute BEA_CONFIG_DIR/XDG_CACHE_HOME,
BEA_NO_UPDATE_NOTIFIER=1, no inherited BEA_FILE/BEA_TOKEN, closed stdin,
no TTY:

```sh
bea --json --no-input init /absolute/qa/preset --preset personal@1 --currency USD --date 2024-02-01 --opening-balance 'Assets:Cash -12345678901.123456789012345678'
bea --json --file /absolute/qa/preset/main.bean check
bea --json --file /absolute/qa/preset/main.bean query "SELECT account,number WHERE account ~ '^Equity:'"
```

All exit 0. The file's opening transaction is:

```beancount
2024-01-31 * "Opening balance"
  Assets:Cash  -12345678901.123456789012345678 USD
  Equity:OpeningBalances  12345678901.12345678901234568 USD
```

The exact offset is **12345678901.123456789012345678**, independently
calculated with context-free Decimal.copy_negate(). The query returns
the shortened positive equity amount. The input leg remains exact on disk.
Reproduced twice with `personal@1`, and twice with `freelance@1` using
`Assets:Bank`.

Working controls, each twice:

- Without `--preset`, use `Assets:Checking` and the same negative amount:
  equity is the full exact negation, and fresh check passes.
- Preset amounts of either sign with 28 significant digits
  (`±1234567890.123456789012345678`) write exact offsets and check clean.

A positive 29-digit preset amount is refused during validation because
upstream accumulation rounds while its positive boundary assertion retains
the literal digits. No ledger is written. That separate precision limit is
excluded from this finding; do not weaken assertion validation to make it
pass. The initial exploratory script assumed that case would succeed, then
the complete sign/preset/control matrix was rerun with the correct model.

Cause: `cli/src/bea_engine/initiating.py:251`, `answer_preset`, interpolates
`{-amount:f}`. Unary minus applies the default 28-digit decimal context.
The legacy `answer` at lines 84–92 already uses an exact sum and
copy_negate() since 310 (`dd8e4a53`); 697 preserves unsigned zero there.
The preset path was added by `1ba20bffa` and still uses the old negation.
Its caller is the `init --preset` engine dispatch in `main.py:502`.

Fix: negate the preset opening amount without context rounding, preserving
the existing validated amount and date/assertion behavior. Pin both tested
presets, both 28-digit controls, and the legacy exact-negation control.
No dependencies, backend changes or upstream arithmetic rewrite are needed.

Dedupe: searched all board states for init/opening precision, 28-digit
rounding and equity negation, and reviewed active milestone scopes.
Completed 310's real-command tests use only the legacy template; completed
697 is cancelling legacy totals. Open 875–878/889 concern preset title,
zero-state, summaries, prompts and date bounds; 898 is the arithmetic-price
probe. No open item covers this preset negation. Current main has no later
repair in targeted history.

Acceptance: on both reproduced negative-preset fixtures, the equity line
contains all input digits with the opposite sign; check and query still
succeed. Retain all controls and existing positive-wide refusal. Evidence
is retained in ignored pass5 `repro_preset_opening_precision_v2.py`,
`preset-precision-v2-results.json`, twelve cases and captures. Only macOS
and this checkout tested; amounts this wide are contrived for preset fiat
currencies.

---

**Resolved 2026-10-22** — the preset initializer now writes the equity offset with `copy_negate()` instead of unary minus, so a wide negative opening balance is cancelled digit for digit (as the legacy initializer has done since w5/310). `cli/tests/test_init_preset_wide_opening.py` checks both presets plus the 28-digit controls of either sign, with fresh check and query, and fails for the wide cases without the fix; shipped in the commit that moves this note (`cli`). The separate positive 29-digit validation limit is unchanged.
