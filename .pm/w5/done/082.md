# `--meta` drops a leading `#` from a text value and misreports a `name:` value as a bad key

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS. A bare `--meta` value is documented to
become a string. A value starting with `#` loses that character on the way
into the ledger, with exit 0, and a value shaped like `Word:Word` under the
key `name` — the key the guide's own example uses — is refused with a message
blaming the key. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Assets:Cash
2026-01-01 open Expenses:Food
2026-01-01 open Equity:Opening

2026-01-02 * "Open"
  Assets:Checking  5000.00 USD
  Equity:Opening
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f /absolute/books/main.bean add transaction x --date 2026-02-01 -p "Expenses:Food 5" -p Assets:Checking --meta 'check:#1042' --meta 'channel:#general'
bea -f /absolute/books/main.bean add transaction x --date 2026-02-01 -p "Expenses:Food 5" -p Assets:Checking --meta 'name:Chase:Sapphire'
```

Actual: the first exits 0 and writes `check: "1042"` and
`channel: "general"`; `--json` and `bea list transaction --details` report
the altered values. The second exits 2 with `Invalid --meta key 'name';
Beancount rejected it (Invalid account name: Chase:Sapphire).` Repeated
twice. `add commodity --meta 'issue:#12'` stores `"12"` the same way, and
`--meta 'cc:NULL'` writes an empty `cc:`.

Controls: `--meta 'card:Chase:Sapphire'` stores `"Chase:Sapphire"`;
`--meta 'gg:^link'` stores `"^link"`; the quoted form
`--meta 'check:"#1042"'` keeps the `#`; bulk JSON
`"meta": {"check": "#1042"}` keeps it.

Expected: `docs/USAGE.md` — "Bare text such as `note:hello` or
`receipt:IMG_1234.jpg` becomes a string. Valid native numbers, booleans,
dates and amounts retain their types". `#1042` and `Chase:Sapphire` are
neither, so both should be stored as the text typed; a check number, a chat
channel and an issue reference are ordinary metadata.

Cause: `cli/src/bea_engine/ledger/adding.py:900-902` probes the value by
parsing `key: <raw>` as a metadata line; `#1042` lexes as a tag, whose
parsed value is the bare name, and that is stored as if it were the typed
text. At `:908-912` the "bad key" branch tests `f"{key}:" in message`,
which matches `Invalid account name: …` whenever the key is `name`.

Fix: when the probe yields a plain string or nothing from an unquoted value,
store the raw text rather than the parser's reading of it; keep typed results
only for the documented kinds. Decide key errors from the key token, not from
a substring of the parser message. No dependency or API change.

Dedupe: board search for metadata with a leading sigil, tag-shaped values and
"Invalid --meta key" finds nothing.

Acceptance: the first command stores `"#1042"` and `"#general"`; the second
stores `name: "Chase:Sapphire"`; `cc:NULL` stores the text `"NULL"` or is
refused by name, as the owner prefers; typed numbers, booleans, dates,
amounts and quoted strings are unchanged; `add commodity --meta` matches.
Only macOS and the checkout were exercised.

---

**Resolved 2026-10-12** — An unquoted `--meta` value keeps the parser's reading only for the documented kinds (number, boolean, date, amount); anything the probe read as a string or as nothing is stored as the text typed. `check:#1042` and `channel:#general` are written as `"#1042"` and `"#general"`, and `cc:NULL` as the text `"NULL"` (chosen over refusing it: the guide says bare text becomes a string). Key errors are decided by probing the key alone. `add commodity --meta` shares the parser and matches. Shipped in `3891990f` (`cli`).

`name:Chase:Sapphire` was already accepted at HEAD before this change: w5/080 (`220f7ed3`) stopped standalone probes from treating `Invalid account name` as an error, which removed the message the old key test matched. The substring test itself is replaced here so no other parser message can trigger it.

Real-command regression tests cover nine bare-text values (tag-shaped, account-shaped, `NULL`, a link, a currency code, free text) asserting the written line, the JSON value and a passing `check`; six typed and quoted values that must be unchanged; `add commodity`; and an unclosed quote under the key `name`, still refused as a value problem. Four fail with the fix reverted. `make check-all` passed. Only macOS was exercised.
