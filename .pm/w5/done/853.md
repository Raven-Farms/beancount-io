# `bea query -o /dev/fd/N` (and process substitution `-o >(cmd)`) fails with a bare "Bad file descriptor", and `-o /dev/fd/3` corrupts the engine's reply channel, dumping the rows into it

**Minor · cli · 15m · A1.** Real CLI QA, 2026-10-17, HEAD `4375177a4`, checkout `bea 0.3.1`, macOS 26.5.1.
USAGE (around :259-261) says "A device or FIFO destination is written through
rather than replaced", and `>(…)` is a standard shell idiom. No product fix
implemented.

`a.bean` holds one transaction. In bash:

```sh
bea --file /abs/a.bean query -f csv -o >(cat > ps.csv) "SELECT date, payee, position"
bea --file /abs/a.bean query -f csv -o /dev/fd/3 "SELECT date, payee, position" 3>fd3.csv
```

Actual:
- The first exits 1 with `Error: OSError: [Errno 9] Bad file descriptor:
  '/dev/fd/63'.`, and `ps.csv` stays empty.
- The second exits 1 with `The Beancount engine did not answer 'bea-engine
  query … --output /dev/fd/3 …'`. The CSV rows (`date,payee,position`) land in
  the engine's reply channel, and `fd3.csv` stays empty.
- `--json … query -o /dev/stderr 2>err.json` exits 1 with `Cannot write /dev/fd/2
  (No such file or directory)` (hunter's run).
- `query --source main.bean -o >(cat)` blames the input: `Cannot read the
  --source: '/dev/fd/63': Bad file descriptor.` (hunter's run).

Control: `-o /dev/stdout`, `/dev/fd/1`, `-`, `/dev/null` and a named FIFO work,
as do `format -o >(cat)` and `treeify -o >(cat)`, where the frontend writes the
file.

Expected: the query is written to the named descriptor.

Cause:
- `cli/src/cli/commands/query.py` (around `:315`) maps only stdout paths to
  stdout and forwards any other `/dev/fd/N` to the engine as `--output`. The
  engine opens it in its own process, where the descriptor is closed or is
  its reply pipe (fd 3, from `os.dup(1)` in `cli/src/bea_engine/protocol.py`).
- Under `--json`, `atomic_write` stats `/dev/fd/2` as a regular file and tries
  to stage a temporary copy next to it.
- The `--source` error path words any `OSError` as a read failure.

Fix: write descriptor destinations in the frontend from the engine's
returned text, or pass the descriptor through; treat descriptor paths as
write-through in `atomic_write`; name `--output` in the error.

Dedupe: w5/436 (done) covers `<(…)` inputs; w5/795 and 792 (open) cover
`-o /dev/stdout` with a file redirect and `--rules` descriptors.

Acceptance: both commands write the CSV to the descriptor. A test pins `>(cat)`.

---

**Resolved 2026-10-20** — a `query -o` destination that names one of the frontend's own descriptors (`/dev/fd/N`, `/proc/self/fd/N`, `/dev/stderr`, what `>(cmd)` passes; detected with w5/792's `is_descriptor_path`) is no longer forwarded to the engine: the frontend writes the engine's answer there itself, `--source` captures upstream's output and writes it, `atomic_write` writes a descriptor through instead of staging beside it, and the interactive shells refuse one naming `--output`. `-o >(cat > ps.csv)`, `-o /dev/fd/3` with `3>fd3.csv`, `--json -o /dev/stderr` and `query --source … -o >(cat)` now deliver the rows, and a closed descriptor exits 2 with `Cannot write --output /dev/fd/9: Bad file descriptor.`. `tests/test_query_output_descriptor.py` pins each through real bash process substitution; USAGE says so.
