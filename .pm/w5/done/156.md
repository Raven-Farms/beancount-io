# `bea format -o FILE` writes in place: a failed write truncates the existing destination and leaves a partial ledger

**Minor · cli · 20m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
`format -o` opens the destination and writes directly. When the write
fails part-way (disk full, file-size limit), an existing export is
replaced by a fragment that ends mid-directive, and the error does not
say so. `query -o` on the same failure keeps the old file. No product fix
implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD

2026-01-05 * "Café" "Lunch"
  Expenses:Food  12.00 USD
  Assets:Cash
```

and `/absolute/books/f2.out` and `q2.out`, each containing `GOOD` and a
newline. Simulate a full disk by running the child with
`RLIMIT_FSIZE=60` (for example Python `subprocess.run(…, preexec_fn=lambda:
resource.setrlimit(resource.RLIMIT_FSIZE, (60, 60)))`).

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, no TTY, cwd `/absolute/books`.

```sh
bea format main.bean -o f2.out
bea -f main.bean query "SELECT account, date, narration, position" -o q2.out
```

Actual: `format` exits 1 with `Error: [Errno 27] File too large`;
`f2.out` is now a 60-byte fragment of the ledger. `query` exits 1 and
`q2.out` still holds `GOOD`.

Control: the `query -o` run above. A worker saw `treeify -o`, `format -i`,
`add note` and `init` also leave their targets intact under the same
limit, and `format -o` leave a partial new file when none existed.

Expected: `docs/USAGE.md` says "One-shot query exports replace the
destination only after a successful query; a failed query or write
preserves an existing export", and a command "that wrote only part of what
it promised, exits nonzero and says what is missing". `format -o` should
be all-or-nothing like its siblings.

Cause: `cli/src/cli/commands/format.py:521` calls
`destination.write_text(...)` with no staging.

Fix: route through `cli.utils.atomic_write(destination, text,
export=True)`, which the other exporters use. No dependency or API change.

Blast radius: `format FILE -o`, `format - -o`, text and `--json`.

Dedupe: board search for `format -o` with atomic, partial and truncate
finds w3/404 and w3/380 (query export atomicity, done) and w5/117 (`price
export` partial write); none covers `format -o`.

Acceptance: under the size limit `format -o` exits nonzero and `f2.out`
still holds `GOOD`, with no temporary file left; a successful run is
unchanged. Only macOS and the checkout were exercised; a real full disk
was not used.

---

**Resolved 2026-10-13** — `bea format -o FILE` now stages its output beside the destination and swaps it in through `cli.utils.atomic_write(..., export=True)` in `cli/src/cli/commands/format.py`, the same path `query -o` and `treeify -o` use, instead of writing the destination in place. A write that fails part-way therefore exits nonzero with the existing export byte-identical, no partial file where none existed, and no staging file left behind; `cli/docs/USAGE.md` states the guarantee. `cli/tests/test_format_output_is_atomic.py` induces a real EFBIG write failure with a file-size limit on the child and covers `format FILE -o` in text and `--json`, `format - -o`, a new destination, the `query -o` control and an unchanged successful run; four of its seven cases fail with the fix reverted. The error text itself is unchanged (`[Errno 27] File too large`), and a real full disk was not used. Only macOS was exercised. `make check-all` passed. Shipped in `57c16297` (`cli`).
