# Ask mistakes `from entries` inside BQL strings or comments for the source table and mislabels posting counts

**Minor · cli · 30–45m · A1/A2.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `d7ed47ef5`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
Twice from pristine fixtures, using the installed SDK and an owned loopback
OpenAI-compatible simulator. Counts were independently verified by real
`bea query`; no hosted quota or model answer-accuracy claim. No fix made.

Create `/abs/case/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Equity:Opening USD
2024-01-02 * "Transfer from entries one"
  Assets:Cash 10 USD
  Equity:Opening -10 USD
2024-01-03 * "Transfer from entries two"
  Assets:Cash 20 USD
  Equity:Opening -20 USD
```

Use cwd `/abs/case`, isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`, closed stdin/no TTY.
Set `BEA_API_URL` to an owned loopback stub and only a synthetic `BEA_TOKEN`
in this child's environment; do not record headers. Run:

```sh
bea --json --file /abs/case/main.bean check
bea --json --file /abs/case/main.bean query "SELECT count(*) WHERE narration ~ 'from entries'"
bea --file /abs/case/main.bean ask 'Synthetic QA question' --print
```

Have the simulator's first chat completion call the real local tool:

```json
{"id":"call_qa_relation","type":"function","function":{"name":"run_bql_query","arguments":"{\"query\":\"SELECT count(*) WHERE narration ~ 'from entries'\"}"}}
```

It is an assistant `tool_calls` message with `finish_reason: tool_calls`
in the standard chat-completions envelope, served at
`/api-gateway/ai/openai/chat/completions`. On the following request, inspect
the `role: tool` content, then return a fixed synthetic assistant answer.

Actual: check, query and Ask exit **0**; the real query count is **4**
postings from **2** transactions, but Ask sends the model:

```text
1 row(s) from the entries table.
count(*)
4
```

It also omits the normal note that `count(*)` counts postings rather than
transactions. There is no actual `FROM` clause. Replacing the narration
regex with `'(from) entries'` matches exactly the same postings and returns
4, but Ask correctly says `postings`, explains its grain and supplies the
posting-count warning. A real `FROM #entries WHERE type = 'transaction'`
control returns **2** and correctly says `entries`. All controls repeated twice.

Two comment variants also reproduced twice:

- `SELECT count(*) /* from entries */ WHERE narration ~ '(from) entries'`
  still counts 4 postings, but Ask says `entries` and omits the warning.
- `SELECT count(*) FROM /* choose entry source */ #entries WHERE type = 'transaction'`
  counts 2 entries, but Ask says `postings` and wrongly warns it counted
  postings. The comment prevents recognizing the real `FROM`.

Every command leaves the ledger byte-identical. These are observed wrong
tool annotations, which can mislead an answer about transaction counts;
no actual model's resulting answer was evaluated.

Expected: report the query's actual relation and apply the count warning to
postings only. This is the explicit result contract in completed
w3/m51/t001 and `cli/docs/USAGE.md:2104–2114`.

Cause: `cli/src/cli/ask/results.py:73–79` applies `_FROM_TABLE` to the raw
query. Its first regex match can be inside a literal/comment, and it cannot
skip a comment between `FROM` and its relation. `format_result` trusts that
guess both for the header (:94–97) and the count footnote (:141–142).
The only product caller is `run_bql_query` in `cli/ask/agent.py:603`.
The engine executes these queries correctly; this is frontend annotation.

Fix: derive the relation from query syntax that distinguishes literals and
comments from code, or carry the engine's resolved relation in the tool
result. Preserve valid quoted table identifiers and the frontend's
no-Beancount boundary. Do not alter query text or its correct counts.

Dedupe: searched every board state and active milestone scope for Ask grain,
relations, table detection and quoted/commented `FROM`. Completed w3/m51
(`79ef0386d`) introduced this heuristic; its only later change in
`results.py` clips long first rows (`fe329f378`). Completed w3/399 handles
literal/comment masking in the engine's table-name rewriting, not this
independent frontend detector. No matching open repair or newer fix found.

Acceptance: pin both literal/comment false matches and commented real
`FROM`, plus the equivalent-regex and actual-entries controls through the
real tool. Require correct counts, relation and footnote together. Evidence:
`.tmp/qa-2026-10-20-cli-loop-pass3-69d827bc/repro_ask_relation.py`,
`repro_ask_relation_comments.py`, `ask-relation{,-v2}-simulation.json`,
`ask-relation{,-v2}-{1,2}/` and matching captures. All owned servers stopped,
no credentials captured. Hosted answers, broader nested-query relation
semantics, other platforms and repaired behavior remain unverified.

---

**Resolved 2026-10-22** — Ask now looks for the query's `FROM` in code only: string literals and `/* */` / `--` comments are blanked first (a double-quoted name right after `FROM` is kept), so a regex like `'from entries'` no longer relabels a postings count and a comment between `FROM` and `#entries` no longer hides the real relation; the postings count warning follows. `cli/tests/test_ask_result_relation.py` pins the relation and the footnote together and fails without the fix; shipped in the commit that moves this note (`cli`). Nested-query relation semantics remain unverified.
