# `cloud logout` treats a 504/524 on revocation as a plain failure (exit 1), and Cloudflare 521/522/523 (origin never reached) are reported as "the request arrived" with exit 4 (incomplete fix of w5/517)

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-17, HEAD `b8d871d0`, checkout `bea 0.3.1`, macOS 26.5.1. Simulation: local stub answers with gateway statuses. Follow-up to w5/517 (done).
w5/517 maps gateway timeouts on cloud writes to the unknown-outcome exit 4,
and USAGE:316 now says a write answered 504 or 520–524 exits 4. No product
fix implemented.

1. **Logout.** With a stored `credentials.json` and no `BEA_TOKEN`, a stub
   answering the revocation with 504 (or 524) `text/html`: `bea --json cloud
   logout` exits 1 with `Removed the local credential, but server revocation
   failed: Server error (HTTP 504). The session may still be valid…`. A stub
   that sleeps past the timeout gives exit 4 (`…timed out (ReadTimeout); the
   outcome is unknown…`). Expected: exit 4 with the unknown-outcome wording for
   504/524, as for create and delete. Cause: `cli/src/cli/commands/cloud/app.py:113`
   catches only `httpx.TimeoutException`; the gateway error falls to `except
   Exception` (`:118`).
2. **521–523 scope.** `bea --json cloud ledger create newbook` (and `-y cloud
   ledger delete qa/books`) answered 521, 522 or 523 exits 4 with `…timed out
   at the server's gateway (HTTP 521): the request arrived but was not
   answered. The outcome is unknown…`. Per Cloudflare's definitions, 521 (origin
   refused the connection), 522 (connecting to the origin timed out) and 523
   (origin unreachable) mean the origin never got the request, so w5/368's
   "never connected" rule applies: exit 1, "Could not reach the server". Only
   504, 520 and 524 mean the origin received it. Cause: `_GATEWAY_TIMEOUTS`
   (`cli/src/cli/errors.py:359`); USAGE:316 repeats the claim.

Fix: classify logout's gateway responses like other writes; narrow the
unknown-outcome set to 504, 520 and 524, and correct USAGE.

Dedupe: w5/517 and 521 (logout classification, open) are related; w5/368
(done) is the never-connected rule.

Acceptance: logout under 504 exits 4; create under 521/522/523 exits 1 with
"Could not reach". Tests pin them.

Addendum (CLI QA 2026-10-17, HEAD `101b89e3`): w5/521 (`315af713`) now catches
`GatewayTimeout` on logout, so item 1 is fixed. With a stored credential and a
stub answering 504 or 524 `text/html`, `bea --json cloud logout` exits 4 with
`…the server's answer to the revocation was lost or unreadable (HTTP 504); the
outcome is unknown.` Item 2 now applies to logout too: 522 gets the same exit 4
"lost or unreadable" message, although the origin never received the request.
Narrowing `_GATEWAY_TIMEOUTS` to 504, 520 and 524 fixes both paths.

**Resolved 2026-10-18** — Shipped in `bbd618b01c598934797235f720350cf5ffea188e` (`cli`). Cloudflare 521 and 523 now report connection failures with exit 1 (`Could not reach the server`) for create/delete/logout; reads remain exit 1. Gateway errors no longer claim that the request definitely arrived. Logout's existing unknown-outcome handling now also retains the request ID. The note's original logout 504/524 gap was already fixed in `315af713`; a real local stub confirmed both still exit 4.

The proposed removal of 522 was not adopted: [Cloudflare's primary 522 documentation](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-522/) lists both connection-setup and resource-request acknowledgment timeouts after TCP connects. We infer that status 522 alone cannot establish whether the write took effect, so it remains unknown-outcome exit 4 with 504/520/524. [521](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-521/) is a refused connection, and [523](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-523/) is an unreachable origin. USAGE records the distinction and cites the 522 source.
