# `bea import` on a ledger with a Latin-1 byte inside a comment exits 1 with a raw `UnicodeDecodeError` (category `validation`), although the ledger loads and `check` passes; `add` gives the clean decode message

**Minor · cli · 10m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
[w5/278](./done/278.md) deliberately keeps a non-UTF-8 byte that sits
only in a comment loadable: `check` passes and reads work. `add` refuses
to write to such a file with "Cannot decode … Re-save the file as UTF-8
and retry". The import preview builds its diff with an unguarded
`decode("utf-8")`, so preview and `--apply` both die with a Python class
name. The user cannot import into a ledger that every other command
accepts, and is not told how to fix it. No product fix implemented.

Create a ledger with a single Latin-1 byte in a comment, and a CSV:

```sh
printf 'option "operating_currency" "USD"\n; caf\xe9 comment\n2026-01-01 open Assets:Cash USD\n2026-01-01 open Expenses:Uncategorized USD\n' > main.bean
printf 'Date,Narration,Amount\n2026-01-05,food,-5.00\n' > s.csv
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, and
closed stdin.

```sh
bea -f /absolute/books/main.bean check
bea -f /absolute/books/main.bean import s.csv --account Assets:Cash --csv date=Date,narration=Narration,amount=Amount
```

Actual: `check` exits 0. `import` exits 1 with `Error: UnicodeDecodeError:
'utf-8' codec can't decode byte 0xe9 in position 39: invalid continuation
byte Pass --debug …` (JSON: `validation`). `--apply` fails the same way,
and the ledger is unchanged. Reproduced twice by the hunter and once by
me.

Control: `add transaction` on the same file exits 1 with `Cannot decode
'…' as UTF-8: invalid continuation byte at byte 39. Re-save the file as
UTF-8 and retry.`

Expected: import gives the same decode message as `add`, with no class
name and with the byte offset and remedy.

Cause: `appended_content` (`cli/src/bea_engine/ledger/write.py:1748`,
`original.decode("utf-8")`) is called from the import preview
(`cli/src/bea_engine/importing.py:477`) with no decode handling.

Fix: catch the decode error there, or in the preview, and raise the
existing `decode_error_message` `LedgerError`. No dependency change.

Blast radius: `bea import` preview and `--apply` on ledgers with stray
Latin-1 bytes in comments, which are common in hand-edited or migrated
books.

Dedupe: w5/278 covers reads and `check`. r57 found `add --into` refuses
cleanly. 440 covers doctor. None covers import's raw error.

Acceptance: on the fixture, import exits 1 with the "Cannot decode …
Re-save" message and no `UnicodeDecodeError`. A test pins it.

---

**Resolved 2026-10-15** — the decode guard that `add` used now lives in
`decoded_append` (`cli/src/bea_engine/ledger/write.py`). Both import
preview appends call it: the proposed diff and the entries-after load in
`cli/src/bea_engine/importing.py`. On the fixture, the preview and
`--apply` both exit 1 with `Cannot decode '…/main.bean' as UTF-8: invalid
continuation byte at byte 39. Re-save the file as UTF-8 and retry.`, with
no `UnicodeDecodeError`. The ledger is unchanged, and `check` still
passes. Pinned by `cli/tests/test_import_undecodable_comment.py`, which
fails without the fix.
