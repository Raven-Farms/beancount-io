# Check every recognized currency symbol in a CSV amount cell

**Minor · cli · 20–30m · A1.** A malformed CSV amount with two contradictory,
already recognized currency symbols is accepted when the first symbol agrees
with the resolved commodity. `-£4.50€` becomes −4.50 GBP, exit 0 and check
clean; reversing those symbols correctly refuses the row. This is ambiguous
source data that should require correction, not a basis for choosing either
currency. No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `55f3bb0cd` (rechecked unchanged CLI sources
after pulling `5793e4e95`), checkout `bea 0.3.1`, macOS 26.5.1 arm64,
frontend Python 3.13.3, existing managed Python 3.12 engine. Fresh subprocesses,
closed stdin/no TTY, absolute isolated `BEA_CONFIG_DIR` and `XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`.

Create disposable `/abs/books/main.bean`:

```beancount
option "operating_currency" "GBP"
2024-01-01 open Assets:Cash GBP
2024-01-01 open Expenses:Food GBP
```

Create `/abs/books/bank.csv`:

```csv
Date,Description,Amount,Reference
2024-02-01,Coffee,-£4.50€,coffee-1
```

From `/abs/books`, using the isolated child environment above:

```sh
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --account Assets:Cash --csv date=Date,narration=Description,amount=Amount,id=Reference --default-account Expenses:Food
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --account Assets:Cash --csv date=Date,narration=Description,amount=Amount,id=Reference --default-account Expenses:Food --apply
bea --json -f /abs/books/main.bean query "SELECT number,currency WHERE account='Assets:Cash'"
bea --json -f /abs/books/main.bean check
```

Actual: all four exit 0. Preview marks the row ready as `-4.50 GBP`; apply
writes one transaction. Fresh BQL answers `[["-4.50", "GBP"]]`; check passes.
Both symbols disappear from the authored posting. Preview preserves ledger
bytes and the source CSV remains byte-identical.

Expected: preview/apply refuse at exit 2, naming the row, amount column and
contradictory symbol(s), with zero writes. IMPORTING's currency-symbol rule
requires refusing a symbol that contradicts the resolved currency. `€` already
has an EUR-only association in the implemented guard. Do not auto-select a
currency, convert the number, or widen the account's allowed currencies.

Controls and scope:

- Fourteen fresh JSON journeys, two repetitions of seven cases: GBP with
  `-£4.50€`, EUR with `-€4.50£`, and RUB with `-₽4.50€` all preview/apply
  successfully in the first symbol's currency. All six ambiguous writes pass
  fresh checks; unchanged repeats skip their native IDs. A single `-4.50€`
  against GBP correctly refuses at exit 2 without changing the ledger.
- Redundant matching `-£4.50£`/GBP and `-€4.50€`/EUR succeed correctly, as does
  the documented ambiguous-dollar control `-$4.50€`/EUR. Preserve these
  controls: the needed rule is to check every recognized association, not to
  reject any cell that contains two symbols.
- Sixteen additional fresh human-output journeys, twice each: reversed
  first-mismatching symbols correctly refuse on GBP and EUR accounts; currency
  column, debit pair, credit pair, direction, `sign=ledger` and constant
  currency modes all reproduce the accepted contradiction. Magnitudes and
  signs remain correct, including positive credits. Source CSVs stay unchanged.

Cause: `cli/src/bea_engine/csv_mapper.py:_cell_symbol_currency` (:138–151)
returns inside the first recognized-character iteration. `_check_cell_symbols`
(:1548–1578) therefore checks only that association; when it agrees, it proceeds
to the next amount column. `_split_amount_sign` (:170–214) strips both edge
symbols before parsing the number, so the unchecked contradiction is lost.
`CsvImporter.extract` invokes this shared guard at :1743 after resolving
currency for all supported amount modes. No frontend twin of this guard or
other caller was found; Python importers and native explicit-commodity
postings do not use this CSV symbol stripping.

Fix: inspect all recognized symbols in each mapped amount cell and require the
resolved currency to belong to every recognized symbol's association set.
Preserve the documented `$`/`¥` exceptions and the shared `£`/`₩` associations,
including GIP and KPW controls. Repeated compatible symbols remain accepted.
Keep the existing currency-resolution precedence and exact number/sign handling;
no dependency or backend/API change needed.

Dedupe: searched all `.pm` states for multiple/first/conflicting currency
symbols and the helper name; scanned 46 active/blocked milestone scopes and
targeted history. Completed w3/421 and w3/m49/t004 (`78217b30d`) introduced
this first-match guard. Completed w5/265 handles symbol/sign placement and
w5/757 (`dabfdb4ce`) expands shared pound/won associations. Open w5/924 is
missing table entries: all symbols in this finding already exist in that
table, so adding its five mappings does not address this early return. No
overlapping open repair or later fix found.

Acceptance: the public malformed cell and the EUR/RUB variants refuse in
preview/apply with unchanged ledgers; symbol order cannot hide a contradiction.
All amount modes agree. Single matching symbols, repeated compatible symbols,
the ambiguous-dollar control and w5/757's shared associations remain accepted.
The public commands above were replayed twice from pristine fixtures. Only
macOS/checkout tested; repaired behavior remains unverified.

**Resolved 2026-10-22** — the CSV currency-symbol guard now reads every distinct recognized symbol in an amount cell (`_cell_symbol_currencies`) and refuses the row if the resolved currency fails any of them, so `-£4.50€` on a GBP account is refused like the reversed `-€4.50£`, with exit 2 and the ledger unchanged; repeated compatible symbols, a single matching symbol and the deliberately ambiguous `$`/`¥` still import. `cli/tests/test_import_multiple_currency_symbols.py` fails for the GBP-then-EUR, EUR-then-GBP and RUB-then-EUR cells without the fix; shipped in the commit that moves this note (`cli`). The currency-column, direction, ledger-sign and constant-currency modes share the guard and were not run separately.
