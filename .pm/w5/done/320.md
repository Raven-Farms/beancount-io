# A managed engine whose packages are present but damaged still reports `Provisioned: yes`: every command prints a traceback, and a write exits 4 "the outcome is unknown" although nothing ran

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, simulated managed engine root (Python 3.13).
[w1/122](../w1/done/122.md) made an engine missing the `beancount` or
`beanquery` directory count as unprovisioned, so it gets rebuilt. If those
directories exist but their contents are damaged, the engine is still
trusted. Damage like this can come from a cleaner or antivirus quarantine
removing a compiled extension, an interrupted copy, or a half-deleted
package.

The result:

- `bea engine status` reports `Provisioned: yes`.
- Every helper command fails with a raw `ImportError` traceback.
- A write exits 4 (`conflict`) with "the outcome is unknown. Inspect the
  file before retrying", although the engine died while importing its own
  modules and never read the request.

No product fix implemented.

Setup (simulation, no network):

- Build a working managed root at `/absolute/eng/noso`: `bin/python` and
  `pyvenv.cfg` from a Python 3.13 venv that has Beancount and Beanquery,
  plus that venv's `lib/python3.13/site-packages`.
- Delete only `beancount/parser/_parser.cpython-313-darwin.so`.
- Set `BEA_ENGINE_DIR=/absolute/eng/noso`.
- Use isolated BEA_CONFIG_DIR and XDG dirs, BEA_NO_UPDATE_NOTIFIER=1, no
  inherited BEA_FILE/BEA_TOKEN/BEA_ENGINE_PYTHON, and closed stdin.
- Use any valid ledger.

```sh
bea engine status
bea -f /absolute/books/main.bean balance
bea -f /absolute/books/main.bean add note --date 2026-01-05 -a Assets:Checking -m x
bea --json -f /absolute/books/main.bean add note --date 2026-01-05 -a Assets:Checking -m x
```

Actual:

- `engine status` exits 0 with `Provisioned: yes`, served from the managed
  engine.
- `balance` exits 1 with `The Beancount engine did not answer … (exit 1).`
  and a traceback ending in `ImportError: cannot import name '_parser'
  from 'beancount.parser'`.
- Both `add note` runs exit **4** with `… the outcome is unknown. Inspect
  the file before retrying.`, and JSON reports `"category": "conflict"`.
  The ledger is unchanged.
- An empty `beancount/` directory behaves the same way.
- Retrying never helps, and nothing rebuilds the engine.

Reproduced independently in a fresh run.

Control:

- With `BEA_ENGINE_DIR` unset, `add note` exits 0.
- A root missing the `beancount` directory is rebuilt (w1/122).
- A `BEA_ENGINE_PYTHON` override that cannot import the helper exits 1
  and names the variable (w5/269).

Expected: `docs/USAGE.md` says "A broken managed environment is discarded
and rebuilt on the next successful provision", and that exit 4 means "a
write whose outcome is unknown". So `engine status` should report a managed
engine that cannot import the helper as damaged, and the next command
should rebuild it or say "Remove <root> and rerun". A write that was
refused at import time ran nothing and should not exit 4.

Cause: `is_provisioned` (`cli/src/cli/engine/paths.py:107-121`) only checks
that `bin/python` exists and that the core package directories are
directories. When the helper dies without an envelope, `launch.py:578-594`
calls `_refuse_unusable_override` (`:611-645`). That returns at once unless
`BEA_ENGINE_PYTHON` is set, so a managed engine is never import-probed,
and a writer falls through to the unknown-outcome `ConflictError`.

Fix: when the helper produced no envelope, run the same probe for the
managed tier (`python -P -c "import bea_engine.main"`). If it fails,
report the managed root as damaged (name it and say "Remove <root> and
rerun", or mark it unprovisioned so the next command rebuilds it under
the provisioning lock), and exit 1 for a write. Optionally, have
`engine status` run the probe too. No dependency or API change.

Blast radius: every helper-path command (`balance`, `list`, `report`,
`query`, every `add`, `import`, `price`) on a managed root whose package
contents are damaged.

Dedupe: searched `.pm/**` (including `done/`) for `is_provisioned`,
"damaged", "did not answer" and "Provisioned: yes".

- w1/122: fixed only the missing-directory case.
- w5/269: the override probe only.
- w1/061: plugin stdout.
- w2/022: tier reporting.

None of them is open.

Acceptance: on the fixture,

- `engine status` does not report an unqualified `Provisioned: yes`;
- `balance` either rebuilds the engine or exits 1 naming the root and the
  remedy, with no bare traceback;
- `add note` exits 1 (not 4), names the root, and leaves the ledger
  unchanged.

A regression test covers a managed root missing its `_parser` extension.
Only macOS and a simulated managed root were exercised.

---

**Resolved 2026-10-15** — `cli/src/cli/engine/launch.py` factors the w5/269/w5/309 sentinel probe into `engine_load_failure(python)`. `_refuse_unusable_engine` (formerly `_refuse_unusable_override`) now probes whichever tier served, override or managed, when the helper produces no envelope. A managed engine that cannot import the helper exits 1 with "The managed Beancount engine at <root> is damaged and cannot load (<reason>). Remove <root> and rerun; bea provisions a fresh engine.", so a write no longer exits 4. `bea engine status` runs the same probe for a managed engine and prints `Provisioned: damaged — …` (JSON `damaged`) instead of `yes`. A copy of the real engine with `beancount/parser/_parser*.so` removed (`BEA_ENGINE_DIR` pointed at the copy) showed all three behaviours, and the ledger stayed unchanged. USAGE's provisioning paragraph says so. `cli/tests/test_engine_damaged_managed_root.py` uses a venv whose `beancount/` and `beanquery/` are present but empty, the same import failure, and covers status, `balance` and `add note`; all 3 fail with the fix reverted. `test_engine_optional.py`'s tier test, whose fake venv cannot import, now stubs the probe. The engine is not rebuilt automatically: removing the user's engine directory is left to them. Only macOS was exercised. `make check-all` passed. Shipped in `a79f56d0` (`cli`).
