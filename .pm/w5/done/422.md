# `cloud ledger create`/`delete` exit 1 ("Empty response (HTTP 201)", "Unexpected server response (HTTP 200)") when the server answers a write with a success status bea cannot read, so a retry conflicts or finds nothing

**Trivial · cli · 15m · A2.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1. **Simulation:** the server behaviour comes from a localhost mock. The defect is in how the CLI classifies the outcome of a write.

A 2xx response to a write most likely means the server applied it.
When bea cannot read the body (version skew, a proxy, an empty 201/204),
it reports the read-style "unexpected response" with exit 1 and category
`validation`. The user is not told that the ledger may now exist, or may
already be deleted, so the natural retry hits 409 or 404. With `create
--clone`, the clone is silently skipped. USAGE reserves exit 4 for "a
write whose outcome the CLI cannot know … and says so rather than
guessing". That is A2 because USAGE also states the generic exit-1 rule
for unreadable 2xx bodies. No product fix implemented.

Setup: a localhost mock answers `POST /api-gateway/v1/ledgers` with 201
and a valid body (or 200 with `{}`/`null`), and `DELETE
/api-gateway/v1/ledgers/{owner}/{name}` with 200 and `{}`. Use isolated
BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, an obviously
fake `BEA_TOKEN`, `BEA_API_URL` and `BEA_DASHBOARD_URL` on 127.0.0.1,
and closed stdin.

```sh
bea cloud ledger create my-new
bea --yes cloud ledger delete qa/one
```

Actual: exit 1 with `Empty response (HTTP 201).` and `Unexpected server
response (HTTP 200).`. Nothing says the write may have happened. The
hunter also saw 202/204 and the `--clone` variant. Reproduced at least
twice by the hunter and once by me.

Control: the same writes answered with 200 and a valid body succeed with
exit 0.

Expected: on write paths, a 2xx that cannot be parsed, or that is empty,
should exit 4 with an unknown-outcome sentence, for example "the server
accepted the create but its response could not be read; check `bea cloud
ledger list` before retrying". Reads keep the documented exit-1 rule.

Cause: `call` and `unwrap` (`cli/src/cli/api/client.py`, about
`:150-177`) raise the generic read errors. The write callers catch only
transport errors for `unknown_write_outcome`:

- create: `cli/src/cli/commands/cloud/ledger/app.py:68-71`;
- delete: the generated `cli/src/cli/commands/cloud/generated/ledger.py:95-98`,
  from `cli/scripts/gen_cloud_commands.py`.

Fix: in those write paths and the generator template, map an unreadable
or empty 2xx to `unknown_write_outcome` (exit 4). No dependency change.

Blast radius: `bea cloud ledger create`/`delete` during server or proxy
version skew.

Dedupe: 366 (parse fallback on `cloud status`), 367 (redirect or 204 on
`status`), 368 (refused connection mislabelled exit 4) and 371 (target
check after create) cover other parts. None covers an unreadable 2xx on a
write.

Acceptance: with the mock bodies above, both commands exit 4 with the
unknown-outcome wording, in text and JSON. A 200 with a valid body still
succeeds. A mocked-transport test pins create and delete.

---

**Resolved 2026-10-15** — `call` and `unwrap` (`cli/src/cli/api/client.py`)
now raise `UnreadableSuccess`, a `BeaError` carrying the status, for a
success whose body cannot be read or is empty. Reads keep their exit-1
`Unexpected server response` / `Empty response` wording. On writes,
`unknown_write_outcome` (`cli/src/cli/errors.py`) turns it into exit 4:
`Creating ledger 'new2' was answered with HTTP 201, but the response
could not be read. It most likely took effect, but the outcome is unknown
— check the current state before retrying.`, in text and JSON (category
`conflict`). Both write paths catch it: `cloud ledger create`
(`cli/src/cli/commands/cloud/ledger/app.py`), and the generator
(`cli/scripts/gen_cloud_commands.py`) with its regenerated `cloud ledger
delete`. A readable 200 still succeeds. USAGE states the write rule.
Pinned by `cli/tests/test_cloud_write_unreadable_success.py` (simulated
with pytest-httpx), which fails without the fix.
