# `bea cloud login` with `BEA_TOKEN` set prints "Logged in successfully." and exits 0, but the new session is never used: the next command still sends `BEA_TOKEN`

**Minor · cli · 10–15m · A1/A2.** Real CLI QA, 2026-10-16, HEAD `d16aea3e`, checkout `bea 0.3.1`, macOS 26.5.1. Simulation: local stub API runs the device flow; one run on a PTY with `BROWSER=/usr/bin/true`, no real login.
USAGE: `BEA_TOKEN` "takes precedence over the stored file unconditionally …
rather than to log in, which would not change which credential is sent".
bea's own 401 message says the same. `cloud logout` handles a set
`BEA_TOKEN` explicitly; `cloud login` does not. A user whose CI token was
revoked logs in, sees success, and is still refused. No product fix
implemented.

Stub: `POST /api-gateway/v1/cli-sessions` returns a device code;
`GET …/cli-sessions/<code>` returns `{"status":"AUTHORIZED"}`;
`POST …/consume` returns a fresh token; `GET /api-gateway/v1/user-profile`
returns 401 `Token revoked` for the stale token.

```sh
BEA_TOKEN=stale BROWSER=/usr/bin/true bea cloud login     # on a terminal
BEA_TOKEN=stale bea --json cloud status
```

Actual: login exits 0 with `Logged in successfully.` and writes
`credentials.json`; `cloud status` exits 3 with `Not authorized (Token
revoked). BEA_TOKEN is the credential in use, and 'bea cloud login' does not
change that: correct or unset BEA_TOKEN…`. The stub log shows the profile
request carrying the stale token.

Control: without `BEA_TOKEN`, `cloud status` after the login shows `Source:
file` and exits 0.

Expected: with `BEA_TOKEN` set, `cloud login` refuses before starting the
flow (exit 2: `BEA_TOKEN is set and takes precedence over a login; unset it
first`). Alternatively it completes and warns on stderr that `BEA_TOKEN` will
still be used, without the unqualified success line.

Cause: `cloud_login` (`cli/src/cli/commands/cloud/app.py:24-38`) never checks
the environment before `run_device_flow` and `output.success`.

Fix: the refusal (or warning) above, mirroring `cloud_logout`'s
`ENVIRONMENT` branch.

Dedupe: w5/012 (401 advice) and w1/002 (logout with `BEA_TOKEN`) are done;
no note covers login.

Acceptance: login with `BEA_TOKEN` set refuses (or warns) and never prints
the bare success line. A test pins it.

---

**Resolved 2026-10-17** — Shipped in `3f055ad1` (`cli`). `cloud login` (`cli/src/cli/commands/cloud/app.py`) now exits 2 when `BEA_TOKEN` is set (non-empty, as `load_credentials` reads it), before the device flow starts or anything is written. The message is `BEA_TOKEN is set in this shell and takes precedence over a login, so the new session would never be used. Unset BEA_TOKEN first, then run 'bea cloud login'.` It never prints the bare success line. USAGE's credentials paragraph says so. `tests/test_cloud_login_with_env_token.py` pins the refusal, with no credential file and no request, which fails without the fix, and that an empty `BEA_TOKEN=` still counts as unset.
