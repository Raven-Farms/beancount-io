# Parallel previews lose per-file `sign=ledger` memory, so a flag-free apply books the opposite sign with exit 0 (follow-up to w5/594 and w5/214)

**Major · cli · 45–60m · A1.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `fdeb23a35`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
Reproduced twice from pristine synthetic ledgers/configuration, with four
real CLI preview processes launched together; sequential controls repeated
twice. No plugin, artificial barrier, mocked operation or product fix.

Create a fresh `/abs/books/main.bean`:

```beancount
2024-01-01 open Liabilities:QaCard USD
2024-01-01 open Expenses:Uncategorized USD
```

Create four CSV files with the same header, distinct rows and positive
ledger-signed charges; launch these previews concurrently. This standalone
driver closes stdin, captures each stream/status, and bounds every child:

```python
import os, subprocess
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path
books = Path('/abs/books')
env = os.environ.copy()
for key in ('BEA_FILE', 'BEA_TOKEN'):
    env.pop(key, None)
env.update(BEA_CONFIG_DIR=str(books / 'config'),
           XDG_CACHE_HOME=str(books / 'cache'), BEA_NO_UPDATE_NOTIFIER='1')
for i in range(1, 5):
    (books / f'memory-{i}.csv').write_text(
        f'Date,Description,Amount\n2024-02-{i:02},Concurrent memory {i},{i*10}.00\n')
def preview(i):
    return subprocess.run(
        ['/abs/checkout/cli/.venv/bin/bea', '--json', '--file', str(books/'main.bean'),
         'import', str(books/f'memory-{i}.csv'), '--account', 'Liabilities:QaCard',
         '--csv', 'date=Date,narration=Description,amount=Amount,sign=ledger'],
        cwd=books, env=env, input='', text=True, capture_output=True, timeout=15)
with ThreadPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(preview, range(1, 5)))
for result in results:
    print(result.returncode, result.stdout, result.stderr)
```

All four previews exit 0 and leave the ledger unchanged. They correctly
show card amounts −10, −20, −30 and −40 USD. Both captured runs then have
only **one** entry in the record's `sign_ledger_files` map, instead of four.
The surviving file varies. With the same isolated environment/cwd, apply
the unchanged files without flags, then query/check:

```sh
bea --json --file /abs/books/main.bean import /abs/books/memory-1.csv --apply
bea --json --file /abs/books/main.bean import /abs/books/memory-2.csv --apply
bea --json --file /abs/books/main.bean import /abs/books/memory-3.csv --apply
bea --json --file /abs/books/main.bean import /abs/books/memory-4.csv --apply
bea --json --file /abs/books/main.bean query 'SELECT account, sum(number) GROUP BY account ORDER BY account'
bea --json --file /abs/books/main.bean check
```

Actual: every apply exits 0, but files whose sign disappeared are booked
positive, opposite to their previews. In repeat 1, only file 1 retained its
sign; the final card balance is **+80 USD**. In repeat 2, only file 2
retained it; the final card balance is **+60 USD**. Expenses have the
opposite totals, so check passes. Expected: card **−100 USD**, expenses
**+100 USD**, matching the four earlier previews. There is a note claiming
the lost file is another file and is therefore "read bank-signed"; it does
not preserve the sign already chosen for that very file.

The first lost-file apply was independently queried before applying the
rest: repeat 1 writes file 2 as **+20**, where its preview was **−20**;
repeat 2 writes file 1 as **+10**, where its preview was **−10**. Its JSON
result reports one row written. Thus the mismatch is persisted accounting
data, not only a preview or summary difference.

Working control: perform the same four explicit previews sequentially on a
pristine root/configuration, then apply the same files without flags. Both
repetitions retain the signs, write −20/−10 for the selected individual
controls, and finish with card **−100** / expenses **+100 USD** and a clean
check. IMPORTING's per-file sign contract at :327–338 explicitly says
previewing another file leaves each earlier file's sign in place. Four
files are below the implementation's 64-entry cap.

Cause: `cli/src/cli/commands/import_.py:1431–1444` builds the entire
`csv_to_remember`, including `_signed(_sign_ledger_files(prior), ...)`,
**before** launching the engine at :1510. Concurrent previews capture the
same earlier sign map. `_remember_csv` (:688–724) does acquire an exclusive
lock and re-read the record, but filters out the matching header/account
entry and replaces it wholesale with that stale spec. This preserves
different mapping entries (w5/214) while losing concurrent per-file sign
updates inside the same entry. Key-only sign updates also build their map
before the helper at :1188–1191; that route was traced but not separately
exercised here.

Fix: apply this run's per-file sign change against the latest matching
entry **inside** the record lock, instead of replacing its complete sign
map from a pre-preview snapshot. Preserve independent files, the 64-file
bound, legacy records, canonical account matching and intentional
`sign=bank` removal of only the selected file. Merely unioning stale maps
can resurrect an intentional removal. Keep existing whole-record locking
for other headers/accounts, and ordinary explicit mapping refresh behavior.
No dependency or backend/API change is needed.

Dedupe: searched all board states for parallel/concurrent sign memory,
`sign_ledger_files`, per-file signs and lost updates, and reviewed open
milestone scopes. Completed w5/214 (`b229498d`) locks whole-record updates
for distinct mappings; w5/594 (`53f4c4ca1`) adds per-file sign maps and pins
sequential flows. Its sequential acceptance still holds, but the new field
is computed outside that older lock. Targeted history contains no repair
for this same-entry race. No overlapping open item found.

Acceptance: parallel successful previews retain every file's chosen sign,
and unchanged flag-free applies book all four exactly once as −100/+100
USD with check passing. The sequential controls, per-file bank-sign
override, legacy migration and different-account/header locking remain
correct. Pin real concurrent CLI coverage and a deterministic shared-record
regression test. Windows/Linux, simultaneous opposite sign choices for one
file, key-only sign updates and repaired behavior remain unverified.
Sanitized fixtures, immediate memory snapshots and captures are under
`.tmp/qa-2026-10-20-cli-loop-pass2-2afc4ed1/`, especially
`concurrent-sign-memory-{1,2}/`, `sequential-sign-memory-{1,2}/` and
`captures/concurrent-sign-*.json`. The public reproduction is self-contained.

## Adjacent case: a concurrent bank-sign override is lost or resurrected

Two fresh repetitions with the same CLI sources also exercise an intentional
removal. Use the root above, `a.csv` containing
`2024-02-01,Charge A,10.00` and `b.csv` containing
`2024-02-02,Charge B,20.00`, both under `Date,Description,Amount`.

1. Preview A with the full mapping and `sign=ledger`, seeding its sign.
2. Launch two previews together: A with the same full mapping but
   `sign=bank`, and B with `sign=ledger`. Both exit 0 and correctly preview
   A as **+10**, B as **−20 USD**; ledger bytes remain unchanged.
3. Apply A and B without flags, query the card total, then check.

Repeat 1 applies A as **−10** and B as **−20**, total **−30 USD**: B's stale
map resurrected A's removed ledger sign. Repeat 2 applies A as **+10** and B
as **+20**, total **+30 USD**: A's stale removal discarded B's newly chosen
sign. Every apply exits 0 and each final ledger passes check. Expected in
both cases: **−10 USD**, from the +10/−20 previews.

The otherwise identical sequential updates (seed A ledger, preview A bank,
preview B ledger, then apply both) produce **−10 USD** with a clean check in
both repetitions. This directly supports applying independent per-file
changes inside the lock and proves why unioning stale maps is insufficient.
These are opposite choices for different files; conflicting concurrent
choices for the very same file remain unverified. No new root cause or
separate work item is claimed. Evidence is
`.tmp/qa-2026-10-20-cli-loop-pass3-69d827bc/sign-removal-{1,2}-{parallel,sequential}/`
and matching `captures/sign-remove-*.json`.

The original w5/214 control was rechecked for all **50** requested
repetitions: two parallel previews with one header and different source
accounts retain both accounts, and a flag-free apply exits 2 naming both,
with every ledger byte-identical. This isolates the new same-entry sign-map
race from the older whole-record race. Evidence is
`original-parallel-mapping-controls.json` and
`captures/original-parallel-*.json` in the same pass-3 directory.

**Resolved 2026-10-22** — a run's per-file sign change is now applied to the stored entry under the CSV-memory lock, not written from the map it read before its preview ran, so parallel previews keep every file's chosen sign and a concurrent `sign=bank` removal is neither lost nor resurrected. `cli/tests/test_import_sign_memory_concurrent.py` pins both interleavings deterministically plus four real parallel previews and their flag-free applies, and fails without the fix; shipped in the commit that moves this note (`cli`). Key-only sign updates and opposite choices for one file were not exercised.
