# Preserve an existing short lot's label when a positive posting covers it

**Major · cli · 45–60m · A1.** A positive-quantity short cover is treated as
a new long purchase for label normalization. A multiline lot selector becomes
another existing label, silently covering the wrong short lot: gain and
at-cost net worth become **30 USD instead of 10 USD**, exit 0, check clean.
No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `650ce6f72` (CLI unchanged from
`b38e69407`), checkout `bea 0.3.1`, macOS 26.5.1 arm64, frontend Python
3.13.3, existing managed Python 3.12 engine; Beangulp already enabled.
Fresh subprocesses, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited
`BEA_FILE`/`BEA_TOKEN`. All cases reproduced twice from pristine synthetic
fixtures. This is lot selection, not same-day batch ordering.

Create disposable `/abs/books/main.bean`. The first lot's label contains a
literal line break; the second contains a space. Both are valid distinct lots:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Stock HOOL "FIFO"
2024-01-01 open Assets:Cash USD
2024-01-01 open Income:Gains USD
2024-01-02 * "First short lot"
  Assets:Stock -2 HOOL {100 USD, "First
Lot"}
  Assets:Cash 200.00 USD
2024-01-03 * "Second short lot"
  Assets:Stock -2 HOOL {120 USD, "First Lot"}
  Assets:Cash 240.00 USD
```

Create `cover.json` (JSON `\n` denotes the first label's real line break):

```json
[
  {
    "date": "2024-02-01",
    "narration": "Cover first short lot",
    "postings": [
      {
        "account": "Assets:Stock",
        "units": {"number": "1", "currency": "HOOL"},
        "cost": {"label": "First\nLot"}
      },
      {"account": "Assets:Cash", "units": {"number": "-90.00", "currency": "USD"}},
      {"account": "Income:Gains"}
    ]
  }
]
```

From `/abs/books`, with the isolated child environment above:

```sh
bea --json -f /abs/books/main.bean check
bea --json --no-input -f /abs/books/main.bean add transactions --from /abs/books/cover.json
bea --json -f /abs/books/main.bean query "SELECT date,number,cost_number,cost_date,cost_label WHERE account='Assets:Stock' ORDER BY date,cost_date"
bea --json -f /abs/books/main.bean query "SELECT sum(number) WHERE account='Income:Gains'"
bea --json -f /abs/books/main.bean check
```

All exit 0; apply writes one transaction. It writes `{"First Lot"}`, not the
given selector. The cover's fresh BQL row has **1 HOOL, cost 120 USD,
acquisition date 2024-01-03, label `First Lot`**. Gains query returns
**−30.00 USD**, so profit is 30. The JSON input remains byte-identical.

Expected cover: **cost 100 USD, date 2024-01-02, original multiline label**,
gains −10.00 USD. Covering one share sold at 100 for 90 earns 10, not 30.
Cash is 350 and net quantity is −3 under either result, so those checks alone
miss the wrong lot. At-cost balance sheet and income statement also report
30 instead of 10. The remaining short cost basis is wrong by 20 USD.

Independent native control: rebuild the original two-lot fixture above as
`/abs/books/native.bean`, then append this exact directive:

```beancount
2024-02-01 * "Cover first short lot"
  Assets:Stock 1 HOOL {"First
Lot"}
  Assets:Cash -90.00 USD
```


All exit 0; native booking selects the first 100 USD lot and gains −10.00.
No engine modification or special plugin is involved.

Controls and scope:

- Twelve fresh journeys: two repetitions × wrong-alias cover / cover without
  an alias / date-only cover / negative-quantity long sale / plain-label cover /
  new long buy. With no space-labelled sibling, CLI falsely refuses the valid
  cover at exit 1 and leaves the ledger unchanged; native control succeeds.
  A date-only selector covers the intended short lot. The long sale and
  ordinary-label cover select correctly and earn 10. New long buys retain the
  documented new-label normalization; do not fix this by disabling it globally.
- Four additional human-bulk/Python-importer journeys reproduce the wrong
  120 USD lot and 30 USD gain, twice each. The inspected importer returns a
  positive cover with the same raw label and a normal omitted balancing amount.
  Preview preserves the ledger but renders the changed label; apply writes the
  wrong trade, check passes, and an unchanged stable-ID repeat skips it.
- Eight financial-report reads on CLI versus native copies confirm profit and
  at-cost net worth **30 versus 10 USD**. All native reference fixtures validate.

Cause: `cli/src/bea_engine/ledger/writer.py:238–253`,
`normalize_entry_strings.posting_strings`, considers a label a reduction
selector only when the units number is **negative**. A short cover is positive
but reduces a held negative lot. `single_line` therefore changes its selector
before booking. If the normalized label names another held lot, native booking
correctly selects that different lot and infers the wrong gain without errors.
If it names none, the otherwise valid cover refuses.

Caller search finds repeated normalization in `writer.format_entry` (:320),
the add answer path (`ledger/adding.py:1228`), and importer extraction/indexing/
hash paths (`importing.py:444/:494/:1098/:2316`). Fixing one display renderer
alone cannot preserve the selector through those steps. Booked inventory, not
units sign alone, determines whether a posting reduces a lot.

Fix: preserve the exact label of a real lot reduction, including a positive
short cover, through normalization, writing and JSON answers. Use the existing
inventory/booking semantics to distinguish reductions from new lots; do not
globally stop normalizing new labels or guess from positive/negative sign.
Keep native booking, exact acquisition dates, and the date-only/plain-label/
long-sale/new-buy controls. No dependency or backend/API change needed.

Dedupe: searched all board states for short-cover labels and label normalization,
and scanned active milestone scopes. Completed w5/733 (`d92b34a97`) preserves
negative sale labels but explicitly defines reduction by negative units, leaving
this positive cover gap. Open [884](./884.md) reorders same-day bulk trades;
this single later-dated cover uses already booked inventory and needs no
reordering. [915](./915.md) concerns printing an empty booked label. No open
short-cover selector repair or later fix found.

Acceptance: the public cover and native control select the same first lot,
with gains −10, profit/net worth 10 and check clean. With no alias, the valid
cover succeeds; human, bulk JSON and Python-importer paths agree. Source input
bytes and existing ledger lines remain unchanged, and a genuine no-match still
refuses. Preserve the working controls and unchanged-ID repeat behavior.

**Resolved 2026-10-22** — a positive posting whose cost label names a short lot the ledger holds is now treated as a reduction, so its label is matched and written exactly as typed: `normalize_entry_strings` consults a per-write, lazily evaluated set of the ledger's short labelled lots (`short_lot_labels`, set around single/bulk `add` and around `import`), asked only for a labelled positive posting so no other write reads the ledger for it. A multiline selector now covers the first short lot (gain −10, not −30), the cover with no space-labelled sibling no longer refuses, an importer's cover agrees, and a new long buy still normalizes its label. `cli/tests/test_add_short_cover_lot_label.py` fails for the three cover paths without the fix; shipped in the commit that moves this note (`cli`). Human bulk output and at-cost report reads were not rerun separately.
