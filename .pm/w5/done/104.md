# `--json query PRINT` emits Python object reprs for `custom` values and `open` booking

**Minor · cli · 30–45m · A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS.
Directive rows in query JSON are dumped field by field with a string fallback,
so machine output contains Python internals — `"Booking.FIFO"`,
`"<class 'str'>"`, `"_tuplegetter(0, …)"` — where `bea list` emits a
clean, documented shape for the same directives. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Broker HOOL "FIFO"
2024-01-01 open Expenses:Food
2024-01-04 custom "budget" Expenses:Food "monthly" 400.00 USD TRUE 2024-01-01 -3.5
2024-01-05 * "Grocer" "Refund (partial)" #food #trip #reimbursable
  Expenses:Food  -5.00 USD
  Assets:Cash
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY. The fixture passes
`bea check`.

```sh
bea --json -f /absolute/books/main.bean query "PRINT FROM type = 'custom' OR type = 'open'"
bea --json -f /absolute/books/main.bean list custom
```

Actual: the query exits 0 and its rows include

```text
"booking": "Booking.FIFO"
{"value": "Expenses:Food", "dtype": "<AccountDummy>"}
{"value": "monthly", "dtype": "<class 'str'>"}
{"value": {"number": "400.00", "currency": "USD"}, "dtype": {"number": "_tuplegetter(0, 'Alias for field number 0')", "currency": "_tuplegetter(1, 'Alias for field number 1')"}}
{"value": "-3.5", "dtype": "<class 'decimal.Decimal'>"}
```

Repeated twice.

Control: `list custom` returns `{"kind": "account", "value":
"Expenses:Food"}`, `{"kind": "text", "value": "monthly"}`,
`{"kind": "amount", "number": "400.00", "currency": "USD"}` and
`{"kind": "number", "value": "-3.5"}`. A worker confirmed `list open`
gives `"booking": "FIFO"` and the text `PRINT` is valid Beancount.

Expected: `docs/USAGE.md` points at the directive models as the exact
fields of directive JSON, and the board has treated Python reprs in output as
bugs (w3/450, w1/145). A directive in query JSON should use the shape
`list` uses, or at minimum carry no interpreter reprs: the booking method
as `"FIFO"`, custom values as `{kind, value}`.

Cause: `cli/src/bea_engine/protocol.py:275-287` (`_jsonable`), reached
from `cli/src/bea_engine/query.py:172`. A directive is dumped through
`_asdict`; anything unrecognised falls to `str(value)` at `:287`. The
`Amount` class used as a `dtype` passes the `number`/`currency`
attribute test and yields the two property reprs.

Fix: serialise directives in query JSON through the reader models `list`
already uses; failing that, map enums to their value and custom values to
`{kind, value}`, dropping `dtype`. Note the shape in USAGE. No dependency
change; this alters a JSON shape nobody can rely on today.

Blast radius: `--json` with `PRINT`, `SELECT entry` and `SELECT *` on
entry tables, for ledgers with a `custom` directive or an explicit booking
method.

Dedupe: board search for `_tuplegetter`, `AccountDummy`, `Booking.` and
`dtype` finds nothing; w1/145 (CSV metadata repr) is nearest.

Acceptance: the fixture's query JSON contains no `<`, `_tuplegetter` or
`Booking.` substring and its custom values equal `list custom`'s; other
directive types are unchanged. A regression test parses the envelope for
every directive type. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-12** — Took the note's fallback fix: the engine's JSON walk serializes an enum by its name (`"booking": "FIFO"`) and a `custom` directive's value in the tagged shape `bea list custom` answers (`{"kind": "account" | "text" | "amount" | "bool" | "date" | "number", …}`), dropping `dtype`. On the fixture the query JSON contains no `<`, `_tuplegetter` or `Booking.` substring and its custom values equal `list custom`'s. Directives are not routed through the reader models, so the rest of a directive's shape in query JSON is unchanged. `docs/USAGE.md` notes the two shapes. Shipped in `9c204087` (`cli`).

Regression tests parse the envelope for eleven directive types (commodity, open, pad, balance, custom, transaction, price, note, event, query, close), asserting no interpreter repr in any, compare the custom values with `list custom`, and compare the booking method with `list open`. Four fail with the fix reverted; the nine other directive types pass either way. A test I first wrote for `SELECT entry` returned no rows for these postings-less directives and so proved nothing; it was removed rather than kept as a vacuous pass. `make check-all` passed. Only macOS was exercised.
