# `bea import` has no way to leave out a card export's Pending rows, and the docs never mention them: a pending charge that posts at a different amount is double-booked

**Minor · cli · 30–45m · A1.** Real CLI QA, 2026-10-16, HEAD `be46147e`, checkout `bea 0.3.1`, macOS 26.5.1.
Card and bank CSV exports commonly carry a `Status` column (`Pending`/`Posted`),
and a pending charge often posts days later at a different amount (tips,
holds, FX). bea imports every row. The mapping has no status field, so
`--csv …,status=Status` is refused, and USAGE and IMPORTING never say what
to do. An agent reconciling the month ends exactly the pending amount off.
The customer import skill already handles this case; the CLI does not. No
product fix implemented.

Ledger opening `Liabilities:CreditCard USD`, `Expenses:Dining`,
`Expenses:Uncategorized`.

`sep.csv`:

```csv
Transaction Date,Description,Amount,Status
09/27/2026,BISTRO 9,-50.00,Pending
09/28/2026,BLUE BOTTLE,-4.50,Posted
```

`oct.csv`:

```csv
Transaction Date,Description,Amount,Status
09/27/2026,BISTRO 9,-58.00,Posted
10/02/2026,CAFE,-5.00,Posted
```

```sh
bea --no-input --file /abs/main.bean import sep.csv --csv 'date=Transaction Date,narration=Description,amount=Amount' --account Liabilities:CreditCard --apply
bea --no-input --file /abs/main.bean import oct.csv --apply
bea --file /abs/main.bean balance CreditCard
```

Actual: both imports write every row as `new` with no note about the `Status`
column; the card shows `-117.50 USD`; the true balance is −67.50 USD.
`--csv …,status=Status` is refused as an unknown field.

Expected: one of the following.

- A `status=` mapping with a documented rule. Rows whose status reads
  pending are skipped, or written with `!` and reported. A later posted row
  for the same date and description is then a possible duplicate of the
  pending one.
- At minimum, a note when an unmapped column holds "Pending", plus
  IMPORTING.md guidance to drop pending rows before importing.

Cause: no status field in the mapping allow-list
(`cli/src/cli/csv_mapper.py:24-36`, `_MAPPING_FIELDS`); no doc coverage.

Fix: as above (ask the maintainers which behavior the CLI should own; the
note plus documentation is the smallest step).

Dedupe: searched `pending`, `status column`; only dashboard and mobile notes
match.

Acceptance: the two-month fixture ends at −67.50 USD through the documented
path, and a test pins it.

---

**Resolved 2026-10-17** — Shipped in `a4a4e81e` (`cli`).
- A `status=COLUMN` mapping field (frontend `cli/src/cli/csv_mapper.py`, engine `cli/src/bea_engine/csv_mapper.py`) leaves out rows whose status reads `Pending`, `Authorized` or a hold.
- The preview names them ("Left out 1 pending row(s) (09/27/2026 BISTRO 9 -50.00); import them from the export they post in.") and counts them in JSON `skipped_pending`; the human summary adds ", 1 pending row left out".
- Header inference maps a `Status` column. A mapping without `status=` gets a note naming a column that marks rows pending and suggesting `status=` for it.
- Through the documented path, the note's two-month fixture ends at −67.50 USD.
- Product call, as the note invited: the CLI leaves pending rows out rather than writing them with `!` as the customer skill does. A pending amount that posts differently is not even a possible duplicate, and statement balances are posted-only.
- IMPORTING documents it.
- `tests/test_import_pending_rows.py` pins the two-month flow, the unmapped-column note and inference. All 3 fail without the fix. `make check-all` passed.
