# `PYTHONIOENCODING=utf-16` (or `utf-32`, `cp037`) in the environment makes bea call a healthy managed engine "damaged" and tell the user to delete it

**Minor · cli · 5–10m · A1.** Real CLI QA, 2026-10-17, HEAD `cc6b52ed`, checkout `bea 0.3.1`, macOS 26.5.1. Found beside the w5/532 checks.
No product fix implemented. (Nothing was deleted during QA.)

```sh
PYTHONIOENCODING=utf-16 bea -f /abs/main.bean list transaction
PYTHONIOENCODING=utf-16 bea engine status
```

Actual:
- The first exits 1 with `The managed Beancount engine at
  ~/.local/share/bea/engine/0.3.1 is damaged and cannot load (it is not a
  Python that loads the engine). Remove ~/.local/share/bea/engine/0.3.1 and
  rerun; bea provisions a fresh engine.`, itself printed in UTF-16 (every
  character spaced out).
- `engine status` reports the engine as damaged.
- `cp037` behaves the same (hunter's run).

Control: unset, `latin-1` and `ascii` work. Native tools already get
`PYTHONIOENCODING=utf-8` (`cli/src/cli/engine/launch.py:183`).

Expected: the engine works whatever the parent's `PYTHONIOENCODING`, and bea
never advises deleting an engine that loads.

Cause: `_helper_env` (`cli/src/cli/engine/launch.py:720`) passes the inherited
`PYTHONIOENCODING` to the helper and to the `engine_load_failure` probe. The
probe reads UTF-16 output as text and misses its sentinel.

Fix: set `PYTHONIOENCODING=utf-8` in `_helper_env` as `_native_env` does, and
have the frontend's own error output ignore an unusable inherited encoding.

Dedupe: w5/675 (open) covers `BEA_ENGINE_PYTHON` overrides; nothing covers
`PYTHONIOENCODING`.

Acceptance: both commands work under `PYTHONIOENCODING=utf-16`. A test pins
the helper environment.

**Resolved 2026-10-18** — Shipped in `29612fa62ef92153ac328a2689a1bc94a7a92cd8` (`cli`). `_helper_env` pins `PYTHONIOENCODING=utf-8` as `_native_env` does, so the helper and the engine probe speak UTF-8 whatever the parent exports. The frontend's error rendering (`output.error` and `failure`) reconfigures stderr to UTF-8 when an explicitly inherited `PYTHONIOENCODING` is not UTF-8 — locale-derived encodings untouched — and `engine status` prints UTF-8 (w5/405 precedent), so both commands work observably. Reproduced the note's recipe first (spaced-out "damaged" error, status reporting damaged), then verified `list transaction` exits 0, status reports "Provisioned: yes" in clean UTF-8, a real error under utf-16 prints a clean `Error: …`, and cp037 works. 6 new tests in `test_engine_inherited_encoding.py` (helper env pins utf-8 for utf-16/utf-32/cp037, probe loads, error bytes, status bytes); all 6 fail pre-fix. Full suite 9063 passed / 2 skipped; `spec-check` still fails identically on clean HEAD (pre-existing description-only backend drift, recorded under w5/716). No doc change: no documented promise covered inherited encodings.
