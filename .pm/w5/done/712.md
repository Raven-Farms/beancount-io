# A file whose last byte is a lone CR does not converge under `format -i`: the first run leaves `\r\n`, `--check` then fails, and a second `-i` deletes the CR

**Trivial · cli · 5–10m · A1.** Real CLI QA, 2026-10-17, HEAD `a7c2762d`, checkout `bea 0.3.1`, macOS 26.5.1.
USAGE:562-569 says `format -i` is the convergence path, that `--check` fails
on a CRLF file only "until `-i` has run", and that a lone CR inside a line is
text the formatter keeps. No product fix implemented.

`a.bean` is the bytes `2026-01-01 open Assets:Cash USD\n; c\r`, with no final
LF.

```sh
bea format -i /abs/a.bean
bea format --check /abs/a.bean
bea format -i /abs/a.bean
```

Actual:
1. Exit 0, `1/1 file(s) formatted`, and the file now ends `; c\r\n`.
2. Exit 1, `would format`.
3. Rewrites the end to `; c\n`, so the CR is gone.

An `add` on the same tail writes `; c\r\n2026-01-05 …` with no blank line,
treating the CR as part of a line ending.

Control: `; c\rd\n` in the middle of the file is kept, and formatting is
idempotent.

Expected: one `-i` reaches a fixed point, with the CR either kept as comment
text plus a new `\n`, or removed on the first run.

Cause: `cli/src/bea_engine/ledger/formatting.py:248` appends `"\n"` to a
protected line, which turns a trailing `\r` into `\r\n`. The append path
(`write.py`, around `:2445-2458`) joins the CR to the new line ending in the
same way.

Fix: treat a trailing lone `\r` as content followed by a missing newline on
both paths.

Dedupe: w5/355, 380, 169, 108 and 244 (done) cover other CR cases; none
covers end of file.

Acceptance: `-i` then `--check` exits 0 on the fixture.
