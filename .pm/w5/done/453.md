# At the `bea ask` "Confirm AI write" panel, typing `n` or `2` and pressing Enter approves the write: only arrows, `j`/`k`, Enter and Ctrl-C are bound, and the highlighted default is "Yes"

**Minor · cli · 15m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1. **Simulation:** the model's proposed write came from a localhost mock.

The approval panel lists numbered options ("1. Yes 2. No 3. Yes to all
4. Deny all"), which invites typing a number or `n`. Those keys are not
bound and are silently ignored. Enter then returns the highlighted
option, which starts on "Yes". A user who types `n` and presses Enter to
reject an AI-proposed directive approves it instead. The panel is the
only gate between model output and the ledger. No product fix
implemented.

The hunter scripted a mock model that returns one `write_directive` with
`2026-01-01 open Assets:Pwned`, then the reply "done". It ran `bea -f
repo/main.bean ask` under a PTY with isolated BEA_CONFIG_DIR/XDG_CACHE_HOME,
a fake `BEA_TOKEN` and the API URL on 127.0.0.1, then typed a question
and, at the panel:

| Keys at the panel | Ledger |
|---|---|
| `n`, then Enter (two runs) | `open Assets:Pwned` appended |
| `2`, then Enter | appended |
| Down, then Enter (control) | unchanged |
| Ctrl-C (control) | unchanged |

I confirmed the bindings and the default in the code. My own PTY attempt
did not reach the panel, a harness problem.

Expected: no key a user might type to mean "no" should approve. Bind `1`
to `4` and `y`/`n`/`a`/`d` to their options, and either default to "No"
or require an explicit choice before Enter is accepted. Document the keys
in USAGE's ask section.

Cause: `_ask_write_permission` (`cli/src/cli/ask/repl.py:85-155`) sets
`selected = [0]` (Yes). Its `KeyBindings` handle only `up`/`k`,
`down`/`j`, `enter` (returns the highlighted option) and `c-c`.

Fix: add the number and letter bindings, and make the default No, or make
Enter a no-op until the selection moves. No dependency change.

Blast radius: every `bea ask` session write approval. An unintended
approval writes model-proposed text into the ledger.

Dedupe: 374 (tab display in the panel), w3/451 (escaping) and w3/452
(file name) cover the panel's content. None covers its key handling or
default.

Acceptance: in a PTY test, `n` + Enter and `2` + Enter decline and leave
the ledger unchanged. `y` and `1` approve. Enter alone does not approve
by default.

---

**Resolved 2026-10-15** — `_ask_write_permission` (`cli/src/cli/ask/repl.py`) starts the selection on **No**, so Enter alone declines. Each option's number (`1`–`4`) and letter (`y`/`n`/`a`/`d`) moves the selection to it before Enter confirms. `n`+Enter and `2`+Enter decline, `y`/`1` approve, and arrows, `j`/`k` and Ctrl-C behave as before. The choice still needs Enter, so no stray Enter falls through to the REPL. USAGE's ask section documents the keys. `cli/tests/test_ask_write_panel_keys.py` drives the real panel through prompt_toolkit's pipe input for Enter alone, every number and letter, a changed mind (`y2`), and Up; 9 of 11 fail on the old panel. The PTY suites that approved with a bare Enter (`test_ask_write_then_fail.py`, `test_ask_consent_surface.py`) now type `y` first and still pass end to end. One gate run hit an unrelated load flake in `test_write_keeps_file_metadata.py`: `ls -le` printed an ACL principal as a UUID. It passed alone and on the rerun. Only macOS was exercised. `make check-all` passed (6048 tests). Shipped in `4298450a` (`cli`).
