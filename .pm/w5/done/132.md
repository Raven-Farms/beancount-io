# An import rule written `match = "\bshell\b"` never matches and says nothing

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
In a double-quoted TOML string `\b` is a backspace, so the natural
word-boundary rule compiles to a pattern containing two control characters
and can never match. The import exits 0 and files every row under
`Expenses:Uncategorized`. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Fuel
2026-01-01 open Expenses:Uncategorized
2026-01-01 open Equity:Opening
2026-01-02 * "Opening balance"
  Assets:Checking  1000.00 USD
  Equity:Opening
```

`/absolute/books/s.csv`:

```csv
Date,Description,Amount
2026-08-02,SHELL OIL 123,-40.00
2026-08-03,SEASHELL CAFE,-9.99
```

`/absolute/books/r.toml`:

```toml
[[rule]]
match = "\bshell\b"
account = "Expenses:Fuel"
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea --file main.bean import s.csv --account Assets:Checking --rules r.toml --apply
```

Actual: exit 0, every row `RULE unmatched`; `2026-08-02 ! "SHELL OIL 123"`
is written against `Expenses:Uncategorized`. No warning.

Control: with the rule in single quotes, `match = '\bshell\b'`, row 1 shows
rule `\bshell\b` and posts to `Expenses:Fuel`; `SEASHELL CAFE` stays
unmatched. A worker observed that other invalid escapes such as `"oil \d+"`
fail loudly with exit 2 (`Unescaped '\' in a string`); only the escapes TOML
accepts (`\b`, `\f`, `\t`, `\n`, `\r`) slip through.

Expected: `\b` is the obvious fix for a plain `shell` rule that also catches
`SEASHELL CAFE`. `docs/IMPORTING.md` and `docs/examples/rules.toml` show only
double-quoted `match` strings and never mention literal strings. A `match`
containing a control character cannot match bank text, since imported text
has line breaks flattened; the rule should be refused with exit 2 naming the
rule and suggesting single quotes or `\\b`.

Cause: `cli/src/bea_engine/csv_mapper.py:282` (`CsvRule.compile`) and its
frontend twin in `cli/src/cli/csv_mapper.py` compile the parsed string as
given, with no check for control characters.

Fix: refuse a `match` containing a C0 control character; add the same
single-quote hint to the existing `Cannot parse rules file … Unescaped '\'`
error and one line in `IMPORTING.md`. No dependency or API change.

Blast radius: every `--rules` file and remembered rules path.

Dedupe: board search for backspace, word boundary, literal string and
single-quoted, plus the notes on `--rules`, finds w1/062 and w3/342 (empty
match catch-all) and w1/063 (NFC); none covers TOML escapes.

Acceptance: the double-quoted rule exits 2 with a message naming rule 1 and
the single-quote remedy, and writes nothing; the single-quoted control is
unchanged. A real-command regression test covers `\b` and `\t`. Only macOS
and the checkout were exercised.

---

**Resolved 2026-10-13** — Both copies of `CsvRule.compile` (frontend `cli/src/cli/csv_mapper.py` and engine `cli/src/bea_engine/csv_mapper.py`) now refuse a rule whose `match` contains a C0 control character or DEL, with exit 2, naming the rule number and the single-quote or doubled-backslash remedy; nothing is written. The existing "Cannot parse rules file … Unescaped" error carries the same hint, and `docs/IMPORTING.md` gained a sentence on literal strings. The regression test runs the real `bea import --rules … --apply` for `\b` and `\t`, the single-quoted and doubled-backslash controls, and the engine copy directly; five cases fail with the fix reverted. A remembered `--rules` path holding such a rule still follows the existing warn-and-import-without-rules path. Only macOS was exercised. `make check-all` passed. Shipped in `4e58c427` (`cli`).
