# A read that overlaps a `bea add` on a slow-loading ledger freezes a stale load cache: the write is invisible to later reads, and a later import double-books it

**Major · cli · 45–60m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
On a ledger large enough to use the load cache (load time over one
second), a read that starts while an `add` is about to commit can store a
cache holding the pre-write entries under the post-write fingerprint. From
then on every read answers from that cache: the exit-0 transaction is in
the file but missing from `balance`, `list` and `query`, and `import
--apply` of the same transaction finds no duplicate and writes it again.
The state lasts until a ledger file next changes. No product fix
implemented.

Generate disposable `/absolute/books/main.bean` (50,000 transactions, about
3 MB):

```sh
python3 -c "
f=open('main.bean','w')
f.write('option \"operating_currency\" \"USD\"\n2020-01-01 open Assets:Cash USD\n2020-01-01 open Expenses:Food USD\n\n')
for i in range(50000): f.write(f'2021-01-{1+i%28:02d} * \"t{i}\"\n  Expenses:Food  1.00 USD\n  Assets:Cash\n\n')"
```

`/absolute/books/x.csv`:

```csv
Date,Description,Amount
2022-02-01,Lunch,-100.00
```

Use one isolated BEA_CONFIG_DIR/XDG_CACHE_HOME shared by all commands,
BEA_NO_UPDATE_NOTIFIER=1, no inherited BEA_FILE/BEA_TOKEN, closed stdin, no
TTY, cwd `/absolute/books`, no `.main.bean.picklecache` at the start.

```sh
bea -f main.bean add transaction Lunch --date 2022-02-01 -p "Expenses:Food 100.00 USD" -p Assets:Cash &
sleep 3.2
bea --json -f main.bean balance &
wait
bea --json -f main.bean query "SELECT sum(position) WHERE account='Assets:Cash'"
bea --json -f main.bean list transaction --search Lunch
bea --json -f main.bean import x.csv --csv date=Date,amount=Amount,narration=Description --account Assets:Cash --default-account Expenses:Food --apply
```

Actual: with the reader started 2.8, 3.2 or 3.6 s after the add (3 of 4
offsets tried; 2.4 s was unaffected), both racing commands exit 0 and the
Lunch transaction is in `main.bean`. Afterwards the query returns
`-50000.00 USD`, the list returns no Lunch item, and the import exits 0 and
writes a second Lunch transaction. The file now holds two.

A worker measured 12 stale outcomes in 40 trials with a random 0–5 s
offset, saw the same result when the second process was an `add price`
that itself exited 4, and confirmed that deleting `.main.bean.picklecache`
makes the transaction reappear at once.

Control: the same commands one after another give `-50100.00 USD`, one
Lunch item, and the import exits 4: `Import needs review; nothing was
written. Choose --duplicates skip/include for possible duplicates.` A
worker saw a ledger that loads in under one second unaffected, since no
cache is written.

Expected: `docs/USAGE.md`: "Exit 0 is a promise: the documented effect
happened"; `docs/IMPORTING.md` calls the ledger itself the dedup database.
The file holds one more 100.00 USD posting, so `Assets:Cash` is −50100.00,
and a read started after the commit must see it.

Cause: Beancount's loader parses the files first and computes the cache
fingerprint (`input_hash`, from each file's size and mtime) only afterwards,
then stores the result when the load took at least a second. A commit that
lands between the read and the fingerprint yields old entries under the new
fingerprint, which the loader then trusts indefinitely.
`cli/src/bea_engine/managed_load.py` (`_load_fresh`) goes through this
unguarded, although it already holds each file's stat from before the load.

Fix: in `_load_fresh`, compare the pre-load stats with the files' state
after the load; on a mismatch discard the cache (and reload or return the
result uncached), so a load that overlapped a change never leaves a cache
behind. No dependency or API change.

Blast radius: every read that goes through the managed load: `balance`,
`list`, `query`, reports, `--json check`, import duplicate detection, and
the pre-write reads of `add price` and `add balance`; any ledger whose load
takes a second or more (fewer transactions with plugins or many lots). A
hand edit landing during a read has the same window. The native `bea check`
path uses the same upstream cache (not measured).

Dedupe: board search for `picklecache`, "load cache", `input_hash` and
stale cache finds w1/done/083 (cache ignored a newly glob-matched file),
w5/111 (`check --auto` poisons the cache), w5/116 (document existence
frozen), w5/175 (cache file mode) and w5/181–183 (write locks); none covers
a load that overlaps a commit.

Acceptance: for reader offsets from 0 to 5 s in 0.2 s steps, twice each,
the later query returns −50100.00, the list returns one Lunch item, and the
import exits 4 as a possible duplicate. Only macOS and the checkout were
exercised.

---

**Resolved 2026-10-13** — `_load_fresh` in `cli/src/bea_engine/managed_load.py` now compares the stats the ledger snapshot captured before the load with the files after it, and removes Beancount's load cache when any file changed, so a read that overlapped a `bea add` or a hand edit no longer leaves old entries cached under the new fingerprint; the overlapped read itself is returned as loaded, uncached. `cli/tests/test_load_cache_overlapping_write.py` lands a real `bea add`, and in-place edits to the root and to an included file, between the loader's parse and its fingerprint, then checks that the later `query` total, `list` and `import --apply` (exit 4, one transaction in the file) see the write, with sequential and cache-hit controls; four of its six cases fail with the fix reverted. The note's timed acceptance sweep (offsets 0 to 5 s in 0.2 s steps, twice each) was not run in full: on the 50,000-transaction fixture one real two-process race reproduced the stale state before the fix and thirteen races around the commit were clean after it. A reader that opens the cache in the instant between Beancount writing it and this check removing it can still get one stale answer, but the cache no longer persists; the native `bea check` path the note lists as unmeasured was not measured here either. Only macOS was exercised. `make check-all` passed. Shipped in `b7be159f` (`cli`).
