# The `bea ask` write-approval panel shows tab indentation as literal `\x09`, while the engine accepts the tabs and writes the directive realigned with spaces, so the panel is not "what will be written"

**Trivial · cli · 15m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, pydantic-ai 2.19.0. **Simulation:** the model's proposed directive came from a localhost mock.

The confirmation panel escapes every control character with
`inert_text`, including tab. The engine treats tab as allowed whitespace
and realigns the posting with spaces when it appends. A model that
indents with tabs, which is common in generated text, therefore produces
a panel of `\x09Expenses:Food\x094 USD`. That looks like garbage and
invites the user to decline a valid write. What reaches the file
differs from what was shown. No product fix implemented.

Setup: the scripted mock returns one `write_directive` call with
`2026-02-01 * "Cafe" "coffee"\n\tExpenses:Food\t4 USD\n\tAssets:Cash`,
then `Added it.`. Use the environment from [373](./373.md) and a ledger
that opens `Expenses:Food` and `Assets:Cash`. Run `bea -f
/absolute/books/main.bean ask` under a PTY: type a question, accept
"Yes" at the panel, then press Ctrl-D.

Actual:

- The panel shows `\x09Expenses:Food\x094 USD` and `\x09Assets:Cash`.
- The file receives `  Expenses:Food    4 USD` and `  Assets:Cash`, with
  spaces and alignment.
- Exit 0.
- `Assets:Cash\t\t-4.000 USD` shows `\x09\x09` and is written aligned.

Reproduced twice by the hunter (PTY transcripts). I confirmed the
rendering path.

Control: space-indented text shows unchanged, apart from realignment.

Expected: `docs/USAGE.md` says the confirmation "shows the directive with
any control character escaped to a visible `\xNN`, so what is on screen
is what will be written". The engine's `refuse_control_characters`
(`cli/src/bea_engine/ledger/text.py:93-115`) says "Tabs, LF and CR are
the exceptions". A tab is not a refused control character, so it should
not appear as an escape. Ideally, the panel shows exactly the text the
engine will append.

Cause: the confirm function in `make_confirm_fn`
(`cli/src/cli/ask/repl.py:174-182`) renders `inert_text(directive)`,
which escapes `\t` (`cli/src/cli/utils.py:41-55`). The engine's
`append --dry-run` returns only `count`, `target`, `warnings` and
`token`, not the text it will write.

Fix: either show the text the engine will append, by having the dry run
return it (this also covers realignment), or render tabs as spaces in
the panel while escaping the other control characters. No dependency
change.

Blast radius: the `bea ask` REPL write approval whenever the model
indents with tabs.

Dedupe: searched `.pm/**`, including `done/`, for `\x09` and tab together
with ask, panel or confirm. Related notes:

- w3/451: introduced the escaping and the refusal.
- w3/452: the panel's file name.
- w5/245: `\x09` in query output, which is intended there.

None covers tabs in the approval panel.

Acceptance: with the tab-indented directive, the panel shows readable
indentation that matches what is then appended. A directive containing a
real control character (such as `\x07`) still shows the escape and is
refused. A test pins both.

**Resolved (the "show the text the engine will append" option).** The engine's `append --dry-run` (`ledger/appending.py`) now also returns `text`: the exact lines the commit will append. It comes from the new `ledger_write.appended_lines`, which keeps only what `appended_content` adds, aligned as `bea format` leaves it and LF-terminated, and it accounts for a new include's seed. The `write_directive` tool shows that text on the approval panel. It falls back to the proposal only if an engine sends no `text`. So the tab-indented proposal now reads `  Expenses:Food  4 USD`, which is what lands. A string still containing a control character keeps its visible `\xNN`. `src/bea_engine/README.md` and the `docs/USAGE.md` consent paragraph describe the new field.

`tests/test_ask_tab_indented_approval.py` covers three cases:

- the dry-run `text` equals the bytes the commit then appends, with no tab;
- the panel callback gets exactly what lands, and the rendered panel has no `\x09`;
- a `\x07` in the narration is still refused before any panel, with the ledger unchanged.

With the fix stashed, the two text cases fail. `test_ask_consent_surface.py`'s destination test now compares the shown directive token-wise, since it is the aligned rendering.
