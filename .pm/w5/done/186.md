# A transaction whose only posting has no amount is written with exit 0, and the posting then vanishes

**Minor · cli · 20m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
`bea` refuses a zero-net transaction with an inferred balancing posting,
because Beancount drops that leg. A transaction with a single posting
and no amount slips past the guard: it is written with exit 0, and `list
transaction` then reports it with no postings at all — a row `add
transactions` itself refuses to read back. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food
```

`/absolute/books/rows.json`:

```json
[{"date":"2026-02-02","narration":"only","postings":[{"account":"Expenses:Food"}]}]
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea --json -f main.bean add transactions --from rows.json
bea --json -f main.bean list transaction
```

Actual: the first exits 0 with `"written": 1`; the ledger gains

```beancount
2026-02-02 * "only"
  Expenses:Food
```

The second reports the transaction with `"postings": []`.

Control: a row with `{"account":"Expenses:Food","amount":"0 USD"}` and
`{"account":"Assets:Cash"}` exits 1: `Row 1: Refusing a zero-net
transaction with an inferred balancing posting; Beancount drops that leg
from list/query.` A worker saw the single-entry `add transaction only
--date 2026-02-02 -p Expenses:Food` behave like the bulk form.

Expected: the same refusal — a lone posting with no amount is
necessarily an inferred zero.

Cause: `_inferred_leg_is_zero` in
`cli/src/bea_engine/ledger/adding.py:767` returns `bool(weights) and
all(...)`; with no posting that has an amount, `weights` is empty and the
guard stands aside.

Fix: treat "one amount-less posting and none with an amount" as an
inferred zero and refuse it. No dependency or API change.

Blast radius: `add transaction` and `add transactions`.

Dedupe: w3/done/339, w4/done/165 and w4/done/166 built the guard for two
or more legs; none covers the single-posting case.

Acceptance: both the bulk and single forms exit 1 with the zero-net
refusal and write nothing; the two-posting control is unchanged. Only
macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — The zero-net guard in `cli/src/bea_engine/ledger/adding.py` (`_inferred_leg_is_zero`) stood aside when no posting carried an amount, so a transaction whose only posting had no amount was written with exit 0 and then read back with no postings. An empty set of weights now counts as an inferred zero, so `bea add transaction` and `bea add transactions` both give the existing zero-net refusal and write nothing. Two new cases in `cli/tests/test_add_refuses_zero_net_inferred.py` cover the single and bulk forms beside the two-posting control, a lone posting that does carry an amount, and an ordinary inferred leg that still writes; both cases fail with the fix reverted. The bulk form exits 1 as the note asks, while the single form exits 2, the usage-error status its existing zero-net refusal already uses. Only macOS was exercised. `make check-all` passed. Shipped in `5795720a` (`cli`).
