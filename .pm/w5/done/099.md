# BQL `filename` names vanished staging files on every ledger with a managed price include

**Major (silent wrong result, exit 0) · cli · 30–45m · A1.** Real CLI QA,
2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS. On a ledger that
carries a managed price include, the posting-level `filename` column in
`bea query` holds the path of a temporary staging copy (`.bea-<random>.tmp`)
instead of the ledger file. The name changes on every run and the file is gone
when the command returns, so a query that filters or groups by source file
silently matches nothing. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
include "https://beancount.io/prices/BTC-USD"
include "sub/jan.bean"

2026-01-02 * "Lunch"
  Expenses:Food  12.00 USD
  Assets:Cash
```

and `/absolute/books/sub/jan.bean`:

```beancount
2026-01-03 * "Coffee"
  Expenses:Food  4.50 USD
  Assets:Cash
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.
`--offline` with an empty cache keeps the run off the network; nothing was
fetched and no credential was used:

```sh
bea --offline -f /absolute/books/main.bean query --allow-errors "SELECT filename, lineno, account WHERE account ~ 'Food'"
bea --offline -f /absolute/books/main.bean query --allow-errors "SELECT sum(position) AS total WHERE filename ~ 'jan' AND account ~ 'Food'"
```

Actual: the first query exits 0 with

```text
/absolute/books/.bea-080655cf8f99b764.tmp       8  Expenses:Food
/absolute/books/sub/.bea-bb5641b7c8df7859.tmp   2  Expenses:Food
```

A second run prints different random names. `ls -a` afterwards shows neither
file. The second query exits 0 with `(no rows)`. Repeated twice from a fresh
fixture. A worker observed the same with a simulated loopback feed serving
prices (no `--offline`, no `--allow-errors`, `check` exit 0) and in `-f csv`
and `--json` output; I did not re-run those variants.

Control: the same two files without the managed include line return
`/absolute/books/main.bean 7` and `/absolute/books/sub/jan.bean 2`, and the
sum query prints `4.50 USD`. Independent arithmetic: `sub/jan.bean` holds one
4.50 USD posting to `Expenses:Food`.

Expected: `docs/USAGE.md` Managed price includes says the line works "in
every command" and that `query` sees the same ledger as every other command;
the engine's own contract at `cli/src/bea_engine/managed_load.py:15-17` is
that "entry and error filenames map back to the originals before anything is
returned". Beanquery documents the column as "The ledger where the posting is
defined." So `filename` should be the real ledger path, and the sum should be
`4.50 USD`. Splitting spend by yearly or per-account include file is a common
query shape; here it returns an empty answer with exit 0.

Cause: `cli/src/bea_engine/managed_load.py:584-591` (`_remap_entry`) maps
only `entry.meta["filename"]` back to the original. Each posting of a
transaction keeps its own `meta["filename"]` pointing at the staged twin, and
Beanquery's postings table reads the column from the posting's metadata.
Entry-level consumers (`list`, check errors, `--on-disk`) read the entry meta
and are correct.

Fix: in `_remap_entry`, for a transaction, also rebuild each posting whose
`meta` carries a staged `filename`, mapping it through the same table. Keep
entries untouched when nothing maps, as today. No dependency or API change.

Blast radius: every `bea query` that selects, filters or groups on
`filename`, `meta('filename')` or `any_meta('filename')` from the default
postings table, in every output format, online or offline, on any ledger with
a managed include. The `#entries`-style tables read entry meta and are
unaffected.

Dedupe: board search for staged paths, `.bea-`, `SELECT filename` and posting
metadata finds w1/135 (staged paths inside error text, done), w3/390 (cache
sidecars) and w5/092 (line shift under a multi-file glob); none covers posting
metadata. `git log -S_remap_entry -- cli` shows only the introducing commit.

Acceptance: on the fixture both queries name `main.bean` and `sub/jan.bean`
and the sum is `4.50 USD`, with no `.bea-` substring in text, CSV or JSON
output; the include-free control is unchanged. A real-command regression test
loads a ledger with a managed include from a seeded offline cache and asserts
posting-level `filename` values for the root and an included child. Only
macOS and the checkout were exercised.

---

**Resolved 2026-10-12** — The managed loader's filename remap now covers each posting's own metadata as well as the entry's. On a ledger with a managed price include, the posting-level `filename` names `main.bean` and `sub/jan.bean`, the filter `filename ~ 'jan'` sums to `4.50 USD`, `meta('filename')` matches too, and no `.bea-` name appears in text, CSV or JSON output. Shipped in `43710153` (`cli`).

Real-command regression tests against a loopback feed assert the posting-level filenames and line numbers for the root and an included child (with an include-free control), the source-file filter and its `meta('filename')` form, and text and CSV output free of staging names with no staging file left behind. Four fail with the fix reverted; the include-free control passes either way. `make check-all` passed. The feed was simulated on loopback rather than run offline against an empty cache, and only macOS was exercised.
