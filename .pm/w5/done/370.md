# In every unattended run (`--json`, `--no-input`, no TTY, `CI`), `cloud ledger clone` replaces the user's `core.sshCommand`/`GIT_SSH` with plain `ssh -o BatchMode=yes`, so clones that work interactively fail for scripts and agents

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1. **Simulation:** the API and the git server came from a localhost mock and local bare repositories. The defect is in how the CLI sets up the git child.

For unattended runs, `_git_env` sets `GIT_SSH_COMMAND` to `ssh -o
BatchMode=yes`, or the existing `GIT_SSH_COMMAND` with BatchMode appended,
so that prompts never hang. In git, `GIT_SSH_COMMAND` takes precedence
over `core.sshCommand` and `GIT_SSH`. The user's own SSH setup, such as a
dedicated key (`ssh -i ~/.ssh/beancount_key`) or a wrapper for an agent
like 1Password, is therefore dropped in exactly the modes agents use. No
product fix implemented.

Setup:

- The mock API returns a ledger whose `sshUrl` is `git@127.0.0.1:book.git`.
- The git config (with `GIT_CONFIG_GLOBAL` pointing at a run-dir file
  and `GIT_CONFIG_NOSYSTEM=1`) sets `core.sshCommand = <run>/fakessh`, a
  wrapper that runs `git-upload-pack` on a local bare repository.
- Isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, an
  obviously fake `BEA_TOKEN`, and API and dashboard URLs on 127.0.0.1.

```sh
bea cloud ledger clone qa/book                       # under a PTY
bea --json cloud ledger clone qa/book                # under a PTY
bea --no-input cloud ledger clone qa/book </dev/null
```

Actual:

- The interactive run exits 0 and clones `main.bean`, using fakessh.
- The `--json`, `--no-input` and closed-stdin runs exit 1 with `Clone
  failed … ssh: connect to host 127.0.0.1 port 22: Connection refused`.
  fakessh is never invoked.
- `GIT_SSH=<fakessh>` instead of `core.sshCommand` fails the same way.

Reproduced by the hunter three times (core.sshCommand) and once
(GIT_SSH). I confirmed the code path.

Control: a plain `git clone git@127.0.0.1:book.git` in the same
environment honours both settings. `GIT_SSH_COMMAND=<fakessh> bea --json
cloud ledger clone` works, because bea appends to it.

Expected: `docs/USAGE.md` says cloning "uses `git clone` over SSH, so it
needs Git and working SSH access". BatchMode exists to stop prompts
hanging (the `_git_env` comment). It should not replace the user's SSH
configuration. A setup that clones interactively should clone the same
way in JSON or `--no-input` mode.

Cause: `_git_env` (`cli/src/cli/commands/cloud/ledger/manager.py:75-84`)
does `existing = env.get("GIT_SSH_COMMAND", "ssh")` and always sets
`GIT_SSH_COMMAND`.

Fix:

- When `GIT_SSH_COMMAND` is unset, read `git config --get
  core.sshCommand` and `GIT_SSH`, and append BatchMode to whichever is in
  effect, or pass it through `-c core.sshCommand=…`.
- Default to `ssh -o BatchMode=yes` only when neither is set.
- Keep `GIT_TERMINAL_PROMPT=0`, and also give the git child
  `stdin=DEVNULL` when unattended.
- No dependency change.

Blast radius: `cloud ledger clone` and `cloud ledger create --clone` in
`--json`, `--no-input`, CI and non-TTY runs, for every user whose SSH
access depends on `core.sshCommand` or `GIT_SSH`.

Dedupe: searched `.pm/**`, including `done/`, for BatchMode, sshCommand,
`GIT_SSH` and `_git_env`. There are no hits. w1/089 covers URL and option
hardening.

Acceptance: with `core.sshCommand` (or `GIT_SSH`) set to a wrapper, the
`--json`, `--no-input` and closed-stdin clones use it, with BatchMode
still in effect, and succeed. A clone with no SSH configuration still
cannot hang on a prompt. A test pins the env that `_git_env` builds for
each case.

**Resolved.** `_git_env` (`commands/cloud/ledger/manager.py`) now resolves the SSH command `git clone` would run, in git's precedence order: `GIT_SSH_COMMAND`, then `core.sshCommand`, then the `GIT_SSH` program (shell-quoted), then `ssh`. It appends `-o BatchMode=yes` to that command. `core.sshCommand` is read with `git --git-dir=<devnull> config --get`, which covers global, system and `-c`/`GIT_CONFIG_*` but not the repository bea runs in. That matches clone itself, verified with `GIT_TRACE`. PuTTY-family programs (`plink`, `putty`, `tortoiseplink`) are left as configured, since `-o` is OpenSSH syntax. `GIT_TERMINAL_PROMPT=0` stays. An unattended clone also gets `stdin=DEVNULL`, through a new `stdin_closed` flag on `launch.run_captured`. `docs/USAGE.md` describes this.

`tests/test_cloud_clone_ssh_command.py` pins the environment `_git_env` builds for each case:

- nothing configured;
- an attended clone;
- `GIT_SSH_COMMAND`;
- `core.sshCommand` (beating `GIT_SSH`);
- `GIT_SSH` with a space in the path;
- a local repo's config, which is ignored;
- plink;
- git missing from PATH.

It also runs a real unattended `clone_ledger` through a fake-ssh wrapper set by `core.sshCommand` and by `GIT_SSH`. The clone succeeds, and every wrapper call carries `-o BatchMode=yes`. With the fix stashed, five tests fail, including both wrapper clones.
