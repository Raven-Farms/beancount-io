# Honor a valid remembered custom date format on an unchanged export

**Minor · cli · 30–45m · A1/A2.** Real CLI QA, 2026-10-21, checkout
`bea 0.3.1`, HEAD `7b9d14760`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
A successful import with an explicit custom date format cannot be repeated
without resupplying the same flag. The unchanged file is falsely called a
format mismatch, and following its suggested replacement can book those
same source rows again on different dates. No product fix implemented.

Create `/abs/books/main.bean`:

```beancount
option "operating_currency" "USD"
2020-01-01 open Assets:Cash USD
2020-01-01 open Expenses:Food USD
```

Create `/abs/books/bank.csv`, whose bank convention is `YYMMDD`:

```csv
Date,Description,Amount
240115,Coffee 0,-1.00
240116,Coffee 1,-1.00
240117,Coffee 2,-1.00
```

From `/abs/books`, closed stdin/no TTY, isolated absolute `BEA_CONFIG_DIR`
and `XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, with inherited `BEA_FILE`
and `BEA_TOKEN` removed:

```sh
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --account Assets:Cash --default-account Expenses:Food --date-format %y%m%d --apply
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --apply
```

First: exit 0, writes three rows on **2024-01-15, 16, 17** and remembers
`%y%m%d`. Both subsequent commands exit **2**, stdout empty, with stderr:
`Remembered --date-format %y%m%d does not match bank.csv, whose dates look
like %Y%m%d. Pass --date-format %Y%m%d (or --csv) for this file.` Its
details simultaneously say it is using the remembered `%y%m%d` settings.
The CSV is unchanged, the chosen format still parses every date correctly,
and each refusal leaves the ledger bytes unchanged. Human repeat fails
identically. Reproduced twice from pristine fixtures.

Resupplying only `--date-format %y%m%d` succeeds with three duplicates,
zero written and unchanged ledger bytes. The documented remembered-mapping
workflow should do that without requiring the flag again.

On the same owned fixtures, following the error's specific advice instead:

```sh
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --date-format %Y%m%d --apply
```

Actual: exit 0, writes **three more** payments on **2401-01-05, 06, 07**.
`%Y%m%d` greedily reads four year digits and unpadded month/day digits from
the six-digit cell. Fresh BQL has six Cash postings totaling **−6.00 USD**,
although the unchanged source export contains three −1.00 payments; check
passes. This additional write was tested only in disposable synthetic data.
The default false refusal itself does not change the ledger.

A second supported custom format reproduces the same root twice:
`%Y-%d-%m` on `2024-05-03`, `2024-06-03`, `2024-07-03` correctly writes
**March 5, 6, 7** initially. Flag-free repeat falsely recommends
`%Y-%m-%d`; following it appends the same three payments as **May 3, June 3,
July 3**, also producing six postings/−6.00 USD with check passing. Thus
this is not a request to add automatic `YYMMDD` support.

Controls, each twice (12 fixture journeys total):

- Remembered eight-digit `%Y%m%d` and ISO `%Y-%m-%d` formats repeat at exit
  0 with three duplicates and no writes.
- Remembered `%d/%m/%Y` with dates that also parse month-first remains
  honored; this is the existing recognized-ambiguity behavior.
- An actually changed export from ISO to `15/02/2024` etc. is still refused
  at exit 2 when the old ISO choice cannot parse it. Explicitly choosing
  `%d/%m/%Y` then writes the three intended February rows and passes check.
- Resupplying each affected format works and skips every already-booked row.

Cause: `cli/src/cli/commands/import_.py:1330–1348` checks a recalled choice
by re-inferring from the frontend's finite built-in format list. If one
alternative fits and differs, it refuses without testing whether the
recalled custom format also fits. `cli/src/cli/csv_mapper.py:403–416`
includes `%Y%m%d` but neither `%y%m%d` nor `%Y-%d-%m`; `_parses`
(:929–934) simply calls `datetime.strptime`, including its variable-width
compact parsing. The helper's `ambiguous` result therefore cannot express
the valid custom alternative the user already chose. The engine accepts
that original format when it is sent explicitly, explaining the control.
The guard came from `77eb123fb` (w1/m24/t007).

Fix: include the recalled choice when deciding whether a format mismatch
is actually proven. Honor it when it still parses all eligible date rows;
retain the existing refusal when it does not fit the new export. Respect
blank/pending/repeated-header rules, retain the saved choice, and avoid
advising a guessed replacement that reinterprets the unchanged dates.
Do not remove date re-validation or redesign import memory. No dependency
or backend/API change is needed.

Dedupe: whole-board remembered/custom-date-format searches, source history
and current milestone review found no open coverage. Completed w3/308 and
w1/m24/t007 require detecting genuinely changed conventions; that control
still works here. Completed [267](./done/267.md) preserves a format during
explicit mapping refresh, and [073](./done/073.md) saves an explicit
override. Neither repairs this false veto during ordinary recall.

Acceptance: both unchanged custom-format exports preview/re-import at exit
0 using the remembered dates and report three duplicates/zero writes;
source and ledger bytes stay unchanged. Keep the changed-format and known
ambiguity controls intact, with no misleading century/month replacement
hint. Pin real CLI coverage. Evidence is under ignored
`.tmp/qa-2026-10-21-cli-loop-pass9-96e3506d/`:
`repro_remembered_custom_dates.py`, `remembered-custom-date-results.json`
and `captures/remembered-dates-*.json`.

---

**Resolved 2026-10-22** — the recall check for a remembered `--date-format` now lets the remembered format compete with the built-in list (`also=` on `infer_date_format`/`inspect_date_column`): a custom format that still reads every date makes the column ambiguous, which the existing guard never refuses on, so an unchanged `%y%m%d` or `%Y-%d-%m` export repeats with the saved format, three duplicates and no writes and no replacement advice; a genuinely changed export (the remembered format no longer parses it) is still refused. `cli/tests/test_import_remembered_custom_date_format.py` fails for both custom formats without the fix; shipped in the commit that moves this note (`cli`). The remembered `%d/%m/%Y` ambiguity case relies on the existing guard and was not rerun separately.
