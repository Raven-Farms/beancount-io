# A successful `add` on a ledger with decomposed (NFD) account names makes stock `bean-check` fail

**Minor · cli · 30–45m · A1 · owner call.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, Beancount 3.2.3, macOS.
On a ledger whose account names are spelled in decomposed Unicode, `bea
add` writes the new directive with the composed (NFC) spelling — as
documented. `bea` itself treats both as one account, but stock Beancount
does not: the ledger passed `bean-check` before the write and fails
after it, though the user typed exactly the spelling the ledger uses.
The NFC write is a documented choice; the consequence for other
Beancount tools is not recorded. No product fix implemented.

Create `/absolute/books/main.bean` where `é` in both places is `e`
followed by U+0301:

```sh
printf '2026-01-01 open Assets:Cafe\xcc\x81 USD\n2026-01-01 open Equity:Opening\n\n2026-01-02 * "o"\n  Assets:Cafe\xcc\x81  5 USD\n  Equity:Opening\n' > main.bean
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bean-check main.bean                    # stock, from the managed engine
bea -f main.bean add note --date 2026-02-01 -a "$(printf 'Assets:Cafe\xcc\x81')" -m hi
bean-check main.bean
```

Actual: the first `bean-check` exits 0. `bea add note` exits 0 and
appends `2026-02-01 note Assets:Café "hi"` with `é` as the single
character U+00E9 (bytes `c3 a9`). The second `bean-check` exits 1:
`main.bean:8: Invalid reference to unknown account 'Assets:Café'`. `bea
check` still exits 0.

Control: the same fixture and command spelled NFC throughout stays valid
for stock `bean-check`.

Expected: a write that exits 0 leaves no new stock `bean-check` error.
`docs/USAGE.md` says a differently normalized name "resolves to the same
account … and the new directive is written NFC" — which is what happens;
the gap is that the result is no longer a valid ledger for stock tools.

Cause: `cli/src/bea_engine/ledger/text.py` (`parse_account`) and
`cli/src/bea_engine/ledger/writer.py:255-288` always emit NFC; `bea`'s
own reads normalize the whole file, so it never sees the split.

Fix: when the name matches an already-opened account under NFC
comparison, write the spelling the ledger uses, and use NFC only for new
names; or document that an NFD ledger stops being valid for other
Beancount tools after a write, and offer a one-step normalization
(`format -i`). Owner decision.

Blast radius: every account-bearing `add`; only `add note` was run.
Import was not tested.

Dedupe: w3/done/278 introduced NFC writes; w5/130 (custom account
refusal), w5/135 (doctor) and w5/144 (NFD directory) are other
normalization gaps. None records stock `bean-check` failing after an
exit-0 add.

Acceptance: after the command, stock `bean-check` still exits 0 on the
NFD fixture, or the documentation states the limitation and the command
warns. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — Took the note's second option, because `docs/USAGE.md` and w1/m26/t004 already fix the contract that new directives are written NFC and existing bytes are never renormalized: the write is unchanged, and it is no longer silent. `cli/src/bea_engine/ledger/write.py` now compares the account tokens of the appended text with those of the include closure and, when the ledger spells the same account in another normalization, returns a warning naming both spellings as escapes, saying that other Beancount tools such as `bean-check` will report the new line as an unknown account, and advising to re-save the ledger as NFC; it is printed on stderr, carried in `warnings` under `--json`, and covers every `add`, bulk `add transactions`, raw append and import because they share that write path. `cli/docs/USAGE.md` states the limitation and that `format -i` does not renormalize. `cli/tests/test_add_respelled_account_note.py` runs the note's fixture through real commands and a separate stock `bean-check` process: the NFD ledger passes before and fails after the add with the warning shown, the warning repeats on later writes, appears once per account for a transaction and a bulk batch, and is absent for an all-NFC ledger (which stays valid for stock Beancount) and for a name that appears only inside a string or comment; four of the seven cases fail with the source change reverted. Stock `bean-check` still fails on the NFD fixture after the write, so the first acceptance alternative (writing the ledger's own spelling) is not met by design, and no one-step normalization command was added. Only macOS was exercised. `make check-all` passed. Shipped in `09f60342` (`cli`).
