# Two `write_directive` calls in one `bea ask` model reply open two approval prompts at once: keystrokes reach either one, approving both writes only one, and the session can hang

**Major · cli · 20–30m · A1.** Real CLI QA, 2026-10-16, HEAD `0c12f2dc`, checkout `bea 0.3.1`, macOS 26.5.1. Simulation: local stub of the AI proxy; interactive REPL on a PTY.
Models batch independent tool calls ("add a coffee and a lunch"), and bea
does not ask for sequential calls. pydantic-ai then runs both
`write_directive` calls at once in worker threads. Each thread draws its own
prompt_toolkit selector on the same terminal and dry-runs against the
original file. The consent gate, the one check before an AI-proposed write,
no longer ties an answer to the directive on its panel. No product fix
implemented.

Ledger with `Assets:Cash`, `Expenses:Food` open. The stub's first reply has
two `tool_calls`, both `write_directive`: `2026-02-01 * "Cafe" "latte"` (5.25
USD) and `2026-02-02 * "Bakery" "bread"` (3.00 USD); the next reply is text.

```sh
bea -f /abs/main.bean ask        # in a terminal; type "add both", then answer the prompts
```

Actual:

- both panels print, then two selectors render together, each on "2. No";
- `y` then Enter (yes to the first, no to the second) wrote "bread" in 5 of
  7 runs and "latte" in 1;
- `y` twice wrote exactly one directive in every run, and the tool result for
  the other reads `Write rejected; nothing was written: The ledger changed
  while the operation was running`;
- in some runs one `y` followed by Ctrl-D leaves the spinner over a hidden
  selector, and the process never returns (killed at 40–90 s).

Exit 0 in the runs that return.

Control: one `write_directive` per reply behaves correctly for y, n, Enter,
Ctrl-C and d; two writes in consecutive replies both land.

Expected: panels appear one at a time; each answer applies to the directive
on its panel; two approved writes both land (the second dry-run after the
first write). USAGE: the confirmation "shows the directive as it will be
appended" and "starts on No".

Cause: `write_directive` is registered with a plain `@agent.tool()`
(`cli/src/cli/ask/agent.py:408`), so parallel calls run concurrently; each
calls `confirm_fn` (`agent.py:438`), which runs its own `Application`
(`cli/src/cli/ask/repl.py:194`) and stops and starts the shared spinner
(`repl.py:214`, `:233`); the dry-run token is taken before either write
(`agent.py:448`).

Fix: make the tool sequential (`@agent.tool(sequential=True)` in the
installed pydantic-ai, or a lock around the whole tool body), so each dry run
and prompt follows the previous write.

Dedupe: searched `parallel tool`, `sequential`, `two panels`; the
`write_directive` notes (w1/095, w3/452, w5/374, w5/453) are different.

Acceptance: with the two-call reply, `y` `y` writes both, `y` Enter writes
only latte, and Ctrl-D never hangs. A test drives two parallel calls.

---

**Resolved 2026-10-17** — Shipped in `2857e778` (`cli`). `write_directive` (`cli/src/cli/ask/agent.py`) now runs its body under a per-agent `threading.Lock`. When a model reply holds two writes, the dry run, consent panel and write of each happen in turn, so the second dry run follows the first write and each answer applies to the directive on its panel. The fix is a lock rather than the note's `@agent.tool(sequential=True)`, because the `ask` extra accepts `pydantic-ai>=0.3`, older than that option. The two concurrent selectors that caused the hang can no longer exist. USAGE says several writes in one reply get their panels one at a time.

`tests/test_ask_parallel_writes.py` sends a two-call reply through pydantic-ai with a stub model. With `y`/`y` both directives land; with `y`/`n` only latte does. Peak panel overlap is 1 in both cases. Both tests fail without the fix (overlap 2).

Not exercised: the PTY Ctrl-D path itself. `make check-all` passed.
