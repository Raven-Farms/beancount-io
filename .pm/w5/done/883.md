# `treeify` leaves valid accounts containing a non-ASCII space flat inside a successful half-tree (incomplete w5/137 grammar support)

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `363c528db`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
Reproduced twice from pristine fixtures for U+00A0 (non-breaking space) and
U+3000 (ideographic space), through file, stdin and `-o` output. No product
fix implemented.

Create a synthetic ledger with this Python snippet; the escape makes the
account's character unambiguous:

```python
from pathlib import Path
books = Path('/abs/books')
books.mkdir(parents=True, exist_ok=True)
account = 'Assets:Bank:My\u00a0Savings'
(books / 'main.bean').write_text(
    f'2024-01-01 open {account} USD\n'
    '2024-01-01 open Equity:Opening USD\n'
    '2024-02-01 * "Opening"\n'
    f'  {account} 1.00 USD\n'
    '  Equity:Opening -1.00 USD\n', encoding='utf-8')
```

With cwd `/abs/books`, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, and no inherited
`BEA_FILE`/`BEA_TOKEN`:

```sh
bea --json --file /abs/books/main.bean check
bea --file /abs/books/main.bean query 'SELECT account, sum(position) GROUP BY account ORDER BY account' > balances.txt
bea treeify balances.txt
bea treeify < balances.txt
bea treeify balances.txt -o tree.txt
```

Check and query exit 0, without stderr. All three treeify forms exit 0
without stderr, but draw only Equity → Opening. The asset row is left as
the original flat `Assets:Bank:My<U+00A0>Savings 1.00 USD`, above that
branch. Its Assets and Bank parents never appear. Filtering the query to
`WHERE account ~ "^Assets:"` before `GROUP BY` leaves only this account;
treeify then exits 2 with `Could not find any valid column in input` and
advice for names "outside Beancount's account grammar". That diagnosis is
wrong: the very same ledger passed check. Changing U+00A0 to U+3000 produces
the same failures. Source ledger bytes remain unchanged.

Passing controls, each repeated twice: use `Assets:Bank:Épargne` instead,
or keep the original account and pass
`bea treeify balances.txt -r '[^ :]+(:[^ :]+)+'`. Both draw Assets → Bank →
the full final component, including its original space or accent, with no
flat asset row. The accented single-account query also renders successfully.

Expected: `cli/docs/USAGE.md:557,606` promises the account column drawn as a
tree using Beancount's grammar. Its own formatter documentation at :681
explicitly recognizes non-ASCII spaces as account-name characters. The
installed Beancount lexer's `ACCOUNTTYPE`/`ACCOUNTNAME` include all non-ASCII
UTF-8 characters; they do not subtract Unicode whitespace.

Cause: `cli/src/cli/commands/treeify.py:27–28,36,40–42` uses
`[^\x00-\x7F\s]`. Python's `\s` removes these legal non-ASCII characters
from both `_LETTERS` and `_COMPONENT`. `_decide_pattern` (:60) cannot
recognize the asset row; the supplied pattern (:320) therefore lets upstream
render only the other rows. The fallback pattern has the same exclusion.
`-r` bypasses bea's default pattern, explaining the working control. This is
bea's wrapper grammar, not an upstream inability to render the name.

Fix: make the default root/component character classes agree with the lexer
for non-ASCII account characters while retaining ASCII column delimiters
and existing account-column selection. Preserve explicit `-r`, `-A`, `-F`,
ordinary ASCII/accented/CJK accounts and output protections. No dependency,
backend or API change is needed. File, stdin and `-o` share this path.
Keep the documented `add` refusal for account names containing Unicode
whitespace (w5/490 and w5/687); this finding concerns reading existing
valid ledgers, and does not request changing that write policy.

Dedupe: searched all board states for treeify/Unicode/space/NBSP/ideographic
space, and reviewed current open milestone scopes. Completed w5/137
(`a715cbba`) introduced the incomplete `\s` exclusion while adding accented
and CJK components; w5/414 (`90a2797b6`) carried it into renamed roots, and
w5/769's column selection retained it. Those fixes' recorded accent/CJK and
renamed-root outcomes remain useful controls. No overlapping open item or
later grammar repair was found in targeted history.

Acceptance: the real query → treeify journey renders the full Assets → Bank
branch for both space characters in file, stdin and `-o` modes, with no flat
account row; the filtered single-account form exits 0. The accented control
and explicit-pattern override retain their current output. Pin meaningful
CLI regression coverage. Windows/Linux, held-descriptor fallback inputs,
renamed roots containing these spaces and repaired behavior are unverified.
Sanitized fixtures/captures are under
`.tmp/qa-2026-10-20-cli-loop-pass2-2afc4ed1/`, especially
`tree-spaces-{1,2}-{nbsp,ideographic,accent-control}/` and
`captures/tree-spaces-*.json`; the public reproduction is self-contained.

---

**Resolved 2026-10-22** — `treeify`'s default account pattern no longer excludes non-ASCII whitespace from components, so `Assets:Bank:My\u00a0Savings` (and the ideographic space) draws inside its branch from file, stdin and `-o`; ASCII column delimiters are unchanged. `cli/tests/test_treeify_unicode_spaces.py` fails without the fix; shipped in the commit that moves this note (`cli`).
