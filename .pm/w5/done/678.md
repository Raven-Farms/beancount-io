# `bea format FILE` and `bea format FILE -o OUT` on an unparseable file exit 0 silently and echo it unformatted, while `--check` and `-i` exit 1 naming the parse error

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-17, HEAD `6d74be10`, checkout `bea 0.3.1`, macOS 26.5.1.
"Exit 0 is a promise: the documented effect happened." Formatting a file
with a syntax error does nothing, yet the stdout and `-o` modes report
success. An agent piping `format` output back into the ledger sees no
failure. No product fix implemented.

`bad.bean`:

```text
2026-01-01 open Assets:X     USD
2026-01-02 * "x
  Assets:X  1 USD
```

```sh
bea format /abs/bad.bean
bea format /abs/bad.bean -o out.bean
bea --json format /abs/bad.bean -o out2.bean
bea format --check /abs/bad.bean
```

Actual: the first three exit 0 with nothing on stderr; stdout (or `out.bean`)
is byte-identical to the input; JSON reports `{"scanned": 1, "output": …}`. The
fourth exits 1 with `cannot parse: …/bad.bean:2: Invalid token: '"x'`; `-i`
exits 1 with `1 file(s) cannot be parsed`.

Expected: the stdout and `-o` modes run the same syntax gate and exit 1 naming
the file and line, writing nothing to `-o`.

Cause: `_render` (`cli/src/cli/commands/format.py:580`) calls the engine's
`render_file` (`cli/src/bea_engine/ledger/formatting.py:183`), which skips the
syntax scan that `--check` and `-i` run (`format.py:490`).

Fix: run the syntax scan for stdout and `-o`.

Dedupe: searched `cannot parse` with stdout and output; no match.

Acceptance: the three commands exit 1 with the parse error, and `out.bean` is
not created. A test pins them.
