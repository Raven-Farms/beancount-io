# A plain `add balance` (or an importer's statement balance) with a wrong amount in a second currency is accepted silently: an old pad already used by the first currency's assertion fills the gap, backdated, exit 0

**Major · cli · 15–20m · A1.** Real CLI QA, 2026-10-17, HEAD `116cf55c0`, checkout `bea 0.3.1`, macOS 26.5.1.
USAGE:1110 says ordinary `add balance` "remains a strict assertion: review
missing transactions before choosing to create an adjustment". Upstream
Beancount keeps a pad active for every currency it has not yet padded. So a
pad consumed by a USD assertion months ago silently absorbs a wrong EUR
statement balance today.

---

**Resolved 2026-10-20** — plain `add balance` refuses a gap a non-staged pad would silently pad, naming the pad and the inserted amount (exit 1, reported in JSON); staged pads still complete, and `--pad-from`/`--force` opt in. The importer's statement-balance half is tracked as follow-up work. Shipped in `d4d22a2e3` (`cli`).

`mc.bean`:

```
option "operating_currency" "USD"

2026-01-01 open Assets:Checking
2026-01-01 open Equity:OpeningBalances

2026-01-05 * "Deposit"
  Assets:Checking  1000.00 USD
  Equity:OpeningBalances

2026-01-06 * "Euros"
  Assets:Checking  200.00 EUR
  Equity:OpeningBalances

2026-01-09 pad Assets:Checking Equity:OpeningBalances

2026-01-10 balance Assets:Checking   1100.00 USD
```

```sh
bea --json --file /abs/mc.bean add balance --date 2026-03-15 -a Assets:Checking --amount "250.00 EUR"
bea --file /abs/mc.bean check
```

Actual:
- The write exits 0 with `"warnings": []` and `"pad": null`, and `check` exits 0.
- The account holds 200 EUR, but the 2026-01-09 pad now also inserts `50.00
  EUR` from `Equity:OpeningBalances`, two months before the statement.
- An importer returning `Balance(2026-03-15, Assets:Checking, 250.00 EUR)` is
  written the same way with `--apply` (hunter's run).

Control: without the pad line (and the USD balance at 1000.00), the same
command exits 1 with `Balance failed … expected 250.00 EUR != accumulated
200.00 EUR (50.00 too little)`. The `--pad-from` path already warns in this
situation ("The existing pad at … fills this assertion, inserting X").

Expected: refuse (or at least warn) naming the pad and the amount it would
insert, and report it in JSON. Keep the staged-pad two-step, where an unused
pad is completed by the next balance, working.

Cause: the plain path in `cli/src/bea_engine/ledger/adding.py` (around
`:345-379`) validates and appends without asking whether a pad that was
already used fills the new assertion. Import uses the same validation.
`_covering_pad` (`:596`) and `_book_units` (`:565`) already compute what is
needed.

Fix: when a non-staged pad pads the new assertion, refuse with the pad's
location and inserted amount (or require `--pad-from` to opt in).

Dedupe: w1/116 (done) fixed the `--pad-from` form; w5/611 (open) is about
reporting a fresh pad's amount.

Acceptance: the command exits 1 naming the 2026-01-09 pad and 50.00 EUR; the
staged two-step still writes. Tests pin both.
