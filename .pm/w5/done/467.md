# `bea import` no longer recognises a `{}` sale as the entry already in the ledger: a hand-entered twin is written again with exit 0, and a re-import with a native ID exits 4 on bea's own entry

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-16, HEAD `8195088f`, checkout `bea 0.3.1`, macOS 26.5.1. Regression from the w5/349 fix (`9669be9d`).
A Python importer that books a sale against an open cost spec (`-4 HOOL {} @ 160 USD`, the usual way a
brokerage importer writes a reduction) is compared against the ledger's
*booked* copy of the same sale, whose cost booking has filled in as
`{150 USD}`. The two never compare equal, so:

- a sale the user already entered by hand is not even a possible duplicate,
  and `--apply` writes it a second time with exit 0;
- when the importer sets a native ID (`fitid`), the first `--apply` writes
  the sale and re-running the identical command exits 4: `Row 1 (conflict):
  Stable ID matches an entry with different transaction data.`, for
  byte-identical data bea wrote itself;
- an entry written before `9669be9d` with the units-only `import-id` no
  longer matches, which the w5/349 acceptance promised it would.

No product fix implemented.

Disposable `main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Broker:Cash USD
2026-01-01 open Assets:Broker:HOOL HOOL
2026-01-01 open Income:Gains USD
```

`importers.py` beside it (any file `s.txt`):

```python
import datetime
from decimal import Decimal
import beangulp
from beancount.core import data, amount, position
from beancount.core.number import MISSING

class Broker(beangulp.Importer):
    name = "broker"
    def identify(self, filepath): return filepath.endswith(".txt")
    def account(self, filepath): return "Assets:Broker"
    def extract(self, filepath, existing):
        meta = data.new_metadata(filepath, 1)
        # variant B: meta["fitid"] = "SELL1"
        return [data.Transaction(meta, datetime.date(2026, 2, 1), "*", None, "sell", data.EMPTY_SET, data.EMPTY_SET, [
            data.Posting("Assets:Broker:HOOL", amount.Amount(Decimal("-4"), "HOOL"),
                         position.CostSpec(MISSING, None, None, None, None, False), amount.Amount(Decimal("160"), "USD"), None, None),
            data.Posting("Assets:Broker:Cash", amount.Amount(Decimal("640"), "USD"), None, None, None, None),
            data.Posting("Income:Gains", None, None, None, None, None)])]
CONFIG = [Broker()]
```

Isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, closed stdin.

```sh
bea -f /abs/main.bean import s.txt --apply
```

Actual (A, hand-entered sale present): exit 0, `1 ready, 0 exact duplicates,
0 possible duplicates`, `Wrote 1 entry`; the ledger holds two `"sell"`
entries and `Assets:Broker:HOOL` falls to `2 HOOL {150 USD}` instead of 6.
`bea check` passes.

Actual (B, ledger without the sale, importer sets `fitid`): the first
`--apply` writes it (exit 0); the second exits 4 with the conflict above.

Control: the same importer without `fitid` and no hand-entered sale matches
on its own generated `import-id` string on the second run (exit 0, `1 exact
duplicates`). An importer that states the cost (`{150 USD} @ 160 USD`)
matches in all three variants.

Expected: the `{}` sale is the same row as its booked twin: an exact
duplicate under a shared native or legacy ID, and a possible duplicate
otherwise. `cli/docs/IMPORTING.md` says an exact native-ID match is skipped
and that ids written before the lot change "still match, but only the same
lot".

Cause: `_lot_text` (`cli/src/bea_engine/importing.py:833-855`) renders the
ledger entry's booked `Cost` (number and currency filled in by booking) but
the importer's unbooked `CostSpec`, where `{}` has neither, so it adds
nothing. The text feeds `_fingerprint` (`:858-867`), the content checks in
`_same_row` (`:962`), and the leg comparison at `:1470`. Its docstring
already drops the lot date "since booking fills it in"; booking also fills
the per-unit number and currency of `{}`, `{USD}`, `{2026-01-10}` and
`{150}`.

Fix: compare only the cost fields the importer's spec states. When the
incoming spec leaves the number or currency open, leave them out of both
sides' lot text (or compare against the ledger entry's unbooked spec), so a
`{}` sale matches its booked twin while two stated lots at 100 and 120 USD
stay distinct (keep w5/349's test green).

Blast radius: any Python importer that reduces lots with an open or partial
cost spec; re-imports of brokerage statements. CSV imports carry no cost.

Dedupe: searched `_lot_text`, `booked cost`, `open cost`, `CostSpec`. Only
w5/349 (the fix that introduced this) matches.

Acceptance: variants A and B and the legacy-id case all skip or flag the
sale; the 100/120 USD distinct-lots case from w5/349 still imports both rows.
Tests pin each.

---

**Resolved 2026-10-16** — Shipped in `7319dfc7` (`cli`). Duplicate matching in `cli/src/bea_engine/importing.py` now compares each source leg's units and price as text, beside the cost fields it actually states (`_lot`), through `_legs_agree`: a cost number, currency or label that either side leaves open agrees with any value, so the importer's `{}` sale matches the lot booking chose on the ledger's copy. Native-id content checks, legacy-id claims and the possible-duplicate lookup all use it; the generated-id hash is unchanged. `tests/test_import_open_cost_matches_booked.py` pins variant A (a hand-entered twin is a possible duplicate and `--apply` writes nothing), variant B (a `fitid` re-import is an exact duplicate), and the units-only legacy id (a duplicate). A stated `{170 USD}` under the same native id is still a conflict, and w5/349's 100/120 USD lots still import as two rows. The three repro tests fail without the fix. `cli/docs/IMPORTING.md` says an open cost compares only what it states.
