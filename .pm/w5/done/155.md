# `bea query` reading BQL from stdin skips the UTF-8 rule: a silent empty answer under a C locale, a raw codec error otherwise

**Minor · cli · 25m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
A query piped to `bea query` in a non-UTF-8 encoding is not rejected the
way `bea format -` and `add transactions --from -` reject such input.
Under a C/POSIX locale (cron, CI) the bad byte is smuggled through and the
query silently matches nothing, exit 0. Under a UTF-8 locale it fails with
a raw codec message as a ledger validation error. No product fix
implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD

2026-01-05 * "Café" "Lunch"
  Expenses:Food  12.00 USD
  Assets:Cash
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, no TTY, cwd `/absolute/books`.

```sh
printf "SELECT date, payee WHERE payee = 'Caf\xe9'\n" | LC_ALL=C bea -f main.bean query
printf "SELECT date, payee WHERE payee = 'Caf\xe9'\n" | LC_ALL=en_US.UTF-8 bea -f main.bean query
```

Actual: the first exits 0 with `(no rows)`. The second exits 1 with
`Error: 'utf-8' codec can't decode byte 0xe9 in position 37: invalid
continuation byte`.

Controls: the same query in UTF-8 (`Caf\xc3\xa9`) under `LC_ALL=C`
returns both postings, exit 0. Latin-1 text piped to `bea format -` fails
with `Cannot decode 'stdin' as UTF-8: invalid continuation byte at byte
17. Re-save the file as UTF-8 and retry.` A worker saw a UTF-8 BOM on
stdin rejected as a BQL syntax error at an invisible character, and UTF-16
give `embedded null byte`.

Expected: `docs/USAGE.md` says piped input to `bea format -` that is not
UTF-8 "fails the same way, naming `stdin`", and that bulk JSON on stdin
"must be UTF-8 … (a BOM is fine)" with undecodable input a usage error
(exit 2). `query` reads BQL from piped stdin and should apply the same
rule: accept a BOM, and refuse undecodable bytes with exit 2 naming
`stdin`.

Cause: `cli/src/cli/commands/query.py:261,283` call `sys.stdin.read()` in
text mode; under a C locale Python decodes with `surrogateescape`, so
`0xE9` becomes a lone surrogate that never matches. The fix made for
`format` (`_stdin_text`) was not applied here.

Fix: read `sys.stdin.buffer`, decode as `utf-8-sig`, and raise a usage
error naming `stdin` with the re-save hint on failure, for both stdin
branches. No dependency or API change.

Blast radius: `bea query` with piped BQL, text and JSON.

Dedupe: board search for surrogate, "embedded null" and BOM with query or
stdin finds w1/done/166 (the same defect in `format -`, fixed), w1/done/112
and w3/done/248 (`--from`); none covers `query`.

Acceptance: both commands exit 2 with a message naming `stdin` and the
byte offset; a BOM-prefixed UTF-8 query runs; the UTF-8 control is
unchanged. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — `bea query` now reads piped BQL as bytes and decodes it as UTF-8 with an optional BOM through a new `_stdin_query` helper in `cli/src/cli/commands/query.py`, used by both the `--file` and `--source` stdin branches. Undecodable input is a usage error (exit 2) reading `Cannot decode 'stdin' as UTF-8: ... at byte N`, identical under a C and a UTF-8 locale and inside the `--json` error envelope, and UTF-16 input gets the same refusal with a UTF-16 hint instead of `embedded null byte`. `cli/docs/USAGE.md` states the rule beside the stdin paragraph for `query`. The regression test `cli/tests/test_query_stdin_decode.py` runs the real command for Latin-1 input under both locales on both branches, the JSON envelope, UTF-16 with and without a BOM, and UTF-8 with and without a BOM; 9 of its 11 cases fail with the fix reverted, the two plain UTF-8 controls passing either way. The message reuses the shared wording, so its remedy says "Re-save the file" although the input is a pipe. Only macOS was exercised. `make check-all` passed. Shipped in `712c6a7e` (`cli`).
