# Two empty-ledger slips: `list`'s empty-result notice ("No prices found.") goes to stdout, unlike `query`'s `(no rows)` and `balance`'s "No accounts match" on stderr, and a BOM-only file's first append gets two leading newlines where a zero-byte file gets one

**Trivial · cli · 5–10m · A1.** Real CLI QA, 2026-10-17, HEAD `473bce6af`, checkout `bea 0.3.1`, macOS 26.5.1.
No product fix implemented.

1. **Empty notice on stdout.** `bea -f /abs/z.bean list price >o.txt 2>e.txt` on
   a zero-byte ledger writes `No prices found.` to stdout, with stderr empty
   and exit 0. `list transaction --details` says `No transactions found.` the
   same way. USAGE:827 says an empty `query` result prints `(no rows)` on stderr,
   and `balance` prints `No accounts match …` on stderr, so a `| head` or `> file`
   pipeline reads the `list` notice as a data row. Cause:
   `cli/src/cli/commands/list.py:409` uses `typer.echo(spec.empty)`.
2. **BOM spacing.** On a file holding only `EF BB BF`, `add open --date 2026-01-01
   --account Assets:Cash -c USD` writes `EF BB BF 0A 0A 2026-01-01 open…`. A
   zero-byte file gets a single `0A` before the open. Both pass `check`. USAGE
   says a BOM file loads like any other. Cause: the append treats `"\ufeff"` as
   an unterminated line and adds a repair newline before the separator
   (`cli/src/bea_engine/ledger/write.py`, around `:2784`).

Fix: write the list notice to stderr, and ignore a leading U+FEFF in the
emptiness test.

Dedupe: no note covers either.

Acceptance: the notice is on stderr, and both files get the same layout.
