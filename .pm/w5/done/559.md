# A stored query (`.run NAME`) whose `FROM OPEN ON D` falls on or after its `query` directive's date answers `(no rows)` with exit 0, or "CLOSE date must follow OPEN date" for a CLOSE nobody wrote (gap in w3/398)

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-16, HEAD `7898f69d`, checkout `bea 0.3.1`, macOS 26.5.1.
Upstream closes a stored query's window at the `query` directive's date. So
a stored query dated 2026-01-15 that opens on 2026-01-15 has a zero-day
window, and one that opens later has a reversed window. USAGE refuses a
zero-day window "rather than answered with an empty result that reads like
an empty day". w3/398 promised stored queries the same validation "after
stored-query defaults", and its resolution left default-date variants
unverified. No product fix implemented.

`sq.bean`:

```beancount
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "Opening"
  Assets:Cash  100.00 USD
  Equity:Opening
2026-01-10 * "Lunch"
  Expenses:Food  10.00 USD
  Assets:Cash
2026-01-20 * "Dinner"
  Expenses:Food  20.00 USD
  Assets:Cash
2026-01-15 query "since-jan15" "SELECT date, narration, position FROM OPEN ON 2026-01-15 WHERE account = 'Expenses:Food'"
2026-01-15 query "since-feb" "SELECT date, narration, position FROM OPEN ON 2026-02-01 WHERE account = 'Expenses:Food'"
```

```sh
bea --file /abs/sq.bean query ".run since-jan15"
bea --file /abs/sq.bean query ".run since-feb"
```

Actual: the first exits 0 with `(no rows)` (JSON `data.text: ""`); the Dinner
on 2026-01-20 is silently excluded. The second exits 2 with `CLOSE date must
follow OPEN date.` and `Run bea query .tables…`.

Control: the direct form `… FROM OPEN ON 2026-01-15 CLOSE ON 2026-01-15 …`
gets bea's zero-day explanation with the `CLOSE ON 2026-01-16` hint.

Expected: both refuse with exit 2, explaining that the stored query's window
closes at its directive date (2026-01-15) and suggesting re-dating the
`query` directive or adding an explicit `CLOSE ON`.

Cause: `PreciseShell.execute` runs `_refuse_empty_window` on the query text
only (`cli/src/bea_engine/query.py:1075`); `_run_stored` (`:669`, `:703`)
passes `default_close_date=query.date`, which upstream applies later.

Fix: validate the window with the default close date applied, and name the
directive date in the message.

Dedupe: searched `default_close_date`, `query directive`. Only w3/398 (done).

Acceptance: both `.run` commands exit 2 with the explanation. A test pins
them.

---

**Resolved 2026-10-17** — Shipped in `0f19964c` (`cli`). `PreciseShell.execute` (`cli/src/bea_engine/query.py`) now passes `.run`'s `default_close_date` into `_refuse_empty_window`. That check applies the directive date as Beanquery does, as the outer `FROM`'s `CLOSE ON` when the text names none. The note's `.run since-jan15` and `.run since-feb` both exit 2 with `This stored query's window covers no days: its query directive's date, 2026-01-15, closes the window (exclusive), and OPEN ON starts on that same day.` (or `after it, on 2026-02-01`), plus `Add CLOSE ON … or later to the query, or re-date its query directive after the last day it should cover.` in text and JSON. A stored window that opens before its directive date still answers. `tests/test_query_empty_date_window.py` pins both refusals and the control; both refusals fail without the fix. `make check-all` passed.
