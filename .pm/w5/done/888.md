# Keep the funded-close guard when `check_drained` omits a zero assertion

**Minor · cli · 40–60m · A1.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `74adb75b9`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
Reproduced twice from pristine fixtures in JSON and human modes, with
independent controls. No product fix implemented.

Create `/abs/books/main.bean`:

```beancount
plugin "beancount.plugins.check_drained"
2024-01-01 open Assets:Cash USD
2024-01-01 open Equity:Opening USD
2024-01-01 open Expenses:Food USD
2024-01-02 * "Seed"
  Assets:Cash 100 USD
  Equity:Opening -100 USD
2024-02-01 balance Assets:Cash 100 USD
```

With cwd `/abs/books`, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, and no inherited
`BEA_FILE`/`BEA_TOKEN`:

```sh
bea --json --file /abs/books/main.bean check
bea --json --file /abs/books/main.bean add close --account Assets:Cash --date 2024-02-01
bea --json --file /abs/books/main.bean check
bea --json --file /abs/books/main.bean query 'SELECT account, sum(number) GROUP BY account ORDER BY account'
bea --json --file /abs/books/main.bean add transaction --date 2024-02-02 --narration 'Move funds' -p 'Assets:Cash -100 USD' -p Expenses:Food
```

Actual: the source checks successfully. Close exits **0**, appends
`2024-02-01 close Assets:Cash`, reports `written: 1` with empty warnings,
and has empty stderr. Human mode likewise exits 0, `Added 1 close ...`.
The resulting ledger still checks successfully; the query shows Cash
**100 USD**, opening equity **−100 USD**. The attempted later transaction
exits 1 naming the now-inactive account and preserves the file. The money
is stranded in the closed account, the outcome w2/092's CLI guard was
introduced to prevent.

Controls, each repeated twice from pristine fixtures:

- Keep the plugin and change only the assertion's date to January 31.
  Source check passes; close exits 1, leaves bytes unchanged, and names
  `check_drained`'s generated zero assertion and the remaining 100 USD.
- Keep the February 1 assertion and remove only the plugin. Close exits 1,
  leaves bytes unchanged, and says Cash still holds 100 USD, with `--force`
  as the explicit override.
- On the original fixture, explicitly pass `--force`. Close and the final
  check succeed, preserving that deliberate opt-in behavior.
- Drain Cash with a January 31 transaction to Expenses:Food and set the
  February 1 assertion to zero. Source check, close and final check all
  succeed without force.
- Keep the original 100 USD assertion, but move all funds out with a
  transaction dated February 1, after that start-of-day assertion. Source
  check, close and final check also succeed, twice. Judge the remaining
  holdings through the close date, not the assertion's stated number alone.

The split-ledger/multiple-currency case also reproduces twice: open Cash
and Equity for USD,EUR, put the seed transaction and assertions in an
included `years/2024.bean`, add +5 EUR to Cash/−5 EUR to Equity and a
February 1 `balance Assets:Cash 5 EUR`, and pass `--into years/2024.bean`
to close. With the plugin, close exits 0 and appends only to the include;
the root is unchanged, check passes, and a fresh query grouped by account
and currency retains Cash **100 USD and 5 EUR**. Without the plugin,
the same close exits 1 naming both amounts and preserves both files.
The plain fixture's explicit `--force` control also succeeds twice.

Expected: merely loading `check_drained` must not disable the CLI's funded
close refusal when that plugin inserts no zero check. The supported local
policy is already explicit in `cli/docs/USAGE.md:1382` and completed
w2/092: refuse a remaining balance unless `--force`. An ordinary valid
statement assertion on the requested closing date is not that override.

Cause: `_close` in `cli/src/bea_engine/ledger/adding.py:338–339` sets
`held = {}` whenever a plugin name ends with `check_drained`, assuming
validation will refuse every funded close. In the installed standard
plugin, `beancount/plugins/check_drained.py:76–80` intentionally skips its generated zero
assertion when an explicit assertion already exists for that account,
currency and close date. It does not require that existing assertion to
be zero. Thus the CLI skips its own guard, and the candidate has no failing
plugin assertion to catch the close. `_held_through` would report the
100 USD correctly if called. Only local `add close` uses this branch.

Fix: ensure the existing local nonzero-holding guard covers cases where the
plugin supplies no effective zero assertion; do not use plugin presence as
proof that the account will be drained. Preserve explicit force behavior,
successful drained closes, snapshot/concurrency protection, and genuine
plugin validation/diagnostics where they apply. Do not fork or change
upstream Beancount's plugin semantics. No dependency or backend/API change
is needed for this CLI repair.

Dedupe: searched all board states for same-day/explicit assertions bypassing
`check_drained`, and reviewed open milestone scopes/history. Completed
w2/092 (`d70e58002`) introduces this delegation branch. Its ordinary funded
refusal, force and drained controls still work, but omit this interaction.
w5/399 and w5/771 concern the message when a generated zero assertion
actually fails; w5/152 concerns adding an assertion alongside a generated
one, not accepting this close. No overlapping open CLI item found. Hosted
close policy is separately blocked in w2/095; this record does not change
or claim to have tested that API contract.

Acceptance: the original fixture's close without force exits 1 naming the
remaining 100 USD and leaves the ledger byte-identical, in JSON and human
modes. Earlier-assertion/no-plugin refusals remain correct, explicit force
on this fixture still works, and draining then closing succeeds. Pin real
CLI coverage, including the verified split/multiple-currency case; a green
ledger check alone cannot catch this policy failure. Custom plugin aliases
and repaired behavior remain unverified. Sanitized fixtures, before
snapshots and captures are under
`.tmp/qa-2026-10-20-cli-loop-pass3-69d827bc/`, especially
`close-drained-assertion-{1,2}-{same-day,earlier-assertion,plain}/`,
`close-drained-control-*`, `close-drained-human-*` and
`close-drained-split-multi-*`, plus `captures/close-drained-*.json`.
The public reproduction is self-contained.

## Flow accounts excluded by the standard plugin

Further real CLI QA on 2026-10-21, HEAD `9aa62dbb1`, the same checkout
`bea 0.3.1`, macOS 26.5.1 arm64, frontend Python 3.13.3 and existing managed
Python 3.12.10 / Beancount 3.2.3. Same isolated subprocess environment and
closed stdin/no TTY. This variant needs **no balance assertion at all**.

Create a fresh disposable `/abs/books/main.bean`:

```beancount
plugin "beancount.plugins.check_drained"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
2024-01-02 * "Meal"
  Assets:Cash -7.75 USD
  Expenses:Food 7.75 USD
```

```sh
bea --json -f /abs/books/main.bean check
bea --json --no-input -f /abs/books/main.bean add close --date 2024-02-01 --account Expenses:Food
bea --json -f /abs/books/main.bean list close --on-disk --limit 100
bea --json -f /abs/books/main.bean list balance --limit 100
bea --json -f /abs/books/main.bean check
bea --json -f /abs/books/main.bean query 'SELECT account,sum(number) GROUP BY account ORDER BY account'
bea --json -f /abs/books/main.bean add transaction --date 2024-02-02 --narration Refund --posting 'Expenses:Food -7.75 USD' --posting 'Assets:Cash 7.75 USD'
```

Actual: the first six commands exit 0. Close writes one with empty warnings;
the on-disk close is visible, the balance listing is empty, and the checked
ledger still holds **Expenses:Food 7.75 USD / Assets:Cash −7.75 USD**.
The refund exits 1 because Food is now inactive and preserves all source
bytes. The account was closed with a balance without the required override.
Human close also succeeds with `Added 1 close`.

An income variant opens `Income:Salary`, credits it **−7.75 USD** and debits
Cash **7.75 USD**. It reproduces identically. Remove only the plugin from
either pristine source: the unforced close exits 1, names the nonzero
holding and `--force`, and preserves bytes. An explicit forced close or a
January 31 transaction draining the flow account allows the close and a
fresh check. These controls and both affected account types were each
repeated twice. Asset and equity accounts with the same nonzero amount
remain protected by the real plugin's failing generated zero assertion;
without the plugin the CLI guard protects all four tested types.

Cause: the same blanket delegation in `_close` (`adding.py:338–339`)
assumes more coverage than the installed plugin provides. Upstream
`beancount/plugins/check_drained.py:49–52` deliberately limits `is_covered`
to `account_types.is_balance_sheet_account`; its insertion at :76–94
therefore never handles Income or Expenses. This is valid upstream behavior,
not an upstream defect. The CLI's documented nonzero-close policy applies
to the account regardless of that optional plugin's narrower coverage.

Extend the fix and acceptance above to this case: loading the standard
plugin must not disable the CLI guard for flow accounts. Both unforced
public variants must refuse with exit 1, their exact remaining amount and
no writes. Preserve drained/explicit-force controls and genuine plugin
validation on balance-sheet accounts. `_held_through` already computes
these flow balances correctly; its separate same-day purchase-ordering
caller is outside this fix. No dependency or API change is needed.

Dedupe: whole-board searches for flow-account/check_drained closing gaps
found no separate item. Active/blocked milestone scopes and targeted history
still leave this local branch to w2/092 (`d70e58002`). This extends **888**
because the same `_close` delegation must be repaired, rather than creating
another task for an uncovered branch. The 40–60m estimate remains unchanged.

**Resolved 2026-10-22** — `add close` no longer treats a loaded `check_drained` as proof the account will be drained: the CLI's funded-close refusal now stays for any held currency the plugin will not assert (an explicit assertion already on the close date, whatever it asserts, and Income or Expenses accounts), while currencies the plugin does cover are still left to its own message. `--force`, drained closes and the plugin-only refusal are unchanged. `cli/tests/test_add_close_drained_uncovered.py` fails without the fix; shipped in the commit that moves this note (`cli`). The split-ledger/multi-currency variant was not separately exercised.
