# Unrelated concurrent writes fail with exit 4 when the command reads the ledger before taking the lock

**Minor · cli · 45–60m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
Eight simultaneous `add price` commands for eight different commodities
mostly fail with "The ledger changed during the operation … retry" (exit
4), though the writes do not conflict. The same happens to `add
transaction` when a posting omits its currency, but not when the
currency is spelled out. No data is lost; scripts and agents that fan
out writes must retry. If "exit 4, retry" is acceptable for any
`bea`-versus-`bea` race, this is by design — owner call. No product fix
implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

Use isolated BEA_CONFIG_DIR and one shared XDG_CACHE_HOME,
BEA_NO_UPDATE_NOTIFIER=1, no inherited BEA_FILE/BEA_TOKEN/CI, closed
stdin. Start eight at once, on a pristine ledger each run:

```sh
for c in QQA QQB QQC QQD QQE QQF QQG QQH; do
  bea -f /absolute/books/main.bean add price --date 2024-03-01 --commodity $c --amount "1 USD" </dev/null &
done; wait
```

Actual, over 5 runs (40 writers): 5 exit 0 and 35 exit 4. For eight
`add transaction nI --date 2024-02-01 -p "Expenses:Food I.00" -p
Assets:Cash` (currency omitted): 8 exit 0 and 32 exit 4.

Control: the same eight transactions with `-p "Expenses:Food I.00 USD"`:
40 of 40 exit 0. A worker confirmed that every exit status matched the
file content, and saw `add transactions --partial` and `import --apply`
lose with exit 4 to seven simultaneous single adds three times out of
three.

Expected: writers queue. `docs/USAGE.md` describes writes as "serialized
against every other `bea` write" where a concurrent append "either lands
before … or waits for it", and reserves exit 4 for "An external edit".

Cause: these paths capture a ledger snapshot before the lock and pass it
into the append, whose verification under the lock then rejects any
commit made by the writer it just waited for: `add price`
(`cli/src/bea_engine/ledger/adding.py:545`, passed at `:596`), `add
transaction` with an inferred currency (`:675`, `:725`), bulk
validation, and import (`importing.py`). The explicit-currency path
takes no snapshot.

Fix: take the lock before the decision read, or on a verification
failure under the lock re-capture and re-run the cheap decision; keep
exit 4 for a genuine duplicate or conflicting quote and for external
edits. No dependency or API change.

Blast radius: `add price`, `add transaction` with inferred currency,
`add transactions` and `import --apply` under concurrent `bea` writers.

Dedupe: w5/115 and w3/done/389 treat exit 4 as right for identical
price or import races and for `add balance`; neither covers unrelated
writes being refused or the inferred-currency split.

Acceptance: eight simultaneous `add price` commands for different
commodities all exit 0 and all eight prices are present; two identical
ones still write once. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — The commands that read the ledger to decide what to write now take the write lock before that read instead of after it: `add price`, `add balance`, `add transaction` and `add transactions` in `cli/src/bea_engine/ledger/adding.py`, and `import --apply` in `cli/src/bea_engine/main.py`, with `lock_file` in `cli/src/bea_engine/ledger/write.py` keeping a lock the process already holds rather than waiting on itself when the append asks for it again. Unrelated `bea` writes started together therefore queue and all exit 0, a repeated price is reported as already recorded, a conflicting quote that landed first is still refused, and an edit that takes no lock still exits 4; `cli/docs/USAGE.md` states the queueing. So that a duplicate or a refusal still leaves no file behind, such a command removes a lock file it created when it wrote nothing, and every locker now confirms after acquiring that the path still names the file it locked. `cli/tests/test_concurrent_writers_queue.py` races real commands (eight prices for eight commodities, six transactions with inferred and with explicit currencies, a batch plus an import against single adds, identical and conflicting quotes) and pins the external-edit control and the lock file's lifecycle; with the first version of the fix reverted the eight-price, inferred-currency and lock-release cases failed, while the batch/import and identical-quote cases depend on how the race falls and passed in that run. Beyond the note, `add balance` is covered by the same change, `import --apply` now holds the lock while the importer runs, and the raw-text append behind `ask` is unchanged. Only macOS was exercised. `make check-all` passed. Shipped in `61dc5fed` (`cli`).
