# The load cache keeps serving a date-dependent plugin's output from the day it was cached: under `fava.plugins.amortize_over`, today's amortization row stays missing (or a future one shows early) until a ledger file changes, with exit 0

**Major · cli · 15m · A1.** Real CLI QA, 2026-10-17, HEAD `46d7394e9`, checkout `bea 0.3.1`, macOS 26.5.1.
USAGE:223-225 says a changed plugin "reloads instead of serving the old
plugin's output", and that a cached load is served while it "still matches
the disk". A plugin whose output depends on today's date breaks that rule
without any file changing. No product fix implemented.

`am.beancount`:
- `option "operating_currency" "USD"` and `plugin "fava.plugins.amortize_over"`
- opens for `Assets:Checking`, `Expenses:Food`, `Expenses:Insurance` and
  `Assets:Prepaid`
- 100,000 one-line filler transactions, so the load is slow enough to cache
- `2026-09-18 * "Insurance"` with `amortize_months: 2`, `Assets:Prepaid -100
  USD` and `Expenses:Insurance 100 USD`

The plugin books only the parts dated on or before today: (1/2) on
2026-09-18 and (2/2) on 2026-10-18. When this was run, today was 2026-10-18
in `Pacific/Kiritimati` and 2026-10-17 in `UTC`.

```sh
Q="SELECT date, narration, number WHERE account = 'Expenses:Insurance'"
TZ=Pacific/Kiritimati bea --file /abs/am.beancount query "$Q"   # writes the cache
TZ=UTC bea --file /abs/am.beancount query "$Q"
```

Actual:
- Kiritimati then UTC: both list 2 rows. Under UTC the 2026-10-18 part is
  still in the future, but it is shown.
- With the cache deleted, UTC then Kiritimati: both list 1 row. Kiritimati
  never gets its part.
- Nothing is printed on stderr, and every run exits 0.

In ordinary use this needs no time-zone change: a cache written yesterday
hides today's amortization, and `report income-statement` for the month
misses it. `fava.plugins.forecast` has the same exposure across a year
boundary (hunter's code read).

Control: with the cache deleted, each zone gets its own correct answer.

Expected: each read reflects the plugin as run today.

Cause: `_load_fresh` (`cli/src/bea_engine/managed_load.py:804`) trusts an
engine-marked cache unless the files, documents or plugin fingerprints
changed. `_mark_engine_cache` (`:895`) records no date.

Fix: record the load's local date in the cache record and reload when it
differs. Alternatively, do not cache a load that ran a known date-dependent
plugin (`amortize_over`, `forecast`).

Dedupe: w5/326, 218, 111, 564, 576 and 591 cover other cache staleness; none
covers date-dependent output.

Acceptance: sequence 2 (UTC, then Kiritimati) shows 2 rows the second time. A
test with a mocked date pins it.

---

**Resolved 2026-10-19** — the engine cache record carries the load's local day and a cache from an earlier day loads again, so `amortize_over` no longer serves yesterday's rows, shipped in `fc412e56d` (`cli`)
