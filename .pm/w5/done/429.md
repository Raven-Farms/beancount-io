# User regexes in `query ~`, `report -a` and `treeify -r` that Python reads differently (POSIX classes like `[[:alpha:]]`, nested sets like `[[a]`) silently change meaning, and leak raw `FutureWarning` lines or a duplicated "warning: Possible nested set"

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
This is the [427](./427.md) mechanism, `--rules`, at every other place a
user regex is compiled. Python reads `[[:alpha:]]` as a literal set and
warns. bea's pre-checks compile the pattern without filtering warnings,
so the raw warning, often with a bea or site-packages source path,
reaches stderr. The query or filter then runs with the changed meaning
and exits 0:

- `~ '[[:alpha:]]'` matches nothing;
- `~ '[[a]'` matches accounts containing `[` or `a`.

No product fix implemented.

Use a USD ledger opening `Assets:Cash` and `Expenses:Food` with one
transaction. Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME,
BEA_NO_UPDATE_NOTIFIER=1, no `PYTHONWARNINGS`, and closed stdin.

```sh
bea -f /absolute/books/main.bean query "SELECT account WHERE account ~ '[[:alpha:]]'"
bea --json -f /absolute/books/main.bean query "SELECT account WHERE account ~ '[[:alpha:]]'"
bea -f /absolute/books/main.bean report balance-sheet -a '[[:alpha:]]'
bea treeify -r '[[:alpha:]]+' bal.txt
```

Actual:

- `query` (text) prints `warning: Possible nested set at position 1`
  twice, then `(no rows)`, exit 0.
- In `--json` mode stderr carries `…/cli/src/bea_engine/query.py:1377:
  FutureWarning: Possible nested set …` and a beanquery
  `query_compile.py:295` line. stdout stays clean, with `rows: []`.
- `report -a` prints `…/cli/src/fava/core/filters.py:189: FutureWarning:
  …` and a `beancount/core/account.py:176` line, then shows an empty
  report with exit 0.
- `treeify -r` leaks `…/cli/src/cli/commands/treeify.py:98:
  FutureWarning: …` and an upstream line before its refusal.

Reproduced twice each by the hunter, and by me for `query` and `report
-a`.

Control: `~ 'Food'`, `-a Food` and a valid `-r` produce no warnings. An
invalid regex (`[`) exits 2 through w5/103's pre-check.

Expected: no Python source paths or warning classes on stderr (w3/298,
w5/089). A pattern that Python would read differently from what was
written should exit 2, naming the option and the construct, with a
replacement such as `[^\W\d_]`, as proposed for 427.

Cause: the user-regex compile sites have no warnings handling:

- `cli/src/bea_engine/query.py:1377` (beanquery compiles the pattern again
  at `query_compile.py:295`, hence the duplicate);
- `cli/src/fava/core/filters.py:189` (then beancount `account.py:176`);
- `cli/src/cli/commands/treeify.py:98` (then upstream `treeify.py:61`);
- `cli/src/cli/csv_mapper.py:92`, the frontend twin of 427's site.

Fix: add one shared helper that compiles under
`warnings.catch_warnings(record=True)` and turns
`FutureWarning`/`DeprecationWarning` into a `UsageError` naming the
option. Call it from every pre-check, including 427's. Because the
pre-checks run before upstream sees the pattern, upstream never warns.
No dependency change.

Blast radius: `query` with `~`, `report * -a`, `treeify -r`, and
`--rules`. Users coming from grep or awk habits get silently wrong
results.

Dedupe: 427 covers `--rules`, w5/103 covers invalid `~` patterns, w5/061
covers bad `treeify -r`, and 414 covers treeify's root pattern. None
covers warnings or POSIX-class meaning on these surfaces.

Acceptance: each command above exits 2 naming the option and the POSIX
class, with no `FutureWarning` or `warning:` text, and nothing reaches
upstream. Ordinary patterns are unchanged. A test covers query, report
and treeify.

---

**Resolved 2026-10-15** — `regex_reads_otherwise`
(`cli/src/bea_engine/ledger/text.py`, with a frontend twin in
`cli/src/cli/utils.py`) compiles a user pattern with warnings captured.
For a POSIX class it names the class and its replacement (`[^\W\d_]`,
`\d`, `\s`); for other warnings, such as a nested set, it says how to
escape the construct. `query ~` (both its constant-pattern pre-check and
the run), `report -a` and `treeify -r`/`-d`/`-s` refuse with exit 2 in
bea's words, before anything else compiles the pattern. For example,
`Cannot run this BQL query: in the pattern '[[:alpha:]]', [:alpha:] is a
POSIX class, which Python's regex does not have: …`. No `FutureWarning`
or `warning:` text reaches stderr, in text or JSON, and ordinary patterns
are unchanged. The `--rules` sites stay with 427, which can reuse the
helper. Pinned by `cli/tests/test_user_regex_reads_otherwise.py`, which
fails without the fix.
