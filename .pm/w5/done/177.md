# `FROM OPEN ON <date> CLOSE` fails with a raw Python `TypeError`, and with `GROUP BY 1` the error is masked by an internal `AttributeError`

**Minor · cli · 30–40m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, Beanquery 0.2.0, macOS.
Two defects on one query shape. A bare `CLOSE` after `OPEN ON <date>` is
valid BQL but crashes in the compiler with a Python comparison error,
reported as exit 1 `validation`. And when a failing query groups by
position or expression, `bea`'s own error handler crashes first, so the
user sees `'int' object has no attribute 'name'` instead of the real
error. The root crash is upstream; the classification and the masking are
`bea`'s. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash
2024-01-01 open Expenses:Food

2024-01-05 * "Grocer" "Food"
  Expenses:Food  10.00 USD
  Assets:Cash

2024-01-06 * "No payee"
  Expenses:Food  5.00 USD
  Assets:Cash
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean query "SELECT account, sum(number) FROM OPEN ON 2024-01-01 CLOSE GROUP BY account"
bea -f main.bean query "SELECT account, sum(number) FROM OPEN ON 2024-01-01 CLOSE GROUP BY 1"
```

Actual: the first exits 1: `Error: TypeError: '>' not supported between
instances of 'datetime.date' and 'bool'`. The second exits 1: `Error:
AttributeError: 'int' object has no attribute 'name'`.

Control: `… FROM OPEN ON 2024-01-01 CLOSE ON 2025-01-01 GROUP BY 1` exits
0 with `Expenses:Food 15.00` and `Assets:Cash -15.00`. A worker saw
`BALANCES FROM OPEN ON 2024-01-01 CLOSE` fail the same way, `GROUP BY
root(account, 1), account` give `'Function' object has no attribute
'name'`, and the masking hide other upstream `TypeError`s (22 of 310
runtime errors in a fuzz run).

Expected: valid BQL either runs (open at the date, close at the ledger's
end) or is refused with exit 2 `usage` naming the clause — `docs/USAGE.md`
reserves exit 1 for a ledger that fails validation. An error handler
should never replace the real error with its own.

Cause: upstream Beanquery compares the open date with `True` for a bare
`CLOSE`. In `cli/src/bea_engine/query.py`, the `TypeError` handler
(`:1006-1019`) translates only one case and re-raises; inside it,
`_grouped_columns` (`:1073`) reads `.name` on every group-by item, which
is an `int` for an index and a function node for an expression.

Fix: detect a dated `OPEN` with a bare `CLOSE` and either substitute the
day after the last entry or raise a usage error; use `getattr(column,
"name", None)` in `_grouped_columns`. No dependency or API change.

Blast radius: SELECT, BALANCES and JOURNAL, one-shot, `.run` and the
shell.

Dedupe: board search for bare CLOSE, `_grouped_columns` and "has no
attribute 'name'" finds w3/372 (done; never ran bare `CLOSE` with `OPEN
ON`), w1/067 (added the handler) and w5/103 (evaluation-time errors on
the generic path); none covers these.

Acceptance: the first command runs or exits 2 naming `CLOSE`; the second
reports the same outcome as the first, never an `AttributeError`; the
control is unchanged. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — `FROM OPEN ON <date> CLOSE` is now refused with exit 2 `usage` instead of escaping as a raw `TypeError` with exit 1: the window check in `cli/src/bea_engine/query.py` (`_refuse_window`) names the bare `CLOSE` and points at `CLOSE ON YYYY-MM-DD` or dropping `CLOSE`, for SELECT, BALANCES, JOURNAL, subqueries, stored queries run through `.run`, and the shell, which all share that check. The note allowed either running the query or refusing it; refusing was chosen because substituting a date would mean rewriting the statement text, and `docs/USAGE.md` now records the refusal beside the zero-day window rule. `_grouped_columns` no longer reads `.name` from a positional or function `GROUP BY` item, so the handler stops replacing the real error with its own `AttributeError`, and `GROUP BY root(account, 1), accounts` now gets the set-column advice it was hiding. The new `cli/tests/test_query_open_on_bare_close.py` has 13 cases covering the refusal on each statement form and under `--json`, the three windows that must still answer (dated `CLOSE ON`, `OPEN ON` alone, `CLOSE` alone), and the unmasked `GROUP BY` errors; 10 fail with the fix reverted. The interactive prompt was not driven through a PTY for this note, since it reaches the same check the existing zero-day shell test exercises, and `SELECT accounts, count(*) GROUP BY 1` still surfaces Beanquery's own `TypeError` with exit 1 rather than the set-column advice. Only macOS was exercised. `make check-all` passed. Shipped in `746eb980` (`cli`).
