# `kill -9` on a writing `bea` does not stop the write: the orphaned engine lands it seconds later, and a retry records the entry twice

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, Python 3.13.3.
Since `b2babd61`, the write helper starts in its own session
(`start_new_session=True`), so a SIGKILL sent to the `bea` process never
reaches it. That includes `kill -9`, an OOM kill, `timeout -s KILL`, and
`Popen.kill()` from an agent or CI harness. `bea` dies at once with no
output, and at that moment the ledger is unchanged. The orphaned engine
then finishes and writes the entry a few seconds later. A caller that sees
the kill and retries waits on the orphan's lock, then writes the entry
again.

[014](./done/014.md) recorded the opposite as a verified property: "No
surprise write … the ledger was still unchanged … at +20 s, and no engine
process remained alive". So this is a regression. No product fix
implemented.

Fixture: any ledger big enough that a write takes a few seconds. This run
used 50,000 generated transactions (about 4 MB, about 4 s per `add`):

```beancount
option "operating_currency" "USD"
2020-01-01 open Assets:Checking USD
2020-01-01 open Expenses:Food USD
2020-01-01 open Equity:Opening USD
2020-01-01 * "Open"
  Assets:Checking  1000000.00 USD
  Equity:Opening
; … then 50,000 of:
2020-01-01 * "Shop 0" "item 0"
  Expenses:Food  1.25 USD
  Assets:Checking
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY. Signal the `bea` PID
only, not its process group.

```sh
bea -f /absolute/big/main.bean add note --date 2026-01-05 -a Assets:Checking -m late </dev/null &
sleep 1.5; kill -9 $!
grep -c '"late"' /absolute/big/main.bean      # immediately
pgrep -fl bea_engine                          # immediately
sleep 10; grep -c '"late"' /absolute/big/main.bean
```

Actual:

- `bea` exits 137 with empty stdout and stderr.
- Immediately afterwards, the note count is unchanged and
  `python -P -m bea_engine add --file …/main.bean --type note` is still
  running.
- About 10 s later the count has gone up by one and the engine has exited.

Reproduced independently in a fresh run, and also with the kill at 2.5 s.

Kill and retry: after the kill at 2.0 s, rerun the same `add` at once. The
retry prints `Waiting up to 60 seconds for another bea write on …
main.bean ...`, then `Added 1 note` with exit 0. The ledger ends with two
`late` notes.

Controls:

- SIGTERM at 1.5 s: `bea` exits -15; no note at +0 s or +10 s; no engine
  remains and no `.bea-*.tmp` is left.
- SIGINT to the process group at nine delays from 0.3 s to 6.5 s: each run
  either refused (no note) or completed (one note, exit 0), with nothing
  left behind.

Expected: 014's property holds, "The orphaned child does not carry on and
land the write later". After a kill, the outcome is at worst "unknown, and
settled by the time anyone can look". A retry must never double an entry.

Cause:

- `cli/src/cli/engine/launch.py:455` starts main-thread helpers with
  `start_new_session=True`, so that a group-delivered Ctrl-C does not
  interrupt cleanup twice.
- `_forwarding_teardown` (`launch.py:498-559`) is now the only path that
  stops the child. SIGKILL cannot be handled, so nothing gets forwarded,
  and no group or terminal signal reaches the child either.
- The engine keeps validating and commits through `replace_checked`
  (`cli/src/bea_engine/ledger/write.py:2011-2027`). Its `stopping.check()`
  (`:2025`) watches only for signals the engine itself receives.

Fix: make the engine refuse to commit once its frontend is gone. Record
`os.getppid()` at start. In `stopping.check()`, or immediately before
`os.replace` (`write.py:2027`), abort and drop the candidate if the parent
has changed (the engine was re-parented to 1 or to a subreaper). Optionally
poll the same check during long loads. On Linux,
`prctl(PR_SET_PDEATHSIG, SIGTERM)` can complement this, but the parent
check is the portable part. Keep the separate session. No dependency or
API change.

Blast radius: every staged writer launched through `_run_helper` from the
main thread: all `add` kinds, `add transactions`, `import --apply`,
`format -i`, `query -o` and `price export` file writes, and the `ask`
write tool. Only `add` was exercised. Worker-thread helpers stay in the
process group and were not tested. Windows does not use the separate
session and was not tested.

Dedupe: searched the board, `done/` included, for SIGKILL, orphan,
`kill -9`, `getppid` and `start_new_session`. `git log -S
'start_new_session=sys.platform'` returns only `b2babd61` (2026-10-02).
Related notes:

- w5/014: recorded no surprise write; written before the session change.
- w3/440: SIGTERM/SIGHUP leftovers.
- w1/074: a signal swallowed during parsing.
- w5/208 and w5/234: check, doctor and query-shell orphans.
- w5/252: signal naming.

None of them covers a later write after SIGKILL or a doubled retry.

Acceptance: on the fixture, kill -9 the `bea` PID at 1.5 s and again at
2.5 s.

- The ledger keeps its hash at +10 s.
- No `bea_engine` process outlives the grace period.
- No `.bea-*.tmp` file is left.
- Kill then retry ends with exactly one note.
- SIGTERM and SIGINT behave as they do today.

A real-command regression test kills by PID and checks the hash after a
delay. Only macOS and the checkout were exercised.

Addendum (CLI QA r80, 2026-10-14): related gap for captured natives.
`capture_native` (`cli/src/cli/engine/launch.py:265-277`) forwards no
signals. When the frontend gets SIGTERM or SIGHUP (and exits 143/129), a
`treeify` child that is blocked without writing (for example on a FIFO
input) keeps running. A child that writes dies of SIGPIPE soon after.
Reproduced twice by the hunter. The 435 and 418 hangs leave orphaned
engines in the same way when the frontend is killed.

---

**Resolved 2026-10-14** — `stopping.install()` (`cli/src/bea_engine/stopping.py`) records the engine's parent PID on POSIX and starts a watcher thread. When the engine is re-parented, the watcher sends the engine SIGTERM, which runs the existing handler: staged copies are removed, and a load in progress exits at once. `stopping.check()`, called right before every commit, also refuses once the parent has changed, even if the signal has not been handled yet. The separate session is kept. On the 50,000-transaction fixture, `kill -9` at 1.5 s and at 2.5 s left the hash unchanged at +10 s, with no engine and no `.bea-*.tmp` left. Kill at 2.0 s followed by a retry ended with exactly one note. SIGTERM still exits 143 with no note, and a plain write still succeeds. USAGE's staged-write paragraph says so. `cli/tests/test_engine_orphan_no_late_write.py` pauses validation with a plugin barrier, SIGKILLs the frontend by PID and checks that the ledger, the candidate and the helper are all gone; it fails with the fix reverted (the orphan wrote the note). The addendum (`capture_native` children outliving a SIGTERMed frontend) concerns read-only upstream tools, not this write path; it is filed separately as [466](../466.md). Only macOS was exercised. `make check-all` passed. Shipped in `448f6c6b` (`cli`).
