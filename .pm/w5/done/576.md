# A ledger with a managed price include never uses the load cache: every read re-parses the whole ledger (3.8 s each time at 60k transactions, against 1.1 s cached without the include)

**Minor · cli · 30–45m · A1.** Real CLI QA, 2026-10-16, HEAD `3514cc17`, checkout `bea 0.3.1`, macOS 26.5.1.
USAGE says the load cache is "a full copy of the ledger, written once a load
has taken a second", with no exception for managed includes; ADR018 names
none either. The managed-include load stages the root under a new random
shadow name each time. Beancount keys its cache on that path, so no read ever
hits it, and cleanup removes what was written. Ledgers that use
Beancount.io's live prices, which the CLI promotes, pay the full parse on
every command. No product fix implemented.

A synthetic ledger of ~60,000 transactions plus `include
"https://beancount.io/prices/BTC-USD"` (signed out, `--offline`).

```sh
bea -f /abs/main.bean --offline balance --allow-errors    # run three times
```

Actual: 3.80 s, 3.78 s, 3.84 s; `$XDG_CACHE_HOME/bea/load-cache/` stays
empty. The same ledger without the include takes 1.16 s, then 1.12 s from the
cache. At 300k transactions: ~19 s every run against 5.5 s cached.

Expected: the second read is served from a cache, invalidated by the ledger's
files and the feed revisions in use.

Cause: `_load_with_sources` (`cli/src/bea_engine/managed_load.py`, around
`:300-420`) calls `loader.load_file` on a fresh `_shadow` copy each time.

Fix: give the effective load a cache keyed on the real root, the snapshot's
file stats and the feed revisions (or stable shadow names per ledger, with
the cache file kept out of the cleanup).

Dedupe: searched `load cache` with managed and `every read`; w1/080 and w3/390
concern other leaks.

Acceptance: the second `balance` on the fixture is served from a cache (a test
counts parses), and a feed refresh or file edit invalidates it.

---

**Resolved 2026-10-17** — Shipped in `523a46f4` (`cli`). `_load_with_sources` (`cli/src/bea_engine/managed_load.py`) now keeps its own load cache beside Beancount's, under the private load-cache directory with a `.managed` suffix. It is keyed on a fingerprint of:
- the snapshot's file stats;
- each feed's served revision and failure cause;
- the effective text each feed contributed, by the canonical path entries carry; offline stand-in names are remapped.

The cache is stored after a load past Beancount's one-second threshold. It is not used for write candidates, and not stored when a file changed during the load (w5/218) or an error type is plugin-defined. A hit is rejected when plugins resolve elsewhere (w5/326) or documents moved (w5/116), the same guards `_load_fresh` applies.

On the note's case, a 60,000-transaction ledger with `include "https://beancount.io/prices/BTC-USD"` read with `--offline balance`, the runs take 4.1 s, then 1.0 s and 1.1 s. USAGE mentions the `.managed` cache.

`tests/test_managed_load_cache.py` counts parses: the second read is served from the cache (fails without the fix), and an edited file or a refreshed feed revision parses again. `make check-all` passed.
