# One transfer is taken as the "other side" of every same-amount row within ±3 days, so a real deposit next to a transfer is a possible duplicate of it: `--duplicates skip` loses the deposit and `include` double-books the transfer (new with w5/600)

**Minor · cli · 15m · A1.** Real CLI QA, 2026-10-17, HEAD `5b305b485`, checkout `bea 0.3.1`, macOS 26.5.1. New with w5/600 (done).
IMPORTING (the w5/600 bullet) names `--duplicates skip` as the remedy for a
transfer's other side. A transfer has exactly one other side. No product fix
implemented.

`main.bean` opens `Assets:Checking`, `Assets:Savings` and `Expenses:Uncategorized`
(USD). Rules map "transfer to savings" to `Assets:Savings` and "transfer from
checking" to `Assets:Checking`.

1. Import `c.csv` (`2026-04-10,TRANSFER TO SAVINGS,-200.00`) into
   `Assets:Checking` with `--apply`.
2. Preview `s.csv` for `Assets:Savings`: `2026-04-10,TRANSFER FROM
   CHECKING,200.00` and `2026-04-11,ZELLE FROM MOM,200.00`.

Actual: both savings rows are `possible_duplicate` with the same match
(`main.bean:6`). Row 2 reads `A transfer from Assets:Checking dated 1 day
earlier already posts 200.00 USD to Assets:Savings; this row may be its other
side…`. With `--apply --duplicates skip`, Savings stays at 200.00, so Mom's
200 is lost. With `--duplicates include`, the transfer is double-booked
(Checking −400, Savings 600, hunter's run).

Control: with only the transfer row in `s.csv`, the fix works as documented.

Expected: Checking −200 and Savings 400. Each counterpart pairs with one row
(nearest date first, same day preferred), and later same-amount rows get the
normal rules.

Cause: `_transfer_counterpart` (`cli/src/bea_engine/importing.py:1271`) returns
the latest counterpart for every row, and nothing marks it as paired within
the batch. Because this rule ignores descriptions, it catches far more than
the twin rule.

Fix: pair counterparts one-to-one within the batch.

Dedupe: w5/600 (done) is the parent.

Acceptance: `--duplicates skip` ends at Savings 400. A test pins it.

---

**Resolved 2026-10-20** — a counterpart transfer now has one other side. `_counterpart_row` picks, over every row of the import whose source amounts agree and that falls within the ±3-day window, the one dated nearest the transfer (same day first, the earlier row on a tie), whatever the row order. `_transfer_counterpart` offers a row only transfers it pairs with, nearest first. In the fixture, `TRANSFER FROM CHECKING` stays a possible duplicate and `ZELLE FROM MOM` is new, so `--apply --duplicates skip` leaves Checking at −200.00 and Savings at 400.00. IMPORTING's transfer bullet says so. `tests/test_import_transfer_counterpart_one_side.py` pins it with the deposit row before and after the transfer row (both fail at HEAD).
