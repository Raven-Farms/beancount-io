# Preset init validates the currency after its prompts: an unsupported answer exits instead of retrying, and an unsupported flag still asks for a date

**Minor · cli · 20–30m · A1/A2.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `2a172eaf7`, Darwin 25.5.0 arm64; frontend Python 3.13.3.
Actual PTY subprocesses, isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`, CI unset.
No product fix implemented.

From a disposable directory, with new targets:

1. Run `bea init /abs/a --preset personal@1 --date 2024-02-01`. At
   `Operating currency [USD]:`, answer `BTC`. Actual: exit 2,
   `Unsupported operating currency 'BTC' for a preset ledger.` The currency
   question never retries; a queued `USD` correction is never consumed.
2. Run `bea init /abs/b --preset personal@1 --currency BTC`. Actual: it
   first asks `Earliest date you will record …`; after answering
   `2024-02-01`, it exits 2 with the same currency refusal. That date answer
   had no chance to produce a ledger.

Both sequences reproduced twice in fresh PTYs, without timeouts. No target
ledger is created. Controls: answer `USD` to the first command's currency
question and creation succeeds; legacy init with no preset and explicit
`--currency BTC` still succeeds, as intended for custom Beancount symbols.
A separate PTY legacy-init journey retries invalid syntax, date and amount
answers while retaining earlier valid answers.

Expected: preset input is checked against its supported-currency catalog
at the input boundary. An invalid interactive answer retries the same
question; an explicitly unsupported `--currency` fails before unrelated
questions. `cli/docs/USAGE.md:507` promises invalid answers re-prompt, and
w5/588/813 established that invalid options are checked before prompting.
Keep legacy init's broader currency-symbol support.

Cause: `cli/src/cli/commands/init.py:231–235` validates explicit currency
only with `_currency`'s Beancount grammar; its interactive `value_proc` at
:267 uses that same grammar. Preset ISO-currency membership is checked
only after the prompts, by
`cli/src/bea_engine/initiating.py:219–220` (`answer_preset`). `BTC` is valid
grammar, so it reaches that late refusal. This affects local catalog
presets, not legacy init.

Fix: make frontend currency validation aware of whether a preset is
selected, reading the existing package-local supported-currency catalog.
Use it both before prompts for explicit options and as the currency
question's retry validator; keep engine validation as a backstop.

Dedupe: searched all board states and open/blocked milestone scopes for
preset currency/prompt failures. w3/m53/t004 (`1ba20bffa`) introduced the
split validation; w5/588/813 fixed earlier legacy-init prompt ordering,
not this preset-only membership check. No open overlap or later repair.

Acceptance: BTC→USD retries and succeeds in the same preset-init PTY;
explicit BTC is refused without any question; USD preset and custom-symbol
legacy controls succeed. Add meaningful PTY coverage. Windows/Linux and
repaired behavior remain unverified. Sanitized full terminal transcripts:
`.tmp/qa-2026-10-20-cli-loop-d3c5ebec/captures/pty-preset-*.json`, with
the `legacy-btc-control.json` and `pty-init.json` controls alongside them.
The public terminal steps above reproduce the defect independently.

---

**Resolved 2026-10-22** — `bea init --preset` checks the currency against the setup catalog's supported list where it is entered: an unsupported `--currency` is refused before any question, and an unsupported prompt answer retries the question. Legacy init keeps accepting any Beancount symbol. PTY tests in `cli/tests/test_init_preset_currency_prompt.py` fail without the fix; shipped in the commit that moves this note (`cli`).
