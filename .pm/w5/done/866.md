# A plugin that normalizes payee or narration disables import dedupe: importing the identical CSV twice writes the same payment twice, exit 0 (regression from w5/662)

**Major · cli · 25–40m · A1.** Real CLI QA, 2026-10-18, HEAD `e1bf4ac4a`, checkout `bea 0.3.1`, macOS 26.5.1. Payee and narration variants each reproduced twice from pristine synthetic ledgers, with isolated `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, stdin closed and no TTY. No product fix implemented.

Create `main.bean`:

```beancount
option "operating_currency" "USD"
option "insert_pythonpath" "TRUE"
plugin "normalize_header"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized
```

Beside it, create inspected local plugin `normalize_header.py`:

```python
from beancount.core.data import Transaction
__plugins__ = ["normalize"]

def normalize(entries, options):
    return [entry._replace(payee="ACME") if isinstance(entry, Transaction)
            else entry for entry in entries], []
```

Create `bank.csv`:

```csv
Date,Payee,Description,Amount,Reference
2026-02-01,Acme Ltd,Original description,-10.00,BANK-123
```

Run the same command twice:

```sh
bea --json --file /abs/main.bean import /abs/bank.csv \
  --csv date=Date,amount=Amount,payee=Payee,narration=Description,id=Reference \
  --account Assets:Checking --apply --duplicates skip
bea --json --file /abs/main.bean query "SELECT count(*), sum(position) WHERE account = 'Assets:Checking'"
bea --file /abs/main.bean check
```

Actual: both imports exit 0, each with `written: 1`, `duplicates: 0`, and row status `new`. The ledger contains two identical source transactions, each carrying `bank_id: "BANK-123"` and `import-id: "bank:BANK-123"`. The fresh query gives count 2 and −20.00 USD, and check passes. Replacing the plugin's payee change with `entry._replace(narration="Cleaned description")` produces the same double-booking.

Control: a plugin that returns each transaction unchanged writes once, then reports `duplicates: 1`, `written: 0`, and preserves the ledger bytes on the second call; the query gives count 1 and −10.00 USD. The failing plugin does not create, delete, redate or change the amounts/IDs of transactions; it only normalizes a display header.

Additional verification: omitting `id=Reference` so the CLI writes its own `csv:sha256:...` ID also double-books under both normalizers; the unchanged-plugin control still skips. The original w5/662 forecast fixture holds: its January/February real payments both import as new, and a repeated import skips both. Keep that control while repairing this regression. The shared-location generated-fee case was not rerun in this QA batch.

Expected: a stable native ID on a transaction actually written in the ledger still deduplicates after a plugin changes its payee/narration. The same source payment is written once. IMPORTING says payee/narration edits do not change stable identity and exact IDs are skipped. Preserve w5/662's protection against forecast projections and generated fees.

Cause: w5/662 (`d4ff55a16`) changed import's existing-entry filter in `cli/src/bea_engine/importing.py:358` to require `entry_generated(..., require_declaration=True)` for every transaction. `_declares` in `cli/src/bea_engine/ledger/reader.py:189` compares the loaded transaction's payee/narration with the plugin-free source header. A normalizer makes that comparison false, so the real written transaction is removed before the native-ID index and all duplicate matching are built. `entry_generated`'s default listing behavior remains different. Both CSV and Python importers consume the filtered existing-entry index.

Fix: preserve stable identities of real source transactions independently of header transformations; a rewritten header alone must not classify that source transaction as newly synthesized. Keep genuinely generated forecast/fee entries out of the duplicate index, including shared source locations. Do not restore the old forecast false-duplicate behavior by merely removing the new guard.

Dedupe: searched all board states for plugin-normalized/rewritten payees/narrations and import dedupe, and scanned open milestone scopes. w5/662 (done) is the introducing fix; open w5/779 concerns different hashes emitted by customer migration references, not native IDs preserved in a local plugin. No open item covers this regression. Targeted `git log -S require_declaration=isinstance` points to `d4ff55a16`.

Acceptance: both normalization plugins write once and skip the exact re-import, with one payment and −10.00 USD after a fresh load, for native and generated content IDs. Forecast and generated-fee controls from w5/662 still import real payments correctly. Pin the ID cases with real import/apply/query journeys.

---

**Resolved 2026-10-20** — import's stable-ID index (native IDs, `import-id`, digests, transfer IDs) is built from every transaction on disk by date and location, so a written row whose payee or narration a plugin normalizes still deduplicates; the declared-header requirement from w5/662 now gates only the content matches (possible twins, transfer counterparts), so a forecast's rewritten same-date copy and a generated fee at a shared line still cannot hide a real payment. `tests/test_import_plugin_normalized_header.py` imports the identical export twice under payee and narration normalizers and an unchanged control, with a bank ID and a generated ID, checking one payment and −10.00 USD by query; the w5/662 forecast/fee tests still pass. IMPORTING says a stable ID survives a header rewrite. Gate note: `make check-all` had two load-induced timeouts in `test_price_source_limit.py` (load average ~70); the file passes in isolation. Shipped in `92a53e4e7` (`cli`)
