# A `{}` sale that booking splits across lots is still not matched to its booked twin: re-importing bea's own write exits 4 as a conflict, and a hand-entered FIFO sale is written twice (incomplete fix of w5/467)

**Major · cli · 20–30m · A1.** Real CLI QA, 2026-10-16, HEAD `b2de72a3`, checkout `bea 0.3.1`, macOS 26.5.1. Follow-up to w5/467 (done, `c077ac7f`).
w5/467 made an open-cost (`{}`) sale compare only the cost fields it states.
When booking reduces more than one lot, the ledger entry holds one posting
per lot. The importer's entry holds a single posting, and the leg
comparison needs a one-to-one match of identical units text. So the
note's own variants still fail whenever the sale spans lots, which is the
common case for a full or FIFO sale. No product fix implemented.

`main.bean` (STRICT, the default): the w5/467 header (opens for
`Assets:Broker:Cash`, `Assets:Broker:HOOL`, `Income:Gains`, `commodity HOOL`)
plus two buys, `10 HOOL {150 USD}` on 2026-01-10 and `10 HOOL {155 USD}` on
2026-01-20. The w5/467 importer, with `fitid = "SELL1"`, extracting `-20 HOOL
{} @ 160 USD`, `+3200 USD` and an empty `Income:Gains` leg.

```sh
bea -f /abs/main.bean import s.txt --apply     # run twice
```

Actual: the first run writes the sale (booked as `-10 HOOL {150 USD}` and `-10
HOOL {155 USD}`); the second, identical run exits 4 with `Row 1 (conflict):
Stable ID matches an entry with different transaction data.` With
`option "booking_method" "FIFO"`, three lots of 10 (150/155/158 USD) and a
hand-entered `-15 HOOL {} @ 160 USD` sale, the import reports `1 ready, 0 …
possible duplicates`, exits 0, writes a second sale, and HOOL falls from 15 to
0 with `bea check` passing.

Control: the single-lot variants of w5/467 pass; w5/349's 100/120 USD lots
still import as two rows.

Expected: IMPORTING.md, "an open cost compares only what it states": the
split booking is the same row (exact duplicate under the shared ID, possible
duplicate without one).

Cause: `_legs` (`cli/src/bea_engine/importing.py:919`) makes one leg per source
posting; `_legs_agree` (`:933-949`) requires a one-to-one match with identical
units text (`-20 HOOL @ 160 USD` against two `-10 HOOL @ 160 USD`);
`_candidate_key` (`:1637`) and `_same_row` (`:1069`) inherit it.

Fix: when the incoming leg's cost is open, sum the ledger entry's source
postings for the same account, currency and price before comparing (and
compare the summed units).

Dedupe: searched `FIFO`, `split lots`, `across two lots`; w5/467 (done) is the
parent.

Acceptance: both commands above behave as w5/467's acceptance states (second
run an exact duplicate; the FIFO twin a possible duplicate). Tests pin both.

---

**Resolved 2026-10-17** — Shipped in `9ed4b93c` (`cli`).
- `_legs_agree` (`cli/src/bea_engine/importing.py`) now accepts, for an open-cost leg with no single match, the legs booking split it into (`_split_booking`): same currency and price, lots agreeing with what it states, units adding up to its own.
- The candidate key (`_amounts_key`) sums amounts by currency and price, so a split booking and the importer's single posting share a bucket.
- Both of the note's commands now behave as w5/467's acceptance states:
  - The second identical run of a `-20 HOOL {}` sale booked across the 150/155 USD lots, under FITID `SELL1`, is an exact duplicate.
  - The FIFO hand-entered `-15 HOOL {}` twin is a possible duplicate: exit 4, nothing written.
- A sale of a different quantity is still new. w5/349's two-row lots and w5/467's single-lot tests pass unchanged.
- IMPORTING documents it.
- `tests/test_import_open_cost_split_lots.py` pins all three; the two bug cases fail without the fix. `make check-all` passed.
