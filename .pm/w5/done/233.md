# Ctrl-C while the query shell loads the ledger drops a transaction, and the damaged load is cached so every later command fails

**Major · cli · 60–90m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
Pressing Ctrl-C while `bea query` is still loading a large ledger does not
cancel. The interrupt is swallowed inside the parser, one directive is
dropped, the shell opens and answers from 39,999 of 40,000 transactions,
and that result is saved to the load cache. Afterwards `bea check` and
every other command fail on the unchanged, valid ledger with a
`KeyboardInterrupt` "ledger error" until a ledger file changes. No product
fix implemented.

Generate disposable `/absolute/books/main.bean` (40,000 transactions):

```python
import datetime, pathlib, sys
d = pathlib.Path(sys.argv[1]); d.mkdir(parents=True)
out = ['option "operating_currency" "USD"', '2020-01-01 open Assets:Checking USD', '2020-01-01 open Expenses:Food USD']
start = datetime.date(2020, 1, 1)
for i in range(40000):
    out.append(f'{start + datetime.timedelta(days=i % 2000)} * "Shop {i % 97}" "item {i}"\n  Expenses:Food  1.00 USD\n  Assets:Checking\n')
(d / "main.bean").write_text("\n".join(out) + "\n")
```

Run on a real PTY (stdin, stdout and stderr all the terminal) with the
child's HOME set to a disposable directory (the shell keeps its history
under `$HOME/.config/beanquery/`), XDG_DATA_HOME pointing at the installed
engine, isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1,
`TERM=dumb`, no inherited BEA_FILE/BEA_TOKEN/CI. No `.main.bean.picklecache` at the start.

1. Start `bea -f /absolute/books/main.bean query`.
2. Send Ctrl-C 0.4–0.5 s after launch, while the ledger is parsing.
3. At the prompt type `SELECT count(*) AS n, sum(number) AS s WHERE
   account = 'Expenses:Food';` then `.exit`.
4. In fresh processes run `bea -f /absolute/books/main.bean check` and the
   same query one-shot.

Actual (both delays tried, 0.4 s and 0.5 s): the shell prints a line ending
`beancount/parser/grammar.py:474: KeyboardInterrupt` (`:276` in the other
run), opens, and answers `39999  39999.00`; `.exit` gives exit 0 and
`.main.bean.picklecache` exists. Then `bea check` exits 1 and the one-shot
query exits 1, both reporting the `KeyboardInterrupt` line as a ledger
error. A worker saw the same from `.reload` after an edit, stock
`bean-check` failing on the same cache, and `--allow-errors` answering
39,999; appending a newline to the ledger cleared it.

Control: without Ctrl-C the shell answers `40000  40000.00` and later
commands exit 0. With Ctrl-C at 0.6 s on this machine, after the parse, the
process simply exits; a worker saw exit 130 there.

Expected: `docs/USAGE.md`: "In the shell, `Ctrl-C` cancels the current line
and returns to `beanquery>`". A cancel must never yield a partial ledger
that answers queries, and must never be persisted.

Cause: `cli/src/bea_engine/main.py:526` switches SIGINT to Python's default
handler (`cli/src/bea_engine/stopping.py:43-47`) before the shell loads the
ledger (`:531`), so the load-time guard at
`cli/src/bea_engine/managed_load.py:243` does nothing. Beancount's parser
catches the `KeyboardInterrupt` raised inside a callback, records it as an
error, drops that directive and continues; the loader then writes the
cache. `.reload` (`cli/src/bea_engine/query.py:613-621`) runs under the
same handler.

Fix: during every load in an interactive session (startup and `.reload`,
for `shell` and `source-shell`) defer SIGINT to a flag; if it fired,
discard the load and any cache it wrote, exit 130 at startup or keep the
previous data on `.reload`. Never store a result whose errors include a
captured `KeyboardInterrupt`. No dependency or API change.

Blast radius: interactive `bea query` and `bea query --source`, at startup
and on `.reload`, on any ledger slow enough to interrupt; the poisoned
cache is then trusted by every local command and by stock tools.

Dedupe: board search for `KeyboardInterrupt`, `picklecache` and
"interrupted" finds w1/done/074 (signal during a write's load, whose guard
the shell bypasses), w5/218 and w5/220 (other stale-cache triggers) and
w5/106 (`.reload` that raises); none covers Ctrl-C in the shell.

Acceptance: Ctrl-C at any moment during shell startup or `.reload` either
exits 130 or returns to a prompt with complete data; afterwards `bea check`
exits 0 and the count is 40,000; no cache containing a `KeyboardInterrupt`
error is ever written. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — The interactive query shell now holds Ctrl-C while a ledger load is running instead of letting Python raise it inside Beancount's parser, which swallowed it, dropped a directive and let the damaged result be cached: `cli/src/bea_engine/stopping.py` gains a `deferring_interrupt()` guard, and `cli/src/bea_engine/query.py` applies it to the startup load and `.reload` of both the `--file` and `--source` shells. The interrupt is raised once the load has completed, so a startup Ctrl-C exits 130 without opening a prompt and a `.reload` prints `(interrupted)` and returns to the prompt; `cli/docs/USAGE.md` states this. The regression test `cli/tests/test_query_shell_interrupted_load.py` delivers SIGINT from inside the parser's transaction callback on a real PTY, with Beancount's cache threshold lowered so the load is cached, and asserts the exit status or complete count plus a clean `bea check` and one-shot query afterwards; all four cases (startup and reload, for both shells) fail with the fix reverted. Deviation from the note: because the parser no longer sees the interrupt, the load and any cache it writes are complete, so no cache is discarded; on a `--file` reload the previous data is kept, while a `--source` reload attaches the complete new data before returning to the prompt. The note's 40,000-transaction reproduction was also rerun with a real SIGINT at 0.3 to 1.3 seconds and gave exit 130, a passing check and a count of 40,000 every time. Only macOS was exercised. `make check-all` passed. Shipped in `d302c7f9` (`cli`).
