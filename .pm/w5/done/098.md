# `add transaction` fills a missing commodity on a cost or priced posting with the operating currency

**Minor (input slip with a silent wrong lot; owner call) · cli · 20–30m ·
A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS. A posting that gives a cost or a price but forgets the commodity —
`3 {80 USD}` — is completed with the operating currency and written as
`3 USD {80 USD}`, with exit 0 and a passing `bea check`. The books then
show three dollars held at eighty dollars each. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Assets:Brokerage
2026-01-01 open Equity:Opening

2026-01-02 * "Opening"
  Assets:Checking  10000.00 USD
  Equity:Opening

2026-01-03 * "Buy HOOL"
  Assets:Brokerage  10 HOOL {100.00 USD}
  Assets:Checking
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bea -f /absolute/books/main.bean add transaction "Buy more" --date 2026-02-01 -p "Assets:Brokerage 3 {80 USD}" -p "Assets:Checking"
```

Actual: exit 0, `Added 1 transaction`, and the file gains
`Assets:Brokerage  3 USD {80 USD}`. `bea check` exits 0; 240 USD leaves
`Assets:Checking`. `-p "Assets:Brokerage 100 @ 1.08 USD"` likewise writes
`100 USD @ 1.08 USD`. Repeated twice.

Control: `-p "Assets:Brokerage 3 HOOL {80 USD}"` writes the intended lot.
Bulk input refuses the same shorthand (`"amount": "3 {80 USD}"`).

Expected: `docs/USAGE.md` describes the currency default for "a numbered
posting [that] omits its currency" and says "Ambiguous currencies require an
explicit symbol". A commodity held at a cost in itself, or priced in itself,
is never what was meant; refuse with the existing ambiguous-currency error
and the form to type.

Cause: `cli/src/bea_engine/ledger/adding.py:687-696` replaces a missing
units currency with the account's sole currency or the operating currency
without looking at whether the posting has a cost or a price.

Fix: do not default the units commodity when the posting carries a cost or
price; refuse naming the posting. Plain amounts keep today's default. No
dependency or API change.

Dedupe: board search for missing commodities on cost postings and the
currency default finds w3/421 (import currency resolution) and w3/268 (a bare
`@`); neither covers this.

Acceptance: both fixture commands exit 2 with the file unchanged; the control
and plain `-p "Expenses:Food 5"` still work. Only macOS and the checkout
were exercised.

---

**Resolved 2026-10-12** — `add transaction` refuses, with exit 2 and the file unchanged, a posting whose missing commodity would default to the currency of its own cost or price: `3 {80 USD}` and `100 @ 1.08 USD` name the posting and the form to type instead of being written as `3 USD {80 USD}` and `100 USD @ 1.08 USD`. `docs/USAGE.md` Adding directives states the rule. Shipped in `5a0571e7` (`cli`).

Narrower than the note's fix, deliberately: the note says never to default a commodity on a cost or priced posting, but its stated reason is that "a commodity held at a cost in itself, or priced in itself, is never what was meant". An account opened for a single commodity (`open Assets:Hool HOOL`) with `3 {80 USD}` defaults to HOOL, which is a sensible lot and not that mistake, so that default is kept. If the owner prefers the blanket refusal, it is a one-condition change.

Real-command regression tests cover per-unit and total cost, per-unit and total price, and a sole-currency account whose default is the rate's currency (all refused, ledger unchanged), then the commodity written out, a single-commodity account supplying it, and a plain amount keeping the currency default. Five fail with the fix reverted. `make check-all` passed. Only macOS was exercised.
