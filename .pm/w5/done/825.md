# A stop (SIGTERM/SIGINT/SIGHUP) 0–20 ms after a write commits still kills bea silently, almost every time, and the retry records the entry twice; a multi-file `format -i` stopped after its first replace keeps rewriting for 5 s, then dies silently (regression of w5/606)

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-17, HEAD `2f69b1461`, checkout `bea 0.3.1`, macOS 26.5.1. A harness polls the target file and signals the `bea` PID when it is replaced. Regression of w5/606 (done, `c55256462`).
USAGE:1016-1019 says a stop "that arrives during the replace or after it never
undoes the write or silences it. bea prints the write's normal result, adds
`Stopped (SIGTERM) after the write had completed; its result stands.` … and
exits 0". The w5/606 acceptance says "never a silent death". Supervisors,
`timeout` and agent harnesses send exactly these signals. No product fix
implemented.

1. **Just after the commit.** The ledger opens five accounts and holds 40
   transactions. SIGTERM is sent 5 ms after `main.bean`'s inode changes,
   during `bea -f main.bean add transaction Coffee --date 2026-01-05 -p
   "Expenses:Food 3 USD" -p Assets:Checking`.
   - All five runs end with rc −15 and empty stdout and stderr. The ledger
     holds the Coffee entry, and the retry writes a second one.
   - In the hunter's runs, SIGHUP and SIGINT behave the same (12/12, 11/12),
     and so do `add transactions`, `import --apply`, `format -i` and `--json`.
     From 15–30 ms "Added…" prints but rc is still −15; at 50 ms or more it is
     correct.
2. **Multi-file `format -i`.** With 10 misaligned 20k-entry ledgers in one
   directory and SIGTERM sent when the first is replaced, `bea --json format -i
   .` ends with rc −15 and no output after 10 s. 5 of the 10 files are
   rewritten and nothing reports them. In the hunter's run, 10 of 30 files
   were rewritten after exactly 5 s.

Control: the commit's own test (a stop held inside `os.replace`) reports
correctly, and a stop before the commit leaves the ledger unchanged.

Expected: case 1 prints the result plus the "Stopped … its result stands"
line and exits 0. Case 2 stops before the next file and reports `formatted`
and `not_attempted` (or finishes and reports).

Cause:
- The engine restores the default stop handlers right after `app()` returns
  (`cli/src/bea_engine/__main__.py`, around `:17-21`). Interpreter shutdown
  then runs under SIG_DFL for tens of ms, and a forwarded stop kills an
  engine that has already answered `ok: true`.
- `_answered_success` (`cli/src/cli/engine/launch.py:589`) requires
  `returncode == 0`, so `_run_helper` treats the write as uncommitted and
  `_die_by` (`:599`) dies silently.
- For case 2, the committed flag in `cli/src/bea_engine/stopping.py` makes later
  stops ignored, so the file loop continues until the frontend's 5 s grace
  (`_CLEANUP_GRACE_SECONDS`, `launch.py:496`) ends in SIGKILL.

Fix:
- Treat an `ok: true` envelope as committed whatever the exit status.
- Keep the note-only handler installed until the process exits.
- In multi-file `format -i`, honour a stop before each later file and report
  the partial result.
- A writing child killed after a forwarded stop with no envelope should get
  the exit-4 "may have completed" result, not a silent death.
- Pin it with a shim that delays after `app()` returns.

Dedupe: w5/606 (done) is the parent; w5/676 (open) covers `init`/`price export`
not being marked as writes.

Acceptance: case 1 never dies silently at any delay. Case 2 reports which
files were formatted.

---

**Resolved 2026-10-20** — four windows closed. (1) The engine prints its envelope with `flush=True` and, once `app()` returns, sets the stop signals to `SIG_IGN` instead of restoring the default disposition, so a forwarded stop during interpreter shutdown no longer kills an engine that answered. (2) The frontend's `_reports_commit` treats an `ok: true` envelope, or a failure whose result reports what was written (`written`, or a stopped `format -i`'s `formatted`), as committed whatever the exit status. (3) A `bea` process (`cli.entry` and `python -m cli.main` call `own_process()`) keeps holding stops after a committed write until it exits, then ignores them from the last exit handler on; it used to hand the handlers back when the command closed, so a stop during its own shutdown ended it by the signal after "Added…" had printed. That is the 15–30 ms case, which a stress run of 36 stops at 0.02–0.8 s reproduced once before this part and not after. An embedding `CliRunner` still gets its handlers back. (4) Multi-file `format -i` checks `stopping.requested()` before each file and ends with exit 1, "Stopped (SIGTERM) after N file(s) formatted; M file(s) not attempted", listing both. A writer SIGKILLed after the 5 s grace period with no envelope is now the exit-4 "outcome is unknown" result rather than a silent death; a child that died of the stop itself before installing its handlers still ends bea by the signal. USAGE's stop paragraph covers the last two. `tests/test_stop_after_answer_never_silent.py` holds the engine after it answered (SIGTERM, SIGHUP, SIGINT, `--json`), the frontend at its own exit, `format -i` across four files, and a writer past the grace period; 7 of its 8 cases fail at HEAD, and the SIGINT one is the control. Gate note: gated as one stack with w5/824–822 (one `make check-all`, 9727 passed; each item shipped as its own commit). An earlier gate of this item alone caught a regression — every stopped writer with a negative status was reported as exit 4, including one stopped before its handlers were installed — which was fixed before this gate. This gate's only failures were the known load-induced managed-price timeouts in `test_price_source_limit.py`, which pass in isolation. Shipped in `cf3aa1aa1` (`cli`)
