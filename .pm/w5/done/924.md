# Refuse mismatched lari, tenge, tugrik, manat and guarani symbols in CSV amounts

**Major · cli · 20–35m · A1.** CSV import silently discards several currency
symbols and books their amounts as another commodity, despite the existing
symbol-contradiction guard. `-₾4.50` applied to a USD account becomes
`-4.50 USD`, exit 0, check clean. The same journey with `€` is correctly
refused. No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `5fe50c5d3`, checkout `bea 0.3.1`, macOS
26.5.1 arm64, frontend Python 3.13.3, existing managed Python 3.12 engine.
Fresh subprocesses, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited
`BEA_FILE`/`BEA_TOKEN`. Reproduced twice from pristine synthetic fixtures.

Create disposable `/abs/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Local GEL
2024-01-01 open Expenses:Food
```

Create `bank.csv`:

```csv
Date,Description,Amount,Reference
2024-02-01,Coffee,-₾4.50,qa-1
```

From `/abs/books`, with the isolated child environment above:

```sh
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --csv date=Date,narration=Description,amount=Amount,id=Reference --account Assets:Cash --default-account Expenses:Food
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --csv date=Date,narration=Description,amount=Amount,id=Reference --account Assets:Cash --default-account Expenses:Food --apply
bea --json -f /abs/books/main.bean query "SELECT number,currency WHERE account='Assets:Cash'"
bea --json -f /abs/books/main.bean check
```

Actual: every command exits 0. Preview calls the row ready and renders
`-4.50 USD`; apply writes one transaction in USD. Fresh BQL returns
`[["-4.50", "USD"]]`, and check passes. The authored transaction no longer
contains the lari sign, so the file itself looks like an ordinary USD purchase.
Preview preserves ledger bytes and the original CSV stays unchanged.

Expected: refuse the contradictory symbol at preview/apply, exit 2, naming the
row, symbol and resolved currency, leaving the ledger unchanged. The symbol
identifies GEL, not USD. Choosing the proper local account should import GEL;
do not infer currency, convert money or widen the USD account automatically.
IMPORTING promises this refusal for a symbol naming one commodity, and the
same rule already works for `€`/EUR and other entries in the guard's table.

Verified symbol/code pairs: **₾ GEL, ₸ KZT, ₮ MNT, ₼ AZN, ₲ PYG**. Each
appears under only that code in the symbol/narrow-symbol fields of the current
[Unicode CLDR currency data](https://raw.githubusercontent.com/unicode-org/cldr-json/main/cldr-json/cldr-numbers-full/main/en/currencies.json),
checked 2026-10-21. This is a bounded extension of the existing verified table,
not an ISO-registry requirement for arbitrary Beancount commodities.

Controls and scope:

- Twenty-four fresh journeys: two repetitions × six symbols (these five plus
  `€`) × USD/matching-currency accounts. All ten mismatched cases for the five
  missing symbols write USD at exit 0; all ten matching-account cases write
  the correct commodity. The two EUR/USD mismatches refuse at exit 2 with
  unchanged ledgers, while both matching EUR cases succeed. Fresh checks pass
  and source CSVs remain byte-identical throughout.
- Twelve additional human-output journeys, twice each across a currency column,
  debit pair, credit pair, `direction=Type`, `sign=ledger`, and constant
  `currency=USD`, reproduce the lari mismatch. These use a USD/GEL account so
  both commodities are otherwise legal; the contradiction is in the source
  symbol, not an account-open validation error. Signs remain correct, but the
  posted commodity is USD instead of refusing the mismatched row.
- Eight existing-policy controls (twice each) still accept `£` for GIP and
  `₩` for KPW, plus the documented ambiguous `$`/`¥` cases. Preserve these
  multi-currency exceptions rather than turning every symbol into one code.

Cause: `cli/src/bea_engine/csv_mapper.py:_split_amount_sign` (:170–214)
strips leading/trailing Unicode `Sc` characters. `_cell_symbol_currency` (:138–153) only
recognizes `_SYMBOL_CURRENCIES` (:122–135), which omits the five verified
symbols. It returns `None`, so `_check_cell_symbols` (:1548–1578) skips the
contradiction check. `CsvImporter.extract` calls that guard at :1743 for every
amount mode after resolving currency. The parser then supplies the plain
number to normal balanced postings, explaining why check cannot detect the
lost source currency. This is in the CSV engine path; native explicit-commodity
postings and Python importers are outside this symbol-stripping path.

Fix: include the five verified symbol/code associations in the existing
contradiction guard and pin mismatched/matching real imports across amount
modes. Keep currency resolution order, exact numbers, arbitrary commodity
support, the documented ambiguous symbols and w5/757's shared `£`/`₩`
associations. No new dependency, currency auto-inference or backend/API change
needed.

Dedupe: searched all board states for these glyphs/codes and currency-symbol
contradictions; scanned active milestone scopes. Completed w3/421 and
w3/m49/t004 introduced the guard but exercised `€` and its initial small
symbol table. Completed w5/757 (`dabfdb4ce`) repairs shared pound/won meanings,
not these missing table entries. w5/907 is a minor-unit advisory, unrelated to
source currency being silently discarded. No overlapping open repair or later
fix found.

Acceptance: the public mismatch refuses at preview/apply with zero writes;
choosing `Assets:Local` writes −4.50 GEL and passes fresh query/check. All five
symbols reject contradictory resolved currencies and accept matching ones;
currency column, pair, direction, ledger-sign and constant modes agree. Existing
ambiguous-symbol controls remain valid. Refused runs preserve ledger and CSV
bytes. Only macOS/checkout tested; repaired behavior unverified.
