# `bea check` fails with a traceback on the bundled `fava.plugins.*` plugins while `--json check` says valid

**Major · cli · 45m · A1/A2.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS. A ledger that uses one of the Fava
plugins `bea` bundles and documents — forecast, link_documents — fails
plain `bea check`, the documented CI gate, with a raw `ModuleNotFoundError`
traceback, while `bea --json check`, reports and queries all load the same
ledger successfully. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
plugin "fava.plugins.forecast"

2024-01-01 open Assets:Checking USD
2024-01-01 open Equity:Opening
2024-01-01 open Expenses:Rent

2024-01-01 * "Opening balance"
  Assets:Checking  10000.00 USD
  Equity:Opening

2024-01-15 # "Rent [MONTHLY REPEAT 3 TIMES]"
  Expenses:Rent  1000.00 USD
  Assets:Checking
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, and an absolute `--file`.

```sh
bea -f /absolute/books/main.bean check
bea --json -f /absolute/books/main.bean check
```

Actual: the first exits 1 with about twenty lines beginning `<load>:0: Error
importing "fava.plugins.forecast": Traceback (most recent call last):` and
ending `ModuleNotFoundError: No module named 'fava'`. The second exits 0
with `{"valid": true, "errors": []}`. `bea --strict … report
income-statement -i yearly` exits 0 and shows Rent 3,000.00, so the plugin
ran. `plugin "fava.plugins.link_documents"` splits the same way. Repeated
twice.

Control: with `plugin "beancount.plugins.auto_accounts"` instead, plain
`bea check` exits 0.

Expected: human and JSON `check` give the same verdict; `docs/USAGE.md`
presents `--json check` as the same check in an envelope and names "the
forecast and amortize plugins" among those `list` understands, and the test
suite loads `fava.plugins.forecast` ledgers. A ledger migrated from Fava
should pass the gate that every other command already agrees it passes.

Cause: `cli/src/cli/commands/check.py:64` runs upstream's executable through
`launch.run_native("bean-check", …)` with no extra environment.
`cli/src/cli/engine/launch.py:111-122` starts it without the helper source
root on `PYTHONPATH`, which `:507-524` adds only for `bea_engine`
children. The vendored `fava` package is importable only there.

Fix: make native `bean-check` resolve the same plugin modules as the helper
load — either give `run_native` the helper source root, or route a closure
that names `fava.plugins.*` through the helper check, as the existing
compatibility probe already does for BOM, non-NFC and URL-include closures.
Check the other `run_native` callers that load a ledger (`bean-doctor`
operations) for the same gap. No dependency or API change.

Dedupe: board search for `fava.plugins`, `No module named`, and plugin
import failures finds w1/113 (`--on-disk` marking of plugin copies), w3/359
(traceback verbosity for genuinely missing plugins) and w1/122 (a missing
`beancount` module); none covers native-versus-helper plugin resolution.

Acceptance: plain and JSON `check` both exit 0 on the fixture and on a
`link_documents` ledger; a genuinely missing plugin still fails in both
modes; `doctor` operations on the fixture load the plugin. Reproduced on
this checkout with the managed engine; a PyPI or Homebrew install is
unverified.

---

**Resolved 2026-10-12** — Upstream executables started by `bea` (`bean-check`, `bean-doctor` and the other native tools) now get the helper's bundled source root on `PYTHONPATH`, appended after any inherited value, so a ledger's `fava.plugins.*` plugins resolve as they do in the helper load. On the fixture against the managed engine, plain and JSON `check` both exit 0, `doctor print-options`, `missing-open`, `roundtrip` and `context` load the plugin, and a plugin that does not exist still fails in both modes. Managed-price settings stay helper-only. Shipped in `4397aa58` (`cli`).

Tests: a stand-in executable whose interpreter sees no site directory — as a managed engine does not see a checkout — must be able to find `fava` through both `run_native` and `capture_native`, with and without an inherited `PYTHONPATH`; the search-path order and the absence of the price credential are pinned; and real-command tests cover plain/JSON `check` on forecast and link_documents ledgers, two `doctor` operations, and a missing plugin. The four launcher tests fail with the fix reverted. The real-command tests pass either way in the suite, because the test engine is the checkout interpreter where `fava` is already importable; the defect itself was reproduced and confirmed fixed by hand against the managed engine on this machine.

`make check-all` passed on the second run. The first run had one unrelated failure, `test_acl_xattrs_and_flags_survive_on_macos[format]`: `ls -le` printed the `nobody` user's UUID instead of its name under parallel load, while the ACL it checks was intact; it passed three times in isolation and in the rerun. A PyPI or Homebrew install is unverified, and only macOS was exercised.
