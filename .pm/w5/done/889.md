# Preset creation with a known opening on `0001-01-01` returns a raw `OverflowError` instead of explaining the missing prior day

**Minor · cli · 15–25m · A1/A2.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `71e462f50`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
Reproduced twice in human and JSON modes from pristine fixtures; controls
repeated twice. No product fix implemented.

With cwd `/abs/case`, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, and no inherited
`BEA_FILE`/`BEA_TOKEN`, where `nested/` does not yet exist:

```sh
bea --json --no-input init /abs/case/nested/books --preset personal@1 --currency USD --date 0001-01-01 --opening-balance 'Assets:Cash 100'
```

Actual: exit **1**, empty stdout, one stderr object:

```json
{"error":{"category":"validation","message":"OverflowError: date value out of range. Pass --debug before the command for a traceback.","exit_code":1}}
```

Without `--json`, the same exit 1 prints the same class name and traceback
hint. It names neither the conflicting inputs nor a usable date. `nested/`
and the target file remain absent; no data-loss or cleanup defect is claimed.
`--debug` traces the failure to the prior-day calculation in `answer_preset`.

Controls, each twice in fresh directories:

- Change only `--date` to `0001-01-02`: init exits 0, opens accounts and
  writes the opening transaction on January 1, with the boundary assertion
  on January 2; a fresh `bea --json --file <created-main.bean> check` passes.
- Keep January 1 and omit the opening balance: preset init and check pass.
- Omit `--preset`, keep January 1, and use legacy init's valid account
  `--opening-balance 'Assets:Checking 100'`: init and check pass.

A known preset opening on `9999-12-31` also created a valid checked ledger
in a separate boundary probe. The problem is the unavailable day before
the minimum date, not rejection of all early or boundary dates.

Expected: reject this unsupported input combination with usage exit 2,
naming `--date` and the known opening balance. Explain that catalog openings
are recorded on the day before the history start and that a known opening
therefore needs `0001-01-02` or later; an unknown opening can still start on
January 1. Do not invent year-zero directives, move the opening silently,
or change legacy init's same-day behavior. This follows ADR021's opening
boundary rule and the CLI exit table's category for bad arguments.

Cause: `cli/src/bea_engine/initiating.py:230` computes
`day - datetime.timedelta(days=1)` whenever the balances map is nonempty,
after accepting the date with `date.fromisoformat` but without checking
this bound. The same subtraction appears at :249 when rendering the
opening transaction. The helper protocol catches the unexpected exception
as a generic validation error (`protocol.py:166`). The only caller is the
preset branch in `bea_engine/main.py:502`, exposed by local `bea init`.

Fix: validate the previous-day requirement before either subtraction and
before any creation, returning the actionable usage refusal above. Preserve
unknown/known distinctions and successful controls; explicit-zero handling
remains separately tracked in w5/876. No dependency or API-adapter change
is needed for this local diagnostic fix.

Dedupe: searched all board states for preset/opening minimum dates,
`0001`, underflow and `OverflowError`, and reviewed open milestone scopes.
Completed w5/842 covers first-day reports/BQL, not setup; w3/m53/t004
(`1ba20bffa`) introduces this preset calculation. Open w4/m38 is backend
directive date validation, a different package/path. No overlapping open
item or later repair found in targeted history.

Acceptance: both output modes give the usage refusal with the prior-day
reason and correction, no traceback/class-name fallback and no new target
or parents. The three repeated controls still initialize checked ledgers.
Pin real CLI regression coverage. Other presets, zero-state behavior at
the bound, Windows/Linux and repaired behavior remain unverified. Evidence
is `.tmp/qa-2026-10-20-cli-loop-pass3-69d827bc/`, especially
`init-first-known-{1,2}-{json,human}/`, `init-first-control-*`,
`init-date-v2-last-known/` and matching `captures/init-first-*.json` and
`captures/init-date-v2-*.json`. Initial probes using an account not in the
personal preset were invalid fixtures and excluded before classification;
the public commands above use its supported `Assets:Cash`.

---

**Resolved 2026-10-22** — `init --preset` with a known (nonzero) opening on `0001-01-01` now refuses with usage exit 2 naming `--date` and the known opening, explaining the opening is recorded the day before and suggesting `0001-01-02` or later, before anything is created; an unknown or explicit-zero opening still starts on January 1. `cli/tests/test_init_preset_opening_minimum_date.py` covers JSON and human output plus the neighbouring controls and fails without the fix; shipped in the commit that moves this note (`cli`).
