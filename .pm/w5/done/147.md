# An invalid `fiscal-year-end` option is silently ignored, so `-t FY2026` reports the calendar year with exit 0

**Minor · cli · 30m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
A `fiscal-year-end` value that cannot be a date (`"06-31"`, `"6-30"`,
`"garbage"`) is dropped without a word. A fiscal-year filter then quietly
means the calendar year: the report exits 0 with different numbers, and
JSON says `ledger_valid: true`. The heading does print the period used. No
product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2020-01-01 custom "fava-option" "fiscal-year-end" "06-31"
2024-01-01 open Assets:Checking USD
2024-01-01 open Expenses:Food USD

2025-12-31 * "in FY2026"
  Expenses:Food  31.00 USD
  Assets:Checking

2026-10-01 * "in FY2027"
  Expenses:Food  10.00 USD
  Assets:Checking
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean check
bea -f main.bean report income-statement -t FY2026
bea --json -f main.bean report income-statement -t FY2026
```

Actual: `check` exits 0 silently. The report exits 0 with empty stderr:
`Income Statement — 2026-01-01 through 2026-12-31`, Expenses `10.00 USD`.
JSON has `"period": {"start": "2026-01-01", "end_exclusive":
"2027-01-01"}`, `"ledger_valid": true`, `"ledger_errors": []`.

Control: the same file with `"06-30"` prints `Income Statement —
2025-07-01 through 2026-06-30`, Expenses `31.00 USD`. A worker saw the same
silent fallback for `"6-30"`, `"02-30"` and `"garbage"`, and for
`-t fiscal_year` and `FY2026-Q1`.

Expected: `docs/USAGE.md` says "Reports run with loader errors also carry
`ledger_valid: false` and `ledger_errors` in JSON." The vendored Fava
ledger treats a bad option as a ledger error. The option error should be
surfaced, or a fiscal filter refused when the option did not parse.

Cause: `cli/src/fava/core/fava_options.py` collects the parse failure into
`fava_options_errors`, but `cli/src/bea_engine/report.py` builds its ledger
errors only from the loader's errors; nothing in `bea_engine` or `cli`
reads `fava_options_errors`.

Fix: in the report loader, append `fava_options_errors` to the ledger
errors under the same strict/lenient policy as loader errors; at minimum
refuse `FY…`/`fiscal_*` filters when the option failed to parse. No
dependency or API change.

Blast radius: `bea balance` and all four `bea report` commands. Every
malformed `fava-option` is swallowed the same way; only `fiscal-year-end`
changes numbers.

Dedupe: board search for `fiscal-year-end`, `fava_options_errors` and
`fava-option` finds w5/091 (`default-file` crash, which uses a valid
`"06-30"` as its control); nothing covers an invalid value.

Acceptance: the report on the `"06-31"` fixture either exits nonzero
naming the option, or exits 0 with a stderr warning and `ledger_valid:
false`; it never presents a calendar year for `FY2026` silently. The
`"06-30"` control is unchanged. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — The report loader in `cli/src/bea_engine/report.py` now refuses a fiscal time filter (`FY2026`, `FY2026-Q1`, `fiscal_year`, `fiscal_quarter`, alone or in a range) when the ledger's `fiscal-year-end` option failed to parse: `bea balance` and all four `bea report` commands exit 1 with a message naming the option and the `file:line` of the bad directive, in text and `--json`, instead of reporting the calendar year under the fiscal label. This is the note's "at minimum" fix, chosen over treating every malformed `fava-option` as a ledger error, so an unrelated or editor-only option still cannot block a report; the refusal also holds under `--allow-errors`, because the period itself is undefined. Calendar periods on the same ledger and a valid `"06-30"` option are unchanged, and `cli/docs/USAGE.md` now states the rule. `cli/tests/test_report_invalid_fiscal_year_end.py` covers the five commands, four fiscal spellings against three bad values, `--allow-errors`, and both controls; 18 of its 24 cases fail with the fix reverted. Other malformed `fava-option` values are still not surfaced, and `ledger_valid` is unchanged for them. Only macOS was exercised. `make check-all` passed. Shipped in `9c5cbe12` (`cli`).
