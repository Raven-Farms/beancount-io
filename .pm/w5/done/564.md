# Text `bea check` exits 0 on a ledger `bean-check` rejects once the load takes over a second: native bean-check reads the helper's load cache, which never ran bean-check's data-type validation

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-16, HEAD `fe8ed158`, checkout `bea 0.3.1`, macOS 26.5.1. Differential run against upstream `bean-check`.
`bea check` first runs a helper load (`--documents-only`), then native
bean-check when the helper did not find the ledger clean. Beancount writes
its pickle cache whenever a load takes over a second, and the cache key
ignores `extra_validations`. The helper's load writes the cache without
bean-check's `HARDCORE_VALIDATIONS`. bean-check then reads that cache, gets
the helper's errors (none), and exits 0. USAGE says `bea check` "applies
bean-check's own validations", and that exit 0 is a promise. Not w5/493:
that note is about `--json` and BOM paths, where text check is said to fail,
which holds only for fast loads. No product fix implemented.

`notags.py` beside the ledger:

```python
from beancount.core import data
__plugins__ = ["notags"]
def notags(entries, options_map):
    return [e._replace(tags=None) if isinstance(e, data.Transaction) and e.narration == "BAD" else e
            for e in entries], []
```

`main.bean`: `option "insert_pythonpath" "TRUE"`, `plugin "notags"`, opens for
`Assets:Cash USD` and `Expenses:Food USD`, then ~60,000 small transactions,
then one `2020-06-01 * "BAD"` transaction.

```sh
bea --file /abs/main.bean check        # fresh BEA_CONFIG_DIR / XDG_CACHE_HOME
bea --file /abs/main.bean check -C
```

Actual: `check` exits 0 with empty output (also with `-v`). `check -C` exits
1 with `main.bean:180005: Invalid data types: Invalid tags type: <class
'NoneType'>`. With an extra unbalanced transaction, plain `check` lists only
`Transaction does not balance` and drops the data-type error.

Control: the same ledger with three transactions (fast load) exits 1 with the
data-type error; upstream `bean-check` (cached or `-C`) exits 1.

Expected: exit 1 with the data-type error at any ledger size.

Cause: the helper load (`cli/src/cli/commands/check.py:97` →
`managed_load._load_fresh`, `cli/src/bea_engine/managed_load.py:579/588`)
passes no `extra_validations` and writes the cache under the pattern native
bean-check also uses (`cli/src/cli/engine/launch.py:179`); `check.py:123` then
runs bean-check against it.

Fix: run native bean-check with `--no-cache` (or a separate cache pattern)
whenever the helper ran first, or store the validation errors in the helper's
cache entry, or report them from the helper (which also serves w5/493).

Dedupe: searched `Invalid data types`, `HARDCORE`, `extra_validations`, `load
cache`. Siblings: w5/111 and w5/326 (cache not keyed on load mode or plugins),
w5/493 (open, JSON path). It contradicts w1/m19/t003's acceptance (native
validation matches, "including timing, cache").

Acceptance: the large fixture exits 1 with the data-type error on the first
and second run. A test forces the cache write and pins it.

---

**Resolved 2026-10-17** — Shipped in `8671cb98` (`cli`). `bea check` (`cli/src/cli/commands/check.py`) now always runs native bean-check with `--no-cache`, unless the user names a `--cache-filename` or already passes `-C`; `--auto` keeps its w5/111 isolation either way. bean-check runs there only for a ledger the helper found errors in, or for bean-check's own options. A clean ledger without options is still answered from the helper's load, so the cost of a fresh load falls only on runs that report errors.

This is the note's first option. A cache of bean-check's own was tried first: it would have held plugin-defined error classes that a later bean-check cannot unpickle (`Cache file is corrupted: No module named …`, the w5/326 failure mode).

`tests/test_check_native_cache_validations.py` runs a slow plugin that breaks a transaction's tags and warms the cache with a read; both following `check` runs then exit 1 with `Invalid data types`. It fails without the fix. Two tests were updated: the forwarded-argv test now expects `--no-cache` first, and the w5/111 auto test warms its cache with `list open`, because `check` no longer writes one. USAGE says the native load skips the cache. `make check-all` passed.
