# A write re-reads every sibling ledger once per "unknown account" error, so one missing `open` stalls writes for minutes

**Major (hang without output) · cli · 30–45m · A1.** Real CLI QA, 2026-10-11, HEAD `0227141a` (CLI unchanged since `97600b74`),
checkout `bea 0.3.1`, macOS.
When a ledger with an include has many transactions that reference an
unopened account, every `bea add …` spends time quadratic in the number of
those errors before it answers. Four thousand such transactions take half a
minute to be refused; a worker's 60,000-transaction ledger never finished
within 90 seconds and left engine processes spinning after the frontend gave
up. `bea check` on the same ledger answers in a fraction of a second. No
product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2000-01-01 open Assets:Bank USD
include "big.bean"
```

and generate `/absolute/books/big.bean`:

```sh
python3 -c "open('big.bean','w').writelines(f'2020-01-01 * \"t{i}\"\n  Expenses:Food  1 USD\n  Assets:Bank\n\n' for i in range(4000))"
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bea -f /absolute/books/main.bean add note --account Assets:Bank --comment hi --date 2021-03-01
```

Actual: exit 1 with `The change would leave the ledger invalid; nothing was
written.` after 30.8 seconds. With 1,000 transactions the same command takes
2.3 seconds. A worker measured 0.8 s / 2.3 s / 9.1 s / 30.1 s for 500 / 1,000
/ 2,000 / 4,000 errors with `--allow-errors` (exit 0), and 9.7 s against
5.6 s on a valid 60,000-transaction ledger with 40 typo'd-account
transactions appended.

Controls: `bea --json -f … check` on the 4,000-error ledger exits 1 in
0.3 seconds. The same 4,000 transactions in a single file with no include and
no sibling ledger are refused in 1.1 seconds. A worker confirmed
`add open --account Expenses:Food`, which leaves no errors, takes 0.3 s.

Expected: a refusal or a write in roughly the time it takes to load the
ledger, as `check` does. A user fixing a ledger with one forgotten `open`
by running `bea add` should not meet a silent multi-minute stall, and an
agent's timeout should not strand an engine process.

Cause: `cli/src/bea_engine/ledger/write.py:704` calls
`root_ledger_hints(...)` inside the per-error loop of
`validate_candidate` for every unknown-account message. That calls
`including_root` (`write.py:544-565`), which globs the ledger's directory
and its parent for ledger files and captures a full snapshot — a lex of the
whole include closure — for each. A worker's profile of the 2,000-error case
showed 2,000 calls accounting for 16.3 of 17.2 seconds.

Fix: compute the including-root hint at most once per validation, and only
when the invoked file is not already the root. Separately consider whether
the engine child should stop when the frontend times out or is interrupted.
No dependency or API change.

Blast radius: every `add` subcommand and `import --apply`, which share
`validate_candidate`. The other caller of the hint (`adding.py:694`) is
outside any loop.

Dedupe: board search for `including_root`, `root_ledger_hints` and
quadratic finds w3/438 (the wording of that hint, done) and w1/087 (quadratic
`format --check` over include chains, a different path).

Acceptance: the 4,000-error fixture is refused in under 2 seconds with the
same message, and time grows linearly with the error count. A regression
test asserts the hint is computed once. Only macOS and the checkout were
exercised.

---

**Resolved 2026-10-13** — Write validation in `cli/src/bea_engine/ledger/write.py` asked for the including-root hint once per unknown-account error, and each ask re-read every sibling ledger's include closure, so refusal time grew quadratically with the error count. The hint is now looked up lazily on the first unknown-account error of a validation and reused, which covers every `add` subcommand and `import --apply`. The regression test counts the lookups: one for a 40-error include tree with the same refusal and an untouched file, one for an included leaf that still gets its `--into` hint (both fail with the fix reverted), and none for a clean write. Time now grows linearly (2.8 s for 4,000 errors on a heavily loaded machine, against 25 s for 2,000 before), so the note's "under 2 seconds" clause was not demonstrated. The note's separate suggestion to stop the engine child on a frontend timeout is not addressed. `make check-all` passed. Only macOS was exercised. Shipped in `891ab502` (`cli`).
