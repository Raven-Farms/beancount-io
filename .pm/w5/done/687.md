# Five doc sentences describe behavior today's fixes changed: Unicode-space account names, cache paths outside the ledger's files, server messages on errors, `engine status` JSON fields, and the `--id-key` key rule

**Trivial · cli docs · 15–20m · A1.** Real CLI QA, 2026-10-17, HEAD `306653d5`, checkout `bea 0.3.1`, macOS 26.5.1. Docs drift after the w5/469, 481, 482, 490 and 497 fixes.
No product fix implemented.

1. **USAGE.md:939-943 (w5/490).** It says an account name may hold any
   non-ASCII character Beancount loads (the w5/203 promise). Since w5/490,
   `add note`, `add balance` and `add transaction -p` refuse an account
   containing U+00A0 even when the ledger already opens it (`Invalid account
   … U+00A0 (NO-BREAK SPACE) is not allowed`). The w5/490 resolution accepts
   the trade-off, so the doc should exclude Unicode spaces and say an
   existing such account must be renamed.
2. **USAGE.md:209-210 (w5/497).** "A cache path outside the ledger's own
   files keeps working" is no longer true for a new path an include glob would
   claim (now refused with exit 2).
3. **USAGE.md:316 (w5/482).** "Keeping the server's own message" no longer holds
   for HTML, multi-line or long bodies, which fall back to the HTTP status.
4. **USAGE.md:56-61 (w5/481).** The `engine status` JSON field list omits the new
   `usable`, `unusable` and `damaged` fields.
5. **IMPORTING.md:440-442 (w5/469).** The documented `--id-key` rule names empty
   keys and keys not starting lowercase. The regex (`[a-z][A-Za-z0-9_-]+`)
   also needs two characters, so `--id-key x` exits 2, and its message ("starts
   with a lowercase letter and holds letters, digits…") describes a rule `x`
   meets. Fix the message and the doc.

Dedupe: w5/524, 527, 528, 624 and 633 cover other doc slips.

Acceptance: each sentence matches current behavior (item 5's message too).
