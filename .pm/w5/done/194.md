# The recovery the 9999-12-31 error recommends (`--time 9999`) silently omits every entry dated 9999-12-31

**Minor · cli · 30–40m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
For a ledger whose last entry is dated 9999-12-31, reports refuse and
say "Name the period explicitly and it reports fine, as in --time 9999."
Following that advice exits 0 with a report that ends on 9999-12-30 and
leaves the 9999-12-31 entries out, with no partial notice. Only the
calendar's last day is affected; this is a leftover of w3/407. No
product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
9999-12-31 open Assets:Cash USD
9999-12-31 open Equity:Opening USD
9999-12-31 * "Boundary"
  Assets:Cash 1 USD
  Equity:Opening
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean balance
bea -f main.bean balance -t 9999
bea -f main.bean query "SELECT account, sum(position) GROUP BY account"
```

Actual: the first exits 2 with the advice quoted above. The second exits
0: `Trial Balance — 9999-01-01 through 9999-12-30`, every section empty.
The query shows `Assets:Cash 1 USD` and `Equity:Opening -1 USD`.

Control: the same fixture dated 9999-12-30 reports `Cash 1 USD` and
`Opening -1 USD` with `-t 9999`. A worker saw `-t 9999-12-31` refused
(exit 2), so no `--time` spelling reaches that day, and a ledger with
10.00 in May and 5.00 on 9999-12-31 report 10.00.

Expected: w3/407's acceptance — do not "silently omit/clamp the dated
entry" — and the error's own promise that the period "reports fine".

Cause: `cli/src/fava/util/date.py:123-127` returns the maximum date when
the next year overflows, and that becomes the exclusive end of the
window; the same clamp exists for the other interval sizes. The
regression test asserts only exit 0.

Fix: flag or refuse a window that cannot include 9999-12-31, or reword
the hint in `cli/src/bea_engine/report.py` so it does not promise a
complete report; assert the boundary amount in the test. No dependency
change.

Blast radius: reports and `balance` on ledgers with entries on
9999-12-31.

Dedupe: w3/407 (done) fixed the diagnostic only and lists near-maximum
interval shapes as unverified.

Acceptance: `balance -t 9999` on the fixture either includes the 1 USD
entry or states that 9999-12-31 is excluded; the 9999-12-30 control is
unchanged. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — A report whose period ends at the calendar's last day now says that it leaves 9999-12-31 out instead of silently omitting those entries: `_metadata` in `cli/src/bea_engine/report.py` adds `excluded_date` to the JSON when the exclusive end is 9999-12-31 and the ledger has dated activity on that day, and `_heading` in `cli/src/cli/commands/report.py` prints "Entries dated 9999-12-31 are not included" on stderr for `balance` and all four report kinds. The unfiltered refusal's hint in the same engine file no longer promises that `--time 9999` "reports fine"; it says the period reports everything before 9999-12-31 and that entries on that day are left out. The entry itself is still not reportable, which is the "states that 9999-12-31 is excluded" branch of the acceptance rather than the "includes the 1 USD entry" branch, and an explicit range ending on 9999-12-30 gets the same note because it shares the same exclusive end. `cli/tests/test_report_calendar_last_day_excluded.py` runs the real command over `balance -t 9999`, JSON, every report kind, and month, quarter and range periods that clamp, with the 9999-12-30 ledger and an earlier period as unchanged controls; 10 of its 12 cases fail with the fix reverted and the 2 controls pass either way. Only macOS was exercised. `make check-all` passed. Shipped in `c96b6f23` (`cli`).
