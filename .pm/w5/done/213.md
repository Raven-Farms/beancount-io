# Bulk `"amount": "1,234.56 USD"` is refused, though `--posting` and longer bulk amounts accept the same comma grouping

**Minor · cli · 15m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
Low priority; the error is clear. A two-token bulk amount with thousands
separators is rejected as "not a number", while the identical number is
accepted by `add transaction --posting` and by a bulk amount that has a
cost or arithmetic in it. Acceptance depends on how many tokens the string
has. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Broker
2024-01-01 open Assets:Cash USD
```

`/absolute/books/rows.json`:

```json
[{"date":"2024-06-01","narration":"deposit","postings":[
  {"account":"Assets:Broker","amount":"1,234.56 USD"},
  {"account":"Assets:Cash","amount":"-1,234.56 USD"}]}]
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean add transactions --from rows.json
```

Actual: exit 1, nothing written.

```text
Row 1, postings.0: Value error, Could not parse amount '1,234.56 USD' as 'NUMBER CURRENCY': '1,234.56' is not a number. …
```

Control: `bea -f main.bean add transaction deposit --date 2024-06-01 -p
"Assets:Broker 1,234.56 USD" -p "Assets:Cash -1,234.56 USD"` exits 0 and
writes `1234.56 USD`. A bulk row with `"amount": "1,000 ABC {1,234.56
USD}"` and `"amount": "0 - 1,234,560.00 USD"` exits 0 and writes
`1000 ABC {1234.56 USD}` / `-1234560.00 USD`.

Expected: `docs/USAGE.md` says the bulk `amount` shorthand "accepts the
same lot spelling" as the posting flag; the documented bulk refusals do not
include Beancount's comma grouping. Both spellings should accept the same
numbers, or the docs should state that a plain bulk amount takes an
ungrouped decimal.

Cause: `cli/src/bea_engine/ledger/models.py:148-160`: a two-token amount
takes a shortcut through `Decimal(number)`; three or more tokens go through
Beancount's grammar.

Fix: when the shortcut fails to parse, fall through to the grammar path
(keeping the zero-divisor refusal); or document the restriction. No
dependency or API change.

Blast radius: bulk `amount` strings of exactly two tokens. A worker reads
the code as refusing two-token arithmetic such as `"84/2 EUR"` the same
way (not run).

Dedupe: board search for `1,234`, `thousands` and "is not a number" finds
w3/done/256 and w4/done/164 (CSV import amounts) and w5/done/010 (zero
divisor); nothing covers the bulk shorthand.

Acceptance: the batch exits 0 and writes `1234.56 USD` / `-1234.56 USD`,
or the docs name the restriction and the error suggests removing the
commas. Only macOS and the checkout were exercised.

---

**Resolved 2026-10-13** — The bulk `amount` shorthand in `cli/src/bea_engine/ledger/models.py` no longer refuses a two-token amount whose number is not a bare decimal: it now falls through to the same Beancount grammar path that longer amounts use, so `"1,234.56 USD"` writes `1234.56 USD` and two-token arithmetic such as `"84/2 USD"` writes `42 USD`, matching `--posting`. A two-token `"1/0 USD"` now gets the zero-divisor refusal, and garbage such as `"abc USD"` is still refused, with the wording changed from "is not a number" to the posting-fragment message carrying the parser's reason. `cli/docs/USAGE.md` states that a plain two-token amount accepts comma grouping and arithmetic. The regression test `cli/tests/test_bulk_two_token_grammar_amount.py` runs the real command for the bulk writes, the `--posting` control, the remaining refusals (`abc`, `1/0`, `1e3`, `1_000`) and the bare-decimal shortcut; 4 of its 11 cases fail with the fix reverted. Only macOS was exercised. `make check-all` passed. Shipped in `cabb100d` (`cli`).
