# A flag-free `import --apply` drops options typed on the remembered preview and writes different rows

**Major (wrong dates and categories written) · cli · 45–60m · A1/A2.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS.
Once a CSV mapping is remembered, an option typed on a later preview —
`--date-format`, `--rules` — changes that preview but is never saved. The
documented flag-free `--apply` then recomputes without it and writes rows the
user did not review, with exit 0. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"

2026-01-01 open Assets:Checking USD
2026-01-01 open Liabilities:Card USD
2026-01-01 open Expenses:Food
2026-01-01 open Expenses:Uncategorized
2026-01-01 open Equity:Opening

2026-01-02 * "Opening balance"
  Assets:Checking  1000.00 USD
  Equity:Opening
```

and `/absolute/books/a.csv`:

```csv
Date,Description,Amount
05/01/2026,Lunch,-20.00
06/02/2026,Train,-40.00
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`, and
a fresh configuration directory so no mapping is remembered.

```sh
bea -f /absolute/books/main.bean import a.csv --account Assets:Checking
bea -f /absolute/books/main.bean import a.csv --date-format %d/%m/%Y
bea -f /absolute/books/main.bean import a.csv --apply
```

Actual: the first preview exits 0 showing `2026-05-01` and `2026-06-02` and
advises "day-first and month-first cannot be told apart. Pass --date-format if
that is the wrong reading." The second, following that advice, exits 0 showing
`2026-01-05` and `2026-02-06`, under
`Using remembered settings for a.csv: … --date-format %d/%m/%Y`. The apply
exits 0, prints `Using remembered settings for a.csv: … --date-format
%m/%d/%Y`, and writes `2026-05-01 ! "Lunch"` and `2026-06-02 ! "Train"` —
the dates of the first preview, four months off the reviewed ones. Repeated
twice from a pristine fixture. Because the date is part of the row's
`import-id` hash, a corrected re-import shows both rows as `new` and would
write them a second time.

The same gate drops `--rules`: with a remembered mapping, a preview run with
`--rules rules.toml` shows a matched row categorized, and the flag-free
`--apply` books it to `Expenses:Uncategorized` with `!`. `--default-account`
and `--delimiter` pass through the same branch (source-inferred, not run).

Control: typing the whole mapping on the second step — `--csv
date=Date,amount=Amount,narration=Description --date-format %d/%m/%Y --account
Assets:Checking` — then the flag-free `--apply` writes `2026-01-05` and
`2026-02-06`.

Expected: `docs/IMPORTING.md` says "The first import previews every row; the
mapping is remembered, so `--apply` re-runs flag-free", that "`--apply`
recomputes the preview from the current files", and — of the one setting it
singles out — that replaying it "keeps a preview honest". The preview a user
last saw for a file is what a flag-free apply of that file must write. Either
the typed options are saved with the remembered settings, or the apply refuses
because its effective settings differ from the last successful preview.

Cause: `cli/src/cli/commands/import_.py:594` builds the settings to persist
only `if not remembered_run`. On a recalled run (`:422-440`) an option the
user typed wins for that process — the recall fills only values that are
`None` — but nothing writes it back, so the next flag-free run re-infers the
date format or reuses the older rules path.

Fix: on a successful recalled run, persist every setting the user typed in
that invocation, merged into the recalled entry under the same ledger, header
and account key, and name the replaced values the way an explicit `--csv`
refresh already names dropped settings. Keep `sign=` out of memory as
documented. Failed runs must still leave memory untouched. No dependency or
API change.

Dedupe: board search for remembered settings, flag-free apply and
`--date-format` finds w1/150 (the same principle for `sign=` only), w3/308
(a remembered explicit format applied to another file), w3/311 (an explicit
`--csv` refresh dropping rules) and w3/425 (a failed run replacing memory);
none covers an option typed on a recalled preview.

Acceptance: on the fixture the flag-free apply writes `2026-01-05` and
`2026-02-06` and its settings line names `%d/%m/%Y`; the `--rules`,
`--default-account` and `--delimiter` variants apply what their preview
showed; JSON `remembered` reports the updated values. Regression tests run the
three-step journey through the real command. Only macOS and the checkout were
exercised.

---

**Resolved 2026-10-12** — A successful import that used the remembered mapping now saves the `--date-format`, `--rules`, `--default-account` and `--delimiter` typed on that run into the recalled entry, under the same ledger, header and account key, and reports `Updated remembered settings for <file>` naming each value and what it replaced. On the fixture the flag-free `--apply` writes `2026-01-05` and `2026-02-06`, its settings line names `%d/%m/%Y`, and JSON `remembered` carries the updated values. `sign=` is still never stored. `docs/IMPORTING.md` describes the behavior. Shipped in `02089c0d` (`cli`).

Regression tests run the three-step journey through the real command: the ambiguous-date fixture, `--rules` with `--default-account`, `--delimiter`, a failed recalled run that must leave the stored record byte-identical, and a re-typed unchanged option that produces no update note. The date and rules journeys fail with the fix reverted; the delimiter journey passes either way because detection already reads that file, so it pins the stored value rather than reproducing a defect. `make check-all` passed. Only macOS was exercised.
