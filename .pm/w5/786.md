# SIGTERM to `bea` during first-use provisioning leaves `uv` running, and a retry in that window leaves a 25 MB `<version>.partial.<pid>` that is never removed (gap in w5/437)

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-17, HEAD `46d7394e9`, `bea 0.3.1` installed from a freshly built wheel with isolated data and uv cache, macOS 26.5.1 (hunter's runs, twice; code path checked).
USAGE says a build killed mid-install leaves a `<version>.partial.<pid>`
directory that the next provision removes. w5/437's acceptance says signal
forwarding holds for every child bea starts. No product fix implemented.

1. Start `bea check` on an unprovisioned engine and send SIGTERM to the `bea`
   PID only, about 1.2 s in (a supervisor, `timeout` or an agent harness does
   this). `bea` exits on signal 15, but its `uv pip install --python
   …/0.3.1.partial.<pid>/bin/python …` keeps running.
2. Immediately run `bea check` again. It exits 0 (`Installing…`/`ready`).
3. After the orphaned uv exits, `engine/` holds `0.3.1`, `0.3.1.lock` and
   `0.3.1.partial.<pid>` (25 MB, a complete venv). Later commands never
   remove it, because provisioning no longer runs, and `engine status` does
   not mention it.

Control: Ctrl-C to the process group exits 130 with no orphan and no partial
directory. Letting the orphan finish before the retry lets the sweep remove
it.

Expected: SIGTERM is forwarded to uv, uv is stopped within the grace period,
and the partial directory is removed.

Cause: `provision._run` (`cli/src/cli/engine/provision.py:491-498`) uses a bare
`subprocess.run`. `_sweep_abandoned` (`:382`) removes the dead bea PID's
directory while the orphaned uv is still writing into it.

Fix: run uv through the signal-forwarding wrapper w5/437 added, and sweep
stale partials after a successful publish.

Dedupe: w1/123 and w5/437 (done) are the parents.

Acceptance: step 1 leaves no running uv, and no partial directory survives
step 3.
