# `BEA_ENGINE_PYTHON` naming a directory, a non-executable file or a program that is not Python escapes the w5/269 check: a raw `[Errno 13]`, or `add` exits 4 "the outcome is unknown"

**Minor · cli · 15–25m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, Python 3.13.3.
[269](./done/269.md) made an override that cannot load the engine fail
with a message naming the variable, and made a refused write exit 1. Two
neighbouring values get past that check:

- A directory or a non-executable file. Every helper command (`balance`,
  `list`, `add`) fails with `Error: [Errno 13] Permission denied:
  '<path>'`, which does not name the variable.
- An executable that is not Python, such as `/bin/echo` or a stale wrapper
  that exits 0. `add` exits **4** with `The Beancount engine did not
  answer … (exit 0); the outcome is unknown. Inspect the file before
  retrying.`, although nothing ran and the ledger is unchanged.

Only `bea check`, on the native path, names the variable. No product fix
implemented.

Use any valid ledger at `/absolute/books/main.bean`, for example a fresh
`bea init`. Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME,
BEA_NO_UPDATE_NOTIFIER=1, no inherited BEA_FILE/BEA_TOKEN, and closed
stdin. Create `/absolute/noexec` containing `x` with mode 644.

```sh
BEA_ENGINE_PYTHON=/absolute/noexec bea -f /absolute/books/main.bean balance
BEA_ENGINE_PYTHON=/absolute       bea -f /absolute/books/main.bean add note --date 2026-01-05 -a Assets:Checking -m e
BEA_ENGINE_PYTHON=/bin/echo       bea -f /absolute/books/main.bean add note --date 2026-01-05 -a Assets:Checking -m e
```

Actual:

- The first two exit 1 with `Error: [Errno 13] Permission denied:
  '/absolute/noexec'` (or `'/absolute'`).
- The third exits 4 with the unknown-outcome message, and the ledger is
  unchanged.

Reproduced in three fresh runs.

Controls:

- `BEA_ENGINE_PYTHON=/absolute/nope` exits 1 with `BEA_ENGINE_PYTHON
  points at '/absolute/nope', which does not exist.`
- `BEA_ENGINE_PYTHON=/bin/echo bea check` exits 1 with a message that
  names the variable and says to correct or unset it.

Expected: `docs/USAGE.md` says overrides "are checked before use: one that
names a path which does not exist, or an environment missing the tool
being run or unable to load the engine, fails with a message naming the
variable and telling you to correct or unset it; a write refused this way
exits 1, since nothing ran."

Cause:

- `paths.python_override()` (`cli/src/cli/engine/paths.py:72-80`) checks
  only `exists()`.
- `_run_helper` (`cli/src/cli/engine/launch.py:446`) surfaces the
  `PermissionError` from `subprocess` as a generic error.
- `_refuse_unusable_override` (`launch.py:611-645`) returns early on
  `OSError`. It also accepts any probe that exits 0, so `/bin/echo -P -c
  "import bea_engine.main"` passes.

Fix:

- In `python_override()`, also require a regular executable file
  (`is_file()` and `os.access(X_OK)`), with the same "points at … Correct
  or unset" wording.
- Treat an `OSError` from the probe as unusable.
- Require the probe to prove itself, for example by printing a sentinel
  that is then checked on stdout.
- A write refused this way exits 1.

No dependency or API change.

Blast radius: every command on the helper path while the override is set,
which matters mostly for tests and recovery tooling.

Dedupe: board search for `BEA_ENGINE_PYTHON`.

- w5/011 fixed the native-path remedy and `BEA_UV` existence.
- w5/269 fixed an interpreter without Beancount; its tests use a bare
  Python.
- w2/022 covers engine status.

None of these covers a non-executable path or a non-Python executable.

Acceptance: each of the three commands exits 1 with a message naming
`BEA_ENGINE_PYTHON` and the remedy, prints no unknown-outcome text, and
leaves the ledger unchanged. A real-command regression test covers a
directory, a mode-644 file and `/bin/echo`. Only macOS and the checkout
were exercised.
