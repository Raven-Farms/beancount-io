# `--json` `target.file` names a symlinked root's resolved target, which on its own loads a different, broken ledger (residue of w1/056)

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-16, HEAD `3514cc17`, checkout `bea 0.3.1`, macOS 26.5.1.
USAGE says a symlinked root "keeps the path you named", with includes
resolved beside the link, and `target` identifies the operation's scope. An
agent that re-runs a command on `target.file` gets a different ledger. No
product fix implemented.

`B/real.bean` (opens plus `include "inc.bean"`), `A/inc.bean` (one
transaction), `A/main.bean -> ../B/real.bean`. Run in `A`:

```sh
bea --json check
bea -f "<target.file from above>" check
```

Actual: `target.file` is `…/B/real.bean`; re-running on it exits 1 with
`File glob "inc.bean" does not match any files`. Balance, list, report, query
and add (`into` too) report the same target. Text errors name `…/A/inc.bean`.

Expected: `target.file` is the lexical absolute path the command used
(`…/A/main.bean`).

Cause: `file_target` (`cli/src/cli/output.py:328-329`) uses `path.resolve()`,
while `RunContext.entry_file` is deliberately lexical (`cli/src/cli/context.py:181-184`,
w1/056).

Fix: report the lexical path in `target`; keep `resolve()` for alias and lock
checks.

Dedupe: w1/056 (done) listed this symptom but fixed include resolution only.

Acceptance: `target.file` names `A/main.bean`, and re-running on it gives the
same answer. A test pins it.
