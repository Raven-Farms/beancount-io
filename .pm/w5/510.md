# A "No position matches" refusal names the wrong posting when two postings share an account and units (gap in w5/333)

**Minor · cli · 15m · A1.** Real CLI QA, 2026-10-16, HEAD `bea189ec`, checkout `bea 0.3.1`, macOS 26.5.1.
w5/333 rewrote Beancount's reduction error to name the posting. It finds the
posting by account and units only. When two lots of the same size are sold
in one transaction, it names the first one, which may be the lot that did
match, beside holdings that include it. No product fix implemented.

`main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Stock HOOL "STRICT"
2024-01-01 open Assets:Cash USD
2024-01-01 open Income:Gains USD
2024-01-05 * "buy"
  Assets:Stock  10 HOOL {100.00 USD}
  Assets:Cash
2024-01-06 * "buy2"
  Assets:Stock  10 HOOL {110.00 USD}
  Assets:Cash
```

```sh
bea -f /abs/main.bean add transaction "Sell two lots" --date 2024-03-01 \
  -p 'Assets:Stock -5 HOOL {100.00 USD}' -p 'Assets:Stock -5 HOOL {120.00 USD}' \
  -p 'Assets:Cash 1200 USD' -p Income:Gains
```

Actual: exit 1, nothing written, `No position matches -5 HOOL {100.00 USD} in
Assets:Stock; it holds (5 HOOL {100.00 USD, 2024-01-05}, 10 HOOL {110.00 USD,
2024-01-06})`.

Control: with the two postings swapped it names `{120.00 USD}`.

Expected: it names `-5 HOOL {120.00 USD}`, the posting upstream rejected.

Cause: `cli/src/bea_engine/query.py:2103` picks the first posting with the
same account and `str(units)`; the cost spec in upstream's error, and the
posting's `lineno`, are ignored.

Fix: match on the cost spec (or the posting's line) carried by the error;
fall back to upstream's text when ambiguous.

Dedupe: searched `No position matches`. w5/333, w3/416, w1/135 and w0/026
(done) do not cover duplicates.

Acceptance: the command names `{120.00 USD}`. A test pins it.
