# A macOS AppleDouble file (`._main.bean`) beside a ledger makes `bea format --check .` and `format -i .` stop with "Cannot decode … as UTF-8. Re-save the file as UTF-8"

**Minor · cli · 10m · A1/A2.** Real CLI QA, 2026-10-16, HEAD `c210da9b`, checkout `bea 0.3.1`, macOS 26.5.1.
macOS writes `._<name>` resource-fork files on exFAT, FAT and SMB volumes.
They also appear when a macOS tar or zip archive is unpacked elsewhere. The
directory walk treats `._main.bean` as a ledger file. The run stops, `-i`
formats nothing, and the advice is to re-save a binary metadata file as
UTF-8. USAGE already skips Emacs `.#name` lock files for the same reason, and
include globs never match dotfiles. No product fix implemented.

A ledger directory with `main.bean` and a 4 KB AppleDouble `._main.bean`
(starts with the magic bytes `00 05 16 07`).

```sh
bea format --check .
bea format -i .
```

Actual: exit 1, `Error: Cannot decode '…/._main.bean' as UTF-8: invalid start
byte at byte 37. Re-save the file as UTF-8 and retry.`; `-i` formats nothing.
`bea check` passes.

Expected: AppleDouble files are skipped (named as skipped, or silently, like
editor lock files), and the real files are formatted.

Cause: `_walk` (`cli/src/cli/commands/format.py:525-526`) accepts every
`*.bean`/`*.beancount` name; only `_editor_lock` is exempt.

Fix: skip `._*` files (at least those starting with the AppleDouble magic), or
skip dotfiles in directory walks as include globs do.

Dedupe: searched `AppleDouble`, `resource fork`, `._`. No match.

Acceptance: `format --check .` and `-i .` ignore the AppleDouble file. A test
pins it.
