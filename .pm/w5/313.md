# `SELECT accounts, count(*) GROUP BY 1` still crashes with `TypeError: issubclass() arg 1 must be a class`: the w3/358 refusal recognises `accounts` only when it is grouped by name

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, Python 3.13.3.
[w3/358](../w3/done/358.md) (`0e04c47b`) made `GROUP BY accounts` exit 2
with the `joinstr` recipes instead of an `issubclass` TypeError. Grouping
the same column by position (`GROUP BY 1`, `GROUP BY 1, 2`) still exits 1
with category `validation` and a Python class name in the message. `tags`
grouped by position is refused correctly. [177](./done/177.md)'s
resolution mentions this case in passing ("still surfaces Beanquery's own
`TypeError` with exit 1"), but no note tracks it. No product fix
implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
2026-01-01 open Equity:Opening
2026-01-05 * "Lunch"
  Expenses:Food  12.50 USD
  Assets:Checking
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bea -f /absolute/books/main.bean query "SELECT accounts, count(*) GROUP BY 1"
bea --json -f /absolute/books/main.bean query "SELECT accounts, count(*) GROUP BY 1"
bea -f /absolute/books/main.bean query "SELECT date, accounts, count(*) GROUP BY 1, 2"
```

Actual: each command exits 1 with `Error: TypeError: issubclass() arg 1
must be a class Pass --debug before the command for a traceback.` The JSON
error has `"category": "validation"`. Reproduced in three fresh setups.

Controls:

- `GROUP BY accounts` exits 2 with `BQL cannot use DISTINCT or GROUP BY on
  accounts: a set is not a value it can compare.`
- `SELECT tags, count(*) GROUP BY 1` exits 2.
- `SELECT accounts, count(*)` (implicit grouping) exits 2, naming
  `accounts (set)`.

Expected: `docs/USAGE.md` says BQL that does not parse or compile exits 2
with the reason. A positional `GROUP BY` names the same column, so it
should get the same refusal.

Cause: `_compiled` (`cli/src/bea_engine/query.py:1424-1436`) converts the
`issubclass` TypeError into a usage error only when
`_grouped_columns(statement)` contains a set column. `_grouped_columns`
(`query.py:1563-1576`) keeps only items that have a `name`. A positional
`GROUP BY 1` is an int, so the guard is skipped and the TypeError is
re-raised (`:1447`). `tags` by position works because it fails differently
and is caught through `_set_columns` over the SELECT targets.

Fix: resolve an integer `GROUP BY` item to the name of the matching
1-based SELECT target, or fall back to the bare `accounts`/`tags`/`links`
targets when the TypeError fires. The command should exit 2 naming
`accounts`. No dependency change.

Blast radius: `bea query` one-shots, `.run` stored queries and the
interactive shell (all use `_compiled`), for positional grouping on
`accounts`.

Dedupe: searched the board for `issubclass`, `GROUP BY 1` and "set is not
a value".

- w3/358: fixed grouping by name only.
- w5/177: mentions this case in passing; not filed.
- w5/260: implicit grouping.
- w3/253: `GROUP BY 1` on positions.

None of these tracks positional grouping on `accounts`.

Acceptance: on the fixture, all three commands exit 2 with `BQL cannot use
DISTINCT or GROUP BY on accounts …`, category `usage` under `--json`, and
no `TypeError` text. A real-command regression test covers `GROUP BY 1` and
`GROUP BY 1, 2`. Only macOS and the checkout were exercised.
