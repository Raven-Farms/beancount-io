# In the `bea ask` REPL, a question asked within ~5 s of the previous answer is sent to the proxy twice; the first (billed) response is discarded

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-16, HEAD `0c12f2dc`, checkout `bea 0.3.1`, macOS 26.5.1. Simulation: local stub of the AI proxy; REPL on a PTY.
Each REPL turn runs `agent.run_sync` on a new event loop, because the prompt
in between runs its own. The cached httpx client keeps the previous turn's
keep-alive connection, which is bound to the old loop. The request is sent,
reading the reply raises `RuntimeError: … bound to a different event loop`,
and the OpenAI SDK silently retries on a new connection. The backend
records usage on every proxy call, so the user's quota pays twice. USAGE
promises a fixed request budget per question. No product fix implemented.

Stub replies `answer one`, `answer two`, `answer three`; `BEA_NO_ASK_HISTORY=1`.

```sh
bea -f /abs/main.bean ask     # type "first", wait 1 s after the answer, type "second"
```

Actual: the stub receives three requests: one for "first", then two identical
requests for "second" with `x-stainless-retry-count` `0` and `1`. "answer
two" is discarded and "answer three" is shown. Every later turn does the
same. Exit 0; nothing tells the user. With `OPENAI_LOG=debug` the error is
`RuntimeError: <asyncio.locks.Event …> is bound to a different event loop`
in httpcore after the request body was sent.

Control: a 6 s gap (past httpx's keep-alive expiry) sends one request;
`--print` (one loop) never retries.

Expected: one hosted request per model step.

Cause: `cli/src/cli/ask/repl.py:296` calls `agent.run_sync` per turn while
`session.prompt()` (`repl.py:268`) runs its own loop; the provider is built
with `OpenAIProvider(base_url, api_key)` and no `http_client`
(`cli/src/cli/ask/agent.py:370`), so its pooled connections outlive their
loop.

Fix: give each turn a fresh `httpx.AsyncClient` (or close the pool after each
run), or run the whole REPL on one persistent loop. Set the SDK's
`max_retries` and timeout explicitly while there.

Dedupe: searched `event loop`, `keep-alive`, `retry-count`, `max_retries`.
w3/449 and 454 mention SDK retries of 429/400 only.

Acceptance: two turns 1 s apart send exactly two requests. A test with a
stub counts them.
