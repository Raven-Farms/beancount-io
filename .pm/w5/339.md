# `bea import` marks a row `new` ("2 ready") when its counter-account is open but inactive on the row's date, then `--apply` refuses the whole batch with exit 1 instead of blocking that row

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
w3/276 made rows that post to a never-opened account show as `blocked`,
with the `bea add open` remedy. Those rows are left out of `ready` and out
of writes, and `--apply` exits 4. The check only asks whether an `open`
exists, though. It ignores the open's date and any `close`.

So when a rule account was closed before the row's date, or opened after
it:

- the preview calls the row `new` and counts it as ready;
- `--apply` fails ledger validation with exit 1 and writes nothing, not
  even the valid rows.

A user who closes an old category but leaves a rule pointing at it hits
this on every later import. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Groceries USD
2026-01-01 open Expenses:Dining USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Equity:Opening
2026-01-03 close Expenses:Dining
```

Use `s.csv` from [338](./338.md), and an `r.toml` with one rule:
`match = "diner"`, `account = "Expenses:Dining"`. Use the same environment.

```sh
bea -f main.bean import s.csv --csv date=Date,payee=Payee,narration=Narration,amount=Amount --account Assets:Checking --rules r.toml
bea --json -f main.bean import s.csv --csv date=Date,payee=Payee,narration=Narration,amount=Amount --account Assets:Checking --rules r.toml --apply
```

Actual:

- The preview exits 0 with `2 ready`. Both rows are `new` with `reason:
  null`. Below the diff it prints `Proposed append (not written): Invalid
  reference to inactive account 'Expenses:Dining' … Account closed
  2026-01-03 at main.bean:7.`
- `--apply` exits **1** (`validation`) with `Import would leave the ledger
  invalid; nothing was written.` The valid Whole Foods row is not written
  either.
- With `Expenses:Dining` opened on `2026-02-01` instead, after the row's
  `2026-01-06` date, the result is the same.

Reproduced in three fresh directories.

Control: with `Expenses:Dining` never opened, row 2 is `blocked` with a
`bea add open` remedy, the preview counts `1 ready`, and `--apply` exits 4.

Expected: `docs/IMPORTING.md` says blocked rows are left out of ready and
out of writes, and that `--apply` exits 4. w3/276 set the rule that a
preview must not call a row ready if writing it would fail. An account
that is inactive on the row's date fails the same way, so it should be
treated the same way:

- show the row as `blocked`, naming the open or close date and its
  location;
- give a remedy that fits: re-date the close or map the rule to an open
  account; for a late open, re-date the open to the earliest use, as in
  w5/076;
- leave the row out of `ready`, and exit 4 on `--apply`.

Cause: `_open_currencies` (`cli/src/bea_engine/importing.py:893-906`)
collects every `Open` regardless of date and never reads `Close`.
`_blocked_reason` (`:948-997`) only tests `account not in
open_currencies`.

Fix: record each account's open and close dates next to its currencies,
and in `_blocked_reason` block a posting whose account is not active on
`entry.date`, with the remedies above. No dependency or API change.

Blast radius: `import` preview and `--apply`, for CSV (rules, category
column, `--default-account`) and for Python importers, whenever a counter
or source account is closed before a row's date or opened after it.

Dedupe: searched `.pm/**`, including `done/`, for "inactive account",
"closed account", close together with import or blocked, and
`_open_currencies`. Related notes cover adjacent cases:

- w3/276: never-opened accounts.
- w5/076: the remedy date for those.
- w5/222: wording for plugin-generated closes.
- w5/124: rescan cost.

None of these covers an account that is open but inactive.

Acceptance: on the fixture, the preview shows row 2 as `blocked`, naming
the close at `main.bean:7`, and counts `1 ready`. `--apply` exits 4 and
writes nothing. The late-open variant blocks the same way and names the
open date. A real-command regression test covers a closed account, a
late-opened account, and the never-opened control. Only macOS and the
checkout were exercised.
