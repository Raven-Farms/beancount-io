# `add` exits 0 on a ledger that `check` now rejects for data-type errors, without `--allow-errors`, and the write adds another such error (gap next to w5/493)

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-16, HEAD `06e9ca0f`, checkout `bea 0.3.1`, macOS 26.5.1. Related to w5/493 (fix `06e9ca0f`) and w5/564.
After the w5/493 fix, `bea --json check` reports Beancount's data-type
validation errors. USAGE says a ledger with errors "refuses every write …
Pass --allow-errors", and that "a write that exits 0 introduces no new `bea
check` error". The write path's validation never runs those validations, so
it sees a clean ledger before and after. No product fix implemented.

The w5/493 fixture: `notags.py` (a plugin that sets every transaction's tags
to `None`) and a `main.bean` that loads it with one transaction.

```sh
bea --json -f /abs/main.bean check
bea -f /abs/main.bean add transaction X --date 2024-01-06 -p 'Expenses:Food 5 USD' -p 'Assets:Cash'
bea --json -f /abs/main.bean check
```

Actual: the first check exits 1 with `main.bean:5: Invalid data types: Invalid
tags type: <class 'NoneType'>`; the `add` exits 0 (`Added 1 transaction`) with
no `--allow-errors`; the second check reports 2 errors.

Expected: the `add` refuses with the existing-errors message (exit 1, `Pass
--allow-errors to write anyway`), and with the flag it still refuses a write
that adds a new data-type error.

Cause: `HARDCORE_VALIDATIONS` run only in the check path
(`cli/src/bea_engine/main.py:_validate`, around `:888`); `validate_candidate`
(`cli/src/bea_engine/ledger/write.py`, around `:1460`) never runs them.

Fix: run the same validations in the write gate's before and after loads
(sharing the code that w5/493 added).

Dedupe: w5/493 (fixed, note open) and w5/564 (open, cache path) cover `check`.

Acceptance: the `add` exits 1 without the flag; with it, the new error is
refused. A test pins both.
