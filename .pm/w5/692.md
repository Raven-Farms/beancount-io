# Importing history from before init's date blocks each row on one inactive account at a time, and the remedy never mentions the `Opening balances` transaction, which then counts the history twice

**Minor · cli · 15m · A1.** Real CLI QA, 2026-10-17, HEAD `101b89e3`, checkout `bea 0.3.1`, macOS 26.5.1. Follows w5/339 (done).
A newcomer who accepts init's default date (today) and then imports last
month's bank export gets every row blocked. That is correct (w5/339), but the
remedy takes several rounds and leaves the books wrong. No product fix
implemented.

```sh
bea --no-input init books --currency USD --date 2026-10-17 --opening-balance "Assets:Checking 800"
printf 'Date,Description,Amount\n2026-09-28,Trader Joes,-55.10\n2026-10-02,Payroll,1500.00\n' > sep.csv
bea --file /abs/books/main.bean import sep.csv --account Assets:Checking
```

Actual:

1. Round 1 exits 0, `0 ready … 2 blocked`. Each row says only `Account
   'Assets:Checking' opens 2026-10-17 (at …/main.bean:6), after this row's
   2026-09-28. Re-date that open to 2026-09-28 or earlier.` Each row also posts
   to `Expenses:Uncategorized`, which opens the same day.
2. After re-dating that open, round 2 blocks every row again on
   `Account 'Expenses:Uncategorized' opens 2026-10-17 (at …:18)`. With rules,
   each rule account takes another round. `--apply` exits 4 with the same
   details.
3. After both opens are re-dated, `--apply` writes. Checking then reads
   2244.90 USD: the stated 800 plus the imported history. The `Opening
   balances` transaction is still dated 2026-10-17, after the imported rows,
   and no message mentions it.

Control: `bea add transaction` with the same back-dated postings names both
inactive accounts in one refusal.

Expected: one blocked reason naming every inactive account in the row. When
the source account carries init's `Opening balances` entry on its open date,
also say to move or restate that entry. Init's prompt says opening balances
"must be as of this date", and USAGE:396-398 says to "edit the relevant account
opens and ensure the opening balances still describe that history".

Cause: `_inactive_reason` (`cli/src/bea_engine/importing.py:1332`, called at
`:1299`) returns on the first inactive account.

Fix: collect every inactive account per row into one reason (the earliest
date for each). Add the opening-balance remedy when an opening-balance
transaction sits on that open date.

Dedupe: w5/339 (done) created the blocked state; w5/636 (open) covers staging
file names. Neither covers the remedy.

Acceptance: round 1 names both accounts, and the remedy mentions the
opening-balance transaction. A test pins both.

Addendum (CLI QA 2026-10-17, HEAD `473bce6af`): a missing account hides an inactive
one too. With `fut.bean` = `2027-06-01 open Assets:Cash USD` and a 2026-03-01
CSV row, the preview gives only `Row 1: Account 'Expenses:Uncategorized' is not
open. Run: …`. After that remedy, the rerun reveals `Account 'Assets:Cash' opens
2027-06-01 …, after this row's 2026-03-01.` The "not open" reason returns
before the inactive check (`cli/src/bea_engine/importing.py`, around
`:1530-1544`). The combined reason this note asks for should include missing
accounts as well as inactive ones.
