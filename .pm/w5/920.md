# Treat signed zero as equal in import amounts and prices

**Major · cli · 30–45m · A1.** A zero-value bank row carrying `-0.00` is
accepted and written, then falsely conflicts on an unchanged repeat. It can
block the rest of an overlapping export, including new nonzero payments.
An equal signed-price change also defeats generated IDs and writes a second
stock disposal: loss 200 / cost net worth 800 USD instead of 100 / 900.
See the price extension below. No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `a9922ee5f`, checkout `bea 0.3.1`, macOS
26.5.1 arm64, frontend Python 3.13.3; existing managed Python 3.12 engine.
Synthetic fixtures, fresh subprocesses, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited
`BEA_FILE`/`BEA_TOKEN`. CSV and Python-importer cases reproduced twice.

Create disposable `/abs/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

Create `bank.csv`:

```csv
Date,Description,Amount,Reference
2024-02-01,No charge,-0.00,zero-1
```

Run this twice from `/abs/books` with the isolated child environment above:

```sh
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --csv date=Date,narration=Description,amount=Amount,id=Reference,decimal=point --account Assets:Cash --default-account Expenses:Food --apply
```

First: exit 0, writes one row with `bank_id: "zero-1"`,
`import-id: "bank:zero-1"`, `Assets:Cash -0.00 USD` and its zero
counterposting. Second: exit **4**, stdout empty, JSON stderr reports
`Stable ID matches an entry with different transaction data`. Preview calls
the unchanged row a conflict. `--duplicates include` still refuses; all
rejected calls preserve ledger bytes. Fresh `check` passes, and this query
returns `[[1, "0.00"]]`:

```sh
bea --json -f /abs/books/main.bean query "SELECT count(*), sum(number) WHERE account='Assets:Cash'"
```

Expected: the repeat is an exact duplicate, writes zero, exits 0. Zero and
negative zero are the same monetary value; the documented native-ID guard
requires different source amounts or commodities to conflict. Native loading
the written negative zero as positive zero is expected and should stay.

Controls and blast radius:

- In 20 fresh amount-notation journeys (two repetitions, point/USD and
  comma/EUR, five sign modes), all **360** first-import amounts and signs
  matched independently calculated values. Twelve repeats falsely conflict
  only on negative-zero source legs. This includes bank-sign `-0.00`,
  `sign=ledger` on `0.00`, and `direction=Type` with `DEBIT` on zero.
  The remaining rows, including grouped amounts, symbols, parentheses,
  trailing minus and Unicode minus, repeat correctly. Debit/credit pair
  controls without a zero-only row repeat correctly.
- Sixteen smaller CSV journeys cover these failures and working positive-zero,
  opposite ledger-sign, `CREDIT` zero and generated-hash controls. Omitting
  `id=Reference` from the unchanged negative-zero row correctly skips it.
  Actually changing zero to `-0.01` under the same native ID correctly
  conflicts; preserve that guard.
- Eight additional journeys include an inspected Python importer returning
  `Decimal('-0.00')` with `bank_id`: it also falsely conflicts, while its
  positive-zero control skips. Human output reproduces the refusal. Appending
  a new `Coffee,-4.50,coffee-1` row after the first zero import previews one
  conflict and one ready row, but apply exits 4 and books neither: Cash stays
  0.00 instead of reaching −4.50 USD. Every fresh check passes, and refused
  writes preserve the ledger.

Cause: `cli/src/bea_engine/importing.py:_exact_amount` (:2230–2252) claims
equal values render identically, but `Decimal.normalize()` retains zero's
sign. `_legs` (:1386–1391) therefore renders the incoming amount as
`-0 USD`, while its native-loaded copy is `0 USD`. `_same_row`
(:1754–1775) calls `_legs_agree` (:1400–1418), which compares those strings
and reports a changed amount. The shared `answer` path affects both CSV and
Python importers. Caller search also finds this renderer in generated hashes,
source-amount previews, prices and transfer amount keys; do not change their
identity compatibility accidentally.

Fix: canonicalize zero's sign for monetary comparison so an unchanged native
ID does not conflict solely on zero's spelling. Keep nonzero digits exact,
commodity distinctions, genuine amount-change refusals, existing generated-ID
lookup compatibility and authored ledger bytes. Do not drop accepted zero rows
or change the native loader to retain a negative zero.

Dedupe: searched all board states for signed/negative zero and native IDs,
reimport, fingerprints and identity; scanned active milestone scopes and
targeted history. Completed w5/217 changes rounded report text, w5/697 changes
init's cancelling opening total, and w5/729 normalizes typed custom values;
none repairs import comparison. w3/408 preserves exact CSV sign changes,
including zero. The exact-amount helper came from `4e5c6ec51` (w1/160).
Completed [881](./done/881.md) recovers exact written evidence when a plugin
or wide-number load changes real source facts; this case instead needs numeric equality for
two spellings of the same zero, without recovering a different source amount.
No overlapping open repair or deployment lag found.

Acceptance: native-ID CSV and Python negative-zero repeats skip at exit 0;
bank, ledger-sign and direction mappings work for USD and EUR. An overlapping
export can skip the existing zero and import its new −4.50 payment. Positive
zero, generated hashes, ordinary nonzero sign/notation controls and the genuine
`-0.01` conflict remain correct. Verify fresh BQL, check and unchanged bytes on
duplicate/refused runs. Only macOS/checkout tested; repaired behavior unverified.

## Also affected: signed disposal prices can book the same sale twice

Additional real CLI QA, 2026-10-22, clean main `e82202686` (initial
reproduction on `dc6748182`; signed-amount renderer unchanged), same
checkout/managed versions and isolated child-process environment above.
This extends the same `_exact_amount` repair, and raises severity because
the generated-ID case appends another sale. No product fix implemented.

The source quantity is **−1 HOOL**, never a zero-unit transaction. One lot
holds two shares costing 100 USD each; cash is 800 USD. A legitimate
zero-proceeds disposal reduces it to one share, with a 100 USD realized
loss and cost-basis net worth 900 USD. The inspected importer supplies all
counter amounts explicitly, avoiding the separate [926](./926.md) sentinel
problem.

Put the checkout's `bea` on PATH and replace `/abs/case` below with a fresh
absolute disposable directory. The default uses a generated ID and changes
only the mathematically equal price spelling from `0.00` to `-0.00` after
the first real apply:

```python
import json, os, re, subprocess
from pathlib import Path
case = Path('/abs/case')
case.mkdir(parents=True)
ledger = case / 'main.bean'
ledger.write_text('''option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Stock HOOL "FIFO"
2024-01-01 open Equity:Opening USD
2024-01-01 open Income:Gains USD
2024-01-01 * "Capital"
  Assets:Cash 1000.00 USD
  Equity:Opening -1000.00 USD
2024-01-02 * "Buy"
  Assets:Stock 2 HOOL {100 USD, "Lot"}
  Assets:Cash -200.00 USD
''')
use_native_id = False
initial_price = '0.00'
later_price = '-0.00'
seed_old_hash = False
config = case / 'importer.py'
config.write_text('''import datetime, json
from decimal import Decimal as D
from pathlib import Path
from beancount.core.amount import Amount
from beancount.core.data import Transaction, Posting, new_metadata
from beancount.core.position import CostSpec
class Sales:
    name = 'signed-zero-disposal'
    def identify(self, file): return str(file).endswith('.json')
    def account(self, file): return 'Assets:Stock'
    def extract(self, file, existing_entries=None):
        row = json.loads(Path(file).read_text())
        price = D(row['price'])
        cash = abs(price)
        meta = new_metadata(str(file), 1)
        if row['native']: meta['bank_id'] = 'disposal-1'
        return [Transaction(meta, datetime.date(2024, 2, 1), '*', None,
            'Disposal', frozenset(), frozenset(), [
            Posting('Assets:Stock', Amount(D('-1'), 'HOOL'),
                CostSpec(D('100'), None, 'USD', None, 'Lot', False),
                Amount(price, 'USD'), None, None),
            Posting('Assets:Cash', Amount(cash, 'USD'), None, None, None, None),
            Posting('Income:Gains', Amount(D('100')-cash, 'USD'), None, None, None, None)])]
CONFIG = [Sales()]
''')
config_bytes = config.read_bytes()
source = case / 'sale.json'
source.write_text(json.dumps({'native': use_native_id, 'price': initial_price}))
env = os.environ.copy()
for key in ('BEA_FILE', 'BEA_TOKEN', 'BEANCOUNT_LOAD_CACHE_FILENAME',
            'BEA_ENGINE_PYTHON', 'BEA_ENGINE_DIR'):
    env.pop(key, None)
env.update(BEA_CONFIG_DIR=str(case / 'config'), XDG_CACHE_HOME=str(case / 'cache'),
           BEA_NO_UPDATE_NOTIFIER='1')
def run(tag, args, json_mode=True):
    argv = ['bea', *(['--json'] if json_mode else []), '--no-input', '-f', str(ledger), *map(str, args)]
    result = subprocess.run(argv, cwd=case, env=env, stdin=subprocess.DEVNULL,
                            capture_output=True, text=True, timeout=25)
    print(json.dumps(dict(tag=tag, args=argv, exit=result.returncode,
                         stdout=result.stdout, stderr=result.stderr)), flush=True)
run('baseline-check', ['check'])
args = ['import', source, '--config', config]
run('first-apply', [*args, '--apply'])
if seed_old_hash:
    assert not use_native_id and initial_price == later_price == '-0.00'
    text = ledger.read_text()
    ids = re.findall(r'^  import-id: "csv:sha256:[0-9a-f]{16}"$', text, re.M)
    assert len(ids) == 1
    ledger.write_text(text.replace(ids[0], '  import-id: "csv:sha256:ed28b5cce117a339"'))
authored = ledger.read_bytes()
source.write_text(json.dumps({'native': use_native_id, 'price': later_price}))
source_bytes = source.read_bytes()
run('human-preview', args, json_mode=False)
run('preview', args)
assert ledger.read_bytes() == authored
run('apply', [*args, '--apply'])
run('repeat', [*args, '--apply'])
run('positions', ['query', 'SELECT account,sum(number) GROUP BY account ORDER BY account'])
run('cost-profit', ['report', 'income-statement', '--time', '2024-02', '--conversion', 'at_cost'])
run('cost-sheet', ['report', 'balance-sheet', '--time', '2024-02', '--conversion', 'at_cost'])
run('check', ['check'])
assert ledger.read_bytes().startswith(authored)
assert config.read_bytes() == config_bytes and source.read_bytes() == source_bytes
```

All ten default commands exit **0**. The first apply writes one disposal.
After the equal signed-price change, preview wrongly says **ready 1 /
duplicates 0 / possible_duplicates 0**; human preview calls it new. Apply
writes **1** more sale under another generated ID. Its exact repeat then
skips, leaving:

```text
Assets:Cash       800.00 USD
Assets:Stock        0 HOOL
Equity:Opening -1000.00 USD
Income:Gains      200.00 USD
```

Cost-basis reports show **loss 200 / net worth 800 USD** instead of **100 /
900** after the one disposal; the sheet reconciles, check passes, and the
first sale remains an unchanged prefix. The source JSON changes only its
price's zero sign; configuration bytes stay fixed. Two bounded sales use the
two available shares; no oversold-inventory limit was exercised.

The same price field also causes a native-ID false conflict: in a fresh
fixture set `use_native_id = True` and both prices to `'-0.00'`. An unchanged
preview then reports conflict 1, and both applies exit 4 while preserving
one sale / one remaining share / loss 100 / cost net worth 900. Its positive
zero control (`use_native_id = True`, both prices `'0.00'`) skips correctly.

Other working controls: generated IDs with both prices `'0.00'`, or both
`'-0.00'`, skip unchanged repeats and keep the correct figures. For the latter,
`seed_old_hash = True` explicitly preserves the old negative-price digest
`csv:sha256:ed28b5cce117a339`, so future regressions test an already-authored
pre-repair ID rather than regenerate only new IDs. On the current code the
first real apply already produces that exact digest: the seed is a no-op.
Keep that authored ID and bytes on repaired reimport. A native-ID change
from `'0.00'` to `'0.01'` still correctly conflicts; its adjusted cash and gain
make it a valid but genuinely changed disposal. Independent native loading
confirms that 0.01-price source is bookable on the fresh starting inventory.

Runtime evidence:

- Twelve fresh price journeys (**84 CLI calls**), twice each of native
  negative/positive unchanged, generated positive-to-negative, generated
  negative/positive unchanged, and the genuine native 0.01-price change.
  Only the equal generated sign change appends another disposal; native
  negative-price repeats falsely conflict. Positive controls and unchanged
  negative generated IDs skip. Every rejected apply and preview preserves
  the ledger and all inspected configuration bytes stay fixed.
- **24 cost-basis reports** and **14 independent unwrapped native graph
  references** agree on remaining shares, cost inventory, realized loss and
  worth. The extra two native graphs validate the genuine 0.01-price input.
- Four direct price/hash/native-owner controls confirm the mechanism below.
  The exact public recipe was also replayed twice with JSON/human apply,
  positive controls, old generated-ID preservation and genuine-change control;
  the original Cash negative/positive-zero recipes were rechecked too.

Further cause: `_price_text` (`importing.py:1379–1383`) reuses `_exact_amount`
(`:2353–2378`) and embeds ` @ -0 USD` or ` @ 0 USD` in both `_legs` and the
canonical hash's source-amount text. Direct controls prove numeric prices
are equal, source units are −1 on both sides and loaded prices are positive
zero, yet their canonical IDs are respectively
`csv:sha256:ed28b5cce117a339` and `csv:sha256:a16796b4da2b06a3`.
Both IDs occur on the duplicated actual ledger entries. Price-bearing
fingerprints/twin keys differ too, so the generated sign change is called
new rather than even a possible duplicate. With a native ID, both the
loaded and raw written owner exist but `_same_row` wrongly rejects them
solely on those price strings. Completed 881's raw-source fallback cannot
repair numeric inequality introduced by this renderer.

Extend the repair to zero-valued prices wherever they affect comparison,
generated IDs, twin/counterpart keys and preview amounts. Canonicalize zero's
sign while preserving source units, commodities and every nonzero price.
Preserve existing signed-zero generated digests as lookup-compatible IDs;
changing the canonical renderer must not turn an unchanged old import into
another new row. Do not erase price fields or rewrite authored IDs.

Dedupe: whole-board signed-price/zero/identity searches found this open item;
its caller analysis already names prices and generated hashes. The price
journeys above now prove those consumers. [975](./975.md) loses transfer
history and [976](./976.md) ignores native transfer reservations; these are
one-account stock-source disposals without transfers. Extend 920, not a new
finding.

Additional acceptance: default equal-price replay skips with one remaining

original. Keep the original Cash amount/overlap controls and run
