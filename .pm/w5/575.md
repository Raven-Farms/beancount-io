# Text-mode `bea query` takes about twice as long as `--json` on large ledgers (1.8 s vs 0.9 s at 60k transactions, 8.8 s vs 4.7 s at 300k): the shell keeps every entry alive until interpreter shutdown

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-16, HEAD `3514cc17`, checkout `bea 0.3.1`, macOS 26.5.1.
Upstream `BQLShell.__init__` sets `warnings.showwarning = self.warning`. The
one-shot shell bea builds for text answers therefore stays reachable through
the `warnings` module, along with its context and all entries, and they are
freed only during interpreter finalization. The answer is ready at the same
time as with `--json`; the extra seconds are teardown. No product fix
implemented.

A synthetic ledger of ~60,000 transactions (`include "txns/*.bean"`, one large
member), loaded once so the cache is warm.

```sh
bea -f /abs/main.bean query "SELECT account FROM #accounts LIMIT 2"
bea --json -f /abs/main.bean query "SELECT account FROM #accounts LIMIT 2"
```

Actual: text 1.78 s and 1.76 s; `--json` 0.94 s and 0.92 s. At 300k
transactions: 8.75 s against 4.69 s. Wrapping the engine shows its main
function returns at 3.8 s while the process exits at 8.3 s, with ~440,000
objects alive (about 28,000 for `check`).

Control: `--json query`, `check`, `balance` and `list` exit promptly. A
sitecustomize atexit hook that restores `warnings.showwarning` and collects
brought the 300k text query to 4.47 s.

Expected: about the cost of `--json`.

Cause: `build_shell` / `text_answer` (`cli/src/bea_engine/query.py`, around
`:185-235` and `:928`) construct a `PreciseShell` whose `showwarning` hook
outlives the answer.

Fix: save and restore `warnings.showwarning` around the one-shot shell (or
drop the shell before returning), so the entries are freed normally. Check
the interactive shell's exit too.

Dedupe: searched `showwarning`, `finaliz`, `query slower`. No match.

Acceptance: text and `--json` timings for the fixture are within ~10%. A test
asserts the hook is restored after a one-shot text query.
