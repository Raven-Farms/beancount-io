# The generated `csv:sha256` import-id hashes a tab in the description as the literal text `\X09`, not as whitespace collapsed to a space as IMPORTING.md and dedup.md define

**Minor · cli · 10m · A1.** Real CLI QA, 2026-10-17, HEAD `0e9729be5`, checkout `bea 0.3.1`, macOS 26.5.1.
IMPORTING.md:471 says the description is "uppercased with whitespace
collapsed", and dedup.md:30 says "runs of whitespace collapsed to one space".
No product fix implemented.

`tab.csv` is `Date,Description,Amount` / `2026-01-10,"POS<TAB>STARBUCKS",-9.00`.

```sh
bea --file /abs/main.bean import tab.csv --account Assets:Checking --apply
```

Actual: it writes `"POS\\x09STARBUCKS"` with `import-id:
"csv:sha256:792956864926c2e6"`, which is sha256 of
`2026-01-10|-9 USD|POS\X09STARBUCKS|Assets:Checking`. The documented input
`2026-01-10|-9 USD|POS STARBUCKS|Assets:Checking` gives `967710cea24faf54`.
Ids from earlier versions and from skill-computed hashes therefore miss. In
the hunter's run, a re-import against a 0.3.0-style entry was reported as
`possible_duplicate`, which needs `--duplicates`. Bidi characters are hashed
in their escaped form the same way.

Control: `POS STARBUCKS` with a plain space hashes as documented.

Expected: hash the description as documented, with whitespace controls
collapsed to one space before escaping.

Cause: `_hash_rows` (`cli/src/bea_engine/importing.py:1461`) hashes the entry
after `normalize_entry_strings`. `single_line`
(`cli/src/bea_engine/ledger/text.py:37`) has already escaped `\t` to `\x09`
before `.upper().split()`.

Fix: hash the description before escaping, and accept the escaped spelling as
a lookup-only key for ids written since 0.3.1.

Dedupe: w5/733 (open) is the same escaping side effect for lot labels.

Acceptance: the fixture's id is `967710cea24faf54`, and a row written with the
escaped id still dedupes. A test pins both.
