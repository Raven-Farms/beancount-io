# A remembered `encoding=cp1252` is replayed onto a later UTF-8 export, writing mojibake (`CafÃ© ZÃ¼rich`) with exit 0

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-12, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
One statement in Windows encoding is imported with `encoding=cp1252`. The
bank's next export, same header, is UTF-8. The flag-free import decodes it
with the remembered codec and writes `CafÃ© ZÃ¼rich` to the ledger, exit
0. The import id is hashed from the corrupted text, so a later correct
re-import will not recognise the row, and rules with accented patterns stop
matching. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Assets:Savings USD
2026-01-01 open Expenses:Food
2026-01-01 open Expenses:Uncategorized
```

Create the two statements (bytes matter):

```sh
printf 'Date,Description,Amount\n2026-01-05,Caf\xe9 Z\xfcrich,-3.00\n' > jan.csv            # cp1252
printf 'Date,Description,Amount\n2026-02-05,Caf\xc3\xa9 Z\xc3\xbcrich,-4.00\n' > feb.csv  # UTF-8
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME (fresh), BEA_NO_UPDATE_NOTIFIER=1,
no inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean import jan.csv --csv date=Date,amount=Amount,narration=Description,encoding=cp1252 --account Assets:Checking --apply
bea -f main.bean import feb.csv --apply
```

Actual: both exit 0. The ledger gains `2026-01-05 ! "Café Zürich"` and
then `2026-02-05 ! "CafÃ© ZÃ¼rich"`. The second run's settings line ends
`--csv encoding=cp1252`. A worker saw a UTF-8 file with a BOM fail instead
(exit 2, the header no longer matches).

Control: with a fresh config directory, `bea -f main.bean import feb.csv
--account Assets:Checking --apply` writes `2026-02-05 ! "Café Zürich"`.

Expected: `docs/IMPORTING.md`: "Files read as UTF-8 (with or without a
BOM) unless `--csv encoding=` names cp1252 or latin-1". The same document
re-validates the remembered `--date-format` against each new file because
two exports can share a header without sharing a convention; encoding is
the same kind of per-file property. A file that is valid UTF-8 with
multi-byte sequences is not cp1252.

Cause: `cli/src/cli/commands/import_.py:597` strips only `sign` from the
stored mapping, so `encoding=` is saved; `:426` replays it and `:503-504`
take the codec from it. `_recall_csv` (`:205-215`) has already read the
header as UTF-8 and nothing uses that fact; the only re-validation is for
the date format (`:530-544`).

Fix: on a recalled run, decode as UTF-8 when the file is valid UTF-8 and
fall back to the remembered codec only when it is not; or refuse, naming
the remembered `encoding=`. No dependency change.

Blast radius: any header remembered with `encoding=cp1252` or `latin-1`.
The typed override, key-only `--csv encoding=utf-8`, runs into w5/078.

Dedupe: board search for mojibake, cp1252, latin-1 and `encoding=` with
remembered finds w5/077 (a detected delimiter replayed, which fails
safely), w5/078 (key-only `--csv`), w1/m24/t002 (which asked for the
encoding to be remembered); none covers a replayed encoding corrupting
text.

Acceptance: the second command writes `"Café Zürich"` (or exits 2 naming
the remembered encoding); a cp1252 file after it is still read with the
remembered codec. Only macOS and the checkout were exercised.
