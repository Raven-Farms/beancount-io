# `--allow-errors` refuses every write when the existing error is a non-syntax parser diagnostic such as an invalid option

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, Beancount 3.2.3, macOS.
A ledger with a pre-existing "Invalid option" (or, per a worker,
"Duplicate metadata field") diagnostic cannot be written to at all:
`--allow-errors` is refused with "The change would leave the ledger
invalid", listing only the old error. These are not syntax errors — every
entry loads — but `bea` classes them with syntax errors, which the docs
say are always refused. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
option "experiment_explicit_tolerances" "TRUE"

2026-01-01 open Assets:Cash USD
2026-01-01 open Equity:Opening

2026-01-02 * "Open"
  Assets:Cash  100.00 USD
  Equity:Opening
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean add note --date 2026-02-01 -a Assets:Cash -m hi --allow-errors
```

Actual: exit 1, file unchanged: `Error: The change would leave the
ledger invalid; nothing was written.` with the single detail
`main.bean:2: Invalid option: 'experiment_explicit_tolerances'`.

Control: a ledger whose only error is a failing `balance` assertion
accepts the same command with exit 0 and prints the old error as a
warning. A worker saw the refusal for duplicate metadata keys and for
`add price`, a deprecated option tolerated, and `list --allow-errors`
answer on the same ledgers.

Expected: `docs/USAGE.md` says every add "accepts `--allow-errors` for a
semantic error already in the books" and that only "Syntax errors and pad
references to unknown or inactive accounts are always rejected." The
write adds no error; at minimum the refusal should say that this class
cannot be tolerated.

Cause: `cli/src/bea_engine/ledger/write.py:769` treats any `ParserError`,
`ParserSyntaxError` or `LexerError` as a syntax error. Upstream uses
`ParserError` for grammar-action diagnostics (invalid option, duplicate
metadata, unbalanced push/pop); real syntax failures are the other two.

Fix: restrict the always-refuse set to `ParserSyntaxError` and
`LexerError`, plus any `ParserError` the before/after comparison shows as
new; otherwise name the blocking class in the message. No dependency or
API change.

Blast radius: every validating writer; `add note`, `add price` and `add
transaction` were run.

Dedupe: w5/079, 096, 144, 150 and 153 are other false `--allow-errors`
refusals with different causes; board search for "Invalid option" and
"Duplicate metadata" finds nothing.

Acceptance: the command exits 0 and prints the invalid-option error as a
warning; a ledger with a real syntax error is still refused. Only macOS
and the checkout were exercised.
