# A failed stdout write (disk full, file too large, I/O error) exits with the undocumented status 120 and Python's "Exception ignored on flushing sys.stdout", or with a raw `[Errno 27]` and category `validation`; `doctor` prints a traceback

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
A `BrokenPipeError` on stdout is handled: exit 141 and fd 1 repointed to
`/dev/null`. Any other `OSError` while writing stdout goes to the
generic error path. That path prints the raw `[Errno N] …` with category
`validation`, and leaves stdout's buffer unflushed. At shutdown CPython
retries the flush, fails again, prints `Exception ignored on flushing
sys.stdout`, and replaces the exit status with 120. Commands that already
flushed exit 1 with the raw errno text. Forwarded `doctor` passes through
upstream's traceback. None of these messages says that writing the output
failed. No product fix implemented.

macOS has no `/dev/full`, so a 512-byte file-size limit forces `EFBIG`
on stdout. That is the same `OSError` path as `ENOSPC` or `EIO`. Use
isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, and any ledger with enough
transactions to print more than 512 bytes.

```sh
( trap "" XFSZ; ulimit -f 1; bea --help >out 2>err ); echo $?
( trap "" XFSZ; ulimit -f 1; bea -f /absolute/books/main.bean list transaction --limit 6000 >out 2>err ); echo $?
( trap "" XFSZ; ulimit -f 1; bea -f /absolute/books/main.bean query "SELECT date, narration, position" >out 2>err ); echo $?
( trap "" XFSZ; ulimit -f 1; bea doctor lex /absolute/books/main.bean >out 2>err ); echo $?
```

Actual:

- `--help`, `list`, `report`, `--json balance` and `check -v` exit
  **120**. stderr reads `Error: [Errno 27] File too large`, `Exception
  ignored on flushing sys.stdout:`, `OSError: [Errno 27] File too large`.
- `query`, `format`, `example` and `--json list` exit 1 with `Error:
  [Errno 27] File too large`, or JSON category `validation`.
- `doctor lex` exits 120 with a full upstream traceback.

Reproduced twice by the hunter, and by me for `--help` and `list`.

Control: the same commands writing to a normal file exit 0. `| head -c
1` exits 141 silently. Closed stdout (`>&-`) exits 0 (w1/107).

Expected: `docs/USAGE.md` says "These five codes are the whole table …
rather than passing … through as an undocumented status". The only
exceptions are 130 and 141. A write failure should exit 1 with a bea
sentence such as `Could not write output: File too large (errno 27)`,
without "Exception ignored" or a traceback (w3/298, w5/089).

Cause:

- `_GuardedGroup.invoke` (`cli/src/cli/main.py:197-198`) sends non-pipe
  `OSError`s to `output.error`, which prints `to_bea_error(exc)` (raw
  `str`, category `validation`; `cli/src/cli/errors.py:197`).
- Only `_exit_on_broken_pipe` (`main.py:72-90`) repoints fd 1, so the
  shutdown flush fails again and exits 120 (see `_settle_stdout`,
  `:55-70`).
- Forwarded natives pass through the child's traceback.

Fix:

- Catch an `OSError` from writing or settling stdout. Report
  `Could not write output: <strerror>` with exit 1, then repoint fd 1 to
  `/dev/null` as the pipe path does.
- Map a forwarded native's write failure to the same sentence.
- No dependency change.

Blast radius: every command when stdout lands on a full disk, a quota
limit or a failing device, or under file-size limits. Scripts get an
undocumented 120.

Dedupe: searched `.pm/**`, including `done/`, for 120, "Exception
ignored", `/dev/full`, ENOSPC, EFBIG and "File too large". Related notes:

- w1/107 and w5/258: closed streams.
- w3/440 and w5/014: signals.

None covers a failed stdout write.

Acceptance: under the file-size limit, each command exits 1 with the
write-failure sentence on stderr, no "Exception ignored", and no
traceback. JSON category is not `validation`. A test simulates `EFBIG`
on stdout.
