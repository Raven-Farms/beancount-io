# A transfer imported from both banks is double-booked whenever the two banks describe it differently ("TRANSFER TO SAVINGS" / "TRANSFER FROM CHECKING"); the import skill promises the mirrored row "will surface as a fuzzy suspected duplicate", but neither its fuzzy layer nor the CLI can see it

**Major · cli + skills · 30–45m · A1.** Real CLI QA, 2026-10-16, HEAD `5e09bcc4`, checkout `bea 0.3.1`, macOS 26.5.1. Reproduced on the m10 migration fixture and on a minimal ledger.
`skills/.claude/skills/beancount-import/references/categorization.md` (around
line 26) tells the agent to warn the user that importing the other account's
export will show the mirrored row as a fuzzy suspected duplicate, to be
skipped there. The skill's Layer 2 (`references/dedup.md`, around line 61)
examines only entries **lacking** an `import-id`, and the first side has one.
The CLI flags only an identical payee or narration (IMPORTING.md). So the
ordinary checking/savings transfer, worded differently by each bank, is
booked twice. This is the journey m10 was meant to make safe after a
migration. No product fix implemented.

`main.bean`: opens for `Assets:Checking`, `Assets:Savings`,
`Expenses:Uncategorized` (USD). `c.csv`: `2026-04-10,TRANSFER TO
SAVINGS,-200.00`; `s.csv`: `2026-04-10,TRANSFER FROM CHECKING,200.00` (header
`Date,Description,Amount`). Rules map each to the other account.

```sh
bea --file /abs/main.bean import c.csv --csv date=Date,narration=Description,amount=Amount --account Assets:Checking --rules c.toml --apply
bea --file /abs/main.bean import s.csv --csv date=Date,narration=Description,amount=Amount --account Assets:Savings  --rules s.toml --apply
bea --file /abs/main.bean balance Assets
```

Actual: both exit 0 with `1 ready, 0 exact duplicates, 0 possible
duplicates`; Checking `-400.00`, Savings `400.00` for one 200 USD transfer.
On the migrated m10 ledger, `checking-may.csv` and `savings-may.csv` with the
fixture's own wordings move Checking to 2,045.80 and Savings to 1,901.25
(expected 2,245.80 and 1,701.25).

Control: identical descriptions on both sides (`ONLINE TRANSFER`) are flagged
`possible_duplicate` in either order.

Expected: the second side is surfaced for review before writing.

Fix (either or both):

- CLI: flag an existing entry where `--account` is a counter posting with the
  same date (± a day) and the opposite amount, from a different import
  identity, as a "possible transfer counterpart", whatever the description.
  Change `_candidate_key` (`cli/src/bea_engine/importing.py:1636`) or add a
  second key.
- Skill: let Layer 2 include imported entries whose source account is only a
  counter posting, and correct the categorization promise to match.

Dedupe: searched `mirrored`, `both sides of`, `second side`. m10 (done)
covered migrated pairs only.

Acceptance: the second import reports the transfer as a possible duplicate
in both orders, and the m10 May fixtures end at 2,245.80 / 1,701.25 after
skipping it. Tests (CLI and skills eval) pin it.
