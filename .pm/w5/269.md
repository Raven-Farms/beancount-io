# `BEA_ENGINE_PYTHON` naming an interpreter without Beancount gives a raw traceback that never names the variable, and `bea add` exits 4 "outcome is unknown"

**Minor · cli · 30–45m · A1.** Real CLI QA, 2026-10-12, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
The docs say both engine overrides "are checked before use". That is true
for forwarded tools (`bea check` names the variable and the remedy) but
not for the helper path: `balance`, `list`, `query`, `report` print a
Python traceback ending `ModuleNotFoundError` with no mention of the
variable, and a write exits 4 claiming an unknown outcome although nothing
could have been written. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Cash USD
2026-01-01 open Expenses:Food USD
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`. `P` is any existing Python 3.12+ interpreter that cannot
import `beancount`.

```sh
BEA_ENGINE_PYTHON=$P bea -f main.bean balance
BEA_ENGINE_PYTHON=$P bea -f main.bean add transaction Lunch --date 2026-01-05 --posting "Expenses:Food 4.00 USD" --posting Assets:Cash
```

Actual: `balance` exits 1 with `Error: The Beancount engine did not answer
'bea-engine balance --file …' (exit 1).` followed by a nine-line traceback
ending `ModuleNotFoundError: No module named 'beancount'`, without
`--debug`. `add` exits 4: `… (exit 1); the outcome is unknown. Inspect the
file before retrying.`; the ledger is byte-identical.

Control: with the same variable, `bea -f main.bean check` exits 1 with
`BEA_ENGINE_PYTHON=… names an environment with no 'bean-check' (…).
Correct or unset BEA_ENGINE_PYTHON, or run 'bea engine status' …`. Without
the variable, `balance` exits 0.

Expected: `docs/USAGE.md`: "Both are checked before use: one that names a
path which does not exist, or an environment missing the tool being run,
fails with a message naming the variable and telling you to correct or
unset it."

Cause: `cli/src/cli/engine/launch.py:446-480` (`_parse`) reports any
helper exit without an envelope generically, and as a conflict (exit 4)
for writers; it never consults the override, unlike `native_command`
(`:276-284`). `helper_command` (`:486-505`) runs the override unchecked.

Fix: when an override is set and the helper produces no envelope, raise
the same "names an environment that cannot run the engine … Correct or
unset BEA_ENGINE_PYTHON" message, with the traceback only under `--debug`;
a writer that failed before starting is exit 1, not 4. No dependency
change.

Blast radius: every helper-path command while the override is set (tests
and recovery tooling, per the docs).

Dedupe: board search for `BEA_ENGINE_PYTHON`, "did not answer" and "names
an environment" finds w5/done/011 (the forwarded-tool path only) and
w1/done/122 (a damaged managed engine); nothing open.

Acceptance: both commands exit 1 with one message naming
`BEA_ENGINE_PYTHON` and the remedy, no traceback, and no "outcome is
unknown"; the `check` control is unchanged. Only macOS and the checkout
were exercised.
