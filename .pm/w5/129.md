# A bulk row with an invalid metadata key aborts the whole batch, defeats `--partial`, and does not name the row

**Minor · cli · 30–45m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`),
checkout `bea 0.3.1`, macOS.
In `add transactions`, a row whose metadata key Beancount's grammar rejects
(for example a capitalised `Category`) is not caught by row validation. The
batch fails later with a message about "0 directive(s)" that names neither
the row's field nor the key, exits 2 instead of 1, and `--partial` writes
nothing although the other rows are valid. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2020-01-01 open Assets:Cash USD
2020-01-01 open Expenses:Food
```

and `/absolute/books/rows.json`:

```json
[{"date":"2021-01-05","narration":"r1","postings":[{"account":"Expenses:Food","amount":"10 USD"},{"account":"Assets:Cash"}]},
 {"date":"2021-01-06","narration":"r2","meta":{"Category":"food"},"postings":[{"account":"Expenses:Food","amount":"11 USD"},{"account":"Assets:Cash"}]},
 {"date":"2021-01-07","narration":"r3","postings":[{"account":"Expenses:Food","amount":"12 USD"},{"account":"Assets:Cash"}]}]
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bea --json -f /absolute/books/main.bean add transactions --from /absolute/books/rows.json --partial
```

Actual: exit 2 with `{"error": {"category": "usage", "message": "Directive
2 of 3 would be written as 0 directive(s); a field holds a line break or a
value that is not one token. Nothing was written.", "exit_code": 2}}`. No
row is written. A worker saw the same for keys `c`, `a b`, `a.b`,
`1a`, `_a` and `é`, found the directive number counts surviving rows
rather than JSON rows, and found a key starting with `__` is silently
dropped with exit 0.

Control: replacing the bad key with a bad value (`"category": {"x": 1}`)
exits 1 with `Added 2 of 3 transactions; 1 row was rejected.`, details
`Row 2, meta.category: Unsupported metadata value …`, and
`"written_rows": [0, 2], "rejected_rows": [1]`. A worker confirmed the
single-add form says `Invalid --meta key 'Category'; keys must match
[a-z][A-Za-z0-9_-]*`.

Expected: `docs/USAGE.md` says "If any row is invalid the ledger is left
byte-identical and the command exits 1, listing the rejected rows.
`--partial` appends the valid rows instead" and "Schema errors show a human
row number, field path, and example".

Cause: `_bulk_meta_problems`
(`cli/src/bea_engine/ledger/adding.py:942`) checks reserved keys and values
but not the key grammar. The bad key first fails in
`require_one_entry_each` (`cli/src/bea_engine/ledger/write.py:1037`) as a
usage error, which neither the batch handler (`adding.py:1071`) nor the
per-row partial loop (`:1095`) catches. `metadata_for_write`
(`write.py:1263`) silently skips `__`-prefixed keys.

Fix: validate each bulk metadata key in `_bulk_meta_problems` with the
single-add rule and report `Row N, meta.<key>: …` as a per-row rejection;
reject `__` keys in write input instead of dropping them. No dependency or
API change.

Dedupe: board search for the message text and bulk metadata keys finds
w1/109 (bad values and reserved keys, done) and w3/229, w3/284 (single-add
key messages); none covers the key grammar in bulk rows.

Acceptance: the fixture with `--partial` exits 1, writes rows 1 and 3,
and names `Row 2, meta.Category` with the key rule; without `--partial`
it exits 1 and writes nothing; a `__` key is a named rejection. Only macOS
and the checkout were exercised.
