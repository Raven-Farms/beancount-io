# A CSV row with a payee is skipped as an "exact duplicate" of a payee-less ledger entry, so a new transaction is dropped with exit 0

**Major · cli · 45–60m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
When two rows share date, amount and narration and one has an empty payee
cell, the payee-bearing row is matched to the stored payee-less entry's id
and skipped as an exact duplicate, while the row that really is in the
ledger is only a "possible duplicate". With `--duplicates skip --apply` the
new transaction is never written and the run exits 0. The trigger is narrow
(a merchant column blank on some rows plus a generic description); the owner
may downgrade. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "Open" "Opening balance"
  Assets:Checking  5000.00 USD
  Equity:Opening
```

`/absolute/books/a.csv`:

```csv
Date,Payee,Description,Amount
2026-02-01,,CARD PURCHASE,-5.00
```

`/absolute/books/b.csv`:

```csv
Date,Payee,Description,Amount
2026-02-01,STARBUCKS,CARD PURCHASE,-5.00
2026-02-01,,CARD PURCHASE,-5.00
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean import a.csv --csv date=Date,payee=Payee,narration=Description,amount=Amount --account Assets:Checking --apply
bea -f main.bean import b.csv --csv date=Date,payee=Payee,narration=Description,amount=Amount --account Assets:Checking --duplicates skip --apply
```

Actual: the second command exits 0 and writes 0 entries.

```text
csv → Assets:Checking: 0 ready, 1 exact duplicates, 1 possible duplicates
1    duplicate           2026-02-01  STARBUCKS / CARD PURCHASE  -5.00 USD  hash
2    possible_duplicate  2026-02-01  CARD PURCHASE              -5.00 USD  hash
Row 1: import-id csv:sha256:fe7220df4ddb25c4 is already in the ledger.
```

The id named for row 1 belongs to the payee-less entry. `STARBUCKS` does not
appear in the ledger afterwards.

Control: the same two rows with the payee-less row first give `duplicate`
then `new`, and the STARBUCKS entry is written once with its own id
`csv:sha256:3384590a1fee9aa1`. A worker also saw a two-row file imported
once then re-imported in reverse order report `1 exact duplicates, 1
possible duplicates` and exit 4 on `--apply`.

Expected: `docs/IMPORTING.md` says "A row with both a payee and a narration
hashes both … so rows that differ only in payee keep distinct ids however
the export orders them." STARBUCKS should be `new` and the payee-less row
`duplicate`, in either order.

Cause: in `cli/src/bea_engine/importing.py`, `_hash_rows` (`:803`)
increments the narration-only occurrence counter for payee-bearing rows too,
so a payee-less row's id depends on what precedes it; and
`_claim_payeeless_ids` (`:822`) cannot claim a stored payee-less entry by
payee, so its id goes to whichever row reaches it first — here the
payee-bearing row, which is then classed `duplicate` because date and
amount agree. Payee-less rows are never part of a claim group, so the true
owner is not considered.

Fix: give a stored narration-only id whose entry has no payee first to a
payee-less row with the same base in the batch, falling back to the legacy
claim only otherwise; number payee-less rows independently of
payee-bearing rows. No dependency or API change.

Blast radius: CSV and Python-importer rows (shared hashing), preview and
apply, text and JSON.

Dedupe: board search for `_claim_payeeless`, payee-less and narration-only
finds w1/done/149 (generated id ignored payee, fixed); this is the residual
of that fix for the empty-payee case. w5/075 covers a reused inferred bank
reference, which is different.

Acceptance: the second command reports row 1 `new` and row 2 `duplicate`
and writes the STARBUCKS entry once; the reversed-order control is
unchanged, and re-importing either order afterwards reports two exact
duplicates. Real-command regression tests cover both orders. Only macOS and
the checkout were exercised; `--duplicates include` on this fixture was not
run.
