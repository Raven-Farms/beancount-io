# Infer comma decimals after removing supported thousands-group fillers

**Minor · cli · 15–25m · A1/A2.** Continuous real CLI QA, 2026-10-20,
checkout `bea 0.3.1`, HEAD `c0ce55bff` (CLI unchanged through `48639043a`),
Darwin 25.5.0 arm64, frontend Python 3.13.3. A consistently comma-decimal
export is refused when amounts have exactly three fractional digits and
space/apostrophe grouping. Removing the grouping or forcing comma decimals
imports the same amount correctly. No product fix implemented.

Create `/abs/books/main.bean`:

```beancount
option "operating_currency" "KWD"
2024-01-01 open Assets:Cash KWD
2024-01-01 open Expenses:Food KWD
```

Create `/abs/books/bank.csv`; the grouping character here is an ordinary
ASCII space:

```csv
Date;Description;Amount
2024-02-01;Withdrawal;-1 234,567
```

From `/abs/books`, closed stdin/no TTY, isolated absolute `BEA_CONFIG_DIR`
and `XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, with inherited `BEA_FILE`
and `BEA_TOKEN` removed:

```sh
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --account Assets:Cash --default-account Expenses:Food
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --account Assets:Cash --default-account Expenses:Food --apply
```

Actual: both exit **2**, stdout empty, JSON error on stderr:
`Row 1 (line 2): cannot parse amount '-1 234,567' in column 'Amount'.
Accepted: plain decimals (1000.50), $/€ symbols, thousands separators,
(parentheses) or trailing-minus negatives; comma decimals like 1.000,00
only when the whole column uses them.` The ledger and CSV stay byte-identical.
An explicit `--csv date=Date,amount=Amount,narration=Description` fails the
same way. Human apply also refuses with the same located amount message.

The ordinary space, NBSP (U+00A0), narrow NBSP (U+202F), ASCII apostrophe
and curly apostrophe (U+2019) each reproduced twice, through preview and
apply with automatic and explicit mappings: **20 failing journeys**.

Working controls, each twice for every grouping character:

- Add `--csv date=Date,amount=Amount,narration=Description,decimal=comma`:
  preview and apply succeed, write one **−1234.567 KWD** withdrawal, check
  passes, and a fresh BQL `SELECT number WHERE account = 'Assets:Cash'`
  returns `-1234.567`. A flag-free re-import writes zero and changes no bytes.
- Remove only the group filler: `-1234,567` automatically imports as
  **−1234.567 KWD**, with the same query, check and repeat-import controls.
- Keep the grouping but use two decimals, `-1 234,56`: imports as
  **−1234.56 KWD**. A point-decimal `-1 234.567` imports as
  **−1234.567 KWD**. Both control families pass all those checks.

The same refusal reproduced twice with `debit=Debit,credit=Credit`, a
`1` + narrow NBSP + `234,567` debit and a zero-filled credit; forcing comma
decimals writes **−1234.567 KWD** and passes check. A standalone `-1,234`
grouping control remains **−1234 KWD**. A file also containing the point
decimal `-1,234.56` is still refused, as mixed conventions should be.
There is no silent amount-change claim here: the affected imports refuse.

Expected: support the grouping fillers the amount parser already accepts
when deciding this unambiguous comma-decimal column. IMPORTING.md's amount
contract accepts thousands separators and resolves the decimal convention
from the whole column; it specifically treats `1613,030` as comma decimals
because its whole part cannot be one thousands group. Removing the space
from `1 234,567` gives the same unambiguous shape. The existing override
proves this is supported input rather than a malformed amount.

Cause: `_resolve_decimal_comma` in `cli/src/bea_engine/csv_mapper.py:244–248`
passes `_split_amount_sign`'s core directly to `_separator_vote`. Its
three-decimal rule (:223) requires `\d+,\d{3}`, so an internal filler prevents
the strong comma vote. With no other vote, the column falls back to point
decimals. `_parse_amount_cell` (:365–377) then removes
`_THOUSAND_SEPARATOR_FILLER` and rejects `1234,567` as invalid comma grouping.
The two phases therefore disagree about the same supported filler.
Two/four-or-more fractional digits use the looser `_COMMA_DECIMAL_TAIL`
rule and do vote comma, explaining those controls.

Fix: apply consistent supported grouping normalization when recognizing
decimal-convention evidence, retaining original cells for diagnostics.
Keep ambiguous `1,234` grouping, explicit decimal choices and mixed-column
refusals intact. The shared amount parser serves amount and debit/credit
mapping, including direction-mapped amounts; the direction spelling was
not separately exercised for this three-decimal case. No dependency or API
change is needed.

Dedupe: searched all board states for grouped spaces/apostrophes with three
comma decimals, `_separator_vote`, and three-decimal inference; reviewed
current milestone scopes. Completed w1/130 (`e3b4354ed`) added the ungrouped
`0,125`/`1613,030` rule; completed w5/753 (`0e1a09e0b`) added dot-group
inference and overrides. Their controls still work. Open [895](./895.md)
concerns combining two separate columns' conventions; this single-column
failure needs normalization before its own vote. No overlapping open repair
or subsequent source fix was found.

Acceptance: all five filler spellings with three comma decimals preview and
apply at their exact values under inferred and explicit mappings; fresh
queries/check/re-import agree. Retain the controls above, including refusal
of genuinely mixed conventions and byte preservation on refusal. Pin real
CLI regression coverage. Evidence is under ignored
`.tmp/qa-2026-10-20-cli-loop-pass7-9d3acadc/`:
`repro_grouped_comma_three.py`, `grouped-comma-three-results.json`,
`grouped-comma-three-extra-results.json` and `captures/comma-three-*.json`.
