# One bulk row that breaks Beancount's booking arithmetic aborts the whole `--partial` batch naming no row; a zero-unit total cost (`0 HOOL {{310 USD}}`) fails with a raw `DivisionByZero`

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-16, HEAD `c3c42a48`, checkout `bea 0.3.1`, macOS 26.5.1.
USAGE: a row that cannot be written "is rejected as `Row N` with Beancount's
reason, so `--partial` still writes the others". The per-row pre-check parses
but does not book. Booking exceptions escape as a batch-wide error, so the
valid rows are not written and nothing says which row failed. No product fix
implemented.

Ledger with `Assets:Brokerage`, `Assets:Checking USD`, `Assets:Cash`,
`Expenses:Food` open. Batch `[OK, BAD, OK]`. Each OK row is a 5 USD food
purchase from `Assets:Cash`. BAD (a):

```json
{"date": "2026-02-02", "narration": "zero units",
 "postings": [{"account": "Assets:Brokerage", "units": {"number": "0", "currency": "HOOL"},
               "cost": {"number_total": "310", "currency": "USD"}},
              {"account": "Assets:Checking", "amount": "-310 USD"}]}
```

BAD (b): `"amount": "0.12345678901234567890123456789 USD"` beside an inferred
leg.

```sh
bea --json -f /abs/w.bean add transactions --from j.json --partial
bea -f /abs/w.bean add transaction zt --date 2026-02-01 -p 'Assets:Brokerage 0 HOOL {{310 USD}}' -p 'Assets:Checking -310 USD'
```

Actual: (a) exit 1, `{"error": {"category": "validation", "message":
"DivisionByZero: [<class 'decimal.DivisionByZero'>] Pass --debug before the
command for a traceback."}}`, with no `result` and nothing written; the
single add gives the same raw message. (b) exit 2, `Beancount cannot load the
ledger with this write: … wider than the 28 significant digits … Nothing was
written.`, naming no row.

Control: `0 EUR @@ 10 USD` is rejected cleanly as `Row 1: … does not
balance`; `--posting` with a literal `100/0` is refused before parsing
(w5/010).

Expected: zero units with a total cost are refused at input (bulk and `-p`,
exit 2, naming the row and posting). Other booking-time decimal errors are
attributed to their row, so `--partial` writes the rest.

Cause: the pre-check (`cli/src/bea_engine/ledger/adding.py:1301`,
`write.one_entry_problem`) never books; the batch load (`adding.py:1349-1351`)
catches only `LedgerError`; `write.py:1531` turns `InvalidOperation` into a
batch-wide `UsageError` and lets `DivisionByZero` from upstream
`convert_costspec_to_cost` through raw.

Fix: as above.

Dedupe: searched `DivisionByZero`, `zero units`, `28 significant`. w5/010,
057 and 263 cover other paths.

Acceptance: (a) and (b) reject only row 2 under `--partial` and write rows 1
and 3; the single add exits 2 with a clear message. Tests pin each.

Addendum (CLI QA 2026-10-16, differential run against `bean-check`): the read
side has the same crash. A ledger holding `Assets:Broker  0 HOOL {{10 USD}}`
(opens for `Assets:Cash USD` and `Assets:Broker`, balanced by `Assets:Cash
-10 USD`) makes `bea check` print upstream's 47-line `DivisionByZero`
traceback (exit 1) and `bea --json check` say only `DivisionByZero: [<class
'decimal.DivisionByZero'>] Pass --debug…`, naming no file or line. Upstream
`bean-check` crashes the same way, but bea already rewrites other upstream
crashes (w5/010, w5/256). Fix alongside: attribute the failure to the posting
(`FILE:LINE: zero units with a total cost`), or pre-scan for it at load.

Addendum (CLI QA 2026-10-16, precision sweep): reads crash the same way on a
balancing amount wider than 28 significant digits. A ledger with `2026-02-01 *
"A"` / `Assets:Wallet  12345678901.123456789012345678 SHIB` / `Equity:Opening`
(opens for both) makes `bea check` print a 47-line upstream traceback ending
`decimal.InvalidOperation`, and `--json check`, `balance`, `list`, `query` and
`report` exit 1 with only `InvalidOperation: [<class
'decimal.InvalidOperation'>]`, naming no file, line or limit. An unrelated
write then gets the w5/263 message blaming the new write. Cause: the read-side
load (`cli/src/bea_engine/managed_load.py:1075`) does not translate booking's
`DecimalException`, and `cli/src/cli/commands/check.py:96-104` falls through to
native bean-check. Fix alongside: catch `DecimalException` around the read
load and report `FILE:LINE` with the 28-digit explanation (the write path's
wording, `write.py:1523`), without running native bean-check.
