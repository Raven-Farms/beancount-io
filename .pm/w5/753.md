# A CSV column of whole amounts with dot thousands separators (ISK, CLP, VND, JPY exports) is refused when one cell has two dot groups (`1.650.000`), and otherwise imported 1000× too small with exit 0

**Major · cli · 15–20m · A1.** Real CLI QA, 2026-10-17, HEAD `0e9729be5`, checkout `bea 0.3.1`, macOS 26.5.1.
IMPORTING.md:90 says "the point-vs-comma convention is resolved from the whole
column". A column whose cells use only dot grouping never votes for comma
decimals, so whole-number exports in dot-grouping locales are refused or
silently misread. There is no `--csv` key to force comma decimals. No product
fix implemented.

`isk.bean`: `option "operating_currency" "ISK"`, `open Assets:Banki ISK`,
`open Expenses:Uncategorized`, `open Income:Uncategorized`.

1. `A.csv`:

   ```
   Date;Description;Amount
   02.01.2026;Kaffi;-12.500
   03.01.2026;Leiga;-185.000
   04.01.2026;Laun;1.650.000
   ```

   `bea --file /abs/isk.bean import A.csv --account Assets:Banki` exits 2 with
   `Row 3 (line 4): cannot parse amount '1.650.000' in column 'Amount'.
   Accepted: … comma decimals like 1.000,00 only when the whole column uses
   them.`. `1.650.000` can only be dot grouping, so the column is comma-decimal
   (−12500, −185000, 1650000).
2. `B.csv` is the same with `650.000` as the last amount. `… import B.csv
   --account Assets:Banki --apply` exits 0 and writes `-12.500 ISK`, `-185.000
   ISK` and `650.000 ISK`, with no note. The balance is 452.500 ISK instead of
   452,500 ISK. This reading is genuinely ambiguous (BHD has 3 decimals), but
   for an ISK account it is almost certainly wrong, and nothing says so.

Control: the same rows written `-12.500,00` etc. import as −12500.00 …
(hunter's run).

Expected: (1) a cell with two or more dot groups votes for comma decimals, so
`A.csv` imports as whole numbers. (2) A dot-only column that could be either
gets a note (as ambiguous dates do), and a `--csv decimal=comma|point` override
exists.

Cause: `_separator_vote` (`cli/src/bea_engine/csv_mapper.py:155`) casts an
"eu" vote only for a cell with a comma. `_parse_amount_cell` (`:241`) in
point mode then fails on `Decimal("1.650.000")`.

Fix: treat `[1-9]\d{0,2}(\.\d{3}){2,}` as an "eu" vote; note a dot-only
three-decimal column against a zero-decimal account currency; add the
override.

Dedupe: w3/564 (open) is the dashboard Smart Import analogue; w4/164 (done)
covered comma decimals only.

Acceptance: `A.csv` imports 1650000; `B.csv` gets a note, and the override
reads it as whole numbers. Tests pin both.
