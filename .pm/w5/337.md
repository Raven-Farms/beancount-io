# A bulk batch that fails ledger validation without `--partial` never names the bad row, although the refusal already counted the good ones ("Pass --partial to append the 49 valid rows"), and the JSON lists every row as `unwritten_rows`

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
Take a 50-row batch in which one row fails a ledger check, such as an
unbalanced transaction or an unknown account. Without `--partial`, the
refusal prints Beancount's message with no row number, and its JSON
`result` lists all 50 indexes as `unwritten_rows`. Yet the same refusal
has just worked out which 49 rows are valid: its own message says "Pass
--partial to append the 49 valid rows". To find the wrong row, the user has
to bisect a large file, or run `--partial` and write data. With
`--partial`, the same row is reported as `Row 38: …`. No product fix
implemented.

Use any valid ledger that opens `Expenses:Food` and `Assets:Cash` in USD,
with the environment from [335](./335.md). `in.json` holds 50 rows like
`{"date":"2026-02-DD","narration":"rN","postings":[{"account":"Expenses:Food","amount":"1.25 USD"},{"account":"Assets:Cash"}]}`.
Row 38 (index 37) instead has `[{"account":"Expenses:Food","amount":"5
USD"},{"account":"Assets:Cash","amount":"-4 USD"}]`.

```sh
bea -f /absolute/books/main.bean add transactions --from in.json
bea --json -f /absolute/books/main.bean add transactions --from in.json
bea -f /absolute/books/main.bean add transactions --from in.json --partial
```

Actual:

- The first run exits 1 with:

  ```text
  Error: The change would leave the ledger invalid; nothing was written. Pass --partial to append the 49 valid rows.
    Proposed append (not written): Transaction does not balance: (1 USD)
  ```

- The JSON run shows the same details, plus `"result": {"written": 0,
  "written_rows": [], "unwritten_rows": [0, 1, …, 49]}`, with no
  `rejected_rows`.
- An unknown account in row 38 also gives no row number.
- The `--partial` run names `Row 38: …` and reports `rejected_rows: [37]`.

Reproduced in three fresh runs.

Control: a schema error in row 38 without `--partial` is reported as
`Row 38, postings.0.units.currency: …`, with `rejected_rows: [37]`.

Expected: `docs/USAGE.md` says "If any row is invalid the ledger is left
byte-identical and the command exits **1**, listing the rejected rows".
[w3/315](../w3/done/315.md) asked that the refusal not imply every
unwritten index is equally unrecoverable. When the refusal already knows
which rows would be accepted, it should name the rest (`Row 38:
Transaction does not balance …`) and report `rejected_rows: [37]` in JSON.

Cause: the non-partial branch of `_transactions`
(`cli/src/bea_engine/ledger/adding.py:1276-1296`) calls `_recoverable_rows`
only to count the valid rows for the hint. It then raises with unlabeled
`batch_error.details` and sets `unwritten_rows` to every valid index. The
`--partial` path labels rows through `_named_rows`.

Fix: when `_recoverable_rows` returns a set, label the details of the rows
outside it (`Row N: …`), as the `--partial` path does, and add
`rejected_rows` to `result`. Keep `unwritten_rows` with its documented
meaning. The rows are already computed, so the w1/167 load budget still
holds. No dependency change.

Blast radius: `add transactions` without `--partial`, in text and JSON,
whenever the failure comes from ledger validation (balance, unknown or
closed accounts, booking, assertions) rather than schema.

Dedupe: searched `.pm/**`, including `done/`, for "Pass --partial to
append", `unwritten_rows` and "which row". w3/315 added the hint, w1/167
bounded its cost, and w3/231 covers overstated counts. None of them names
the failing row in the atomic refusal.

Acceptance: on the fixture, the run without `--partial` names `Row 38` in
text and reports `rejected_rows: [37]` in JSON, and the ledger is
unchanged. `--partial` output is unchanged. A real-command test covers an
unbalanced row and an unknown account. Only macOS and the checkout were
exercised.
