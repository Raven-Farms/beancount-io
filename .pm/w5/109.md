# The query shell prints Python tracebacks for a mistyped date and an out-of-range ORDER BY index

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-11, HEAD `0227141a` (CLI unchanged since `97600b74`),
checkout `bea 0.3.1`, macOS, driven through a real pseudo-terminal.
Two ordinary typing mistakes at the interactive query prompt produce
multi-screen Python tracebacks, although the same statements as one-shot
queries are explained in a sentence. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
2026-01-05 * "Cafe" "Coffee"
  Expenses:Food  4.00 USD
  Assets:Checking
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN/CI, `TERM=dumb`, and stdin, stdout and stderr all
attached to a pseudo-terminal.

```sh
bea -f /absolute/books/main.bean query
```

then type

```text
SELECT date WHERE date = 2026-02-30;
SELECT account, sum(position) GROUP BY 1 ORDER BY 3;
```

Actual: each prints `error:` and a long traceback (133 traceback lines for
the pair), ending in `ValueError: day is out of range for month` and
`CompilationError: invalid ORDER-BY column index 3` (worker-observed final
lines). The session continues. Repeated twice.

Control: the one-shot `bea -f … query "SELECT date WHERE date = 2026-02-30"`
exits 2 with `Cannot run this BQL query: invalid date literal: day is out of
range for month.` and the hint "Write dates as YYYY-MM-DD with a real month
and day". A worker confirmed the one-shot ORDER BY form is equally clean and
that `SELECT nocol;` is explained cleanly in the shell.

Expected: the code's own contract (`cli/src/bea_engine/query.py:469-481`,
`:964-979`) is that a mistake at the prompt is ordinary input, every
execution path explains the same failure the same way, and `--debug` is how
to ask for a traceback; w1/067 fixed three other inputs on that basis.

Cause: the date-literal translation exists only in `_executed`
(`query.py:946-961`); the shell goes through `_compiled`, which lacks it.
`_compiled` is called with `context=None` when interactive (`:686`), so
a Beanquery error without parse position is re-raised to upstream's renderer,
which falls back to a formatted traceback.

Fix: move the literal-error branch into `_compiled`, and for an interactive
Beanquery error without parse position print `error: <message>` only.
No dependency or API change.

Blast radius: the interactive shell and the `--source` shell. Invalid regex
and other evaluation-time errors also print tracebacks at the prompt; their
one-shot handling is w5/103 and should be closed together.

Dedupe: board search for traceback at the prompt finds w1/067 (set columns
and subqueries, done), w3/397 (bea's own usage errors at the prompt, done)
and w1/085 (one-shot date literal, done), plus w5/103;
none covers these two inputs in the shell.

Acceptance: both statements print a one-line explanation matching the
one-shot wording and no `Traceback`; `--debug` still shows one. A PTY
regression test covers both. Only macOS and the checkout were exercised.
