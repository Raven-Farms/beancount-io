# `init --preset --opening-balance 'Assets:Cash 0'` silently discards the confirmed zero and creates byte-identical books to an omitted opening balance

**Minor · cli · 30–45m · A1/A2.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `4c01ed572`, Darwin 25.5.0 arm64; frontend Python 3.13.3.
No product fix implemented.

In a disposable `/abs/case`, with isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, no inherited
`BEA_FILE`/`BEA_TOKEN`, closed stdin/no TTY:

```sh
bea --json init /abs/case/unknown --preset personal@1 --currency USD --date 2024-02-01
bea --json init /abs/case/zero --preset personal@1 --currency USD --date 2024-02-01 --opening-balance 'Assets:Cash 0'
bea --json --file /abs/case/zero/main.bean list balance
bea --json init /abs/case/known --preset personal@1 --currency USD --date 2024-02-01 --opening-balance 'Assets:Cash 100'
```

Actual: every command exits 0. The unknown and zero `main.bean` files are
byte-identical. `list balance` for the explicit zero answers `data: []`;
there is no boundary assertion or metadata retaining the confirmed zero.
The nonzero control records an opening transaction on 2024-01-31 and a
`2024-02-01 balance Assets:Cash 100 USD`. Both zero and known ledgers pass
`check`. Reproduced twice using fresh directories.

Additional working control:

```sh
bea --json --file /abs/case/zero/main.bean add balance --date 2024-02-01 --account Assets:Cash --amount '0 USD'
```

This writes the explicit zero assertion successfully. Zero is representable
and valid; it was lost before the preset builder saw it.

Expected: for catalog presets, a confirmed zero is retained as a confirmed
opening state and an appropriate boundary assertion, distinguishable from
an omitted/unknown amount. Completed w3/m53's definition of done explicitly
requires `unknown`, `zero` and `known` to stay distinct. ADR021's setup rules
and `cli/src/bea_engine/setup_catalog.json` make the same distinction. Keep
legacy init's historical behavior when no preset is supplied.

Cause: `cli/src/cli/commands/init.py:298` forwards an opening balance to the
helper only under `if amount`. `Decimal("0")` is false, so the explicit flag
is dropped. That pre-existing optimization was appropriate for the legacy
fixed template's nonzero-only opening transaction, but the preset path
reuses it. `answer_preset` in `cli/src/bea_engine/initiating.py:228–254`
receives an empty balances map and treats the call exactly like omission.

Fix: preserve explicit zero inputs when forwarding preset creation, and
retain the catalog's confirmed-zero state in the file. Test omission, zero,
and a nonzero opening through the real CLI and fresh reads, alongside a
legacy no-preset control. Do not infer confirmed zeros for every omitted
account or add fictional opening money.

Dedupe: whole-board searches for preset/zero/opening-state collapse, plus
open/blocked milestone scopes, found no separate open item. w3/m53 is
completed, but its full DoD includes this distinction. `1ba20bffa`
introduced preset creation; `git log -S 'if amount:'` traces the shared
forwarding guard to legacy init. The existing CLI conformance tests cover
clean presets and one known nonzero opening, leaving zero unexercised.
This is a gap against that completed DoD, filed in w5 as requested.

Acceptance: explicit zero and omission produce distinguishable portable
opening states, the zero boundary is queryable, and both files validate;
nonzero openings and legacy no-preset init retain their intended behavior.
No dependency or API contract change is needed for this local CLI defect.
Windows/Linux, other preset accounts and repaired behavior remain unverified.
Sanitized evidence is retained under
`.tmp/qa-2026-10-20-cli-loop-d3c5ebec/`: `captures/s5-*-zero.json`,
`captures/preset-zero-*.json`, the two zero fixtures' `initial.bean.txt`
snapshots, and the clean/known fixtures in `sweep5/`. The public commands
above independently reproduce the issue.
