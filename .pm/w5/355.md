# `bea format -i` turns every lone CR into a line break, inside comments and strings too, so a valid ledger can become invalid, or a payee change value, while it reports "1/1 file(s) formatted" with exit 0

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
Beancount's lexer ends a line only at `\n`. A lone `\r` inside a comment
or a string is just a character to it. The formatter normalizes with
universal newlines (`\r\n` → `\n`, then `\r` → `\n`). It therefore splits
such a line in two:

- A comment's tail becomes a new line at column 0, which can be a syntax
  error.
- A string such as a payee gets a different value.

`format -i` reports success with exit 0, and the plain stdout `format`
produces the same text. [w5/169](./done/169.md) fixed the lone CR in the
engine's line tables but did not touch the formatter. No product fix
implemented.

Create disposable `/absolute/books/main.bean`:

```sh
printf 'option "operating_currency" "USD"\n2020-01-01 open Assets:Cash USD\n2020-01-01 open Equity:O\n2020-01-02 * "Shop" "memo"\n  Assets:Cash   5 USD ; old\rEquity:O -5 USD\n  Equity:O\n2020-01-03 * "pay\ree" "x"\n  Assets:Cash   1 USD\n  Equity:O\n' > main.bean
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, and closed stdin.

```sh
bea -f /absolute/books/main.bean check
bea format -i /absolute/books/main.bean
bea -f /absolute/books/main.bean check
```

Actual:

- The first `check` exits 0.
- `format -i` exits 0 with `1/1 file(s) formatted.`
- The second `check` exits 1 with `main.bean:6: syntax error, unexpected
  ACCOUNT`, because `Equity:O -5 USD` from the comment now starts a line.
- The payee `pay\ree` becomes `pay\nee`, a different string. In a file
  where only that case occurs, the meaning changes without any error.

Reproduced by the hunter twice from fresh fixtures, with the comment and
string cases also separately, and once by me.

Control: the same file without the stray `\r` formats and still passes
`check`. A CRLF file converts cleanly.

Expected: `docs/USAGE.md` describes `-i` as the convergence path that
"rewrites the file to LF". That is a line-ending conversion, and it must
not change the ledger's meaning. A `\r` that is not part of `\r\n` should
be kept. Alternatively, a file whose lines all end in `\r` could be
detected and converted as a whole. A lone `\r` within a line should
either be left alone, with that line protected from alignment as the
other foreign line breaks are (w5/165, w5/271), or make the file
unformattable, naming the line.

Cause: `_read` (`cli/src/bea_engine/ledger/formatting.py:207`) and
`_aligned` (`:212`) both do `.replace("\r\n", "\n").replace("\r", "\n")`.
`_FOREIGN_LINE_BREAKS` (`:48`) guards `\x0b`, `\x85`, U+2028 and others,
but not a lone `\r`.

Fix:

- Normalize only `\r\n`.
- Treat a lone `\r` like the other foreign line breaks: protect the line,
  or refuse naming it.
- Keep `--check`'s carriage-return gate consistent with that choice.
- No dependency change.

Blast radius: `format`, `format -i` and `format --check`/`--dry-run` on
files containing a stray `\r`, which pasted bank text and old Mac exports
can produce. The result is a silently corrupted ledger or changed string
values.

Dedupe: searched `.pm/**`, including `done/`, for "lone CR", `\r` and
"carriage return" together with format. Related notes:

- w5/169: engine line tables.
- w5/108, w5/244 and w5/107: display.
- w3/m50/t002: rendered output.
- w3/415: string preservation, which did not consider `\r`.

None covers the formatter rewriting a lone CR.

Acceptance: on the fixture, `format -i` either leaves the comment and the
payee intact, so `check` still passes and `list --json` shows `pay\ree`,
or refuses naming lines 5 and 7 and leaves the file unchanged. CRLF files
still convert. A real-command test covers the comment and string cases.
Only macOS and the checkout were exercised.
