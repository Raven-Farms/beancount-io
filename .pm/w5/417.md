# `bea check --cache-filename PATH` silently deletes any existing file at PATH that is not a Beancount cache (a CSV, a note, anything), exits 0, and leaks `ERROR:root:Cache file is corrupted …`

**Minor · cli · 15m · A2.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
Upstream's loader treats any file it cannot unpickle at the cache path as
a corrupted cache and removes it. bea guards the path only against the
ledger's own include closure (w5/065). A user who mistypes the cache path
to point at a bank statement or any other file loses that file without
warning, and the command exits 0. The upstream log line also reaches
stderr raw. USAGE says a `--cache-filename` "is used exactly as Beancount
defines it", which may be intended (hence A2). Still, deleting an
arbitrary user file conflicts with bea's write-safety promises. No
product fix implemented.

Use any small ledger. Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME,
BEA_NO_UPDATE_NOTIFIER=1, and closed stdin.

```sh
printf 'Date,Amount\n2026-01-05,-5\n' > /absolute/w/stmt.csv
bea -f /absolute/w/main.bean check --cache-filename /absolute/w/stmt.csv
ls /absolute/w/stmt.csv
```

Actual: exit 0. stderr shows `ERROR:root:Cache file is corrupted: invalid
load key, 'D'.; recomputing.`, and `stmt.csv` no longer exists. With a
ledger small enough not to be cached, nothing is written in its place.
Reproduced twice by the hunter and once by me. The hunter saw the same
with a 30k-transaction ledger.

Control:

- A cache path that is the ledger or one of its includes is refused with
  exit 2 and "Nothing was changed" (w5/065).
- A nonexistent path is not created for a small ledger.
- `--json check --cache-filename` is refused before running.

Expected: `docs/USAGE.md` says "a `bea` command never replaces a file it
was not given". The file was given as a cache location, not as something
to delete. bea should refuse an existing file that is not a Beancount
cache (for example, by checking the pickle header) with exit 2 naming it.
At minimum, it should document that any unreadable file at that path is
deleted. The `ERROR:root:` line should be silenced or translated, in the
same family as 411.

Cause:

- Upstream `beancount/loader.py:239` (log) and `:250-253`
  (`os.remove(cache_filename)`).
- bea's `refuse_cache_over_ledger` (`cli/src/cli/output.py:432-460`)
  compares only against the include closure.

`BEANCOUNT_LOAD_CACHE_FILENAME` (w5/067) goes through the same loader and
is likely affected the same way, though that was not exercised.

Fix: before forwarding, if the cache path exists and does not start with
a pickle protocol header, refuse with exit 2 naming the file. Apply the
same check to `BEANCOUNT_LOAD_CACHE_FILENAME`. Configure the
`beancount.loader` logger. No dependency change.

Blast radius: `bea check --cache-filename` (and possibly
`BEANCOUNT_LOAD_CACHE_FILENAME`) with a mistyped path. The result is
silent deletion of an arbitrary user file.

Dedupe: w5/065 and w5/067 (done) cover aliasing of ledger files only;
their control used a real cache file. 411 covers the `WARNING:root` cache
write line. None covers deletion of non-cache files.

Acceptance: on the fixture, the command exits 2 naming `stmt.csv`, which
still exists. A real cache file at the path still works. A test pins
both.

Addendum (CLI QA r74, 2026-10-14): `bea check -C --cache-filename X`
also leaks upstream's `WARNING:root:Cache disabled; Explicitly overridden
cache filename … will be ignored` (exit 0). That is stock bean-check
behaviour passed through. Include it in the same logger configuration
fix.
