# Explain rejected locale date shorthand without claiming it reads as 1900

**Trivial · cli · 10–15m · A1.** The explicit-year guard correctly follows
w5/783's rule, but its explanation is false for `%x` and `%c`: both locale
shorthands read the year in the file, while the CLI says every row would be
read as 1900 and suggests adding a year. Preserve the existing requirement
for an explicit `%Y`, `%y` or `%G`; explain the unsupported shorthand and its
replacement accurately. No product fix implemented.

Real CLI QA, 2026-10-21, HEAD `556471ab4` (CLI sources unchanged after pulling
`dbfdff600`), checkout `bea 0.3.1`, macOS 26.5.1 arm64, frontend Python
3.13.3, existing managed Python 3.12.10. Fresh subprocesses, closed stdin/no
TTY, isolated absolute `BEA_CONFIG_DIR`/`XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, no inherited `BEA_FILE`/`BEA_TOKEN`. Additionally
set **`LC_ALL=C` and `LANG=C`** for these children so the format is fixed.

Create disposable `/abs/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

Create `/abs/books/bank.csv`:

```csv
Date,Description,Amount
02/01/24,Coffee,-4.50
```

From `/abs/books`, with the isolated C-locale child environment above:

```sh
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --csv date=Date,narration=Description,amount=Amount --date-format '%x' --account Assets:Cash --default-account Expenses:Food
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --csv date=Date,narration=Description,amount=Amount --date-format '%x' --account Assets:Cash --default-account Expenses:Food --apply
bea --json --no-input -f /abs/books/main.bean import /abs/books/bank.csv --csv date=Date,narration=Description,amount=Amount --date-format '%m/%d/%y' --account Assets:Cash --default-account Expenses:Food --apply
bea --json -f /abs/books/main.bean query "SELECT date,number WHERE account='Assets:Cash'"
bea --json -f /abs/books/main.bean check
```

Actual: exits `2, 2, 0, 0, 0`. Both refusals say:
`--date-format '%x' has no year directive (%Y, %y or %G), so every row would
be read as 1900. Pass a format that reads the file's year … or add the year
to the file's dates first.` Ledger bytes stay unchanged. The expanded format
writes once at 2024-02-01; fresh query returns that date and −4.50 USD, and
check passes. The source CSV stays byte-identical throughout.

The native runtime controls contradict the 1900 claim:

```python
from datetime import datetime
print(datetime.strptime("02/01/24", "%x").date())
print(datetime.strptime("Thu Feb  1 12:30:00 2024", "%c").date())
# Both print 2024-02-01 in the C locale.
```

Executed independently with both the actual frontend Python 3.13.3 and managed
engine Python 3.12.10, not a simulated parser. Native C-locale `D_FMT` is
`%m/%d/%y`. `%c` likewise contains a year; its explicit working counterpart
here is `%a %b %d %H:%M:%S %Y`.

Twelve fresh CLI journeys, twice each across `%x`, `%c`, the two explicit
counterparts, genuinely yearless `%m/%d`, and literal `%%x %m/%d`. Both locale
forms refuse preview/apply at exit 2 with the false 1900 explanation. Both
expanded forms write the correct date and pass fresh query/check. The genuine
yearless/literal controls correctly refuse and would parse as 1900 under both
native runtimes. All refusals preserve ledger bytes; every CSV is unchanged.
The five public commands above were separately replayed twice.

Cause: `cli/src/bea_engine/csv_mapper.py:_has_year_directive` (:1256–1258)
checks only explicit `%Y`/`%y`/`%G` after removing escaped percent signs.
`CsvImporter.__init__` (:1348–1353), its sole production caller, then equates
failure of that policy check with Python defaulting to 1900. That inference
does not hold for year-bearing locale composites. The engine guard is reached
from CSV preview/apply; Python importers that parse their own dates do not use
it. The frontend describes `--date-format` as a `strptime` format.

Fix: retain the explicit-year restriction and exit 2, but describe it as a
requirement for an explicit year directive. For unescaped `%x`/`%c`, say that
the locale shorthand must be expanded into explicit fields, with an accurate
example. Do not claim these formats lack a year or advise changing already
dated source cells. Keep the yearless 1900 warning for genuinely yearless
formats and preserve escaped-percent handling. Update the helper's overbroad
docstring too. This is a diagnostic correction, not new locale-format support;
no dependency or backend/API change needed.

Dedupe: searched all board states for date-format/`strptime` with `%x`, `%c`
and locale dates, scanned active/blocked milestone scopes and targeted
history. Completed w5/783 (`551b6e93c`) deliberately requires an explicit
year directive; this note preserves that decision and corrects its inaccurate
