# `bea init` asks its questions before checking `--date` and `--opening-balance`, then rejects the option with a message that does not name it

**Minor · cli · 10–15m · A2.** Real CLI QA, 2026-10-16, HEAD `f29eb957`, checkout `bea 0.3.1`, macOS 26.5.1. PTY.
USAGE: "Invalid command-line options still fail with exit 2". An invalid
option should fail before anything is asked. `--currency 12` already does. A
newcomer who answers the prompts and is then told `Invalid value: Invalid
date…` cannot tell which input was wrong. No product fix implemented.

In an empty directory, on a terminal:

```sh
bea init books --date 2026-13-01                       # answer EUR
bea init books --opening-balance 'Assets:Nope 10'      # answer EUR, then Enter
bea init books --opening-balance 'Assets:Checking 1e3' # answer EUR, then Enter
```

Actual: each exits 2 only after the answers: `Operating currency [USD]: EUR`
then `Error: Invalid value: Invalid date '2026-13-01': not a calendar date
(month must be in 1..12).`; the opening-balance cases fail after both
prompts with `Opening balance must be 'ACCOUNT NUMBER' …` and `Invalid value:
Scientific notation '1e3' is not supported…`. None names the option.

Control: `--currency 12` exits 2 before any prompt with `Invalid operating
currency: '12'…`.

Expected: every option is validated before the first prompt, and the
message names it (`--date '2026-13-01': …`, `--opening-balance 'Assets:Nope
10': …`).

Cause: `cli/src/cli/commands/init.py:139-169` prompts for the currency before
`parse_date(date)` and validates opening balances after the date prompt; the
`typer.BadParameter` is raised outside Click's option handling, so its
"Invalid value:" prefix lacks the option name.

Fix: parse and validate `--date` and every `--opening-balance` up front, and
raise `UsageError` naming the option.

Dedupe: w3/411, w5/290 and 330 (done) concern the value grammar.

Acceptance: the three commands exit 2 before any prompt, naming the option. A
PTY test pins them.
