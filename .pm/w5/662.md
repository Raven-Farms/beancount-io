# On a forecast ledger, `import --duplicates skip` drops the real payment that falls on the forecast template's own date, exit 0: the first projection is treated as a written entry (sibling of w5/325)

**Major · cli · 20–30m · A1.** Real CLI QA, 2026-10-16, HEAD `5a0cdcb4`, checkout `bea 0.3.1`, macOS 26.5.1.
IMPORTING.md: "a transaction a plugin generates — a `fava.plugins.forecast`
projection … — is neither a duplicate nor a possible duplicate, so a real
payment it predicted imports as new." The forecast plugin removes the
template and emits projections, and the first projection carries the
template's date and line. bea counts a copy as on disk when its date equals
its source line's date. So the January projection is a "written" entry that
the real January payment matches, and `--duplicates skip` drops the payment.
No product fix implemented.

`main.bean`:

```beancount
option "operating_currency" "USD"
plugin "fava.plugins.forecast"

2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Rent USD
2026-01-01 open Equity:Opening USD

2026-01-02 * "Fund"
  Assets:Checking  5000 USD
  Equity:Opening

2026-01-15 # "Rent [MONTHLY REPEAT 3 TIMES]"
  Expenses:Rent  1000 USD
  Assets:Checking  -1000 USD
```

`s.csv`: `Date,Description,Amount` / `2026-01-15,Rent,-1000` / `2026-02-15,Rent,-1000`.

```sh
bea --file /abs/main.bean import s.csv --csv date=Date,narration=Description,amount=Amount --account Assets:Checking --default-account Expenses:Rent --apply --duplicates skip
```

Actual: exit 0, `1 ready, 0 exact duplicates, 1 possible duplicates`. Row 1
cites `Existing entry at …/main.bean:12: 2026-01-15 # "Rent"` (line 12 reads
`"Rent [MONTHLY REPEAT 3 TIMES]"`, so this is the plugin's copy). Only the
02-15 row is written, and the real January payment is lost; `balance Rent`
reports three projections plus February.

Control: the 02-15 row of the series is `new`; without the plugin line, a `#`
entry is ordinary and matching it is fair.

Expected: both real payments import as new.

Cause: import's written-entry filter (`cli/src/bea_engine/importing.py:322-327`)
uses `entry_generated` (`cli/src/bea_engine/ledger/reader.py:179-220`), which
treats a copy as on disk when its date matches its source line; `_declares`
(`reader.py:170`) runs only for shared locations.

Fix: for import dedupe, count a transaction as written only when its header
line declares it (the narration matches), not merely its date. Keep `list
--on-disk`'s documented behavior separate.

Dedupe: searched `forecast`, `possible duplicate`, `entry_generated`; w5/325
(done) used a fixture that avoided the template date.

Acceptance: both rows import as new under `--duplicates skip`. A test pins it.

Addendum (CLI QA 2026-10-17, re-check of the w5/507 fix): the same import
filter also treats a plugin entry stamped at a real transaction's location as
written. With w5/507's `myplug.py` (a `"Broker" "fee (generated)"` 1 USD
transaction for each `#inv` entry, at its filename and line) and a real
`2026-01-05 * "buy" #inv`, importing `bank.csv` = `2026-01-05,-1.00,Broker,fee`
with `--duplicates skip --apply` exits 0 with `1 possible duplicates`, citing
`Existing entry at …/main.bean:9: 2026-01-05 * "Broker" "fee (generated)" #gen`,
and writes nothing. `list transaction` labels that fee `generated`. Cause:
`cli/src/bea_engine/importing.py:327` calls `entry_generated(entry, …)` without
`shared=reader.shared_locations(existing)`. The fix here should cover both
cases.
