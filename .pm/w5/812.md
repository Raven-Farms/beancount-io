# `cloud logout` exits 1 ("server revocation failed … The session may still be valid") on a 401 whose JSON body lacks the `{ok, error}` envelope, though USAGE says a 401 means already revoked and exits 0

**Minor · cli · 5–10m · A1.** Real CLI QA, 2026-10-17, HEAD `46a722c5c`, checkout `bea 0.3.1`, macOS 26.5.1. Simulation: a one-shot local HTTP stub on 127.0.0.1.
USAGE:1871 says "A 401 answer means the session was already revoked, so it
exits 0". No product fix implemented.

With a fake stored credential, and the stub answering `POST
/api-gateway/v1/logout` with `401` and `{"message": "Unauthorized"}`:

```sh
BEA_API_URL=http://127.0.0.1:<port> bea cloud logout
```

Actual: exit 1, `Removed the local credential, but server revocation failed:
Not authorized (Unauthorized). Run 'bea cloud login'. The session may still be
valid: revoke it from the dashboard.`. Bodies `{"error": "unauthorized"}` and
`[]` behave the same (hunter's runs). A proxy, gateway or framework default
401 often has no envelope.

Control: a 401 with the `{"ok": false, "error": {…}}` envelope, or a plain-text
body, gives `Logged out.` with exit 0 (hunter's runs).

Expected: `Logged out.` with exit 0 for any 401.

Cause: `call()` (`cli/src/cli/api/client.py`, around `:159-169`) turns a
non-envelope error body into `error_from_status(401)` and raises it, so
logout's `status_code != 401` check (`cli/src/cli/commands/cloud/app.py:122`)
is never reached.

Fix: in logout, treat an `AuthError` from an HTTP 401 as already revoked.

Dedupe: w1/058, w5/516, 012 and 701 cover other logout outcomes.

Acceptance: the stub case exits 0. A test pins it.
