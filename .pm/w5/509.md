# BQL regex functions (`grep`, `grepn`, `subst`, `findfirst`) still read `[[:alpha:]]` as a character set with exit 0, and `--json` leaks a raw `FutureWarning` with the engine's site-packages path (gap in w5/429)

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-16, HEAD `bea189ec`, checkout `bea 0.3.1`, macOS 26.5.1.
w5/429 refuses POSIX classes and nested sets in `~`, `!~` and `?~` operands.
The same patterns passed to beanquery's regex functions go through
unchecked: the query answers wrongly with exit 0, and Python's warning
reaches stderr. No product fix implemented.

Any ledger with a few transactions.

```sh
bea --json -f /abs/main.bean query "SELECT grep('[[:alpha:]]+', narration) AS g"
bea -f /abs/main.bean query "SELECT narration WHERE grep('[[a]', narration) IS NOT NULL"
```

Actual: the first exits 0 with every row `null`; stderr shows
`<engine>/site-packages/beanquery/query_env.py:320: FutureWarning: Possible
nested set at position 1` and `match = re.search(pattern, string)`. The
second exits 0 and matches `Pay` (it read "contains `[` or `a`"), with
`warning: Possible nested set at position 1`. `subst(…)` and `grepn(…)`
behave the same.

Control: `WHERE narration ~ '[[:alpha:]]+'` exits 2 with the POSIX-class
message.

Expected: the w5/429 acceptance: exit 2 naming the construct, no
`FutureWarning`/`warning:` text.

Cause: `_PATTERN_LITERAL` (`cli/src/bea_engine/query.py:1732`) matches only
`~`/`!~`/`?~` operands, so the pre-check (`:1570-1573`) never sees
constant-string arguments of regex functions.

Fix: run the same check on constant string arguments of beanquery's regex
functions (`grep`, `grepn`, `subst`, `findfirst`, `splitcomp`-style
helpers), and capture warnings during execution as a backstop.

Dedupe: searched `grep(`, `subst(`, `Possible nested set`. w5/429 and 427
(done); w6/034 is unrelated.

Acceptance: both commands exit 2 with the POSIX/nested-set message and no
warning text. A test pins them.

Addendum (CLI QA 2026-10-16, differential run against `bean-query`): `JOURNAL`'s
account pattern is unchecked too. `bea --file /abs/main.bean query "JOURNAL
'Expenses:[[:alpha:]]+'"` exits 0 with `warning: Possible nested set at
position 10` and `(no rows)`; `--json` leaks `…/beanquery/query_compile.py:295:
FutureWarning: Possible nested set at position 10`. `WHERE account ~
'Expenses:[[:alpha:]]+'` is refused with the POSIX-class message. Include the
`JOURNAL` (and `BALANCES … WHERE`/`FROM` account-pattern) operands in the same
check; the warnings backstop above would also cover it.
