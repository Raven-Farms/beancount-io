# price status says there are no managed includes immediately after reporting a refused URL include

**Trivial · cli · 10–15m · A1.** Real CLI QA, 2026-10-17, HEAD `8e35a3636`, checkout `bea 0.3.1`, macOS 26.5.1. Twice from fresh synthetic fixtures with isolated config/cache, stdin closed, no TTY, offline throughout. No product fix implemented.

```beancount
include "https://example.invalid/prices/BTC-USD"
2026-01-01 open Assets:Checking USD
```

```sh
MANAGED_PRICE_ORIGINS= bea --offline --file /abs/main.bean price status
MANAGED_PRICE_ORIGINS= bea --json --offline --file /abs/main.bean price status
```

Actual: stderr correctly names line 1 and `managed price includes are disabled.` Human stdout then says `No managed price includes in this ledger.` JSON instead gives `data: {sources: []}`. Both exit 0 and preserve ledger bytes. No network call is needed. The error proves a URL include exists; the empty-status message denies it.

Expected: distinguish an absent managed include from one refused by URL policy. Preserve the established status-command exit policy; the misleading empty-state message is the bug. Help says status lists every managed source and its errors.

Cause: `_collect_managed` (`cli/src/bea_engine/managed_load.py:1060`) separates refused URLs from pending sources. `_stage_content` (`:1222`) records their ledger errors, but the returned source list (`:513`) includes only pending sources. `_status` (`cli/src/cli/commands/price.py:92`) prints the empty-state sentence whenever that list is empty.

Fix: make status explicitly report refused includes and their causes, or qualify the empty state as no accepted/usable managed price sources while retaining the existing refusal diagnostic. Do not present a refused source as healthy or fetch it. The shared load representation is also used by refresh/export, so preserve their refusal behavior.

Dedupe: searched the whole board for the empty-state text and refused-status cases. Open w5/680 item 5 covers missing JSON ledger-validity metadata on invalid ledgers; this is the separate misleading absent-source state. w5/067 and 432 (done) concern other empty-source behavior.

Acceptance: absent includes still have a clear empty state; refused URL includes are explicitly distinguished in human and JSON status. Both remain offline and read-only.
