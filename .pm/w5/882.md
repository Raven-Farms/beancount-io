# Two equal transfers reserve the same incoming row, so `--duplicates skip` double-books the other transfer; reversing the export avoids it (follow-up to w5/821)

**Major · cli · 45–60m · A1.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `70156b1b7`, Darwin 25.5.0 arm64; frontend Python 3.13.3.
No product fix implemented. Failure, reversed-order control and same-day
control each reproduced twice from pristine synthetic fixtures.

Create `/abs/books/main.bean`:

```beancount
2024-01-01 open Assets:Checking USD
2024-01-01 open Assets:Savings USD
2024-01-01 open Expenses:Uncategorized USD
```

`checking.csv`:

```csv
Date,Description,Amount,Category,Reference
2024-02-01,TRANSFER TO SAVINGS,-100.00,Assets:Savings,C-1
2024-02-03,TRANSFER TO SAVINGS,-100.00,Assets:Savings,C-2
```

`savings.csv` (the two transfers post a day later at the receiving bank):

```csv
Date,Description,Amount,Category,Reference
2024-02-02,TRANSFER FROM CHECKING,100.00,Assets:Checking,S-1
2024-02-04,TRANSFER FROM CHECKING,100.00,Assets:Checking,S-2
```

With cwd `/abs/books`, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, and no inherited
`BEA_FILE`/`BEA_TOKEN`:

```sh
bea --json --file /abs/books/main.bean import /abs/books/checking.csv --csv date=Date,narration=Description,amount=Amount,category=Category,id=Reference --account Assets:Checking --apply
bea --json --file /abs/books/main.bean import /abs/books/savings.csv --csv date=Date,narration=Description,amount=Amount,category=Category,id=Reference --account Assets:Savings
bea --json --file /abs/books/main.bean import /abs/books/savings.csv --csv date=Date,narration=Description,amount=Amount,category=Category,id=Reference --account Assets:Savings --apply --duplicates skip
bea --json --file /abs/books/main.bean query "SELECT account, sum(number) GROUP BY account ORDER BY account"
bea --json --file /abs/books/main.bean check
```

Actual: checking writes both transfers. Savings preview reports row 1 as
`possible_duplicate`, matched to the February 3 checking transfer, and row 2
as `new`, with no match. Apply exits 0 with `written: 1` and
`possible_duplicates: 1`. Totals become Checking **−300.00 USD**, Savings
**300.00 USD**, and check passes. The two bank statements each describe only
200.00 USD of transfers: importing their other side added a third transfer.

Working controls, each starting again after only the checking import:

- Reverse the two savings data rows, keeping their dates, amounts and
  references. Both become `possible_duplicate`, each naming a different
  existing transfer; apply writes 0, preserves ledger bytes, and totals stay
  Checking −200.00 / Savings 200.00 USD.
- Use savings dates February 1 and 3. The same correct result holds.

Expected: pair existing transfers and incoming counterpart rows one-to-one
within the documented ±3-day window, preferring near dates, so both sides
of these two transfers are recognized for review. Skipping those matches
must preserve the two recorded transfers, regardless of input row order.
w5/821's explicit fix specification is one-to-one pairing within the batch;
IMPORTING says each transfer has one other side and offers `--duplicates
skip` for importing both bank statements.

Cause: the `pairs` dictionary and `paired` callback at
`cli/src/bea_engine/importing.py:481–486` cache an independent nearest-row
choice for each existing transfer. `_counterpart_row` (:1699–1720) chooses
February 2 for **both** existing transfers; it does not reserve rows
uniquely. `_transfer_counterpart` (:1671–1696) then offers a transfer only
to its selected row. February 4 cannot match either one, even though there
are two counterparts and two incoming rows. Reversing the export breaks the
tie differently and happens to avoid the collision. No native-ID hit is
involved: the banks issue different references for their respective sides.

Fix: assign counterpart matches across the eligible existing-transfer and
incoming-row sets, enforcing uniqueness on both sides rather than only one
preferred row per transfer. Preserve the date/amount window, source-account
scoping, ordinary duplicate handling and the original w5/821 control where
one transfer must not consume an additional real deposit. Do not simply
classify every same-amount row as a duplicate. No dependency or backend/API
change is needed.

Dedupe: searched all board states for multiple transfers claiming one row,
pairing collisions and nearest-row reservations; reviewed open/blocked
milestone scopes and completed w5/821 (`ed12b48f0`). That fix tests one
existing transfer against two incoming rows, but leaves the inverse
many-to-one collision above. `git log -S '_counterpart_row'` traces this
logic to that commit, with no later repair. No overlapping open item found.

Acceptance: both savings row orders yield two distinct counterpart matches,
write zero under `--duplicates skip`, preserve the ledger bytes, and retain
−200.00/200.00 USD in a fresh query. Same-day and the original
single-transfer/extra-deposit controls hold. Pin real preview/apply/query
journeys. Windows/Linux, Python importer variants and repaired behavior
remain unverified. Sanitized fixtures, after-checking snapshots and captures
are under `.tmp/qa-2026-10-20-cli-loop-pass2-2afc4ed1/`, especially
`transfer-collision-{1,2}-{staggered,reversed,same-day}/` and
`captures/pair-*.json`. The public reproduction is self-contained.
