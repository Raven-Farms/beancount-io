# `add transactions --partial` is still superlinear when a batch has several bad rows, and on a mixed batch it is now several times slower than before the w5/537 fix; bisection also changes which rows are kept (incomplete fix of w5/537)

**Major · cli · 30–45m · A1.** Real CLI QA, 2026-10-17, HEAD `cc6b52ed`, checkout `bea 0.3.1`, macOS 26.5.1. Follow-up to w5/537 (done, `e22bd04d`).
w5/537 asked for "at worst O(k log n) for k bad rows". The fix bisects, which
helps the single-bad-row case but makes batches with many bad rows slower. A
monthly bulk add with a few typos and an assertion-breaking row is that
case. No product fix implemented.

`bal.bean` is the w5/537 fixture:

```
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Assets:Cash
2026-01-01 open Expenses:Food
2026-12-31 balance Assets:Checking 0 USD
```

`mixed400.json` holds 400 rows like `{"date": "2026-02-01", "narration": "rI",
"postings": [{"account": "Expenses:Food", "amount": "1 USD"}, {"account":
"Assets:Cash"}]}`, with some rows changed:
- every 10th row (i%10==5) posts to `Assets:Checking`, breaking the
  assertion;
- every 7th (i%7==3) uses an unopened `Expenses:Nope`;
- every 13th (i%13==4) puts EUR into the USD-only `Assets:Checking`.

```sh
bea -f /abs/bal.bean add transactions --partial --from mixed400.json
```

Actual: both trees exit 1 with `Added 286 of 400 transactions; 114 rows were
rejected.` and write byte-identical ledgers. Timings:

| Batch | Pre-fix (`e22bd04d^`) | HEAD |
| --- | --- | --- |
| mixed400 (my run) | 25.3 s | 388 s (load average rose to 39 during the run, so inflated) |
| mixed400 (hunter) | 7.5 s | 28.5 s |
| mixed800 (hunter) | 25.9 s | 103.8 s |
| unopened-plus-one-assertion, 800 rows (hunter) | 31 s | 42 s |
| unopened-plus-one-assertion, 2000 rows (hunter) | 224 s | 339 s |
| w5/537's single bad row, 400 rows (my run) | 9.4 s | 0.9 s |

Loads counted by the hunter for mixed400: 932 at HEAD, 401 before.

Second effect (hunter's runs). The rows are:
1. Checking +1 from `Income:Salary`
2. Food 1 from Checking
3. Food 1 from Cash
4. Checking +1 from Salary

HEAD keeps rows 1–3; the pre-fix code keeps only row 3. Reordering the rows
changes which one HEAD rejects. Both results pass `check`, but the
resolution's rule ("a row is kept exactly when it loads after the rows kept
before it") no longer holds: row 1 alone breaks the assertion.

Expected: at most O(k log n) loads and never slower than the per-row
fallback, with a documented, order-stable keep rule.

Cause:
- `_named_rows` (`cli/src/bea_engine/ledger/adding.py:1498`) gives up on the
  whole batch as soon as one error cannot be placed (`_rows_with_errors`,
  `:1577`), discarding the rows it could name.
- `_refused_in_order` (`:1522`) then finds each remaining bad row with a fresh
  bisection over the whole rest of the batch. Each halving loads a near-full
  batch, so k proportional to n gives O(n² log n) work.

Fix:
- First drop the rows the batch error does name, then bisect only for the
  unplaceable remainder.
- Search forward from the last refused position, or fall back to per-row
  trials once k·log n exceeds n.
- State, in USAGE, the keep rule bisection implements.

Dedupe: w5/537, 123 and 337 (done) are the parents.

Acceptance: mixed400 finishes faster than the pre-fix 400 loads, the
single-bad-row case stays fast, and a test pins a load-count bound for a
multi-error batch.
