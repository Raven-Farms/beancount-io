# Editing a ledger's local plugin does not invalidate the load cache: on a slow ledger `bea check` keeps saying valid, and every read serves the old plugin's output

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
The load cache is checked only against the ledger files. A plugin beside
the ledger (loaded through `option "insert_pythonpath"`) is code the load
runs, yet editing it does not invalidate a cached load. Once a ledger is
slow enough to be cached (a load of about 1 s or more), every read answers
with the previous plugin's output until a ledger file changes:

- `bea check` and `--json check` say valid, with exit 0, after the plugin
  has started rejecting the books.
- `list`, `balance` and the other reads show the old generated entries.

w5/111, w5/116 and w5/220 fixed the same class of stale cache for
`check --auto`, attachments and foreign caches. No product fix implemented.

Fixture: `/absolute/books/main.bean` starts with the lines below, followed
by about 100,000 generated two-posting transactions (a load of several
seconds).

```beancount
option "operating_currency" "USD"
option "insert_pythonpath" "TRUE"
plugin "bigplug"
2020-01-01 open Assets:Checking USD
2020-01-01 open Expenses:Food USD
2020-01-01 open Equity:Opening
```

`/absolute/books/bigplug.py` starts as a pass-through:

```python
__plugins__ = ["run"]
def run(entries, options_map, config=None):
    return entries, []
```

Use an empty isolated XDG_CACHE_HOME and BEA_CONFIG_DIR,
BEA_NO_UPDATE_NOTIFIER=1, no inherited BEA_FILE/BEA_TOKEN, and closed
stdin.

```sh
bea -f /absolute/books/main.bean check            # exit 0, writes the load cache
cat > /absolute/books/bigplug.py <<'EOF'
import collections
__plugins__ = ["run"]
E = collections.namedtuple("E", "source message entry")
def run(entries, options_map, config=None):
    return entries, [E(entries[0].meta, "plugin now rejects the books", None)]
EOF
bea -f /absolute/books/main.bean check
bea --json -f /absolute/books/main.bean check
```

Actual:

- The second `check` exits **0** silently, and `--json check` gives
  `"valid": true`.
- In a variant where the plugin adds a note, `list note` keeps showing
  `VERSION-ONE` after the file is changed to say `VERSION-TWO`.
- After `touch main.bean`, or after deleting the load cache, `check` exits
  1 with `main.bean:4: plugin now rejects the books`.

Reproduced in fresh cache directories, one of them an independent rerun.

Once the cache holds an error type defined by the local plugin, every
plain `bea check` also prints `ERROR:root:Cache file is corrupted: No
module named 'bigplug'; recomputing.` Native bean-check unpickles the
cache without the ledger directory on `sys.path`.

Control: a ledger that loads in under a second, so no cache is written,
reflects plugin edits immediately.

Expected: `docs/USAGE.md` says "A cached load that still matches the disk
is served as before". A plugin module that the ledger loads from beside
itself is part of what the load reads. `bea check` is the documented CI
gate, and it must not certify a ledger against plugin code that no longer
exists.

Cause: `_load_fresh` (`cli/src/bea_engine/managed_load.py:540-556`)
trusts Beancount's own cache validity, which fingerprints only the parsed
ledger files. It then rechecks includes, documents and writes made during
the load, but records no plugin modules resolved through
`insert_pythonpath`. Native `bean-check` reads the same cache.
`_export_plugin_modules` (`:1247-1274`) already knows how to find those
modules.

Fix (choose one):

- Treat local plugin modules as cache inputs: record their paths,
  `mtime_ns` and size in the engine's cache mark, and drop the cache when
  any of them differs.
- Do not write a cache for a ledger that loads a plugin from beside
  itself.

Either way, `bea check`'s native pass must see the same decision. Plugins
in site-packages can stay out of scope. No dependency or API change.

Blast radius: every command that loads through `_load_fresh` or native
`bean-check` (`check`, `list`, `balance`, `report`, `query`, `price`, the
`add` pre-write reads, and `import` duplicate detection), on cached
ledgers with a local plugin.

Dedupe: searched `.pm/**`, including `done/`, for "load cache" and
`picklecache` together with plugin, edit or stale, and for "Cache file is
corrupted".

- w5/111: `check --auto`.
- w5/116: attachments.
- w5/220: foreign caches.
- w5/218: writes during a load.
- w5/065 and w5/067: cache path aliasing.

None covers plugin code edits.

Acceptance: on the fixture, after the plugin edit and without a `touch`,
`check` exits 1 naming the plugin's error, `list` reflects the new plugin,
and plain `check` prints no "Cache file is corrupted" line. A real-command
regression test edits a local plugin between two cached reads. Only macOS
and the checkout were exercised.

Addendum (CLI QA r97, 2026-10-14): the cache also hides a plugin that
can no longer be imported. On a 150k-transaction ledger with `plugin
"myplug"`, a read with `PYTHONPATH` set writes the load cache. `bea
check` without `PYTHONPATH` then exits 0 and `balance` still shows the
cached totals. With an empty `XDG_CACHE_HOME`, the same `check` reports
`Cannot import plugin "myplug": ModuleNotFoundError`. Reproduced twice by
the hunter. The fix should also treat "module no longer importable" (or
a changed module path) as invalidating the cache.

Addendum (CLI QA r102, 2026-10-14): `bea check -C/--no-cache` bypasses
the stale cache. With the plugin module removed after a cached load,
plain `check` exits 0, while `check -C` exits 1 naming `Cannot import
plugin "myplug"`. Until the cache key is fixed, the docs could point at
`check -C` as the escape hatch.
