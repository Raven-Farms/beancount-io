# BQL value errors caused by a typo still exit 1 as "validation" with a Python class name: `parse_date('x')` gives `ParserError: Unknown string format`, and `date + 99999999` gives `OverflowError`

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, Python 3.13.3.
[103](./done/103.md) made an invalid regular expression in BQL a usage
error: exit 2, category `usage`, naming the pattern. Its resolution says
"Other evaluation-time errors the note mentions (date overflow,
`parse_date('x')`) take the generic path still and were not filed or
changed". Both are mistakes in the query text, yet they still exit 1 as
`validation`, which the exit-code table reserves for ledger errors. The
message also starts with a Python exception class name and offers a
traceback. No product fix implemented.

Use the fixture from [313](./313.md) and the same environment.

```sh
bea -f /absolute/books/main.bean query "SELECT parse_date('x')"
bea --json -f /absolute/books/main.bean query "SELECT date WHERE date > parse_date('nope')"
bea -f /absolute/books/main.bean query "SELECT date + 99999999"
```

Actual:

- `parse_date('x')` exits 1 with `Error: ParserError: Unknown string
  format: x Pass --debug before the command for a traceback.`
- The `--json` form gives `{"error": {"category": "validation",
  "message": "ParserError: Unknown string format: nope …", "exit_code": 1}}`.
- `date + 99999999` exits 1 with `Error: OverflowError: date value out of
  range …`.
- `parse_date('2026-13-45')` and `date_add(date, 9999999)` behave the same
  way.

Reproduced in three fresh setups.

Controls:

- `SELECT 'x' ~ '('` exits 2 with `Cannot run this BQL query: '(' is not a
  valid regular expression …`.
- A mistyped date literal (`2020-99-01`) exits 2.

Expected: the `docs/USAGE.md` exit table maps 2/`usage` to "Bad arguments"
and 1/`validation` to "Ledger or validation error". 103 established that a
malformed operand in the query text is a usage error that names the
problem and shows no class name.

Cause: `_compiled` (`cli/src/bea_engine/query.py:1380-1405`) translates
`re.error`, Beanquery errors and parser-literal `ValueError`s. Any other
`ValueError` is re-raised at `:1397`, including dateutil's `ParserError`,
which subclasses it. `OverflowError` is never caught. The frontend
(`cli/src/cli/engine/launch.py:415-423`) then prefixes the class name.

Fix: in `_compiled`, map a `ValueError` or `OverflowError` raised while
evaluating rows to `UsageError("Cannot run this BQL query: <reason>.")`
(exit 2), as 103 did for `re.error`. If that is too broad, limit it to
`ParserError` and date-arithmetic `OverflowError`. Keep tracebacks for
`--debug`. No dependency change.

Blast radius: `bea query` one-shots, `.run` and the interactive shell, in
text and JSON. Affects `parse_date`, date arithmetic, `date_add`, and any
BQL function that raises `ValueError` or `OverflowError` on a bad argument.

Dedupe: searched the board for `parse_date`, `Unknown string format`,
`ParserError`, `OverflowError` and "date value out of range".

- w5/103: regex only; its resolution leaves these cases out.
- w5/109: date literals.
- w3/407: report-range arithmetic.
- w5/200: Beancount's `ParserError` in writes.

None of these is open.

Acceptance: on the fixture, the three commands exit 2. The message starts
with `Cannot run this BQL query:`, names the bad value, and contains no
`ParserError:` or `OverflowError:`. `--json` reports category `usage`. A
real-command regression test covers `parse_date('x')` in SELECT and WHERE,
and date overflow. Only macOS and the checkout were exercised.

Addendum (CLI QA r47, 2026-10-14, same HEAD). Two more cases share the
cause:

- `LIMIT` above `sys.maxsize`: `bea -f main.bean query "SELECT account
  LIMIT 9223372036854775808"` exits 1 with `Error: ValueError: Stop
  argument for islice() must be None or an integer: 0 <= x <=
  sys.maxsize`, raised by upstream `beanquery/query_execute.py:238`
  inside `run()` (`cli/src/bea_engine/query.py:1381`).
  `LIMIT 9223372036854775807` works.
- `query --source`: this case and this note's own triggers
  (`parse_date('x')`, `date + 99999999`) print a 170–270 line boxed Rich
  traceback with exit 1. `source_query` (`cli/src/bea_engine/main.py:616-640`)
  and `native_one_shot` (`query.py:566-570`) catch only `BeanqueryError`,
  `EngineError` and `OSError`. w5/293 covers other `--source` tracebacks,
  not evaluation errors.

Extend the fix to map this `ValueError` (or check `LIMIT <= sys.maxsize`
when compiling), and make sure the mapped error also reaches `--source`
as one line with exit 2. The acceptance then also covers the `LIMIT`
case and all three `--source` runs. Reproduced by me with `-f` and with
`--source` (170 lines).
