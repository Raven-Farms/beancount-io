# Any nonzero holding disables same-day batch purchase ordering, even when the sale needs more shares (follow-up to w5/730 and w5/543)

**Minor · cli · 45–60m · A1.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `79dc0d7aa`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
Both the on-disk partial-holding case and an earlier-row partial purchase
reproduced twice from pristine fixtures; nearby controls repeated twice.
No product fix implemented.

Create `/abs/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Broker HOOL "FIFO"
2024-01-01 open Equity:Opening USD
2024-01-01 open Income:Gains USD
2024-01-01 * "Cash"
  Assets:Cash 1000 USD
  Equity:Opening -1000 USD
2024-01-02 * "Old lot"
  Assets:Broker 1 HOOL {100 USD}
  Assets:Cash -100 USD
```

Create `/abs/books/batch.json`, with the sale before the same-day buy:

```json
[
  {"date":"2024-02-01","narration":"Sell two","postings":[
    {"account":"Assets:Broker","amount":"-2 HOOL {}"},
    {"account":"Assets:Cash","amount":"300 USD"},
    {"account":"Income:Gains"}
  ]},
  {"date":"2024-02-01","narration":"Buy two","postings":[
    {"account":"Assets:Broker","amount":"2 HOOL {150 USD}"},
    {"account":"Assets:Cash","amount":"-300 USD"}
  ]}
]
```

With cwd `/abs/books`, closed stdin/no TTY, isolated absolute
`BEA_CONFIG_DIR`/`XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, and no inherited
`BEA_FILE`/`BEA_TOKEN`:

```sh
bea --json --file /abs/books/main.bean add transactions --from /abs/books/batch.json
bea --json --file /abs/books/main.bean check
bea --json --file /abs/books/main.bean query 'SELECT account, sum(cost(position)) GROUP BY account ORDER BY account'
```

Actual: add exits 1, stdout empty, with one JSON error on stderr:
`Row 1: Proposed append (not written): Not enough lots to reduce "-2 HOOL
{}": 1 HOOL {100 USD, 2024-01-02}`. It reports zero written and preserves the
ledger bytes. Check passes on that unchanged ledger. The error suggests
`--partial`; a fresh fixture with that flag writes only the purchase,
rejects the sale, exits 1 and accurately reports `written_rows: [1]`.
That partial outcome is documented behavior, not a separate finding or
silent data-loss claim.

Working control: on a pristine copy, swap the two JSON objects so the buy
comes first. Both write, check passes, and a fresh query has broker cost
**150 USD**, cash **900 USD**, opening equity **−1000 USD**, gains
**−50 USD**. FIFO closes the old 100 USD share and one new 150 USD share
against the 300 USD proceeds, leaving one new share. All input amounts and
dates are otherwise identical.

The same hole exists for purchases earlier in the batch: omit `Old lot`
from the root and prepend a February 1 `Buy one first` row posting
`1 HOOL {100 USD}` to Broker and `-100 USD` to Cash. Order
`Buy one first, Sell two, Buy two` refuses Row 2 with only one available
share; `Buy one first, Buy two, Sell two` writes all three and produces the
same correct totals above.

Additional controls, each twice: with no existing holding and just the
original two rows, the CLI moves `Buy two` before `Sell two`, writes both,
and leaves no stock/gain with cash 1000 USD. With **two** old shares instead
of one, it correctly preserves `Sell two` before `Buy two`, closes the old
lot for 100 USD gain, and leaves two new shares at 300 USD cost. Preserve
that input-order behavior from completed w5/730.

Expected: the documented whole-batch handling in `cli/docs/USAGE.md:1585`
lets a sale use a purchase later in the same-date input. Having some shares
is not proof that this sale already books in input order. Reorder only a
sale that needs the later same-day purchase to book, while keeping a sale
that actually books in its original place. Do not return to unconditional
reordering, which changed realized gains in w5/730.

Cause: `_same_day_purchases_first` in
`cli/src/bea_engine/ledger/adding.py:1937–2021`, called only by bulk add at
:1827, tracks purchases as sets of `(account, commodity)`. Its
`file_holds` (:1984–1991) returns true for **any nonzero** summed units, and
its `before` set (:2004–2016) records only whether a prior purchase exists.
Neither proves that the available quantity/lots can satisfy the sale. That
boolean blocks the same-day reorder, and later validation rejects the
otherwise bookable batch. `_held_through` itself is also used by close;
the repair should stay in batch ordering, preserving close's semantics.

Fix: make the ordering decision reflect whether this sale can actually book
against the preceding inventory, including quantities and relevant lot
selection. A booking-aware fallback or quantity-aware dependency check must
retain the sufficient-holding control and input row indexes. Keep atomic
refusal and partial-outcome reporting accurate. No dependency, backend or
API change is needed.

Dedupe: searched all board states for partial/insufficient holdings,
quantities, same-day sales and `Not enough lots`, and reviewed current open
milestones. Completed w5/543 added ordering; w5/730 (`6468f1cb2`) added the
nonzero/set guard and its sufficient-holding controls. The current case is
an uncovered boundary of that fix; its recorded successful controls still
hold. No overlapping open item or later repair was found in targeted
history. w5/150 concerns allowed pre-existing errors, not ordering a new
valid batch.
