# Ask drops the server request ID on ordinary HTTP failures while cloud errors and Ask redirects preserve it

**Minor · cli · 15–25m · A1/A2.** Real CLI QA, 2026-10-20, checkout
`bea 0.3.1`, HEAD `1bbcd6204`, Darwin 25.5.0 arm64, frontend Python 3.13.3.
The installed Ask SDK made real HTTP calls to an owned loopback simulator;
this is a local error-translation defect, not a hosted-service finding.
Reproduced twice from fresh synthetic ledgers; controls twice. No fix made.

Serve this inspected synthetic handler on localhost, choosing an unused port:

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
class Handler(BaseHTTPRequestHandler):
    def log_message(self, *args): pass
    def answer(self):
        if self.command == 'POST':
            self.rfile.read(int(self.headers.get('Content-Length', '0')))
        body = b'{"error":{"message":"Synthetic Ask failure"}}'
        self.send_response(500)
        self.send_header('Content-Type', 'application/json')
        self.send_header('Content-Length', str(len(body)))
        self.send_header('X-Request-ID', 'qa-ask-request-id')
        self.send_header('x-should-retry', 'false')
        self.end_headers()
        self.wfile.write(body)
    do_POST = answer
    do_GET = answer
HTTPServer(('127.0.0.1', 18790), Handler).serve_forever()
```

Both exit **1**, stdout empty. Ask prints only
`Error: Server error (Synthetic Ask failure).`; cloud prints that sentence
plus `  Request ID: qa-ask-request-id`. Changing the handler to 403 gives
Ask's correct permission message and exit **3**, but again loses the ID.
There is one request per command; the synthetic ledger remains byte-identical.

Nearby controls: a 302 with `Location: /must-not-follow` and the same request
ID gives Ask's documented redirect sentence and the ID, exit 1, without
following it. A 403 without the header correctly has no ID. All four controls
and the two failing statuses were repeated in independent processes; no
hosted requests or AI quota were used. The broader simulation also observes
the loss on 400, 401, 409 and 429, with their correct existing exit categories.

Expected: preserve the backend ID in every supported HTTP failure, as
`cli/docs/USAGE.md:368` promises, so terminal users can give support a
correlation ID. Preserve the existing status categories, sentences, retry
policy and write accounting. Ask's documented JSON refusal stays unchanged.

Cause: `cli/src/cli/ask/agent.py:269` calls `error_from_status` in the
`ModelHTTPError` arm without `request_id`. The SDK supplies lowercased
response headers on this exception (`pydantic_ai/exceptions.py`), and its
OpenAI adapter populates them from the actual response. The neighboring
redirect arm passes headers, and `_model_api_error` at :333–335 already
passes `request_id_from(response.headers)` for wrapped HTTP errors.
The special quota branch at :267 also constructs a bare `BeaError`; include
its ID when supplied, without changing its quota wording. That special
branch was source-traced, not separately reproduced in this run.

Fix: carry the request ID from the status exception's headers into the
translated error, including quota refusals. Use the shared extraction logic
and preserve safe rendering; do not expose arbitrary headers or SDK strings.

Dedupe: searched all board states and active milestone scopes for Ask,
`ModelHTTPError` and request IDs. Completed w5/369 fixes text rendering of
an ID already attached to `BeaError`; this path never attaches it. Completed
w5/679 (`6fce45709`) fixes SDK-wrapped redirects and their IDs, while ordinary
HTTP failures use the separate earlier arm. w5/701 concerns logout's unknown
write outcome. No matching open repair or later source fix found.
