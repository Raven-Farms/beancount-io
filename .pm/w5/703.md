# A malformed `BEA_TOKEN` gets "or run 'bea cloud login'", which login refuses while the variable is set, and `cloud logout` exits 3 instead of its documented `BEA_TOKEN` no-op (gap in w5/516)

**Trivial · cli · 5–10m · A1.** Real CLI QA, 2026-10-17, HEAD `733ea312`, checkout `bea 0.3.1`, macOS 26.5.1. Follow-up to w5/516 (done).
No product fix implemented.

```sh
BEA_TOKEN='qa token' bea cloud logout
BEA_TOKEN='qa token' bea cloud login
```

Actual:
- logout exits 3: `Invalid BEA_TOKEN or stored credential (contains
  whitespace, control or non-ASCII characters). Fix the environment value or
  run 'bea cloud login'.`
- login exits 2: `BEA_TOKEN is set in this shell and takes precedence over a
  login… Unset BEA_TOKEN first`.

Control: `BEA_TOKEN=qa-fake-token bea cloud logout` exits 0 with `BEA_TOKEN is
set in this shell; 'bea cloud logout' leaves it unchanged…`.

Expected:
- When the variable is the source, the advice is to fix or unset `BEA_TOKEN`
  and does not suggest login. USAGE:1826 says advice follows "the source
  actually in use".
- Logout gives its documented `BEA_TOKEN` no-op, since it never sends the
  token.

Cause: `_validate_token` (`cli/src/cli/auth/credentials.py:25-31`) uses one
message for both sources, and logout loads the credential before it checks
for `ENVIRONMENT`.

Fix: word the error by source, and check `BEA_TOKEN` in logout before
validating it.

Dedupe: w5/516 (done) is the login side; w1/005, w1/057 and w3/271 (done)
cover other token-validation cases.

Acceptance: both commands advise only about `BEA_TOKEN`; logout exits 0 with
the no-op note.
