# A FIFO in place of a write-lock file fails `add` with exit 1 `UnsupportedOperation: File or stream is not seekable`, and a directory there is blamed on the lock directory

**Trivial · cli · 10m · A1.** Real CLI QA, 2026-10-16, HEAD `595daa2f`, checkout `bea 0.3.1`, macOS 26.5.1.
USAGE's lock section gives exit 3 naming the obstruction. The lock file is
opened, then `fdopen`ed outside the error handling. The message assumes any
`OSError` came from the lock directory. The opened descriptor also leaks.
No product fix implemented.

After one `add` (so `$XDG_CACHE_HOME/bea/locks/<key>.lock` exists), replace
that lock file with a FIFO (or a directory):

```sh
bea --json -f /abs/main.bean add price --commodity AAPL --amount '100 USD' --date 2024-01-05
```

Actual: FIFO: exit 1, `{"error": {"category": "validation", "message":
"UnsupportedOperation: File or stream is not seekable. Pass --debug…"}}`,
naming no path. Directory: exit 3, `Cannot take the write lock: the lock
directory …/cache/bea/locks cannot be created or is not writable (Is a
directory).`, though the directory is fine. The ledger is unchanged in both.

Control: a read-only cache root exits 3 with a correct message.

Expected: exit 3 naming the lock file and what it is (`…/locks/<key>.lock is
not a regular file`), or replace a non-regular entry inside bea's own `0700`
directory.

Cause: `cli/src/bea_engine/ledger/write.py:866` (`os.fdopen(fd, "r+b")`) sits
outside the `try` at `:854-864`, whose message assumes the directory.

Fix: check `S_ISREG` after opening, name the lock file, and close the
descriptor on failure.

Dedupe: searched `not seekable`, `UnsupportedOperation`; w5/113 (done) covers
the lock directory.

Acceptance: both fixtures exit 3 naming the lock file. A test pins them.
