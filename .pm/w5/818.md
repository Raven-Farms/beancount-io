# Two re-imports the w5/598 fix broke: a Python importer's own entry whose first posting is a sub-account (or another balance-sheet leg) is held as a "possible duplicate … on the other side of a transfer" (exit 4), and a migrated transfer's `import-id-2` no longer exact-matches the second account's row (regression from w5/598)

**Major · cli · 20–30m · A1.** Real CLI QA, 2026-10-17, HEAD `3d73eb246`, checkout `bea 0.3.1`, macOS 26.5.1. Regression from w5/598 (done, `57a00fd7d`).
IMPORTING's "Duplicate decisions" says import "always checks `import-id` and
`import-id-2`", and that an exact match is skipped. dedup.md says that
re-importing a file adds zero entries, and that `import-id-2` exists so the
counterparty's row matches "mechanically — no user decision needed". Before
`57a00fd7d`, both cases below were exact duplicates (hunter's run on the
pre-fix tree). No product fix implemented.

1. **Importer's own entry.** The ledger opens `Assets:Broker`,
   `Assets:Broker:HOOL HOOL` and others. A minimal beangulp importer with
   `account() = Assets:Broker` emits one row: FITID `B1`, "Buy HOOL", postings
   `Assets:Broker:HOOL 10 HOOL {50 USD}` and `Assets:Broker -500 USD`.
   - `bea -f /abs/main.bean import buy.ofx --config imp.py --apply` writes it
     (exit 0).
   - Running the same command again exits 4: `Import needs review; nothing was
     written.`, with `Stable ID ofx:B1 is on the other side of a transfer from
     Assets:Broker:HOOL…`. HOOL is the importer's own sub-account.
   - `--duplicates include` writes a second copy of the trade. A Checking →
     Savings transfer row behaves the same (hunter's runs).
2. **`import-id-2`.** The ledger holds a migrated transfer:

   ```
   2026-03-10 * "Transfer to savings"
     import-id: "bank:1001"
     import-id-2: "bank:2002"
     Assets:Checking  -500.00 USD
     Assets:Savings    500.00 USD
   ```

   `bea -f /abs/main.bean import savings.csv --csv
   date=Date,amount=Amount,narration=Description,id=ID --account Assets:Savings
   --apply` (row `2026-03-10,TRANSFER FROM CHECKING,500.00,2002`) exits 4. The
   row is a `possible_duplicate`, and `Stable ID bank:2002 is on the other side
   of a transfer from Assets:Checking…`. `--duplicates include` doubles Savings
   to 1,000.00 USD (hunter's run).

Control: with every leg under the importer's account, the re-import is an
exact duplicate. The checking side (`bank:1001`) still matches exactly.

Expected: both are exact duplicates, exit 0, and nothing is written.

Cause: `_issued_elsewhere` (`cli/src/bea_engine/importing.py:1214`) counts the
first posting as the importer's own only if it is in `_source_legs` (`:936`),
which holds only exact-account postings when any exist. The entry's native
IDs then go to the transfer index instead of the exact one. `_identities`
(`:1140`) treats `import-id-2` like `import-id`, though it is by definition the
second account's own ID.

Fix: treat a first posting to the account or any sub-account as the
importer's own, and always index `import-id-2` as an exact identity for the
non-first balance-sheet leg.

Dedupe: w5/598 and 600 (done) are related; nothing open covers this.

Acceptance: both re-imports report exact duplicates and exit 0. Tests pin
both.
