# Two `bea import` runs at once lose one remembered mapping, and a later flag-free `--apply` writes rows to the wrong account

**Major · cli · 45–60m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
Import memory is updated by read-modify-write with no lock. When a
checking and a savings export with the same headers are previewed in
parallel (a script or agent fanning out over several statements), one
account's entry is often lost. `bea` then no longer knows the header is
ambiguous, and a flag-free `--apply` of the other file exits 0 with its
rows on the surviving account. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Assets:Savings USD
2026-01-01 open Expenses:Uncategorized USD
2026-01-01 open Equity:Opening USD
2026-01-02 * "Open" "Opening balance"
  Assets:Checking  5000.00 USD
  Equity:Opening
```

`/absolute/books/checking.csv`:

```csv
Date,Description,Amount
2026-02-02,Grocer,-20.00
2026-02-03,Cafe,-4.50
```

`/absolute/books/savings.csv`:

```csv
Date,Description,Amount
2026-02-05,Interest,1.25
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME (fresh for each run),
BEA_NO_UPDATE_NOTIFIER=1, no inherited BEA_FILE/BEA_TOKEN, closed stdin, no
TTY, cwd `/absolute/books`.

```sh
bea -f main.bean import checking.csv --account Assets:Checking &
bea -f main.bean import savings.csv  --account Assets:Savings  &
wait
bea -f main.bean import savings.csv --apply
```

Actual: both previews exit 0. In 4 of 8 fresh runs the record
`$BEA_CONFIG_DIR/importers/csv-<sha256>.json` held one source
(`Assets:Checking`) instead of two. In such a run the third command exits
0, prints `Wrote 1 entry`, and the ledger gains:

```beancount
2026-02-05 ! "Interest"
  import-id: "csv:sha256:0eb9ed705a3e81c0"
  Assets:Checking            1.25 USD
  Expenses:Uncategorized    -1.25 USD
```

The savings interest is booked to checking. The only signal is a stderr
note about remembered settings. A worker saw the survivor be
`Assets:Savings` in other runs, with `import checking.csv --apply` then
writing both checking rows to savings.

Control: in the other 4 runs, and whenever the two previews run one after
the other, both accounts are remembered and the flag-free apply exits 2:
`This CSV header matches multiple source accounts: Assets:Checking,
Assets:Savings. Pass --account ACCOUNT to select the export's account;
nothing was written.`

Expected: `docs/IMPORTING.md`: "If checking and savings exports share
headers, their mappings are kept separately and subsequent previews and
applies require `--account ACCOUNT`; bea refuses to choose between them."

Cause: `cli/src/cli/commands/import_.py:263-284` (`_remember_csv`) reads
the record, appends its own entry and replaces the file atomically, without
a lock. The rename prevents a torn file but not a lost update: the later
writer drops the earlier writer's entry. `_recall_csv` (`:233-241`) then
finds a single match and never reaches the multiple-accounts refusal.

Fix: hold a lock across the read and the replace of the record, or store
one file per (header signature, account) so writers never share a file. No
dependency or API change.

Blast radius: any parallel `bea import` on one ledger, preview or apply.
With different headers per file a lost entry makes the next flag-free
import exit 2 (a worker saw "Read a column mapping … but not which
account"), which is safe. Ledger writes themselves are locked and
unaffected.

Dedupe: board search for remembered settings with concurrent, parallel,
race, and "lost update" finds w5/181–183 (ledger write locks), w5/073 and
w5/205 (what is remembered and how it is keyed) and w1/done/105 (corrupt
record); none covers concurrent loss of import memory.

Acceptance: after N parallel successful previews the record holds N
sources, for 50 repetitions of the two-file race, and the shared-header
flag-free apply always exits 2 naming both accounts. Only macOS and the
checkout were exercised.
