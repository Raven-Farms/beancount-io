# With an unwritable config directory, the update check runs on every command: offline, each interactive command waits the full 3-second timeout instead of "at most once a day"

**Minor · cli · 15–20m · A2.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, Python 3.13. Simulation: a uv-tool install layout, with the index pointed at an unroutable address.
The update notice caches every outcome for 24 hours so that "an offline
machine waits at most once a day". When the cache cannot be written, the
outcome is never remembered. Every interactive command from a uv-tool,
pipx or Homebrew install (one with a terminal on stderr) then queries the
index again. Offline, each of them blocks for the full `TIMEOUT_SECONDS`
(3 s) before exiting, and prints nothing that explains the delay.

The cache can be unwritable when `BEA_CONFIG_DIR` / `~/.config/bea` or
`update-check.json` is not writable. Examples: a root-owned directory left
by `sudo bea …`, an immutable or read-only home in a container or Nix
setup, or a mode-0400 cache file. No product fix implemented.

Setup (simulation):

- A frontend installed under a `…/uv/tools/beancount-io` venv, so the
  channel is `uv-tool`.
- `BEA_UPDATE_API_URL=http://10.255.255.1`, an unroutable address.
- Isolated `BEA_CONFIG_DIR=/absolute/cfg` and XDG dirs.
- `BEA_NO_UPDATE_NOTIFIER`, `CI`, `--json` and `--no-input` all unset.
- stdin and stderr on a PTY, stdout to a pipe.
- Any valid ledger.

```sh
mkdir /absolute/cfg && chmod 500 /absolute/cfg
bea -f /absolute/books/main.bean balance     # three times, timing each
```

Actual: all three runs exit 0 and take 3.11 s each. stdout and stderr are
clean, and no cache file is created. Reproduced in two fresh setups.

Control: with a writable `/absolute/cfg`, the first run takes 3.12 s and
caches `{"checked_at": …, "version": ""}`, and the second run takes 0.25 s.

Expected: `docs/USAGE.md` › The update notice: "Every outcome — including a
failure — is cached for 24 hours … so an offline machine waits at most
once a day and prints nothing." The `write_cache` docstring says "a
read-only home must not break a command". A 3 s stall on every command
breaks interactive use.

Cause: `write_cache` (`cli/src/cli/update.py:121-127`) swallows the
`OSError`, and `latest_version` (`:156-180`) has no other record of the
outcome. So `start` launches a fetch on every run, and `print_notice`
waits for it for up to `TIMEOUT_SECONDS`.

Fix (any one):

- Fall back to a per-user location under `cache_dir()`.
- Before starting the check, test whether the cache is writable; if it is
  not, skip the check.
- In `print_notice`, do not wait when there is nowhere to save the answer.

Any of these keeps the cost to at most one timeout per day. No dependency
or API change.

Blast radius: every interactive command on a release install whose config
directory or cache file is unwritable while the index is unreachable or
slow. `--json`, `--no-input`, `CI`, checkout installs and non-TTY runs are
muted and unaffected.

Dedupe: searched `.pm/**` (including `done/`) for `update-check`,
`write_cache`, "once a day", "read-only" and "unwritable".

- w5/008 explicitly left "offline failure caching" unexercised.
- w5/176 moved the cache under `BEA_CONFIG_DIR`.

Neither covers an outcome that cannot be cached.

Acceptance: on the fixture, the second and third runs finish well under
1 s, and a writable config directory still caches as before. A test with a
read-only config directory and a hanging fake index asserts that the second
run makes no request (or does not wait). Only macOS and a simulated
install and network state were exercised.
