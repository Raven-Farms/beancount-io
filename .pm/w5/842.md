# A period starting at 0001-01-01 is refused: `-t 0001` gets "Invalid time filter '0001'. Use … YYYY …", and BQL `FROM OPEN ON 0001-01-01` says "date value out of range", though the 9999 boundary got a dedicated fix (sibling of w3/407)

**Minor · cli · 10m · A1.** Real CLI QA, 2026-10-17, HEAD `473bce6af`, checkout `bea 0.3.1`, macOS 26.5.1. Sibling of w3/407 (done).
No product fix implemented.

`y1.bean` opens `Assets:Cash USD` and `Expenses:Food USD` on 0001-01-01 and has
one 5 USD transaction that day.

```sh
bea -f /abs/y1.bean report income-statement -t 0001
bea -f /abs/y1.bean query "SELECT date FROM OPEN ON 0001-01-01"
```

Actual:
- The report exits 2 with `Invalid time filter '0001'. Use month, year, YYYY,
  YYYY-MM, or a date range … date value out of range`. It rejects a
  well-formed YYYY and suggests YYYY. `balance -t "0001-01 - 0001-03"` behaves
  the same (hunter's run).
- The query exits 2 with `Cannot run this BQL query: date value out of
  range.`, but the date is in range.

Control: the unfiltered report works (`0001-01-01 through 0001-01-01`), as do
`-t 0001-02` and `-t 0002`. `-t 9999` gets w3/407's dedicated note.

Expected: report from the start without an opening summary, or name the
lower boundary as w3/407 does for the upper one.

Cause: Beancount's period clamp computes `date - 1 day`
(`beancount/ops/summarize.py`, via `cli/src/fava/core/filters.py`, around
`:399`). `_unreportable_boundary` (`cli/src/bea_engine/report.py:566`) detects
only `date.max`.

Fix: handle a begin of `date.min` (skip the summary) or name the boundary, in
reports and BQL.

Dedupe: w3/407, w5/194, 390 and 314 (done) cover the upper bound.

Acceptance: `-t 0001` reports the year; the BQL case answers or names the
boundary.
