# A UTF-8 BOM on line 1 hides a first-line `pushtag`/`pushmeta` and `option "name_*"` from the write checks: an append under `--allow-errors` silently inherits the tag, and adds under a renamed root are refused as "not used" (incomplete fix of w5/464; gap in w5/402)

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-17, HEAD `a7c2762d`, checkout `bea 0.3.1`, macOS 26.5.1. Follow-up to w5/464 and w5/402/462 (done).
USAGE:589 says a BOM-marked ledger "loads like any other". Two write-path
checks scan the raw text, where the BOM sits in front of the first
directive, so a match anchored at the start of line 1 fails. No product fix
implemented.

1. **Inherited tag.** `main.bean` is `include "inc.bean"` followed by opens
   for `Assets:Cash` and `Expenses:Food`. `inc.bean` is the bytes `EF BB BF`
   followed by `pushtag #trip` and one transaction.
   - `bea --file /abs/main.bean add transaction Groceries --date 2026-01-05
     -p "Expenses:Food 10 USD" -p Assets:Cash --into inc.bean` exits 1 with
     `The ledger already has 1 error(s)… Unbalanced pushed tag: 'trip'. Pass
     --allow-errors to write anyway.`
   - With `--allow-errors` it exits 0, and `query "SELECT narration, tags"`
     shows `Groceries  trip`. The JSON echo says `"tags": []`.
   - `pushmeta`, `add note`, `add transactions` and `import --apply` behave
     the same.
   - Control: without the BOM, the write exits 2 with `…ends inside
     \`pushtag #trip\` at line 1, so an entry appended there would silently
     inherit it.`, as w5/464 requires "even under `--allow-errors`".
2. **Renamed roots.** `bom.bean` is `EF BB BF` followed by `option
   "name_expenses" "Aufwand"` and opens for `Assets:Cash` and `Aufwand:Food`.
   - `check` exits 0.
   - `add note -a Aufwand:Food …` and `add open -a Aufwand:X …` exit 2: `Account
     'Aufwand:Food' has root 'Aufwand', which this ledger does not use; its
     roots are Assets, Liabilities, Equity, Income, Expenses…`. `add close`,
     `pad` and `document` behave the same, and `add transaction`'s advice to
     `add open` loops into this refusal.
   - With a BOM root holding `option "name_assets" "Activos"`, `add
     transaction … --into txns/new.bean` exits 1 asking to "Repeat the root's
     options at the top of new.bean", the seed that the no-BOM control writes
     itself.
   - Control: the same files without the BOM succeed.

Expected: a BOM-marked file behaves exactly like the same file without the
BOM in both checks.

Cause:
- `open_pushes(original.decode("utf-8"))` (`cli/src/bea_engine/ledger/write.py:2560`)
  keeps U+FEFF, so the lexer sees `﻿pushtag` as an error token.
- `root_names_of` (`cli/src/bea_engine/ledger/text.py:331-344`, called from
  `ledger/adding.py:89`) and `new_include_seed` (`write.py:2512-2523`) match
  `^option` on text that still has the BOM.

Fix: drop a leading U+FEFF (decode with `utf-8-sig`) before each scan.

Dedupe: searched `pushtag`, `pushmeta`, `name_*` with `BOM`. w5/464, 402 and
462 (done) never mention a BOM; w5/704 is the ingest side.

Acceptance: both fixtures behave like their no-BOM controls. A test pins one
case of each.
