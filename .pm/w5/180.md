# A scalar subquery in a `WHERE` comparison exits 1 as a ledger validation failure with a raw `AttributeError`

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, Beanquery 0.2.0, macOS.
`WHERE date > (SELECT min(date) …)` is unsupported by Beanquery. `bea`
already turns the SELECT-list form of this mistake into a helpful exit-2
message; the comparison form escapes as `'EvalQuery' object has no
attribute 'dtype'` with exit 1. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash
2024-01-01 open Expenses:Food

2024-01-05 * "Grocer" "Food"
  Expenses:Food  10.00 USD
  Assets:Cash

2024-01-06 * "No payee"
  Expenses:Food  5.00 USD
  Assets:Cash
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.

```sh
bea -f main.bean query "SELECT account, count(*) WHERE date > (SELECT min(date) FROM #entries) GROUP BY account"
bea -f main.bean query "SELECT date, (SELECT max(date) FROM #prices) AS d"
```

Actual: the first exits 1: `Error: AttributeError: 'EvalQuery' object has
no attribute 'dtype' Pass --debug before the command for a traceback.`

Control: the second exits 2: `BQL cannot use a subquery in the SELECT
list. Filter with it instead: SELECT ... WHERE column IN (SELECT ...)`.
A worker confirmed `WHERE date IN (SELECT min(date) FROM #entries)` exits
0.

Expected: exit 2 `usage` with the same guidance; `docs/USAGE.md` reserves
exit 1 for a ledger that fails validation.

Cause: `cli/src/bea_engine/query.py:1020-1029` recognises only the
`childnodes` message of the SELECT-list case; the comparison case raises
on `.dtype`.

Fix: also match the `EvalQuery` message and raise the same usage error.
No dependency or API change.

Blast radius: any comparison or arithmetic against a subquery, in WHERE
or HAVING.

Dedupe: w3/360 (done) fixed only the SELECT-list variant; w5/103 is the
regex case on the same generic path.

Acceptance: the first command exits 2 with the subquery guidance; the
`IN (SELECT …)` form still runs. Only macOS and the checkout were
exercised.
