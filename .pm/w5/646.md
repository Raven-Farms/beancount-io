# Pressing TAB after two different global `-f` values (or a repeated command option) prints an 11 MB traceback instead of completions (regression from w5/485)

**Minor · cli · 10m · A1.** Real CLI QA, 2026-10-16, HEAD `604894f6`, checkout `bea 0.3.1`, macOS 26.5.1. Follow-up to w5/485 (done).
The w5/485 fix gave the root group the single-value parser. That parser
raises `UsageError` on conflicting values even under Click's
`resilient_parsing`, which shell completion relies on. In completion mode
bea sets the terminal width to 100,000 columns, so the Rich traceback box is
111 lines of 100,000 characters. Command options repeated with different
values (`--date a --date b`) already crashed completion the same way through
the w5/238/311/381 parser. No product fix implemented.

Any two ledgers `main.bean` and `other.bean` in the working directory. This is
what the generated zsh completion runs on TAB:

```sh
_TYPER_COMPLETE_ARGS="bea -f main.bean -f other.bean ad" _BEA_COMPLETE=complete_zsh bea
_TYPER_COMPLETE_ARGS="bea -f main.bean add transaction --date 2026-01-01 --date 2026-01-02 --pa" _BEA_COMPLETE=complete_zsh bea
```

Actual: exit 1, nothing on stdout, and 11.3 MB on stderr: `Error: Conflicting
values for one option: -f 'main.bean' and -f 'other.bean'. Pass it once.`
followed by the traceback box (`NoSuchOption … UsageError … Exit: 2`).

Before the w5/485 fix: the first call exits 0 and offers `add`.

Control: `bea -f main.bean ad<TAB>` completes `add`.

Expected: completion never raises; it offers candidates (or none) silently.

Cause: `_SingleValueParser._get_value_from_state`
(`cli/src/cli/single_value.py:30-41`) raises regardless of
`ctx.resilient_parsing`; `_GuardedGroup.make_parser` (`cli/src/cli/main.py`)
now returns it.

Fix: skip the conflict check when `self.ctx.resilient_parsing` is set.

Dedupe: searched `resilient`, completion with `conflicting`; w5/485 (done) is
the parent.

Acceptance: both completion calls exit 0 and print no traceback. A test pins
them.
