# With more than 64 include files, `list --on-disk` and full listings re-read a source file for every entry

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
A ledger split into more than 64 include files whose entries interleave by
date (one file per account, payee or month) makes `list … --on-disk` and
large listings super-linear: the same 40,000 transactions take twice as long
in 100 files as in 50. Output is correct; only time is lost. No product fix
implemented.

Generate disposable `/absolute/books/main.bean` plus `inc/` (first argument
is the file count, second the transactions per file):

```sh
mkdir -p /absolute/books/inc && cd /absolute/books && python3 -c "
import datetime as d,sys;F,M=int(sys.argv[1]),int(sys.argv[2])
open('main.bean','w').write('option \"operating_currency\" \"USD\"\n2000-01-01 open Assets:Bank USD\n2000-01-01 open Expenses:Food USD\n'+''.join(f'include \"inc/f{i:03d}.bean\"\n' for i in range(F)))
hs=[open(f'inc/f{i:03d}.bean','w') for i in range(F)]
for t in range(M):
  for i in range(F): hs[i].write(f'{d.date(2000,1,1)+d.timedelta(days=t%9000)} * \"P{i}\" \"txn {t} {i}\"\n  Expenses:Food  {1+i%7}.25 USD\n  Assets:Bank\n\n')" 100 400
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, cwd `/absolute/books`.
Delete `.main.bean.picklecache` before each run.

```sh
bea -f /absolute/books/main.bean list transaction -l 2
bea -f /absolute/books/main.bean list transaction -l 2 --on-disk
```

Actual (two repetitions each, 40,000 transactions, exit 0 everywhere):

| layout | plain | `--on-disk` |
| --- | --- | --- |
| 100 files × 400 | 2.02 s, 2.08 s | 4.55 s, 4.54 s |
| 50 files × 800 (control) | 2.05 s, 2.09 s | 2.07 s, 2.03 s |

A worker measured the growth: with 100 files, `--on-disk` took 0.79 / 1.64 /
4.67 / 14.08 / 44.39 s for 10k / 20k / 40k / 80k / 160k transactions (the
overhead grows with exponent ≈1.8), against 8.24 s plain at 160k;
`--json list transaction -l 10000000` took 64 s at 160k. With 60 files and
the same totals every command stayed linear. At 50k transactions the step is
sharp: 64 files 2.6–2.8 s, 65 files 9.7 s.

Expected: time proportional to the number of entries, as with 64 or fewer
files. `--on-disk` is documented as a filter, not a costlier load.

Cause: `cli/src/bea_engine/ledger/reader.py:98` caches `_source_lines` with
`@lru_cache(maxsize=64)`, and `entry_generated` asks for an entry's file
lines once per entry. Entries arrive in date order, so with more than 64
files interleaved each call evicts and re-reads a whole file. The function's
own docstring says "The engine answers one invocation per process, so a
cached read cannot outlive the file it came from." A worker's profile of
100 × 500 showed 50,001 file reads for 50,009 calls.

Fix: make the cache unbounded for the life of the process, or group entries
by filename before testing them. No dependency or API change.

Blast radius: every `list <type> --on-disk`, every listing that returns many
rows, and the `add price` conflict guard (a worker measured that one linear,
since it only reads matching pairs).

Dedupe: board search for `_source_lines`, `lru_cache`, `maxsize` and
`--on-disk` finds w1/049, w1/114, w3/394 and w5/169, all about the
correctness of the generated flag; none is about cost.

Acceptance: on the 100 × 400 fixture `list transaction -l 2 --on-disk` takes
about as long as the plain listing (within 25%), and the rows are unchanged.
A regression test counts file reads for a 70-file interleaved ledger. Only
macOS and the checkout were exercised.
