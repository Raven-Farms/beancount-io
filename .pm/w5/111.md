# `bea check --auto` on a slow-loading ledger poisons the load cache, and later commands call a broken ledger valid

**Major (false "valid", exit 0) · cli · 45–60m · A1.** Real CLI QA, 2026-10-11, HEAD `0227141a` (CLI unchanged since `97600b74`),
checkout `bea 0.3.1`, macOS.
On a ledger large enough for Beancount to write its load cache (about one
second of loading), one `bea check --auto` stores a result computed with the
auto-insert plugins. Every later command reads that cache: plain `bea check`,
`--json check`, `balance` and `list` all report the ledger valid although
it references an account that is never opened. The state lasts until a ledger
file's size or modification time changes. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2000-01-01 open Assets:Bank USD
include "big.bean"
2021-01-01 * "tail"
  Expenses:Food  1234.00 USD
  Assets:Bank
```

and generate `/absolute/books/big.bean` (60,000 transactions; nothing opens
`Expenses:Food`):

```sh
python3 -c "open('big.bean','w').writelines(f'2020-01-01 * \"t{i}\"\n  Expenses:Food  1 USD\n  Assets:Bank\n\n' for i in range(60000))"
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY.

```sh
bea -f /absolute/books/main.bean check --auto
bea -f /absolute/books/main.bean check
bea --json -f /absolute/books/main.bean check
bea --json -f /absolute/books/main.bean balance Expenses
bea -f /absolute/books/main.bean list open
touch /absolute/books/main.bean
bea --json -f /absolute/books/main.bean check
```

Actual: `check --auto` exits 0 in about 3 seconds and leaves
`.main.bean.picklecache` beside the ledger. Plain `check` then exits 0.
`--json check` exits 0 with `{"valid": true, "errors": []}`. `balance`
exits 0 with `"ledger_valid": true, "ledger_errors": []`. `list open`
shows `2020-01-01  Expenses:Food  (any)  generated`, an account no file
opens. After `touch`, `--json check` exits 1 with `60001 error(s)`
naming `Invalid reference to unknown account 'Expenses:Food'`. A worker
reproduced the sequence twice from pristine, and found that running plain
`check` first makes a following `check --auto` exit 1 from the cache
instead.

Control: the same ledger with one transaction in `big.bean` loads too fast
to be cached; `check --auto` and `--json check` both exit 1 with the
unknown-account errors (the `--auto` half of that is w5/088).

Expected: `docs/USAGE.md` Exit codes says "Exit 0 is a promise". Whether a
ledger is valid must not depend on which command last warmed a cache: after
`check --auto`, plain `check`, `--json check`, `balance` and `list`
should report the 60,001 errors exactly as they do cold.

Cause: `cli/src/cli/commands/check.py:64` forwards `--auto` to upstream
bean-check, which loads with the auto plugins enabled and writes the shared
sidecar cache. Beancount keys that cache only on the include filenames with
their sizes and times, not on the plugin set. Every engine read then trusts
it through `cli/src/bea_engine/managed_load.py:459-481` (`_load_fresh`),
whose only extra staleness test is the include-set comparison from w1/083.
The helper re-check at `check.py:69` reads the same cache. Stock
`bean-check --auto` followed by `bean-check` shows the same upstream
behaviour.

Fix: a load made with non-default loader state must neither write nor be
served from the shared cache. Simplest is to add `--no-cache` whenever
`--auto` is forwarded; in addition, or instead, have engine reads reject a
cache that was not produced by the engine's own default load (for example by
marking the engine's caches). Fix together with w5/088, which touches the
same lines. No dependency or API change.

Blast radius: every caller of `managed_load.load_file` — list, query,
report, balance, import, the `add` validators and the write boundary — so a
write validated against the poisoned cache can also be admitted.

Dedupe: board search for `--auto`, picklecache and cache poisoning finds
w5/088 (the opposite symptom on small ledgers), w1/083 (new glob members) and
w5/067 / w5/065 (cache path aliasing); none covers plugin state in the cache.

Acceptance: on the fixture, after `check --auto`, plain `check`,
`--json check`, `balance` and `list open` report the unknown-account
errors and no generated `Expenses:Food`; a valid large ledger still benefits
from the cache on ordinary reads. A regression test uses a ledger slow enough
to be cached. Only macOS and the checkout were exercised.
