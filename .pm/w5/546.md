# `bea ask` prints an answer cut off at the CLI's own 1,500-token cap (`finish_reason: "length"`) as if complete, exit 0

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-16, HEAD `0c12f2dc`, checkout `bea 0.3.1`, macOS 26.5.1. Simulation: local stub of the AI proxy.
USAGE: "Exit 0 is a promise… A command that … wrote only part of what it
promised exits nonzero and says what is missing", and each answer "carries
an explicit output cap". The cap is bea's own `MAX_OUTPUT_TOKENS = 1500`, so
hitting it is foreseeable. A figure can be cut mid-number. No product fix
implemented.

Stub reply: content `Your total spend in January was 1`, `finish_reason:
"length"`.

```sh
bea -f /abs/main.bean ask "How much did I spend in January?" --print </dev/null
```

Actual: exit 0, stdout `Your total spend in January was 1`, stderr empty. The
REPL prints `I added it and your new bal` the same way after an approved
write.

Control: `finish_reason: "stop"` with the same text is the same output (as it
should be); a truncated tool-call argument with `length` is already retried.

Expected: the answer is followed by a notice (`The answer reached the
per-answer limit and was cut off; ask a narrower question.`). In `--print`,
the notice goes to stderr with a nonzero exit (or at least the stderr
notice).

Cause: `cli/src/cli/commands/ask.py:94` and `cli/src/cli/ask/repl.py:332`
print `result.output` without checking the last response's `finish_reason`.

Fix: check it and add the notice (and exit code in `--print`).

Dedupe: searched `finish_reason`, `output cap`, `cut off`. w3/m51 t005 and
w3/m52 introduced the cap without handling it.

Acceptance: the stubbed `length` answer carries the notice and `--print` exits
nonzero. A test pins it.
