# Check funded descendants that close_tree closes with an empty parent

**Minor · cli · 45–60m · A1.** Real CLI QA, 2026-10-21, checkout
`bea 0.3.1`, HEAD `95c455516` (CLI unchanged through `5b1a4a5f4`), Darwin
25.5.0 arm64, frontend Python 3.13.3. Closing an empty parent with the
standard `close_tree` plugin also closes its funded child, bypassing the
CLI's unforced funded-close refusal. No product fix implemented.

Create `/abs/books/main.bean`:

```beancount
plugin "beancount.plugins.close_tree"
option "operating_currency" "USD"
2024-01-01 open Assets:Bank
2024-01-01 open Assets:Bank:Checking USD
2024-01-01 open Equity:Opening USD
2024-01-02 * "Fund"
  Assets:Bank:Checking 100 USD
  Equity:Opening -100 USD
```

From `/abs/books`, closed stdin/no TTY, isolated absolute `BEA_CONFIG_DIR`
and `XDG_CACHE_HOME`, `BEA_NO_UPDATE_NOTIFIER=1`, with inherited `BEA_FILE`
and `BEA_TOKEN` removed:

```sh
bea --json -f /abs/books/main.bean check
bea --json --no-input -f /abs/books/main.bean add close --date 2024-02-01 --account Assets:Bank
bea --json -f /abs/books/main.bean list close
bea --json -f /abs/books/main.bean balance Assets:Bank:Checking -t 2024-02
bea --json -f /abs/books/main.bean check
```

Actual: close exits **0**, `written: 1`, `warnings: []`, appending the parent
close. A fresh listing has both `Assets:Bank` and `Assets:Bank:Checking`
closed February 1; the child's row is `generated: true`. The child still
holds **100 USD**, the balance read reports complete valuation, and check
passes. Human close also succeeds without warning. Both modes reproduced
twice from pristine fixtures.

This later clearing transaction exits 1 for an inactive child, naming the
parent's plugin-generated close; the ledger stays byte-identical:

```sh
bea --json --no-input -f /abs/books/main.bean add transaction 'Move funds' --date 2024-02-02 -p 'Assets:Bank:Checking -100 USD' -p 'Equity:Opening 100 USD'
```

Expected: before writing, refuse this unforced close at exit 1, name the
funded child and its 100 USD, and require it to be drained on/before the
close date or explicitly force the operation. Preserve `close_tree`'s
intentional descendant generation. The existing w2/092 policy prevents a
close from stranding balances; here the proposed operation actually closes
the child, even though the requested parent itself has no postings.

Twice-fresh controls (14 fixture journeys total):

- Remove `close_tree`: the same parent close correctly succeeds, generates
  no child close, and the later child clearing transaction succeeds. Ordinary
  parent/child account independence must remain intact.
- Drain the child before closing: parent/child close succeeds and check
  passes with no balance remaining.
- Pass `--force` with the plugin: the operation deliberately closes both
  accounts with the child balance retained.
- Put the 100 USD directly in the parent instead: the existing guard
  refuses unforced close and writes nothing.
- Give the child its own explicit close before proposing the parent close:
  the plugin generates no additional child close, and the empty-parent
  operation succeeds. Do not block a new close merely because a previously
  closed descendant still holds money.
- Load `check_drained` **after** `close_tree`: its generated zero assertion
  catches the funded child, so validation refuses and preserves the file.
  This control does not excuse the unguarded no-check_drained case.

Before/after BQL in every fixture confirms that closing itself clears none
of the starting holdings. Fresh listings distinguish written and generated
closes, and all persisted ledgers pass check.

Cause: `_close` in `cli/src/bea_engine/ledger/adding.py:324–350` loads the
current ledger, checks `_held_through(entries, directive.account, date)`
only for the requested parent (:339), then calls `_appended`. It never
applies that balance policy to the additional close directives produced by
candidate validation. The installed upstream `beancount/plugins/close_tree.py`
intentionally generates closes for descendant opens without a recorded
close; native validation permits a nonempty account to close. The plugin is
working as designed. Frontend `add close` sends this one close request;
the missing check belongs in its engine-side handling of actual effects.

Fix: enforce the existing balance/force decision for the accounts newly
closed by this proposal, including generated descendants. Use the candidate's
actual close effects, preserving plugin order, date, snapshot validation,
no-plugin parent semantics and already-closed controls; do not blindly block
every funded account sharing a prefix or change upstream plugin semantics.
No dependency or new feature is needed.

Dedupe: whole-board `close_tree`/funded-child/closing-guard searches and
current milestone review found no open coverage. Completed w2/092 is the
parent; its child-account control covers ordinary closes without this plugin.
Completed [222](./done/222.md) supplies the correct generated-close recovery
hint seen after the failure. Open [888](./888.md) concerns trusting
`check_drained` over an explicit nonzero assertion, and [909](./909.md)
concerns losing lot costs inside the requested account's balance check.
Neither covers an additional funded account closed by the proposal.
Hosted funded-close parity is separately tracked by blocked w2/095; no
hosted behavior was exercised here.

Acceptance: refuse the funded-child unforced close without writing, name the
affected child/balance, and preserve every control above. Pin real CLI
regression coverage with a fresh generated-close listing and subsequent
child posting. Evidence is under ignored
`.tmp/qa-2026-10-20-cli-loop-pass8-80df309f/`:
`repro_close_tree_funded_descendant.py`, `close-tree-funded-results.json`
and `captures/close-tree-*.json`.
