# A malformed HTTP reply from a price feed crashes every command, even when a good cached revision exists

**Major · cli · 30m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
When a managed price feed answers with something that is not HTTP (a
captive portal, a broken proxy, the wrong service on the port), every
command that loads the ledger exits 1 with a raw `BadStatusLine` — reads,
`check`, and writes with `--allow-errors` alike — although a good cached
revision is on disk. No failure is recorded, so each later command
refetches and crashes again. A well-formed HTTP 500 degrades correctly.
No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Coin BTC
2024-01-01 open Equity:Opening
2024-01-01 commodity BTC
2024-01-01 commodity USD

2024-01-02 * "Open"
  Assets:Cash  10000.00 USD
  Equity:Opening

2024-01-03 * "Buy"
  Assets:Coin  2 BTC {1000.00 USD}
  Assets:Cash  -2000.00 USD
```

followed by `include "http://127.0.0.1:PORT/prices/SW1"`.

The feed is a **simulation**: a loopback server on `127.0.0.1` allowed
through `MANAGED_PRICE_ORIGINS`, which proves local handling only, not the
real service's behaviour. Use isolated BEA_CONFIG_DIR and a fresh
XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no inherited BEA_FILE/BEA_TOKEN,
closed stdin, no TTY, cwd `/absolute/books`. The simulated feed first replies `HTTP/1.0 200 OK` with body
`2024-01-05 price BTC 1100.00 USD`, and afterwards replies with the raw
bytes `SSH-2.0-OpenSSH_9.0\r\n`.

```sh
bea -f main.bean check              # good reply: caches a revision
# switch the simulation to the junk reply
bea -f main.bean price refresh
bea -f main.bean check
bea -f main.bean add note -a Assets:Cash --date 2024-02-01 -m n --allow-errors
```

Actual: the first exits 0. The other three each exit 1:

```text
Error: BadStatusLine: SSH-2.0-OpenSSH_9.0
 Pass --debug before the command for a traceback.
```

The ledger is unchanged.

Control (worker observation, simulation): the same sequence with a
well-formed `HTTP 500` gives `price refresh` exit 1 with "fetch failed
(provider): HTTP 500 …; serving revision …", `check` exit 0 and the write
exit 0, and records a retry delay. The worker saw the crash also for a
reply with no status line, an over-long header line and more than 100
headers, and `--json` classify it as `validation`; only `--offline` kept
working.

Expected: `docs/USAGE.md` — "A failed refresh never replaces the last
good revision", and a failed refresh is reported per source while "a
cached revision can still serve". A feed problem should degrade to the
cached prices, not block reads and writes.

Cause: `cli/src/bea_engine/managed_prices.py:285-324` catches
`HTTPError`, `URLError` and `OSError` only; `http.client.HTTPException`
subclasses raised while reading the response are none of those and
escape before any failure state is written.

Fix: catch `http.client.HTTPException` in the fetch and return the
existing "network" failure ("the price service sent a malformed HTTP
response"), so the degraded path serves the cache and records the retry
window. No dependency or API change.

Blast radius: every command that loads a ledger with a managed include.
Whether TLS shields the default origin from this was not verified.

Dedupe: board search for BadStatusLine, HTTPException and malformed HTTP
finds nothing; nearest are w1/077 (truncated download) and w1/079 (raw
errno on the cache).

Acceptance: with the junk reply, `price refresh` exits 1 naming the
source and the served revision, and `check` and the write exit 0 from the
cache; no Python exception name appears. Only macOS, the checkout and a
loopback simulation were exercised.
