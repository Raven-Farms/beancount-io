# Every `bea` ledger write (`add`, `import --apply`, `format -i`) silently splits a hard link to the file: the written name gets a new inode and the other name keeps the old bytes

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
Writes go through a validated staged copy and then `os.replace`, so the
written name always gets a new inode. [w1/099](../w1/done/099.md) made
the write carry over mode, group, ACLs, xattrs and flags, because "a
rename installs a new inode" loses them. Other hard links to the same
file cannot be carried over that way.

A user who keeps the ledger hard-linked into a synced or backup folder
sees the two names silently diverge after the first `bea` write. Every
command exits 0 and says nothing. No product fix implemented.

Create disposable `/absolute/h/main.bean` that opens `Assets:Cash USD`
and `Expenses:Food USD`, then run `ln main.bean twin.bean`. Use isolated
BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no inherited
BEA_FILE/BEA_TOKEN, and closed stdin.

```sh
stat -f '%i %l' main.bean twin.bean      # same inode, 2 links
bea -f /absolute/h/main.bean add transaction X --date 2026-01-05 -p 'Expenses:Food 1 USD' -p Assets:Cash
stat -f '%i %l' main.bean twin.bean
cmp main.bean twin.bean
```

Actual:

- Exit 0 with `Added 1 transaction`.
- Afterwards `main.bean` has a new inode, both names have a link count
  of 1, and `cmp` reports that they differ. `twin.bean` still holds the
  old ledger.
- `format -i` on a misaligned linked file and `import --apply` behave the
  same way.

The hunter reproduced the `add` case twice and the other two once each.
I reproduced the `add` case.

Control: a symlinked target or include stays a symlink, and the write
lands in the real file. Mode 640 and a custom xattr survive (w1/099).

Expected: w1/099 established that a ledger write must not silently drop
properties of the file it replaces. A hard link is another such
property, and silent divergence is a data-integrity surprise. When
`st_nlink > 1`, bea should either write the validated bytes back into the
existing inode under its lock (with fsync), or refuse with exit 3,
naming the extra link. The chosen behaviour should be documented in
USAGE next to the write-safety text.

Cause: `replace_checked` (`cli/src/bea_engine/ledger/write.py:2011-2027`)
ends in `os.replace(candidate, file)`. `keep_file_metadata`
(`write.py:1922-…`) cannot preserve other links. `format -i` uses the
same staged replace (`cli/src/bea_engine/ledger/formatting.py`).

Fix: check the original stat's `st_nlink`. If it is above 1, either copy
the validated contents into the original file in place, or refuse with a
clear message. Cover `add`, bulk add, `import --apply` and `format -i`.
No dependency change.

Blast radius: every ledger write to a file with more than one hard link.

Dedupe: searched `.pm/**`, including `done/`, for "hard link",
hardlink, `nlink` and inode. Related notes:

- w1/099: metadata, with no mention of links.
- w3/300, w3/400, w3/431, w5/058, w5/065, w5/068 and w3/m48/t001: hard
  links only as output destinations that alias the ledger.
- w5/300: the SIGKILL orphan write.

None covers a ledger write splitting a link.

Acceptance: on the fixture, after `add`, `format -i` and `import
--apply`, both names show the new content and the link count stays 2, or
the write is refused with exit 3, naming the link, and nothing changes.
A real-command test pins the chosen behaviour.
