# Ignore metadata insertion order when deduplicating imported nontransaction directives

**Minor · cli · 25–40m · A1.** Real CLI QA, 2026-10-21, checkout
`bea 0.3.1`, HEAD `0f3516410` (CLI unchanged from reproduction at
`3fb568c16`), macOS 26.5.1 arm64, frontend Python 3.13.3, managed engine
Python 3.12 / Beancount 3.2.3. Reordering two metadata keys without changing
their values makes an already-imported note import again. For an account
opening, commodity declaration or close, the same reorder makes the repeat
invalid and blocks the import. No product fix implemented.

Create disposable `/abs/case/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
```

`/abs/case/statement.json`:

```json
{"provider":"Example Bank","reference":"Jan-2024"}
```

`/abs/case/importers.py`:

```python
import datetime
import json
from pathlib import Path
from beancount.core import data

class Statement:
    name = "metadata-order"
    def identify(self, path): return path.endswith(".json")
    def account(self, path): return "Assets:Cash"
    def extract(self, path, existing):
        meta = data.new_metadata(path, 1)
        meta.update(json.loads(Path(path).read_text()))
        return [data.Note(meta, datetime.date(2024, 2, 1),
                          "Assets:Cash", "Monthly statement",
                          frozenset(), frozenset())]

CONFIG = [Statement()]
```

Cwd `/abs/case`, isolated absolute `BEA_CONFIG_DIR` and `XDG_CACHE_HOME`,
`BEA_NO_UPDATE_NOTIFIER=1`, inherited `BEA_FILE` and `BEA_TOKEN` removed,
closed stdin, no TTY:

```sh
bea --json --no-input -f /abs/case/main.bean import /abs/case/statement.json --config /abs/case/importers.py --apply
```

First apply exits 0, `written: 1`. An unchanged repeat exits 0,
`written: 0`, `duplicates: 1`. Replace only the JSON key order:

```json
{"reference":"Jan-2024","provider":"Example Bank"}
```

Run the same import without `--apply`, then with it. Preview leaves the
ledger unchanged but reports `new`, `ready: 1`, `duplicates: 0`. Apply exits
0, `written: 1`. Fresh `list note` has two semantically identical notes,
including equal metadata mappings; only the order and source line differ.
Fresh `check` exits 0. The two written blocks are:

```beancount
2024-02-01 note Assets:Cash "Monthly statement"
  provider: "Example Bank"
  reference: "Jan-2024"

2024-02-01 note Assets:Cash "Monthly statement"
  reference: "Jan-2024"
  provider: "Example Bank"
```

Reproduced twice from pristine fixtures, reversing which key order came
first, across eight directive kinds. Notes, events, balances, stored queries
and documents are appended again. An otherwise identical `open`,
`commodity` or `close` previews as `invalid`; apply exits 1 and preserves the
ledger. For example, returning `data.Open(meta, day, "Assets:Other",
["USD"], None)` reports `Duplicate open directive for Assets:Other` after
the key reorder. The account was already imported successfully, so an
otherwise valid later statement can be held back by its repeated opening.

Two same-batch notes with reversed key order also write twice; with the same
key order they write once. Human note/open preview and apply reproduce the
same outcomes twice. All final ledgers pass a fresh check.

Expected: `cli/docs/IMPORTING.md` promises identical nontransaction
directives are skipped. Metadata is a key/value mapping; changing its
insertion order does not change the directive. Preserve the existing
precision-sensitive treatment of balance amounts and tolerances.

Cause: `cli/src/bea_engine/importing.py:465` builds `other_entries` from
`_directive_text`; `:649,692–695` compares the new printed text with that
set. `_directive_text` (`:1504–1514`) NFC-normalizes the printable directive
and removes computed balance differences, but leaves metadata insertion
order significant. The installed upstream `EntryPrinter.write_metadata`
deliberately iterates `meta.items()` in insertion order to preserve the
presentation. That is appropriate for writing; using those bytes as the
identity creates this failure. Caller search also finds the preliminary
printability check at `:1101`.

Fix: make metadata key order irrelevant in the **comparison key** for
nontransaction directives, against both written entries and earlier accepted
rows of the batch. Keep the original metadata order in appended text and the
preview. Do not ignore metadata values or types, other directive fields,
balance precision or tolerance. Keep the NFC/computed-difference handling
from [224](./done/224.md), and existing plugin-generated-entry exclusions.
No dependency or API change is needed.

Working controls, each repeated twice: unchanged key order deduplicates;
changed metadata value or numeric-versus-string type remains new; balance
`0.00` versus `0.000`, or explicit tolerance `0.01` versus `0.1`, remains
distinct. Price value matching and transaction bank-ID matching already
ignore metadata order and write once.

Dedupe: searched every `.pm` state for metadata order/sorting/insertion,
nontransaction duplicates and `_directive_text`, checked active milestone
scopes, callers and targeted history. Completed 224 (`7d2490c05`) handled
NFC and computed balance differences, not mapping order. Completed
[302](./done/302.md) replaced price text matching and explicitly retained
precision-sensitive matching for other kinds. Neither covers this case;
no overlapping open item found.

Acceptance: after importing either metadata order, the other order previews
as one duplicate and applies with `written: 0`, byte-identical ledger and a
fresh check passing. This holds for annotations and the repeated opening;
same-batch reordered metadata writes once. Retain the changed-value/type,
balance precision/tolerance, price and transaction controls above.
