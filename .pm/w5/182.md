# A writer behind a held lock waits forever with no message

**Minor · cli · 30–45m · A1.** Real CLI QA, 2026-10-11, HEAD `a8b75aed` (CLI unchanged since `97600b74`), checkout `bea 0.3.1`, macOS.
When another process holds the write lock for a ledger, `bea add …`
blocks with nothing on stdout or stderr and no time limit — also under
`--json` with no terminal. If the holder is stuck (a hung plugin, a
stalled filesystem), every later writer hangs silently behind it. No
product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
option "operating_currency" "USD"
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

Use isolated BEA_CONFIG_DIR and `XDG_CACHE_HOME=/absolute/books/cache`,
BEA_NO_UPDATE_NOTIFIER=1, no inherited BEA_FILE/BEA_TOKEN/CI, closed
stdin.

1. Run one `bea -f main.bean add transaction t --date 2024-02-01 -p
   "Expenses:Food 1.00 USD" -p Assets:Cash` so the lock file exists
   under `cache/bea/locks/`.
2. From another process, hold `fcntl.flock(LOCK_EX)` on that lock file.
3. Run `bea --json -f main.bean add transaction t --date 2024-02-01 -p
   "Expenses:Food 1.00 USD" -p Assets:Cash`.

Actual: after 15 seconds the command is still running with empty stdout
and stderr. It completes with exit 0 only when the lock is released.

Control: a worker ran `bea check` and a write to an unrelated ledger
while the lock was held; both completed normally. The worker also saw
the same silent wait behind a real `bea` holder (a plugin that sleeps
during validation) for 60 seconds, `format -i` wait the same way, and
Ctrl-C end the waiter cleanly.

Expected: a bounded wait or at least a notice. `docs/USAGE.md` says of
`--json` and non-terminal runs "In that mode nothing waits for a human",
and describes a concurrent writer only as one that "waits"; no timeout
or message is documented.

Cause: `cli/src/bea_engine/ledger/write.py:339` calls blocking
`fcntl.flock(…, LOCK_EX)` with no non-blocking attempt, deadline or
progress message; `format -i` uses the same helper.

Fix: poll with a non-blocking lock, print "waiting for another bea write
on FILE…" to stderr after about a second, and exit 4 with a "locked, try
again" message after a documented timeout. No dependency change.

Blast radius: every writer. A killed holder is not a trigger — the
kernel drops its lock.

Dedupe: board search for lock wait, timeout, forever and indefinitely
finds no item.

Acceptance: the blocked command prints a waiting notice on stderr within
a few seconds and exits with a documented code after the timeout, with
the ledger unchanged; an uncontended write is unaffected. Only macOS and
the checkout were exercised.
