# A `PRINT` query that matches no directives exits 2 and tells the user to "use PRINT"

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, macOS.
A filtered `PRINT` over a window with no entries — a per-year export of a
year that has no activity yet — is refused as a usage error whose remedy is the
statement the user already typed. The JSON form of the same query succeeds
with zero rows, so the two modes disagree on the exit code. No product fix
implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Assets:Broker HOOL "FIFO"
2024-01-01 open Expenses:Food
2024-01-04 custom "budget" Expenses:Food "monthly" 400.00 USD TRUE 2024-01-01 -3.5
2024-01-05 * "Grocer" "Refund (partial)" #food #trip #reimbursable
  Expenses:Food  -5.00 USD
  Assets:Cash
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY. The fixture passes
`bea check`.

```sh
bea -f /absolute/books/main.bean query "PRINT FROM year = 2025"
bea -f /absolute/books/main.bean query "PRINT FROM year = 2025" -o /absolute/books/y2025.bean
bea --json -f /absolute/books/main.bean query "PRINT FROM year = 2025"
```

Actual: the first two exit 2 with `Error: --format beancount prints
directives, so the query must return entries; use PRINT, or --format text or
csv for a column result.` and no file is created. The `--json` run exits 0
with `"rows": []`. Repeated twice.

Controls: `query "SELECT date FROM year = 2025"` exits 0 with `(no rows)`
on stderr. A worker confirmed `PRINT FROM year = 2024 -o y2024.bean` exits 0
and writes the entries, and that stock `bean-query` exits 0 on the empty
`PRINT`.

Expected: `docs/USAGE.md` says "An empty result prints `(no rows)` on
stderr." An empty `PRINT` is an empty result: exit 0, `(no rows)` on
stderr, and with `-o` an empty export, in step with the JSON mode. A script
that archives each year with `PRINT … -o` should not fail on a quiet year.

Cause: `cli/src/bea_engine/query.py:792-793` (`_require_entries`, called
at `:715`). With zero rows the check falls back to the column's declared
type; `PRINT`'s single column `ROW(*)` is typed `object`, not a
directive, so the statement is taken for a column `SELECT` under
`--format beancount`. The guard arrived with w1/m23/t005 for w3/269.

Fix: let a statement that is a `PRINT` pass `_require_entries` when it
returns no rows; keep an empty column `SELECT` under `-f beancount` at
exit 2. Decide whether an empty `-o` export creates a zero-byte file or
leaves none, and document it. No dependency or API change.

Blast radius: every filtered `PRINT` in one-shots and stored `.run`
queries that reach the same path.

Dedupe: board search for the error text, `ROW(*)` and empty `PRINT` finds
w3/269 (the opposite case: an empty column `SELECT` wrongly succeeding),
w2/021 and w1/m23/t005 (the guard), and w5/085 (`PRINT` with a pad); none
covers an empty `PRINT`.

Acceptance: the first two commands exit 0 with `(no rows)`, matching the
JSON run; a non-empty `PRINT` and an empty column `SELECT -f beancount`
behave as today. Real-command regression tests cover text, `-o` and JSON.
Only macOS and the checkout were exercised.
