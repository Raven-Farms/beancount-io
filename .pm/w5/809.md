# Fava-option edges: `fiscal-year-end "00-31"` is accepted and makes `FY2026` calendar 2025 (`"99-31"` puts it in 2033–34), and USAGE never says that bea ignores every Fava option except `fiscal-year-end`

**Trivial · cli docs · 10m · A1.** Real CLI QA, 2026-10-17, HEAD `f28d154ff`, checkout `bea 0.3.1`, macOS 26.5.1.
No product fix implemented.

1. **Month 00.** With `custom "fava-option" "fiscal-year-end" "00-31"`, `report
   income-statement -t FY2026` exits 0 with `Income Statement — 2025-01-01
   through 2025-12-31`. With `"99-31"`, it reports 2033-04-01 through
   2034-03-31 (hunter's run). USAGE:1538-1540 says a value that "is not a real
   month and day" refuses fiscal periods. Upstream Fava documents months 13–24
   (a year end in the following year). Cause: the vendored `parse_fye_string`
   (`cli/src/fava/util/date.py`, around `:495-504`) checks only
   `(month-1)%12+1`.
2. **Ignored options undocumented.** bea honors only `fiscal-year-end`. In the
   hunter's 15-option fixture, `default-file`, `insert-entry`, `import-config`,
   `indent`, `currency-column`, `invert-income-liabilities-equity`, `locale` and
   the rest changed no output. `fava-extension` lines are never loaded, and
   `check` does not report invalid values. These behaviors match bea's
   documented rules (`--into`, bean-format alignment, Beancount signs), but
   USAGE mentions only `fiscal-year-end`, so a Fava user cannot tell that the
   rest are ignored.

Fix: in `report.py` (leaving vendored Fava unchanged), refuse a parsed month
outside 1–24 and document the 13–24 meaning. Add one USAGE sentence: bea
honors only `fiscal-year-end`, ignores other `fava-option` values and
`fava-extension`, and `check` does not validate them.

Dedupe: w5/091 and 147 (done) cover other Fava-option issues.

Acceptance: `"00-31"` is refused for fiscal periods, and USAGE has the
sentence.
