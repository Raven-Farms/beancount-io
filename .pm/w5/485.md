# A repeated global `-f`/`--file` with two different ledgers silently uses the last one, so `bea -f main.bean -f other.bean add …` writes to `other.bean` with exit 0

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-16, HEAD `7334a32b`, checkout `bea 0.3.1`, macOS 26.5.1. Gap in the w5/238, 311 and 381 rule.
USAGE's rule is that an option holding one value "refuses two different ones
… with exit 2 naming both and nothing written, instead of keeping the last".
That rule now covers every command's own options, but not the global ones.
`--file` decides which ledger a write lands in. An agent that builds the
argument list from a default plus an override writes to whichever came
last. No product fix implemented.

Two copies of any valid ledger, `main.bean` and `other.bean`, with
`Expenses:Food` and `Assets:Cash` open. Isolated config/cache, closed stdin.

```sh
bea --json -f main.bean -f other.bean add transaction X --date 2026-01-05 -p 'Expenses:Food 1 USD' -p 'Assets:Cash'
```

Actual: exit 0. `target.file` is `…/other.bean`; `other.bean` gains the entry
and `main.bean` is unchanged. `check`, `list` and the other reads also use the
last value.

Control: `… add transaction X --date 2026-01-05 --date 2026-01-06 …` exits 2
with `Conflicting values for one option`.

Expected: exit 2 naming both `--file` values, nothing written. The same
applies to the other single-value globals (`--shell`). The same value
repeated stays accepted.

Cause: the root callback (`cli/src/cli/main.py:355`) belongs to
`_GuardedGroup`, which does not use `SingleValueCommand`'s parser
(`cli/src/cli/single_value.py`), so Click keeps the last value.

Fix: apply the same-value-or-refuse check to the group's scalar options,
reusing `SingleValueCommand`'s logic.

Dedupe: searched `Conflicting values`, `global option`. w5/238, 311 and 381
(done) cover command options; w5/243 and 416 are about global placement.
New.

Acceptance: the command above exits 2 and writes nothing; `-f main.bean -f
main.bean` still works. A test pins both.
