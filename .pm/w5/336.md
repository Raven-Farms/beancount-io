# JSON nested between about 1,000 and a few thousand levels crashes bulk add with `RecursionError` (exit 1, "validation"): the w5/185 surrogate scan runs before the w1/112 depth guard can catch it

**Minor · cli · 10–15m · A1.** Real CLI QA, 2026-10-14, HEAD `bce2c992`, checkout `bea 0.3.1`, macOS 26.5.1, engine Python 3.12.
[w1/112](../w1/done/112.md) made absurdly deep `--from` JSON a usage
error. Its fixture nested 100,000 levels, which still fails in the
frontend's `json.loads` and is refused correctly. Shallower nesting gets
past the frontend parser and then overflows the engine's recursive
unpaired-surrogate scan, added for [w5/185](./done/185.md). The command
fails with a Python class name, exit 1 and category `validation`, whether
the input comes from a file or from stdin. No product fix implemented.

Use any valid ledger, with the environment from [335](./335.md).

```sh
python3 -c 'print("["*2000+"]"*2000)' > deep.json
bea -f /absolute/books/main.bean add transactions --from deep.json
python3 -c 'print("["*2000+"]"*2000)' | bea --json -f /absolute/books/main.bean add transactions --from -
```

Actual: both runs exit 1 with `Error: RecursionError: maximum recursion
depth exceeded Pass --debug before the command for a traceback.` In JSON
the category is `validation`. Depths of 1,000 and 3,000 behave the same
way, as does a row whose `meta` nests 3,000 objects. `--debug` shows the
recursion in `_surrogate_problems` (`cli/src/bea_engine/ledger/adding.py:1174`).
The ledger is unchanged. Reproduced in three fresh runs.

Control: at depth 900, the row is rejected normally. At depth 100,000, the
command exits 2 with `… nests JSON too deeply; send a flat array of rows.`

Expected: `docs/USAGE.md` says "absurdly deep nesting … is a usage error
(exit **2**) naming the problem". That should hold at every depth.

Cause: the frontend guard (`cli/src/cli/commands/add.py:565-566`) catches
`RecursionError` only from its own `json.loads`. The C decoder accepts
deeper input than the engine's recursive Python walk
(`adding.py:1150-1176`, from `4d4c7042`) can traverse.

Fix: make `_surrogate_problems` iterative with an explicit stack, or cap
its depth and reject the row. Optionally, check the depth in the frontend
after parsing and refuse anything beyond a sane limit using the existing
exit-2 message. No dependency change.

Blast radius: `add transactions` with `--from FILE` or `--from -`, in text
and JSON. In practice this comes from a buggy generator or from
adversarial input.

Dedupe: searched `.pm/**`, including `done/`, for `RecursionError`, "too
deeply" and "nesting". w1/112 added the guard and tested it only at
100,000. w5/209 is a different path, and w5/185 introduced the walk. None
of them covers this depth band.

Acceptance: depths of 1,000, 3,000 and 100,000 each exit 2 with a nesting
message and no `RecursionError` text. Depth 900 still gets the row
rejection. A regression test covers a file and stdin. Only macOS and the
checkout were exercised.
