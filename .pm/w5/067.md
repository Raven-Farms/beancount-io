# Read-only commands delete ledger files when the Beancount cache variable aliases them

**Major (data loss, narrow trigger) · cli · 45–60m · A1.** Real CLI QA,
2026-10-10, HEAD `97600b74`, checkout `bea 0.3.1`, engine Python 3.12,
macOS. `BEANCOUNT_LOAD_CACHE_FILENAME` is upstream Beancount's documented way to
relocate the loader's pickle cache. When its value resolves to the root ledger
or an included file, `bea list`, `query`, `balance`, `report`, `price status`
and `doctor print-options` delete that file while "reading" it. w5/065 closed
the same hazard for `bea check` only and recorded this wider exposure as
needing its own item. No product fix implemented.

Create disposable `/absolute/books/main.bean`:

```beancount
2026-01-01 open Assets:Cash USD
include "sub/apr.bean"
```

and `/absolute/books/sub/apr.bean`:

```beancount
2026-04-02 note Assets:Cash "cache safety"
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN, closed stdin, no TTY, and a foreign cwd:

```sh
BEANCOUNT_LOAD_CACHE_FILENAME='{filename}' bea --file /absolute/books/main.bean list open
```

Actual: exit 1, empty stdout, stderr

```text
ERROR:root:Cache file is corrupted: could not find MARK; recomputing.
Error: Ledger has 1 error(s). Pass --allow-errors to report anyway.
  <load>:0: File "/absolute/books/main.bean" does not exist
```

and `main.bean` is gone. Each of these, on a fresh copy of the fixture with the
same variable, also removed the root: `query "SELECT 1"`, `balance`,
`report trial-balance`, `price status` (which still exits 0 and prints
`No managed price includes in this ledger.`), and `doctor print-options
/absolute/books/main.bean`. With the variable set to
`/absolute/books/sub/apr.bean`, or to the relative `sub/apr.bean`,
`list open` deletes the include instead and reports
`File glob "sub/apr.bean" does not match any files`. Every case was repeated
from a pristine copy with existence checks before and after. No real ledger
was used.

Adjacent state: `add note` under the same variable leaves the ledger
byte-identical (hash checked) but fails with exit 1 and the misleading
`<load>:0: File "/absolute/books/main.bean" does not exist` — the staged
candidate deleted itself — so a valid write is refused with a wrong reason.

Controls: the same variable pointing at an unrelated `other.cache` beside the
root leaves both files intact and `list open` exits 0. `bea check` with
`{filename}` exits 2 before anything runs, naming the variable and the ledger
file (the w5/065 guard). `bea format` does not load through the Beancount
loader and is unaffected.

Expected: a read command never removes a ledger file. `docs/USAGE.md` Output
destinations states the rule for `check` — "a cache path that is the ledger or
one of its includes is refused before bean-check runs" — and the hazard is the
same on every command that loads the ledger. Refuse with exit 2 naming the
variable, its value and the colliding ledger file, before the loader starts,
leaving every file and link intact; a cache path outside the include closure
keeps working.

Cause: the guard lives only in the frontend's check handler,
`cli/src/cli/commands/check.py:77-112` (`_refuse_cache_over_ledger`). Every
other local command reaches upstream through the engine helper, which inherits
the environment (`cli/src/cli/engine/launch.py:524`) and calls
`beancount.loader.load_file` at `cli/src/bea_engine/managed_load.py:474`
(and `:362`, `:480` for staged candidates). Upstream's
`pickle_cache_function` unpickles the cache path, removes it when that fails,
and only then parses — so a cache path equal to a ledger file deletes it
first. `doctor` forwards to `bean-doctor`, which initializes the same loader.

Fix: apply one identity-based check at the engine's loading boundary rather
than per command — resolve the effective cache path the way
`beancount.loader.get_cache_filename` does (the existing helper at
`cli/src/bea_engine/ledger/write.py:243` already does this for staged
candidates) and refuse when it is the root or any member of the include
closure, by file identity so symlinks and hard links are covered. Cover the
native `doctor` path the same way the check guard does. Keep ordinary cache
relocation working; do not change cache serialization or fork upstream.
Staged write candidates need the same resolution so `add`/`import` report the
collision instead of a missing-file error. Extend `docs/USAGE.md` Output
destinations to say the rule covers the environment variable on every local
command. No dependency or API change.

Dedupe: full-board search for `BEANCOUNT_LOAD_CACHE_FILENAME`, cache deletion
and cache-filename finds w5/065 (check only; its resolution names this gap as
not covered and unfiled) and w3/390 (stale staged-write cache name, a different
defect). `git log -S BEANCOUNT_LOAD_CACHE_FILENAME -- cli` shows only those
two fixes and w1/083's cache-miss reload; none adds a guard outside check.

Acceptance: with the variable resolving to the root or an include — absolute,
relative, `{filename}` pattern, symlink or hard-link alias — `list`, `query`,
`balance`, `report`, `price status`, `doctor`, `add` and `import` exit 2 naming
the variable and file, and every directory entry and its bytes are unchanged; a
separate cache path still succeeds. Regression tests run the real commands from
a foreign working directory and fail, by deleting the fixture, with the guard
removed. Only macOS and the checkout engine were exercised; Homebrew-installed
engines and other platforms are unverified.
