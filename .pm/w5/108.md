# A carriage return in ledger text reaches the terminal raw in query tables and overwrites the row

**Minor · cli · 15–20m · A1.** Real CLI QA, 2026-10-11, HEAD `0227141a` (CLI unchanged since `97600b74`),
checkout `bea 0.3.1`, macOS, driven through a real pseudo-terminal.
Query text tables escape control characters so ledger text cannot drive the
terminal, but a lone carriage return is let through as a "line break". On a
terminal it moves the cursor to column 0, so the rest of the cell is drawn
over the row's date and payee. No product fix implemented.

Create disposable `/absolute/books/main.bean` (printable ASCII only;
`\r` is Beancount's own string escape). `bea check` exits 0:

```beancount
option "operating_currency" "USD"
2026-01-01 open Assets:Checking USD
2026-01-01 open Expenses:Food USD
2026-01-06 * "Mallory" "x\r2026-01-06  Landlord  Rent          1.00 USD"
  Expenses:Food  950.00 USD
  Assets:Checking
```

Use isolated BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1, no
inherited BEA_FILE/BEA_TOKEN/CI, `TERM=dumb`, and stdin, stdout and stderr all
attached to a pseudo-terminal.

```sh
bea -f /absolute/books/main.bean query "SELECT date, payee, narration, position WHERE account ~ 'Food'"
```

Actual: exit 0. The PTY stream holds `2026-01-06  Mallory  x` then the raw
byte 0x0d then `2026-01-06  Landlord  Rent          1.00 USD   950.00 USD`.
A terminal therefore shows a row that reads
`2026-01-06  Landlord  Rent          1.00 USD   950.00 USD`, with the real
payee overwritten. Repeated twice; a worker saw the same inside the
interactive shell.

Control: `bea -f /absolute/books/main.bean list transaction` on the same
terminal shows the narration as `x 2026-01-06  Landlord …`, the return
flattened to a space. A worker confirmed ESC, BEL and TAB in the same query
table are shown as `\x1b`, `\x07`, `\x09`.

Expected: `docs/USAGE.md` says "Every other control character … is replaced
by a visible `\xNN` … so text from an untrusted source … cannot drive your
terminal … a cursor-movement sequence could otherwise redraw over the rows
above it." A bare carriage return is cursor movement and should be shown as
`\x0d` or flattened as `list` does.

Cause: `cli/src/bea_engine/query.py:758-774` (`_inert_cell`) escapes the
set in `cli/src/bea_engine/ledger/text.py:19` (`CONTROL_CHARACTERS`),
which leaves out 0x0a and 0x0d so that line breaks survive.

Fix: in text-format query cells, render `\r` as `\x0d` (or flatten CR
and CRLF the way `list` cells do). JSON, CSV and Beancount output keep the
exact value. No dependency or API change.

Blast radius: text rendering for one-shot queries, the shell and `.run`.
Whether the `ask` BQL tool shares the renderer was not checked.

Dedupe: board search for carriage return and `_inert_cell` finds w4/173
(the other control characters, done), which states line breaks are unchanged;
a carriage return as overwrite is not covered.

Acceptance: on the fixture the PTY stream contains no 0x0d inside a table
row and the row shows `Mallory`; JSON and CSV output still carry the exact
narration. A regression test asserts the bytes of the text table. Only macOS
and the checkout were exercised.
