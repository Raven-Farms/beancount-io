# Managed price sources are fetched one after another, so a slow or unreachable price service adds 5 s per source to a command (10 s for 2, 30 s for 6, 80 s at the 16-source limit), again every 60 s

**Minor · cli · 20–30m · A1.** Real CLI QA, 2026-10-16, HEAD `c0267f61`, checkout `bea 0.3.1`, macOS 26.5.1. Synthetic local feed server with an 8 s delay.
ADR018 calls the CLI's fetch a mirror of the hosted ledger's bounded fetch.
The hosted service resolves sources in parallel (`Promise.all` in
`backend-cluster/ledger/src/foundation/managed-prices/managed-price-overlay.ts:324`).
The CLI loops over them, so each source's 5 s timeout adds up. During a
price-service outage every command on a ledger with several feeds stalls
for tens of seconds. No product fix implemented.

A ledger with two (or six) managed includes, all cached; the server delays
every feed by 8 s.

```sh
time bea -f /abs/two.bean price refresh
time bea -f /abs/six.bean check        # after the refresh window lapsed
```

Actual: about 10 s for two sources and about 30 s for six ("timed out after 5
seconds" per source). The next run within 60 s takes 0.3 s.

Expected: fetches run concurrently (or under one per-load deadline), so a
slow service costs about one timeout per command, as on the hosted side.

Cause: the loop at `cli/src/bea_engine/managed_load.py:343-357` calls
`resolve_feed` serially; each fetch waits up to 5 s
(`cli/src/bea_engine/managed_prices.py:323`).

Fix: resolve sources with a thread pool (the cache writes are per feed
directory), or share one deadline across them.

Dedupe: searched `sequential`, `parallel`, `per source` with timeout; w1/078
and w5/188 cover the per-request limit.

Acceptance: six delayed sources cost about 5 s. A test with a stubbed opener
pins concurrency.
