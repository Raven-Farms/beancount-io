# Keep payee and narration boundaries when generating import IDs

**Major · cli · 35–55m · A1.** A pipe inside a payee or narration can move
the apparent field boundary in the hash input. Two different payments then
receive one generated ID, and the second is silently skipped even with
`--duplicates include`, omitting its cash debit and expense. No product fix
implemented.

Real CLI QA 2026-10-20, checkout `c71839efb`, `bea 0.3.1`, Darwin 25.5.0
arm64, frontend Python 3.13.3, managed engine Python 3.12. Reproduced twice
from pristine fixtures, separate bounded processes, closed stdin/no TTY,
isolated absolute BEA_CONFIG_DIR/XDG_CACHE_HOME, BEA_NO_UPDATE_NOTIFIER=1,
no inherited BEA_FILE/BEA_TOKEN. No CLI source change on the subsequent pull.

Create `/absolute/qa/main.bean`:

```beancount
2024-01-01 open Assets:Cash USD
2024-01-01 open Expenses:Food USD
```

`statement-a.csv`:

```csv
Date,Amount,Payee,Narration
2024-02-01,-10.00,Shop|Branch,Purchase
```

`statement-b.csv`:

```csv
Date,Amount,Payee,Narration
2024-02-01,-10.00,Shop,Branch|Purchase
```

From `/absolute/qa`, with the environment above:

```sh
bea --json --no-input -f /absolute/qa/main.bean import statement-a.csv --csv date=Date,amount=Amount,payee=Payee,narration=Narration --account Assets:Cash --default-account Expenses:Food --duplicates include --apply
bea --json --no-input -f /absolute/qa/main.bean import statement-b.csv --csv date=Date,amount=Amount,payee=Payee,narration=Narration --account Assets:Cash --default-account Expenses:Food --duplicates include
bea --json --no-input -f /absolute/qa/main.bean import statement-b.csv --csv date=Date,amount=Amount,payee=Payee,narration=Narration --account Assets:Cash --default-account Expenses:Food --duplicates include --apply
bea --json -f /absolute/qa/main.bean query "SELECT payee,narration,number WHERE account='Assets:Cash' ORDER BY payee"
bea --json -f /absolute/qa/main.bean check
```

All exit 0 with empty stderr. A writes 1 with
`import-id: "csv:sha256:75481c2ac8103096"`. B's preview renders the two
different fields correctly but reports `ready: 0, duplicates: 1` and reason
`import-id csv:sha256:75481c2ac8103096 is already in the ledger.` The match
entry visibly has payee `Shop|Branch`, not B's `Shop`. Apply writes 0 and
leaves the ledger unchanged. The query returns only
`["Shop|Branch", "Purchase", "-10.00"]`. The second payment is absent:
cash/expense totals are -10/+10 USD instead of -20/+20.

Nearby controls, twice each: replace both pipes in the two source files with
`/` and both payments import; retain the pipes but give the files distinct
ID values (`BANK-1`, `BANK-2`) and map `id=ID`, and both import; repeat the
exact same payee/narration pair and the second correctly skips. Every fresh
check passes. Preview never writes the ledger.

Cause: `cli/src/bea_engine/importing.py:2489–2492` joins the two normalized
description fields as `f"{payee}|{description}"`; `_hash_base` at
2276–2278 joins that into the rest without framing or escaping. Both rows
therefore produce the identical preimage:

```text
2024-02-01|-10 USD|SHOP|BRANCH|PURCHASE|Assets:Cash
```

The canonical digest hit is treated as exact identity, so the differing
payee/narration fingerprint does not get a chance to distinguish them.
The separate occurrence-counter prefixes at 2496–2497 do not make the
encoded fields distinct across files. Caller search finds the shared
`_hash_import_ids` path used by CSV and Python importers, including older
paired spellings. Only CSV was exercised for this finding.

Fix: make arbitrary payee/narration fields unambiguous in generated identity,
including the distinction between one-description and two-description rows.
Preserve existing IDs for unaffected inputs where practical, and retain old
ambiguous spellings only with enough content/claim checking to avoid silently
skipping a different field tuple; surface unresolved legacy ambiguity for
review. Keep the normal case, repeated identical rows, source normalization
and edited-entry identity guarantees. Document any changed hash spelling in
the owning CLI contract; flag corresponding customer hash recipes if needed.
No new dependency or API change is required.

Dedupe: searched all board states for hash/digest separators, pipe-containing
descriptions and payee/narration hashing; reviewed active milestone scopes.
Completed w1/149 introduced payee hashing (`f47d9adfd`), and w5/140
(`b479ca70`) repaired occurrence/claim ownership. Their ordinary controls
remain valid; neither frames arbitrary field contents. Open 897/899 concern
cost constraints omitted from the amount, not these description boundaries.
No overlapping open repair or later fix was found in targeted history.

Acceptance: both source files import once with distinct IDs, totals -20/+20,
and correct field pairs; re-importing either writes 0. Keep all three controls
and cover ambiguous old IDs without silently consuming another payment.
Evidence retained in ignored pass5 `repro_description_field_boundary.py`,
`field-boundary-results.json`, eight fresh fixtures and captures with exact
argv/environment, streams, exit codes and before/after hashes. Other platforms
and the shared Python-importer path remain unverified.
