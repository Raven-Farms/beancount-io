# `.pm` anti-goals — do not do

Hard constraints for the adoption board. `/pm-brainstorm` and `/pm` read this before proposing or materializing work, and must reject conflicting items explicitly.

- **No private-repo leakage.** Never reference, copy, or depend on content from private sibling repositories (backend services, IDL, private infra). Work that requires private code to change belongs on that repo's board, not here — only propose work that can land entirely in this public monorepo.
- **No secrets on the board.** No credentials, tokens, internal URLs, or user data in any `.pm/` file. The whole tree is public and gitleaks gates every push.
- **Don't re-implement upstream.** Don't fork or duplicate what upstream `beancount` / `fava` already does well — extend, wrap, or integrate instead. Where reimplementation is deliberate (e.g. `fava-slim`), it must stay clean-room and license-clean.
- **No spammy growth tactics.** No star-begging, bulk unsolicited PRs/issues to other repos, fake engagement, or SEO spam. Adoption comes from things that work: docs, skills, tools, examples.
- **No half-self-hosted deployments.** A deployment is either fully self-hosted or fully managed. Do not propose work that assumes, enables, or smooths over a split — a self-hosted dashboard pointed at the managed API, dashboard and API on separate origins reconciled through discovery documents, onboarding that hides which deployment a user is on, or configuration whose only purpose is to make the two halves agree. Self-hosters run the whole stack; managed users use the managed stack. (User decision 2026-09-12, after `w2/m29` was reverted for building exactly these seams.)
- **No hosted-ledger export without SSH setup.** Do not propose or implement "Export hosted ledgers to a local workspace without SSH", including archive/API shortcuts that remove SSH-key setup from this workflow. Users must log in and add an SSH key for hosted-to-local ledger workflows; these requirements are deliberate defenses against bot attacks. (User decision 2026-09-27.)
- **No mobile transaction draft recovery across app restarts.** Do not propose or implement the New Transaction draft-recovery feature retired from `w4/m30`, including persistent local drafts and their Resume/Discard, Keep/Discard, receipt-prefill conflict, and interrupted-submission recovery flows. The added draft-management decisions complicate transaction entry without demonstrated user benefit. Revisit this feature only at the user's explicit request. (User decision 2026-09-28; `w4/m30` was deleted before shipping.)
- **No duplicate stacks for MCP testing.** Do not build, provision, or rebuild a second deployment — a parallel Compose project, alternate ports, fresh copies of databases — only to run MCP agent journeys, benchmarks, or client rehearsals. Real-client MCP evaluation connects to the hosted Beancount.io MCP endpoint (`https://beancount.io/api-gateway/mcp`) with a dedicated QA account and synthetic test ledgers, and records the deployed revision it observed. (User decision 2026-09-15, after `w5/m4` was blocked on choosing a separate benchmark stack.)
- **No mobile findings that reproduce only above AX2 text size.** The supported Dynamic Type ceiling for the native app is iOS `accessibility-large` (AX2, about 2× body text). That matches what the code already designs for: rows stack from 1.3×, amounts and header actions cap at 1.4×, and the search field caps at 2×. Do not file, promote, or schedule a layout or readability finding whose only reproduction is at AX3–AX5 (`accessibility-extra-large` and up). When a candidate shows up at the maximum size, re-test it at AX2 and file only what reproduces there, with AX2 evidence. (User decision 2026-10-15, after `w0/041`–`044` reproduced only at AX5 and were dropped.)
- **No milestone theater.** Don't create milestones to make the board look busy. If it isn't >1h of real work with an observable adoption outcome, it's an inbox note or nothing.
