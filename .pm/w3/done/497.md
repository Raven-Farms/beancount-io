# Public ledgers' Version History bounces anonymous visitors to login: commit reads demand a session the policy doesn't require

**Severity:** minor. It may be a product decision, but no recorded decision was found. **Estimate:** 30–45 minutes including resolver and parity tests. **Owner:** `backend-cluster/backend-v2` (`src/features/gitea/commits/api/commits-resolver.ts`), with a dashboard check of the redirect. **A2/A3:** every other read of a public ledger works signed out: overview, journal, accounts, files, file contents. Files offers a **Version History** button, and following it sends an anonymous visitor to the sign-in page. A shared commit link from a public ledger does the same.

## Live reproduction

Production `https://beancount.io`, 2026-10-16, local main at the time of filing. QA-owned headless Chromium, 1440×1000, a fresh **anonymous** context. Public `open_ledger/example`. Read-only.

1. `/ledger/open_ledger/example/files/tree/main` renders for an anonymous visitor and shows **Version History**. Click it.
2. The page lands on `/auth/login?next=%2Fledger%2Fopen_ledger%2Fexample%2Fcommits`. Directly opening `/commits` or `/commit/f281c34` does the same.
3. Network: the SSR response is HTTP 200. After hydration, `GetLedgerAccounts`, `GetLedgerErrors` and `GetLedgerEvents` succeed anonymously, then `ListCommits` returns `UNAUTHENTICATED "Access denied! Please login to continue!"` and the client's unauthenticated handler redirects to login.
4. Control: as a signed-in non-member, the same Version History lists the ledger's commits normally.

## Root cause

`commits-resolver.ts:12–13` and `:29–30` decorate `listCommits` and `getCommitDetails` with `@Authenticated()`, which rejects any request without a session before authorization runs. The authorization policy itself treats commit history as ledger content: `op-class.ts:773–774` maps both to `LEDGER_REPOSITORY_READ`, and `authorization-service.ts:355` resolves that to `ledgerContentReadRequirement()`. That is the same requirement that lets anonymous visitors read a public ledger's files and journal. The decorator is stricter than the policy.

## Fix

Decide and record it. If public history is intended, which is consistent with public files and the route's indexable SEO head (`createLedgerHead(args, "ledgerCommits")`), drop `@Authenticated()` from both commit reads and rely on `LEDGER_REPOSITORY_READ`. Private ledgers must still return not-found/forbidden. Keep REST's credential requirement unchanged (its documented policy) and keep MCP's resource authorization as-is. If history should stay member-only, hide Version History for anonymous visitors and make the route `noIndex`, so the UI doesn't offer a link that dead-ends at sign-in.

Acceptance: anonymous `/ledger/open_ledger/example/commits` and a commit detail page render the public history (or, under the alternative, Version History is not offered and the route is noindex). A private ledger's history stays inaccessible anonymously. Resolver tests cover anonymous public, anonymous private, and member access. backend-v2 checks (including the parity gate) pass.

## Dedupe

Searched `.pm/**` for anonymous / signed-out / public-reader access to commits or version history. Earlier anonymous QA notes (w4/074, w4/075, w4/083, w4/092) exercised other pages, and w4/144 fixed login continuations. None records a decision that history is member-only, and none covers this resolver gate.

---

**Resolved 2026-10-17** — Public history is intended: it matches public files and journal and the route's indexable SEO head, and the policy already classes commit reads as `LEDGER_REPOSITORY_READ`, the same requirement as other ledger content. `listCommits` and `getCommitDetails` now carry `@AllowAnonymous()` instead of `@Authenticated()`, so the service's PDP decision is the only gate. REST keeps its credential requirement; MCP's resources are unchanged. New schema-level resolver tests run the real decorators and `AuthorizationService`: anonymous-public list and detail succeed on the anonymous Gitea client, anonymous-private list and detail are refused `UNAUTHENTICATED` before any Gitea call, and a member reads a private ledger with their own client. Restoring `@Authenticated()` fails both anonymous-public cases. On a one-off container built from this revision, attached to the local docker-mac stack beside the running service, anonymous `listCommits`/`getCommitDetails` on a public local ledger returned its history and diff files. A private ledger and a nonexistent one both returned the same `UNAUTHENTICATED`. The running older backend still reproduced the original `Access denied! Please login to continue!`. The dashboard needed no change: the redirect came only from the failed `ListCommits`. The production page reaches anonymous visitors after the next backend deploy; the dashboard page was not exercised against the new build. backend-v2 typecheck, lint (including dead code), the full unit suite (320 suites, 5,516 tests, including the parity gate) and the OpenAPI snapshot check passed, shipped in `3897a7b2` (`backend-v2`).
