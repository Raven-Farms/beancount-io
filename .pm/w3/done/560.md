# New Entry accepts any typed account name and writes an entry against an account the ledger never opened

**Severity:** minor. **Estimate:** 45–60 minutes including form tests across the transaction, balance and note tabs. **Owner:** `dashboard` (`features/journal/components/new-directive-dialog/{transaction,balance,note}-form.tsx`, `common/components/ledger-comboboxes/account-combobox.tsx`). **A2:** the account fields are comboboxes with free text allowed (`allowCustom`, default `true` in `common/components/ui/combobox.tsx:48`). A typo (`Expenses:Groceris`), or a new category the user expects to "just exist", is accepted silently. The write succeeds, and the ledger then fails validation with `Invalid reference to unknown account`. Nothing in the dialog says the account isn't open or offers to open it.

## Live reproduction

Production `https://beancount.io`, 2026-10-16, QA-owned headless Chromium, 1440×1000. The signed-in owner used a synthetic ledger whose open accounts don't include `Assets:Nope`. The form was **not submitted** on the hosted ledger.

1. `/journal?action=new-entry&directive=balance`. In **Account**, type `Assets:Nope`. The suggestion list is empty, and the typed text is kept as the value.
2. Enter amount `10`. **Create Balance Entry** is enabled. There is no inline message, and the form's message slots stay empty.
3. The Transaction tab uses the same `AccountCombobox` for every posting account (`transaction-form.tsx`, account schema `z.string().trim()` at ~`:88`), so its submit has the same path.
4. What the write produces, verified offline with `bea check` on a scratch ledger: `Invalid reference to unknown account 'Assets:Nope'`, plus, for a balance, `Balance failed … accumulated 0 USD`.

The dialog's own **Account** tab opens accounts, and the Accounts page has **Open Account**, so the remedy exists. The entry forms just never point to it.

**Confirmed end to end on the hosted ledger (2026-10-17, QA account's disposable synthetic ledger, reverted afterwards).** New Entry → Balance with the typed account `Assets:Qa20261017Nope` (never opened), `10 USD`, `2026-09-08` sent `BulkEntries … "account":"Assets:Qa20261017Nope"` and showed **"Entry created successfully"**. `checkLedger` then reported `E1001 "Account Assets:Qa20261017Nope was never opened"` at `main.bean:100`. Nothing in the dashboard mentioned it (see w3/640 for the missing post-write signal).

## Root cause

`AccountCombobox` loads the ledger's non-closed accounts (`GetLedgerAvailableAccounts`, per its doc comment at `account-combobox.tsx:30`) only as suggestions. The forms' zod schemas check only non-empty strings, and no form compares the submitted account against the loaded list. Neither the backend-v2 `writeBulkEntries` nor the ledger `api/entries.ts` refuses unknown accounts (they check elided amounts, dates and transaction balance), so the entry is appended as typed. A typed name that matches a **closed** account is accepted the same way and produces a posting-after-close error.

## Fix

In each New Entry form, validate account fields against the ledger's open accounts at the entry's date. For a name that isn't open, show an inline, localized message naming it ("Assets:Nope isn't open in this ledger"), with a one-click option to **also open it** on or before the entry date. Selecting it adds an `open` entry to the same atomic `BulkEntries` batch. Without that choice, keep submit disabled. A closed account gets a message naming its close date. Keep free text so a user can still type an exact existing name faster than picking it. Account-name syntax messages stay as they are.

Acceptance: typing an unopened account shows the message and disables submit until **also open it** is chosen. The resulting batch then contains the `open` and the entry, and the ledger has no new errors. An existing account submits unchanged. Rendered tests cover the transaction posting, balance and note fields, a closed account, and the also-open path's mutation variables. Dashboard gates pass.

## Dedupe

Searched `.pm/**` (including `done/` and `blocked/`) for unopened/unknown/not-open account in dashboard forms. Hits are CLI (w3/385–386, w5/380, w5/396) or unrelated (w4/m27). w3/499 (unbalanced New Entry) and w3/557 (Open Account accepting an existing account) are adjacent: same dialog family, different checks. They could be implemented together, but each stands alone. `allowCustom` has been unconditional since the dashboard import, so this is not deployment lag.

Unverified: whether MCP/REST writes should also refuse unknown accounts (they report `validation.newErrors` instead, which is a different contract); the narrow layout; other locales.

---

**Resolved 2026-10-17** — New Entry's Transaction (every posting), Balance and Note forms check each account against the ledger's account directory (`GetLedgerAccountDirectives`) on the entry's date. A never-opened account reads "Assets:Nope isn't open in this ledger." and blocks submit. An **Also open Assets:Nope on 2026-09-08** checkbox adds `{type: OPEN, open: {date, account, currencies: []}}` ahead of the entry in the same atomic `BulkEntries` batch; one per account, even when several postings name it. The checkbox appears only for names Open Account itself would accept: the same shared schema covers root, token shape and existence. An account closed before the entry, or opened after it, names that date ("Assets:OldBank was closed on 2025-12-31, before this entry." / "opens on 2027-01-01, after this entry.") and stays blocked. An entry on the close date is allowed, as in Beancount. Free text still works for exact existing names, and nothing is blocked until the directory has loaded. Four new strings in all 15 journal locales. Rendered tests cover the Balance also-open path's exact mutation entries, an open account submitting unchanged, a closed account and an opens-later account on Note, a name Open Account would refuse, and a misspelled Transaction posting opened in the same batch. Removing the forms' wiring fails the five refusal cases while the open-account control passes. The existing form tests gained a `useQuery` stub. Not done: MCP/REST writes still append unknown accounts and report them through `validation.newErrors`; that is a different contract and was left alone. No live browser pass or hosted write was made. Dashboard format, lint (including dead code), tests (5,816 passed, one skipped), build and a public-tree secret scan passed, shipped in `d695a871` (`dashboard`).
