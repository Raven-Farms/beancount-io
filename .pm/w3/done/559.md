# Bank-import review shows every staged amount as US dollars, even for an account the user mapped to another currency

**Severity:** minor. **Estimate:** 30–45 minutes including a rendered table test. **Owner:** `dashboard` (`features/plaid/components/transaction-review-table.tsx`, `graphql/query/plaid.graphql`). **A2:** the review table is the last thing a user checks before booking bank transactions into the ledger. Account mapping lets them set a per-account currency (`account-mapping-form.tsx`, `UpdatePlaidAccountCurrency`), and booking honors it. The review still shows `-$12.00` for what will be written as `-12.00 EUR`. The amount and date formats also ignore the interface language.

## Evidence

This was traced in source at HEAD. It was **not reproduced live**: the QA account has no bank connection, and linking one is out of bounds for a routine sweep.

- `transaction-review-table.tsx:287–293`: `formatAmount` is `new Intl.NumberFormat("en-US", { style: "currency", currency: "USD" }).format(Math.abs(parseFloat(amount)))`, used for every row at `:790`. `formatDate` (`:295–300`) is `toLocaleDateString("en-US", …)`.
- The rows come from `GetUnsyncedPlaidTransactions` (`graphql/query/plaid.graphql:39–53`). The query selects `plaidAccountId` but no currency, so the table has nothing else to format with.
- Booking (`backend-v2/src/features/plaid/service/plaid-sync-service.ts:709–714`) writes each transaction with `account?.currency ?? "USD"`, which is the mapped account's currency. The page that hosts the table (`plaid-settings/components/plaid-management-state.tsx:105`) already loads those accounts.
- Users set that currency in the account mapping form (`plaid-connections/components/account-mapping-form.tsx:138–160, 268–270`).

So for an account mapped to EUR, CAD or GBP, review shows a dollar amount and booking writes the mapped currency. The table also uses `en-US` grouping and month names in every one of the 15 UI languages, while the rest of the dashboard formats through `useFormatNumber`/`format-datetime`.

## Fix

Format each row's amount in its account's currency: join `plaidAccountId` to the accounts the page already has, or add the currency to the unsynced-transactions selection if the API exposes it. Fall back to USD exactly where booking does. Show the amount through the shared ledger amount formatting (number plus commodity, as the journal does) instead of a hardcoded `$`. Format dates with the shared localized date helper. No booking change is needed. If the GraphQL type gains a currency field, add it to REST/MCP's staged-transaction read (`listStagedBankTransactions`) in the same change for parity.

Acceptance: with a fixture account mapped to EUR, the review row reads `-12.00 EUR`, and a USD account still reads its amount in USD. A rendered table test covers both, plus a non-English locale's date. Dashboard gates pass.

## Dedupe

Searched `.pm/**` (including `done/`) for `transaction-review-table`, hardcoded USD, and bank/Plaid currency display. w4/080 is report section copy claiming USD for a custom-unit ledger, a different component. w3/186 cites this table's `formatDate` only as a year-including control. Recent history on this file (`5787262c`, `e9241515`, `aeec496b`) touched copy and pluralization, not number/currency formatting, so this is not deployment lag.

Unverified: live rendering with a real linked institution; whether Plaid's own `iso_currency_code` ever differs from the user's mapping (the mapping is what booking uses, so it is the right source).

---

**Resolved 2026-10-17** — The bank-import review shows each staged amount in its account's mapped currency, the units booking writes. `GetPlaidAccountsForLedger` now selects `currency`, which `PlaidAccountWithInstitutionType` already exposes, so there is no API change and no new REST/MCP field to keep in parity. Rows join on `plaidAccountId` and render two decimals plus the currency, with booking's own USD fallback for an account it cannot find, inside the shared `Amount` RTL isolation. A EUR account reads `-12.00 EUR` and a USD account `+5.50 USD`; there is no hardcoded `$`. Dates use the interface language and are read in UTC, matching the calendar day booking keeps; the old local-time read could show the previous day west of UTC. Codegen ran against an SDL emitted from backend-v2 HEAD. It also refreshed schema descriptions and fields the committed `definitions.ts` had drifted from; no other operation's types changed. A rendered table test covers EUR, USD and an unmapped account, the `bdi` isolation, and a German date. Restoring the original table fails all three. Not verified live with a linked institution (the QA account has none). Dashboard format, lint (including dead code), tests (5,810 passed, one skipped), build and a public-tree secret scan passed, shipped in `dafb5974` (`dashboard`).
