# Open Account accepts an account that is already open, so one click commits a duplicate `open` and breaks the ledger

**Severity:** minor. It would be major if seen in the wild, because the result is a ledger that fails validation. **Estimate:** 35–50 minutes including validation and rendered tests. **Owner:** `dashboard` (`features/ledger-data/accounts/open-account-dialog.tsx`, the `buildOpenAccountSchema` it uses, accounts locales). Optionally add a server guard in `backend-cluster/ledger` (`api/entries.ts`) so REST/GraphQL/MCP refuse it identically. **A2:** Open Account is the newcomer's first structural write. Typing an existing name, for example to add a sub-account and stopping one segment short, gets no warning. Submitting appends a second `open` line, and the ledger then reports `Duplicate open directive`. Every report, and every later write validated against the ledger, now carries an error the user didn't knowingly make.

## Live reproduction

Production `https://beancount.io`, 2026-10-16, QA-owned headless Chromium, 1440×1000, English. The signed-in owner used a synthetic ledger that already opens `Assets:Cash` and `Equity:Opening-Balances` on 2026-01-01. Read-only: the dialog was inspected and **not submitted**.

1. `/ledger/<owner>/<ledger>/accounts` → **Open Account** (`?action=open-account`).
2. Type `Assets:Cash`. The submit button **Open Account** becomes enabled with no message. `Equity:Opening-Balances` behaves the same.
3. Controls on the same field: `assets:bank`, `Foo:Bar`, `Assets:bank`, `Assets:Cash:` and `Assets:Cash ` are each refused with a specific message, so the field does validate; it just never checks existence.
4. What submission produces, verified offline on a scratch file with the same shape (`bea check`, Beancount 3.2.3 engine): `dup-open.bean:7: Duplicate open directive for Assets:Cash`.

**Confirmed end to end on the hosted ledger (2026-10-17, QA account's disposable synthetic ledger, reverted afterwards).** At local HEAD against the production API, Open Account with `Assets:Cash` sent `BulkEntries … {"type":"OPEN","open":{"date":"2026-10-17","account":"Assets:Cash","currencies":[]}}`. The server answered `success: true, "Added 1 entry successfully"`, and the dialog closed with no message. `checkLedger` then reported `E1002 "Account Assets:Cash is already open (opened on 2026-01-01)"` at `main.bean:92`, and the Accounts directory listed **Assets:Cash twice** (13 / 13 rows, opened 2026-10-17 and 2026-01-01, same postings and balance).

## Root cause

`open-account-dialog.tsx` builds its zod schema from the ledger's root names only (`buildOpenAccountSchema(accountPrefixes, …)`, ~lines 67–90). The dialog never consults the ledger's account list, although the Accounts page that hosts it already has every account with its open/close dates. `onSubmit` sends `BulkEntries` with an `open` entry. Nothing downstream refuses it either: backend-v2's `writeBulkEntries` (`service/ledger-entry-service.ts:251`) checks only elided amounts and dates, and the ledger's `api/entries.ts` (~lines 100–160) checks only transaction balance before appending. A closed account is affected too: Beancount does not allow re-opening it.

**Second entry point (added 2026-10-17):** the New Entry dialog's **Account** tab (`features/journal/components/new-directive-dialog/open-account-form.tsx`, reachable from Journal → New Entry and `?action=new-entry&directive=account`) builds the same `buildOpenAccountSchema(accountPrefixes, …)` (`:60`) and sends the same `open` entry (`:93`), with no existence check either. Fix both forms together, preferably by putting the already-open check inside the shared schema builder so neither can drift.

## Fix

In the dialog, refuse a name that the ledger already opens (open or closed). Use an inline, localized message that names the account and its open date, for example "Assets:Cash is already open (since 2026-01-01)", and keep the submit button disabled while it shows. Use the accounts list the page already loads, compare case-sensitively as Beancount does, and keep the existing prefix and component messages. Optionally refuse the same case in the ledger's entries write with `BAD_USER_INPUT` naming the entry, so the GraphQL, REST and MCP write paths behave alike. The client check alone fixes the dashboard journey.

Acceptance: typing `Assets:Cash` (open) or a closed account shows the already-open message and keeps submit disabled, in both the Accounts page dialog and the New Entry → Account tab. `Assets:Cash:Wallet` stays submittable. A rendered dialog test covers open, closed, new-child and case-different names (`assets:cash` keeps its existing prefix message). Dashboard gates pass. If the server guard is added, ledger tests cover the refusal and the parity gate stays green.

## Dedupe

Searched `.pm/**` (including `done/` and `blocked/`) for duplicate open, already-open, and Open Account terms. w5/530 is CLI import Unicode normalization, where a duplicate-open remedy is printed. The Open Account history (w0/017 invalid-name messages, `05cc495d` incomplete tokens, `dfa91310` draft reset) never added an existence check. `git log -S` on the dialog shows no such check at HEAD, so this is not deployment lag.

Unverified: the actual hosted write (deliberately not submitted on a real ledger) and how the Errors page words the resulting error. Other locales and the 390px layout were not exercised for this dialog.

---

**Resolved 2026-10-17** — Both Open Account forms, the Accounts page dialog and New Entry's Account tab, refuse a name the ledger already opens. The check lives in the shared `buildOpenAccountSchema` and compares names exactly, as Beancount does. An open account reads "Assets:Cash is already open (since 2026-01-01)."; a closed one reads "Assets:OldBank was closed on 2025-12-31; Beancount can't open it again." Submit stays disabled while either shows. A new `useOpenAccountSchema` hook gives both forms the same root prefixes, the `GetLedgerAccountDirectives` list (`cache-and-network`, so an account opened a moment ago is known) and the schema, which removes the duplicated setup that let them drift. New children (`Assets:Cash:Wallet`) stay submittable. `assets:cash` keeps its prefix message, and the other name checks are unchanged. Two new strings in all 15 accounts locales. Tests: schema cases for open, closed, new-child and case-different names, plus a rendered suite run against both surfaces. It asserts the message and the disabled submit for `Assets:Cash`, `Equity:Opening-Balances` and a closed account, and that `Assets:Cash:Wallet` is accepted. Removing the change fails all six refusal cases and the four controls still pass. Not done: the optional server-side guard in the ledger's entries write. GraphQL, REST and MCP writes can still append a duplicate `open`; the write result's validation reports it. That case was not exercised here. No live browser pass was made. Dashboard format, lint (including dead code), tests (5,803 passed, one skipped), build and a public-tree secret scan passed, shipped in `d9a2d746` (`dashboard`).
