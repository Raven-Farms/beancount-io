# Structured ledger writes don't validate amount syntax: a malformed posting returns "service unavailable, retry", and a malformed balance/price/budget amount is committed as unparseable text

**Severity:** major. Any API client can commit text that breaks the ledger file, and a bad request is reported as an outage. It's a regression since 2026-09-25. **Estimate:** 50–60 minutes including tests on all three surfaces. **Owner:** `backend-cluster/ledger` (`api/entries.ts`, `features/ledger/utils/transaction-balance.ts`, `foundation/rustledger/entry-build.ts`) and `backend-cluster/backend-v2` (`features/ledger/service/ledger-entry-service.ts` `writeBulkEntries`, `api/rest/v1/entries-handler.ts` amount schema). **A1:** agents write through MCP `addLedgerEntries` and REST `POST …/entries`, and the dashboard through GraphQL `bulkEntries`. All three accept `amount.number`/`units.number` as an arbitrary string. A posting such as `"(12.50)"` or `"-1,234.56"` makes the ledger service throw, and the caller is told "Ledger API is temporarily unavailable … A dependency is down. Retry with backoff; this is not a problem with the request.", so an agent following that hint retries forever. A balance, price or budget amount such as `"abc"` passes no check at all and is committed verbatim, leaving a parse error in the file.

## Live reproduction

Production API, 2026-10-17, QA account's disposable synthetic ledger (restored byte-for-byte afterwards). MCP `addLedgerEntries`, signed-in API key, one call each:

| entry | result |
| --- | --- |
| transaction, postings `units.number` `"(12.50)"` / `"-(12.50)"` | `SERVICE_UNAVAILABLE: Ledger API is temporarily unavailable`, hint "A dependency is down. Retry with backoff; this is not a problem with the request." Nothing written. |
| transaction, `"-1,234.56"` / `"1,234.56"` | same `SERVICE_UNAVAILABLE`. Nothing written. |
| balance `Assets:Bank:Savings`, `amount.number` `"abc"` | `ok: true`, "Added 1 entry successfully". The file gains `2026-09-07 balance Assets:Bank:Savings abc USD`. `validation.newErrors: [{"message":"parse errors in main.bean","code":"LOAD"}]` |

The dashboard's GraphQL `bulkEntries` behaves identically. Smart Import with those amounts (w3/564) fails with "Import Failed — The service is temporarily unavailable" every time, while a plain `-3.21` control imports. The Errors page lists the committed parse error as "parse errors in main.bean · Unknown file · Unknown line", so the user can't even locate the bad line.

## Root cause

- `transaction-balance.ts:115`: `const amount = new BigNumber(number); if (!amount.isFinite()) return { …"is not a number"… }`. Since `4f169e07` (2026-09-25, "bump dependencies to latest compatible versions") the ledger uses **bignumber.js 11.1.5**, whose constructor **throws** `[BigNumber Error] Not a number: (12.50)` on an invalid string instead of returning `NaN`. Verified by running the module locally: `(12.50)` and `-1,234.56` throw, `-3.21` returns `{ok: true}`. The `isFinite` guard added with the write-path hardening in `c29268be` (2026-09-08) is now dead. The exception escapes as a 500, and backend-v2's `favaApiErrorToDomainError` maps any ≥500 to `ServiceUnavailableError("Ledger API")` (`foundation/fava/error-to-domain.ts:112–120`).
- Non-transaction amounts never go through that check. `entry-build.ts` `toBeancountNumber` (`:46–51`) returns any string without an `e`/`E` verbatim, so `price` (`:138`), `balance` (`:150–157`) and budget (`:193`) amounts are rendered and committed as typed.
- No surface validates the grammar first: the REST/MCP `amountSchema.number` is `z.string()` (`entries-handler.ts:13–17`), and GraphQL `LedgerAmountInput.number` is a `String`.

## Fix

Validate every `number` in a structured write against one decimal grammar (optional sign, digits, optional fraction, optional exponent that `toBeancountNumber` expands) at the shared boundary. Do it in backend-v2 `writeBulkEntries`, where all three surfaces converge, and again in the ledger's entries handler as defense in depth. Refuse anything else with `BAD_USER_INPUT` naming the entry index and field (`entry 0: postings[1].units.number "(12.50)" is not a decimal number`), before any file is read. In `transaction-balance.ts`, construct `BigNumber` only after that check, or catch its throw and return the existing `"is not a number"` result, so the bignumber upgrade can't turn input errors into 5xx again. Add a test that fails on a throwing constructor. Keep the REST v1 response shape. MCP returns the same refusal envelope with its normal bad-input hint.

Acceptance: each request in the table returns `BAD_USER_INPUT` naming the field, with nothing committed, on GraphQL, REST and MCP alike. A plain `-3.21` and an exponent `1e-7` still write. Ledger unit tests cover the throwing constructor, and backend-v2 tests cover each directive type's amount. The parity gate stays green.

## Dedupe

Searched `.pm/**` for `BigNumber Error`, "Not a number", bignumber, malformed amounts and `SERVICE_UNAVAILABLE` on writes. w5/213 is the CLI's own bulk amount grammar, w3/492 is file size, and w1/109 is CLI bulk metadata errors. w3/564 (open) is the dashboard client that *sends* these spellings, and this note is the server hole any client can hit. w3/640 (open) is the missing post-write signal in the dashboard. No item covers the server behavior. Present at HEAD (the module reproduces locally) and on production.

---

**Resolved 2026-10-17** — backend-v2's `writeBulkEntries`, where GraphQL `bulkEntries`, REST `POST …/entries` and MCP `addLedgerEntries` converge, now checks every amount a structured write carries against one decimal grammar: an optional sign, digits with an optional fraction, and an optional exponent the ledger expands. That covers posting `units` and `price`, and `price`, `balance` and `budget` `amount`. The check runs before any file is read and refuses anything else with `BAD_USER_INPUT` naming the entry and field (`entry 0: postings[0].units.number "(12.50)" is not a decimal number`). The ledger's bulk handler repeats the check, custom values included, as defense in depth before reading a file, through `isDecimalNumber` in `entry-build.ts`. `checkTransactionBalance` now catches bignumber.js 11's throwing constructor and returns its "is not a number" result, so a dependency upgrade can't turn bad input into a 5xx again. A unit test asserts the constructor throws and the check still answers. A three-surface parity test (REST/GraphQL/MCP) refuses a parenthesized posting, a grouped posting, a balance `abc`, a price `$4.50` and a budget `1.000,00`. Each names the field, writes nothing and never says service-unavailable, while `-3.21` and `1e-7` still write. Removing the backend-v2 check fails all 15 refusal cases, with the six controls passing. Ledger handler tests cover the same posting, balance and price cases (no file read, nothing committed). The REST v1 response shape is unchanged. Since this note was filed, the ledger also refuses writes whose projection adds bean-check errors (w0/m2). These checks name the bad field before that point. Ledger lint (including dead code), typecheck, build and tests (1,342) passed. backend-v2 typecheck, lint, tests (5,557, including the parity gate) and the OpenAPI drift check passed, as did a public-tree secret scan, shipped in `0830d170` (`ledger`, `backend-v2`). The fix reaches production with the next ledger and backend deploy.
