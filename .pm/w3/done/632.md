# In Persian, the Overview and exported statements label Gregorian ledger periods with Solar Hijri dates: August 2026's figures are titled "شهریور ۱۴۰۵", and a February entry loses its year

**Severity:** minor (localization correctness). **Estimate:** 30–45 minutes, including a shared formatter and fa tests. **Owner:** `dashboard` (`features/reports/overview/lib/overview-utils.ts`, `overview/components/net-worth-card.tsx`, `overview/components/recent-activity-card.tsx`, `features/reports/export/date.ts`, `common/lib/format/format-datetime.ts`). **A2:** with the interface in Persian, `Intl.DateTimeFormat("fa", …)` defaults to the Persian (Solar Hijri) calendar. The dashboard's buckets and dates are Gregorian: the ledger file, the Journal (`2026-08-28`), the period tables (`2026-08-31`), CSV exports and the New Entry date picker (`2026/10/16`, months ژانویه … دسامبر via `react-day-picker`'s `fa-IR` locale) all use Gregorian. But the Overview and statement headers run their dates through the locale default, so the same app shows two calendars, and the labels name the wrong span.

## Reproduction

Local HEAD (`yarn dev`, pointed at the production API), signed-in QA owner of a synthetic ledger, headless Chromium 1440×1000, `?lang=fa`. Read-only.

1. Overview → **Money movement**. The bucket holding the 2026-08-01 salary and the August expenses (Gregorian **August 2026**) is titled **"شهریور ۱۴۰۵"**. Shahrivar 1405 is 23 Aug – 22 Sep 2026, so the label names a different month from the figures under it.
2. Overview → **Recent activity**. The 2026-08-28 FARMERS MARKET entry reads **"۶ شهریور"**, while the Journal row for it reads `2026-08-28`.
3. Overview → **Net Worth** chart. The x-axis month-end points are labelled بهمن … شهریور (Jan 31 → Bahman, Aug 31 → Shahrivar), while its own "Period data" table lists `2026-01-31 … 2026-08-31`. The y-axis ticks use Latin digits (`18.0k`) beside Persian-digit amounts.
4. **Year omission:** `formatActivityDate` drops the year when the *Gregorian* year equals the current one (`recent-activity-card.tsx:42–47`). With `?lang=fa&time=2026-02`, the 2026-02-10 NETFLIX entry renders as **"۲۱ بهمن"** with no year, but 21 Bahman is in **1404**, while the current Persian year is 1405. A Persian reader sees a date that looks like it hasn't happened yet. On the same page, Money movement for Gregorian February is titled **"۱۴۰۴ اسفند"** (Esfand 1404 = 20 Feb – 20 Mar).
5. Control: the New Entry dialog's date field and calendar popover in the same session are Gregorian (`YYYY/MM/DD`, ژانویه … دسامبر).

From source (not exported in this run): statement Markdown/print headers use `formatStatementDate(value, locale)` (`features/reports/export/date.ts:7–11`), with `dateStyle: "long"` and no calendar, so a Persian export's "For the period …" line would also be Solar Hijri, beside a CSV whose `period_start` is `2026-07-01`.

## Root cause

`new Intl.DateTimeFormat(language, {...})` without `calendar` in `overview-utils.ts:379` (`formatPeriodMonth`), `net-worth-card.tsx:55,65,326`, `recent-activity-card.tsx:49` and `export/date.ts:7`. ICU picks `persian` for `fa`. The mobile app pins Gregorian deliberately for exactly this reason (`mobile/src/common/date-format.ts`: "These dates are ledger dates … a list header that disagrees with the file it describes is a bug however well-localized it is"). The dashboard has no shared equivalent, and its date picker happens to be Gregorian.

## Fix

Add one shared ledger-date formatter in `common/lib/format/` that always passes `calendar: "gregory"` (keeping the language's month names and numerals, so Persian shows "اوت ۲۰۲۶"), and route the call sites above through it. Base the "same year → omit year" rule on the same calendar the label uses. Localize the Net Worth y-axis tick formatter's digits like the amounts. Whether Persian should ever switch wholesale to Jalali buckets is a product decision. Until then, labels must match the Gregorian buckets they describe. Non-ledger instants (commit times, "joined" dates) may keep the locale default.

Acceptance: with `?lang=fa`, Money movement for August 2026 is titled with the Gregorian month (اوت ۲۰۲۶), Recent activity shows the Gregorian day and month with the year whenever it differs, and the Net Worth axis labels and digits agree with its table. Statement Markdown/print periods in fa are Gregorian. Unit tests pin fa output for each formatter, and English, German and Chinese are unchanged. Dashboard gates pass.

---

**Resolved 2026-10-17** — A shared `ledgerDateFormat` (`common/lib/format/ledger-date.ts`) wraps `Intl.DateTimeFormat` with `calendar: "gregory"`, keeping the language's month names and digits. Persian reads "اوت ۲۰۲۶" for August 2026. It now formats Money movement period titles (`formatPeriodMonth`), Net Worth's months, x-axis labels and price dates, Recent activity dates, and statement export dates (`formatStatementDate`, used by the Markdown and print headers). Recent activity's same-year rule now compares the calendar the label shows, so a 2026-02-10 entry reads "۱۰ فوریه" with its year whenever 2026 isn't the current year. Net Worth's y-axis ticks use the language's own digits (compact `Intl` notation) where it does not write Latin digits. Latin-digit languages keep the shared `18.0k`. Non-ledger instants (`formatDateTime`, commit and sign-up times) are untouched. Tests pin fa output: Gregorian month name and ۲۰۲۶ with no ۱۴۰۵ for the shared formatter, the period title and the statement date; Net Worth's axis month and Persian-digit tick; and Recent activity's Gregorian date. en/de/zh are unchanged. The old call sites fail all four call-site cases. Whether Persian should ever bucket by Jalali months remains a product question. A fa Markdown export was not generated end to end. Dashboard format, lint (including dead code), tests (6,037 passed, one skipped), build and a public-tree secret scan passed, shipped in `5d7b67b8` (`dashboard`).
