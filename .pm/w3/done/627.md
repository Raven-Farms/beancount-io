# Overview's new chart data tables print floating-point noise: Net Profit `1625.7399999999998 USD`, a flow of `14450.000000000002`, a breakdown row of `855.8100000000001`

**Severity:** minor. It's a regression from w3/495, shipped 2026-10-16. **Estimate:** 30–45 minutes for the three tables, with rendered tests. **Owner:** `dashboard` (`features/reports/overview/components/income-expenses-chart.tsx`, `distribution-chart/distribution-data-table.tsx`, `cash-flow-sankey.tsx`). **A2:** w3/495 gave the Overview's charts readable data tables, which are the text alternative screen-reader and keyboard users rely on. All three print their amounts with `String(number)`, so any value the chart computed client-side (a subtraction, a grouped "Other", a merged flow) shows binary representation error. None of them use the locale formatter the same charts' tooltips use (`formatNum`), so German readers get `4100 USD` in the table and `4.100,00` in the tooltip.

## Reproduction

Local HEAD (`yarn dev`, pointed at the production API), headless Chromium 1440×1000, English. Read-only. Open each public synthetic ledger's Overview and expand the chart disclosures:

| ledger | Income vs Expenses → Period data | Distribution → Breakdown | Cash Flow → Flows |
| --- | --- | --- | --- |
| `open_ledger/budgeting-envelopes` | `4100 USD · 2474.26 USD · 1625.7399999999998 USD` (Jan) | — | — |
| `open_ledger/example` | 18 cells, for example `3002.8899999999994`, `2966.3599999999997` | `855.8100000000001` | 4 cells, for example `357944.57999999996`, `6879.900000000001` |
| `open_ledger/crypto-example` | `198.23000000000002`, `-2998.6499999999996`, … | values with 7–10 decimals (`3965.5310305`, `9725.572332`) | `31649.319999999996`, `110272.95597070002` |
| `open_ledger/freelancer-invoicing` | clean | clean | `14450.000000000002` |

A scan of every other "Period data" table on the same ledgers (Balance Sheet, Income Statement and its views, Cash Flow page, Account pages) found no such noise. Their series are server decimals passed through. The long crypto decimals on Balance Sheet/Assets are exact source quantities, kept on purpose (w4/120).

## Root cause

- `income-expenses-chart.tsx:135–157`: `const net = income - expenses`, then `<Amount>{String(value)} {unit}</Amount>` for income, expenses and net.
- `distribution-data-table.tsx:57`: `{String(item.value)}`, where grouped rows ("Other") are client-side sums. Only the share column (`:66–67`) goes through `formatNum`.
- `cash-flow-sankey.tsx:196`: `{String(link.value)}` for flows that the chart builds by summing postings per link. The tooltip two blocks up (`:126`) uses `formatNum(Number(value))`.

## Fix

Render every amount cell in these three tables with the same formatter as its chart's tooltip (`formatNum`) at the unit's display precision, so the table says what the chart says in the reader's language. Where the table computes a value itself (Net), compute it from decimal strings (`common/lib/beancount/decimal-number.ts`), or round to the operands' precision before formatting. Don't change chart values, grouping, signs or unit selection.

Acceptance: budgeting-envelopes January reads `4,100.00 USD · 2,474.26 USD · 1,625.74 USD` (German: `4.100,00 … 1.625,74`). None of the cells listed above shows more digits than its unit's display precision. Rendered tests for each table feed a sum or difference with representation error (`4100 − 2474.26`, `0.1 + 0.2`) and fail against `String()`. Dashboard gates pass.

## Dedupe

w3/495 (done, 2026-10-16) introduced the three tables. Its resolution says values "come directly from each chart's final option data", which is why computed values carry float error into text. w3/494 (statement tables), w4/112 (account tables), w4/126 (tooltip precision) and w4/120 (lossless Statistics) are adjacent and don't cover these cells. This is a regression at HEAD, not deployment lag.

---

**Resolved 2026-10-17** — The Overview's three chart data tables (Income vs Expenses period data, the distribution Breakdown and Cash Flow Flows) now write every amount with the chart's own `formatNum(value, unit)`, at the unit's display precision and in the reader's language, instead of `String(number)`. A Net computed as `4100 − 2474.26` reads `1625.74 USD` rather than `1625.7399999999998 USD`. A grouped `0.1 + 0.2` row reads two decimals, and German reads `1625,74 EUR`, grouped as `1.625,74` when the ledger renders commas. Chart values, grouping, signs and unit selection are unchanged. The w3/495 suite had pinned `String()` output; it now derives its expectations from the same formatter, German included. New cases cover the computed Net, the grouped row and German formatting, and all three fail against the old tables. The live public ledgers were not re-checked after the change. Dashboard format, lint (including dead code), tests (5,870 passed, one skipped), build and a public-tree secret scan passed, shipped in `fa7b7fc8` (`dashboard`).
