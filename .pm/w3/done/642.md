# Saving Entry Context after the entry changed elsewhere says "The requested resource could not be found"

**Minor · dashboard (optionally backend-v2) · 25–35m · A2.** Live on the QA account's disposable synthetic ledger, 2026-10-17, local HEAD against the production API (reverted afterwards). Open the same transaction's Entry Context in two tabs. Save an edit in tab B (`UpdateLedgerEntrySourceSlice` succeeds and returns a new `entryHash`). Then save a different edit in tab A. Tab A's request returns `NOT_FOUND "Ledger resource not found"`, and the dialog shows the generic toast **"The requested resource could not be found."** The entry exists: it changed in tab B, so the hash tab A holds no longer matches. Tab A's draft stays in the editor, which is good, but the message tells the user their entry is gone and offers no way forward. The same happens after an MCP agent or the CLI edits that entry while the dialog is open.

Cause: Entry Context addresses the slice by the `entryHash` it loaded (`features/journal/components/entry-context-panel.tsx` → `UpdateLedgerEntrySourceSlice`). Any content change gives the entry a new hash, so the stale save can only be "not found". The panel passes the error to the shared mapper, which shows the generic not-found text. MCP agents were handled in w2/m26/t005: `editEntrySource` returns `newEntryHash` for chained edits. The dashboard's two-tab case wasn't covered.

Fix: in the Entry Context save handler, treat `NOT_FOUND` (and `CONFLICT`) from this mutation as "This entry was changed or removed since you opened it." Keep the draft visible with a **Copy my edit** action and a **Reload entry** action that refetches the journal and reopens the entry's latest version when it still exists. Optionally, have backend-v2 return `CONFLICT` when the hash is unknown but the request's `sha256sum` shows the file moved on, so other clients get the same distinction.

Acceptance: the two-tab sequence shows the changed-elsewhere message with Copy and Reload. Reload opens the tab-B version, and nothing is overwritten. A component test with a mocked `NOT_FOUND` asserts the message and that the draft survives. Dashboard gates pass.

Dedupe: searched `.pm/**` for stale hash, entry changed, concurrent edit and Entry Context conflict. w2/m26/t005 (done) fixed MCP's stale `entryHash`, w3/389 is the CLI import conflict, and w3/565 (open) covers discarding drafts on close. Nothing covers the dashboard save message.

---

**Resolved 2026-10-17** — A `NOT_FOUND` or `CONFLICT` from Entry Context's `UpdateLedgerEntrySourceSlice` save is now recognized as a stale entry: its hash changed because the entry was edited elsewhere. Instead of the generic not-found toast, the panel shows an inline notice: "This entry was changed or removed since you opened it, so your edit wasn't saved. Copy your edit, then reload to see the latest version." The draft stays in the editor. **Copy my edit** puts the attempted source on the clipboard. **Reload** clears the cache and closes the dialog through its success path, so the journal refreshes and the latest version can be reopened. Nothing is overwritten. Other save failures keep their toasts. Three new strings in all 15 journal locales (Chinese uses the informal 你, as the catalog rule requires). A dialog test with a mocked `NOT_FOUND` asserts the notice, no error toast, the draft still in the editor, Copy writing the draft, and Reload closing and refreshing. The original panel fails it. Not done: Reload does not find and open the other tab's new version directly (the panel cannot look an entry up by position), and backend-v2 still answers `NOT_FOUND`, not `CONFLICT`, for a moved-on file. The two-tab sequence was not run live. Dashboard format, lint (including dead code), tests (6,089 passed plus the translation suite after its fix), build and a public-tree secret scan passed, shipped in `ffd6c80b` (`dashboard`).
