# OAuth consent: keyboard focus on a ledger choice is invisible, because the radio is `sr-only` and its card has no focus style

**Severity:** minor (accessibility; WCAG 2.4.7 Focus Visible). **Estimate:** 25–40 minutes including a rendered focus test. **Owner:** `dashboard` (`features/oauth/pages/consent.tsx`; same pattern in `features/ledger-list/components/ledger-form.tsx`). **A1:** the consent page is where a user connects Claude, Codex or another MCP client to a ledger. A keyboard user tabbing into the ledger list sees nothing focused. The first Tab silently lands on an invisible 1px radio. They can't tell which ledger arrow keys or Space would pick, and that choice is the security-relevant part of the page.

## Reproduction

Local HEAD (`yarn dev`, pointed at the production API), signed in as a QA owner with three ledgers, headless Chromium 1440×1000, English/light. `/oauth/consent?uid=qa-bogus-uid&scope=ledger.read`. The bogus `uid` makes the requester "could not be identified", so **Approve access** stays disabled and nothing can be granted, but the ledger list renders exactly as it does for a real request. Nothing was submitted.

1. Click the page background, then press **Tab**.
2. Focus goes to `input[type=radio][value="<owner>/example"]`, which is 1px wide (`className="sr-only"`). The card around it (`label`) computes `outline: none`, `box-shadow: none`, an unchanged border colour and a transparent background, which is identical to the unfocused state. Nothing on screen indicates focus.
3. The next **Tab** goes to **Cancel**. The "All accessible ledgers" option, which uses a visible native radio, shows the browser focus ring when reached, so the two kinds of choice behave differently.

## Root cause

`consent.tsx:262–283`: each ledger is a `<label>` whose only state styling is `selected === ledger.fullName ? "border-primary bg-primary/5" : "… hover:bg-muted/50"`. The real control is `<input type="radio" className="sr-only">`, and no `focus-within`/`has-[:focus-visible]` style exists on the label. Selection styling appears only after a choice is made, so with nothing selected (the initial state) focus is entirely invisible.

`ledger-form.tsx:251–268` (the Create Ledger visibility cards) uses the same `sr-only` radio inside a styled label. One option is always selected there, so the group shows *a* highlighted card, but moving focus into or out of the group still produces no visible change.

## Fix

Give these cards a visible focus indicator driven by the hidden radio's keyboard focus. For example, add `has-[:focus-visible]:ring-2 has-[:focus-visible]:ring-ring has-[:focus-visible]:ring-offset-2` (or the equivalent `focus-within` variant already used by shared primitives) to each `label`. Keep it distinct from the selected style, so focused-but-unselected is visible too. Alternatively, use the shared Radix `RadioGroup` primitive, which already renders focus rings. Apply the same treatment to `ledger-form.tsx`.

Acceptance: Tab into the consent ledger list shows a visible ring on the first card before any selection. Arrow keys move the ring and the selection together. The ring disappears when focus leaves. Mouse click behavior is unchanged. A rendered test asserts the focus class or attribute on keyboard focus for both components. Dashboard gates pass.

## Dedupe

Searched `.pm/**` (including `done/`) for consent focus, `sr-only` radio and OAuth consent accessibility. Earlier consent work (w1/m30 "says who is asking", ADR 019 D4) covers requester disclosure, not focus. Accessibility milestones m23/m31/m39 cover dialogs, Entry Context and the sidebar. The radio markup in `consent.tsx` dates from the dashboard import (`af5339de`) and `d3445ed9`, so this is not deployment lag.

Unverified: mobile-consent and identity-consent pages (no radios found there), dark theme contrast of the proposed ring, and actual screen-reader output (the radios do have accessible names from their labels).

---

**Resolved 2026-10-17** — Both radio-card groups whose radio is `sr-only`, the OAuth consent ledger list and Create Ledger's template cards, now draw a focus ring on the card while its hidden radio has keyboard focus: `has-[:focus-visible]:ring-2 ring-ring ring-offset-2 ring-offset-background`. The ring is separate from the selected style, so a focused but unselected consent card is visible. Arrow keys move the ring with the selection. Pointer clicks do not trigger `:focus-visible`, so mouse behaviour is unchanged. The built CSS contains the generated `.has-[:focus-visible]:ring-2:has(:focus-visible)` rule and its colour and offset rules. jsdom cannot compute styles, so the rendered tests assert behaviour plus the class. On consent, Tab reaches the unselected "Personal" radio, which is `sr-only` and focused, and its card carries the focus class without the selected border. On Create Ledger, keyboard focus reaches the Sample template radio and its card carries the class. Restoring the original components fails both. No other `sr-only` radio cards exist in the dashboard. No live browser pass was made, and dark-theme ring contrast was not checked visually. Dashboard format, lint (including dead code), tests (5,826 passed, one skipped), build and a public-tree secret scan passed, shipped in `7611bd47` (`dashboard`).
