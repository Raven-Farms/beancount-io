# Let Version History reach commits older than the newest 30

**Severity:** major (a ledger's audit trail is truncated with no indication). **Estimate:** 40–55 minutes including a rendered paging test. **Owner:** `dashboard` (`features/git/commits/components/commits-split-view.tsx`, `commits-list.tsx`). **A2:** Version History is where a user checks who changed what and reverts a mistake. On any ledger with more than 30 commits, everything older is unreachable from the UI, and the list gives no sign that it was cut off.

## Live reproduction

Production `https://beancount.io`, 2026-10-15, local main `ce83f82b`. QA-owned headless Chromium, 1440×1000, en-US, authenticated owner. Read-only.

1. Open `/ledger/<owner>/<ledger>/commits` on a ledger with more than 30 commits. The route auto-selects the newest commit and lists exactly **30** entries.
2. Scroll the list's own scroll container (`aside … overflow-y-auto`) and the page to the bottom and wait. Still 30. There is no Load more / Older / page control, and no "showing 30 of N" text.
3. API control in the same session, the same `ListCommits` operation the page sends: `page: 1` → 30 commits, `page: 2` → 30 different, older commits, `page: 3` → 30 more. The backend pages correctly. Only the client never asks past page 1.
4. Deep link to a page-2 commit (`/commit/<sha>`): the detail ("Delete entry", Changes) renders, but no list item is selected or present, so the user can't tell where that commit sits or step to its neighbours.

Control: `/ledger/open_ledger/example/commits` has 13 commits, all listed. The cap only bites above 30.

## Root cause

`commits-split-view.tsx:39–46` queries `ListCommitsDocument` with a hard-coded `page: 1, limit: 30` and never requests another page. `commits-list.tsx` renders whatever it gets, with no paging affordance. The backend already supports paging (`backend-cluster/backend-v2/src/features/gitea/commits/service/commits-service.ts:148–153`, `limit = 30`), and it is exposed through GraphQL `listCommits(page, limit)`.

## Fix

Add a "Load older commits" button below the list. It fetches the next page (Apollo `fetchMore` with a merge keyed by `ledgerId`/`branch`) and appends to the list. Hide it once a page returns fewer than `limit` items. Keep focus on the button (or move it to the first newly loaded item) and announce the added count politely. When the selected `commitSha` is not in the loaded pages, either keep loading until it appears (bounded) or show a "Selected commit is older than the loaded history" row with the load control. Keep auto-selection of the newest commit, the narrow-screen history sheet, and the existing locales (new strings in all 15).

Acceptance: on a ledger with more than 30 commits, the user can reach the oldest commit by pressing the control repeatedly. The control disappears at the end. A deep-linked older commit is shown selected in the list or explicitly flagged. A rendered test with mocked pages (30, 30, 7) covers append, end-of-history, and the deep-link state. Dashboard gates pass.

## Dedupe

Searched `.pm/**` (including `done/` and `blocked/`) for commit list/commits page/listCommits, pagination, "load more", "older commits", and Version history. w3/m22 localized commit timestamps, w3/460 fixed feed push titles, and w4/051 concerned the file browser on ledger switch. None covers commit history paging. `git log -S"limit: 30"` shows the cap dates from the dashboard import (`af5339de`). It is not a regression.
