# Smart Import previews bank amount spellings as valid, then submits the raw cell text: `-1,234.56`, `(12.00)`, `$4.50` and `2.500,00` fail the whole import, and a comma-decimal `1.000` is written as one, not a thousand

**Severity:** major. It's a regression of the w0/007 journey, and in one path it writes a silently wrong amount. **Estimate:** 30–45 minutes including submit-path tests. **Owner:** `dashboard` (`features/importer/components/steps/configure/transaction-config-form.tsx`, possibly `utils/csv-validator.ts` to expose the normalized decimal). **A2:** w0/007 (`eb8bcd5f`, 2026-10-15) taught the CSV preview to accept real bank spellings, including thousands groups, accounting parentheses, currency symbols, a trailing minus and comma decimals. Its acceptance only checked the **preview**. Submission still sends the original cell text as the posting number. So the rows w0/007 set out to import (the largest rows of a bank export) still don't import, and the preview now promises they will.

## Reproduction (local HEAD)

Local HEAD (`yarn dev`, pointed at the production API), signed-in QA owner of a synthetic ledger, headless Chromium. Synthetic CSVs only. Steps 1–3 were not submitted. The live submits in steps 4–5 were made later on the QA account's disposable ledger and reverted.

1. `/ledger/<owner>/<ledger>/import`, upload a US-style file with rows `"-1,234.56"`, `(12.50)`, `$-4.75`. Preview: **7 Valid**. Configure displays `-1234.56`, `-12.5`, `-4.75`.
2. Upload an EU-amount file. **Correction (2026-10-17):** an earlier version of this step used a `;`-delimited file. That file never reaches the client parser: it falls through to AI `ParseFile` (w3/643), which returns plain numbers. The client comma-decimal path is reached with a comma-delimited file whose EU amounts are quoted (`qa-20261017-euquoted.csv`: `"-4,50"`, `-1.000`, `"2.500,00"`). `resolveDecimalConvention` resolves that column as comma-decimal, and Configure displays `-4.5`, `-1000`, `2500`. The preview rows themselves show a false "Amount must be a valid number" on the comma cells (w3/644).
3. What **Import** would send, computed with HEAD's own submit expression (`parseDecimalNumber(txn.amountInput) ?? txn.amountInput.trim()`) and `negateDecimalNumber` for the target leg:

| cell | preview amount | source posting sent | target posting sent |
| --- | --- | --- | --- |
| `-1,234.56` | -1234.56 | `-1,234.56` | `1,234.56` |
| `(12.50)` | -12.5 | `(12.50)` | `-(12.50)` |
| `$-4.75` | -4.75 | `$-4.75` | `-$-4.75` |
| `12.50-` | -12.5 | `12.50-` | `-12.50-` |
| `2.500,00` (comma column) | 2500 | `2.500,00` | `-2.500,00` |
| `-1.000` (comma column) | -1000 | **`-1.000`** | **`1.000`** |

4. Server side, **confirmed live 2026-10-17** (QA account's disposable synthetic ledger, local HEAD against the production API): importing a two-row US file sent `units.number` `"-1,234.56"`/`"1,234.56"` and `"(12.50)"`/`"-(12.50)"`. The server answered `SERVICE_UNAVAILABLE "Ledger API is temporarily unavailable"` twice in a row, and the Finish step said "Import Failed — The service is temporarily unavailable. Please try again shortly." Nothing was written. A one-row plain-decimal control (`-3.21`) through the same flow imported successfully. The ledger's `new BigNumber(number)` *throws* on these strings instead of returning NaN, so the refusal becomes a 5xx. That server-side half is filed as w3/641. Either way the whole atomic batch fails, and the user is told to retry something that will never succeed.
5. `-1.000` / `1.000`, however, **is** a plain decimal. In a batch where it's the only kind of row left, for example after the user deselects the comma-valued rows, it passes the balance check and is written as one unit instead of a thousand. **Confirmed live 2026-10-17** (same disposable ledger, reverted afterwards). In `qa-20261017-euquoted.csv`, rows 1 and 3 were deselected and row 2 (Configure: **-1000**) was imported with source `Assets:Bank:Checking` and target `Expenses:Food:Groceries`. The Finish step said "Successfully imported 1 transaction", and `main.bean` gained `Assets:Bank:Checking -1.000 USD` / `Expenses:Food:Groceries 1.000 USD`. That's a silent 1000× understatement, with no ledger error to flag it.

## Root cause

`transaction-config-form.tsx:182`: `amount: parseDecimalNumber(txn.amountInput) ?? txn.amountInput.trim()`. `amountInput` is the raw CSV token, kept deliberately so edits can be revalidated (`importer/AGENTS.md`: "Keep original amount tokens…"). `parseDecimalNumber` knows nothing of bank spellings or the column's `decimalComma`. It returns `null` for most of them, so the fallback sends the raw token, and it misreads `1.000` as a dot-decimal. w0/007 normalized these spellings inside `parseAmount`/`normalizeBankAmount` (`utils/csv-validator.ts:206–240`) but exposes only a JS `number`, and the submit path never used it. Inline edits (`editable-preview-row.tsx:83`) feed the same raw `amountInput`.

## Fix

Submit the normalized exact decimal that validation already computed. Have `parseAmount` (or a sibling) return the normalized decimal **string** from `normalizeBankAmount` together with its `decimalComma` decision, and use that string at `transaction-config-form.tsx:182`: `-1,234.56` → `-1234.56`, `(12.50)` → `-12.50`, `2.500,00` → `2500.00`, `-1.000` (comma column) → `-1000`. Keep `amountInput` as the editable token, and never fall back to sending it raw. If no normalized decimal exists, the row isn't valid and Configure must not accept it. Optionally map `UNBALANCED` to a localized message naming the row, so any future server refusal is actionable.

Acceptance: for both fixtures above, the `BulkEntries` variables carry `-1234.56`/`1234.56`, `-12.50`/`12.50`, `-4.75`/`4.75`, `-12.50`/`12.50`, `2500.00`/`-2500.00` and `-1000`/`1000`, keeping the trailing zeros the cell had. A test that drives preview → configure → submit with a mocked mutation fails against the current raw fallback. Plain-decimal files submit byte-identically to today. Dashboard gates pass.

## Dedupe

w0/007 (done, `eb8bcd5f`) is the precursor. Its acceptance and resolution cover preview only, and its fixture would fail at import exactly as above. w1/028 (`8c7c5508`) introduced the `parseDecimalNumber(amountInput) ?? raw` submit when only plain decimals could pass validation, so it was correct then and became unsafe when w0/007 widened the grammar. w3/m36 (lossy CSV conversions) and w3/m19 predate both. w3/558 (Balance form float round-trip) is a different form. No open item covers the import submit path, and this is current HEAD code, not deployment lag.

Unverified: OFX/QIF paths. The LLM-parser path doesn't carry bank spellings: `use-llm-parser.ts:54` stringifies a number, and live, a `;` file's `-1.000` came back and was written as `-1000`. The server refusal and the `-1.000` write are confirmed above.

**Resolved 2026-10-17** — Smart Import now writes the amount the preview validated. `parseAmount` returns `decimal`, the exact plain decimal it normalized from the bank spelling with the column's `decimalComma`, keeping the cell's digits. Configure carries it per row as `amountDecimal`, and submit writes only that; there is no fallback to the raw token. A preview → configure → `useImportSubmit` test over real `useCSVParser` output and a mocked mutation asserts the exact `BulkEntries` posting numbers. US file: `-1234.56`/`1234.56`, `-12.50`/`12.50`, `-4.75`/`4.75`, `-12.50`/`12.50`. Quoted comma-decimal file: `-4.50`/`4.50`, `-1000`/`1000`, `2500.00`/`-2500.00`. Plain decimals (`-3.21`, `0.00000001`) submit byte-identically. Restoring the old submit expression fails both bank-spelling cases and the plain-decimal control passes. The existing `parseAmount` tests now also pin `decimal` for every bank spelling, including comma-column `-1.000` → `-1000`. A token past the decimal helper's exponent bound is refused as unsupported precision rather than submitted. `importer/AGENTS.md` records that submit writes `decimal`, never the raw token. Not done: the optional `UNBALANCED` row message, and the server half (the ledger's `BigNumber` throw becoming a 5xx), which is w3/641. OFX/QIF paths were not exercised, and no hosted import was made. Dashboard format, lint (including dead code), tests (5,834 passed, one skipped), build, the agent-guidance check and a public-tree secret scan passed, shipped in `6ca64801` (`dashboard`).
