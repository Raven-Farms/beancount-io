# BQL results: a screen reader can reach only the ~20 rendered rows of a virtualized result, the scroll region has no explicit focus stop or name, and history actions sit inside `<summary>`

**Severity:** minor (accessibility; WCAG 1.3.1, 2.1.1, 4.1.2; axe `scrollable-region-focusable` and `nested-interactive`, both "serious"). **Estimate:** 40–60 minutes including tests. **Owner:** `dashboard` (`features/bql/components/query-result-card.tsx`). **A1/A2:** the Query page is where people check BQL answers. Results taller than 600px (`CONTAINER_HEIGHT`) render in a virtualized `react-window` list, so only the rows near the viewport exist in the DOM. A screen-reader user browsing the table meets its end after about 20 rows, although the table announces `aria-rowcount` of 59, and has no way to reach the rest. The scroll container also relies on the browser making scrollers focusable: it has no `tabIndex`, no accessible name, and an ARIA role (`rowgroup`) that isn't meant to be a focus stop.

## Reproduction

Local HEAD (`yarn dev`, pointed at the production API), signed in, headless Chromium 155, 1440×1000, public `open_ledger/example`. Read-only.

1. `/ledger/open_ledger/example/query?query=select account, sum(position) group by account` → **Execute Query**. "Rows: 58".
2. axe-core (WCAG 2.x A/AA) flags `scrollable-region-focusable` on `div[role="rowgroup"]` (`scrollHeight` 2146, `clientHeight` 600, `overflow-y: auto`, no `tabIndex`) and `nested-interactive` on each Query History `<summary>`. The other pages scanned the same way (Overview, Journal, Accounts, Balance Sheet, Import, Settings, Files, `/ledger`, account settings, login) had no serious or critical violations.
3. Keyboard in Chromium: Tab does reach the results, because Chromium and Firefox make scrollable containers focusable implicitly. The focus ring shows, and End scrolls to the last row. The focused element is an unnamed `role="rowgroup"`. WebKit/Safari doesn't make scrollers focusable, so there the region is skipped (not exercised here).
4. With the region scrolled to the top, the DOM holds **20** `role="row"` elements out of 58. A screen reader's table navigation stops there.
5. Each history card's `<summary>` contains **Download CSV** and **Delete query** buttons. They work (their wrapper stops propagation), but the disclosure's accessible name becomes "select account, sum(position) group by account Download CSV".

## Root cause

`query-result-card.tsx:226–250` renders `<List role="rowgroup" onKeyDown={trackEnd} … style={{ height: Math.min(rows × rowHeight, 600) }}>` with no `tabIndex` or label. The `End` pin in `trackEnd` (`:178–186`) shows keyboard scrolling was intended, but it depends on implicit scroller focus. Virtualization keeps unrendered rows out of the accessibility tree. The history actions live inside `<summary>` (`:313–345`).

## Fix

- Wrap the virtualized body in an explicit, named, focusable region (`role="region"`, `tabIndex={0}`, `aria-label` from the result table's label), as w0/014 did for statement tables in `hierarchy-list.tsx`. Leave the rows' ARIA roles to the table.
- Give screen readers the whole result: render all rows when the count is modest (for example ≤ 200, where virtualization buys little), and above that, offer a non-virtualized "All rows" table behind a disclosure or point to Download CSV.
- Move Download CSV/Delete query out of `<summary>` into a sibling toolbar, so the disclosure's name is the query alone.

Acceptance: for the 58-row result, all 58 rows are in the accessibility tree, and axe reports neither violation on the Query page. The results region is reachable by Tab in WebKit as well (explicit `tabIndex`), with a name. The history disclosure's name is the query text, and its two actions stay keyboard-operable. Tests cover the row count in the DOM and the region's focusability. Dashboard gates pass.
