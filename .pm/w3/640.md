# A dashboard write that breaks the ledger reports plain success: New Entry and Open Account say "created" while the write just introduced a bean-check error

**Severity:** minor. It's the missing safety net behind w3/557, w3/558 and w3/560. **Estimate:** 45–60 minutes for the dashboard check, plus about 30 minutes if GraphQL gains the field. **Owner:** `dashboard` (New Entry forms, Open Account dialog, CSV import submit), optionally `backend-cluster/backend-v2` (`AddLedgerEntryResponse` in `features/ledger/api/resolvers/ledger-entry-resolver.mutation.ts`). **A2:** the MCP `addLedgerEntries` tool tells an agent when its write broke the ledger: it returns `validation` with `errorsBefore`, `errorsAfter` and `newErrors` (`backend-v2/docs/mcp.md`, "learn about a broken ledger from the write result itself"). The dashboard's writes go through the same entry writer via GraphQL `bulkEntries`, which returns only `{success, message}`, so a human gets "Entry created successfully" or a silently closing dialog. Their ledger now fails validation, and nothing points them to the Errors page.

## Live reproduction

Local HEAD (`yarn dev`, pointed at the production API), signed-in QA owner, writing to the QA account's disposable synthetic ledger (2026-10-17; restored byte-for-byte afterwards).

1. `checkLedger` before: **0 errors**.
2. Accounts → **Open Account** → `Assets:Cash` (already open) → **Open Account**. `BulkEntries` returned `{"success":true,"message":"Added 1 entry successfully"}`, and the dialog closed with no message.
3. `checkLedger` after: **1 error**, `E1002 "Account Assets:Cash is already open (opened on 2026-01-01)"` at `main.bean:92`. The Accounts directory now lists `Assets:Cash` twice.
4. No toast, banner or badge on Accounts, Journal or the sidebar says the ledger now has an error. The user finds out only by opening Advanced → Errors.

**Second path, Entry Context edits (2026-10-17, same ledger):** opening a qa-prefixed transaction in Entry Context, changing `Assets:Bank:Checking -3.21 USD` to `-3.01 USD` and pressing **Save** sent `UpdateLedgerEntrySourceSlice`, which returned a new hash, and the dialog closed with **"Entry saved successfully"**. `checkLedger` then reported `E3001 "Transaction does not balance: residual 0.20 USD"` at `main.bean:95`. *Creating* the same unbalanced transaction through New Entry/`bulkEntries` is refused with `UNBALANCED`, so editing silently allows what creating refuses. MCP's `editEntrySource` runs the same slice write inside `withPostWriteValidation` (`ai-agent/api/mcp-source-slices.ts:73–86`) and reports the new error. GraphQL `UpdateSourceSliceResponse` (`ledger-journal-resolver.mutation.ts:70–85`) has no validation field. Apply the same warning to the Entry Context save, the file editor's save, and Create File.

**Third path, Smart Import (2026-10-17, same ledger, reverted).** A one-row comma CSV (`-3.21`) was imported with source `Assets:Bank:Checking`, target `Expenses:Food:Groceries` and the Configure **Currency** changed from `USD` to `EUR`. Both accounts are opened `USD`-only. Configure showed no warning, `BulkEntries` sent `units.currency: "EUR"` on both legs, and the Finish step said **"Import Successful! Successfully imported 1 transaction"**. `checkLedger` then reported two `E5002 "Invalid currency EUR not allowed in account …"` errors at `main.bean:89`. Configure could also prevent this before submit by flagging a currency outside the accounts' open-directive currencies on the Currency field. Today it can't, because it loads account names only (`GetLedgerAccounts` returns strings), so that would need the currencies exposed.

The same applies to every structured write the dashboard makes: New Entry (transaction, balance, note, account), Add Budget and CSV import submit. For example, a balance against an unopened account (w3/560) or an unbalanced-but-allowed write.

## Root cause

- MCP: `mcp-tools.ts:346–380` wraps `ledgerEntryService.addBulkEntries` in `withPostWriteValidation` (`ai-agent/tools/write-validation.ts:53`), diffing the ledger's errors before and after.
- GraphQL: `AddLedgerEntryResponse` has only `success` and `message` (`ledger-entry-resolver.mutation.ts:53–59`), and the resolver returns the service result unvalidated.
- REST `POST …/entries` keeps `{success, message}` deliberately ("the v1 contract stays `{success, message}`", `rest/v1/entries-handler.ts:239–241`). The text-append route (`…/directives/text`) and its GraphQL twin already return `newErrors`, and refuse new errors unless `allowInvalid`.

So the shared writer has one structured-write contract with three outcomes, and the dashboard is on the uninformed one.

## Fix

Dashboard (required): after any successful structured write, compare the ledger's error list before and after (the layout already queries `GetLedgerErrors`; refetch it). If the write introduced errors, show a persistent warning naming the first new error ("This entry left your ledger with 1 error: Account Assets:Cash is already open") with a link to Errors, instead of the success toast. Do the same for Open Account and CSV import results.

backend-v2 (recommended for parity): add an optional `validation { errorsBefore errorsAfter newErrors }` to `AddLedgerEntryResponse` and `UpdateSourceSliceResponse`, computed with the same `withPostWriteValidation` the MCP tool uses. It's additive, so the REST v1 shape can stay as decided, or gain the same optional field in a v1-compatible way. Run the parity gate.

Acceptance: repeating step 2 shows a warning naming the E1002 error with a link to Errors, and no success toast. A write that adds no errors still shows the success toast. A component test covers both paths (mocked before/after errors). If the GraphQL field is added, resolver tests and the parity gate cover it. Dashboard (and backend-v2) gates pass.
