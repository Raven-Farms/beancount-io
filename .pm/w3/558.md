# New Entry → Balance writes the asserted amount through a float: `49.70` becomes `49.7`, which loosens the check enough to pass a 5-cent mismatch

**Severity:** major. A reconciliation control silently passes a real discrepancy. **Estimate:** 20–30 minutes including a form-submission test. **Owner:** `dashboard` (`features/journal/components/new-directive-dialog/balance-form.tsx`). **A2:** the Balance tab is where a user records "my statement says 49.70." Beancount infers a balance assertion's tolerance from the digits written. The form re-serializes the number through a JavaScript double, which changes those digits and can change the outcome of the check.

## Reproduction

Production `https://beancount.io`, 2026-10-16, QA-owned headless Chromium, signed-in owner of a synthetic ledger. `/journal?action=new-entry&directive=balance` accepts `49.70`, `12.345678901`, `1e3` and `12345678901234567.89` with **Create Balance Entry** enabled. The form was **not submitted** on the hosted ledger. The serialization is deterministic client code, shown here with the exact expression the form runs:

```text
parseFloat("49.70").toString()                -> "49.7"
parseFloat("100.00").toString()               -> "100"
parseFloat("0.0000001").toString()            -> "1e-7"
parseFloat("12345678901234567.89").toString() -> "12345678901234568"
```

Consequence, verified offline with `bea check` (Beancount 3.2.3 engine) on a scratch ledger whose `Assets:Cash` holds **49.65 USD**:

- `balance Assets:Cash 49.70 USD` (what the user typed): `Balance failed … expected 49.70 USD != accumulated 49.65 USD (0.05 too little)`. Correct.
- `balance Assets:Cash 49.7 USD` (what the form writes): **no errors**. The 5-cent discrepancy passes, because one decimal digit gives a 0.1 tolerance.
- Exponent spellings (`1e-7`) are **not** a ledger-text problem: the ledger's `toBeancountNumber` (`backend-cluster/ledger/src/foundation/rustledger/entry-build.ts:46–51`, `BigNumber#toFixed`) expands them before writing. It cannot restore digits the browser already dropped. A trailing zero, or anything past a double's ~16 significant digits, is gone before the request is sent.

**Confirmed end to end on the hosted ledger (2026-10-17, QA account's disposable synthetic ledger, reverted afterwards).** At local HEAD (`yarn dev`, pointed at the production API), New Entry → Balance with `Assets:Cash`, `08/30/2026`, typed `49.70` sent `BulkEntries … "amount":{"number":"49.7","currency":"USD"}`. The commit wrote `2026-08-30 balance Assets:Cash 49.7 USD`. The account's actual balance was **49.75 USD**, and `checkLedger` returned **zero errors**: the assertion the user typed would have failed by 0.05, but the one written passes.

## Root cause

`balance-form.tsx:86–91`: `const amountNumber = parseFloat(data.amount); … number: amountNumber.toString()`. The schema at `:45–51` validates with `parseFloat` too, so `1e3` and other float-only spellings pass validation. This is the same defect class that w1/028 fixed in `8c7c5508` ("submit typed amounts as exact decimal strings"), but that change covered New Transaction, receipt import and CSV import, and the Balance form was not one of its call sites. The other write paths in `features/` already use `common/lib/beancount/decimal-number.ts` (`parseDecimalNumber`): `transaction-form.tsx:92,219`, `use-receipt-workflow.ts:54`, `transaction-config-form.tsx:182`.

## Fix

Validate the Balance amount with `parseDecimalNumber(val) !== null` and submit `parseDecimalNumber(data.amount)`, exactly as `transaction-form.tsx` does. That keeps the typed digits, including trailing zeros. No API change.

Acceptance: submitting `49.70` sends `number: "49.70"`. `0.00000001` sends `"0.00000001"`, `12345678901234567.89` is sent unchanged, and `1e3` is either rejected with the existing "must be a number" message or sent as `"1000"`, consistent with the Transaction form. A form-submission test (alongside `amount-step-precision.test.tsx`) asserts the mutation variables for these inputs and fails against `parseFloat`. Dashboard gates pass.

## Dedupe

Searched `.pm/**` (including `done/`) for `parseFloat`, balance form, trailing zero, exponent and precision terms. w1/028 is the closed precursor and did not name `balance-form.tsx`. w4/141 is a test flake in `amount-step-precision`. w3/498 is New Entry field labels. w3/116 and w3/189 are display precision. `grep parseFloat dashboard/src/features` at HEAD finds only this call site among write paths, so it is a residual of w1/028, not deployment lag.

Unverified: the hosted write itself (deliberately not submitted). The ledger's `toBeancountNumber` returns an ordinary decimal such as `"49.70"` verbatim (`entry-build.ts:47–48`), and only exponent forms pass through BigNumber. So a client-only fix is sufficient.
