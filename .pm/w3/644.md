# Smart Import preview flags valid comma-decimal amounts (`"-4,50"`, `"2.500,00"`) as "Amount must be a valid number" while its badge counts them valid

**Severity:** minor. **Estimate:** 20–30 minutes including a rendered preview test. **Owner:** `dashboard` (`features/importer/utils/row-edit-schema.ts`, `components/steps/preview/editable-preview-row.tsx`). **A2:** w0/007 taught the CSV parser to resolve an amount column's decimal mark from every cell, so a European file's `-4,50` and `2.500,00` parse as −4.50 and 2500. The preview's inline row validation was never given that column decision. It re-checks each cell as a dot-decimal and paints every comma-decimal row red with "Amount must be a valid number". Meanwhile the badge above says the rows are valid, and Continue carries them into Configure with the right amounts. A user who trusts the red rows deletes or retypes their EU amounts, and one who trusts the badge can't tell which of the two is wrong.

## Live reproduction

Local HEAD (`yarn dev`, pointed at the production API), QA owner, its disposable synthetic ledger, 2026-10-17, headless Chromium, en. File `qa-20261017-euquoted.csv` (comma-delimited, EU amounts quoted; a `;` file instead goes to AI parsing, w3/643):

```text
Date,Payee,Description,Amount
2026-09-05,qa-20261017-q-comma,qa-20261017 quoted comma,"-4,50"
2026-09-06,qa-20261017-q-thousand,qa-20261017 quoted thousand,-1.000
2026-09-07,qa-20261017-q-grouped,qa-20261017 quoted grouped,"2.500,00"
```

1. `/ledger/<owner>/<ledger>/import` → Browse files → the file. No server parse is made.
2. The preview header reads **"3 Valid"**. Rows 1 and 3 render on the destructive background, each showing `amount: Amount must be a valid number` under the raw cell (`-4,50`, `2.500,00`). Row 2 shows the raw `-1.000` with no hint that it was read as a thousand.
3. **Continue to Configure** is enabled, and Configure lists the same rows as `-4.5`, `-1000`, `2500`: the parser's values, not the preview's errors.

With HEAD's own functions, `resolveDecimalConvention(["-4,50","-1.000","2.500,00"])` returns `{decimalComma: true}`, and `parseAmount(cell, {decimalComma: true})` is valid for all three. `parseAmount(cell)` with no options rejects `-4,50` and `2.500,00`.

## Root cause

`utils/row-edit-schema.ts:42`: the amount rule calls `parseAmount(val)` with no `decimalComma`, and `editable-preview-row.tsx:38` resolves the row form with that schema, triggering it on mount (`:57–59`) so parser-accepted rows display its errors. Every other check passes the row's convention: the row's own rebuild on edit (`editable-preview-row.tsx:85`), Configure's `getValidImportRows` (`lib/import-config-draft.ts:47`), and the parser (`hooks/use-csv-parser.ts:222`). The badge counts `row.errors` from the parser (`import-preview-table.tsx:51`), so the badge and the inline messages disagree.

## Fix

Validate the inline amount with the row's column convention: build the resolver per row (for example `createEditableRowSchema({ decimalComma: row.decimalComma })`) or validate the amount in a `superRefine` that receives it, so the form and `buildParsedRow` share one rule. Then show the amount in the preview as the normalized value (`-4.50`, `-1000`, `2500.00`) next to or instead of the raw token, so the decimal reading is visible before Configure. Keep the raw token as the editable value.

Acceptance: the fixture above previews **3 Valid** with no inline error, and shows each row's normalized amount. In a dot-decimal file `-4,50` still gets "Amount must be a valid number". A mixed column still gets the mixed-convention error. A rendered preview test covers a comma-decimal column, and editing a comma cell to another comma value stays valid. Dashboard gates pass.
