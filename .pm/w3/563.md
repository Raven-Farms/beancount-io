# Upload Files stages a file whose name already exists (or the same file twice), then half-commits the batch and reports only "Failed to upload files"

**Severity:** minor. It leaves a partially applied upload with no indication of what landed. **Estimate:** 45–60 minutes including component tests. **Owner:** `dashboard` (`features/ledger-editor/upload-files/index.tsx`, its locales). **A2:** uploading existing Beancount files is how a newcomer moves their books in. A batch that includes a name already in the folder (very likely `main.bean`) is accepted with no warning. The upload then commits every file before the clash, stops at the clash, never attempts the rest, and shows one generic toast. The user can't tell which files are now in the repository, and retrying the same selection fails again on the first file it already created.

## Reproduction

Local HEAD (`yarn dev`, pointed at the production API), signed-in owner of a synthetic ledger whose root holds `main.bean`, headless Chromium 1440×1000. **Nothing was uploaded.**

1. `/ledger/<owner>/<ledger>/files/upload/main`. **Choose your files** → `main.bean`, `qa-20261016-1048576.bean`, `qa-20261016 späce é.bean` (synthetic fixtures).
2. The list shows each file with its size. `main.bean` carries no "already exists" note, and **Upload Files** is enabled once oversized files are removed.
3. Choose the same files again. "Selected files (8)" now lists every file twice, and nothing dedupes them.

What submission does, from source (deliberately not exercised on a real ledger):

- `handleUpload` (`index.tsx:110–160`) loops `for (const file of selectedFiles)` and awaits `CreateLedgerFile` for each path in turn.
- backend-v2 `createLedgerFile` → ledger `POST /ledgers/{o}/{r}/files` (`backend-cluster/ledger/src/api/files.ts:143–170`) → Gitea `repoCreateFile`, which refuses an existing path (HTTP 422 "repository file already exists").
- The first refusal throws out of the loop. Files earlier in the list are already committed, one commit each, and files after it are never sent. The `catch` shows `ledgerEditor.failedToUploadFiles` ("Failed to upload files") with no file name or reason, and the selection stays as it was, so a retry re-sends the already-created files and fails on the first one.
- A file picked twice fails the same way on its second copy, after its first copy was committed.

## Root cause

Selections are appended without identity checks: `setSelectedFiles((prev) => [...prev, ...chosen])` at `:174` (picker) and `:203` (drop). There's no comparison against the target folder's existing names, although the page already loads `GetLedgerDirContent` for that folder. The sequential, non-atomic loop and its single generic catch hide which file failed and why.

## Fix

- Dedupe the staged list by name: a re-picked file with the same name replaces its earlier entry.
- Compare staged names against the folder listing. Mark clashing files inline ("main.bean already exists in this folder"), keep **Upload Files** disabled while any clash remains, and offer Remove. Overwriting is a separate, explicit action (Edit) and out of scope.
- On failure, name the file and the reason, report which files were uploaded, and drop those from the staged list, so a retry sends only what's left. Ideally use one commit for the batch if a multi-file write exists. Otherwise keep per-file commits but report progress honestly.

Acceptance: staging `main.bean` into a folder that has it shows the inline clash and disables upload. Choosing a file twice keeps one row. A mocked mid-batch server failure shows the failing name, removes the files that were created from the list, and a retry uploads only the rest. Component tests cover all three. Dashboard gates pass.
