# A brief API outage signs the user out in the UI: a 502 on `GetCurrentUser` sends a signed-in user from Settings or the ledger list to "Sign in", and ledger pages swap the user menu for "Log In / Sign Up"

**Severity:** minor. **Estimate:** 30–45 minutes including route tests. **Owner:** `dashboard` (`common/server-fn/user.ts` `fetchUserProfile`, `routes/__root.tsx` `beforeLoad`, `common/lib/auth/auth.ts` `requireAuth`). **A2/A3:** gateway blips happen (deploys, Cloudflare 502s, a phone switching networks). When one does, the dashboard tells a signed-in person they are signed out and shows the password form. They then retype credentials during the outage and get a second, different error, or assume their session or password broke. The truthful state is "can't reach Beancount.io right now", with a retry that keeps them where they were.

## Live reproduction

Local HEAD (`yarn dev`, pointed at the production API), signed-in QA owner, headless Chromium, 2026-10-17.

1. **Live, unplanned.** At 23:51:57 UTC production answered `GetCurrentUser` with Cloudflare `502 Bad gateway` (`retry-after: 60`). Navigating to `/settings/general` and `/settings/danger-zone` both landed on `/auth/login?next=%2Fsettings%2F…` with "Welcome back — Sign in to your Beancount account". A ledger page loaded during an earlier blip (SSR `GetCurrentUser ✗`) showed **Log In / Sign Up** in the header while rendering the owner's ledger. Seconds later, with the API back, the same session opened `/settings/general` normally, and `/auth/login?next=…` forwarded straight back. The session had never been invalid.
2. **Deterministic control.** On `/ledger/<owner>/<ledger>/journal`, the browser was made to answer only `GetCurrentUser` with a 502 (a synthetic response, used only to repeat the live state). Clicking **Go to dashboard** went to `/auth/login?next=%2Fledger`. Removing the stub and reloading returned to the signed-in dashboard.

## Root cause

`common/server-fn/user.ts:13–21` `fetchUserProfile` returns `null` from a bare `catch`, so a transport or 5xx failure is indistinguishable from "no session". `routes/__root.tsx:65–75` puts that `null` into `context.userProfile`. `requireAuth` (`common/lib/auth/auth.ts`, used by `routes/settings.tsx`, `ledger.index.tsx`, `ledger-gallery.tsx` and `ledger.0.income_statement.tsx`) then redirects to `/auth/login`, and the ledger header's `<Authenticated fallback>` (`common/components/ledger-layout/layout-header.tsx:138–145`) renders the sign-in button.

## Fix

Make the profile fetch return three states: `{ status: "signed-in", profile }`, `{ status: "signed-out" }` (no session, or an `UNAUTHENTICATED` error), and `{ status: "unavailable", error }` (network failure, 5xx, timeout). Only `signed-out` may redirect to login or show **Log In / Sign Up**. On `unavailable`, protected routes render the existing error page with the service-unavailable copy (`getErrorMessageKey`) and a **Try again** that re-runs the route, keeping the URL. The header shows neither the user menu nor the sign-in button until the profile resolves. Keep the open-redirect checks in `requireAuth` unchanged.

Acceptance: with `GetCurrentUser` answering 502 or failing at the network level, `/settings/general`, `/ledger` and `/ledger-gallery` stay on their URL and show a retryable service-unavailable state. A ledger page shows no **Log In / Sign Up**. After the API recovers, **Try again** shows the signed-in page without re-entering credentials. A genuine signed-out visitor is still redirected with the same safe `next`. Route tests cover all three states, for SSR and client navigation. Dashboard gates pass.
