# Creating a pull request fails on every surface with an opaque "Gitea 500", so an agent's proposed change can never reach the dashboard's review page

**Severity:** major. **Estimate:** 45–90 minutes. The cause is unverified, and the first step is reading the server logs for one failing call. **Owner:** `backend-cluster/backend-v2` (`features/gitea/pull-request/service/pull-request-service.ts` `createPRFromPatch`, and the user Gitea client it uses). The dashboard consumer is `dashboard/src/features/git/pull-requests/pages/pr-review-page.tsx`. **A2/A3:** pull requests are how an MCP agent or API client proposes a ledger change for a person to review. The MCP tool `managePullRequests` (create → approve/reject), REST `POST …/pull-requests`, and GraphQL `createPullRequestFromPatch` all advertise it, and the dashboard's `/ledger/<owner>/<ledger>/pull/<n>` page exists to review the result. On production every create fails, so none of that journey can start.

## Live reproduction

Production API `https://beancount.io/api-gateway/`, 2026-10-17 23:47–23:54 UTC. QA owner signed in (session cookie), its disposable synthetic ledger, which has never had a pull request (`getPullRequestDetails` 1–8 → `NOT_FOUND`). Each call was made once, at human pace, with synthetic `qa-20261017` content:

| surface | change | result |
| --- | --- | --- |
| GraphQL `createPullRequestFromPatch` | edit `main.bean` (append a balanced or unbalanced `qa-20261017` transaction), 3 calls | `success: false`, `"Failed to create PR: Failed to create PR from patch: Gitea 500"` |
| MCP `managePullRequests` `create` | new file `qa-20261017-pr-note.txt` | `INTERNAL_SERVER_ERROR "Internal server error"`, hint "Retry once…" |
| REST `POST /api-gateway/v1/ledgers/<owner>/<ledger>/pull-requests` | same new file, after a 20 s pause | HTTP 200, `{"success":false,"message":"…Gitea 500"}` |
| REST, `fastForward: true` | same | same `Gitea 500` |
| REST, `baseBranch: "qa-20261017-no-such-branch"` (control) | same | HTTP 404 `NOT_FOUND "Branch … not found"`, the correct refusal |
| REST, retried at 23:54 UTC, after a separate 502 blip on the gateway at 23:51 had cleared | same | same `Gitea 500` |

Plain ledger writes on the same ledger in the same session succeed (`createLedgerFile`, `updateLedgerFile`). Those go through the ledger service, not the per-user Gitea API client.

## What the evidence narrows

- Step 2 of `createPRFromPatch` (`repoGetBranch` on the base) works: the unknown-branch control is refused correctly, and an existing base passes it.
- The step-5 diff check (`repoCompareDiff`) is not the cause: `fastForward: true` skips it and still fails.
- So the 500 comes from step 3 (`repoCreateBranch`), step 4 (`repoGetContents`/`repoCreateFile`/`repoUpdateFile` on the head branch), or step 6 (`repoCreatePullRequest`). Those are the only repository **writes** made with the per-user Gitea API client (`giteaClientFactory.getUserApiClient`). Its reads work (`getPullRequestDetails` answers Gitea's 404 as `NOT_FOUND`). The Gitea response carried no `message`, so `describeClientFailure` reports only the status. **Cause unverified.** Plausible candidates: the user token's write scope or repository permission, Gitea commit identity (the ledger history's author is `<owner>@noreply.localhost`), or a Gitea version/API mismatch on branch creation (`old_ref_name`).
- Whether a `pr-patch-*` branch was left behind can't be observed: no surface lists branches, and the w5/053 cleanup deletes the branch on failure as best effort.

Unverified: other accounts and ledgers (the authorization covers only this ledger), approve/reject (no pull request could be created), and the dashboard `/pull/<n>` rendering with real data.

## Fix

1. Reproduce one create against production with backend-v2 logging the failing Gitea call (operation name, status and response body) to find the step. Then fix the cause: for example, issue the user client a token with repository write scope, or make the call match the deployed Gitea's API.
2. Make the failure diagnosable. `describeClientFailure` should name the failed step ("creating branch", "writing main.bean", "opening the pull request") and keep Gitea's body when it isn't JSON. The surfaces should say whether retrying can help: a server-side 5xx is `SERVICE_UNAVAILABLE`/`INTERNAL_SERVER_ERROR` with that step named. Keep the documented REST/GraphQL `success:false` contract for repository refusals, and keep REST, GraphQL and MCP in parity.
3. Add a backend-v2 contract test where the mocked Gitea client returns a 500 with a text body at each step, asserting the step-named message on all three surfaces.

Acceptance: on production, MCP `managePullRequests create` with a one-file change on a disposable ledger returns a `prNumber`. `/ledger/<owner>/<ledger>/pull/<n>` shows its files and diff. **Reject** closes it and **Approve** on a second PR merges it, with the change visible in the Journal. A forced Gitea failure names its step on all three surfaces. Backend-v2 gates pass.

Searched `.pm/**` for `Gitea 500`, `createPullRequestFromPatch`, `managePullRequests`, `pr-patch` and `pull request` + create/500: no open item. Backend-v2 has no newer PR-service commit, so this isn't deployment lag of a fix.
