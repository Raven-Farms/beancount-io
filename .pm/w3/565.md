# Entry Context discards an edited entry without asking: Close, Escape, an outside click, or "Open source" all drop the draft

**Severity:** minor. **Estimate:** 35–50 minutes including dialog tests. **Owner:** `dashboard` (`features/journal/components/entry-context-dialog.tsx`, `entry-context-panel.tsx`). **A2:** Entry Context is the quickest way to fix an entry from the Journal or Overview. Its editor even flags edits with "Source has been modified", yet every way out of the dialog throws the edit away silently. The file editor and Create File already protect drafts (m29, w3/197, `file-edit-mode.tsx` / `create-file/index.tsx` use unsaved-change guards), so the same user gets two different contracts for the same kind of text.

## Reproduction

Local HEAD (`yarn dev`, pointed at the production API), signed-in owner of a synthetic ledger, headless Chromium 1440×1000. **Nothing was saved.**

1. `/ledger/<owner>/<ledger>/journal` → click the first transaction row. **Entry Context** opens with an editable source and **Save** disabled.
2. Type in the editor (for example, append ` ; qa draft`). "Source has been modified" appears and **Save** is enabled.
3. Any one of these closes the dialog at once, with no confirmation, and the edit is gone when the row is reopened:
   - **Close**
   - **Escape**
   - a click outside the dialog
   - **Open source at main.bean:83**, which also navigates to `/files/blob/main/main.bean?editMode=true&lineNumber=83` showing the *unmodified* file, so the draft isn't carried over either.
4. Each exit was repeated on a fresh open, with the same result.

## Root cause

`entry-context-dialog.tsx:167` passes `onOpenChange` straight to the Radix `Dialog`, and the source-link handler (`:208`) calls `onOpenChange(false)` before navigating. The panel tracks `hasChanges` (`entry-context-panel.tsx:363`) only to show the amber notice. Nothing consults it on dismiss.

## Fix

When `hasChanges` is true, intercept dismissal (Close, Escape via `onEscapeKeyDown`, outside interaction via `onInteractOutside`, and the source link). Show the same discard-confirmation pattern the file editor uses: Keep editing / Discard. For the source link, either confirm first or carry the draft into the file editor. With no changes, every exit stays instant. Focus restoration (`restoreFocusOnDialogClose`) must still work after Discard.

Acceptance: with an edit, each of the four exits asks to discard. Keep editing returns to the editor with the text intact, and Discard closes as today. Without an edit, all exits close immediately. Dialog tests cover each exit in both states. Dashboard gates pass.

## Dedupe

Searched `.pm/**` (including `done/`) for Entry Context draft/unsaved/discard terms. m29 and w3/197 cover the **file** editor's drafts, and m23/m31 cover Entry Context focus and keyboard. None covers Entry Context dismissal with edits. This is current HEAD behavior.

Unverified: the Overview's Recent activity entry point (same dialog component); 390px layout; whether browser back while the dialog is open also discards (likely, via route change).
