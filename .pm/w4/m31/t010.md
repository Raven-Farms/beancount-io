## Objective

Let an account owner use authentication email already delivered to reach the same ownership-verified password sign-in lane when the shared mailbox delivery budget is exhausted. Preserve reset behavior, neutral queued responses, mailbox cooldown/cap, single-use action-bound proof, global source limits and the correct-password requirement. A sender who cannot read the mailbox must not be able to starve every ownership proof by choosing reset requests instead of sign-in recovery requests.

## Context

- Triage of m31 reproduced five accepted reset deliveries at one-minute intervals followed by suppressed sign-in recovery delivery. The reset emails contain no sign-in ownership challenge, so an attacker can occupy the shared mailbox cap while maintaining the ordinary password limits.
- The reproduction executes the real mail service and delivery policy with synthetic infrastructure; no production traffic or account is used.
- This closes a cross-action gap in the user-requested account-recovery design. Signup disclosure stays unchanged.

## Steps

1. Add a regression that demonstrates the shared-delivery starvation case.
2. Reuse already delivered mail for a bounded ownership-verified password continuation; do not raise delivery quotas or send mail automatically after password failures.
3. Verify retry, expiry, consumption, reset and response-privacy behavior; run backend gates, close through /pm and ship.

## Acceptance criteria

- [ ] After reset deliveries fill the shared mailbox cap, the owner can complete password sign-in from an already delivered email while ordinary password quotas are exhausted.
- [ ] Wrong passwords, substituted accounts, expired/replayed proofs and Redis outages cannot mint sessions; retry never resurrects consumed proof.
- [ ] Password reset and all existing delivery quotas/neutral responses remain intact; no new dependencies or signup-disclosure change.
