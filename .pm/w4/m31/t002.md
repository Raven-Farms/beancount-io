## Objective

Move signup and reset throttles to shared Redis without changing signup disclosure. Give reset/verification email delivery a 60-second cooldown and five-per-hour account cap, independent IP request budgets, and a durable asynchronous queue so account lookup, token generation and email failures do not alter the reset response. Keep valid tokens on suppressed requests. Add separately bounded OTP verification and short-lived, single-use email ownership proof that permits a small recovery password attempt without clearing IP or request-volume budgets. Never send recovery mail automatically for a password failure; the user requests it. Use existing dependencies.

## Context

- User-approved multi-dimensional rate-limit proposal in this conversation, 2026-10-19.
- Signup account-existence disclosure is an explicit product decision and must remain.

## Acceptance criteria

- [ ] All reset requests follow the same enqueue/response path before account lookup; provider delays/outages cannot distinguish account existence.
- [ ] Queued recovery work survives a backend process restart and concurrent workers do not double-claim it; bounded retries and cleanup exist.
- [ ] The same mailbox cooldown/account cap applies across replacement sessions; existing signup conflict semantics remain unchanged.
- [ ] Recovery proof is single-use, expires, is account/action-bound, and still requires a correct password; all new anonymous ceremonies have explicit protocol exceptions.

## Out of scope

- Changing signup disclosure, adding dependencies, requiring CAPTCHA/MFA for ordinary login, or changing production configuration.
