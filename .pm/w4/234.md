# Execute BQL again against the current ledger instead of returning Apollo's cached result

**Severity:** major. **Estimate:** 30–45 minutes, dashboard. **A1/A2:** a user checking an agent's or another editor's ledger change must receive current facts when explicitly executing a query again.

## Reproduce

Production `https://beancount.io`, 2026-10-20, headless isolated QA-owned Chromium 155.0.8059.85, English/light, synthetic-ledger owner. Local main `c5e4cd11a`; production `main-D9qWGMxD.js`, full deployed SHA unverified. No response substitution. A temporary prefixed Open directive was written through the real API outside Apollo's UI cache to represent another editor's commit; exact file restoration followed.

1. Fresh-load `/ledger/<qa-owner>/<synthetic-ledger>/query?query=select+count%28*%29+from+accounts`. The result is **12**.
2. In the same ledger, append `2026-10-01 open Expenses:Qa-20261020-Count USD` using another editor/client. The real file write succeeds, and an independent `queryShell` POST for the identical query returns HTTP 200, `table.rows:[[13]]`, with no ledger errors.
3. Keep the existing Query page open and click **Execute Query**. It settles immediately with **12**, and sends **zero QueryShell requests**. This is an explicit new execution, not merely an old history card being left open.
4. Reload: **13** now appears. Restore the original file externally and repeat at 390×844. Execute still shows **13**, sends zero QueryShell requests, and the independent identical query returns **12**. A further full reload shows **12**.

The first changed-ledger reproduction used 1440×1000; the reverse-change reproduction starts from the freshly reloaded 13 result. A five-row ordinary SELECT and its CSV download independently matched exactly before this probe. Fixture setup also added temporary budget directives for w4/235; those contain no Open directives and do not contribute to the accounts count. All temporary directives were removed by byte-exact snapshot restoration, verified SHA-256 and a clean ledger check.

## Cause and bounded repair

`dashboard/src/features/bql/pages/index.tsx:61–65` creates `useLazyQuery(QueryShellDocument)` without a fetch policy. `executeQueryAndCache` at lines 104–110 invokes it again with identical variables; `common/apollo/factory.client.ts:14–25` has no policy override. Installed Apollo's `core/ObservableQuery.js:74` defaults to `cache-first`; `react/hooks/useLazyQuery.js:103–117` reobserves with that policy. Thus explicit execution resolves from normalized query cache and the page stores the stale response in `resultsCache` again.

Configure the lazy query's hook-level execution policy to obtain a fresh server result for an explicit run, using the installed Apollo API. Preserve the separate per-query history/result presentation cache, editor/URL state, retained in-flight requests, error handling and prior-ledger response guard. The same submitter serves the Execute button and Monaco Cmd/Ctrl+Enter; history execution also calls `executeQueryAndCache`. Those are searched callers; only the button and bookmarked reload were exercised here. Do not globally change every Apollo query's policy or reset the whole app cache just to execute BQL.

Acceptance: use the real Apollo client/cache with a controlled transport whose response changes after the first result; submit the **same** query again and assert a second request and the new value. Cover the actual button and shortcut, network failure after a previously successful result, loading/settled export coherence, history execution and ledger switching without duplicate URL-triggered runs. Repeat the 12 → 13 → 12 live synthetic control. No API/REST/MCP behavior change is required; direct GraphQL reads are already correct. Run dashboard format/lint/test/build when implementing.
