# Preserve acknowledged file writes when folder refresh fails

**Severity:** minor. **Estimate:** 45–60 minutes across the two file-creation callers, dashboard. **A2:** recovery from a folder-refresh failure should not treat an already committed file as unwritten or retry creating it.

Production `https://beancount.io`, 2026-10-20, English/System theme, QA-owned headless isolated Chromium 155.0.8059.85, designated disposable synthetic ledger owner. Fresh 1440×1000 and 390×844 pages. Local main `c5e4cd11a`; deployed UploadFilesPage exactly matches local source. The failure below is deliberately injected into one browser read, not a claimed production outage.

## Reproduce

1. Open `/ledger/<qa-owner>/<synthetic-ledger>/files/upload/main` with neither test file present. Stage `qa-20261020-upload-refetch-a.txt` and `qa-20261020-upload-refetch-b.txt`, each containing its prefixed 29-byte text fixture.
2. Upload. Let the first real CreateLedgerFile complete unchanged, but abort its following GetLedgerDirContent refetch inside the owned browser.
3. The alert says **“qa-20261020-upload-refetch-a.txt wasn't uploaded: Connection problem. Please check your internet connection and try again.”** Both A and B remain staged and Upload Files is enabled. B has never been attempted.
4. Independent reads prove A is stored with its exact bytes, blob `94258c6dc39e177fe7d1c42749d98ba59c7b2739`, desktop commit `8e063e81976e4e22607df6b6d7b5831b6bcc6060`; directory contains main.bean and A, not B. The mutation response was HTTP 200 with successful data before the read failure.
5. Remove the interception and retry Upload Files. It resends A. GraphQL returns `BAD_USER_INPUT`, `repository file already exists [path: qa-20261020-upload-refetch-a.txt]`. The UI now says A wasn't uploaded because **“Some of the information provided is invalid. Please check and try again.”** Both files remain staged; retry is still enabled and B still is not attempted.
6. Fresh-repeat at 390px: the first successful upload followed by the aborted folder read produces the same false failure and two staged files. A is independently present in commit `253a5d879734f1b319da46be08bf23460e454f26`, while B is absent. Retry was independently exercised on desktop.

Working recovery control: manually Remove A from the desktop staged list, then Upload Files. Only B is created, with exact bytes and zero ledger errors (commit `18ebef12bc488ff439dcfc69eeabf7f454d1c9be`). Existing-name preflight and ordinary successful upload controls remain separate passing coverage. No duplicate file is actually written.

## Cause and bounded repair

`dashboard/src/features/ledger-editor/upload-files/index.tsx:163–179` awaits CreateLedgerFile with directory refetch and `awaitRefetchQueries:true`. The catch at `:181–194` consequently treats a failed read after an acknowledged write as a failed creation. Only after that combined promise succeeds do `:197–198` record the uploaded name and remove its File object. The stale folder cache still lacks A, so preflight permits its next creation attempt.

This is the installed Apollo behaviour: `node_modules/@apollo/client/core/QueryInfo.js:348–352` joins refetch results with `Promise.all` before resolving the mutation promise. Mutation failure and post-write refresh failure need distinct bookkeeping here.

Record each acknowledged creation and remove that exact staged File before optional folder refresh can fail. Report a refresh problem truthfully, retain only files whose creation has not succeeded for retry, and never automatically overwrite an existing path. Preserve ordering, one commit per file, safe existing-name checks, re-pick deduplication, size/permission guards, removal controls and real pre-write failure recovery. The searched dashboard callers using `awaitRefetchQueries:true` are UploadFilesPage and CreateFilePage; the independently reproduced second caller is detailed below. Their canonical branch/path routes and directory actions reach these implementations; nested folders remain source-derived scope. No API or dependency change is needed.

Acceptance: use the real Apollo mutation/refetch path with a controlled successful CreateLedgerFile response followed by failed GetLedgerDirContent. Upload A is reported committed and leaves staging; retry sends only B. Create File also records the acknowledged file as created and completes its covered-save flow despite the separate refresh error; retrying the read must not issue another create for that path. Preserve w4/247's protection for newer input during pending creation. Separately verify a mutation failure before acknowledgement keeps its draft/file staged, normal folder-refresh success, nested directory variables and existing-name refusal. A mocked mutation that rejects only before writing misses this phase. Repeat the fresh desktop/narrow journeys and run dashboard checks on implementation.
