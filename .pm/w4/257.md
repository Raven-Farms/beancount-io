# Offer an in-place retry when General Settings cannot load

**Severity:** minor (error recovery). **Estimate:** 35–50 minutes, dashboard. **A2:** a transient read failure should have an actionable recovery without reloading the whole app or re-entering credentials.

Production https://beancount.io, 2026-10-20, local main `c5e4cd11a`; separate fresh QA-owner contexts at 1440×1000 and 390×844, English/light, isolated headless Chromium155.0.8059.85. Read-only user settings. Only the client GetCurrentUser request is deliberately aborted before transmission; no synthetic response or real server outage is claimed.

## Fresh reproduction and control

1. Open /settings/general with the real QA session and abort that page's one client GetCurrentUser read. Root authentication remains signed in.
2. The URL stays correct and the page honestly says Failed to Load Settings / Connection problem / check your connection and try again. Its only main button is Back. There is no Retry or Try Again action in the visible UI or accessibility snapshot.
3. Remove the browser fault. Click the current General navigation link. Two real GetCurrentUser HTTP200 responses now contain a profile, but the mounted General page still shows its error after waiting seven seconds for User Profile. Both fresh widths reproduce. These root/navigation reads do not recover the failed page observer.
4. A separate fresh narrow control removes the fault and reloads the document. User Profile renders, the error disappears, no sign-in is needed and zero mutation requests occur.

Expected: an explicit retry in the error state re-executes the General page's failed read and restores its content in place. Correctly staying signed in is already a passing behavior. This does not claim the page cannot recover by leaving/remounting it or by a full document reload.

## Cause and bounded repair

`dashboard/src/features/user-settings/pages/general/index.tsx:125–158` renders a static GeneralSettingsError with no callback/action. The page at :168–176 destructures data/loading/error from useQuery(GetCurrentUserDocument), discarding refetch. Its cache-and-network policy and ssr:false put this failure on the client consumer, after the root auth check has succeeded. The error text recommends trying again but offers no corresponding control.

Wire a localized retry to that observer's refetch, with a clear pending state and safe repeat activation; reuse existing error/retry UI where suitable. Preserve real signed-out versus unavailable policy, URL, existing error classification, user-data visibility and settings layout. Keep the failed view free of editable profile or session controls until a successful read. Avoid automatic retry loops or a credential prompt. No API, dependency or cross-package change is indicated.

Acceptance: through the real page/query integration, reject the initial profile read, remove the fault, activate Retry with the keyboard, and show the profile after the new successful response without a document navigation. Repeat failure stays actionable; busy state prevents uncontrolled repeats. Cover the recorded current-nav control, normal load, genuine sign-out and root-unavailable behavior. Run dashboard checks when implementing.
