# Load every Budget directive instead of silently displaying only the first journal page

**Severity:** major. **Estimate:** 45–60 minutes, dashboard. **A2:** a ledger's existing budget must remain discoverable when its total number of targets or revisions exceeds twenty.

## Reproduce

Production `https://beancount.io`, 2026-10-20, QA-owned isolated headless Chromium 155.0.8059.85, English/light, owner of a designated disposable ledger. Local main `c5e4cd11a`; deployed `main-D9qWGMxD.js`, full deployed SHA unverified. The fixture is **real synthetic ledger content written through the API**, not an intercepted response: 21 prefixed, valid monthly budget custom directives, all dated 2026-10-01, on distinct `Expenses:Qa-20261020-Budget01` … `Budget21` accounts, with 1 … 21 USD targets. The ledger check reports no errors.

1. Fresh-load `/ledger/<qa-owner>/<synthetic-ledger>/budget` at 1440×1000.
2. The actual `GetLedgerJournal` request sends only `directiveTypes:["Custom"]` and `customSubtypes:["budget"]`, with no limit/offset. HTTP 200 returns **total:21**, but **data.length:20**, covering Budget21 … Budget02.
3. The page claims **20 / 20 results**, renders 20 named history tables, and offers no next-page/load-more action. Search for **Budget01**: **0 / 20 results — No results found.**
4. Reload at 390×844 and repeat: same false completeness and absent account. Search for Budget02 works and shows its 2 USD row. The real GraphQL control with `limit:20,offset:20` returns the missing Budget01, total 21, one row; `limit:100` returns all 21.

The same fixture was shared with w4/234. Afterwards the original file was restored byte-for-byte (2,817 bytes, matching SHA-256), `getLedgerErrors` returned empty, and a fresh Budget page showed the baseline **No budgets found**. The QA-owned secondary page was closed. No real account data or public ledger was modified.

## Cause and bounded repair

`dashboard/src/features/ledger-data/budget/index.tsx:167–177` requests one ordinary paginated journal page. The GraphQL `JournalQueryInput` in `backend-cluster/backend-v2/src/features/ledger/api/resolvers/ledger-journal-resolver.query.ts:69–73` deliberately defaults to limit 20/offset 0; the ledger service applies its normal slice. This producer behavior is correct. Budget maps only the returned page at lines 179–187, ignores `total`, and treats the resulting groups as the complete corpus. The result denominator at line 272 is `groups.length`, not the real number of loaded/available directives or groups.

Read the complete relevant budget history before grouping and calculating targets. Use supported paging and the returned total/completion signal; do not replace twenty with another silent fixed ceiling. Search must cover every account, and histories must include older target/cadence changes across page boundaries. Preserve filters, canonical hashes, chronological grouping, sparse actuals, primary currency, and write permissions. Keep Add/Update/Delete refetches coherent with that complete history. A later-page failure must show a recoverable loading/error state rather than a successful-looking partial financial comparison or final no-match result. Empty success still renders the existing empty CTA.

This page is the sole production dashboard `groupBudgetEntries` caller. Its Add Budget dialog also names the current first-page journal query in `refetchQueries`; account for that when choosing the paging implementation. The native Budget screen owns a separate reader and was not tested. No server defaults, API contracts, REST or MCP change is needed.

Acceptance: a rendered page using actual paginated response shapes loads 21 distinct accounts, finds Budget01, and reports the complete result count. Add a history case where one account's older target lies after page one and is required for an earlier chart period; check mutation refetch, empty, last partial page, loading and failed later-page recovery. Repeat the fresh desktop/narrow search controls and run dashboard format/lint/test/build when implementing.
