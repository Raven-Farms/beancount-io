# Preserve the current public page when signing in from the ledger or profile header

**Severity:** minor. **Estimate:** 35–50 minutes, dashboard. **A2/A3:** visitors exploring a public example or its author should return to that page and its selected filters/tab after choosing to sign in.

## Reproduce

Production `https://beancount.io`, 2026-10-20, fresh signed-out context in QA-owned headless isolated Chromium 155.0.8059.85, English/light, no auth session cookie. Local main `c5e4cd11a`; deployed `main-D9qWGMxD.js`, full deployed SHA unverified. No response substitution, sign-in form submission, registration, email or social mutation.

1. At 1440×1000, open `/ledger/open_ledger/example` and click header **Log In / Sign Up**. The settled Welcome back form is at **`/auth/login`**, with no `next`; its Sign Up link is only `/auth/sign-up`.
2. Fresh-load `/ledger/open_ledger/example/journal?time=2017-09#main-content` at 390×844 and use the same header action. It again emits `/auth/login`, losing the ledger, Journal route, selected month and fragment.
3. Independently open `/ledger/open_ledger?tab=followers#main-content`. At both widths, header **Sign In** likewise emits bare `/auth/login`; the chosen profile/tab/fragment are absent. The desktop header's direct **Sign Up** link also emits bare `/auth/sign-up`.

Working control: on `/ledger/open_ledger/example?time=2017-09#main-content`, guest **Star** emits `next=/ledger/open_ledger/example?time=2017-09#main-content`, correctly encoded once. The settled login form's Sign Up link preserves that same next. No star mutation is submitted. In a temporary page using the existing QA session, opening that explicit-next login URL reaches the exact public ledger/month/fragment. Opening bare login instead enters the authenticated welcome/default flow. This is an authenticated route-guard control, not a new password or OTP completion.

## Cause and bounded repair

`dashboard/src/common/components/ledger-layout/layout-header.tsx:141` supplies a bare login Link. `features/user-profile/components/user-profile-header.tsx:43–46` supplies bare login and registration Links. None records the current route. `features/auth/pages/login-page/index.tsx:25–42` can only honor an explicit safe next; otherwise its actual password-success callback chooses the user's default ledger or Welcome. `login-page/loader.ts:15–20` similarly honors safe next for an existing session and otherwise redirects to `/auth/welcome`. That post-password consequence is source-traced; password entry was not exercised.

Supply the complete safe relative current location through the existing `useSafeReturnPath` / `getSafeReturnPath` convention for these header links, including path/search/hash, and preserve it through registration. Keep the existing safe-redirect validation and normal login/registration fallback when no return destination exists. Do not queue or perform a Star/Follow action after authentication.

The ledger header is mounted by the shared ledger layout; the profile header is used by the normal and not-found profile pages. Valid public Overview, Journal and profile routes above were exercised; not-found profile and ledger error shells were only found in the caller/link search. `LedgerWriteAccessNotice` already supplies safe next, as do Star/Follow; unrelated bare links such as account deletion and logout may deliberately use the default flow and are outside this repair.

Acceptance: start from the actual signed-out ledger/profile header controls with query plus fragment, assert their emitted next, the login → Sign Up continuation, and the authenticated guard's exact return at both widths. Preserve registered/signed-in navigation, generic auth-page defaults and rejection of unsafe/external destinations. Use the existing real-router continuation coverage rather than testing only LoginPage with an already-correct next. No API, dependency or new translation key is needed. Run dashboard format/lint/test/build when implementing.
