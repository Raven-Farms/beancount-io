# Keep Add posting from becoming Remove posting while focused

**Severity:** minor. **Estimate:** 40–55 minutes. **Owner:** dashboard. **A2:** someone building a transaction by keyboard should not lose a posting because an additive control silently becomes its destructive counterpart under the same focus.

## Reproduction and controls

Production `https://beancount.io`,2026-10-22; owned isolated headless Chromium155.0.8059.85, English/light, signed in to the designated disposable QA ledger. Fresh390×844 and1440×1000 New Entry → Transaction dialogs independently reproduce this. These are local unsaved drafts; no submission or hosted write occurs.

1. Leave the first account blank and enter **-1.25** in Posting1 amount. Enter **1.25** in Posting2 amount. At1440, also select the existing Expenses:Food:Coffee account for Posting2; the first390 case leaves both accounts blank. This is an in-progress draft with the initial two rows and an available Add posting action.
2. From Posting2 amount, native Tab twice reaches **Add posting**. Press Enter once. A third empty row appears and both entered amounts remain intact.
3. The exact original button node remains connected and focused, but its accessible name and handler have changed to **Remove posting 2**. There are now zero Add posting buttons.
4. Without moving focus, press Enter again. Posting2 is deleted: the remaining second row has a blank amount, while Posting1 remains -1.25. At1440, Expenses:Food:Coffee is lost too. Focus falls to the dialog container. Native Cmd+Z at1440 does not restore the account, amount or row.

The first Enter does not itself delete the draft; the defect is the focused action changing from Add to Remove before the next activation. This report does not allege a posted transaction change or an accepted financial write.

A fresh390 control selects Expenses:Food:Coffee/1.25 in Posting2. The same Add activation again leaves Remove posting2 focused. Native Tab then reaches the new Posting3 account, where selecting Assets:Bank:Checking preserves both original amounts and Posting2's account. Native Tab through that new row to **Remove posting 3**, followed by Enter, intentionally removes only that row and retains Expenses:Food:Coffee/1.25. Explicit removal and editing the added row work; keyboard action identity at the Add boundary does not.

## Source and bounded repair

`dashboard/src/features/journal/components/new-directive-dialog/transaction-form.tsx:480` keeps each row keyed by field.id. At569–592, the same button position is Add only for the last of two rows, then Remove for every row once append increases the count. Explicit `addPosting` around339–349 appends with shouldFocus:false. The live element-handle control confirms that this branch change reuses the focused button as Remove posting2.

Keep an explicit Add activation from leaving its focus on a newly destructive action. Preserve a stable Add control, or deliberately hand focus to an appropriate control in the newly added row. Keep automatic blank-row addition's deliberate no-focus/no-scroll behavior separate from the explicit Add action. Preserve existing amounts/accounts, numbering, the minimum row count, exact auto-balance, explicit removal, pending-submit protections and ordinary keyboard order. No global focus policy, persistent draft store, confirmation dialog, dependency or API change is needed.

Acceptance: through the real Transaction form, enter a partial two-row draft and activate Add by keyboard. Assert the next focused action remains additive or belongs to the newly created row, never the previous row's Remove. A subsequent Enter cannot delete the earlier account/amount merely because its action changed in place. Cover explicit removal and automatic blank-row addition as passing controls, repeat desktop/narrow, and run dashboard gates when implementing.
