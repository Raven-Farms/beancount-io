# Show a recoverable error when Budget deletion cannot read or delete its source slice

**Severity:** minor. **Estimate:** 30–45 minutes, dashboard. **A2:** a reader confirming a destructive action must be told when it failed and retain a safe retry or cancel path.

## Reproduce

Production `https://beancount.io`, 2026-10-20, QA-owned headless isolated Chromium 155.0.8059.85, English/light, authenticated disposable-ledger owner. Local main `c5e4cd11a`; production asset `main-D9qWGMxD.js`, full deployed revision unverified. **These are explicitly injected browser-network failures against the real deployed UI, not observed production API outages.**

1. Create a prefixed synthetic budget, then open the row's specifically named Delete action on `/ledger/<qa-owner>/<synthetic-ledger>/budget`.
2. At 1440×1000, abort only the `GetLedgerEntryContext` GraphQL request using Playwright routing. Confirm **Delete**. The delete mutation is never sent.
3. The spinner resets and the identical **Delete Budget** confirmation remains, with Cancel/Delete enabled. There is no error text, no accessible alert and no notification. The page emits an unhandled `Failed to fetch` exception. The user cannot tell what happened.
4. Reload and repeat at 390×844, allowing context lookup to succeed (real HTTP 200) but aborting only `DeleteLedgerEntrySourceSlice` before it reaches the server. The same unchanged confirmation, absent feedback and unhandled exception recur.

Remove each interceptor in a finally block. Working control: Cancel works; a subsequent ordinary context lookup and confirmed deletion both return HTTP 200, the dialog closes, and a fresh journal read proves that exactly the chosen directive disappeared. The snapshot was then restored byte-for-byte, the baseline budget count returned to zero, and the ledger check stayed clean. No request to an actual deletion service was sent by the two failure probes.

## Cause and bounded repair

`dashboard/src/features/ledger-data/budget/delete-budget-dialog.tsx:41–65` awaits the context read and mutation inside `try/finally` with no catch or user-visible failure state. The `finally` only resets `isDeleting`; the rejected async handler attached at line 95 escapes into the page. The rendered confirmation at lines 74–108 has no error feedback. The missing-checksum return at line 51 is another silent source path, but that response shape was not injected during this run.

Catch and format context/mutation failures using the dashboard's existing localized error mechanism. Keep the confirmation and its target available, show an accessible localized error inside the dialog, clear stale feedback for a new target or retry, and retain Cancel/retry once the pending operation settles. Do not close, clear caches, or report success on failure; preserve the current successful single-directive deletion, checksum guard and write permissions. No API/schema/policy change is needed. This component is mounted only by the Budget page and handles every budget-history delete; Add Budget already renders its own formatted inline error and is a source precedent, not an independently failed write here.

Acceptance: render the real dialog with rejected context and rejected delete operations, asserting visible accessible feedback, enabled retry/cancel, no success callbacks/cache clearing, and successful retry. Check a missing checksum without claiming a delete, plus pending controls and cancel/reopen state. Repeat both network-failure journeys from fresh desktop/narrow loads and the successful deletion control. Run dashboard format/lint/test/build when implementing.
