# Restore BQL syntax feedback for the current parser

**Severity:** minor. **Estimate:** 45–60 minutes. **Owner:** dashboard. **A2:** someone learning BQL should see the offending token and position already supported by the query UI, rather than generic invalid-input advice.

## Reproduction and controls

Production `https://beancount.io`,2026-10-22; owned isolated headless Chromium155.0.8059.85, anonymous public open_ledger/example, English/light/UTC. Fresh390×844 and1440×1000 contexts independently reproduce this; a third fresh390 case waits for the actual editor before capturing the settled result. All queries are read-only.

1. Bookmark/load the query page with **SELECT 'ab' AS label FROM )** at1440 or **SELECT '日本' AS label FROM )** at390.
2. The actual QueryShell returns HTTP200/BAD_USER_INPUT with `syntax error at position 26: found ')' expected ...` for ASCII, or position30 for the Japanese literal.
3. Both query cards show only **Some of the information provided is invalid. Please check and try again.** Reloading each bookmark repeats that generic guidance. The settled narrow editor contains the exact malformed query, so this is not an editor-bootstrap or URL-decoding failure.

The closing parenthesis is at zero-based character index26 in both strings. Independent UTF-8 encoding places it at byte26 for ASCII and byte30 for Japanese, matching the observed parser offsets. Both should name the safe token **')'** at **character27** in the existing localized feedback. No wrong character number is currently displayed: the current failure is the generic fallback; these offsets constrain a correct repair.

Working controls: the actual unknown-column query **SELECT '日本' AS label, FROM** names **FROM** correctly. At both widths, replacing the syntax error with an exact valid one-row query and native Cmd+Enter returns the expected literal with no alert in the new result card. Deleting the failed history card leaves the current editor unchanged and starts no query. The separate settled390 control reloads the corrected bookmark with one successful history card, the exact query/value and no query-card alert.

## Source and bounded repair

`dashboard/src/features/bql/lib/query-error.ts:27–29` recognizes only `syntax error at position N: unexpected token 'X'`. The actual current parser emits **found ')' expected ...**, which cannot match. getQueryErrorFeedback therefore returns the generic BAD_USER_INPUT key. QueryResultCard is its sole production caller and already has the originating query available.

Support the current bounded parser diagnostic alongside the legacy form, using the existing localized token/character message. Normalize the observed UTF-8 byte offset against that query before calling it a character position; simply adding one would mislabel the Japanese case as31 instead of27. Keep token capture length/character restrictions, safe integer/range handling, unknown-column guidance and generic fallback for unrecognized or unsafe messages. Do not render the raw expected-token list or change backend/API behavior, execution, history or locale catalogs unnecessarily.

Acceptance: real rejected-query envelopes in both ASCII/Japanese cases render ')' at character27; legacy unexpected-token diagnostics retain their behavior. Preserve unknown-column and unsafe/unrecognized fallbacks. Corrected execution, bookmarked reload and history deletion remain usable. Include meaningful owning-card/helper coverage and desktop/narrow controls, then run dashboard gates when implementing.
