# Preserve the creation draft after a failed request

**Severity:** minor. **Estimate:** 40–60 minutes, dashboard. **A2:** a temporary creation failure should keep the customer's setup and retry identity when they close the dialog and return.

Production https://beancount.io, 2026-10-21, English/UTC, dedicated QA account, owned isolated headless Chromium155.0.8059.85. Independent fresh1440×1000 and390×844 sidebar-dialog journeys. Real UI/reads; the one creation attempt per case is held and then aborted **before transport**. No ledger is created, no acknowledgement is fabricated, and actual server duplication is not claimed.

## Reproduction and controls

1. Open `/ledger` → Create Ledger → Template/Personal → details. Enter a prefixed synthetic name, EUR, Books begin2026-09-01, Assets:Bank and opening amount2500. Read only this wizard's known sessionStorage key, ledger-create-draft, to record its presence and requestId equality in memory.
2. Passing control: close with native Escape and reopen. Details, all four entered values and the same requestId are preserved at both widths, with0 mutation attempts. Resumption normally works.
3. Advance from details to Review. The existing [314](./314.md) bug triggers CreateLedger on Next; the QA guard holds it before transport. The saved draft is still present at review step2 (zero-based), including the amount, and the captured requestId matches the original.
4. Release the guard to abort the request, with no HTTP response/ACK. After failure, Review remains mounted, the name is still visible and Create Ledger is enabled, but **ledger-create-draft has been deleted**.
5. Close that failed review with native Escape and reopen. Both widths now start at Step1of3/Starter instead of the saved flow. Name, EUR, explicit date and amount are not retained, and the new draft has a different requestId.

Expected: failed creation preserves the owned creation draft and requestId across closing/returning. Only confirmed successful creation or an explicit supported reset should clear it. The failure here enters through314, but deletion is a distinct failure-outcome bug in the shared submit chain; preventing Next's premature submit alone does not correct it. A separate explicit-final-button failure and actual successful create are source/regression scope, not live claims in this note.

**Independent edit-mode control, fresh1440:** park a prefixed creation draft at details, then open Edit for the designated synthetic ledger. Cancel preserves that draft and its ID with0 attempts. Reopen Edit and activate Save without changing any fields; abort its UpdateLedger before transport. The edit dialog stays open and enabled, but the unrelated creation draft is deleted. Returning to Create starts at defaults with a different ID. This control attempts no CreateLedger and does not advance through Review, independently separating cleanup ownership from314.

## Cause and bounded repair

`dashboard/src/features/ledger-list/components/ledger-form.tsx:292–297` awaits onSubmit and then unconditionally removes the draft key. The prop is void/Promise<void>; resolution is treated as creation success. DashboardSidebar's handleCreateLedger at:356–372 catches mutation errors, shows feedback and returns normally, so the failed operation fulfills that callback. The form therefore runs its success cleanup. Its draft-persist effect depends on values/step/kind/preset, which did not change on failure, so loading/feedback updates do not restore the key. Closing then unmounts the only remaining in-memory copy.

The removal is also unguarded by isCreate. DashboardSidebar's edit callback at:530–569 catches and resolves its UpdateLedger failure in the same way; the shared edit form then removes the separate creation key, explaining the independent control.

Make the callback outcome/cleanup ownership explicit and clear the owned creation draft only after confirmed creation. Preserve failure feedback and in-place retry without introducing an unhandled rejection. Keep the same setup/requestId across failure and remount, preserve normal successful cleanup and avoid clearing a creation draft through unrelated edit-mode submissions. No API, quota, dependency or new persistence mechanism is indicated.

Acceptance: exercise real LedgerForm with its parent mutation callback, not only a directly rejecting onSubmit mock. A refused/network-failed create followed by close/reopen retains step, fields and requestId; retry uses that same identity. A schema-complete successful test response clears the completed draft once, with a new identity only for a genuinely new flow. Keep the passing ordinary close/reopen control and error feedback. Edit cancellation, failure and a successful test response must preserve an unrelated creation draft. Run dashboard format:check, lint, test and build on implementation; hosted creation is unnecessary for this regression.

**Resolved 2026-10-22** — `LedgerForm.onSubmit` now resolves `true` only once a ledger is created. The sidebar, ledger-switcher and welcome-page create handlers return `true` on success and `false` after their error toast. The form clears its creation draft (step, choices, requestId) only on `true`, and only in create mode, so a failed create keeps it and an edit never touches it. Shipped in `1910e83c4` (`dashboard`).

**Native check:** local production build at 1440 and 390 px, with every CreateLedger held and aborted before transport.
- After the failed create, `ledger-create-draft` keeps step 2, the entered name, Books begin and the same requestId.
- Closing, navigating back to `/ledger` and reopening Create Ledger resumes at Step 3 of 3, and the retry sends the same requestId.
- One write per explicit Create; no premature write (314).

- `ledger-form.test.tsx`'s draft-resume case now models success as `true`.
