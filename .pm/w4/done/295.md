# Protect newer Budget drafts from an earlier pending submission

**Minor · dashboard · 60 minutes.** A2: Budget must not accept edits or a reopened draft that an older request then silently discards. ## Reproduction and controls

These are real browser form interactions with a controlled request boundary: hold BulkEntries **before transport**, then fulfill a schema-complete client-only acknowledgement (`AddLedgerEntryResponse`, success:true, message). Allow the following genuine read to succeed. No mutation reached the server and no budget was persisted; the observed loss concerns accepted unsaved form input.

1. Open `/ledger/<qa-owner>/<synthetic-ledger>/budget` → Add Budget. Choose Expenses:Food:Coffee, Monthly, USD and amount `500`; submit.
2. Desktop: while the submit button is busy, Amount and Cancel remain enabled. Change Amount to `700`; the real field accepts and displays it. Complete the held request with success. The dialog closes; reopening shows an empty amount. The submitted payload contained only `500`.
3. Fresh narrow context: submit `500`, Cancel while held, reopen Add Budget and enter `900`. The new form accepts the value and enables Submit even though the first request remains pending. Complete the older request; it closes and resets this newer form. Reopen: empty amount. A further independent narrow repeat gives the same result. Each case emitted one mutation attempt, with zero forwarded.
4. Negative control: submit `500`, edit to `700`, then abort before acknowledgement. The dialog stays open with `700`, a connection alert and enabled Submit. Ordinary unchanged submission with a successful acknowledgement/read closes as intended (m41's working control).

## Cause and bounded repair

`dashboard/src/features/ledger-data/budget/add-budget-dialog.tsx:127–174` unconditionally resets the current form and closes it after the awaited request succeeds. The close handler at :179–182 and Cancel at :333–339 reset immediately without coordinating the pending request. Only Submit consumes isSubmitting (:343–347); accepted fields and a reopened form have no matching request/draft ownership.

Make input, dismissal/reopening and completion coherent for this component. A bounded pending lock is sufficient, or an equivalent ownership guard that preserves newer accepted input. An older success must not reset or dismiss a newer draft. Preserve genuine failed-write draft recovery, ordinary idle Cancel/reset, exact amount strings, civil dates, locked Update props, accessible controls, focus return and single submission through button/keyboard. Cancel does not undo an already transmitted write. No persistent draft store, backend/API change or dependency is needed.

Acceptance: exercise the actual dialog with a deferred mutation; cover edits while pending, Cancel/Escape/close/reopen, success, refusal/transport failure and retry, and ordinary idle cancellation. Newer input must either be unavailable while pending or survive the older completion. Cover Add and the shared locked Update consumer, then run dashboard format/lint/test/build and repeat native desktop/narrow interactions.
