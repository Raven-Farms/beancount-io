## Objective

Put one in-flight guard at the owning profile submission boundary so Save and either ordinary Enter cannot start overlapping UpdateProfile requests.

## Context

See [the milestone](../README.md) and [browser evidence](../FINDINGS.md). The owning implementation is dashboard/src/features/user-settings/pages/general/user-profile-section.tsx and its existing component tests.

## Steps

1. Holding one submission, repeat both input Enter paths and Save; only one request starts. Genuine success/failure releases the guard, and one deliberate retry uses the current trimmed names. Preserve the existing composition guard and audit the sibling Username callback.

## Acceptance criteria

- [x] The stated objective is verified against the actual transition, with evidence and limitations recorded.
- [x] Preserve the milestone's existing validation, composition, error/retry and draft-ownership controls.

## Out of scope

Backend/API changes, actual account modifications, a persistent draft store, unrelated settings redesign and new dependencies.

## Verification

**Fix.**
- `dashboard/src/common/hooks/use-pending-action.ts` (new) holds one in-flight write per caller. `run` returns `null` while a write is pending, so nothing else starts.
- `usePendingSubmit` (m33/m42) now builds on it, unchanged for its seven form callers. Its pending, focus and refusal suites pass: New Entry, Open Account, Add Budget.
- In `user-profile-section.tsx`, Enter in First Name, Enter in Last Name, and Save all go through `handleUpdateName` → `nameSave.run`. The Username dialog's Enter and Save go through `usernameSave.run` after the existing rule check.
- The composition guard stays in both `onKeyDown` handlers. A failed write (the default error policy rejects, after `onError` toasts or flags the field) releases the lock with the draft intact.

**Regression** (`user-profile-pending.test.tsx`, real Apollo, real Radix dialog):
- With one UpdateProfile held, a second Enter, a third Enter and a Save click send nothing more.
- After the failure, one deliberate Save sends exactly the current trimmed `{Grace, Lovelace-King}`.
- Username: a second Enter sends nothing more, and the server refusal stays on the field.
- The previous component fails all four cases.

**Native, local build + fixture API, writes held in the browser (aborted or locally modeled):**
- 1440/390: First Name Enter, then Last Name typing + Enter + Escape → one UpdateProfile. Last Name stays `Control`.
- After the failure, Space on Save → exactly one more request with the same exact fields.
- Username Enter, `x` + Enter → one UpdateUsername.
- 0 forwarded mutations, 0 page errors.
