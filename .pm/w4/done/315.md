# Review the selected ledger starting point rather than the retained preset

**Severity:** minor. **Estimate:** 20–35 minutes, dashboard. **A2:** the final review should identify whether the customer chose empty books, a preset or fictional Sample activity.

Production https://beancount.io, 2026-10-21, English/UTC, dedicated QA account, owned isolated headless Chromium155.0.8059.85. Fresh1440×1000 and390×844 Sample cases plus a fresh1440 Starter control. Real sidebar dialog and unmodified successful reads; no response fixtures. All mutation attempts are blocked before transport and no ledger is created.

## Reproduction and result

1. Open `/ledger` → Create Ledger. Select **Sample ledger**, advance through details using a prefixed synthetic name, and inspect Step3of3.
2. Review promises **This is exactly what will be created** but its only starting-point value is **Personal ledger**, beside the Private label. Sample/fictional identity is absent from the review. Both widths reproduce.
3. The independently captured pre-transport creation payload has template=SAMPLE and no setup. Thus Personal ledger is not the requested preset; this note does not claim the server builds the wrong template.
4. A fresh Starter path displays the same Personal ledger value, while its attempted payload correctly omits template/setup. The wrong review identity also affects the ordinary default starting point.

The premature attempts are the separately tracked [314](./314.md); its guard lets these review states be inspected without a hosted write. This note's scope is the confirmation's displayed identity, not submission timing or generated files.

## Cause and bounded repair

`dashboard/src/features/ledger-list/components/ledger-form.tsx:235,688–709` resolves preset from presetId even when startKind is starter or sample. presetId defaults to the first Personal preset and persists across choices. The review renders `preset ? t(preset.titleKey) : startKind`, so the retained preset wins for every starting kind. The submit path correctly gates setup on startKind=preset and Sample on startKind=sample, explaining the observed mismatch.

Derive the reviewed starting point from startKind first: localized Starter identity for starter, clearly fictional Sample identity for sample, selected preset title only for preset. Present the starting point under an appropriate localized label, keeping visibility as its own fact. Preserve chosen-preset retention when switching back, preview files/accounts and the actual create payload. Reuse existing localized labels where suitable; no API, dependency or template-content change is indicated.

Acceptance: choose Starter, Sample and at least two presets through the real form and assert Review names the selected kind/preset. Switch preset→Sample→Starter→preset with Back and verify identity and resulting submission variables agree. Preserve privacy, name, selected preset and requestId. Repeat both widths and run dashboard format:check, lint, test and build when implementing. Only Starter/Sample are live reproduced; other preset/switch variations are regression scope.
