# Restore usable keyboard focus when a confirmed file deletion fails

**Severity:** minor. **Estimate:** 40–60 minutes, dashboard. **A2:** after a failed Delete File, keyboard users should be able to retry or continue at the file actions without starting again at the top of the page.

Production https://beancount.io, 2026-10-21, English/UTC, ordinary theme, owned isolated headless Chromium155.0.8059.85, authenticated designated synthetic-ledger owner/admin/push. Fresh1440×1000 and390×844 settled-dialog repeats reproduce. Final dedupe main0946336c7. Deployed action and file-view containers exactly match current source. Failures below are deliberate browser-local pre-transport aborts, not claimed production outages.

## Reproduction and result

1. Open `/ledger/<qa-owner>/<synthetic-ledger>/files/blob/main/<qa-prefixed-file>.txt` for an owned disposable file.
2. Use Enter on **More actions**, End to focus **Delete**, then Enter. Wait for the Delete File dialog's initial Cancel focus and let it settle. Native Tab focuses its Delete button; Enter confirms.
3. Hold the exact DeleteLedgerFile request before transmission. The confirmation closes immediately, the persistent More actions button remains enabled, and focus is BODY. The request has not completed or left the browser.
4. Abort that held request. A useful **Connection problem** toast appears, but the same file page remains with no dialog and focus still on BODY. The next native Tab reaches **Skip to main content**, far from the file actions. The original file is unchanged.

Independent fresh desktop/narrow repeats wait700ms after the dialog initially focuses Cancel,700ms while pending and700ms after failure. Both produce BODY → Skip to main content. Each blocks exactly one mutation, forwards zero, and records0 route errors. Each failed handler also emits one pageerror of type TypeError; no raw exception/request payload is needed to reproduce the focus failure.

Working controls: Escape from the reopened confirmation restores the exact More actions opener at both widths. A separate fresh narrow real successful deletion sends one unchanged exact-path/SHA request, returns HTTP200 without GraphQL errors and navigates to Files; readback confirms the file absent. Preserve successful destination focus ownership rather than restoring a button on the departed file view.

## Cause and bounded repair

`dashboard/src/features/ledger-editor/file-editor/components/non-text-file-views.tsx:114–122` marks deleteConfirmedRef before calling a void-typed onDelete callback, does not await its promise, and immediately closes the dialog. Its onCloseAutoFocus at:204–213 prevents restoration for every confirmation on the assumption that navigation will follow. `components/ledger-file-view/index.tsx:168–196` only toasts on mutation failure; navigation occurs exclusively on success, with no failure focus recovery. Consequently a failed operation takes the success-only focus path.

Make confirmation completion account for the actual asynchronous deletion outcome. Keep a usable focus owner while pending and restore the connected persistent file-action opener, or retain a usable focused confirmation, when the deletion fails and the same file view remains current. Handle the rejected promise. Suppress deferred opener restoration only for the successful departure, and preserve deliberate focus/navigation choices made while waiting. Keep Escape/Cancel restoration, the existing connection feedback, retry with the current file SHA, permission gates and root main.bean refusal. No API or dependency change is indicated.

Acceptance: render the real file view/action dialog with a held and rejected delete; native keyboard focus remains usable through pending/failure and the next Tab stays near the file actions. Include immediate rejection, successful asynchronous deletion with navigation, dismissed confirmation and deliberate pending focus movement. Verify the original file remains on failure and that a retry can succeed once. Run dashboard format:check, lint, test and build when implementing.
