# Keep transaction submit shortcuts out of active composition

**Major · dashboard ·40–55m · A2.** Functional dashboard QA,2026-10-22; production, isolated headless Chromium155, English/UTC,1440×1000 and390×844. A trusted composing Ctrl/Meta+Enter attempts to submit an unfinished transaction. Every write is intercepted before transport; actual booking or duplication is not claimed.

## Reproduction and controls

1. On the designated disposable ledger, open Journal → New Entry → Transaction. Fill existing Assets:Bank:Checking with −1.25 USD and Expenses:Food:Coffee with the matching auto-balanced +1.25 USD. Use narration `qa-20261022-ime-shortcut` and payee prefix `qa-20261022-preedit-`. Let validation/account availability settle.
2. Keep Payee focused and start browser-engine preedit with CDP Input.imeSetComposition, text 日本, selectionStart/End2. The field contains `qa-20261022-preedit-日本`; compositionstart is trusted.
3. Deliver Enter through Input.dispatchKeyEvent with Control (modifier2) or Meta (modifier4). The recorded keydown is trusted, keyCode13, isComposing=true and the corresponding modifier=true.

Both modifiers independently reproduce at both widths. Each emits exactly one BulkEntries request containing a TRANSACTION with the still-unconfirmed payee above, the prefixed narration, date2026-10-22 and the balanced two-posting USD payload. The request is checked against the intended disposable ledger and aborted locally. The resulting connection-error feedback is caused by that deliberate interception and is not a backend failure finding. The dialog remains available after rejection.

Fresh narrow composing Enter **without a modifier** emits zero mutations and keeps the dialog open. A fresh desktop Ctrl+Enter **without active composition**, with payee `qa-20261022-confirmed`, emits the expected single intercepted request. Those controls isolate the application modifier shortcut from the working shared input guard and ordinary submission. No pending write precedes the composing-key failures; this is the first attempted submission.

Expected: the input method owns its composing key, with an ordinary application submission available after composition ends. Actual: the form starts a ledger write while preedit is active. This is demonstrated at the request boundary, not by booking a deliberately unfinished transaction. The later compositionend event in some captures is untrusted and is not used as proof of a native composition commit; the preceding trusted composing keydown and outgoing payload are the primary evidence. Physical OS IME sessions remain unverified.

## Source and bounded repair

`dashboard/src/features/journal/components/new-directive-dialog/transaction-form.tsx:332–337` checks only Ctrl/Meta plus Enter, prevents default and calls submit. It does not check the native keyboard event's composition state. The shared `common/lib/keyboard/is-composition-key.ts` already recognizes isComposing and keyCode229, with the explicit rule that application shortcuts leave composition keys to the input method. The Combobox guard does not cover this parent form handler.

The complete served TransactionForm in `ledger._ledgerOwner._ledgerName.journal-B-R7K1EM.js.map` matches committed main, SHA-256 `9b537ea27bf4485ec1388754ba0b8622877048a188898988dc4a30bde015032d`. Targeted history through d960308a0 contains the pending/focus repair but no composition guard here. TransactionForm's sole production owner is NewDirectiveDialog; its form handler receives bubbled keys from its fields. Only Payee is independently live exercised. Other shortcut owners need their own evidence.

Guard this local application shortcut with the existing native-event composition policy before preventing default or calling submit.
