# Acknowledged actions are presented as failures when follow-up reads fail

**Original Star observations, promoted from W4/294.** A2/A3: a confirmed save action must not look undone because a subsequent read failed. Production beancount.io, 2026-10-20 America/Los_Angeles (2026-10-21 UTC), owned isolated headless Chromium 155, English/System theme, fresh 1440×1000 and 390×844 contexts, authenticated QA on public synthetic open_ledger/example. ## Controlled reproduction

This is a live-client fault-injection test, not an observed backend outage or a real social write. Every mutation is intercepted before transport. StarLedger is fulfilled with the complete queried response shape: StarLedgerResponse, success:true, isStarred:true and a synthetic acknowledgement message. Only the following GetLedger read is aborted.

Both fresh widths start at Star and process exactly one synthetic successful acknowledgement followed by one failed GetLedger read. After settling, the enabled button is back at **Star**, and the only toast says “Connection problem. Please check your internet connection and try again.” The acknowledgement's confirmed starred state is lost, so the UI offers the original action again.

A separate fresh1440 working control returns the same complete acknowledgement and a successful modeled GetLedger read whose isStarred matches it. The button remains **Starred** and shows “Ledger starred successfully”. Thus changing only the follow-up read outcome changes how an already acknowledged action is represented. Screenshots of the narrow failure and desktop successful control were visually inspected.

No StarLedger/UnstarLedger request was forwarded to the backend. Other mutations were blocked, all extra contexts closed, and a real reload after removing the response controls showed the original Star state in every case. No star/follow relationship or ledger content changed. The first exploratory payload omitted queried fields and is excluded; the schema-complete repeats above are the primary evidence. Unstar is a shared-source regression case, not an independently live-exercised acknowledgement failure.

## Cause and bounded repair

`dashboard/src/features/reports/overview/components/star-button/use-star-ledger.ts:11–28` and use-unstar-ledger.ts use refetchQueries:GetLedger with awaitRefetchQueries:true. Installed Apollo core/QueryInfo.js:348–356 folds those read promises into mutation completion; react/hooks/useMutation.js invokes its error callback and rethrows on rejection. The hooks emit generic mutation-error feedback instead of their success onCompleted feedback. StarButton's catch in index.tsx:65–67 then restores the previous local state, without distinguishing a missing/failed mutation acknowledgement from a failed post-ack read.

Keep the authoritative successful result, including its already-queried isStarred value, separate from best-effort metadata refresh. Preserve the confirmed state and truthful acknowledgement feedback when only the read fails; refresh trouble may have its own bounded notice/retry. A cache update from the existing response is another possible bounded approach. Do not silently ignore genuine write errors, globally weaken Apollo error handling, blindly retry the write or report overall write failure after success:true. Preserve pending protection, actual business-failure rollback and prop synchronization. No API/schema or dependency change is needed.

There is one production StarButton caller, Overview, and the two hooks serve that component. Both star and unstar share the awaited-refetch lifecycle and require regression coverage. A meaningful real-Apollo component test must independently control mutation acknowledgement and later read outcome: true/read-fail keeps the acknowledged state; true/read-success, success:false and a genuine pre-ack transport failure retain their intended behavior. Include symmetric Unstar, useful feedback, subsequent retry direction and pending focus/name controls, then run dashboard format/lint/test/build.
