# Default Books begin to the browser's local calendar day

**Severity:** major onboarding failure for the default evening path. **Estimate:** 25–40 minutes, dashboard. **A2:** a newly created preset should accept today's first entry instead of opening every account tomorrow.

Production dashboard https://beancount.io, 2026-10-21, dedicated QA account, owned isolated headless Chromium155.0.8059.85, English. **Controlled browser-clock/timezone checks**: fresh1440×1000 and390×844 America/Los_Angeles contexts at fixed instant2026-10-22T04:30:00Z, or21:30 on local2026-10-21. Only the owned contexts use Playwright's fixed Date; system/server/root-session clocks and API responses remain unchanged. All creation attempts are blocked before transport; no ledger or transaction is booked.

## Reproduction and result

1. Open `/ledger` → Create Ledger → Template, keeping Personal. Advance to details with no prior draft. In both fresh Pacific contexts the browser's local date is2026-10-21, but **Books begin** has canonical input value2026-10-22. The narrow native date field visibly reads10/22/2026.

3. Passing UTC control at the identical instant: local date and input are both2026-10-22. Fresh Tokyo390 control at2026-10-21T16:30:00Z (local01:30 on22nd) instead defaults to2026-10-21, yesterday. This is a UTC-date default, not malformed input or native date-display formatting.
4. Passing Pacific narrow recovery: Back, explicitly correct Books begin to2026-10-21, and return to Review. HTTP200 preview and all12 opens now retain2026-10-21; the guarded create uses it too.

The real preview proves the future account openings. The downstream first-transaction failure is a source-derived consequence, **not an executed booking**: without a known opening, backend setup uses historyStart as openDate. An entry dated the user's current local day would precede those openings and encounter the inactive-account check. With a known opening, the opening assertion boundary is still shifted. No claim is made that an actual customer or production transaction failed during this check.

## Cause and bounded repair

`dashboard/src/features/ledger-list/components/ledger-form.tsx:177–179` defaults historyStart through `new Date().toISOString().slice(0,10)`, converting the current instant to a UTC day instead of the browser's local day. Its existing draft fallback and explicit date input correctly preserve supplied canonical dates. backend-v2's setup/build-ledger.ts:176–179,199 uses the supplied historyStart for unknown-opening account opens, explaining the preview; no backend change is needed for this default.

Initialize only a new unsupplied boundary from the local Gregorian calendar day using existing date utilities/dependencies. Preserve explicit and resumed YYYY-MM-DD strings verbatim; do not parse them as instants or rewrite a customer's date when the clock, locale, currency or step changes. Keep the backend date/creation contract and opening-balance semantics unchanged. No dependency or API change is indicated.

Acceptance: test the real form default in a Pacific evening, east-of-UTC early morning and UTC, with controlled clocks that distinguish local/UTC dates. Verify the local day survives details→preview/create variables, while an explicit different date and resumed draft remain intact across Back/return. Repeat relevant desktop/narrow controls and run dashboard format:check, lint, test and build. Actual creation/first booking are not required for the UI regression; API preview is read-only.
