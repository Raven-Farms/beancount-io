# Show unavailable AI usage when Billing's read fails

**Severity:** minor. **Estimate:** 40–60 minutes, dashboard. **A2:** a customer checking their plan should distinguish an unavailable usage read from a real token allowance or exhausted quota.

Production https://beancount.io/settings/billing, 2026-10-21, English/UTC, owned isolated headless Chromium155.0.8059.85, dedicated QA account. Fresh1440×1000 and390×844 contexts independently reproduce. Browser-local read fault only; no subscription, payment, AI or hosted write.

## Reproduction and result

1. Start a fresh authenticated context. Abort only the GetAiCfoUsage POST at `/api-gateway/` before transport; let subscription, current-user and tier-quota reads complete normally.
2. Open Billing. After loading settles, AI Tokens says **0 / 0 tokens used this month**, with a full red usage bar. There is no usage error or Retry action. Both widths reproduce; measured fill/track widths are1198/1198 desktop and308/308 narrow, with the destructive color class.
3. A fresh narrow control holds that read first: the loading view correctly withholds the usage heading and zero-count text. Aborting it then produces the false count/bar. Thus this is the completed failure state, not a pending skeleton.
4. Remove the fault and reload. A genuine HTTP200 usage response has a positive allowance, and the displayed counts match its returned values at both widths. No new sign-in is needed. Actual account counts are intentionally omitted from this public note.

Expected: usage remains explicitly unavailable after its failed read, with a keyboard-usable retry that re-executes this observer. Successful subscription facts remain independent. A connection failure must not manufacture a zero allowance or exhausted-quota gauge.

## Cause and bounded repair

`dashboard/src/common/hooks/use-ai-cfo-usage.ts` exposes error and refetch, but defaults missing usage counts to0. `features/user-settings/pages/general/subscription-section.tsx:126–129` consumes only the counts and loading flag. Once loading ends it passes those fallback numbers to UsageOverview; its error branch handles subscriptionError alone.

`subscription-usage-overview.tsx` computes0/0 as NaN and `used >= max` as true. The invalid NaN% width is discarded by the browser, leaving the normal block at the track's full width, colored red. The displayed zeroes are not a successful read.

Wire the usage observer's existing status/refetch through Billing. Show a localized unavailable state with pending/repeated-failure recovery, and render genuine usage only when known. Preserve successful zero usage, documented disabled/zero-cap policy, unlimited allowances, loading behavior, locale formatting and independent plan actions. Do not infer failure from numerical0 alone. Reuse existing retry UI where suitable; no API or dependency change is indicated.

Acceptance: exercise the real Billing/query integration with a cold usage failure, pending read, repeated retry failure and successful keyboard retry without a document reload. Assert the failure never presents invented counts or a full exhausted gauge; cover genuine successful zero usage and positive/unlimited allowances as controls. Decide explicitly how cached usage is identified during a failed refresh. Repeat both widths and run dashboard format:check, lint, test and build when implementing.

**Resolved 2026-10-22** — Billing now passes the usage observer's error and refetch through `SubscriptionSection`. While no usage read has succeeded, a failed read renders the localized "Usage is unavailable right now." row with a keyboard Try Again (`common.tryAgain`) in place of counts and gauge. A pending retry stays busy in that row rather than replacing the section, and plan, ledger and plan-action content stay independent. Decision on cached usage: a refresh that fails after an earlier successful read keeps those counts, since they are a genuine read. The busy retry is disabled, so focus returns to Try Again after another failure and to the AI Tokens block once counts load. Shipped in `f4eea97c4` (`dashboard`); the new `userSettings.aiCfoUsageUnavailable` message is translated in all 15 locales. The audited second consumer, `ai-cfo-upgrade-panel`, already hides itself on a zero max and invents nothing.

Native check at 1440 and 390 px against a local build and fixture API, aborting only GetAiCfoUsage in the browser:
- **Cold failure:** unavailable text and Try Again, no counts or bar, plan banner kept.
- **Pending retry:** busy, still no counts, plan banner kept.
- **Repeated failure:** Try Again enabled and focused.
- **Bare Enter, then success:** 1,234 / 20,000 with a 74/1198 (desktop) or 19/308 (narrow) primary-colored bar, and focus on the AI Tokens block.
- **Genuine 0 / 20,000 control:** a 0-width bar.

Every case ran with 0 mutations, 0 page errors and no horizontal overflow.

Regression coverage: `subscription-usage-unavailable.test.tsx` drives the real Apollo query integration through cold failure, a held retry, repeated failure and keyboard success, plus a failed refresh keeping cached counts and genuine-zero and unlimited controls. The failure case fails with the fix reverted, and its focus assertions fail without the handoff.
