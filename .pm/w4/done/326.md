# Keep calendar year choices inside supported ledger dates

**Severity:** minor (edge-case section crash and draft loss). **Owner:** dashboard. **Estimate:** 45–60 minutes. **A2:** choosing a date offered by the app should preserve a usable entry draft.

Production https://beancount.io, 2026-10-21, local main58d84b21b; QA-owned headless isolated Chromium155.0.8059.85, English/light/UTC, fresh1440×1000 and390×844 owner contexts on the designated synthetic ledger. Actual DatePicker/native select controls and button activation; no clock, API-response or calendar fixture.0 mutation attempts and0 hosted writes.

## Reproduction and controls

1. Open Journal → New Entry → Note. Enter Date **0001-01-01** and Tab; it displays **01/01/0001** without aria-invalid. Open Select date.
2. The year dropdown has201 options from internal year-99 through101. Negative years have positive, era-less labels: -99 is0100. There are two indistinguishable **0001** options, values0 and1.
3. Choose the first **0001** (value0) and February. The displayed header says **February 0001**, but an enabled day is named **Tuesday, February 29th, 1**. Select it.
4. The calendar and entire Journal/New Entry section disappear into **Something went wrong** / **Try Again**. Error Details reports **RangeError: Invalid time value**. The route still carries action=new-entry&directive=note. Fresh narrow reproduction gives the same failure; no submit button is activated.
5. Passing narrow control: choose the genuine year1 option (value1) and February. No February29 button exists; selecting February28 yields **02/28/0001**, no Date aria-invalid and a healthy form. Separately typing **0004-02-29** yields **02/29/0004** without invalid state. These verify DatePicker behavior, not server acceptance of a note against an account opened much later.
6. Explicit recovery repeat: before selecting the bad day, Date is01/01/0001, Account is Assets:Cash and Note content exactly matches a prefixed synthetic draft. After the same crash, **Try Again** recovers the Note form with today's date, blank account and blank content. The unsaved draft is gone. No general persistent-draft feature is required; prevent the offered choice from causing the crash.
7. Secondary range control: enter **9999-12-31**, which displays **12/31/9999** without invalid state, and open the year dropdown. It offers values10097/10098/10099 beyond the four-digit input domain. Those upper choices were inspected, not selected; no upper-bound crash is claimed.
8. Separate fresh desktop control: typing **0001-02-29** directly correctly retains it as invalid while the Note dialog stays healthy. Opening the calendar and choosing Today repairs it without a section error. The crash is specific to accepting the offered calendar choice, not ordinary invalid-date typing.

## Cause and bounded repair

`dashboard/src/common/components/ui/date-picker-utils.ts:141–152` returns anchorYear±100 without bounding it to the supported positive four-digit years. DatePicker passes these bounds to its dropdown calendar. Installed react-day-picker `dist/esm/formatters/formatYearDropdown.js:13–14` formats options with **yyyy**, so year0 and year1 both display0001 rather than exposing the unsupported era.

The actual exported helpers independently confirm the bad conversion: a Gregorian JavaScript year0/February29 value passed to calendarToIsoDate becomes **0001-02-29**. parseStrictCalendarDate refuses that string and isoDateToCalendar returns Invalid Date. DatePicker's calendar handler at:160–163 commits the serializer result; showMonthOf at:77–79 sets the month from it without an isValid guard. This feeds invalid calendar state into the observed rendering failure. The precise minified renderer throw frame was not symbolicated; the invalid helper round trip and UI RangeError are independently verified.

Clamp rolling bounds to0001-01-01 through9999-12-31, keeping the rolling100-year window within that domain. Prevent an unsupported/invalid calendar conversion from replacing the current month with Invalid Date. Do not offer BCE/year-zero or five-digit years as ordinary ledger-year choices, add era support, reinterpret them as positive years, weaken strict parsing or expand backend date contracts. Preserve valid years1/4/99/100/9999, current-date navigation, leap arithmetic, native keyboard choices, locale order, timezone-independent civil days and ordinary invalid-draft retention. No new dependency, API/backend change or persistent draft store is needed.

Acceptance: the year1 dropdown starts at1 with a unique0001 option; February in year1 has28 days and in year4 has29; year9999 offers no10000+. The reproduced selection journey cannot throw or erase the draft. Normal2026 bounds remain1926–2126 and continue rolling when browsing; Today and min/max navigation remain usable. Add meaningful helper and actual DatePicker/dropdown regressions, repeat desktop/narrow and run dashboard format:check, lint, test and build when implementing. Coordinate the shared file with [325](./325.md)'s independent digit normalization.

**Resolved 2026-10-22** — `rollingCalendarBounds` now clamps the calendar's rolling ±100-year window to the positive four-digit ledger years 0001–9999.
