# Accept Persian digits in localized Gregorian date entry

**Severity:** minor. **Owner:** dashboard. **Estimate:** 45–60 minutes. **A2/A3:** a Persian-language user should be able to enter the displayed Gregorian date using Persian decimal digits.

Production https://beancount.io, 2026-10-21, local main08db93e53; QA-owned headless isolated Chromium155.0.8059.85, en-US browser/UTC with app language fa, fresh390×844 and1440×1000 owner contexts on the designated synthetic ledger. ## Reproduction and controls

1. Open `/ledger/<qa-owner>/<synthetic-ledger>/journal?lang=fa&action=new-entry&directive=note`. In the visible Note panel, set Account to Assets:Cash and a prefixed synthetic note. The Date field is labelled تاریخ and hints YYYY/MM/DD.
2. Enter **2026/10/22** and Tab. Date has no aria-invalid and **ایجاد ثبت یادداشت** (Create Note Entry) is enabled.
3. Focus Date, select its text and insert **۲۰۲۶/۱۰/۲۲**, then Tab. This is the same Gregorian2026-10-22 with Persian digits, not Solar Hijri1405. The exact text is retained, but aria-invalid becomes true, the field is red and Create is disabled. Both fresh widths reproduce.
4. In the fresh desktop case, Arabic-Indic **٢٠٢٦/١٠/٢٢** is also refused in the same field. Restore ASCII **2026/10/22**: invalid clears and Create re-enables at both widths.
5. Passing narrow submission control after ASCII repair: activate Create Note Entry. Exactly one prepared BulkEntries contains one NOTE dated **2026-10-22**. It is aborted before transport, so no note is created. While Persian digits are invalid there are0 attempts. Existing refusal prevents a wrong write; this finding is the inability to type valid localized digits.

## Cause and bounded repair

`dashboard/src/common/components/ui/date-picker-utils.ts:209–224` trims the raw input, sends it to date-fns parse and requires an exact format round trip. It never normalizes decimal digits. Installed date-fns `parse/_lib/constants.js:16` uses ASCII `^\d{1,4}` for numeric years, selected by `parse/_lib/utils.js:67–76`; the month/day parsers use the same numeric policy. Even a parse-only change would leave the raw Unicode-versus-ASCII round-trip comparison to fix.

DatePicker's current handleInputChange at:138–149 passes e.target.value directly to this helper; blur/invalid checks reuse the same helper. Normalize Persian U+06F0–06F9 and Arabic-Indic U+0660–0669 decimal digits to their ASCII equivalents before parsing and the strict comparison, then keep the existing ASCII canonical YYYY-MM-DD result. Preserve the active locale's order/separators, full four-digit year requirement, Gregorian calendar, invalid/partial draft retention, month-length checks, ISO fallback and timezone-independent civil days. No calendar conversion, OS keyboard setting, new dependency, backend/API change or translation key is indicated. Do not loosen the parser with Date.parse or accept non-decimal numeral characters as digits.

Acceptance: both exact localized-digit inputs resolve to2026-10-22 and enable the same valid Note draft; a held native submit prepares that canonical day once. ASCII and impossible/partial/wrong-order inputs retain their current behavior, including cross-timezone civil-day controls. Add meaningful parser and real DatePicker/form checks, repeat desktop/narrow, and run dashboard format:check, lint, test and build on implementation.
