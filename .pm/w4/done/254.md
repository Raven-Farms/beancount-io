# Preserve source decimal precision in BQL chart tooltips

**Severity:** minor. **Estimate:** 35–50 minutes, dashboard. **A2:** hovering a plotted BQL answer should show the source value rather than a different, fully spelled-out rounded amount.

Production `https://beancount.io`, 2026-10-20, fresh QA-owned isolated headless Chromium 155.0.8059.85 contexts at 1440×1000 and 390×844, English/light, read-only public `open_ledger/example`. Local main `c5e4cd11a`; the deployed chart helper exactly matches local. No ledger writes or substituted responses.

## Reproduce and control

Execute the ordinary read-only query:

```sql
SELECT 'qa-20261020-precision' AS label,
       12345678901234567890.123456789 AS amount
LIMIT 1
```

QueryShell returns HTTP 200, no errors, dtype str/Decimal and row values `["qa-20261020-precision","12345678901234567890.123456789"]`. The rendered result table keeps the exact decimal string at both widths.

Hover the actual bar with the native browser pointer. At both widths the tooltip shows **12,345,678,901,234,567,000**. Digits in the integer part changed and the fractional part disappeared; no approximation marker distinguishes that text from an exact value. Both complete tooltip rectangles remain inside the chart, so this is not the clipping issue already fixed.

Working control in the same narrow context: query the same two-column shape with value `4.00995`. API, table and actual tooltip all show 4.00995. The failure depends on precision beyond the plotted JavaScript number's representation.

Expected: plotting may use numeric coordinates, while detailed tooltip text preserves the source decimal available in the result row. The table and backend result are already exact. This finding does not claim wrong ledger calculations, a corrupt export or a requirement for exact canvas coordinates.

## Cause and bounded repair

`dashboard/src/features/bql/lib/chart-utils.ts:36–47` parses decimal strings with Number. decodeQueryChartValue retains only the numeric amount and optional unit. parseQueryChart pushes those amounts into values and builds the tooltip from numeric chart values; its optional unit formatter also receives the number. The original result row remains available but is not used for detailed display.

Keep numeric series for plotting and retain the original display value/unit for each point's tooltip. Reuse existing lossless decimal/inventory formatting where appropriate; counting fraction digits after Number conversion cannot recover the changed integer digits. Align raw values by point index so repeated category labels do not pick another row. Preserve safe category escaping, units, signs, zeros, supported date/string shapes, mixed-unit/malformed-cell chart omission, bounds, table/CSV data and existing ordinary-value behavior. Do not globally change number formatting or chart defaults, invent precision, add a dependency or alter API output.

Acceptance: call the actual formatter with precise Decimal/int and supported Amount/Inventory values and assert retained source text, including large, tiny, negative and zero cases. Retain the real 4.00995 control and repeated-category alignment. A test of only numeric series values would pass this bug. Repeat native desktop/narrow hover after implementation and run dashboard checks.
