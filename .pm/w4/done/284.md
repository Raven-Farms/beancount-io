# Protect the Accounts Open Account draft while its write is pending

**Minor · dashboard · 60 minutes.** A2: an enabled account-name field must not silently accept edits that the pending success handler discards. Production beancount.io, 2026-10-20, owned isolated headless Chromium 155, English/System theme, desktop 1440×1000 and fresh narrow 390×844 contexts. QA admin/push access to `<qa-owner>/<synthetic-ledger>` only. Local main `df87bd1db`; deployed Accounts chunk `ledger._ledgerOwner._ledgerName.accounts-BrrFcbqV.js`, full deployment revision unverified.

## Live reproduction

1. Snapshot the designated disposable ledger. Open Accounts → Open Account. Use a controlled delay immediately before the genuine BulkEntries request is transmitted; do not replace its payload or response.
2. Submit `Assets:Qa-20261020:Open-Pending-A`. The held payload contains A. The submit button becomes disabled, but Account Name and Cancel remain enabled.
3. Fill Account Name with `Assets:Qa-20261020:Open-Pending-B`. The real input accepts and displays B while A remains pending. The inspected dialog screenshot shows that accepted newer value alongside the pending spinner.
4. Release the original request unchanged. HTTP 200 returns success:true, “Added 1 entry successfully”. The dialog closes and its account-name input disappears. Actual source contains exactly the original A open directive; B is lost. The backend correctly honored A's submitted payload—no server substitution or duplicate write is claimed.

Fresh narrow reproduction independently confirms the pending-dialog boundary: submit C, Cancel while that request is held, reopen through the visible **New** link and enter D. The reopened input is editable and its submit button is enabled even though C remains pending. No second submit was attempted. Before releasing C, a guard detected another run's intervening ledger change. C was aborted before transmission and the other run's bytes were left untouched. Narrow success and dismissal of D are therefore unverified; the genuine successful-edit-loss case above is desktop evidence.

## Cause and bounded repair

`dashboard/src/features/ledger-data/accounts/open-account-dialog.tsx:73–107` awaits addEntryOpen, then unconditionally resets the current form and closes it. Only the submit button consumes formState.isSubmitting at :184. Account/date inputs and the dialog's dismissal paths have no matching pending policy. handleDialogOpenChange resets immediately on close, allowing a new editable lifetime while the original handler is still awaiting its result.

Make input, dismissal and completion ownership coherent for this specific Accounts dialog. A bounded pending lock is sufficient: do not accept edits or reopen a new lifetime that an older success will erase, retain a useful retry draft on failure, and serialize button/keyboard submission paths. Preserve ordinary idle Cancel's intentional reset, validation, canonical civil-date strings, account availability, write-outcome reporting and successful focus return. No persistent draft store, new dependency or backend/API change is needed.

Acceptance: drive the actual dialog/form with a deferred genuine mutation boundary. Its pending state must not accept a newer account/date and then discard it on success; Cancel/Escape/close/reopen cannot let an old result act on a newer draft. Cover successful completion, refusal/network failure and retry, idle Cancel/reopen, and button/keyboard single submission. Keep pending controls accessible, restore normal editability after failure, and repeat native desktop/narrow journeys. Run dashboard format/lint/test/build.
