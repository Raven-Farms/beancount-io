## Objective

Keep an owned, usable focus target during pending modal submissions and restore a logical retry position on failure without stealing a deliberate focus move.

## Verification

- `dashboard/src/common/hooks/use-pending-submit.ts` now owns the pending focus lifecycle. When the lock disables the control that submitted, the hook parks focus on the nearest focusable region around it: New Entry's visible tab panel, or the dialog itself in Accounts and Budget. That puts a focusable element on record as Radix FocusScope's last-focused node. When the lock lifts after a failure, the origin gets focus back if focus is still on that region, on the dialog, or nowhere. A deliberate move to Close or another control is kept. `onValid` resolves `true` once the entry is written; the six callers (four New Entry forms, Accounts Open Account, Budget) return it from their success branch, so a write that succeeded hands nothing back.
- Root cause, observed in local Chromium 155 against a production build: the disabled submit fires `focusout` with no related target, Radix falls back to the `tabIndex=-1` dialog container, and native Shift+Tab from that container targets the background `Query` link. Locally only Radix's outside-focus bounce intercepted it; in QA's production run it did not. Parking explicitly on New Entry's `tabIndex=0` panel keeps the native Tab sequence inside the dialog. In the same runs, parking on the container still proposed the background link.
- Kept: field locking, single-flight guards, pending dismissal and tab protection, validation, accepted values, and successful return focus. No global focus manager, copied Radix trap, re-enabled field, Button change, backend or API change, or dependency.
