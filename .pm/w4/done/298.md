# Make calendar arrow keys follow the rendered RTL day grid

**Severity:** minor (keyboard direction). **Estimate:** 45–60 minutes, dashboard. **A2:** a Persian-language keyboard user should reach the neighboring date in the direction they press, before committing a bookkeeping day.

Production `https://beancount.io`, 2026-10-21 America/Los_Angeles, QA-owned isolated headless Chromium155.0.8059.85. ## Reproduction and working controls

1. Open `/ledger/<qa-owner>/<synthetic-ledger>/accounts?lang=fa`, then the actual Open Account link (`باز کردن حساب`). In Open Date (`تاریخ باز کردن`), type ISO `2026-08-12` and Tab to commit. The localized field correctly displays `2026/08/12`.
2. Focus that field and press ordinary ArrowDown. From Today, native Tab through the calendar controls reaches the selected August12 day button. The document and calendar's computed direction are RTL; the calendar root has no explicit dir attribute. August13 is visually left of12, and August11 is to its right.
3. Press ArrowLeft. At390px, focus moves from August12 at x217 to August11 at x249: **32px to the right**, on the same row. ArrowRight returns from x249 to217, moving left. Fresh1440px repeats x972→1004 for ArrowLeft and back for ArrowRight. The initial independent narrow survey reproduces the same result.
4. Working vertical control: ArrowDown from August12 reaches August19, +40px vertically with the same x; ArrowUp returns. Working pointer control: clicking August13 selects it and displays `2026/08/13`.
5. Native Enter after the erroneous horizontal move selects the actually focused August11 and displays `2026/08/11`; the field accurately reflects that focus target. This is a directional navigation failure, not date-serialization corruption or a claim that an entry was saved.
6. Fresh390px English control: the grid is LTR and ArrowLeft moves August12 at x208 to August11 at x176, correctly 32px left. ArrowRight returns, vertical controls work, and pointer selection displays `08/13/2026`. Escape dismisses each unsaved Open Account dialog and returns focus to its exact opener.

All three retained fresh cases have zero mutation attempts and page errors; narrow documents remain390px wide. No Account submit was attempted. Screenshots show the focus ring on11 to the right of the still-selected12 in Persian, versus11 to the left of12 in English.

## Root cause and bounded repair

`dashboard/src/common/components/ui/calendar.tsx:31–42` passes the active date locale to DayPicker but supplies no default `dir`. Its only production Calendar consumer, shared DatePicker, also supplies none. CSS inherits RTL and the wrapper manually rotates month chevrons, so layout looks localized, while DayPicker's keyboard logic still receives undefined direction.

Installed `react-day-picker` **9.13.0**, `dist/esm/DayPicker.js:176–182`, maps ArrowLeft to the following day only when `props.dir === "rtl"`; otherwise it maps to the previous day. ArrowRight uses the inverse mapping. This directly explains the observed coordinates. The upstream [v9 direction contract](https://daypicker.dev/v9/api/interfaces/PropsBase#dir) supports an explicit RTL prop; no upstream fork or dependency upgrade is needed.

Bridge the active application direction into the shared Calendar's DayPicker props, using the existing localization/direction source and preserving an explicit caller override. Do not fix this by forcing the visible grid LTR, adding per-form Persian checks or intercepting arrow keys. Audit the wrapper's two manual RTL chevron rotations: DayPicker already changes the Chevron orientation when dir is RTL, so retain correct previous/next icons and actions without double mirroring. Preserve Persian labels/week start, month/year navigation, selected-day identity, native focus/Enter/Escape, ordinary LTR behavior and the UTC-backed civil-day contract, including skipped local dates.

Acceptance: in the actual Persian grid at desktop/narrow widths, ArrowLeft from August12 reaches the visually left August13 and ArrowRight returns; English retains August11 as its left neighbor. Vertical keys, native selection, month controls and dialog return focus remain correct. Add a meaningful real Calendar/DayPicker integration regression for RTL/LTR, explicit direction overrides and application-direction changes; a dir/class-string assertion alone is insufficient. Run the dashboard gates when implementing.
