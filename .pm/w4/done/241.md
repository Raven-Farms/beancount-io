# Complete file saves without discarding newer edits

**Severity:** major, upgraded after the pending-save reproduction below. **Estimate:** 45–60 minutes, dashboard. **A2:** successful saves must retain any newer edits accepted while the write is pending, and complete the intended view-mode transition when the whole draft was saved.

## Live reproduction

Production `https://beancount.io`, 2026-10-20, English/light, QA-owned headless isolated Chromium 155.0.8059.85, disposable-ledger owner. Local main `c5e4cd11a`, deployed `main-D9qWGMxD.js`; full deployed revision unverified. Real UI writes and responses, with no response substitution or delayed network.

1. Create prefixed `qa-20261020-notes.txt` through Files → Create File. The file contains a short UTF-8 text fixture; creation returns to the directory and an independent API read matches its bytes.
2. Open the file at 390×844, enter edit mode, wait for the actual editable input and Save toolbar, change its content, and click **Save**. `UpdateLedgerFile` succeeds. Independent file read returns the exact new text, 55 bytes, and commit `252cbcc71ef33716f0505d8bcc94a5816ad80360`; ledger errors are empty.
3. After the metadata/file reads settle, the URL still contains `?editMode=true` and Save/Cancel remain visible. Waiting another 30 seconds does not complete the exit. **Cancel** now exits normally without a dirty warning because the saved source matches the buffer.
4. Fresh-reload the file at 1440×1000 and repeat with a different draft. This saves exactly 53 bytes in commit `dea232246d7bd725a0488ccc148f751ffd6273c1` but again settles in edit mode. Passive DOM observation records **Unsaved Changes → Stay / Leave Without Saving** appearing during the successful-save transition, then disappearing as the layout refreshes. The observer only records DOM changes; it does not change focus, application state or responses. No dialog remains after settlement.

Expected: the successful write's own exit reaches view mode once when its snapshot covers the entire current draft, without an unsaved-changes choice. In these original runs all typed content was saved correctly, but the exit was blocked and lost during refresh. Clean Cancel is a working control; the injected-network control below verifies rejected-save feedback and draft retention. The later pending-save sequence establishes an additional data-loss consequence of this same save/refresh lifecycle.

## Cause and bounded repair

`dashboard/src/features/ledger-editor/file-editor/components/ledger-file-view/text-file-view.tsx:140–157` awaits onSave then calls onExitEditMode. `file-edit-mode.tsx:70–77` blocks every navigation while editedContent differs from the old plainContent, including this save-success navigation; it has no success handoff. Parent `ledger-file-view/index.tsx:132–158` clears ROOT_QUERY on completion without awaiting the refreshed file/layout. That makes the old dirty guard relevant before the new source arrives, then unmounts the dialog through `common/components/ledger-layout/index.tsx:101–102`. The installed TanStack useBlocker (`node_modules/@tanstack/react-router/src/useBlocker.tsx:210–240`) waits for an explicit resolver decision when shouldBlockFn is true; successful mutation alone does not bypass it.

Coordinate the saved buffer, successful navigation and authoritative refresh. Permit only the completed save's covered exit, keep genuine dirty departures guarded, and retain drafts after rejected saves. Account for newer edits typed while a write is pending rather than declaring every draft saved. Preserve current file identity, SHA conflict handling, source-error warnings, keyboard Save, duplicate-write guard, view permissions and ordinary Cancel/Stay/Discard behavior. No API/dependency change is indicated.

Acceptance: a real router, TextFileView/EditModeToolbar, parent mutation/cache behavior and ledger layout exercise success through settled refetch. Assert exact persisted text, view-mode URL/controls, no transient unsaved dialog, one write, and retained failure/dirty controls. A second edit accepted during a held successful save must survive the actual cache refresh as dirty content; only the submitted revision is saved. If editing is instead prevented while pending, verify actual Monaco keyboard input is read-only before it can accept that second revision. A no-op onExit callback or isolated Save mock cannot prove this lifecycle. Repeat desktop/narrow synthetic journey and verify restoration. Run dashboard format/lint/test/build when implementing.

## Pending save discards newer edits — major

Later in the same continuous run, create `qa-20261020-pending-save.txt` on the designated disposable ledger (commit `642042c671b7ac45f4b25ed4debde32b3a07e657`). Repeat at desktop and from a fresh 390px page:

1. Enter `qa-20261020 first saved revision 1440` plus a newline. Start Save and hold only that file's real UpdateLedgerFile request inside the owned browser before transmission. No response is substituted.
2. While Save is disabled, the actual Monaco editor remains `aria-readonly=false`. Replace its buffer with `qa-20261020 second UNSAVED revision 1440` plus newline. The second revision is visibly accepted while the original save is pending.
3. Release the request unchanged. It succeeds with the expected first revision. After authoritative refresh, the editor displays **the first revision** again; the newer accepted text has disappeared. It remains at `?editMode=true` with no settled dirty dialog and no user discard action.
4. Fresh-reload at 390px, repeat with `390` in both revisions, and wait for each actual Monaco rendering before proceeding. Same loss. A passive DOM observer confirms the original editor disconnected during refresh and records the transient Unsaved Changes dialog disappearing. Native editor Undo after settlement leaves the first revision unchanged; it does not recover the newer text.

Independent readbacks contain only the submitted first revisions: desktop commit `ce2459cd5ee83ce20e90917a0822befef06f0c8a`, narrow `43be51ae532d13b87a25868c78e7c9af99e5ab77`; both have zero ledger errors. Those correct server writes are not evidence that the later client edits were saved.

The shared cause is now directly observed: `text-file-view.tsx:66` owns the only draft buffer, `:217` passes readOnly based only on edit mode (not pending save), and `:145–150` exits after the submitted snapshot completes without comparing a newer revision. `ledger-file-view/index.tsx:153` clears the root cache; its file/loading branches and the ledger layout replace the subtree, remounting the buffer from the saved source. Keeping the editor component's render-time sync guard alone cannot retain state after this unmount. Repair the covered-save handoff and prevent any accepted newer draft from being discarded across refresh; preserve the existing single-write guard and the passing failed-save/Stay/retry control.
