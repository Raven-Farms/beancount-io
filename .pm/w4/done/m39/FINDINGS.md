Its query variables at :186–200 use .length; journal-filters.tsx consumes .includes, .filter and array spreads for directive and subtype selections. `common/hooks/use-local-storage-state.ts:76–85` catches invalid JSON syntax, but a successfully parsed object/null is cast to T without shape validation. The same Journal page also has two boolean display choices; preserve them rather than clearing all Journal state.

Validate these arrays at the feature boundary. Keep known DirectiveType values and valid subtype strings, including legitimate empty-string custom values; do not invent a closed enumeration for free-form custom subtypes. Invalid containers need safe feature defaults, valid empty arrays remain intentional, and valid stored choices must not silently reset. Backend enum inputs must never receive invalid decoded types.

Initial quick SSR text before client hydration is excluded; assertions use the settled client state. No release links, social actions or server mutations were invoked.

`common/hooks/use-changelog-watermark.ts:116–120` reads string[] with syncAcrossTabs=true and no decoder; :146 passes it directly to new Set. The hook later spreads the prior readIds when marking a release read. useLocalStorageState's native storage handler at :157–173 likewise publishes any successful JSON.parse result. Validate the read-identities list through the existing deserializer for both initial reads and cross-tab updates. Preserve arbitrary valid identity strings and locale-independent release semantics, without requiring every past identity to be in the currently fetched five releases. Invalid updates should leave a safe/last good state rather than throw during render. Preserve the separate valid seenThrough/flaggedFrom watermarks and device-local policy. No new persistent server state or user-facing cache-management flow is needed.

## Remaining subtype-domain gap — t007

**Minor, bounded25m follow-up in dashboard; original shape fixes above remain effective.** A saved array can have the correct container/member types while containing unsupported subtype strings. Public Example Journal at `/ledger/open_ledger/example/journal?time=2016` still forwards them to the real API, which rejects them. This is narrower than the original JavaScript crash and shares the same persisted preference-to-query boundary.

Fresh1440/390 reproducer: set only `journal.open_ledger/example.transactionSubtypes` to `["*"]` in the isolated context and load Journal. The actual GraphQL request includes directiveTypes=[Transaction], transactionSubtypes=[*], time=2016, offset0, limit60. The real HTTP200 response has `BAD_USER_INPUT`, field transactionSubtypes, message `Unknown transactionSubtypes value "*"`. The UI has zero tables and `Error loading journal entries: Some of the information provided is invalid. Please check and try again.` Reload repeats the same request/error. Replacing that key with `["cleared"]` and reloading restores a real60-entry response and one table; the unrelated canary survives.

Independent fresh controls isolate the other two adapters: desktop documentSubtypes=[attached] is rejected as `Unknown documentSubtypes value "attached"`; changing it to [linked] restores60 entries. Narrow customSubtypes=[the empty string] is rejected as `Unknown customSubtypes value ""`; [budget] restores60 entries. Each failure repeats after reload. These four retained cases forward the real unchanged read response and do not simulate the API result. The earlier exploratory mixed-invalid case is supplementary; individual fields above identify each failure. The narrow Transaction error screenshot was visually inspected.

Cause: JournalPage's `subtypesStorage` applies `decodeStringList(raw)` without a domain predicate, so all strings pass to query construction; only directiveTypes has an allowed-value predicate. The three subtype adapters share that options object. Backend `normalizeJournalKinds` deliberately accepts only the current kind enums, case-insensitively, and rejects other values. Its completed W23/006 contract (`2af6a4d78`) remains required; do not weaken the backend to accept malformed browser preferences. Current UI values are transaction cleared/pending/other, document discovered/linked, and custom budget. The actual product regression in `journal-saved-filters.test.tsx` currently asserts transaction values `!`/`*` and an empty Custom subtype reach the mocked query, so it misses the real API rejection. t001's original “valid subtype strings including empty custom values” assumption is contradicted by these live controls and needs correction through t007.

Repair the dashboard deserialization/query boundary so unsupported subtype values are discarded or deliberately migrated from a proven legacy spelling before they can poison a read, using the current UI/API kinds. Preserve valid values, empty arrays, non-string filtering, per-ledger keys, Metadata/Postings and unrelated storage. Keep one source for supported UI values where practical; no new dependency or cross-package import. Meaningful regressions must check actual supported kinds against this boundary and fail if the predicate is removed; replace the incorrect accepted-invalid expectations. A valid-array/invalid-member control must not be confused with a malformed-container fallback. Do not claim old browser data is rewritten unless persistence migration is actually implemented and verified.

Dedupe searched all board states for Journal subtype strings, saved arrays, decodeStringList and unknown kinds. This extends M39 rather than creating a duplicate note. W23/006 owns strict API normalization and is already complete; W3/463 owns per-ledger preference keys and stays preserved. Targeted source history through536a2619a shows no later dashboard subtype-domain guard. Root and nested dashboard guidance were followed; the fix belongs only to dashboard and requires no API/parity change.

Ignored evidence under `dashboard/tmp/qa-20261020/dashboard-loop/`: `m39-deployed-complete-controls.json`, plus `m39-subtype-{transactionSubtypes,documentSubtypes,customSubtypes}-<width>.png`.
