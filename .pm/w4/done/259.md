# Reject new drops while an upload batch is pending

**Severity:** minor (accepted file selection is discarded). **Estimate:** 25–40 minutes, dashboard. **A2:** Files must not show a newly dropped file as selected, finish the older batch, then silently omit the new file and remove its selection.

Production https://beancount.io, 2026-10-20, local main `c5e4cd11a`; two separate fresh QA-owner contexts at 1440×1000, English/light, isolated headless Chromium155.0.8059.85. Real upload requests are held inside the browser, then continued unchanged. Drop delivery uses Playwright DOM drag/drop with a real browser File/DataTransfer object and isTrusted=false. Native OS dragging and physical mobile drops are explicitly unverified.

## Fresh reproduction and controls

1. Files → Upload Files. Stage prefixed text file A through the file input and click Upload Files. Hold only its real CreateLedgerFile before transmission.
2. Choose your files, Remove and Cancel are disabled while the request is pending.
3. Dispatch a DOM file-drop B onto the actual visible drop zone. The production handler accepts it: Selected files (2), A and B both listed, B's Remove disabled. No application handler is mocked.
4. Release the unchanged real A request. HTTP200 creates A with exact original content, then the page navigates to Files. A exists; B was not uploaded. Automated Back reopens an empty upload form, zero staged rows, Upload disabled.
5. A fresh desktop context repeats with distinct A2/B2. Same accepted selection, real successful original write, omitted B2 and empty Back form.

Working failure control: a third fresh desktop context accepts A/B in the same way, then the held Create request is aborted before transmission. Both selections remain, a useful Connection problem message identifies A, Remove/Upload re-enable, and Cancel leaves normally. Nothing is written for that control. The loss is tied to success departure, not ordinary selection or failed-request retention. The local source files themselves remain on disk; this finding is loss of the staged selection, not destroyed file contents.

## Cause and bounded repair

`dashboard/src/features/ledger-editor/upload-files/index.tsx:153` snapshots selectedFiles into batch. The picker button, row removals, comment and Cancel consume isUploading, but handleDrop at :248–255 always stages its dataTransfer files. The loop only writes the captured batch, removes its original File objects at :198, then navigates unconditionally at :202–211, leaving accepted later selections behind in unmounted state.

Apply the same pending-input contract to the drop path and other file-selection entrypoints. A bounded busy guard that does not accept/stage new drops is sufficient and consistent with the disabled picker. Preserve ordinary idle drops, multiple-file staging/re-picks, size/name validation, permissions, partial-batch failure/retry and the successful original batch. Do not silently stage files the current success cannot retain, automatically upload an unreviewed later batch, or add persistent draft storage. No API, dependency or cross-package change is indicated.

Acceptance: hold real upload creation and the awaited directory-refresh interval, attempt another DOM drop through the rendered production zone, and verify it is not falsely accepted and then discarded. Normal idle drops work; failure retains the accepted original queue; original success books each intended file once. Include keyboard picker and cancellation regressions. If verifying native OS drag during implementation, record that separately from synthetic event coverage. Run dashboard checks.
