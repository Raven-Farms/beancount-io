# Apply the newer budget when Update Budget writes another directive on the same date

**Severity:** major. **Estimate:** 45–60 minutes, dashboard. **A2:** revising today's spending target must change the budget comparison a newcomer sees.

## Reproduce

Production `https://beancount.io`, 2026-10-20, QA-owned headless isolated Chromium 155.0.8059.85, English/light, authenticated owner of a designated disposable synthetic ledger. Reproduced at 1440×1000 and 390×844, including fresh reloads. Local main `c5e4cd11a`; production asset `main-D9qWGMxD.js`, full deployed revision unverified. These are real UI writes and real API responses, without response substitution.

1. On `/ledger/<qa-owner>/<synthetic-ledger>/budget`, use Add Budget to create `Expenses:Qa-20261020-Budget`, date `2026-10-20`, Monthly, `123.45 USD`.
2. On its card, use **Update Budget**, retain the same date/account/currency/cadence, and submit `234.56 USD`. Both `BulkEntries` responses are HTTP 200, `success:true`, `Added 1 entry successfully`.
3. Reload. Both history rows persist, but **Current budget** stays **47.79 USD**, with variance **−47.79 USD**. That is the older 123.45 target prorated over October 20–31 (`123.45 × 12 / 31`). The newer target should produce **90.80 USD** (`234.56 × 12 / 31`). There are no ledger errors or browser exceptions in this normal journey.

API/source control: `getLedgerJournal` filtered to Custom/budget returns the same-date entries **234.56 first, 123.45 second**. The file contains 123.45 at line 89 and the later appended 234.56 at line 92. Deleting only the older 123.45 row through the real confirmation and reloading leaves one 234.56 row and changes the headline to **90.80 USD**. Thus the second write and its value are valid; the tie is resolved incorrectly in the reader. The original file was subsequently restored byte-for-byte; its SHA-256 matches the pre-write snapshot and `getLedgerErrors` is empty.

## Cause and bounded repair

`dashboard/src/features/ledger-data/budget/budget-utils.ts:92–97` stable-sorts by date alone, then reverses to choose the current directive. Equal-date entries retain the API's newest-first order, so reversing picks the older one. `budgetHistory` at lines 105–110 retains that same inverted tie order; `calculateBudgetForInterval` at lines 173–186 stable-sorts it again and advances through every eligible directive, ultimately applying the older target. `budget-history-table.tsx:57–60` reverses it for display, putting the older directive first as well.

The producer deliberately reverses the chronological compiled stream in `backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:610–618`; its ordering is correct for a journal. Preserve that contract. Normalize the dashboard's budget history to chronological order **including compiled/source order for equal dates**, so the later directive wins consistently for the group, cadence, chart/headline calculations, and newest-first history. Entry hashes are opaque identifiers, not sorting keys. Keep the existing daily proration, future-date handling, account/currency grouping, sparse actuals, and permission policy.

The sole production dashboard caller is `budget/index.tsx:187`; all its cards use this history. The mobile package owns a separate selector; it was found during the caller search but not exercised and is not an additional claimed finding. No REST, GraphQL, MCP or producer behavior change is needed.

Acceptance: feed actual newest-first journal-shaped data with two same-date targets into the rendered Budget page; assert the latest target, history order, and prorated headline, then repeat the UI Add → Update → reload journey at both widths. Cover a same-date cadence change, different dates, future targets, separate currencies, empty/loading/error states, and deletion of either duplicate without conflating their hashes. Existing distinct-date tests must continue to pass. Run dashboard format/lint/test/build when implementing.
