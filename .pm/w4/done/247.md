# Prevent Create File success from discarding edits accepted while pending

**Severity:** major. **Estimate:** 30–45 minutes, dashboard. **A2:** a successful file creation must not silently discard a newer filename and text that the form still allowed the user to enter.

Production `https://beancount.io`, 2026-10-20, English/System theme, QA-owned headless isolated Chromium 155.0.8059.85, disposable synthetic ledger owner. Fresh 1440×1000 and 390×844 journeys. Local main `c5e4cd11a`; deployed CreateFilePage source exactly matches local. Real requests were held inside this browser and then continued unchanged; no response data was substituted.

## Reproduce

1. Open `/ledger/<qa-owner>/<synthetic-ledger>/files/new/main`. Name the file `qa-20261020-create-pending-1440.txt` and enter `qa-20261020 saved create revision 1440` plus newline.
2. Start Save and hold that file's real CreateLedgerFile request before transmission. Save and Cancel are disabled, but the filename input remains enabled and Monaco remains `aria-readonly=false`.
3. Change the filename to `qa-20261020-create-pending-1440-newer.txt` and replace its text with `qa-20261020 NEWER UNSAVED create revision 1440` plus newline. Verify the newer text is actually rendered before releasing the request.
4. Release the unchanged request. The UI automatically navigates to the directory without a discard choice. Only the original filename exists, containing only the original submitted revision. The accepted newer filename and text are gone. Back returns to a blank Create File form, not that newer draft.
5. Fresh-reload at 390px and repeat with `390` in the filenames/revisions. The exact newer Monaco rendering is observed before release; the directory again contains only the original submitted filename/revision, with no settled dirty dialog.

Correct server readbacks: desktop creation `7110a8ecce3cd1ca3419ae999e062146ab6a3318`, blob `d79019f27fce83fb242bd295ebc3c7ab0c9d8ca5`; narrow creation `b4790d915296105f7a7988107928f990ab3e27e1`, blob `a79ce47aa7f813ba61b3b4c1d50ed85e263decb2`. Both have zero ledger errors. This is lost later client input, not a claim that the server wrote the wrong original snapshot.

## Cause and bounded repair

`dashboard/src/features/ledger-editor/create-file/index.tsx:146–169` submits the captured filename/content and awaits creation plus directory refetch. At `:173–175` it unconditionally enables `allowNavigationRef` and navigates away. The blocker at `:109–118` consumes that bypass without comparing the current draft to the submitted snapshot. Filename `:224–231` is not disabled while saving, and Monaco `:277–300` has no pending read-only option or change guard.

Make pending inputs and successful departure coherent: disable filename editing and actual Monaco input for the full creation/refetch interval before accepting further input, and retain the existing draft on failure. The success bypass must cover only the submitted draft. Do not add autosave or persistent draft storage; preserve ordinary successful creation, safe-name/duplicate checks, permissions, Cancel/Stay/Leave, and single-submit behaviour. Only CreateFilePage owns this implementation. The canonical new-file route, directory Create File action and legacy `/files/create` redirect reach it; nested directories are source-derived scope, not separately live-tested.

Acceptance: render the real page, Monaco, router and mutation/refetch boundary; hold creation and exercise native keyboard editing attempts on both filename and content. Neither accepts uncovered edits while pending; success stores exactly the submitted snapshot and navigates once without an unsaved prompt. A failed create retains the accepted draft and supports retry/Cancel/Stay. Repeat at both widths, including the awaited refetch phase, then run dashboard checks. No API, dependency or cross-package change is required.
