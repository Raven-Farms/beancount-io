# Preserve an existing UTF-8 BOM when saving text files

**Severity:** minor (unrequested encoding-marker loss). **Estimate:** 40–55 minutes, dashboard. **A2:** an ordinary text edit should preserve the file's existing UTF-8 marker while saving exactly the requested characters.

## Reproduce and working controls

1. Create a new prefixed CSV file through the API with raw UTF-8 bytes: initial `EF BB BF`, followed by `payee,city\r\nqa-20261020 original,café\r\n`. It is43 bytes. Independent readback confirms the marker and exact seed blob; this is setup, not evidence of a browser upload failure.
2. Open its canonical Files blob route with `?editMode=true`. Native editing is allowed. Insert a QA prefix at the beginning of the text and activate the real Save button, without requesting any formatter/encoding conversion.
3. At narrow width, the inserted prefix is the12-byte `qa-20261020 `, so the expected edited file is55 bytes including its original BOM. The actual UpdateLedgerFile request is already marker-free,52 bytes. HTTP200 stores exactly those same bytes. All requested text, café and the two CRLF pairs are preserved; only the three original marker bytes disappear.
4. Independently reseed the original BOM bytes before the fresh narrow case. Desktop also loses exactly three bytes:73 expected versus70 actual for its larger Unicode prefix. The first desktop Meta+End attempt did not move the caret; the retained edit is its actual prefix insertion, independently matched against original text. No cursor-movement or lost-text defect is claimed.
5. Final matched diagnostics use two new files with the same text, one seeded with BOM (43 bytes), one without (40 bytes). Apply the same native12-byte prefix edit to each. Both send/store the identical52-byte body. The plain UTF-8 case is correct, while the BOM case should retain its extra three bytes. Both preserve Unicode/CRLF and have zero page errors or unexpected console errors. Intentional analytics-collector abort noise is excluded. This isolates marker loss from general text serialization, transport, server normalization or a failed save.

The app's own `common/lib/export/csv.ts:54–60` intentionally includes a BOM for reliable Unicode handling in Excel. [Microsoft documents normal UTF-8 CSV opening when the file has a BOM](https://support.microsoft.com/en-gb/excel/opening-csv-utf-8-files-correctly-in-excel). No actual Excel session or downstream corruption is claimed; the directly observed defect is ordinary Save removing an existing marker without a requested format change.

## Cause and bounded repair

`common/lib/utils/encode.ts:70–78` decodes base64 with default TextDecoder behavior, which strips the initial UTF-8 BOM. The same raw-byte runtime control confirms that behavior. `features/ledger-editor/file-editor/components/ledger-file-view/text-file-view.tsx:58–59` uses that decoded value as plainContent and the editable buffer. On Save, `ledger-file-view/index.tsx:132–142` passes the marker-free string to base64Encode without retaining the original file's encoding marker. Actual request inspection shows the loss already happened in the client; Create/reseed preserve it and the server stores the submitted payload byte-for-byte.

Retain the original file's BOM presence independently of its decoded editor text and preserve it once when serializing an ordinary edit. Keep BOM-free files BOM-free. Preserve requested characters, Unicode, CRLF/LF behavior, existing file SHA compare-and-swap, pending-draft ownership, error/retry and permission handling. Avoid duplicating the marker or globally adding one in base64Encode. Keep generic base64Decode/README decoding semantics intact: ledger-readme.ts is the other production decoder consumer and needs no file-save policy change. No backend/API, new dependency, cross-package import, encoding-converter UI or unrelated formatter change is required.

Acceptance: a real incoming base64 BOM file followed by an ordinary edit emits/stores the original marker plus exactly the edited UTF-8 body. A no-BOM counterpart remains byte-exact without a marker; Unicode and both common newline styles remain intact. Exercise the actual decode→editor→Save path with meaningful payload-byte assertions, plus existing error/read-only controls. A helper-only roundtrip or mocked decoder that already retains a BOM would miss this failure. Run dashboard format/lint/test/build when implementing.
