# Submit the currency that transaction auto-balance actually used

**Severity:** minor. **Owner:** dashboard. **Estimate:** 45–60 minutes. **A2:** an inferred balancing posting should use the same monetary unit in the prepared request as in the form's calculation.

## Reproduction and controls

Production https://beancount.io,2026-10-21 America/Los_Angeles, owned isolated headless Chromium155.0.8059.85, English/light, authenticated QA owner of the designated disposable synthetic ledger. Fresh390×844 and1440×1000 form cases; local main `7e884dd09`, full deployed revision unverified.

1. Use a synthetic ledger with operating currency USD and existing open `Assets:Cash` and `Expenses:Food:Groceries` accounts. Journal → New Entry → Transaction. Add a uniquely qa-prefixed narration.
2. Set posting1 to Assets:Cash, amount **0.1**, currency USD. Set posting2 to Expenses:Food:Groceries, leave its amount empty, and clear its currency, committing the empty field with Enter.
3. The second amount displays **−0.1 / auto**, Create Transaction Entry is enabled, and no account-creation consent is needed. A blank unused third row is ignored correctly. The prepared BulkEntries postings are:

   ```json
   [
     {"account":"Assets:Cash","units":{"number":"0.1","currency":"USD"}},
     {"account":"Expenses:Food:Groceries","units":{"number":"-0.1","currency":""}}
   ]
   ```

4. One exact, allowlisted prefixed request was forwarded from the narrow form after snapshotting the clean disposable ledger. The real server returns HTTP200 / **UNBALANCED**, message **entry 0: Transaction does not balance: residual 0.1 USD, 0.1** followed by the blank currency. The dialog remains open and says **Postings don't balance: 0.1 USD, 0.1 left over. Adjust an amount, or clear one to balance it automatically.** The amount is already cleared and inferred; the unit used for calculation was lost during serialization.
5. The independent desktop form prepares the same empty-currency mismatch; that request is blocked before transport. A narrow passing prepared-request control explicitly restores USD to posting2 and produces **0.1 USD / −0.1 USD**. It is also preblocked; no successful booking is claimed.

## Cause and bounded repair

`dashboard/src/features/journal/components/new-directive-dialog/transaction-auto-balance.ts:48` groups a blank/whitespace posting currency under `primaryCurrency`. It records that effective currency with the inferred amount at70–73. `applyAutoBalanceToPostings` at94–97 copies only the inferred number back into the posting. The residual checker likewise substitutes the primary currency at137, so the client sees a balanced USD group. But `transaction-form.tsx:254–262` serializes `currency: posting.currency`, preserving the original empty unit.

Resolve the effective currency consistently for eligible postings before inference, residual validation and request serialization. Under the current primary-currency fallback policy, the case above must prepare USD for both postings. Cover a filled amount with a blank currency as well as an inferred amount; changing only the inferred row would leave the same mismatch on the filled side. Preserve explicitly selected currencies, exact decimal amounts, independent currency groups, account/date availability, pending-submit behavior and exclusion of unused blank-account rows. Do not guess a new unit, perform FX, relax server validation or require a backend/API change.

Acceptance: meaningful form-to-request coverage must show the advertised −0.1 default-currency inference produces the corresponding USD payload; include empty/whitespace currency on the filled and inferred sides, explicit currencies and unused rows. Preserve the existing fully specified residual refusals and multi-currency decimal checks. Repeat desktop/narrow, confirm the corrected case no longer reaches the observed empty-unit refusal, and run dashboard format:check, lint, test and build when implementing. No product fix or tests were authored by QA.
