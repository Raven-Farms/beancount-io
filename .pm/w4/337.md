# Offer a retry after a Holdings read fails

**Severity:** minor. **Owner:** dashboard. **Estimate:** 35–50 minutes. **A2:** a reader encountering the Holdings connection guidance should be able to retry that view beside the error.

## Reproduction and controls

Production https://beancount.io,2026-10-21 America/Los_Angeles, anonymous public synthetic `open_ledger/crypto-example`, English/light, QA-owned isolated headless Chromium155.0.8059.85. Fresh1440×1000 and390×844 contexts independently reproduce. Local main `3f2e0ce31`; full deployed revision unverified. **The failed reads are browser-local request aborts before transport, not an observed production outage.**

1. Open `/ledger/open_ledger/crypto-example/holdings?view=by-currency`. Abort only the `QueryShell` read for that ledger; let unrelated reads proceed normally.
2. After settlement, the selected grouping remains **Holdings by Currency**. Its panel shows the accessible alert **Connection problem. Please check your internet connection and try again.** There are **zero buttons and zero tables in the panel**, including no Retry/Try Again action. One matching read was aborted in each context. At390, the named View selector remains usable and document width remains390.
3. Remove the fault. At1440, reload the same URL: the Currency table returns with **15 rows including its header**, no alert and enabled Export CSV. At390, use View to choose **Holdings by Account**, then **Holdings by Currency**: the original Currency table likewise returns with15 rows, no alert and enabled export. This is an absent local recovery action, not unavailable holdings, an empty state, a lost grouping or a permanent navigation trap.

## Cause and bounded repair

`dashboard/src/features/ledger-data/holdings/holdings-table.tsx:60–66` obtains `data/loading/error` from the current `QueryShell` observer, omitting `refetch`. Its error branch at290–297 renders only Alert/AlertDescription with the existing classified message. The promise to “try again” has no accompanying action. `holdings/index.tsx` renders this same DatasetTable for Holdings, By Account, By Currency and By Cost Currency, each with its own query/row filter; only By Currency's failure is independently live-tested here.

Expose a localized keyboard-usable retry for the current failed DatasetTable query. Reuse existing retry/error UI and translations where appropriate; retain classified guidance. Retry the exact current ledger/query/grouping, handle a repeated rejection, prevent competing activations while pending, and restore that grouping's table/export on success. Preserve the existing loading, empty, row-filter, amount, navigation and download behavior; a late attempt must not replace a different selected grouping. Do not reset the view or require a document reload. No backend, REST/GraphQL/MCP contract, dependency or global query-cache change is needed.

Acceptance: through the real DatasetTable/Apollo lifecycle, fail the initial read, activate Retry by keyboard, verify pending/repeated-failure recovery and eventual success with the original query variables. Confirm the four callers retain their distinct queries, meaningful empty/error separation and working table/export behavior. Repeat desktop/narrow and run dashboard format:check, lint, test and build when implementing. No product fix or tests were authored by this QA run.
