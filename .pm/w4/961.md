
A second supported four-column file whose two amount tokens are `"1,234.56"` and `"1.234,56"` also reaches the same columns/AI offer at both widths, hiding the parser's mixed-convention diagnostics. Do not reinterpret those ambiguous values as valid numbers.

## Cause and bounded repair

`dashboard/src/features/importer/hooks/use-csv-parser.ts` successfully recognizes the supported header, constructs the records and attaches field/column validation errors. `hooks/use-multi-stage-parser.ts:64` returns that result only when `result.validCount > 0 || result.blockLlmFallback`. The latter flag covers unsupported precision alone. Ordinary all-invalid parsed rows therefore fall through to `ai-offer`, whose copy claims the columns could not be read, discarding the already useful repair result.

Carry a structured distinction between recognized rows with validation errors and unreadable/unsupported layout into the orchestrator. Keep supported parsed rows in the existing local repair Preview even when none is yet valid; retain exact raw tokens, complete row diagnostics and disabled Continue until an actual valid row exists. Preserve the explicit AI choice for unreadable formats/unsupported layouts, the existing no-automatic-AI policy, precision safeguards, encoding refusal and valid delimiter/amount behavior. Do not simply route every zero-valid file to Preview, guess unknown columns or weaken amount/date validation. No backend/API change, dependency or new persistence feature.

Acceptance: the sole-invalid-date and mixed-convention files show their real local repair state at both widths; changing the bad date admits exactly the corrected date. Use the real parser and UploadStep/orchestrator in a meaningful regression, with mixed-validity and unsupported-precision controls plus genuinely unknown-column/structural CSV preserving its AI choice. Run dashboard format:check, lint, test and build when implementing.
