# Keep opening-balance choices consistent when ledger presets change

**Severity:** minor. **Estimate:** 40–60 minutes, dashboard. **A2:** a newcomer choosing an opening balance should not review a hidden account from the previous preset or lose an amount entered into an enabled field.

Production https://beancount.io, 2026-10-21, English/UTC, dedicated QA account, owned isolated headless Chromium155.0.8059.85. Fresh1440×1000 and390×844 preset-switch cases, plus fresh390 omission and recovery controls. Real Create Ledger dialog and unmodified successful reads; no response substitutions. Every creation attempt is blocked before transport; no ledger/account/balance is created.

## Reproduction and result

1. Open `/ledger` → Create Ledger → Template, keeping Personal ledger selected. Advance to details; enter a prefixed synthetic name, choose Assets:Bank and type2500 as the opening amount.
2. Back to choices, select Portfolio ledger, then return to details. The visible opening-account select now has value empty and displays **Decide later**. Its options are Decide later, Assets:BrokerCash and Assets:Holdings. Amount2500 remains enabled.
3. Advance to Review. The actual PreviewLedgerSetup variables still contain preset=PORTFOLIO and accounts=[Assets:Bank, KNOWN,2500]. It returns HTTP200/VALIDATION_FAILED: Assets:Bank is not part of portfolio@1. The UI shows that error. Both fresh widths reproduce. The separately blocked CreateLedger attempt contains the same hidden old account.
4. Passing narrow recovery: Back, explicitly choose Assets:BrokerCash, then return to Review. The new preview and blocked create use that account with2500; preview returns HTTP200 with data and no GraphQL errors. The server correctly refuses the prior foreign account; this is client state, not a missing backend check.
5. A separate fresh narrow Personal control keeps Decide later and types2500 into the enabled amount field. Preview and blocked create both omit accounts entirely; successful Review does not show the entered amount. No warning says the amount is unused. This is a local omission, not a claim that an actual balance was booked incorrectly.

Premature creation attempts on Next are independently tracked by [314](./314.md). The guard stops them before transport, allowing these actual preview/variable states to be inspected safely.

## Cause and bounded repair

`dashboard/src/features/ledger-list/components/ledger-form.tsx:236–259` derives moneyAccounts from presetId but retains openingAccount/openingAmount in the shared form. Changing presets at:442 only changes presetId. When the retained account is not an option, the native select visibly falls back to Decide later while React Hook Form still holds Assets:Bank. buildSetup serializes that hidden value whenever amount and openingAccount are nonempty. Conversely, an empty account makes it drop the entered amount without a diagnostic. The amount control at:587–607 is enabled independently of the account selection.

Make the visible selection, retained form values and setup agree. When a preset invalidates the chosen account, clear/reset that account and dependent amount or require an explicit replacement before advancing. Do not silently assign the amount to the first account. Keep an unattached amount from being entered unnoticed, or surface an actionable account-required validation. Preserve valid choices when still applicable, other details/currency and requestId. Review must disclose the actual selected opening account/amount or the deliberate decision to defer it. No backend/API, quota, dependency or template-builder change is indicated.

Acceptance: through real form/step transitions, switch Personal→Portfolio with a known opening and verify no hidden Personal account is sent; a valid Portfolio selection previews normally. Cover presets with no money accounts, same-account-preserving switches, Decide later, zero/negative values under existing conventions, Back and draft resume. An enabled amount must not disappear silently from setup. Repeat both widths and run dashboard format:check, lint, test and build. Blank/same-account/zero/negative/resume variations are regression scope, not live failures claimed here.
