# Keep the active command-picker option visible in forced colors

**Severity:** minor (keyboard visibility). **Estimate:** 40–55 minutes, dashboard. **A2:** a keyboard user should be able to see which account Enter will open when using a contrast theme.

## Reproduce and controls

1. Open `/ledger/open_ledger/example/journal?time=2016-08`. Wait for settled Journal rows and the interactive header. At390px, open Sidebar first. Focus Search accounts... and press Enter.
2. Type `Assets:US:BofA` sequentially. The picker has two visible options: Assets:US:BofA and Assets:US:BofA:Checking. Move the headless pointer away from the popup.
3. With forced colors active, capture the list, then press ArrowDown to move from BofA to Checking. aria-selected changes to Checking and the input's active-descendant reference resolves to Checking's actual id. DOM focus correctly remains on the input.
4. The two286×72 list captures have **zero changed pixels out of20,592**, at both desktop and fresh narrow width. The selected row paints white over a white list, both rows have black text, outline-style is none, and box-shadow is none. There is no visible indication of the changed Enter target.
5. Normal-color control: with Checking selected, press ArrowUp to move back to BofA. The background highlight visibly moves;17,744 pixels change at both widths. This is the same live picker and data, with only browser media emulation changed.
6. In the narrow forced-colors control, select Checking and press Enter. It opens the correct account route, retains time2016-08, and both popup and mobile Sidebar close after their normal exit transition. No page error or ledger write occurs.

The initial normal ArrowDown at the final item did not move selection and is explicitly excluded from the pixel comparison. A first SSR-header activation before client readiness and immediate closing-dialog counts were also excluded; the retained controls use settled state. The inspected narrow images show the invisible active row versus the ordinary background highlight.

## Cause and bounded repair

`dashboard/src/common/components/ui/command.tsx:104–116` gives CommandItem `outline-none` and marks its selected state only through `data-[selected=true]:bg-accent` and the corresponding foreground color. Forced-color rendering removes that palette distinction, and no selected-state outline or other surviving cue remains. The live selected-value change, correct post-arrow active reference and successful Enter target isolate this from missing selection logic.

Add a visible system-color cue for the existing selected state in forced colors, such as a nonclipped outline or an appropriate Highlight/HighlightText treatment. It must follow cmdk's current selected item while DOM focus remains on CommandInput; a :focus-visible-only item rule will not do that. Preserve normal themes, hover/arrow behavior, native input focus/Enter, filtering, empty/error/retry states, row dimensions and narrow popup bounds. Keep the user's contrast palette and the existing selection model. No dependency, API/backend or cross-package change is needed.

CommandItem's production consumers are the account picker and LedgerSwitcher, including its owner/ledger options. Only the public account picker was exercised in this probe; the switcher is shared-source regression scope. The form combobox's separately repaired integration is not another live reproduction here.

Acceptance: real ArrowUp/ArrowDown changes produce a visible active-row cue in forced colors at desktop/narrow widths, with the indicator inside the list and aligned to the actual Enter target. Preserve the normal-color moving highlight, pointer selection and correct account navigation/retained period. Verify rendered browser paint and selection relationships; an assertion that a CSS class string exists cannot establish visibility. Exercise shared picker callers and run dashboard format/lint/test/build.
