# Explain failed BQL and Holdings CSV downloads and keep retry usable

**Severity:** minor. **Estimate:** 45–60 minutes including both action boundaries and focused regressions. **Owner:** dashboard. **A1/A2:** someone exporting a query result or Holdings should receive actionable feedback when the browser cannot generate the download, while keeping the result available to retry.

## Fresh reproduction and working controls

Production `https://beancount.io`, 2026-10-21 America/Los_Angeles, public synthetic `open_ledger/example`, signed out, English/light, separate owned isolated headless Chromium155.0.8059.85 contexts at390×844 and1440×1000. **This is an explicitly simulated browser API failure, not an observed browser outage, disk-full condition or failed API response.**

1. Execute a harmless one-row BQL query, such as `SELECT 'qa-20261021-export café 東京' AS qa_label LIMIT 1`, and wait for the actual result table.
2. In that context only, save `URL.createObjectURL` and temporarily replace it with a function that throws `Error('qa-controlled-download-generation')`.
3. Focus **Download CSV** and activate it with Enter/Space. The browser emits an uncaught Error, but the UI has no failure toast or nonempty alert. The result remains visible, the button stays enabled and focus remains on it. Desktop counts exactly one object-URL attempt, zero downloads and one exception whose message matches the injected marker. The fresh narrow case likewise records one new Error and no feedback.
4. Restore the original API, then activate that same button. Each context downloads a real UTF-8 CSV containing the exact header/value, with no additional exceptions. The desktop retry produces one download; nothing must be rerun or lost to recover.

The narrow ordinary control also uses `SELECT 'café 東京 + # &' AS qa_label LIMIT 1`: the exact query survives URL encoding and a bookmarked reload, the displayed value remains exact, and both successful CSV downloads preserve its accents, Japanese characters, plus, hash and ampersand. This is a download-action failure, not corrupted CSV, invalid BQL, a query-link failure or a missing result.

## Cause and bounded repair

`dashboard/src/features/bql/components/query-result-export.tsx:20–22` calls `exportQueryResultAsCSV` directly from its click handler with no error handling or feedback. `features/bql/lib/export-utils.ts:60–82` serializes and calls the shared CSV downloader. `common/lib/export/csv.ts:63–86` creates the object URL and performs download/cleanup; its exceptions correctly propagate to the owning action, which currently lets them escape the event handler. The BQL result card at390 is the sole production caller of this export control, including historical results.

Handle export failures at that owning user-action boundary with the existing localized notification/error conventions. Keep the query, result, focus and usable retry; report neither a completed download nor success on failure, and safely handle another rejected attempt. Preserve the shared CSV writer's serialization, filenames, encoding and cleanup. Do not swallow helper failures globally, change report/query semantics, add automatic retries or add a dependency/API.

Acceptance: render the actual export control with its real serializer/downloader, make object-URL creation fail, activate by keyboard, and assert localized visible failure feedback with no uncaught exception or download. Restore the browser API and assert the next activation downloads the same exact table. Preserve successful output and focus, historical-card identity, and the completed pending-query export guard. Run dashboard gates when implementing. Other browser APIs/failure causes, native save-dialog errors and repaired behavior remain unverified.
