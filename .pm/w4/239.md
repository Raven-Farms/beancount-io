# Preserve an invalid date draft after an earlier valid edit

**Severity:** minor. **Estimate:** 40–55 minutes, dashboard. **A2:** a newcomer correcting a date must see the invalid text that needs attention, with an accurate invalid state, rather than a valid-looking date beside a blocked form.

## Reproduce

Production `https://beancount.io`, 2026-10-20, QA-owned headless isolated Chromium 155.0.8059.85, English/light, authenticated owner of a disposable ledger. At 1440×1000 and again after a fresh load at 390×844:

1. Open Accounts → **Open Account** (narrow: **New**), and enter a syntactically valid draft account name.
2. Change **Open Date** from `10/20/2026` to `10/22/2026`, then Tab. The input shows October 22 and the submit button is enabled.
3. Replace it with `02/30/2026` and Tab. The input changes to `10/20/2026`, while the alert says **Invalid input** and submission is disabled. The rendered date input has neither `aria-invalid` nor `aria-describedby`.
4. Calendar → **Today** restores a usable, enabled form and clears the alert. Cancel without submitting.

A fresh untouched form is the passing control: typing the same invalid date directly leaves `02/30/2026` visible with `aria-invalid="true"`. The failure requires an earlier valid edit. A separate Persian desktop check has the same sequence with `2026/02/30`, which becomes `2026/10/20` beside the validation alert. No account or other ledger entry was submitted by these probes; prior QA writes had already been restored byte-for-byte.

Additional related sequence, reproduced on fresh Journal → New Entry at 390×844 and Accounts → Open Account at 1440×1000: clear the date completely, then Tab. Both fields repopulate `10/20/2026` beside **Invalid input**, with no aria-invalid; the Accounts submit is disabled. Journal's underlying input has native `required`, so even its DOM-required state disagrees with the displayed value. Accounts' schema also requires a date. No submit was attempted. Clearing a required date must leave an empty, accurately invalid field that the user can correct. The sync guard's `draft.length > 0` condition currently lets a blank default echo overwrite the draft even when the Date reference is unchanged; cover this alongside the valid-then-invalid sequence rather than adding another widget issue. Screenshot: `journal-empty-required-date-390.png` under the same ignored evidence directory.

## Cause and repair

`dashboard/src/common/components/ui/date-picker.tsx:82–113` preserves an invalid draft only when its `value` reference has not changed. After a valid edit, react-hook-form holds the selected Date, which the picker records in `syncedValueRef`. The subsequent invalid edit publishes `undefined`; RHF's Controller supplies its default Date back to the picker. That reference differs from the selected Date, so the sync effect treats the default echo as an external reset and overwrites the invalid draft. The internal form value remains invalid. The input's `aria-invalid` is computed from the now-valid display text, so it disappears too.

Distinguish an invalid local edit/default echo from an intentional external reset, without depending only on Date identity. Keep the raw invalid text and an accurate accessible invalid state until the user corrects it or deliberately selects a valid date. Preserve real resets, calendar/Today recovery and locale reformatting. This is a remaining sequence gap in completed **w0/005**; do not undo its passing invalid-from-default behavior.

Acceptance: real `useForm` + Controller tests cover valid edit → invalid edit → blur, both a different selected day and the original day, direct invalid-from-default, explicit reset, and Calendar/Today recovery. Assert visible text, invalid state and submission state together. Exercise the shared picker in Accounts and one Journal form on fresh desktop/narrow pages. Dashboard format/lint/test/build pass; no API or dependency change is needed.

Include clearing a schema-required date followed by blur, with an accurate accessible error, while preserving genuinely optional blank dates. Form-level required/error semantics must reach the input; do not infer validity solely from its formatted display text.
