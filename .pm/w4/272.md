# Validate saved BQL history before rendering

**Severity:** minor, controlled corrupted-cache recovery. **Estimate:** 40–55 minutes, dashboard. **A2:** an unusable optional browser-history cache should not block the query tool or hide a successfully returned result.

Production `https://beancount.io`,2026-10-20, English, QA-owned isolated headless Chromium155.0.8059.85, signed-out public example ledger,1440×1000 and a fresh390×844 load. Local main `c5e4cd11a`; deployed `main-D9qWGMxD.js`. The browser cache was deliberately seeded with wrong-shaped data; no natural app writer producing it was established. This is a fault-recovery finding, not a claim about normal storage or a corrupted server response.

## Reproduction and working controls

1. In an isolated context on beancount.io, set the localStorage key `beancount-query-history` to the literal string `null`, then open `/ledger/open_ledger/example/query`. The document is HTTP200, but the BQL section displays Something went wrong / Try Again instead of its editor and Execute Query action.
2. The caught console error is `TypeError: Cannot read properties of null (reading 'length')`, originating from the deployed query page. A fresh390px reload repeats it. Try Again returns to the same error, with the key still null and no QueryShell request during that retry. This is a persistent invalid input, separate from w4/264's retained route-loader failures.
3. Seed a valid JSON object instead, such as `{"qa":"qa-20261020 controlled wrong shape"}`, then open the query URL for `SELECT 9 AS qa_20261020_scalar LIMIT 1`. The actual API succeeds with one int column and row `[9]`. After Monaco readiness and a further1.2 seconds, the editor and Execute Query are usable but there is no result table/history card. The console records `prev.filter is not a function` from history insertion; the object remains stored.
4. Remove only that QA history key and reload the same query URL. Result9 appears and valid string-array history persists normally. Invalid JSON text `not json` is a passing separate control: the existing parse-error fallback recovers to empty history, executes result7, and replaces the bad value with valid history.

A separate native quota control also passes: fill only QA-owned keys until real QuotaExceededError, then execute/reload result7. The result remains usable despite failed optional history persistence. Removing all268 fill keys allows result8 history to persist and survive reload. No storage methods or network responses were stubbed in that quota control. Thus the failure is decoded-value shape, not every storage exception.

## Cause and bounded repair

`dashboard/src/common/hooks/use-local-storage-state.ts:76–85` catches parse exceptions but returns successful JSON.parse results as generic T without runtime validation. `features/bql/hooks/use-query-history.ts:13–16` supplies no feature-specific deserializer for its expected string array. Null reaches `pages/index.tsx:346` and crashes on length. An object bypasses both length-based render branches, while addQuery's prev.filter at hook:23 throws inside the shared setter's catch; the query itself still succeeds but its result has no history card to render into.

Validate the saved history shape at the BQL feature boundary, using the hook's existing deserializer option or an equivalent bounded decoder. Recover non-array values to an empty usable history, preserve valid query strings/order and existing history behavior, and allow the next successful save to replace unusable cache data. Keep parse-exception/quota handling, history deletion/size limit, query execution, URL restoration, cross-ledger result isolation, pending state, exports and valid cached queries intact. Do not guess generic T's runtime shape globally or rewrite every localStorage consumer. No backend/API, dependency or cross-package change is needed.

Acceptance: actual malformed null/object reads recover to an operable BQL page; a new query visibly returns its API result and stores valid history. Normal saved string arrays remain usable, and invalid JSON/native quota controls retain their working recovery. Test the real read path with getItem returning the exact seeded serialized value, plus the real page/result relationship; button-enabled or API-success assertions alone miss the hidden result.
