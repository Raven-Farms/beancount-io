# Keep query-history cards mounted when execution reorders them

**Severity:** minor. **Estimate:** 35–50 minutes, dashboard. **A2:** opening an older query with the keyboard should keep the reader at that query and preserve other open results.

Production `https://beancount.io`, 2026-10-20, QA-owned isolated headless Chromium 155.0.8059.85. Fresh owner contexts at 1440×1000 and 390×844, English/light, disposable synthetic ledger. Local main `c5e4cd11a`; deployed page, history hook and result-card sources exactly match local. Read-only.

## Fresh reproduction

1. In a fresh context, keep the two existing history strings in this order: A = `select count(*) from accounts`, B = `select date, account, number, currency limit 5`.
2. Open Query. Wait for A's genuine result 12 and for Monaco to finish mounting with its writable input; this avoids confusing editor startup focus with the history action. A's disclosure is open, B is closed.
3. Focus B's native summary and press Enter. Its real QueryShell read succeeds with five rows and history becomes [B, A].
4. Both original summary DOM nodes are now disconnected. B is newly mounted/open, A is newly mounted/closed, and keyboard focus is BODY rather than B's summary. The same result holds after an additional 300ms at both fresh widths.
5. Working cached control: open A after B has loaded. A already has a cached card result, so opening it does not reorder history. Focus stays on A's summary, A opens and B remains open. These are independent disclosures, not an intentional single-open accordion.

Expected: promoting the executed query preserves its existing card and focused disclosure, while the other result remains open. The query result itself is correct; there is no lost ledger data or failed read.

## Cause and bounded repair

`dashboard/src/features/bql/pages/index.tsx:354–360` gives each card `key={query + index}` (the template-string form in source). `use-query-history.ts:18–25` removes duplicate query strings and promotes an executed query to index zero. Therefore every displaced card gets a different React identity.

Opening an uncached card calls onExecute through `query-result-card.tsx:296–302`. The page's execute-from-history handler adds it to history before awaiting the read. New card instances reset native details state; the focused old summary is removed. The card only auto-opens its new first instance through isInitiallyOpen.

Use the already unique query identity for card lifetime across reorder and verify actual browser focus survives the DOM move. Preserve the existing most-recent execution ordering, per-query cache/loading/error ownership, disclosure choices, delete/export controls, bookmarks and cross-ledger isolation. Do not replace the list with an accordion, forcibly focus every card on render, remove request retention or change query semantics. Coordinate the same page file with w4/234's separate cache-refresh repair.

Acceptance: drive the real history hook/page/cards with a loaded A and uncached B; press Enter on B, settle its successful read, and assert the same card/summary nodes, B focus, both intended disclosure states and correct query/result association. Cover cached expansion, adding a third query and removing a different card. A fixed-order mocked list misses this. Run dashboard gates when implementing; no API or dependency change is needed.
