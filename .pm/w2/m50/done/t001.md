## Objective

Extend `beancount-trade` from one described event per run to a batch: several buys/sells/dividends in one proposal, one confirmation, each write still check-gated, lot ambiguity still resolved per event before anything is written.

## Context

- `beancount-add` already has a `batch` write recipe; trade's scope line says "one described investment event per run".
- A paycheck-cycle 401(k) produces ~26 buys a year; per-event dictation is the walkthrough's top volume complaint.

## Steps

1. Design the batch proposal shape (all entries shown, per-event lot/duplicate results, one yes/no) and the partial-failure rule (report which events landed; never replay blindly).
2. Write it into trade's procedure text, reusing the shared batch recipe.

## Files

- `skills/beancount-trade/SKILL.md`

## Acceptance criteria

- [x] A described set of mixed events is proposed once and written after one yes; an ambiguous lot inside the batch blocks that event's write, not silently the whole story.

## Out of scope

- Statement files (t002/t003).

## Result

Trade now takes a described batch: full proposal shown event-by-event (never a count), per-event duplicate and lot-ambiguity resolution before proposing, one yes. Verified against `bea 0.3.1`: explicit-cost events (buys, named-lot sells with `price`, dividends, transfers, vests) write in one `batch` recipe call — a named-lot sell books its gain with the gains posting's `units` omitted — and the batch is atomic by default (one unheld-lot row rejected the whole batch, ledger byte-identical), so the text forbids `--partial`/`--allow-errors` salvage. Splits (`{{total}}`) and unnamed `{}` reductions, which the batch schema cannot express, write one by one via the native `transaction` recipe after the batch. New executed test `test_trade_batch_books_a_named_lot_sell_and_rejects_wholesale` covers both halves (suite 122 OK); `ci-check.py` passes. Eval-level batch behavior is exercised in t004/t005.
