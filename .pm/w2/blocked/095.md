# The hosted ledger API accepts a close directive over an account that still holds a balance

**Minor · backend-v2 · 1h · A1.** Found closing [w2/092](../done/092.md), 2026-10-19.

`bea add close` now refuses an account that still holds a balance on its close date unless `--force` (`d70e58002`). The hosted ledger API writes close directives on three surfaces — REST entries (`backend-cluster/backend-v2/src/features/ledger/api/rest/v1/entries-handler.ts`), the GraphQL entry mutation (`ledger-entry-resolver.mutation.ts`), and MCP `addLedgerEntries` — and none checks the account's balance, so an agent on a hosted ledger can still strand money in a closed account. The three surfaces agree with each other today, so this is a behavior change to make on all three at once under the root `AGENTS.md` parity rule: refuse the close with the remaining amounts and accept an explicit override (the CLI's `--force` wording), with the parity and op-class tests covering it, and the OpenAPI snapshot regenerated.

**Blocked 2026-10-19** — refusing these closes changes the public hosted API: REST v1 entries, the GraphQL entry mutation, and MCP `addLedgerEntries` accept a close over a balance today, so an existing API client that sends one would start getting an error. Making that change, and choosing its override (a request flag like the CLI's `--force`, or a warning instead of a refusal), is a contract decision for the owner, and the result also needs a production deploy. **Unblock:** the owner chooses refuse-with-override or warn-only for the three hosted surfaces; then implement it on all three in one change with the parity suite and OpenAPI snapshot, and schedule the deploy. **Who can clear it:** the repository owner (decision) and the operator (deploy).
