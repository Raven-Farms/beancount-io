# Decide whether the suite keeps its no-`bea` developer fallback

**Decision · skills · owner · A1/A2.** Found in the agentic-skill review of `skills/`, 2026-10-18.

Every write and check in the suite has two paths: `bea` when installed, and developer `bean-*` tools or appended text otherwise (`beancount-init/references/compatibility.md`, plus "without `bea`…" branches in each skill and in `skills/AGENTS.md`). The fallback is well contained in one reference, but it still doubles each skill's write and check instructions and the evals that would cover them, and the registry metadata accepts `bean-check` as an alternative binary.

`bea` now installs with `brew install bex-co/tap/bea` or `uv tool install beancount-io`, and the managed engine needs no second Beancount install. Options:

1. **Keep** the fallback as is (today).
2. **Read-only fallback:** keep `bean-check`/`bean-query` for checks and reads, and require `bea` for writes.
3. **Require `bea`:** remove `compatibility.md`'s write paths and the `bean-check` registry alternative, and make each skill stop with install instructions when `bea` is absent.

This needs the owner's call, because it decides who the suite serves (existing Beancount users with their own tooling vs. `bea` users). Option 3 would be a milestone (every skill, its evals, `ci-check.py`'s one-install gate, and the `w6/m6` frontmatter metadata); options 1–2 are sub-hour. Record the decision here, then promote or close.
