## Objective

Every customer skill appends only today. Write the contract under which one new skill may change existing entries, and get the owner's explicit confirmation before t002 starts. The contract covers the name, triggers and skips, accepted requests, preview, approval, check, commit, and undo. If the owner declines, block the milestone with that decision on record. Do not narrow it silently into another append-only skill.

## Context

- The boundary today: `skills/evals/routing.json` labels "Fix the typo in the payee of yesterday's Starbucks transaction" as `none` ("Editing an existing entry; every skill appends only"). [m40](../blocked/m40/README.md)'s out-of-scope list repeats the rule for `beancount-add`.
- Real `bea` primitives:
  - `bea --json list transaction --search … --on-disk` returns each entry's `source.filename` and `source.lineno`, without plugin-synthesized rows.
  - `bea format --check`, `--dry-run`, and `--in-place` handle formatting.
  - `bea check` validates the root ledger.
- No `bea` verb rewrites or renames entries (`cli/src/cli/commands/`), so edits are text edits that the diff, check, and commit rails must make safe. Do not invent a command. If a missing primitive blocks a safe recipe, file it as CLI follow-up work.
- Name: pick one that does not collide with a Beancount directive (the concern behind [m39](../blocked/m39/README.md)), for example `beancount-edit`, and check it against the routing set's confusable pairs.
- Decide the preview mechanism. One option: apply the change to a temporary copy of the ledger, run `bea check` there, and show the diff before the real files change. The other: apply it in a clean Git working tree, show `git diff`, then commit on yes or `git restore` on no.
- Decide the fallbacks for a dirty working tree and for a ledger that is not a Git repository. Undo needs a commit. Backup files written into the ledger tree would break the user's layout.

## Steps

1. Draft the contract in this task's `## Contract` section. Cover the triggers and skips; the five supported requests; how entries are located; the preview, approval, and check rules, including "no errors that were not there before" when the ledger is already red; the commit message format; undo; and the dirty-tree and no-Git behavior.
2. For renames, define both paths: rewrite history everywhere, or close the old account and transfer to a new one. Say when the skill asks which the user wants.
3. Ask the owner to confirm that this skill may change existing entries under the contract. Record the decision and its date here.
