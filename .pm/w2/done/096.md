# Let beancount-close propose the recurring entry it already detects as missing

`beancount-close` flags expected-but-missing recurring entries as findings and never creates them (a real missing entry is recorded through import or add). As a user this means re-describing the same rent/mortgage/subscription in a second conversation every time. Consider: when the user confirms a gap is a real missing entry, close hands add a prefilled proposal (same payee/account/amount as the prior months, period date) inside the same session — still propose-then-confirm, still never fabricated silently. Needs a decision on whether close may compose add this way, plus an eval where the user declines and nothing is written. Sub-hour to scope; promote if the composition design grows.

---
**Resolved 2026-10-20** — Decision: yes, close may compose add this way, bounded as follows (now in `beancount-close`'s Recurring completeness step and checklist). A gap stays a finding until the user confirms the charge really happened; then close offers the import route or recording the single entry now, and only on the latter builds beancount-add's full proposal prefilled from the most recent occurrence (same payee/accounts, steady amount, same day-of-month clamped into the close month), runs add's duplicate check, and writes through the shared `transaction` recipe only on that proposal's own explicit yes — re-checking and refreshing the period figures, with the gap marked `recorded at your confirmation`. Without `beancount-add` installed it stays finding-only with the installation pointer. Evals on one client (2.1.289): 3 updated (offers, writes nothing unapproved), new 10 (user declines → nothing written, gap open), new 11 (prefilled proposal → yes → June NETFLIX entry on the May pattern, report refreshed, close commit still separately gated). The second client has not run these yet (usage limit until 2026-11-17). (`skills`)
