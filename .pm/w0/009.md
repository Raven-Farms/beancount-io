# Bound the precision of Holdings' derived average cost

**Severity:** minor. **Estimate:** 25–40 minutes with formatter and CSV tests. **Owner:** `dashboard` (ledger-data/holdings). **A3:** the public example's portfolio view shows prices like `268.22352941176470588235294118` beside tidy two-decimal prices, which reads as broken.

## Live reproduction

Production `https://beancount.io`, 2026-10-15, local main `575a8798`. QA-owned headless Chromium, 1440×1000, en-US. Public ledger `open_ledger/example`, read-only. Reproduced on two fresh loads.

Open `/ledger/open_ledger/example/holdings?view=by-currency`. The `average_cost` column renders the full 28-digit quotient of the BQL division:

| units | average_cost | price |
| --- | --- | --- |
| 17 GLD | 268.22352941176470588235294118 | 306.91 |
| 104 ITOT | 65.662307692307692307692307692 | 79.93 |
| 597.748 RGAGX | 82.05743244644900526643334649 | 81.09 |
| 36 VEA | 137.76388888888888888888888889 | 143.87 |

**Export CSV** carries the same strings. `unrealized_profit_pct` in the same row is rounded to two decimals, and `price` keeps its source precision.

## Root cause

`dashboard/src/features/ledger-data/holdings/holdings-statement.ts` computes `safediv(number(cost(sum(position))), number(units(sum(position)))) as average_cost`, a derived quotient at the engine's 28-significant-digit Decimal context. `utils.ts` `formatHoldingsCell` deliberately keeps every non-percentage column lossless ("Quantity/cost/price/value stay lossless"; w3/035, `6198de37`). That is right for units, book values, and source prices, but a repeating-decimal quotient has no "source precision" to preserve.

## Fix

Treat `average_cost` like the other derived ratio. Format it to a bounded precision that can't hide meaningful digits, for example the largest fractional precision among the price/cost inputs in that row plus two, capped at 8 and trimmed of trailing zeros. Apply the same rule to the table and CSV. Keep units, book/market values, and `price` lossless, as w3/035 requires (small crypto units such as `0.0225` must survive).

Acceptance: by-currency shows `268.22…` at a bounded precision (e.g. `268.2235`). CSV matches. w3/035's CUSDC-style small units/prices still render unrounded. Unit tests cover repeating quotients, exact quotients (`122.20734375` stays exact), and null/zero rows. Dashboard gates pass.
