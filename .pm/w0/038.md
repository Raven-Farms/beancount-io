# Add Budget accepts any non-empty amount text (`12..3`, `abc`, `1 000`) and the write path renders it verbatim into a `custom "budget"` line Beancount cannot parse

**Major · mobile (+ backend-v2/ledger hardening) · 30–45m · A2.** Native mobile QA, 2026-10-15, `main` at `22aec290`, development build `io.beancount.ios` (JS `1.20261002.50`) on iPhone 17e / iOS 26.5, light theme, English. Authenticated production session at `https://beancount.io/` with the dedicated QA account, on a synthetic ledger the account owns. **Done was not tapped:** no budget was written, and `getLedgerErrors` stayed `[]` afterwards. The write outcome comes from an offline run of the ledger engine, below.

## Repro

1. On a ledger you can write, open **Budget** (empty state) → **Add your first budget** (or **+**).
2. **Account** → pick `Expenses:Food:Groceries`. With **Amount** empty (the grey `500` is a placeholder), **Done** stays disabled.
3. Enter `12..3` in **Amount**. On iPhone, the field's `numbers-and-punctuation` keyboard can produce this, as well as `1 000`, `$500` or letters. In this run the text was pasted through the field's edit menu, and `automation_find_view` reported `value: "12..3"`.
4. **Done** turns enabled. There is no inline validation and no hint.

**Expected:** the amount must be a valid decimal (an optional sign, digits, at most one decimal point) before **Done** enables. Invalid input shows a field message. Valid input keeps the existing behavior: the amount is stored as typed, and the sign of an income target is flipped (`build-budget-entry.ts`).
**Actual:** any non-empty text passes and is sent unchanged.

## Root cause and write path (traced, and engine-tested offline)

- `mobile/src/screens/add-budget-screen/add-budget-screen.tsx:209–214`: `canSubmit` requires only `amount.trim().length > 0` (plus an account and a currency). The raw string goes to `saveBudget` as `number` (`:233–240`). `build-budget-entry.ts` keeps it a string on purpose ("records exactly what the user entered") and never checks that it is a number.
- backend-v2: `LedgerAmountInput.number` is a plain `String` (`src/features/ledger/api/resolvers/ledger-entry-resolver.mutation.ts:61–68`). `LedgerEntryService.buildEntry` (`ledger-entry-service.ts:420–438`) copies it into a `custom` value unchanged.
- ledger service: `toBeancountNumber` (`backend-cluster/ledger/src/foundation/rustledger/entry-build.ts:46–52`) only rewrites exponent notation. The bulk endpoint (`src/api/entries.ts:55–185`) renders the text and commits it without parsing the resulting file. Its only pre-write check, `checkTransactionBalance` (`:105–129`), runs for `transaction` rows alone, so a `custom` row's number is never parsed.
- **Offline engine run.** A throwaway jest probe under `.tmp/` imported `entryInputToText` and rendered a `custom` budget entry for each candidate:
  - `500` → `2026-10-15 custom "budget" Expenses:Food:Groceries "MONTHLY" 500 USD` (the valid control)
  - `12..3` → `… "MONTHLY" 12..3 USD`
  - `abc` → `… "MONTHLY" abc USD`
  - `1 000` → `… "MONTHLY" 1 000 USD`

  Each of the last three is a Beancount syntax error once committed. `1,000` is also rendered verbatim. Upstream Beancount accepts thousands commas; whether rustledger does was not checked.

## Fix

Mobile (primary): validate the amount with a decimal pattern, e.g. `^[+-]?(\d+(\.\d*)?|\.\d+)$` after trimming. Optionally strip grouping commas before validating, and document that choice. Gate **Done** on it and show a translated inline error (13 locales). Consider `keyboardType="decimal-pad"` plus a sign control, like the transaction posting field (`multi-postings-transaction-screen.tsx:348–359`). Unit-test `buildBudgetEntry`/the validator with `500`, `-50`, `0.5`, `12..3`, `abc`, `1 000` and an income target.

Hardening (separate change, every surface): reject a non-decimal `amount.number` at the bulk-write boundary with `BAD_USER_INPUT`, so REST/GraphQL/MCP callers cannot commit an unparsable line either. Keep the three surfaces in parity.

## Blast radius

Add Budget only; there is no edit mutation, since revising a budget adds a newer entry. Transaction entry is the working control: `decimal-pad` plus the balance check before Done. Read-only ledgers never reach this form ([w3/121](../w3/done/121.md)).

## Dedupe

Searched `.pm/**` for budget with amount valid/invalid/parse/syntax and `numbers-and-punctuation`. [w4/038](../w4/done/038.md), [w4/039](../w4/done/039.md) and [w3/206](../w3/done/206.md) cover budget ranges, income sign and accessibility, not amount validation. Dashboard budget date-input QA (`w3/done/m24`) is a different surface. [w3/m2](../w3/done/m2/README.md) built this screen and closed on 2026-10-16. Its native verification ([t009](../w3/done/m2/done/t009.md#closeout-verification)) submitted only valid amounts (USD 620, 777), so it never exercised malformed amount text. No open item covers this.

Related: [w3/499](../w3/499.md) (dashboard QA, 2026-10-16) reports the web New Entry sending an unbalanced transaction. The bulk endpoint's pre-write check (`entries.ts:105–129`) refuses non-numeric or unbalanced transaction postings unless `allowInvalid` is set. It skips every non-`transaction` row, so this note's `custom "budget"` amount and [037](./037.md)'s duplicate `open` are never checked. [w3/564](../w3/564.md) relies on the same transaction-only check.
