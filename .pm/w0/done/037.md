# Open Account green-lights an account that is already open ("Will be created as Assets:Bank:Checking"), so one tap on Done writes a duplicate `open` directive

**Major · mobile · 30–45m · A2.** Native mobile QA, 2026-10-15, `main` at `22aec290`, development build `io.beancount.ios` (JS `1.20261002.50`) on iPhone 17e / iOS 26.5, light theme, English. Authenticated production session at `https://beancount.io/` with the dedicated QA account, on a synthetic ledger the account owns. **Done was not tapped**, so no directive was written. The write outcome below is traced in code and Beancount semantics, not exercised.

## Repro

1. Select a ledger you can write that already has `Assets:Bank:Checking` open. In this run, read-only BQL `SELECT open_date("Assets:Bank:Checking")` returned `2026-01-01`.
2. Open **Open Account** (from the account picker's create row, or the inspected route `beancount:///(app)/open-account`).
3. Keep the root **Assets:** and enter `Bank:Checking` in the name field.
4. The form shows **Will be created as Assets:Bank:Checking**, and **Done** turns enabled (green). There is no warning that the account exists.

**Expected:** an account the ledger already opens is refused before submit, with a message such as "Assets:Bank:Checking is already open" and **Done** disabled. The CLI already refuses the same request as a duplicate (`bea add open` on an open account; see [w5/345](../../w5/done/345.md), where that refusal is the working baseline).
**Actual:** the form treats the name as new. Tapping Done would append `2026-10-15 open Assets:Bank:Checking USD`, and the ledger would then fail validation with Beancount's "Duplicate open directive" error, visible later under **Notifications → Ledger errors**.

## Root cause

- `mobile/src/screens/open-account-screen/open-account-screen.tsx:246`: `canSubmit = validation.ok && typedIssue === null && !loading && !saved`. Both checks are about name syntax (`account-name.ts`, `typedSubPathIssue`); neither compares the composed name with the ledger's existing accounts.
- The screen already loads `useLedgerMeta(userId, ledgerId)` (`:196`, used for `currencies`), and the underlying `ledgerMeta.graphql` query returns `accounts`. The existing account set is in hand but unused.
- No server-side guard: `useOpenAccount` posts through `bulkEntries` (`use-open-account.ts`). backend-v2 `LedgerEntryService.writeBulkEntries` (`src/features/ledger/service/ledger-entry-service.ts:250–322`) checks only elided postings and dates, and the ledger service's bulk endpoint (`backend-cluster/ledger/src/api/entries.ts:55–165`) checks only transaction balance before appending. On success the app shows its success haptic and navigates back, giving no hint that the ledger now has an error.

## Fix

Mobile (primary): expose `accounts` from `useLedgerMeta`. In `OpenAccountScreen`, compare the composed name (the same string shown after "Will be created as") with that set. When it matches, show a translated "already open" message in place of the "Will be created as" line, keep **Done** disabled, and announce it with `accessibilityRole="alert"`. Add the key to all 13 locales. Add a unit test for the decision, beside `account-name.ts` (existing, new, and differs-only-in-case, which Beancount treats as a different account so it must stay allowed).

Optional hardening (backend, separate change): refuse an `open` for an account already opened in the target ledger at the bulk-write boundary, so every client and API surface gets the same refusal. Mind the REST/GraphQL/MCP parity rule if this is done.

## Blast radius

Every route into Open Account: the account picker's **Create** row and direct navigation. The picker's create row only appears for unmatched queries, so the main exposure is manual entry and prefilled names that already exist. Read-only ledgers never reach this screen ([w3/114](../../w3/done/114.md)). Working control: the CLI's duplicate refusal ([w5/345](../../w5/done/345.md) context).

## Dedupe

Searched `.pm/**` for Open Account with "already open/exist", "duplicate open" and "existing account". [w4/047](../../w4/done/047.md) fixed half-typed names, [w3/165](../../w3/done/165.md) digit-led and Unicode names, [w4/010](../../w4/done/010.md) prefill capitalization. None checks existence. No open item covers this.

Related: [w3/557](../../w3/557.md) (dashboard QA, 2026-10-16) is the same defect in the web Open Account dialog, and the optional backend hardening above would cover both clients. [w3/499](../../w3/done/499.md) reports the web New Entry sending an unbalanced transaction. The ledger service's bulk endpoint already refuses non-numeric or unbalanced postings (`backend-cluster/ledger/src/api/entries.ts:105–129`, unless `allowInvalid` is set), but that check runs only for `transaction` rows. That is why an `open` (this note) and a `custom "budget"` ([038](../038.md)) reach the file unchecked.

---

**Resolved 2026-10-17** — Open Account now refuses an account the ledger already opens.

What changed:
- New `openAccountSubmitState` (`account-name.ts`) decides whether the form may submit and whether a valid name is refused as already open. It compares the composed name exactly, since Beancount names are case-sensitive, with the `accounts` that `useLedgerMeta` already loads.
- Submit stays disabled until those accounts are known.
- The screen keeps its explicit `!saved` guard (w1/032).
- Instead of "Will be created as…", the screen shows the new string `openAccountAlreadyOpen` ("{{account}} is already open in this ledger.", translated in 13 locales), as an alert with Done disabled.

Verified on iPhone 17e, `puncsky/example`, Done never tapped:
- Prefilled `Assets:Bank:Mercury:Checking` shows the refusal with Done greyed out.
- The control, `Assets:Bank:Mercury:Reserve`, shows "Will be created as…" with Done enabled.

Tests: `openAccountSubmitState` covers an existing account, a new one, a case-only difference, accounts not yet loaded, an empty ledger, and invalid or busy forms. The source check covers the screen wiring. All 7 fail on the previous code. Mobile only.

The optional backend hardening (refusing a duplicate `open` at the bulk-write boundary, related to [w3/557](../../w3/557.md)) is not done here and stays a separate change.
