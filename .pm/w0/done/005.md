# Keep an invalid typed date visible instead of reverting the field to today

**Severity:** minor (regression of completed w3/m24). **Estimate:** 40–55 minutes including real-form regression tests. **Owner:** `dashboard` (shared `DatePicker` and its react-hook-form callers). **A2:** a newcomer who mistypes a date must see which value is wrong. A field that shows a valid date beside "Invalid input" and refuses to submit is a dead end.

## Live reproduction

Production `https://beancount.io`, 2026-10-15. Local main `575a8798`; deployed SHA unavailable. QA-owned headless Chromium, 1440×1000, en-US, authenticated QA owner on a synthetic ledger. Every GraphQL mutation was guarded with a request route that aborts writes; none was attempted.

1. Open `/ledger/<owner>/<ledger>/journal?action=new-entry&directive=transaction`.
2. Click the date input, select all, type `2026-02-30` (an impossible calendar date), and press Tab.
3. The input now shows today's date (`10/15/2026`), and the field error reads "Invalid input". `aria-invalid` is absent on the input.
4. Fill two balanced postings (`Expenses:Food:Coffee 1`, `Assets:Cash -1`) and a narration, then click **Create Transaction Entry**. Nothing is submitted and the dialog stays open, still showing `10/15/2026` beside "Invalid input".
5. Same result on the **Balance** and **Note** tabs with `13/45/2026`. Retyping the displayed date by hand clears the error, which is the only way to recover, and nothing on screen points to it.

Reproduced on fresh loads for all three forms.

## Root cause

`dashboard/src/common/components/ui/date-picker.tsx` publishes `onChange(undefined)` for invalid text (correct since m24). The form callers (e.g. `features/journal/components/new-directive-dialog/transaction-form.tsx:322–333`) render `value={field.value}`. react-hook-form 7.71 `useController` reads the value via `generateWatchOutput` → `get(formValues, name, defaultValue)`, so an `undefined` form value is shown to the picker as the form's **default** (`new Date()`). On blur, the picker's handler (`date-picker.tsx` ~133–139) sees a "valid" `value` and rewrites the visible draft to that default. The form state still holds `undefined`, so `z.date()` fails with the generic "Invalid input".

## Fix

Keep the visible draft on blur whenever the text doesn't parse. Only reformat on blur when the draft parses to a date equal to `value`, or when the draft is empty and the field isn't required. Alternatively, have callers pass a value that distinguishes "invalid" from "default", for example by setting `undefined` through `setValue` without RHF's default fallback. Set `aria-invalid` from the form error as well as from the draft. Replace the generic schema message with the existing localized "enter a valid date" copy, if one exists. Do not substitute today, retain an old date, or hide the raw text; m24's DoD forbids all three.

Acceptance: for Transaction, Balance, Note, Open Account, Budget, and Receipt review, typing `2026-02-30` then Tab leaves `2026-02-30` visible with an accessible invalid state and blocks submission. Correcting the text, Calendar, or Today restores a valid, submittable form. External resets still reformat. Real-picker form tests cover blur after invalid input. Dashboard gates pass.
