## Objective

Count wrong-password attempts per account in Redis and refuse password verification for that account once the budget is spent, on both the dashboard's `Mutation.signIn` and Git HTTP basic auth, without revealing whether the account exists.

## Context

- `backend-cluster/backend-v2/src/features/auth/service/auth-service.ts:242-269` `loginUser` → `user.verifyPassword`. Called from `features/auth/workflow/auth-session-workflow.ts:40` and `features/auth/api/auth-resolver.ts:176`.
- Git: `features/gitea/api/git-proxy-handler.ts:520-556` looks the user up by email and calls `verifyPassword`; on failure it uses `checkRateLimit` from `src/shared/rate-limiter.ts` (in-memory).
- Shared Redis counters: `src/foundation/redis/redis-counter.ts`, used by `server/api/rate-limit.ts` (`consume`, `consumeAnonymous`). They fail open when Redis is down; keep that for this counter too and log it.

## Steps

1. Add an account-failure counter keyed by a hash of the normalized email (not the raw address), with a generous budget (for example 10 per 15 minutes) so a third party cannot cheaply lock someone out.
2. Check it before `verifyPassword` in both paths; increment on a wrong password and on an unknown account (same key shape) so the response does not distinguish them; clear it on success and on a completed password reset.
3. Move the Git failed-auth limiter onto the shared Redis counter.

## Acceptance criteria

- [x] The (N+1)th wrong password for one account is refused even from a new address, on both paths.
- [x] A correct password after the window works; an existing session and SSH-key Git access are unaffected.
- [x] Known and unknown accounts get the same message and status.

## Out of scope

- CAPTCHA, email alerts on repeated failures, and multi-factor sign-in.

## Done (2026-10-18)

New operation `backend-cluster/backend-v2/src/features/auth/operations/password-failure-budget.ts`:
- **Budget.** 10 wrong passwords per 15 minutes per account. The key is a SHA-256 of the trimmed, lowercased email (`CACHE_KEYS.auth.passwordFailuresByAccount`), so it holds no address.
- **`assertPasswordAttemptAllowed`** runs before the password is checked. A spent budget is a `RateLimitedError`: "Too many failed sign-in attempts for this account. Try again later, or reset your password."
- **`recordPasswordFailure`** counts a wrong password and an email no account has alike.
- **`clearPasswordFailures`** runs on a correct password and after a completed password reset.
- **Redis.** The counter gains `peekCount` and `resetCount`. When Redis is unreachable the budget fails open and the per-address limiters still apply.

Wired into:
- **`AuthService.loginUser`** (`Mutation.signIn`): checked first. Unknown accounts and wrong passwords are counted, and success clears the count.
- **`AuthService.resetPassword`**: clears the reset account's budget after the transaction.
- **The Git proxy's email + password basic auth** (`git-proxy-handler.ts`): checked first. A spent budget is a 429 with the plain-text reason, through the handler's existing `RateLimitedError` path. The in-memory per-address `git-auth-fail` limiter is gone; the shared 60-per-minute per-address Git limiter remains.

Not covered: Git basic auth with a Gitea username (the branch that passes the generated Gitea credential straight through) is Gitea's own sign-in, not a password the person knows. SSH keys and existing sessions are untouched.
