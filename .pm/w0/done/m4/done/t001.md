## Objective

Make `AuthService.resetPassword` delete the user's `jwts` rows in the same database transaction that updates the password, so every session issued under the old password stops verifying the moment the reset commits.

## Context

- `backend-cluster/backend-v2/src/features/auth/service/auth-service.ts:381-414`: `resetPassword` consumes the email token (`emailToken.findOneAndDelete`) and then calls `user.updatePassword(this.db, …)`. Nothing is revoked.
- `features/auth/data/jwt-model/postgres-impl.ts:115`: `deleteByUserId(db, userId)` exists and takes a `DbExecutor`, so it can run inside a transaction. `verify` (`:94-102`) returns null when the row is gone.
- `account-service.ts:380-390` already runs `jwt.deleteByUserId` inside a transaction alongside other deletes; follow that shape.
- The CLI's cloud login holds a session JWT too (`cli-auth-service.ts`), so `bea` is signed out by this as well. That is intended.

## Steps

1. Wrap `updatePassword` and `jwt.deleteByUserId` in one transaction (`this.db.transaction`), after the token is consumed as today.
2. Keep the existing ordering guarantee: consuming the reset token first stays, so a failed update cannot be retried with the same token.
3. Check that the dashboard's reset page still ends on the sign-in screen when the browser that reset was itself signed in (its stored token now fails).

## Files

- backend-cluster/backend-v2/src/features/auth/service/auth-service.ts
- backend-cluster/backend-v2/src/features/auth/service/__tests__/ (reset tests)

## Acceptance criteria

- [x] Two sessions created before a reset both fail `jwt.verify` after it.
- [x] A session created after the reset verifies.
- [x] If `updatePassword` throws, no `jwts` row is deleted.

## Out of scope

- OAuth grants and refresh tokens (t002).
- API keys. They are explicit, listed and revocable in Settings; whether a reset should revoke them is a product decision recorded in t003, not changed here.

## Done (2026-10-18)

`AuthService.resetPassword` (`backend-cluster/backend-v2/src/features/auth/service/auth-service.ts`) now updates the password and calls `jwt.deleteByUserId` in one `db.transaction`, after consuming the reset token as before. Every session the old password issued stops verifying when the reset commits, including the CLI's cloud login and the browser that ran the reset.

Dashboard check: after a reset in a browser that was signed in, the page's client-side `navigate({ to: "/auth/login" })` still sees the cached profile, so `loginBeforeLoad` sends it to `/auth/welcome`. Its loader then gets `UNAUTHENTICATED`, and the root error page sends it to the login form. It ends on sign-in, but by a detour; t003 makes it a direct document navigation.

Tests (`service/__tests__/auth-service-reset-password.test.ts`, a session store whose transaction commits only on success):
- two pre-reset sessions stop verifying, and the password changes;
- another user's session survives;
- a session made after the reset verifies;
- a failed password update revokes nothing and leaves the old password, with the token still consumed;
- an unknown reset token revokes nothing.

Reverting the service change fails "ends every session issued before the reset".

Gates: backend-v2 typecheck, eslint and knip pass. Jest passes 5705 of 5706; the one failure is the known environmental `upstream-survival.test.ts`, unrelated (it spawns a child process).
