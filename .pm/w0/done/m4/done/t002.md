## Objective

After a password reset, every OAuth artifact issued to the user (grants, access tokens, refresh tokens, authorization codes, and the provider's interactive session) is revoked, so the mobile app and any connected third-party MCP client must sign in again.

## Context

- OAuth state lives in `oauth_adapter_storage` (`backend-cluster/backend-v2/src/features/oauth/data/oauth-adapter-model/schema.ts`), keyed by `(model, id)` with a denormalized `grant_id` column. There is no account column. The account ID is only inside `payload` (`accountId` on `Grant` and `Session` rows).
- `postgres-impl.ts:111` `revokeByGrantId` deletes one model's rows for a grant; oidc-provider calls it once per model.
- Mobile refresh tokens last 365 days (sliding), and third-party grants last 45 days (sliding, up to a year) (`features/oauth/data/config.ts`). Neither is revoked anywhere today, and there is no UI to list or revoke them.

## Steps

1. Add a model method that finds every `Grant` and `Session` row whose payload `accountId` is the user, and deletes every row (any model) sharing those `grant_id`s, plus the sessions. Either query `payload->>'accountId'` directly, or denormalize an `account_id` column with an index and a migration. Pick by how the table is queried elsewhere and say why in the commit.
2. Call it from `resetPassword` after the transaction in t001 commits. A failure is logged and surfaced; it must not roll back the password change.
3. Check what the mobile app does when its refresh is refused (`mobile/src/common/oauth/`): it should land on sign-in, not retry in a loop. Fix it there if not.
4. Consider whether account deletion should call the same method; if it is missing there too, note it as follow-up rather than widening this task.

- [x] After a reset, a refresh token issued before it is refused at the token endpoint, and an access token issued before it no longer resolves to an identity (`resolveOidcIdentity`, `features/oauth/utils/oidc-verify.ts`).
- [x] Another user's grants are untouched.
- [x] The mobile app returns to sign-in after its refresh is refused.

## Done (2026-10-18)

New model `oauthGrant` (`backend-cluster/backend-v2/src/features/oauth/data/oauth-grant-model/`, registered in `foundation/models`). Its `revokeAllForUser(db, userId)` is one `DELETE` on `oauth_adapter_storage`. It removes every row whose payload `accountId` belongs to the user (Grant, Session, RefreshToken, AuthorizationCode, …), plus every row issued under one of the user's grants. `accountId` is the bare user id or `userId:ledgerId` for a pinned grant, so rows are matched on `split_part(accountId, ':', 1)`, never by prefix. Clients, registration tokens and interactions carry no top-level `accountId` and stay. No migration: the lookup reads the payload, which suits a once-per-reset call on a table no request path scans by account.

`resetPassword` calls it inside the same transaction as the password update and session deletion from t001.

Deviations from the steps:
- **Same transaction, not after it.** Step 2 said a revocation failure should not roll back the password change. All-or-nothing is safer: a reset that reports success with a grant left behind is what this milestone removes. A failed revocation now fails the reset, the old password still works, and the user requests a new link.
- **Access tokens.** They are stateless ES256 JWTs with a one-hour lifetime, verified against the JWKS without a store lookup (`features/oauth/utils/oidc-verify.ts` `resolveOidcIdentity`). Revoking one immediately would mean a store read on every OAuth request. They now run out within the hour and cannot be refreshed; the milestone's definition of done is amended to say so.

Mobile needed no change. A refused refresh returns `invalid_grant`, which `mobile/src/common/oauth/token-manager.ts` treats as terminal: `onTerminalFailure` clears the server-scoped session, so the app returns to sign-in (`token-manager.test.ts`, "clears exactly once for concurrent invalid_grant callers").

Account deletion does not revoke OAuth rows either, and `findAccount` serves a deleted user. Filed as [w0/054](../../../054.md) rather than widening this task.

Evidence:
- Postgres 16 (throwaway container, migration `0009`): seeded grants, refresh tokens, a code, sessions, a client and an interaction for `usr_a`, `usr_b` and the prefix-sharing `usr_ab`. After `revokeAllForUser("usr_a")`, exactly `Client:dcr`, `Grant:g3`, `Grant:g4`, `Interaction:i1`, `RefreshToken:r3` and `Session:s2` remained.
- `oauth-grant-model/__tests__/postgres-impl.test.ts` pins the generated statement: one delete, `split_part` user match, no `LIKE`, the grant-id subquery and its parameters. Changing the segment index fails it.
- `auth-service-reset-password.test.ts` now also covers the user's grants revoked, another user's grants kept, and a failed revocation leaving password, sessions and grants as they were. Removing the call fails two tests.
