## Objective

Move the directive-limit check to the ledger service's common commit boundary, evaluated against the fresh transformed content on every compare-and-swap attempt, so every write that goes through `commitLedgerFiles` (file writes, change-files, bulk entries, source-slice update and delete, entry delete) is covered once.

## Context

- `backend-cluster/ledger/src/features/ledger/operations/commit-ledger-files.ts:144` `commitLedgerFiles(client, owner, repo, transforms, message, rawCreates)` builds the final file contents from `transforms` and commits them, retrying on conflict.
- `core/directive-limit.ts:101` `checkDirectiveLimitForFileChanges(client, owner, repo, fileChanges, { exempt })` takes base64 contents (null for delete) and refuses only when the projected total is over the limit **and** higher than the current one.
- The exemption arrives from backend-v2 as a request header read in `server/auth.ts:96-111`; the commit boundary needs it passed in rather than read from the request.
- Route-level callers today: `api/files.ts:152,185,249`, `api/entries.ts:250`.

## Steps

1. Give `commitLedgerFiles` (or its caller `commitTransforms`) the exemption option and run the check on the computed contents of each attempt before the commit call.
2. Remove the route-level calls the boundary now covers. Keep any whose write does not go through `commitLedgerFiles`, with a comment saying why.
3. Keep the existing fail-open behavior and its log line.

## Acceptance criteria

- [x] A source-slice update that crosses the limit is refused and commits nothing.
- [x] A CAS retry re-checks the fresh projected total.
- [x] An exempt request and a paid ledger are not counted.
- [x] Deleting entries from a ledger already over the limit still works.

## Out of scope

- The mobile `x-app-id` exemption itself, and whether the check should fail closed.

## Done (2026-10-18)

`commitLedgerFiles` (`backend-cluster/ledger/src/features/ledger/operations/commit-ledger-files.ts`) now runs `checkDirectiveLimitForFileChanges` on every attempt. It runs after the attempt's text operations are built from the fresh reads and before `repoChangeFiles`, so a CAS retry re-checks the content it would now commit. It takes a `limit: DirectiveLimitOptions` argument for the request's exemption. A refusal is the existing 403 `directive_limit_exceeded`, raised before the commit and outside the Gitea error mapping, and the check's fail-open behavior is unchanged.

The exemption reaches the boundary through the per-request journal service: `servicesForRequest` builds `LedgerJournalService` with `{ exempt: directiveLimitExempt(ctx) }`, and `commitTransforms` passes it on. That covers source-slice update, source-slice delete and multi-delete (`api/journal.ts`).

Route-level checks: `api/files.ts` (create, update, change-files) and `api/entries.ts` (bulk) write to Gitea directly, with their own SHAs, not through `commitLedgerFiles`. Their checks stay, each with a comment saying so. `LedgerEntryService.addBulkEntries` also commits through `commitLedgerFiles`, so it is now limited too. No route reaches it today (`servicesForRequest().entry` has no caller), so it is left unexempted.

Tests:
- **`operations/__tests__/commit-ledger-files-directive-limit.test.ts`** runs the real check, with only the limit, the committed map (the same fake repository the commit writes to) and the counter stubbed:
  - a commit past the limit is refused with nothing committed;
  - a change within the limit commits;
  - a CAS retry is refused when a concurrent write makes the retried content cross the limit;
  - a shrinking commit on an over-limit ledger passes;
  - exempt and paid ledgers are not counted.

  Skipping the limit fails 2 of them.
- **`service/__tests__/update-source-slice-hash.test.ts`**: the journal service passes `{ exempt: true }` to the commit when built with it, and `{}` by default.

Gates: ledger `typecheck`, `eslint`, `lint:deadcode`, `test` (1361) and `build` pass.
