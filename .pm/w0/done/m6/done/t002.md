## Objective

Before backend-v2 merges a pull request, compare the directive count of the pull request's head with the base branch's, and refuse the merge with `directive_limit_exceeded` when the head is over the owner's limit and higher than the base.

## Context

- `backend-cluster/backend-v2/src/features/gitea/pull-request/service/pull-request-service.ts:546-567` `mergePR` authorizes, then calls `client.repos.repoMergePullRequest` directly.
- `createPRFromPatch` (`:215`) writes the patch to a branch with `repoUpdateFile` / `repoCreateFile`, so branch content is not limited (and should not be, it is not the ledger yet).
- backend-v2 already asks the ledger service for a count in `features/gitea/policy/directive-limit-gate.ts:71` (`GET /ledgers/{owner}/{repo}/directive-count`), which counts the default branch only. It needs an optional `ref` (the PR head SHA).

## Steps

1. Add an optional `ref` query parameter to the ledger's `directive-count` route and to `countDirectivesForRepo`.
2. In `mergePR`, fetch the PR head SHA, count head and base, and refuse as above. Paid ledgers skip the count.
3. Map the refusal to the same error on GraphQL, REST and MCP (`mergePullRequest`, renamed from `managePullRequests` in 7ce5ec802).
4. Check whether a user can still merge through Gitea's own UI or API in the shipped deployments; if so, record it as a follow-up note rather than widening this task.

- [x] Merging a PR that would cross the limit is refused on all three surfaces and the base branch is unchanged.
- [x] A PR that stays under the limit, or reduces the count, merges.

## Out of scope

## Done (2026-10-18)

**Ledger.** `GET /ledgers/{owner}/{repo}/directive-count` takes `?ref=<commit sha>` (`backend-cluster/ledger/src/api/ledgers.ts`). Anything that is not 7–64 hex characters is a 400; branch names and `HEAD` are refused too, because the ref reaches Gitea and the file-map cache key. `countDirectivesForRepo` loads the file map at that commit. It still resolves HEAD with the caller's client in parallel, because the loader can answer a pinned ref from cache without asking Gitea, so that lookup is the access check. A caller who cannot resolve HEAD gets no count.

**backend-v2.** `PullRequestService.mergePR` calls `assertMergeWithinDirectiveLimit` before `repoMergePullRequest`:
1. It reads the pull request (head SHA, `merge_base`).
2. `evaluateMergeDirectiveLimit` (`features/gitea/policy/directive-limit-gate.ts`) looks up the owner's limit with the push gate's `lookupDirectiveLimit` and counts HEAD, the head and the merge base through the ledger service, as the merging user.
3. The projected count is `HEAD + head − mergeBase`, so a base that moved on keeps its own changes.
4. An `over` verdict (projected over the limit **and** above HEAD) throws `ResourceLimitReachedError("directives", limit, projected, …)`. That is the same error a refused structured write maps to, and its message names removing entries and upgrading.
5. Every other outcome merges: an unknown limit, a failed count, or an unreadable pull request (the merge then reports its own failure as before). Those are logged, and a shrinking merge is never refused.

All three surfaces merge through this one method (`Mutation.approvePullRequest`, `POST …/pull-requests/{n}/approve`, MCP `mergePullRequest`; the tool was renamed from `managePullRequests` in 7ce5ec802), so they share the refusal. The error mapping is the shared `DomainError` one.

Deviation: the steps said to compare head with base. Counting the head alone under-counts when the base has moved, so the merge base is counted too.

Step 4 (merging in Gitea itself): users do not hold their Gitea credential; it is generated at sign-up and no API returns it. So Gitea's own merge UI and API are not a normal user's path. The one known way to obtain the credential is the Ask-AI sandbox's credential exposure from the 2026-10-18 security review, which is not on this board. No note is filed here.

Tests:
- `ledger api/__tests__/directive-count-ref.test.ts`: no ref counts HEAD; a SHA is passed through; five non-SHA refs are refused with no count.
- `ledger core/__tests__/directive-limit-current-count.test.ts`: a pinned ref goes to the loader and is reported, and HEAD is still resolved; an unresolvable HEAD refuses the count.
- `backend-v2 policy/__tests__/merge-directive-limit.test.ts`: over; under; a moved base pushing the merge over; a shrinking merge on an over-limit ledger; the three refs requested; unlimited ledgers count nothing; a failed count is unknown.
- `backend-v2 pull-request/service/__tests__/pull-request-merge-directive-limit.test.ts`: `over` throws and never merges; the check uses the head, the merge base and the user's ledger client; under, unlimited and unknown merge; an unreadable pull request merges unchecked. Removing the call fails 2.
