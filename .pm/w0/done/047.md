# Dashboard's rename dialog skips sign-up's username rule, and a server refusal shows as a generic error

**Minor · dashboard · 20–30m · A2.** From `/pm-brainstorm` for w0 (2026-10-17), the dashboard counterpart of w0/036.

`dashboard/src/features/user-settings/pages/general/user-profile-section.tsx` `handleUpdateUsername` (~:92–97) only checks that the new name is not empty. Since w0/036, the server refuses a rename outside 1–20 lowercase a–z, digits and underscore with `BAD_USER_INPUT` on `username`. The dialog shows that refusal as a generic failure.

**Fix:**
- Apply the sign-up form's rule (`^[a-z0-9_]+$`, max 20; `auth/components/register-form/index.tsx`) in the dialog, with its translated messages.
- State the rule next to the field before submit.
- Show a server `BAD_USER_INPUT` on the field.
- Add a component test.

**Dedupe:** w0/036 (backend and mobile), w4/136/137 (sign-up form copy).

---

**Resolved 2026-10-17** — Settings' rename dialog now holds a username to sign-up's rule before submitting, states the rule, and shows a server rule refusal on the field.

What changed (`dashboard`):
- The rule now lives in one place, `src/common/lib/auth/username-rule.ts` (`USERNAME_MAX_LENGTH`, `USERNAME_CHARACTERS`, `usernameRuleError`), used by the registration form and the rename dialog alike. `username-limit-copy.test.ts` reads the limit from it and checks the form applies it.
- The rename dialog (`user-settings/pages/general/user-profile-section.tsx`):
  - states the rule under the field in the existing translated sentences, so no new copy;
  - shows the specific violation inline (`role="alert"`, `aria-invalid`, described-by) once the name is edited, and does not submit while the name breaks the rule;
  - turns a server `BAD_USER_INPUT` on `username` into the localized rule message on the field, instead of the generic "information provided is invalid" toast; the server's own text is never shown.
- An empty name, which used to be a toast, is now the inline "Username is required".

Tests (`user-profile-section.test.tsx`): the rule is shown before typing; `John.Doe`, 21 characters and blank are refused inline without a mutation; `new_name_2` is submitted; a server rule refusal shows on the field with no toast. Five of these fail on the old dialog. The suite's mutation mock had matched `document.toString()` (always `[object Object]`), so both mutations got the username mock; it now matches the operation name.

Not checked live: the dialog renames the signed-in account, and the QA account's username must not change.

Gates: dashboard `format:check`, `lint`, `test` and `build` pass.
