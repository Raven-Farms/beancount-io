# A Plaid webhook that fails signature verification is still queued as pending work

**Minor · backend-v2 · 30–45m · A3.** From a security review of `main` (2026-10-18).

`POST /api/plaid/webhook` (`backend-cluster/backend-v2/src/features/plaid/api/rest/plaid-webhook-handler.ts`) verifies the signature first (`:42-47`), but its single `catch` (`:71-90`) handles a verification failure the same way as a storage failure: it calls `webhookEventModel.create(…)` again with the default `"unknown"` type, code and item and a `{}` body, and returns 200. Every such row is inserted as `status: "pending"` with a fresh ID (`features/plaid/data/plaid-webhook-event-model/postgres-impl.ts:34`).

The processor drains pending and failed rows oldest first, 50 every two minutes (`postgres-impl.ts:87-93`, `scheduler/jobs/plaid-webhook-processor-job.ts:23,46`), while the anonymous webhook budget allows 120 a minute per address (`server/api/rate-limit.ts:195`). Unsigned requests therefore queue ahead of real Plaid events and delay them. The rows are inert when processed (`plaid-webhook-service.ts:99-104`), and the 6-hourly full sync (`plaid-sync-job.ts:14`) bounds how stale transactions get, but item events (login required, revocation) wait in line. The cleanup job removes only `completed` rows (`postgres-impl.ts:203`), so a backlog is never trimmed.

**Fix:**
- Split the `catch`: a signature or parse failure logs a warning (no body) and returns without writing a row. Keep the one storage retry for a *verified* event whose first insert failed.
- Return 401 for a missing or invalid `Plaid-Verification` header; Plaid only retries its own signed deliveries.
- Tests: missing, malformed and invalid signatures create no row; a verified event whose first insert throws is retried once.

**Dedupe:** none open. Trusted client addresses for the per-address budget are [m7](./m7/README.md).

---

**Resolved 2026-10-18** — A webhook that fails signature verification is refused with `401` and stores nothing (`backend-v2`).

What changed (`backend-cluster/backend-v2/src/features/plaid/api/rest/plaid-webhook-handler.ts`):
1. **Verification first.** A missing, invalid or malformed `Plaid-Verification` answers `401 { received: false }`, with a warning logged without the body. No row is created, so the pending queue holds only signed Plaid events. A signed event refused by a transient verification failure is retried by Plaid, instead of being stored as an inert `"unknown"` row as before.
2. **Parsing.** A verified body that cannot be parsed is still stored, with the `"unknown"` fallbacks, for debugging.
3. **Storage.** A verified event whose insert fails is retried once.

`src/features/plaid/AGENTS.md` records the rule.

Tests (`api/rest/__tests__/plaid-webhook-handler.test.ts`):
- missing, invalid and malformed signatures are each refused with `401` and create no row (reverting the handler fails all 3);
- a verified event whose first insert throws is stored on the second try;
- the success and parse-error cases are unchanged.

Gates: backend-v2 typecheck, eslint and knip pass. Jest passes 5807 of 5808; the one failure is the known environmental `upstream-survival.test.ts`.
