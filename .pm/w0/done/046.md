# Sign-up accepts any username server-side, and derives one from the email local part outside the product's rule

**Minor · backend-v2 · 45–60m · A2.** From `/pm-brainstorm` for w0 (2026-10-17), the sign-up side of w0/036.

The username rule (1–20 lowercase letters a–z, digits, underscore) is enforced on rename since w0/036, but not at sign-up:

- GraphQL `SignUpInput.username` is a nullable, unconstrained `String` (`backend-cluster/backend-v2/src/features/auth/api/auth-resolver.ts`). The REST schema in `features/auth/api/account-routes.ts:27` is `z.string().nullable().optional()`. Only the dashboard's registration form validates it.
- With no username, `AuthService.registerUser` falls back to the email local part (`features/auth/service/auth-service.ts:162`, `username ?? email.split("@")[0]`). That fallback can produce uppercase, dots or `+tag` (e.g. `John.Doe+x`), longer than 20 characters, or a name already taken. It reaches the git host's `createUser` as is.

**Fix:**
- Validate an explicit sign-up username with the shared `assertValidUsername` (`features/auth/utils/username-rule.ts`) and return `BAD_USER_INPUT` on `username`.
- Normalize the derived fallback into the rule: lowercase, map other characters to `_`, trim to 20, and append digits on a case-insensitive conflict.
- Cover both the GraphQL and the REST sign-up surfaces with tests, keeping them in parity. Existing accounts are unaffected.

**Dedupe:** w0/036 (rename only) and w4/136/137 (dashboard form copy). No other item covers server-side sign-up usernames.

---

**Resolved 2026-10-17** — Sign-up now holds a username to the same rule renames follow, and a sign-up without one gets a name in the rule.

What changed (`backend-v2`, `features/auth`):
- `createSignUpSession` checks an explicit username with `assertValidUsername` before the conflict lookup and before any code is emailed. Uppercase, dots, spaces, dashes or more than 20 characters return `BAD_USER_INPUT` on `username`. `registerUser` checks it again before writing.
- The fallback is a new `usernameFromEmail` (`utils/username-rule.ts`):
  - the email's local part, lowercased;
  - every other character mapped to `_`, then cut to 20 (`John.Doe+tag@…` → `john_doe_tag`);
  - `user` if nothing is left;
  - numbered (`john_doe2`, …) while the case-insensitive lookup says the name is taken, staying within 20 characters.
- Existing accounts are unaffected.

Surfaces: the GraphQL `signUp` mutation is the only sign-up entry point; there is no REST sign-up route. The note's `account-routes.ts:27` is the profile *output* schema. The check lives in the service, so any future surface inherits it.

Tests (`service/__tests__/auth-service-signup-username.test.ts`):
- five refused names, none of which creates a session or sends mail;
- a valid name is accepted, and an omitted one still works;
- a derived name, and a numbered one after a case-insensitive clash;
- a chosen name outside the rule refused in `registerUser`;
- the helper's mapping, truncation and empty fallback.

Reverting the service change fails 8 of them. backend-v2 typecheck, eslint and knip pass. Jest passes except the known environmental `upstream-survival.test.ts`.
