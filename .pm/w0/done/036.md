# Profile accepts usernames that sign-up forbids, and nothing server-side checks them, so a bad rename can only fail as "Failed to save"

**Minor · mobile + backend-v2 · 40–60m · A2.** Native mobile QA, 2026-10-15, `main` at `22aec290`, development build `io.beancount.ios` (JS `1.20261002.50`) on iPhone 17e / iOS 26.5, light theme, English. Authenticated production session at `https://beancount.io/` with the dedicated QA account. **No save was attempted:** a rename that the server accepted would rename a real account and every ledger URL under it. The server-side half below is traced in code, not exercised.

## Repro (client side, observed)

1. **Settings → Account row → Profile**. Username shows the current name. **Save** is disabled.
2. Replace the username with `José`, using the field's edit menu → Paste.
3. **Save** turns enabled, and no hint or error appears under the field. The same happens for names with uppercase letters, dots, or more than 20 characters. Only an empty value or one with a space is refused, by the client-side zod rule (`profileUsernameRequired`, `profileUsernameNoSpaces`).
4. Back without saving. Profile reopens with the original username (verified through `automation_find_view` on `profile-username`).

**Expected:** the Profile form enforces the same username rule as sign-up, the dashboard sign-up form's `^[a-z0-9_]+$` with 1–20 characters (`dashboard/src/features/auth/components/register-form/index.tsx:57–61`, copy fixed in [w4/136](../../w4/done/136.md)). It explains that rule before submit. The server enforces the same rule and returns a field-level validation error the app can show.
**Actual:** the app accepts anything without a space. The server accepts any string too, and only the git host can refuse it.

## Root cause (traced)

- Mobile: `mobile/src/screens/profile/profile-screen.tsx` (`schema`: `username: z.string().trim().min(1).regex(/^\S+$/)`). On failure, `onSubmit` maps only `CONFLICT` to a field message (`profile-changes.ts`, `isUsernameTaken`). Every other error becomes the root message `saveFailed` ("Failed to save").
- backend-v2: `Mutation.updateUsername` (`src/features/auth/api/account-resolver.ts:166–174`; `UpdateUsernameInput` at `:102–105` has no constraint) calls `AccountService.updateUsername` (`src/features/auth/service/account-service.ts:155–188`). That method checks only for a case-insensitive conflict (`user-model/postgres-impl.ts:70–82`), writes the new name in a transaction, and calls the ledger service's `admin.renameUser`. `backend-cluster/ledger/src/api/admin.ts:81–89` forwards `new_username` to the git host unchanged. A name the git host rejects therefore surfaces as a generic upstream failure, not a `BAD_USER_INPUT` naming the rule. A name the git host accepts but sign-up forbids (uppercase, dots, longer than 20) is stored. `shared/ledger-slug.ts` `LEDGER_OWNER_PATTERN` admits those characters, so ledger IDs keep working, but the account ends up outside the product's own username rule.
- The dashboard's rename dialog has the same gap (`dashboard/src/features/user-settings/pages/general/user-profile-section.tsx:92–97` checks only non-empty). That is listed for completeness, not as this note's scope.

## Fix

1. backend-v2: validate `username` in `AccountService.updateUsername` before the conflict check, against one exported rule shared with sign-up (lowercase letters, digits and underscore, 1–20 characters). Throw `BadUserInputError(<rule>, "username")` so GraphQL returns `BAD_USER_INPUT` with the rule. Add service tests for a valid name, uppercase, accented, a dot, 21 characters, and empty input. `updateUsername` is GraphQL-only by a documented parity exemption (`op-class.ts`, `gqlOnly … M.notAgentShaped`), so no REST/MCP adapter changes are needed.
2. mobile: mirror the rule in the Profile schema with a translated message (new key in all 13 locales, a plural-free sentence). Map `BAD_USER_INPUT` on `username` to the field error instead of `saveFailed`. Update the hint under the field so it states the allowed characters. Add unit tests in `src/screens/profile/__tests__/`.
3. Separate follow-up (dashboard package): apply the same rule in the rename dialog.

## Blast radius

One mutation and two clients (mobile Profile, dashboard settings). Sign-up is unaffected. Existing usernames that already break the rule keep working: the new check applies only to changes, and an untouched username sends no `updateUsername` (`profileChanges`).

---

**Resolved 2026-10-17** — Rename now follows sign-up's username rule: 1–20 characters, lowercase a–z, digits and underscore.

backend-v2:
- New `features/auth/utils/username-rule.ts` holds the rule. `assertValidUsername` throws `BadUserInputError(rule, "username")` and also refuses non-strings: `RegExp.test(undefined)` matched the pattern, because the value is stringified to "undefined".
- `AccountService.updateUsername` checks it right after authorization, before the lock, the conflict check and the git-host rename.
- GraphQL returns `BAD_USER_INPUT` with `field: "username"`. The mutation stays GraphQL-only under its documented parity exemption, so no REST or MCP adapter changes, and the OpenAPI snapshot shows no drift.
- Sign-up is unchanged: its email-local-part fallback is out of scope. Existing names keep working.

mobile:
- The Profile form refuses a *changed* username outside the rule. An unchanged legacy name still saves the other fields.
- A server `BAD_USER_INPUT` becomes the field error instead of "Failed to save".
- The hint now states the rule. The new key `profileUsernameRule` is translated in 13 locales; the unused `profileUsernameNoSpaces` is removed.

Tests:
- Service: 7 refused names and 4 accepted. All refusals happen before any account, lock or git work.
- Real-schema GraphQL tests: a refused name returns `BAD_USER_INPUT` on `username` with the rule text, and an allowed name passes through.
- These resolver tests now share one schema. A second `buildSchema` in the file had been resolving every `@Args()` as `undefined`, so the existing username-search test also asserts its argument now.
- Mobile tests for `usernameAllowed` and `usernameErrorKey`.
- All of these fail on the previous code.

Verified on iPhone 17e: Profile shows the rule under Username. Save was not tapped, because this is a real account and production does not have the backend check yet. Separate follow-up, not done here: the dashboard's rename dialog (`user-profile-section.tsx`).

Gates: mobile, all green; backend-v2 typecheck, eslint and knip green. The full jest suite passes except `llm/utils/upstream-survival.test.ts`, which spawns `npx ts-node`. On this checkout `node_modules/.bin` holds copies instead of symlinks, so the spawned binary cannot load. The failure is environmental and unrelated.
