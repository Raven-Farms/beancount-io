## Objective

Make the shared structured-write path validate the post-write ledger before it commits, and refuse a write that introduces new bean-check errors unless `allowInvalid` is set — the same contract the text-append route already has.

## Context

- Text-append: `backend-cluster/backend-v2/src/features/ledger/workflow/directive-append-workflow.ts` (`newErrors.length > 0 && !allowInvalid && !dryRun`) and its message contract in `utils/directive-text-contract.ts`.
- Structured writes: `LedgerEntryService.writeBulkEntries` (`features/ledger/service/ledger-entry-service.ts`) → the ledger service bulk endpoint (`backend-cluster/ledger/src/api/entries.ts`), which today only refuses an unbalanced transaction.
- All three surfaces already pass `allowInvalid` into the service (GraphQL `bulkEntries` arg, REST `entriesBodySchema`, MCP `addLedgerEntries`).

## Steps

1. Reuse the text-append validation (render the entries, diff the ledger's errors before and after) for structured writes; do not add a second validator.
2. Refuse with a transport-agnostic domain error that names each new error, mirroring the text-append message.
3. Keep `allowInvalid` committing and reporting the new errors.
4. Unit-test the workflow: duplicate `open` refused, `allowInvalid` commits, a clean write unchanged.

## Files

- backend-cluster/backend-v2/src/features/ledger/service/ledger-entry-service.ts
- backend-cluster/backend-v2/src/features/ledger/workflow/ (shared validation)

## Acceptance criteria

- [x] A second `open` for an open account is refused with nothing committed and the error named.
- [x] `allowInvalid: true` commits and returns the new errors.
- [x] A write that adds no error is unchanged.

## Out of scope

## Done (2026-10-17)

The check lives in the ledger service's bulk endpoint (`backend-cluster/ledger/src/api/entries.ts`). All three surfaces reach it through `writeBulkEntries`, so one change covers GraphQL, REST and MCP.

Ledger service:
- When `allowInvalid` is off, the endpoint runs the existing projection check (`LedgerDataService.checkProjectedErrors`) on the baseline and on the projected files before committing. It diffs them with the new `newLedgerErrors` (message plus file:line).
- If the write adds errors, it throws the new `NewLedgerErrorsError`: category `BAD_USER_INPUT`, code `NEW_LEDGER_ERRORS`, details `{ count, detail }`. This follows the text-append route's check-then-commit order.
- `checkProjectedErrors` gained `enforceInputLimits` (default `true`). The public `/check` keeps its file and byte caps, while a write's own projection skips them, so a large ledger's ordinary append is not refused.

backend-v2:
- `favaApiErrorToDomainError` maps `NEW_LEDGER_ERRORS` to `ValidationError("entries", …)`, with a fix-or-`allowInvalid` hint. That is the structured twin of text-append's refusal.

Tests:
- Ledger: `entries-new-errors.test.ts` drives the real handler with the engine's verdict scripted (unit tests are WASM-free). A duplicate `open` is refused with the envelope and nothing committed; `allowInvalid` commits; a clean write commits; pre-existing errors are not blamed. Reverting the endpoint fails the refusal test.
- Ledger: `new-ledger-errors.test.ts` covers the diff.
- backend-v2: `mcp-errors.test.ts` maps the code to `VALIDATION_FAILED` with the hint.

Gates:
- Ledger typecheck, lint (with knip), build and test (1332) pass.
- backend-v2 typecheck, eslint and knip pass. Jest passes except the known environmental `upstream-survival.test.ts`, which spawns `npx ts-node` through this checkout's copied `.bin` entries.
