# A Git HTTP client that hangs up mid-clone leaves the Gitea request running

**Minor · backend-v2 · 30m · A3.** Found during w0/m8/t005 (2026-10-18).

`git-proxy-handler.ts` (`backend-cluster/backend-v2/src/features/gitea/api/git-proxy-handler.ts:607-661`) forwards Git smart-HTTP to Gitea with `node-fetch` and no `signal`, then sets `ctx.body` to node-fetch's body (or a PassThrough over it). When the client disconnects, Koa destroys that body. node-fetch's body is its own PassThrough, though, and destroying it leaves the upstream socket open (shown in w0/m8/t001: the Gitea socket was still open 6 s later). Gitea keeps building an `upload-pack` response nobody reads until backpressure or a timeout stops it. w0/m8 fixed the same thing for archive downloads by moving to the built-in `fetch` with `Readable.fromWeb`, where destroying the body cancels the request.

**Fix:**
- Use the built-in `fetch` with `Readable.fromWeb`, as `LedgerArchiveService` and `ssh-proxy-server.ts` already do. Keep `ctx.req` streaming for `receive-pack` bodies (built-in `fetch` needs `duplex: "half"`), and keep the `HookResponseScanner` observation path.
- Test against a real HTTP origin: a client that disconnects mid-response closes the upstream socket. The `archive-origin.ts` test helper shows the shape.

**Dedupe:** w0/m8 covers archive downloads only; the SSH proxy already aborts on channel close.
