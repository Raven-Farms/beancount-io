## Objective

Prove the source-slice update refusal reaches callers identically on every surface: the REST v1 handler, the GraphQL mutation and the MCP `updateEntrySource` tool all return the directive-limit refusal with the same code, limit and projected count.

## Context

- REST: `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/source-slice-handler.ts`.
- GraphQL: `features/ledger/api/resolvers/ledger-journal-resolver.mutation.ts`.
- MCP: `features/ai-agent/api/mcp-source-slices.ts`, `mcp-tools.ts`.
- All three go through `features/ledger/service/ledger-journal-service.ts` to the ledger's `PUT …/source-slice`.

## Steps

1. Add one contract test per surface with the ledger service returning `directive_limit_exceeded`, asserting the mapped status or error code and details.
2. Fix any surface that drops or rewrites the error.

## Files

- backend-cluster/backend-v2/src/features/ledger/**/__tests__/
- backend-cluster/backend-v2/src/features/ai-agent/**/__tests__/

## Acceptance criteria

- [x] Each surface's test fails if its error mapping is removed.

## Out of scope

- Other write operations, which existing contract tests cover.

## Done (2026-10-18)

`backend-cluster/backend-v2/src/features/ledger/api/rest/v1/__tests__/source-slice-parity.test.ts` gains "a source edit past the directive limit via rest / gql / mcp". The existing parity fixture drives the real REST v1 server, GraphQL execution and an MCP client (`updateEntrySource`) against one `LedgerJournalService`. A new `limited` state makes the stubbed ledger client's `updateSourceSlice` answer the way the ledger's commit boundary does: 403 `directive_limit_exceeded` with `{ limit: 2, current: 5 }`.

Every surface refuses, and no slice changes:
- **REST:** `{ ok: false, error: { code: "RESOURCE_LIMIT_REACHED", message, metadata: { resource: "directives", limit: 2, current: 5 } } }`.
- **GraphQL:** the error carries category `RESOURCE_LIMIT_REACHED` and that metadata (raw `graphql()` skips `formatError`, which copies them into `extensions`).
- **MCP:** `{ ok: false, error: { code: "RESOURCE_LIMIT_REACHED", message } }`.

In each case the message keeps the ledger's own sentence: delete entries, or upgrade. No adapter needed a fix. All three already map the error through `favaApiErrorToDomainError`.

If the ledger's code is replaced by an unrecognized one, all 3 fail. The fixture now also returns GraphQL `errors` and the full MCP `structuredContent`, so refusals can be asserted.

Gates: backend-v2 typecheck and eslint pass. Jest passes 5753 of 5754; the one failure is the known environmental `upstream-survival.test.ts`.
