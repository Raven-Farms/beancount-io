## Objective

Move the directive-limit check to the ledger service's common commit boundary, evaluated against the fresh transformed content on every compare-and-swap attempt, so every write that goes through `commitLedgerFiles` (file writes, change-files, bulk entries, source-slice update and delete, entry delete) is covered once.

## Context

- `backend-cluster/ledger/src/features/ledger/operations/commit-ledger-files.ts:144` `commitLedgerFiles(client, owner, repo, transforms, message, rawCreates)` builds the final file contents from `transforms` and commits them, retrying on conflict.
- `core/directive-limit.ts:101` `checkDirectiveLimitForFileChanges(client, owner, repo, fileChanges, { exempt })` takes base64 contents (null for delete) and refuses only when the projected total is over the limit **and** higher than the current one.
- The exemption arrives from backend-v2 as a request header read in `server/auth.ts:96-111`; the commit boundary needs it passed in rather than read from the request.
- Route-level callers today: `api/files.ts:152,185,249`, `api/entries.ts:250`.

## Steps

1. Give `commitLedgerFiles` (or its caller `commitTransforms`) the exemption option and run the check on the computed contents of each attempt before the commit call.
2. Remove the route-level calls the boundary now covers. Keep any whose write does not go through `commitLedgerFiles`, with a comment saying why.
3. Keep the existing fail-open behavior and its log line.

## Acceptance criteria

- [ ] A source-slice update that crosses the limit is refused and commits nothing.
- [ ] A CAS retry re-checks the fresh projected total.
- [ ] An exempt request and a paid ledger are not counted.
- [ ] Deleting entries from a ledger already over the limit still works.

## Out of scope

- The mobile `x-app-id` exemption itself, and whether the check should fail closed.
