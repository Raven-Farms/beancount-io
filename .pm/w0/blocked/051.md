# Account deletion accepts an application-API OAuth token of any scope, including `ledger.read` only

**Minor · backend-v2 · 30–45m · A1.** From a security review of `main` (2026-10-18). Latent today; needs a decision first.

`AUTHORIZATION_ACTIONS.USER_DELETE` (`backend-cluster/backend-v2/src/server/api/authorization/authorization-service.ts:230-234`) admits `INTERACTIVE_OR_OAUTH` with no `capability`, and operations that carry an `authorizationAction` skip the transport scope check (`server/api/op-class.ts:2011-2013`). So `Mutation.deleteAccount` and `DELETE /api-gateway/v1/account` accept an application-API OAuth token that holds only `ledger.read`. The tests pin it: `authorization-service.test.ts:872` allows `[USER_DELETE, "oauth", [], "user"]`.

Why it is latent: only the first-party `beancount-mobile` client is issued application-API tokens. Dynamically registered clients are forced onto the MCP audience (`features/oauth/api/oidc-route.ts:197-208`), and MCP exempts account deletion (`op-class.ts:219`). The mobile app asks for all three ledger scopes (`mobile/src/common/oauth/discovery.ts`), but the server issues whatever subset a request names (`oidc-route.ts:549`), so a narrower token can exist. It becomes a real gap the day any narrower API-audience client ships.

**Decision first:** [w2/m12](../../w2/done/m12/README.md)'s definition of done says user deletion has no `ledger.admin` dependency, because a ledger scope is the wrong authority for deleting a user. Options:
- Require `capability: "admin"` on `USER_DELETE`. Smallest change; the mobile app already holds `ledger.admin`, so nothing breaks. It reverses that m12 line.
- Require the token to carry every API scope the client is registered for (a "full-access" token), without naming a ledger scope.
- Keep it as is and record that any future API-audience client must not be issued a narrower token.

**Fix (after the decision):** change the catalog entry, flip the `:872` test to deny a `ledger.read`-only token and allow the full mobile token, update `op-class.test.ts:432-440`, and note the decision in the m12 design record's follow-up. GraphQL and REST share the catalog, so parity holds.

**Dedupe:** w2/m12 (the original design). No open item covers scope on account deletion.
