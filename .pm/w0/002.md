# Show the position and token of a BQL syntax error in the query editor

**Severity:** minor. **Estimate:** 40–55 minutes including localized copy and regression coverage. **Owner:** `dashboard` (BQL feature). **A2 — Frictionless onboarding:** a newcomer learning BQL hits syntax errors first, and needs to see where the query broke.

## Live reproduction

Production `https://beancount.io`, 2026-10-15. Local main `575a8798`; deployed SHA unavailable. Headless isolated Chromium, 1440×1000, English/light, authenticated QA owner, synthetic ledger, read-only. Reproduced with UI runs and direct GraphQL controls.

1. Open `/ledger/<owner>/<ledger>/query`.
2. Run `SELEC account`, then `SELECT nonsense FROM`, then `SELECT sum(account) GROUP BY`.
3. Each card shows only "Some of the information provided is invalid. Please check and try again."

The same `QueryShell` operation (HTTP 200, `extensions.code: BAD_USER_INPUT`) returns a precise, safe diagnostic each time:

```text
Invalid BQL query: syntax error at position 0: unexpected token 'SELEC'
Invalid BQL query: syntax error at position 16: unexpected token 'FROM'
Invalid BQL query: syntax error at position 20: unexpected token 'GROUP'
```

Control: `SELECT account FROM postings ORDER BY nope` correctly shows "Unknown column “nope”…" (completed w4/160). A valid query renders rows.

## Root cause

`dashboard/src/features/bql/lib/query-error.ts` (`getQueryErrorFeedback`) recognizes only `column '<name>' not found`. Every other `BAD_USER_INPUT` falls back to the shared generic `common.errors.badUserInput`. `lib/__tests__/query-error.test.ts` ("keeps generic feedback for other bad-input diagnostics") currently asserts this behavior for a syntax error. w4/160 deliberately limited itself to unknown columns.

## Fix

Add one more narrowly parsed diagnostic in the BQL feature: match `syntax error at position (\d+): unexpected token '([^'\n]{1,64})'` and show localized feedback ("Syntax error near “{token}” at character {position}"), in all 15 locales. Optionally highlight the offset in the Monaco editor with a marker. Interpolate only the captured, length-bounded token and integer, so raw server text is never rendered. Keep the generic fallback for anything else (including `type error: cannot compare values`, which has no safe location). Update the existing test so the syntax case expects the new key, and keep HTML-like and unknown diagnostics generic. Server, API, and engine stay unchanged.

Acceptance: the three queries above name the token and position on run and after a fresh load of their `?query=` URL. Unknown-column feedback is unchanged. A corrected query replaces the error with results. Dashboard gates pass.
