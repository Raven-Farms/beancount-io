# A ledger-pinned credential keeps its ledger's old name after a rename: its own `listLedgers` shows the new name, which the pin then refuses

**Severity:** minor. **Estimate:** a milestone if pins are bound to the repository ID; 30 minutes for an accurate refusal only. **Owner:** `backend-cluster/backend-v2`. Pins are compared as `owner/name` strings in `resolveMcpLedger` (`src/features/ai-agent/api/mcp-context.ts`), in `identityAllowsLedgerScope` and the audit check (`src/server/api/authorization/authorization-service.ts`), in API-key minting (`src/features/apikeys/service/api-key-service.ts`) and in `restrictToPin` (`src/features/ledger/workflow/ledger-workflow.ts`). **A1/A2:** year-end "rename `personal` to `personal-2025`" leaves every pinned agent credential addressing the ledger by a name that no listing shows.

Split out of w23/061, which fixed that note's create and rename half.

## Repro (production, 2026-10-22, from w23/061)

A `ledger.read` token pinned to `<owner>/qa-…-p1`; the ledger is then renamed to `qa-…-p2`. `initialize` still says "Ledger <owner>/qa-…-p1". The token's own `listLedgers` returns `qa-…-p2`, because a pinned listing fetches the pin by name and the host redirects. Yet `ledger: "<owner>/qa-…-p2"` is refused with `FORBIDDEN` "outside this credential's ledger restriction". Omitting `ledger`, or passing the old name, works only through the host's redirect.

## Cause

A pin is the ledger's name at grant time: the OAuth `ledger_id` claim (from the grant's `accountId`, `src/features/oauth/api/oidc-route.ts`, `oauth-token-gen.ts`) and the API key's `ledger_scope` column. Every check compares it with the requested name as a string. Nothing binds a pin to the repository itself. So a rename leaves the pin on the old name, and if the old name is then taken by a newly created ledger (creating it deletes the redirect), the pin silently follows that different repository.

## Options (owner decision; it is the credential trust boundary)

1. **Bind pins to the repository ID.** Record the ID at grant and key-mint time (token claim and API-key column, with a migration that resolves existing pins). Resolve it to the current name per request, cached, and compare canonical names everywhere a pin is checked. The pin then follows renames and never follows a recreated name.
2. **Canonicalize by name.** Resolve the pin's current `full_name` through the redirect when the identity is built, and accept both names. This fixes the rename case, but a recreated name is still followed silently, as it is today.
3. **Accurate refusal only.** Keep string pins. Make the refusal name the pin ("pinned to `<owner>/qa-…-p1`; a pin keeps the name it was granted with — omit `ledger`, or use a new credential for the new name"), and have a pinned `listLedgers` say which name the pin uses.

Tests for 1 or 2: a pinned token addresses its ledger by the new name. For 1 only: a pin to a renamed-then-recreated name refuses the new repository.

## Dedupe

w23/061 (done) covered former names on create and rename. ADR 0007 scopes MCP credentials; w23/026 (blocked) is a different trust-boundary question about the same credentials.

---

**Blocked 2026-10-22** — This is the choice the note asks the owner to make. Nothing on the board, in ADR 0007 (which scopes MCP credentials) or elsewhere decides how a pin identifies its ledger.

- Option 1 changes the OAuth `ledger_id` claim, the grant flow and the API-key `ledger_scope` column, with a migration for existing pins.
- Option 2 makes every pinned request resolve its pin through the host's redirect.

Both move the credential trust boundary, which a worker should not settle. Option 3 changes only refusal wording and is compatible with either; it is the cheap interim if the owner wants something before deciding.

**Unblock:** the owner chooses option 1, 2 or 3 (or 3 now and 1 later), recorded on the board or as an ADR 0007 amendment. Who can clear it: the repository owner.
