# `updateLedgerFiles` with two edits to one file previews both, reports success, and commits only the last

**Severity:** major (silent data loss on a reported success). **Estimate:** 30–45 minutes including tests. **Owner:** `backend-cluster/backend-v2` (`src/features/ai-agent/tools/edit-ledger-files-tool.ts`). MCP-only: REST `PUT …/files/{path}` writes one file per request and GraphQL has no multi-operation edit. **A1:** agents batch several `old_string` edits to the same file in one call; the preview they approve is not what lands.

## Repro (production, 2026-10-21, OAuth `ledger.read ledger.write` token pinned to a disposable QA ledger)

1. `createLedgerFiles` `qa-a.bean` with `"; qa x1\n; qa y1\n"`.
2. `updateLedgerFiles {files: [{path: "qa-a.bean", old_string: "x1", new_string: "x2"}, {path: "qa-a.bean", old_string: "y1", new_string: "y2"}], dry_run: true}` → `ok`, diff `-x1 -y1 +x2 +y2`, "Dry run: 2 change(s) previewed".
3. The same call without `dry_run` → `ok`, "Committed 2 change(s) to qa-a.bean, qa-a.bean. No new bean-check errors."
4. `readLedgerFiles qa-a.bean` → `"; qa x1\n; qa y2\n"`. The first edit is gone, and nothing reports it.

The related create case fails loudly instead: two `create` operations for one new path preview as "2 change(s)" with the last content, then the commit refuses with `BAD_USER_INPUT` "commit failed: repository file already exists" for a file that does not exist.

## Cause

`projectContents` (the dry run and the validation) chains later operations onto earlier ones for the same path. The commit branch of `prepare()` builds each `update` from the cached **original** content (`cached.content.replace(f.old_string, f.new_string)`) with the original `sha`, and sends one Gitea operation per entry. Gitea applies them in order, so the last whole-file write wins. The post-commit validation checks the projection, so it reports the state the user previewed, not the one committed.

## Fix

Collapse the operations per path before committing: fold every `update`/`replace` for one path into a single `update` whose content is the chained projection (reuse `projectContents`), and match `old_string` counts against the chained text so the dry run and commit refuse the same inputs. A `create` followed by edits of the same path becomes one `create` with the final content. Refuse with `BAD_USER_INPUT` naming the path whatever cannot be collapsed (two `create`s, or `delete` then edit). Tests: two `old_string` edits to one file commit both; a dry run and a commit of the same input return the same diff and refusal; two creates of one path are refused before any request.

Acceptance: step 4 reads `"; qa x2\n; qa y2\n"`, and the commit reports one change for that path.

## Dedupe

Searched `.pm/**` and git history for same-path, duplicate-path and chained edits in the file tools. Nothing matches. w23/017 is a concurrent-write race between two requests. This is one request contradicting itself.
