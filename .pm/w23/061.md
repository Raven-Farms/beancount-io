# After a ledger rename, its old name is refused with a false "already exists", and a pinned credential's own `listLedgers` names a ledger it may not address

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** `backend-cluster/ledger` for `findExistingRepo` (create path, `src/api/ledgers.ts`), and `backend-cluster/backend-v2` for the pin check (`src/features/ai-agent/api/mcp-context.ts`). Both flow through REST, GraphQL and MCP `createLedger`/`updateLedger`. **A1/A2:** "rename `personal` to `personal-2025` and start a fresh `personal`" is a routine year-end request.

## Repro (production, 2026-10-22, OAuth `ledger.admin` account-wide plus a `ledger.read` token pinned to the first ledger; all ledgers `qa-`, since deleted)

1. `createLedger {name: "qa-…-p1"}`, then `updateLedger {ledger: "<owner>/qa-…-p1", name: "qa-…-p2"}`. Both succeed, and `listLedgers` shows only `p2`.
2. `createLedger {name: "qa-…-p1"}` returns `CONFLICT` "Ledger conflict: Name already exists", with the hint "Your existing ledgers are listed by `listLedgers`", which does not list it. After renaming `p2` back to `p1` (allowed since w3/496), `createLedger {name: "qa-…-p2"}` fails the same way.
3. For the token pinned to `p1`, `initialize` still says "Ledger <owner>/qa-…-p1". Its own `listLedgers` returns `qa-…-p2`, yet `ledger: "<owner>/qa-…-p2"` is refused with `FORBIDDEN` "outside this credential's ledger restriction". Omitting `ledger`, or passing the old name, works only because the repository host redirects the old name.

## Cause

The repository host keeps a redirect from a renamed repository's old name. `findExistingRepo` calls `repoGet(owner, name)`, which follows that redirect, so the create path treats any former name as occupied. w3/496 taught only the rename path to accept a redirect to the same repository; a redirect to a different repository is still reported as an existing ledger. Pins are stored as the `owner/name` string in the token's `ledger_id` claim (`oauth-token-gen.ts`), so a pin keeps the old name and is compared by string.

## Fix

1. When the `repoGet` result's `full_name` differs from the requested name, the name is a former name. Either allow the create (the host deletes the redirect, and old links to the renamed ledger stop resolving), or keep refusing with an accurate message: "`qa-…-p1` is the former name of `<owner>/qa-…-p2`; it stays reserved while links to it redirect." Which to do is an owner decision. The current message must not claim a ledger exists.
2. For pinned credentials, resolve the pin through the same redirect: compare the canonical `full_name` of the pin target with that of the requested ledger, not the raw strings. Alternatively, say in the refusal that the pinned ledger was renamed.

Tests: create over a former name (refused with the new message, or allowed); a pinned token addresses its ledger by the new name; a pin to a deleted-then-recreated name does not silently follow a different repository.

## Dedupe

w3/496 (done) covered rename-back to a self-redirect only. w5/042 (done) covered the collision wording for real collisions, and w3/566 (done) the dashboard rename slug. Nothing covers former names on create, or pins across a rename.
