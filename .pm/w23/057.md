# MCP tool calls still drop unknown keys inside nested objects: `readLedgerFiles` `startLine` returns the whole file, and a misspelt `sourceAccount` imports against the default account

**Severity:** major. A misspelt optional key in `importStagedBankTransactions` books bank rows against the wrong account and reports success. **Estimate:** 30 minutes including tests. **Owner:** `backend-cluster/backend-v2`, `refusingUnknownArguments` in `src/server/api/composition-root.ts`. **A1:** agents write tool arguments from memory, and `readLedgerFiles` returns `startLine`/`endLine` in camelCase, which invites the camelCase spelling on input.

## Repro (production, 2026-10-22, `beancount-mcp` 1.0.0, protocol `2025-11-25`, OAuth `ledger.read ledger.write` pinned to the QA ledger)

```json
{"name":"readLedgerFiles","arguments":{"files":[{"path":"main.bean","startLine":2,"endLine":3}]}}
```

Actual: `ok: true` with `startLine: 1, endLine: 92` — the whole file. `{"path":"main.bean","bogus":1,"end_line":1}` is likewise accepted. Control: `start_line: 2, end_line: 3` returns lines 2–3, and an unknown top-level key is refused (`Unrecognized key: "bogus"`).

Expected: `BAD_USER_INPUT` naming `files.0.startLine`. This is the refusal w5/039 added for top-level arguments.

## Cause

`refusingUnknownArguments` applies `.strict()` only to the root `ZodObject`. w5/039's resolution records the gap: "Only top-level arguments are covered; a nested object's unknown key is still dropped." Two live tool schemas still have a non-strict nested object, according to a walk of every published `inputSchema` for objects without `additionalProperties: false`:

- `readLedgerFiles` `files[]` (`src/features/ai-agent/tools/read-ledger-files-tool.ts`).
- `importStagedBankTransactions` `transactions[]` (`submitInput` in `src/features/ai-agent/tools/bank-import-tool.ts`). `source_account` is optional, so a misspelt `sourceAccount` is dropped and the rows post against the mapped account. This was found by reading the code; it was not run live, because the QA ledger has no bank connection.

## Fix

Make the refusal recursive: strictify nested `ZodObject`s that are reached through arrays, optionals and unions, while leaving schemas that already have a catchall alone. Alternatively, add `.strict()` to both item schemas and add a test that walks every registered tool's schema so that no nested object stays loose. Tests: `files.0.startLine` and `transactions.0.sourceAccount` are refused with their path; snake_case calls are unchanged.
