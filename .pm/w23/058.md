# `insertReceiptTransaction` stores the receipt before the entry is validated: a refused entry leaves an orphan document commit (git storage) or an orphan permanent copy (S3)

**Severity:** major. A refused call is not side-effect free, and every retry adds another orphan. **Estimate:** 45–60 minutes including tests. **Owner:** `backend-cluster/backend-v2`, `LedgerReceiptWorkflow` in `src/features/ledger/workflow/ledger-receipt-workflow.ts`. The workflow is shared, so REST `POST …/receipts/insert`, GraphQL `insertReceiptTransaction` (dashboard and mobile receipt review) and MCP `insertReceiptTransaction` change together. **A1:** an agent that gets `UNBALANCED` fixes the postings and retries, which is exactly the path that multiplies orphans.

## Repro (production, 2026-10-22, `beancount-mcp` 1.0.0, OAuth `ledger.read ledger.write` pinned to the QA ledger)

1. Put the ledger on git receipt storage: `2000-01-01 custom "beancountio-option" "receipt_storage" "git"`.
2. Call `generateTempAssetUploadUrl`, then PUT a 70-byte PNG.
3. Call `insertReceiptTransaction` with `input.postings` `Expenses:Food:Groceries 1.00 USD` and `Assets:Cash -2.00 USD` (unbalanced), `payee: "qa-…-rcpt"` and `date: "2026-08-30"`.

Actual: `isError: true`, `UNBALANCED` "entry 1: Transaction does not balance: residual 1.00 USD". The repo nevertheless gained the commit `docs: add receipt documents/2026-08-30-qa-…-rcpt-<id>.png`, and `listLedgerFiles dir_path=documents` lists that file. No transaction or `document` directive references it. A retry commits another file with a new random `<id>`.

Under the default S3 storage, the same call is refused with "entry 0: …", after `copyTempToPermanent` has already copied the upload into the ledger's permanent asset scope. Nothing references that copy, and the temporary object is kept, so each retry adds another permanent copy. This was found by reading the code; it is not observable through the API.

Expected: a refused insert has no side effects, which matches the REST description "in one operation".

## Cause

Both strategies promote the receipt (`createLedgerFile` commit, or `copyTempToPermanent`) and only afterwards call `writeBulkEntries`. That call is the first place the postings, date, accounts and tokens are validated. Neither the tool nor the REST/GraphQL schema checks `date`, the posting balance or the account names up front.

## Fix

Validate before promoting: build the same `LedgerEntryInput[]` first and run the ledger's checks without committing. For example, give the bulk-entries route a validate-only mode and call it first. If that is too heavy, compensate on refusal: delete the receipt file just committed (git) or the permanent copy (S3), then rethrow. Tests, on every surface: an unbalanced or invalid-account insert leaves the repo's file list and commit count unchanged, and the S3 path deletes the permanent copy; a valid insert is unchanged.

## Dedupe

The board has no receipt atomicity item. w2/m17/t004 (done) kept the existing "receipt cleanup and commit" ordering during the authorization migration but did not examine the refusal path.

QA cleanup: the orphan probe file was deleted (`deleteLedgerFiles`, by blob sha), and the fixture's `main.bean` is byte-identical to the pre-probe blob.
