# A file batch inside both documented caps fails with `SERVICE_UNAVAILABLE`: the internal hop to the ledger service has a smaller body limit

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** `backend-cluster/ledger` (`app.use(bodyParser({ jsonLimit: "2mb" }))` in `src/server/start-server.ts`) and `backend-cluster/backend-v2` (the edit tool's projected bean-check and commit calls, plus the mapping of the ledger's 413). Shared by MCP `createLedgerFiles`/`updateLedgerFiles` and their REST/GraphQL twins. **A1:** importing a year of statements as two or three large files is the batch `docs/mcp.md` sizes for. The agent is told a dependency is down and retries forever.

## Repro (production, 2026-10-22, token pinned to the QA fixture, dry runs only)

`createLedgerFiles {dry_run: true}` with two new files of plain comment text, each under the 1 MiB file cap, in a request under the 2 MiB request cap:

| files | result (stable across retries) |
| --- | --- |
| 1 × 1.0 MB | `ok`, preview |
| 2 × 0.4 MB, 2 × 0.5 MB, 2 × 0.7 MB | `ok`, preview |
| 2 × 0.9 MB (~1.8 MB request) | `SERVICE_UNAVAILABLE` "preview refused: Ledger API is temporarily unavailable", hint "A dependency is down. Retry with backoff" |

Controls: a 1.1 MB single file is refused correctly, naming the 1 MiB file cap. A 2.2 MB request is refused with 413 (wording: w23/073).

## Cause (from source; confirm with the ledger log)

The preview runs bean-check over the projected ledger (existing files plus the new ones), and the commit sends the files to the ledger service. Both go as JSON bodies to a service whose parser stops at 2 MB. A request that is just under backend-v2's 2 MiB cap re-serializes past that limit, which grows further with existing files or any encoding. The ledger's 413 then surfaces as `SERVICE_UNAVAILABLE`.

## Fix

Make the internal limit cover the largest request backend-v2 can forward: the 2 MiB MCP cap plus the projected files, or derive both from one constant with headroom. Alternatively, have backend-v2 refuse up front with `BAD_USER_INPUT` naming the combined limit. Either way, map a ledger-service 413 to `BAD_USER_INPUT` "the change is too large to validate in one request; split it", never to `SERVICE_UNAVAILABLE`. Tests: 2 × 0.9 MB create previews and commits (or is refused with the size message); a ledger 413 maps to `BAD_USER_INPUT`.

## Dedupe

w23/073 is the outer 2 MiB refusal's wording. w23/072 is a different `SERVICE_UNAVAILABLE` (concurrent writes). No item covers the internal body limit.
