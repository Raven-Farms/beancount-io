# `commits` silently caps `limit` at 50: asking for 1000 returns 50, which reads as the end of history

**Severity:** minor. **Estimate:** 20 minutes. **Owner:** `backend-cluster/backend-v2`, in the commits input schema shared by MCP `beancount://{owner}/{name}/commits`, REST `GET …/commits` and GraphQL. **A1:** an agent auditing "every change this year" requests a large page, gets 50, and stops, because a page shorter than `limit` normally means the last page.

## Repro (production, 2026-10-21, OAuth `ledger.read` token pinned to a disposable QA ledger with more than 100 commits)

| Read | Items |
| --- | --- |
| `commits` (default) | 30 |
| `commits?limit=50` | 50 |
| `commits?limit=60` / `?limit=1000` | 50 |
| `commits?limit=1000&page=2` | the same 50 as `limit=50&page=2` (commits 51–100) |
| REST `GET /api-gateway/v1/ledgers/<owner>/<name>/commits?limit=1000` | 200, 50 items |

The REST OpenAPI declares `limit: {minimum: 1, default: 30}` with no maximum. `docs/mcp.md` gives only the defaults. Neither says the repository host caps a page at 50.

## Fix

Declare `maximum: 50` on `limit` in the shared schema, so REST, GraphQL and MCP refuse `limit > 50` with `BAD_USER_INPUT` "limit: at most 50". That matches how `listLedgers` (`maximum: 100`) and `listLedgerEntries` (`maximum: 1000`) advertise theirs. Add "at most 50 per page; page through with `page`" to `docs/mcp.md`. Check the other repository-host-backed lists that take `limit` (collaborators, social lists, catalog) against the host's cap in the same change. Tests: `limit=51` is refused on each surface, and `limit=50` still returns 50.
