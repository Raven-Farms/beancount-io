# Social follower/following/starred lists answer an unknown user, or a repository-host outage, with an empty success

**Severity:** minor. `beancount://social/profile?username=nosuchuser` is `NOT_FOUND`, but the three list reads for the same name return `{"users":[],"total":0}` / `{"repositories":[],"total":0}`, indistinguishable from a real user with no followers (the w23/014 class). Any upstream failure — timeout, 5xx — is also reported as an empty list. **Estimate:** 20–30 minutes with tests. **Owner:** `backend-cluster/backend-v2` — `src/features/gitea/user-profile/service/user-profile-service.ts` (`getUserFollowers`, `getUserFollowing`, `getUserStarredRepos`), shared by REST `/api-gateway/v1/social/*`, GraphQL and MCP `beancount://social/{followers,following,starred-repositories}`. **A1.**

## Repro (production, 2026-10-21, account-wide OAuth `ledger.read` token)

- `beancount://social/profile?username=nosuchuser-qa-x` → JSON-RPC `-32002`, `data.code: NOT_FOUND`, "User with ID 'nosuchuser-qa-x' not found".
- `beancount://social/followers?username=nosuchuser-qa-x` → `200` `{"users":[],"total":0}`; `following` and `starred-repositories` likewise.

## Cause

Each list method wraps the repository-host call in `try { … } catch (error) { logger.error(…); return { users: [], total: 0 }; }`, swallowing the host's 404 and every other failure. The profile read in the same file already distinguishes a 404 (`isNotFound`) and throws `NotFoundError`.

## Fix

In the three list methods, map a host 404 to `NotFoundError("User …")` (reuse `isNotFound`) and let other failures propagate so they surface as `SERVICE_UNAVAILABLE`. Tests per method: unknown user → `NOT_FOUND` on REST, GraphQL and MCP; host 500 → `SERVICE_UNAVAILABLE`; a real user with no followers still returns `[]`.
