# REST answers a bearer token it rejected with "send `Authorization: Bearer <token>`", the header the caller just sent

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** `backend-cluster/backend-v2`, `requireIdentity` in `src/server/rest/v1-route.ts` and the bearer resolution in front of it. **A1:** agents connected over MCP routinely try the same token against REST, for the archive fallback (w23/023) or a REST-only read. Told to send the header they already sent, they retry or conclude the API is broken, instead of switching credentials.

## Repro (production, 2026-10-22)

`GET /api-gateway/v1/ledgers/<owner>/mcp-agent-eval/years` with `Authorization: Bearer <token>`:

| token | status | message |
| --- | --- | --- |
| valid OAuth token issued for the MCP resource (`…/api-gateway/mcp`) | 401 | "This endpoint requires a credential: send `x-api-key: <personal-access-token>` or `Authorization: Bearer <token>`." |
| `garbage.token.value` | 401 | same |
| no header | 401 | same |

The MCP audience refusal is by design (ADR 0007, `docs/mcp.md`: "Application API/mobile tokens targeting `{issuer}/v1` do not authenticate to MCP", and the reverse holds too). The defect is the message: a presented but rejected credential, whether wrong audience, expired, or malformed, is reported as an absent one.

## Fix

When an `Authorization: Bearer` or `x-api-key` header is present but resolves to no identity, answer 401 `UNAUTHENTICATED` with a message saying the credential was not accepted. When the token verifies for the MCP resource, name it: "This token was issued for the MCP endpoint (`/api-gateway/mcp`); REST needs a personal access token or an application token". Otherwise say "expired, revoked, malformed, or issued for another resource". Keep the current text for requests with no credential. Tests: no header, garbage bearer, MCP-audience token and expired token each get their own message; GraphQL's equivalent refusal gets the same wording.
