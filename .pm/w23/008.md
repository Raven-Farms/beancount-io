# A failed `createLedger` leaves its `requestId` stuck "in progress" for 24 hours, so the idempotent retry can never succeed

Found by MCP QA on 2026-10-20 against `https://beancount.io` (OAuth `ledger.read ledger.write ledger.admin`, account-wide, on the QA account, which is at its free-plan ledger limit).

**Repro (MCP; REST `POST /api-gateway/v1/ledgers` and GraphQL `createLedger` share the workflow):**

```text
createLedger {name:"qa-20261020-mcp-w23", requestId:"qa-20261020-w23-b"}  → RESOURCE_LIMIT_REACHED (correct)
createLedger {name:"qa-20261020-mcp-w23", requestId:"qa-20261020-w23-b"}  → CONFLICT "Ledger creation conflict: A creation with this requestId is still in progress"
… same call 20s, 40s, 60s later                                          → same CONFLICT
```

Nothing is in progress: the first attempt finished, with a refusal. The same happens after any failure inside creation: a plan limit, a name the host refuses, or an upstream `SERVICE_UNAVAILABLE`. The last case is exactly the one an idempotency key exists to retry safely. After the user frees room or the outage clears, the documented retry with the same `requestId` keeps answering `CONFLICT` until the 24-hour TTL expires.

The `CONFLICT` hint makes it worse. It says "`getEntryContext` returns the entry's current `sha256sum`" (`mcp-errors.ts:80-81`), an instruction about journal entries that has nothing to do with ledger creation.

**Expected:** a request that ends in an error releases its `requestId`, so a retry with the same request runs again and returns its real outcome: the ledger, or the same refusal. Only a concurrently running attempt answers "in progress". The `CONFLICT` hint for creation should say to wait and retry the same `requestId`, or to use a new one.

**Root cause:** `backend-cluster/backend-v2/src/features/ledger/workflow/ledger-workflow.ts:556-588`. The record is written `status: "in-progress"` before `createLedgerOperation`, and only a success overwrites it with `"done"`. A throw leaves the in-progress record behind for `TTL.HOUR_24`. The `w3/m53/t003` tests cover replay, a different request, and the in-progress case, but not a failure followed by a retry.

**Fix:** wrap the create in `try/catch`, delete the idempotency key (or mark it `failed`) before rethrowing, and keep the per-user lock around both. Give `ConflictError` a creation-specific hint, or let the error carry its own hint so the generic entry hint isn't applied. Add a workflow test where the first attempt throws `RESOURCE_LIMIT_REACHED` and the same `requestId` then succeeds, plus one parity case on REST, GraphQL and MCP. Owner: backend-v2. Estimate: ~30m.
