# `createLedger`/`updateLedger` accept names their schema allows but the service rewrites: `x-` is created as `x`, `a--b` as `a-b`

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** `backend-cluster/backend-v2`, the ledger name schema shared by REST `ledgerCreateInput`/`ledgerUpdateInput`, GraphQL and MCP `createLedger`/`updateLedger`. The rewrite is `slugify` in `backend-cluster/ledger/src/shared/ledger-name.ts`. **A1:** an agent addresses the ledger by the name it sent, and the next call is `NOT_FOUND`.

## Repro (production, 2026-10-22, OAuth `ledger.admin` account-wide; ledger since deleted)

`createLedger {name: "qa-…-x-", private: true}` returns `ok`, and the ledger is created as `<owner>/qa-…-x`. `deleteLedger {ledger: "<owner>/qa-…-x-"}` then answers `NOT_FOUND`, and `listLedgers` shows `qa-…-x`. The published `inputSchema` pattern `^[a-z0-9_-]+$` admits leading, trailing and repeated hyphens, and `slugify` collapses `-+` and trims hyphens from both ends.

Related: if `books` exists, `createLedger {name: "books-"}` reports "Name already exists" for a name the caller never used. The dashboard and mobile forms show a slug preview (w4/041, w21/477); API callers get no notice.

## Fix

Refuse names that `slugify` would change, with `BAD_USER_INPUT` naming the normalized form ("use `qa-x`"). Alternatively, tighten the shared pattern to `^[a-z0-9_]+(-[a-z0-9_]+)*$` so `tools/list` publishes the real rule. Apply this to create and rename alike. Tests: `x-`, `-x` and `a--b` are refused on REST, GraphQL and MCP; `a-b` and `a_b` are unchanged.

## Dedupe

w4/041 and w21/477 (done) cover the mobile slug preview; w0/023 (done) covers the dashboard message for an empty slug; w3/566 (done) covers the dashboard rename slug. None covers the API accepting a non-slug name.

The `-` and `_` refusals word the same rule two ways ("at least one alphanumeric character" vs "at least one letter or number"); unify them while here.
