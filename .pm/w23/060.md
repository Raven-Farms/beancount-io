# `addLedgerEntries` and `appendLedgerText` always return `entryHashes: []`, so an agent can't act on the entry it just wrote

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** `backend-cluster/backend-v2`: `addLedgerEntries` in `src/features/ai-agent/api/mcp-tools.ts`, which hard-codes `entryHashes: []`, and `append-ledger-text-tool.ts:98`. **A1:** add → verify → fix is the core agent loop, and `getEntryContext`, `updateEntrySource` and `deleteEntrySource` all take the hash.

## Repro (production, 2026-10-22)

`addLedgerEntries` with one balanced transaction returns `ok`, "Added 1 entry to main.bean", `wrote: [{path: "main.bean"}]` and `entryHashes: []`. A committed `appendLedgerText` returns `wrote: [{path, line: 53}]` and `entryHashes: []`. To get the hash, the agent has to call `listLedgerEntries` with account, time and type filters and guess which row is new, which is ambiguous when identical entries exist.

The output schema says "Entry hashes the write created or touched, when known". The server knows them after the commit: it re-reads the ledger to bean-check (`validation.errorsAfter`) and can match the written spans, as `updateEntrySource` already does with `newEntryHash`.

## Fix

After the commit, map each written entry to its hash (by file and line from the projected ledger, or by computing the canonical hash of the written directive) and return them in request order, on REST and GraphQL as well if they expose the hashes. Tests: one hash per written entry; it resolves through `getEntryContext`; `deleteEntrySource` with that hash removes exactly that entry.

## Dedupe

w5/942 (open) covers the same gap for `importStagedBankTransactions`. Its claim that "other MCP write tools report the file and the hashes they wrote" holds for `wrote` but not for `entryHashes`, so both items should be fixed together.
