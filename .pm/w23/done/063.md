# `leaveLedger` by the ledger's owner answers `NOT_FOUND` "Ledger not found" instead of the documented "owners cannot leave"

**Severity:** minor. **Estimate:** 20–30 minutes. **Owner:** `backend-cluster/backend-v2`, `LedgerCollaboratorsWorkflow.leaveLedger` (`src/features/ledger/workflow/ledger-collaborators-workflow.ts`). It is shared by REST, GraphQL and MCP `leaveLedger`. **A1:** an agent that gets "Ledger not found" for a ledger it just read concludes the ledger is gone.

## Repro (production, 2026-10-22, OAuth `ledger.admin` account-wide, disposable `qa-` ledger since deleted)

`createLedger {name: "qa-…-leave"}`, then `leaveLedger {ledger: "<owner>/qa-…-leave"}` → `isError: true`, `NOT_FOUND` "Ledger not found". `checkLedger` on the same ledger still succeeds.

Control: `removeLedgerCollaborator {collaborator: <owner>}` on the same ledger returns `OPERATION_NOT_ALLOWED` "…owns this ledger; an owner's access can't be granted or removed as a collaborator" (w23/025).

Expected: `docs/mcp.md` says "Owners cannot leave their own ledger", so the response should be `OPERATION_NOT_ALLOWED` with a hint to `deleteLedger` (or transfer, when that exists).

## Cause

`leaveLedger` calls the host's delete-collaborator for the caller's username. The owner is not a collaborator, so the host answers 404, which `error-to-domain.ts` maps to "Ledger not found". w23/025 added the owner check to `addOrUpdateCollaborator` and `deleteCollaborator` only.

## Fix

Before the host call, compare the caller with the ledger owner and refuse with the 025 wording adapted for leaving. Also check how a non-collaborator reader of a public ledger is answered: it should get a clear refusal, not `NOT_FOUND`. Tests on all three surfaces: owner leave → `OPERATION_NOT_ALLOWED`; collaborator leave unchanged.

## Dedupe

w23/025 (done) covers set/remove for the owner but not leave. w23/047 (done, not yet deployed when this was filed) only changes the 404 wording for entries and branches.

---

**Resolved 2026-10-22** — The owner now gets `OPERATION_NOT_ALLOWED` "alice owns this ledger; an owner can't leave it", with a hint to `deleteLedger`. A reader of a public ledger who holds no grant gets "carol is not a collaborator on this ledger, so there is nothing to leave". A caller who cannot see the ledger still gets `NOT_FOUND`.

**The cause differed from the note.** The host's 404 was never reached. The authorization model gives `can_leave` only to explicit collaborators (`collaborator_admin|write|read`, never the owner or the public wildcard), and `LEDGER_COLLABORATORS_LEAVE` conceals any relationship denial as "Ledger not found", which is meant for callers who cannot see the ledger.

**The fix.** `LedgerCollaboratorsWorkflow.leaveLedger` (`backend-cluster/backend-v2/src/features/ledger/workflow/ledger-collaborators-workflow.ts`) catches that concealed `NOT_FOUND` and asks whether the caller may read the ledger's metadata. If so, it refuses with the real reason, telling the owner apart by login (case-insensitive, as in w23/025). Otherwise it rethrows the concealment unchanged, so nothing about a hidden ledger leaks. Credential refusals and the anonymous path are unchanged. REST, GraphQL and MCP share the workflow, and `docs/mcp.md` documents it.

**Tests:** `collaborator-parity.test.ts`, through the real REST, GraphQL and MCP adapters, the authorization PDP and the source-backed relationship evaluator, checks on every surface:
- the owner's refusal;
- a public-ledger reader's refusal;
- `NOT_FOUND` for a caller who cannot see the ledger, with no removal.

The fixture gained the sources a content-read check consults: the ledger's visibility, the owner's account, and a grant lookup that answers 404 without a grant, as the ledger service does. The existing leave test still passes: a collaborator leaves, and a former member of the private ledger still gets `NOT_FOUND`. Reverting the fix fails the new test on all three surfaces.

**Gates:** backend-v2 typecheck, lint/Knip, 6789 tests, OpenAPI unchanged. `batch-processor` timed out under load and passed alone (17/17); the environment-only `upstream-survival.test.ts` (w23/027) failed as usual.
