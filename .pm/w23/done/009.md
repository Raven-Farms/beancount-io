# Star state is readable only on GraphQL: REST and MCP can set a star but never read it back

Found by MCP QA on 2026-10-20 against `https://beancount.io` (OAuth `ledger.read ledger.write` token pinned to a synthetic QA ledger, plus the same account's session for GraphQL and REST).

**Repro:**

```text
MCP setLedgerStar {starred:true}                                → {success:true, isStarred:true}
GraphQL getLedger(ledgerId:"<owner>/<name>"){ isStarred }        → true
MCP resources/read beancount://<owner>/<name>/metadata          → {id, name, fullName, …, permissions, description}   (no isStarred)
REST GET /api-gateway/v1/ledgers/<owner>/<name>                  → same fields, no isStarred
MCP beancount://social/starred-repositories?username=<owner>     → {"repositories":[],"total":0}   (the starred ledger is private)
```

Unstarring flips GraphQL back to `false`, and REST and MCP show nothing either way. An agent on MCP or REST can't find out whether a ledger is starred before toggling it, or confirm the result later.

**Expected:** the `getLedger` verb returns `isStarred` for the caller on all three surfaces: REST `GET /ledgers/{owner}/{name}`, the MCP `metadata` resource, and GraphQL `getLedger`. It is `null`/absent only for an anonymous caller, as GraphQL's nullable field already allows.

**Root cause:** GraphQL computes `isStarred` in a field resolver (`backend-cluster/backend-v2/src/features/ledger/api/resolvers/ledger-resolver.query.ts:200-212`, `workflow.isLedgerStarred`). The REST handler and the MCP `ledgerMetadata` resource serialize the workflow's ledger object, which never calls it. `op-class.ts:883-887` maps the three surfaces to one verb, and the surface-parity gate compares verbs, not result fields, so the gap passes CI.

**Fix:** add `isStarred` to the REST/MCP `getLedger` result through `workflow.isLedgerStarred` when the caller is authenticated, add it to the v1 OpenAPI schema (`yarn generate-v1-openapi`), and add a contract test that stars through one surface and reads `isStarred: true` on all three. Owner: backend-v2 (REST + MCP; GraphQL unchanged). Estimate: ~30m.

---

**Resolved 2026-10-20** — `LedgerWorkflow.getLedgerMetadata` returns `getLedger`'s result plus the caller's `isStarred` from `isLedgerStarred`. REST `GET /api-gateway/v1/ledgers/{owner}/{name}` and the MCP `metadata` resource now use it. GraphQL `getLedger` keeps its on-demand field resolver, so it makes no extra star lookup. An anonymous reader gets no `isStarred` and no check runs, matching GraphQL's nullable field. The star check has its own credential rule, so a caller the metadata read admits but that rule refuses still gets the metadata, without `isStarred`. Authorization outages still propagate. `ledgerResultSchema` already declared an optional `isStarred`; the endpoint and resource descriptions now mention it (one-line OpenAPI description change, regenerated). `ledger-star-parity.test.ts` adds a case through the real workflow, `AuthorizationService` and source-backed evaluator: a star set via each of REST, GraphQL and MCP reads back as `isStarred` true, then false after unstarring, on all three surfaces. `ledger-workflow.test.ts` covers the star state, the anonymous omission, the refused-star-check fallback and outage propagation. `v1-routes.test.ts` now targets the new method. Reverting the REST and MCP wiring fails 3 parity cases. Native gates pass: typecheck, lint/Knip, 369 suites / 6370 tests, regenerated OpenAPI checked in. Shipped in the commit that moved this note (`backend-cluster/backend-v2`).
