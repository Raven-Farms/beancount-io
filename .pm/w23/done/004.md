# `banks/{itemId}` looks up the item before authorizing and ignores the ledger in its path

Found by MCP QA on 2026-10-20 against `https://beancount.io` with OAuth tokens pinned to a synthetic QA ledger (`ledger.read`, and `ledger.read ledger.write`). Neither holds `ledger.admin`, which every bank read requires.

**Repro** (`resources/read`, item id `x` that does not exist):

| URI | Result |
| --- | --- |
| `beancount://<owner>/<name>/banks` | `FORBIDDEN` "requires the \"ledger.admin\" scope" |
| `beancount://<owner>/<name>/banks/x/accounts` | `FORBIDDEN` (same) |
| `beancount://<owner>/<name>/banks/x/suggested-mapping` | `NOT_FOUND` "Bank connection not found" |
| `beancount://<owner>/<name>/banks/x` | **`BAD_USER_INPUT`** "Plaid Item not found", with the hint "Fix the named argument…" |

**Expected:**

- `banks/{itemId}` authorizes first, against the ledger named in the path, exactly as `getAccounts` does. A credential without `ledger.admin` gets `FORBIDDEN` before any lookup.
- An item that is missing, or that belongs to another ledger or user, gets the same concealed `NOT_FOUND` "Bank connection not found" that `BANK_CONNECTION_CONCEALMENT` already defines.
- The response never depends on whether the id exists elsewhere.

**Root cause:** `PlaidItemService.getItem` (`backend-cluster/backend-v2/src/features/plaid/service/plaid-item-service.ts:275-297`):

- It takes only the item id. It loads the item globally, throws `BadUserInputError("Plaid Item not found")` when the id is absent, and only then authorizes against the item's own ledger.
- When the id exists but authorization is denied, the caller gets the concealed `NOT_FOUND` instead, so the two answers differ.
- REST (`banks-handler.ts:96`) and MCP (`mcp-resources.ts:309-316`) both drop the `{owner}/{name}` in their paths. A bank on another ledger is returned under this ledger's URI.

**Fix:** give `getItem` the route's `ledgerId`, as `getAccounts(identity, itemId, ledgerId)` already has, and call `authorizeBankAction(…, BANK_CONNECTION_READ, ledgerId, itemId)` first. Missing or mismatched items become the concealed `NOT_FOUND`. GraphQL `getPlaidItem(id)` has no ledger argument: keep resolving the item's ledger there, but answer a missing id with the same concealed `NOT_FOUND`, not `BAD_USER_INPUT`. Add a three-surface case to the plaid parity tests covering a missing id, another ledger's id, and a credential without admin scope. Owner: backend-v2 (REST, GraphQL, MCP). Estimate: ~45m.

---

**Resolved 2026-10-20** — `PlaidItemService.getItem` takes the route's ledger. REST `banks/{itemId}` and MCP `beancount://{owner}/{name}/banks/{itemId}` pass it, and `getItem` authorizes `BANK_CONNECTION_READ` against that ledger and item before any lookup. A credential without bank authority gets `FORBIDDEN` whether or not the id exists, and the item is never read. The PDP's item check already conceals a missing item, another user's, or another ledger's as `NOT_FOUND` "Bank connection not found", so another ledger's bank is no longer returned under this ledger's URI. GraphQL `getPlaidItem(id)` names no ledger and still resolves the item's own. A missing id there, or a post-authorization mismatch, now answers `NOT_FOUND` "Bank connection not found" instead of `BAD_USER_INPUT`. The new `bank-item-read-parity.test.ts` drives REST, MCP and GraphQL through the real service, `AuthorizationService` and source-backed relationship evaluator. It covers the ledger's own bank (200 on all three), a missing id and another user's bank (the same concealed `NOT_FOUND` on all three), another ledger's bank (404 under this path, 200 under its own path and on GraphQL), and a `ledger.read ledger.write` token (`FORBIDDEN` with zero item lookups). Reverting the three production files fails 3 of 5 cases. Native gates pass: typecheck, lint/Knip, 369 suites / 6342 tests, OpenAPI generation without drift. Shipped in the commit that moved this note (`backend-cluster/backend-v2`).
