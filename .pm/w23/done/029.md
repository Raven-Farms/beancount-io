# `renameLedgerFile` matches `include` lines as literal repo-root paths, so it misses, falsely refuses, and corrupts relative includes

**Severity:** major (a reported-clean rename leaves broken includes, or rewrites a valid include to a missing file). **Estimate:** 45–60 minutes including tests. **Owner:** `backend-cluster/backend-v2`, in `src/features/ledger/workflow/ledger-workflow.ts` (`includeTargetOf`, `matchesIncludeLine`, `rewriteIncludeLine`, `renameLedgerFile`). The workflow is shared, so REST `POST …/rename-file`, GraphQL `renameLedgerFile` and MCP `renameLedgerFile` all change together. **A1:** agents reorganize ledgers into `2026/`-style folders, which is exactly where relative includes live.

## Repro (production, 2026-10-21, OAuth `ledger.read ledger.write` token pinned to a disposable QA ledger)

Setup, created in one `createLedgerFiles` call:
- `d/x.bean`
- `d/inc.bean`: `include "x.bean"`
- `d/b.bean`
- `d/inc2.bean`: `include "b.bean"`
- root `b.bean`
- root `inc3.bean`: `include "./b.bean"`

Following beancount, the ledger service (`resolveIncludeTarget`, `backend-cluster/ledger/src/foundation/rustledger/file-map-loader.ts`) resolves `d/inc.bean`'s include to `d/x.bean` and `d/inc2.bean`'s to `d/b.bean`. `inc3.bean`'s resolves to root `b.bean`.

| Call | Result | Expected |
| --- | --- | --- |
| `renameLedgerFile d/x.bean → d/y.bean` | `ok`, `updatedIncludes: []`; `d/inc.bean` still says `include "x.bean"` | refuse without `updateIncludes`, as for a root include |
| `renameLedgerFile b.bean → c.bean` | `BAD_USER_INPUT` "b.bean is still included by d/inc2.bean" | refuse naming `inc3.bean`; `d/inc2.bean` includes a different file |
| same with `updateIncludes: true` | `ok`, `updatedIncludes: ["d/inc2.bean"]`; `d/inc2.bean` now says `include "c.bean"` (resolves to the missing `d/c.bean`); `inc3.bean` still says `include "./b.bean"` (now missing) | rewrite `inc3.bean` to `./c.bean` or `c.bean`; leave `d/inc2.bean` alone |

Each rename reported "No new bean-check errors" because the fixtures aren't reachable from `main.bean`. In a real ledger the same renames break the load or silently drop the included entries.

## Cause

`matchesIncludeLine` compares the include's literal target with `oldPath`, and `rewriteIncludeLine` writes `newPath` verbatim. Neither resolves the target against the including file's directory, normalizes `./` or `..`, or considers globs.

## Fix

Resolve each include with the same rule as `resolveIncludeTarget` (`posix.join(dirname(including), target)`, normalized, leading `/` stripped), and match on the resolved path. Rewrite with a target relative to the including file's directory (`posix.relative(dirname(including), newPath)`), keeping the original quoting and comment. Report a glob include whose matches change (`include "d/*.bean"` when `d/x.bean` moves out of `d/`) in the refusal rather than rewriting it.

Tests: the three rows above, a `../` include from a subdirectory, a quoted name with spaces, and a glob that still matches after the rename (no refusal) versus one that stops matching (refused).

Acceptance: the table's Expected column holds on REST, GraphQL and MCP.

## Dedupe

Searched `.pm/**` and history for rename plus include plus relative or subdirectory. w4/017 (done) fixed how the ledger reports URL includes and pinned the repo-relative resolution this note relies on. No rename item covers relative targets.

## Also: the rewritten include is not escaped (2026-10-21)

Same function, output side. `rewriteIncludeLine` interpolates `newPath` raw into `include "${newPath}"`. Production, disposable QA ledger, qa-only files (`qa-20261021-p.bean` containing `include "qa-20261021-c.bean"`, not itself included by `main.bean`): `renameLedgerFile {oldPath: "qa-20261021-c.bean", newPath: "qa-20261021-c\"x.bean", updateIncludes: true}` → `ok`, "updated includes: qa-20261021-p.bean. No new bean-check errors." The parent now reads `include "qa-20261021-c"x.bean"`, which beancount cannot parse; the check passed only because the parent is outside the loaded closure. Fix in the same change: write the target through the serializer's string escaping (`\\`, `\"`), or refuse a `newPath` containing `"`, `\` or a control character when any include must be rewritten. Test: a rename to a name with `"` either round-trips through bean-check or is refused, never written broken. (Separately, `renameLedgerFile` has no `dry_run`, unlike the other file writes: "Unrecognized key: \"dry_run\"".)

**Resolved 2026-10-21** — `renameLedgerFile` (`src/features/ledger/workflow/ledger-workflow.ts`), shared by REST `POST …/rename-file`, GraphQL `renameLedgerFile` and MCP `renameLedgerFile`, now resolves every `include` target against the directory of the file that declares it before matching. A new `src/features/ledger/utils/include-target.ts` restates the ledger service's `resolveIncludeTarget` rule: `posix.join(dirname(including), target)`, normalized, leading `/` stripped, URL targets skipped. The table's Expected column now holds. `d/x.bean → d/y.bean` is refused naming `d/inc.bean`, and with `updateIncludes` it rewrites that file to `include "y.bean"`. `b.bean → c.bean` names `inc3.bean` (and `d/up.bean`'s `../b.bean`) but never `d/inc2.bean`. With `updateIncludes`, each include is rewritten relative to its own file, keeping a leading `./` or `/` and its comment (`./e/c.bean`, `../e/c.bean`), and `d/inc2.bean` is left alone. A rewritten target is escaped (`\"`, `\\`), and double-quoted includes are parsed with escapes, so a rename to `c"x.bean` writes `include "c\"x.bean"`, which a rename back finds again. A glob include (`*`, `?`, `[…]`, `**`, Python `glob.glob(recursive=True)` semantics including the hidden-name rule, matched by a non-backtracking per-segment NFA) is never rewritten: a rename the glob still matches proceeds, and one that leaves it is refused as `BAD_USER_INPUT` on `newPath` naming the file and the pattern, even with `updateIncludes`. `docs/mcp.md` documents the rule. Tests: `include-target.test.ts` (41 cases: parsing, escaping round-trips, resolution, targets in the previous style, glob semantics, a 40-star pattern against a 2000-character name) and six `rename-parity.test.ts` cases on each of REST, GraphQL and MCP.
