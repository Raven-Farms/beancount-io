# Auto-routed writes create a new year file that nothing includes: the entry is committed, invisible, and reported as "No new bean-check errors"

**Severity:** major. Entries silently drop out of every report. **Estimate:** 45–60 minutes. **Owner:** `backend-cluster/backend-v2` `DirectiveAppendWorkflow.appendDirectiveText` (`appendLedgerText` on REST, GraphQL and MCP) and the bulk entry writer behind `addLedgerEntries` and bank import. Both route through `resolveEntryFile`'s `beancountio-option` templates. **A1:** the first entry of every new year or month is exactly what an agent writes after a year-end close.

## Repro (production, 2026-10-22, disposable `qa-` ledger, since deleted)

`main.bean`:

```beancount
2000-01-01 custom "beancountio-option" "transaction_file" "txns/{year}.bean"
include "txns/2026.bean"
2020-01-01 open Assets:Cash USD
2020-01-01 open Equity:Initial USD
```

`txns/2026.bean` holds one 1 USD transaction.

1. `appendLedgerText` with a 2027-01-03 transaction of 5 USD returns "Added 1 directive to txns/2027.bean. No new bean-check errors." The dry run says the same.
2. `addLedgerEntries` with a 2028-01-04 transaction of 7 USD returns "Added 1 entry to txns/2028.bean. No new bean-check errors."
3. `SELECT sum(position) WHERE account = 'Assets:Cash'` returns **1 USD**, not 13 USD. `listLedgerFiles dir_path=txns` lists `2027.bean` and `2028.bean`, but no `include` reaches them.

## Cause

w23/035 refused an explicit `path` outside the include closure but kept auto-routed targets as they were, because "the ledger's own routing rules may create the file they route to". Nothing adds an `include` for a newly created routed file, though. The projected bean-check loads from `main.bean`, so an unincluded file can never produce an error, and "No new bean-check errors" holds vacuously. A glob include such as `include "txns/*.bean"` avoids the problem; per-year includes, a common layout, do not.

## Fix

When a routed target is outside the include closure:

- (a) add `include "<target relative to main.bean>"` to `main.bean` in the same commit and say so in the summary; or
- (b) refuse with `BAD_USER_INPUT` naming the file and the missing include.

Option (a) matches what routing is for. Apply the same check in the bulk entry writer. Either way, never report "No new bean-check errors" for text the ledger does not load. Tests on REST, GraphQL and MCP: a new year file with per-year includes is included (a) or refused (b); a glob-covered new file is unchanged; an existing included year file is unchanged.

## Dedupe

w23/035 (done) covers an explicit `path` and expressly left auto-routing out. w23/056 covers `renameLedgerFile`'s own includes, a different path. No item covers routed files outside the closure.

---

**Resolved 2026-10-22** — Option (a). A routed write to a file the ledger does not load now adds `include "<file>"` to `main.bean` in the same commit, and says so. The projected check therefore loads the new entries, and "No new bean-check errors" is no longer vacuous.

**Whether a file would be loaded** comes from the ledger service's own include closure (`collectSourceFiles`: globs, includes of not-yet-existing files, cycles), computed over the projected file map. Nothing restates the rule. This matters because an extra include for a file a glob already covers is itself an error: the engine reports `Duplicate filename parsed`.

**Ledger (`backend-cluster/ledger`):**
- New `LedgerDataService.projectedSourceFiles`.
- New `POST /reports/{o}/{r}/source-files` (operation `getProjectedSourceFiles`, same caps as `/check`).
- New `addIncludes` (`src/features/ledger/utils/routed-includes.ts`), which inserts after the entry point's last `include`, so a per-year list stays together, or at its end.
- The bulk-entries route adds the include to `main.bean`'s text before any entry text, so w23/060's entry ranges stay right. It answers `included_files`, on dry runs too. The IDL and client are regenerated.

**backend-v2:**
- The bulk writer (`addLedgerEntries`, bank import, receipts) puts "; main.bean now includes …" in `message`; MCP also puts it in the summary and lists `main.bean` in `wrote`.
- `DirectiveAppendWorkflow` asks `ILedgerRepoService.projectedSourceFiles` about routed targets, projecting only the files it creates. It threads directives into the entry point after adding the include, so `wrote` lines hold. It reports "now includes" or, on a dry run, "would include" with the diff. A named `path` is unchanged (w23/035 already requires it to be loaded).
- If the closure lookup fails, for example against a ledger service deployed before the route, the append degrades to the previous behaviour and logs a warning instead of refusing every routed write. A ledger without `included_files` reads as none.
- `docs/mcp.md` documents both write tools.

**Real-engine check (scratch script):** on the note's layout, `include "txns/2026.bean"` plus a 2027 write gains `include "txns/2027.bean"`, loads both transactions, and has no errors. Under `include "txns/*.bean"` nothing is added, both load, and there is no duplicate error.

**Tests:**
- Ledger:
  - `addIncludes` (after the last include, appended, quoting);
  - `projectedSourceFiles` (per-year includes leave a new file out; a glob, or an include naming the file, takes it in);
  - the bulk route (commit carries `main.bean` with the include; a dry run reports it; an already loaded file leaves `main.bean` alone).
- backend-v2:
  - `addIncludeLines`;
  - `directive-append-workflow` (same-commit include, a check that loads it, dry-run diff, glob-covered unchanged, entry point also a target with lines still right, failed lookup degrades, named path not looked up);
  - `directive-text-parity` and `structured-entry-parity`: the include on REST, GraphQL and MCP.

Reverting the fix fails 3 ledger and 9 backend-v2 tests.
