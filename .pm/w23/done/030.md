# Backend read-modify-write tools replace a non-UTF-8 file's bytes with U+FFFD and report success

**Severity:** major (silent byte corruption on a reported-clean write). **Estimate:** 45–60 minutes including tests. **Owner:** `backend-cluster/backend-v2`. The cause is `src/shared/file-content.ts` `decodeFileContent`, read through `LedgerRepoService.getFilesContent` and `renameLedgerFile`'s include scan.

Affected writers:
- MCP `updateLedgerFiles` (`old_string` edits).
- `appendLedgerText` / `addLedgerEntries` on every surface, through the shared `directive-append-workflow.ts`.
- `renameLedgerFile` with `updateIncludes` on REST, GraphQL and MCP.

This is the backend counterpart of w4/276 (dashboard) and w21/042 (mobile). Both now open such files read-only. **A1:** an agent editing a ledger exported in Windows-1252 changes every non-ASCII byte it never touched.

## Repro (production, 2026-10-21, disposable QA ledger, OAuth `ledger.read ledger.write` token)

1. Create `qa-latin1.txt` with bytes `; qa Caf` + `E9` + ` latin-1 comment\nqa-tail\n` (GraphQL `createLedgerFile` accepts base64). The blob SHA equals `git hash-object` of those bytes. A `.txt` was used so production's w23/011 behavior didn't break the shared fixture's reads.
2. MCP `updateLedgerFiles {files: [{path: "qa-latin1.txt", old_string: "qa-tail", new_string: "qa-tail2"}]}` → `ok`, "Committed 1 change(s) … No new bean-check errors."
3. The new blob SHA equals the hash of the bytes with `E9` replaced by `EF BF BD` (`Caf�`), not of the original bytes with only `qa-tail2` changed.

REST `GET …/files/{path}` and `readLedgerFiles` also return the lenient decode (`Caf�`) with no signal that the text is lossy. An agent that copies it back with `replace` or REST `PUT` does the same damage.

## Cause

`decodeFileContent` uses `Buffer.toString("utf-8")`, which substitutes U+FFFD for invalid sequences. The edit, append and include-rewrite paths re-encode that text as UTF-8 and commit it whole. The ledger service rejected lenient decoding for exactly this reason in w23/011 ("it would let source-slice edits write U+FFFD back over the original bytes"). backend-v2's file paths never got the same rule.

## Fix

Decode strictly (`new TextDecoder("utf-8", { fatal: true })`) wherever content will be written back: the edit tool's file cache, the append workflow's targets, and the rename include scan. Refuse with `BAD_USER_INPUT` naming the file: "`<path>` is not valid UTF-8; convert it to UTF-8 before editing (rename and delete still work)". For reads, either keep the lenient text and add a flag such as `lossy: true` on `readLedgerFiles` and REST/GraphQL file reads, or refuse there as well. Pick one rule and apply it on all three surfaces.

Tests: a Latin-1 fixture, where an `old_string` edit, `appendLedgerText` with `path`, and an include rewrite each refuse without committing, and a byte-preserving `renameLedgerFile` of the same file still succeeds.

Acceptance: step 2 is refused with the blob unchanged. No backend write path can produce `EF BF BD` from a byte the request didn't touch.

## Dedupe

w4/276 and w21/042 (done) fixed the dashboard and mobile editors client-side. w23/011 (done, ledger service) handles undecodable files during load. Searched `.pm/**` for U+FFFD, lenient, non-UTF-8 and Latin-1. No backend write-path item exists.

---

**Resolved 2026-10-21** — `decodeFileContent` (`src/shared/file-content.ts`) now reports `lossy` when a file's bytes are not valid UTF-8 (`buffer.isUtf8`). `LedgerRepoService.getFilesContent` carries it as `lossy: true`. A new `assertWritableText` refuses every path that would rewrite a file from that text, with `BAD_USER_INPUT` "`<path>` is not valid UTF-8; convert it to UTF-8 before editing it (rename and delete still work)". It covers an `old_string` edit in the file tools (preview and commit alike), `appendLedgerText`/`addLedgerEntries` through `directive-append-workflow.ts` (preview and commit), and `renameLedgerFile`'s include rewrite on REST, GraphQL and MCP. Whole-file `replace`, delete, and a rename that moves the file's own bytes unchanged still work. For reads, the rule is one flag: REST `GET …/files/{path}` (`LedgerFile.lossy`, regenerated into `docs/openapi/v1.json`) and MCP `readLedgerFiles` keep the readable text and add `lossy: true` for such files. GraphQL `getLedgerFile` already returns the exact bytes as base64 with `encoding`. `docs/mcp.md` and the read tool's description say so. Not covered: the MCP `beancount://…/files/{path}` resource still returns the lenient text without a flag, because a text resource result has no field for one. Tests: `file-content.test.ts` (exact text including a kept BOM; Latin-1, truncated and overlong bytes marked lossy), `file-read-directory-parity.test.ts` (REST and the MCP tool flag the note's Latin-1 file and leave a base64 UTF-8 file unmarked), `edit-ledger-files-refusals.test.ts` (the repro's `qa-tail` edit refused in preview and commit with no commit; replace and delete still commit), `directive-append-workflow.test.ts` (a lossy target refused in preview and commit), and `rename-parity.test.ts` on all three surfaces (a Latin-1 includer refused under `updateIncludes`; a Latin-1 file renamed byte for byte). Reverting the production code fails 15. Gates: typecheck, lint/Knip, 6586 tests, OpenAPI regenerated. The one failure was the environment-only `upstream-survival.test.ts` (see w23/027). Shipped in the commit that moved this note (`backend-cluster/backend-v2`).
