# OAuth grants unknown scopes verbatim: requesting `ledger.superuser` yields a token whose `scope` says `ledger.read ledger.superuser`

Found by MCP QA on 2026-10-20 against `https://beancount.io`, on the QA account with its own dynamically registered public client and PKCE. Nothing beyond `ledger.read` was approved.

**Repro:** run the authorization-code flow with `scope=ledger.read ledger.superuser` and `resource=https://beancount.io/api-gateway/mcp`, approve on the consent page with one ledger selected, and exchange the code.

```text
token response  → {"token_type":"Bearer","expires_in":3600,"scope":"ledger.read ledger.superuser"}
JWT claims      → scope: "ledger.read ledger.superuser", aud: "https://beancount.io/api-gateway/mcp", ledger_id: "<owner>/<name>"
MCP listLedgers → ok (ledger.read works; the extra scope confers nothing)
```

Controls: a `resource` of `https://beancount.io/v1` is refused with `invalid_target` "dynamic clients must use the MCP resource", and an `openid`-only token gets `FORBIDDEN` on every tool.

**Why it matters:** `/.well-known/oauth-authorization-server` advertises `scopes_supported` without `ledger.superuser`, yet the server accepts it. The consent page then shows whatever scope strings the client invented, and a signed token asserts them. Authorization in backend-v2 ignores unknown scopes today (`identity.ts:129-132` checks membership in the known set), so nothing is exposed now. But a client can present misleading scope names to the person approving, and any future prefix or wildcard scope check would inherit forged claims.

**Expected:** an unknown resource scope is refused before the consent page with `invalid_scope` per RFC 6749 §4.1.2.1, or dropped, so the issued `scope` contains only `openid`, `offline_access`, `profile`, `email`, `ledger.read`, `ledger.write` or `ledger.admin`.

**Root cause:** `backend-cluster/backend-v2/src/features/oauth/api/oidc-route.ts:647-651`. The comment says "unsupported values were already rejected against `scopes` above", but the login-prompt branch calls `grant.addResourceScope(resource, requestedScope)` with the raw requested string. `getResourceServerInfo` (`:211-214`) lists the allowed scopes, yet nothing intersects the request with them.

**Fix:** intersect `requestedScope` with `openid offline_access ${API_SCOPES}` before `addOIDCScope`/`addResourceScope`, or validate at the authorization endpoint and refuse with `invalid_scope`. Make the consent page show only recognized scopes. Add an `oidc-route` test where a request with a bogus scope yields a token without it, or is refused. Owner: backend-v2 (OAuth; no REST/GraphQL/MCP parity change). Estimate: ~30m.

---

**Resolved 2026-10-20** — `oidc-route.ts` now builds every view of the requested scope through `supportedScope()`, which drops any value not in `SUPPORTED_SCOPES`. That list is the one the provider's `scopes` config now reads: `openid`, `offline_access`, `profile`, `email` and `API_SCOPES`. It applies at the consent-page URL, the interaction-details response the consent page renders, the OIDC and resource grants created at approval, and the "displayed scopes match the interaction" checks for account-wide and native-client consent. A client asking for `ledger.read ledger.superuser` is shown, granted and issued `openid ledger.read`. RFC 6749 §3.3 lets a server grant less than requested, so this takes the note's "dropped" option rather than an `invalid_scope` redirect. oidc-provider has no hook to refuse an unknown scope at its authorization endpoint without reimplementing its redirect validation. A new `oidc-route.test.ts` case runs the full dynamic-client PKCE flow for a ledger-pinned and an account-wide grant. The consent URL shows only supported scopes, the token response's `scope` is exactly `openid ledger.read`, and the signed JWT's `scope` lacks `ledger.superuser`. Reverting fails both. OAuth only; no REST/GraphQL/MCP parity change. Native gates pass: typecheck, lint/Knip, 370 suites / 6403 tests, OpenAPI generation without drift. Shipped in the commit that moved this note (`backend-cluster/backend-v2`).
