# `updateEntrySource` summary names the new hash twice and never the old one

Found by MCP QA on 2026-10-20 against `https://beancount.io` (OAuth read/write token pinned to a synthetic QA ledger).

**Repro:** append a transaction, take its `entry_hash` from `listLedgerEntries` (`d6bc22ae…` here) and its `sha256sum` from `getEntryContext`, then call `updateEntrySource` with a changed amount.

**Actual result:**

```json
{"summary": "Updated entry 788a6783… (new hash 788a6783…). No new bean-check errors.",
 "message": "Updated entry d6bc22ae…",
 "entryHash": "788a6783…", "newEntryHash": "788a6783…"}
```

**Expected:** `"Updated entry d6bc22ae… (new hash 788a6783…)"`. The summary is the line an agent reads first; today it says the old hash is the new one, and the agent then retries against the wrong one.

**Root cause:** `backend-cluster/backend-v2/src/features/ai-agent/api/mcp-source-slices.ts:87` formats `written.entryHash`. `LedgerJournalService.updateSourceSlice` (`src/features/ledger/service/ledger-journal-service.ts:419-426`) deliberately returns the *new* hash in `entryHash`, as the comment there says. The request's own `args.entryHash` is in scope in `SOURCE_SLICE_EXECUTORS.update`.

**Fix:** format the summary from the request's `entryHash` and `written.newEntryHash`, and add an assertion to the existing source-slice MCP test. MCP-only text, so no parity change. Estimate: ~10m.

---

**Resolved 2026-10-20** — `SOURCE_SLICE_EXECUTORS.update` now formats the `updateEntrySource` summary from the request's `entryHash` and the result's `newEntryHash`, giving `Updated entry <old> (new hash <new>)`. The result fields are unchanged; `entryHash` is still the new hash, as the ledger service's wire contract defines. `source-slice-parity.test.ts` let this through because its fake ledger service echoed the request's hash as `entry_hash`. The fake now follows the real contract (`backend-cluster/ledger/src/api/journal.ts`: `entry_hash` is the new hash), and the REST, GraphQL and MCP expectations follow it. The MCP summary assertion distinguishes the old hash from the new. Reverting the executor change fails the two MCP update cases. MCP-only text, so no parity change. Native gates pass: typecheck, lint/Knip, 369 suites / 6357 tests, OpenAPI generation without drift. Shipped in the commit that moved this note (`backend-cluster/backend-v2`).
