# A ledger description over Gitea's limit is refused with the raw "[Description]: MaxSize", and no schema declares the limit

**Severity:** minor. **Estimate:** 20 minutes. **Owner:** `backend-cluster/backend-v2`. Change the `createLedger` and `updateLedger` inputs on all three surfaces: the GraphQL `CreateLedgerInput`/`UpdateLedgerInput` (`ledger-resolver.types.ts`), the REST v1 body schema and the MCP input schema. **A1:** an agent writing a ledger description can't learn the limit from `tools/list` and can't act on the refusal text.

## Repro (production, 2026-10-21, OAuth `ledger.read ledger.admin` token pinned to the disposable QA ledger; description restored afterwards)

`updateLedger {description: "x" × 3000}` → `BAD_USER_INPUT` "[Description]: MaxSize", with the generic hint "Fix the named argument". The published MCP `inputSchema` for `description` is `{"type": "string"}` with no `maxLength`. `name` declares its limit (`maxLength: 100` plus the pattern), and the GraphQL input has `@MaxLength(100)` for name only.

Unicode, HTML-like text, newlines, `""` and `null` all behave correctly: they are stored or cleared as sent, and privacy is unchanged.

## Fix

Declare Gitea's limit for repository descriptions (2048 characters in the pinned Gitea version; confirm it against `deploy/`) as `maxLength` / `@MaxLength` on create and update across REST, GraphQL and MCP. Validate it before the Gitea call with a message that names the limit and the received length. Add a parity test that a 2049-character description is refused with that message on each surface.

## Dedupe

Searched `.pm/**` for MaxSize and ledger description limits. Nothing matches.

---

**Resolved 2026-10-22** — The repository host's limit on a ledger description, Gitea 1.24's `MaxSize(2048)` on create and edit (`deploy/` pins `gitea:1.24`), is now `LEDGER_DESCRIPTION_MAX` in `src/features/ledger/workflow/ledger-workflow.types.ts`. It is declared on every surface. The shared REST/MCP Zod `description` (`lifecycle-handler.ts`, behind REST `POST`/`PUT …/ledgers` and MCP `createLedger`/`updateLedger`) carries `max(2048)`, so `docs/openapi/v1.json` and `tools/list` advertise `maxLength: 2048`. GraphQL `CreateLedgerInput`/`UpdateLedgerInput` carry `@IsOptional() @MaxLength(2048)`. Every surface refuses with "A ledger description can be at most 2048 characters" before the host is called. `createLedger`/`updateLedger` in the workflow repeat the check for in-process callers, counting characters as Gitea does, with "description is N characters; a ledger description can be at most 2048". Tests: `lifecycle-parity.test.ts` on REST, GraphQL and MCP refuses a 2049-character description on create and update (no ledger created, description unchanged) and accepts exactly 2048. Reverting fails all 3. Gates: typecheck, lint/Knip, 6618 tests, OpenAPI regenerated (`maxLength` on both bodies). The three failures were the environment-only `upstream-survival.test.ts` (see w23/027) and the `archive-parity` and `batch-processor` timing flakes under the parallel run. Shipped in the commit that moved this note (`backend-cluster/backend-v2`).
