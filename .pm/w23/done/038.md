# `commits` silently caps `limit` at 50: asking for 1000 returns 50, which reads as the end of history

**Severity:** minor. **Estimate:** 20 minutes. **Owner:** `backend-cluster/backend-v2`, in the commits input schema shared by MCP `beancount://{owner}/{name}/commits`, REST `GET …/commits` and GraphQL. **A1:** an agent auditing "every change this year" requests a large page, gets 50, and stops, because a page shorter than `limit` normally means the last page.

## Repro (production, 2026-10-21, OAuth `ledger.read` token pinned to a disposable QA ledger with more than 100 commits)

| Read | Items |
| --- | --- |
| `commits` (default) | 30 |
| `commits?limit=50` | 50 |
| `commits?limit=60` / `?limit=1000` | 50 |
| `commits?limit=1000&page=2` | the same 50 as `limit=50&page=2` (commits 51–100) |
| REST `GET /api-gateway/v1/ledgers/<owner>/<name>/commits?limit=1000` | 200, 50 items |

`beancount://social/followers?username=open_ledger&limit=100` also returns 50 users (the account has more than 400), so the social lists share the cap. Their documented `total` is the page size, so it can't reveal the truncation either.

The REST OpenAPI declares `limit: {minimum: 1, default: 30}` with no maximum. `docs/mcp.md` gives only the defaults. Neither says the repository host caps a page at 50.

## Fix

Declare `maximum: 50` on `limit` in the shared schema, so REST, GraphQL and MCP refuse `limit > 50` with `BAD_USER_INPUT` "limit: at most 50". That matches how `listLedgers` (`maximum: 100`) and `listLedgerEntries` (`maximum: 1000`) advertise theirs. Add "at most 50 per page; page through with `page`" to `docs/mcp.md`. Check the other repository-host-backed lists that take `limit` (collaborators, social lists, catalog) against the host's cap in the same change. Tests: `limit=51` is refused on each surface, and `limit=50` still returns 50.

**Resolved 2026-10-22** — The commits part had already shipped in `d4006198a` (w21/314): `MAX_COMMITS_PAGE_SIZE = 50`, refused on REST, GraphQL and MCP and published in the schemas. This item finished the note's "check the other repository-host-backed lists" part. A new shared `src/shared/host-page.ts` holds `HOST_PAGE_MAX = 50` (Gitea's `MAX_RESPONSE_ITEMS`) and `assertHostPage`, which refuses a non-positive or fractional page or limit and a limit above 50 as `BAD_USER_INPUT` ("limit must be at most 50"). The commits service now uses it, and it is applied in the services so GraphQL is covered. That includes the social followers, following and starred lists (`UserProfileService`), where the check sits outside the try, so a refusal is not swallowed into the empty upstream-failure page; ledger collaborators (`LedgerCollaboratorsWorkflow.listCollaborators`); and SSH public keys (`LedgerPublicKeyService.listPublicKeys`). The REST and MCP query schemas (`socialListQuery`, `collaboratorListQuery`, the public-key list query) now declare `int().min(1).max(50)`, regenerated into `docs/openapi/v1.json`, and `docs/mcp.md` gives the per-page maximum for collaborators, commits and social lists. REST reports these schema refusals as `VALIDATION_FAILED`, as it does every query bound. The activity feed's paging is w23/045. Tests: `host-page.test.ts`, `user-profile-service.test.ts` (all three social lists refuse 51 and page 0 before the host), `ledger-collaborators-workflow.test.ts` (51, page 0 and 2.5 refused before the authorization decision or the host), and `public-key-parity.test.ts` (REST 400 and GraphQL refusal for 51 with the host never called; 50 still 200).
