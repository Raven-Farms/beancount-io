# `addLedgerEntries` and `appendLedgerText` always return `entryHashes: []`, so an agent can't act on the entry it just wrote

**Severity:** minor. **Estimate:** 30–45 minutes. **Owner:** `backend-cluster/backend-v2`: `addLedgerEntries` in `src/features/ai-agent/api/mcp-tools.ts`, which hard-codes `entryHashes: []`, and `append-ledger-text-tool.ts:98`. **A1:** add → verify → fix is the core agent loop, and `getEntryContext`, `updateEntrySource` and `deleteEntrySource` all take the hash.

## Repro (production, 2026-10-22)

`addLedgerEntries` with one balanced transaction returns `ok`, "Added 1 entry to main.bean", `wrote: [{path: "main.bean"}]` and `entryHashes: []`. A committed `appendLedgerText` returns `wrote: [{path, line: 53}]` and `entryHashes: []`. To get the hash, the agent has to call `listLedgerEntries` with account, time and type filters and guess which row is new, which is ambiguous when identical entries exist.

The output schema says "Entry hashes the write created or touched, when known". The server knows them after the commit: it re-reads the ledger to bean-check (`validation.errorsAfter`) and can match the written spans, as `updateEntrySource` already does with `newEntryHash`.

## Fix

After the commit, map each written entry to its hash (by file and line from the projected ledger, or by computing the canonical hash of the written directive) and return them in request order, on REST and GraphQL as well if they expose the hashes. Tests: one hash per written entry; it resolves through `getEntryContext`; `deleteEntrySource` with that hash removes exactly that entry.

## Dedupe

w5/942 (open) covers the same gap for `importStagedBankTransactions`. Its claim that "other MCP write tools report the file and the hashes they wrote" holds for `wrote` but not for `entryHashes`, so both items should be fixed together.

---

**Resolved 2026-10-22** — `addLedgerEntries` and `appendLedgerText` now return one hash per committed entry, in request order. REST and GraphQL return the same `entryHashes`.

The hashes come from the ledger service, which resolves each written entry in the post-write ledger. That is the same full, correctly booked parse and provenance mapping that `updateSourceSlice` uses for `newEntryHash`, so pushtags, plugins and duplicates hash exactly as the journal, `getEntryContext`, `updateEntrySource` and `deleteEntrySource` see them.

**Ledger (`backend-cluster/ledger`):**
- `LedgerDataService.projectedEntryIds` resolves source ranges over the repository file map with overlays applied, sharing that projection with `checkProjectedErrors`.
- The resolver gained a batched `resolveEntryIdsAtSources`, which builds the ID map once per parse; `resolveEntryIdAtSource` delegates to it.
- The bulk-entries route records each row's line range as it builds the appended text. After the commit it answers `{entry_hashes}` instead of `null`.
- New `POST /reports/{o}/{r}/entry-ids` takes `{files, locations: [{path, line}]}` (at most 200 locations) and answers `entry_hashes` per location, `null` where no directive starts.
- The IDL (`EntryAddBulkEntriesResult`, `getProjectedEntryIds`) and the backend-v2 client are regenerated.

**backend-v2:**
- The entry writer returns the bulk route's hashes. An older ledger that answers `null` gives `[]`.
- `DirectiveAppendWorkflow` locates its `wrote` lines through the new `ILedgerRepoService.projectedEntryHashes`, gated like `checkProjectedFiles`.
- REST `POST …/entries` and `…/directives/text`, GraphQL `bulkEntries` and `appendLedgerText`, and both MCP tools carry `entryHashes`. `docs/mcp.md` and the OpenAPI snapshot are updated; both changes are additive.

Lookup after the commit is best-effort, as for `newEntryHash`. A failed lookup, or any entry left unresolved, returns `[]` rather than a partial list that would not say which hash is whose, and the write still stands. A dry run returns `[]`.

**Found on the way:** `insertDirectives` reported stale lines in two cases, and the lines are how the append path finds its hashes.
- A directive threaded in above one already placed did not move the earlier report down.
- A later directive's text carries its blank separator line, so its reported line was that blank line, not its header.

Both are fixed, so `wrote` is now correct for multi-directive text.

**Real-engine check (scratch script):** an appended copy of an existing entry resolved to the journal's second-occurrence ID (`…:1`); an out-of-order entry under a `pushtag` resolved with its tag; a balance resolved too. Every ID was one the journal serves for that directive.

**Tests:**
- Ledger:
  - batched resolver (request order, other files, occurrence suffixes);
  - `projectedEntryIds` (source-details parse over the projection; a projection without its entry point);
  - the bulk route (each entry located on its own non-overlapping lines; `[]` and the commit kept when the lookup throws or misses);
  - the new `entry-ids.test.ts` (line-to-range mapping and input refusals).
- backend-v2:
  - `structured-entry-parity` and `directive-text-parity`: the same hashes on REST, GraphQL and MCP; `[]` and no lookup on a dry run;
  - `directive-append-workflow`: locations equal `wrote` and point at the headers in the committed content; `[]` when the lookup throws or misses;
  - `directive-text`: the two line-report cases.
