# `addLedgerEntries` writes string meta values that look numeric or date-like unquoted: `"00123"` reads back as `123`, `"02134"` as `2134`, `"-0"` as `0`

**Severity:** moderate. Metadata is where agents put identifiers — invoice and check numbers, ZIP codes, external transaction IDs — and the API accepts only string meta values ("Transaction metadata accepts string-valued objects on all three surfaces", `docs/mcp.md`). The write reports success, but the stored value is a different type and loses its leading zeros, so later matching on the identifier fails. This is the hosted counterpart of the CLI fix w5/128. **Estimate:** 20–30 minutes with tests. **Owner:** `backend-cluster/ledger` — `renderMetadata` in `src/foundation/rustledger/journal-serialize.ts` (`NUMBER_LITERAL_RE` / `DATE_LITERAL_RE` unquoting), behind `POST /ledgers/{o}/{r}/entries` (REST `…/entries`, GraphQL, MCP `addLedgerEntries`, and `insertReceiptTransaction`, which writes through the same path). **A1.**

## Repro (production, 2026-10-21, OAuth `ledger.read ledger.write` token pinned to the disposable QA ledger; entry removed and `main.bean` restored to blob `729bd32`)

`addLedgerEntries` with one balanced transaction whose `meta` is `{"invoice":"00123","zip":"02134","ref":"1.50","due":"2026-01-31","neg":"-0"}` → `ok`, "Added 1 entry". The source slice reads:

```
2026-03-22 * "qa-20261021-meta" "meta probe"
  invoice: 00123
  zip: 02134
  ref: 1.50
  due: 2026-01-31
  neg: -0
```

`listLedgerEntries` returns `"invoice": "123"`, `"zip": "2134"`, `"neg": "0"`; `due` is now a date and `ref` a number.

## Cause

`renderMetadata` renders any string matching `^-?\d+(\.\d+)?$` or `^\d{4}-\d{2}-\d{2}$` without quotes. The comment explains why: rustledger's wire format stringifies number and date meta, so the *journal re-serializer* cannot tell `3` from `"3"` and guesses number. That guess is applied to `addLedgerEntries` input too, where the caller's value is known to be a string.

## Fix

Give the entries route its own rendering for caller-supplied meta: always quote string values (escape as today). Keep the number/date heuristic only for re-serializing parsed entries, or better, carry the original meta type from rustledger so neither path guesses. Optionally accept typed meta (`{"type":"number","value":"3"}`) later. Tests: `"00123"`, `"02134"`, `"-0"`, `"1.50"` and `"2026-01-31"` round-trip as the same strings through `addLedgerEntries` → `listLedgerEntries` on REST, GraphQL and MCP.

---

**Resolved 2026-10-22** — `directiveToText` (`backend-cluster/ledger/src/foundation/rustledger/journal-serialize.ts`) takes a new `literalStringMeta` option, threaded through `renderTransaction` and every `renderMetadata` call. `entryInputToText` (`entry-build.ts`), the renderer behind the bulk-entries route (REST `POST …/entries`, GraphQL, MCP `addLedgerEntries`, Plaid sync and `insertReceiptTransaction`), sets it, so a caller's meta values, which are strings by contract, are always quoted and escaped. `"00123"`, `"02134"`, `"1.50"`, `"2026-01-31"` and `"-0"` are written as quoted strings. The number/date heuristic stays only where it is needed: re-serializing parsed entries (plaintext export, journal text), whose wire values arrive stringified. A scratch run through the real engine read all five values back as the identical strings, with no errors. Tests: an `entry-build.test.ts` case asserts each value's quoted line. Reverting fails it. Gates: ledger typecheck, lint and 1619 tests. Shipped in the commit that moved this note (`backend-cluster/ledger`).
