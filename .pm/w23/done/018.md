# `appendLedgerText` accepts `option`, `plugin` and `include` lines as "directives", contrary to its contract

Found by MCP QA on 2026-10-20 against `https://beancount.io` (OAuth `ledger.read ledger.write` token pinned to the synthetic QA ledger; every call below is `dry_run: true`, so nothing was written).

**Repro:**

| `text` | Result |
| --- | --- |
| `option "operating_currency" "EUR"` | "Would add 1 directive to main.bean … No new bean-check errors"; diff appends the line at the end of `main.bean` |
| `plugin "beancount.plugins.auto_accounts"` | same |
| `include "other.bean"` | same, plus one new error (file not found) |
| `include "*.bean"` | one new error: include cycle |
| a comment only, or empty | `BAD_USER_INPUT` "text contains no Beancount directives" (control) |

`docs/mcp.md` § Writing directives as Beancount text says the tool "parses the text into directives and refuses anything that is not one". The REST twin `POST …/directives/text` and GraphQL `appendLedgerText` share the workflow.

**Why it matters (A1):** these lines aren't records. They reconfigure the whole ledger.

- An appended `operating_currency` changes the currency of every summary and report.
- `auto_accounts` switches off the open-account check that `appendLedgerText`'s own validation relies on.
- Both report "No new bean-check errors", so an agent, or a prompt-injected statement it is transcribing, changes ledger semantics with no signal.
- An appended `include` pulls in another file wholesale.

**Expected:** `option`, `plugin` and `include` are refused with `BAD_USER_INPUT`, naming the line and pointing at `updateLedgerFiles` for a deliberate configuration change. `pushtag`/`poptag` wrapped around entries can stay, since they only tag the entries inside them.

**Where:** the directive parser in `backend-cluster/backend-v2/src/features/ledger/workflow/directive-append-workflow.ts` (or the ledger service's text-append parser it calls) counts these statements as directives. Filter by kind before routing, and add a test per statement on all three surfaces. Owner: backend-v2, and possibly `backend-cluster/ledger`. Estimate: ~30m.

---

**Resolved 2026-10-20** — `parseDirectiveText` (`backend-cluster/backend-v2/src/features/ledger/utils/directive-text.ts`), shared by MCP `appendLedgerText`, REST `POST …/directives/text` and GraphQL `appendLedgerText`, now refuses `option`, `plugin` and `include` lines. The refusal is `BAD_USER_INPUT` naming the line ("line N: `option` configures the ledger and is not appended as an entry"), with field `text` and a hint pointing at `updateLedgerFiles` for a deliberate configuration change. It fires before any projection, bean-check or write, in preview and in commit mode. `pushtag`/`poptag` and `pushmeta`/`popmeta` are still accepted. `insertDirectives` still recognizes these statements in existing files, so routing and date-ordered insertion are unchanged. The unit test that asserted `option`/`include` were accepted, which pinned the bug, was replaced by a tag-stack acceptance case and one refusal case per keyword. `directive-text-parity.test.ts` adds each keyword on REST, GraphQL and MCP, previewed and committed, with zero checks or writes. Reverting fails 12 cases. `docs/mcp.md` § Writing directives documents the refusal. No prompt or customer skill appends configuration through this tool. Native gates pass: typecheck, lint/Knip, 370 suites / 6395 tests, OpenAPI generation without drift. Shipped in the commit that moved this note (`backend-cluster/backend-v2`).
