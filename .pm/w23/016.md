# Hosted BQL rejects `neg(inventory)` and `filter_currency(position, …)` that beanquery accepts, and returns empty `meta('lineno')`

Found by MCP QA on 2026-10-20 through differential testing: the same queries on the public `open_ledger/example` source, hosted `runBqlQueryStructured` versus local beanquery 0.2.0 / beancount 3.2.3 (`cli/.venv`). 53 of 60 queries across two batteries agreed. These differences reject or blank out what upstream answers:

| Query | beanquery | hosted (`@rustledger/wasm` 0.24.0) |
| --- | --- | --- |
| `SELECT account, neg(sum(position)) WHERE account ~ '^Income' GROUP BY account` | rows | `BAD_USER_INPUT` "type error: NEG expects a number or amount" |
| `SELECT account, sum(filter_currency(position, 'USD')) WHERE account ~ '^Assets' GROUP BY account` | rows | "type error: FILTER_CURRENCY expects (inventory, string)" |
| `SELECT meta('lineno') LIMIT 1` | `80` | `""` |
| `SELECT entry_meta('filename') LIMIT 1` | the source path | `""` (blanking a server path is reasonable; `lineno` has no such reason) |

`runBqlQuery`'s description points agents at the upstream BQL reference, and these are documented upstream forms. An agent that sign-flips an income inventory with `neg()`, a common step for presenting income as positive, gets a type error and no hint about the supported spelling.

**Expected:** documented beanquery forms work, or the refusal names the hosted engine's supported alternative (for income, `neg()` per amount or `-sum(number)` grouped by currency). `meta('lineno')` returns the posting's line, matching `listLedgerEntries`, which already reports `meta.lineno`.

**Fix:** report the two signature gaps and the missing `lineno` metadata to `rustledger/rustledger` with these reproducers, and bump when fixed. Don't reimplement BQL here (`.pm/DO_NOT_DO.md`). Meanwhile, in `backend-cluster/ledger`, map these engine type errors to a hint naming the working alternative, and add the reproducers to `verify:rustledger`. Owner: `backend-cluster/ledger`, plus an upstream report. Estimate: ~30m here; the upstream fix isn't in this repo's control.
