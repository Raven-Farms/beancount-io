# MCP `updateLedgerFiles` whole-file `content` (and `deleteLedgerFiles`) has no base version, so it silently overwrites commits made since the agent read the file

**Severity:** major. Another writer's committed change is silently lost on a reported-clean write. **Estimate:** 45–60 minutes including tests. **Owner:** `backend-cluster/backend-v2`, in `src/features/ai-agent/tools/edit-ledger-files-tool.ts` and the `readLedgerFiles` output (`read-ledger-files-tool.ts`). This is a parity gap: REST `PUT`/`DELETE …/files/{path}` require the blob `sha` and refuse a stale one. **A1:** agents work alongside the dashboard, the mobile app and other agents. The usual pattern is read the file, rewrite it, then `updateLedgerFiles` with `content`, and it drops whatever landed in between.

## Repro (production, 2026-10-21, disposable QA ledger, `qa-` file deleted afterwards)

1. Agent A: `readLedgerFiles qa-lost.bean` → `"; v1 line a\n; v1 line b\n"`. The result carries no `sha`.
2. Writer B: REST `PUT …/files/qa-lost.bean` with the current `sha` appends `; B added this line` → 200.
3. Agent A: `updateLedgerFiles {files: [{path: "qa-lost.bean", content: <v1 with "line a" → "line A-edited">}]}` → `ok`, "Committed 1 change(s) … No new bean-check errors."
4. The file is now `"; v1 line A-edited\n; v1 line b\n"`. B's committed line is gone, and neither writer is told.

`old_string` edits are implicitly guarded: the old text must still match. `content` replace and `delete` are not.

## Cause

`prepare()` fetches the file's **current** sha just before committing and attaches it to the `update`/`delete` operation. The concurrency check therefore compares against a version the tool read milliseconds earlier, not the one the agent based its rewrite on. The internal retry on `ConflictError` deliberately excludes `replace` and `delete` ("would silently overwrite or drop the change that won"), but the base it guards is the tool's own read, not the caller's.

## Fix

Return each file's blob `sha` from `readLedgerFiles` (and the `files/{+path}` resource). Accept an optional `sha` on `updateLedgerFiles` `content` items and on `deleteLedgerFiles` items, and send it as the operation's sha instead of the freshly fetched one. A mismatch is refused with `CONFLICT` "`<path>` changed since you read it; re-read and retry", which needs w23/032's 409 mapping. In the tool descriptions and `docs/mcp.md`, say that a `content` rewrite without `sha` overwrites concurrent changes. Consider requiring `sha` for `content` and `delete` the way REST does, with a one-release deprecation.

Tests:
- A stale `sha` is refused and the file is unchanged.
- The current `sha` commits.
- An omitted `sha` keeps today's behavior, if it stays optional.
- `readLedgerFiles` returns `sha`.

## Dedupe

Searched `.pm/**` for lost update, clobber, and a base sha with MCP or `updateLedgerFiles`. w4/045 (done, dashboard Edit Transaction) and w3/434 (done, CLI format) are the same hazard on other surfaces. w23/017 is two concurrent edits racing inside the server. This is the caller's base version never reaching the server.
