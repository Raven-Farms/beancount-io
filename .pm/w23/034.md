# backend-v2 counts an existing bean-check error as new once a write shifts its line, so `appendLedgerText` refuses valid text

**Severity:** major. A clean, valid append is refused, and every MCP write misreports new errors on any ledger that already has an error below the insertion point. **Estimate:** 20–30 minutes including tests. **Owner:** `backend-cluster/backend-v2`, in `src/features/ledger/utils/bean-check-errors.ts` (`diffBeanCheckErrors`).

Callers:
- `directive-append-workflow.ts`, the `appendLedgerText` / append refusal on REST, GraphQL and MCP
- `write-validation.ts`, the post-write `validation` on every MCP write tool
- `edit-ledger-files-tool.ts` dry runs
- `bank-import-tool.ts`

**A1:** real ledgers carry a stale error or two (a missing document, an old balance), and the agent is then told its own valid write broke the ledger.

## Repro (production, 2026-10-21, disposable QA ledger, OAuth `ledger.read ledger.write` token)

The ledger has one existing error: `checkLedger` → `Document file not found: <file> (main.bean:93)`.

1. `appendLedgerText` with a balanced transaction dated before line 93, using accounts that carry no balance assertion, and `dry_run: true`. The result is "1 new bean-check error: Document file not found … (main.bean:97)", with `validation: {errorsBefore: 1, errorsAfter: 1, newErrors: [that error]}`.
2. The same call without `dry_run` is refused: `VALIDATION_FAILED` "appending it would introduce 1 new bean-check error: Document file not found … (main.bean:97)". HEAD is unchanged.

The "new" error is the existing one, moved down 4 lines by the insertion.

## Cause

`diffBeanCheckErrors` matches `before` against `after` on `message` **and** `source` (`file:line`). The ledger service fixed the same comparison in w21/m1 (`backend-cluster/ledger/src/features/ledger/utils/new-ledger-errors.ts` `newLedgerErrors`): it matches by message and file, ignores the line, and lets each `before` error excuse one `after` error. backend-v2's copy was never aligned.

## Fix

Port `newLedgerErrors`' rule: key on message plus filename, with multiset counting. Better still, expose one shared implementation's result, so the two services can't drift again. Tests:
- An error below an insertion is not new.
- A second copy of a known message is new.
- The same message in another file is new.
- `appendLedgerText` commits in the repro.
- `validation.newErrors` is empty for an `updateLedgerFiles` that only shifts lines.

Acceptance: step 2 commits, and the dry run reports `newErrors: []`.
