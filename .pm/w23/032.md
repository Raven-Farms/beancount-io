# A stale `sha` or a create over an existing file returns `400 BAD_USER_INPUT`, not the documented `409 CONFLICT`

**Severity:** minor. These are wrong-but-readable errors that break conflict handling. **Estimate:** 20–30 minutes including tests. **Owner:** `backend-cluster/ledger`, in `src/server/error-middleware.ts` (`toErrorResponse`'s Gitea branch). One change fixes REST, GraphQL and MCP together. **A1:** a client that handles `CONFLICT` by re-reading and retrying (documented for REST `PUT`, and done internally by MCP `updateLedgerFiles`) treats a lost race as its own bad input and gives up.

## Repro (production, 2026-10-21, QA session cookie and OAuth token, disposable QA ledger)

| Call | Result | Expected |
| --- | --- | --- |
| REST `PUT …/files/qa.bean` with the `sha` of the previous version (file changed since) | **400** `BAD_USER_INPUT` "sha does not match [given: …, expected: …]" | **409** `CONFLICT`; the route's OpenAPI lists 409 |
| REST `DELETE …/files/qa.bean` with a stale `sha` | **400** `BAD_USER_INPUT`, same message | 409 |
| REST `PUT` without `sha` on an existing file | **400** "repository file already exists" | 409 |
| MCP `createLedgerFiles` over an existing path, committed | `BAD_USER_INPUT` "commit failed: repository file already exists", hint "Fix the named argument" | `CONFLICT`, as its own dry run answers ("main.bean already exists", hint: use `replace`) |

## Cause

Gitea answers these with HTTP 422 and a message that `isGiteaWriteConflict` already recognizes (`/sha does not match|already exists?|not up to date/`). The ledger's error middleware applies that classifier only to `status >= 500`, the lost-ref race w23/017 added. A 422 is forwarded as-is, and backend-v2 maps a forwarded 4xx to `BAD_USER_INPUT`. So the raw write routes (`change-files`, file update and delete) never return 409 for the conflicts the classifier was written for. `commitLedgerFiles` does catch them through its own retry loop. MCP `updateLedgerFiles` retries only on `ConflictError`, so a 422 race on `replace` or `delete` gets no retry and no conflict code.

## Fix

In `toErrorResponse`, answer every `isGiteaWriteConflict(err)`, not only 5xx, with 409. Give "already exists" its own message ("`<path>` already exists; update it with its sha, or choose another path") and keep "the ledger changed under a concurrent write; re-read it and retry" for sha mismatches. Tests: the middleware maps 422 "sha does not match" and 422 "repository file already exists" to 409, and a 422 with any other message stays 4xx. Add a backend-v2 parity case asserting `CONFLICT` for a stale-`sha` REST `PUT` and for an MCP create over an existing file.

Acceptance: the Expected column holds.
