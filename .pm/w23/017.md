# Two concurrent file writes: the loser gets `SERVICE_UNAVAILABLE` "dependency is down" instead of a retry or `CONFLICT`

Found by MCP QA on 2026-10-20 against `https://beancount.io` (OAuth `ledger.read ledger.write` token pinned to the synthetic QA ledger). It first appeared organically: another QA session committed to the same ledger while one of my `updateLedgerFiles` calls was in flight. I then reproduced it deliberately on a scratch file I created and deleted afterwards.

**Repro:** create `qa-…-race.bean` with `"; a\n; b\n"`, then fire two `updateLedgerFiles` calls at the same moment. They edit different lines, `{old_string:"; a\n", new_string:"; 0\n"}` and `{old_string:"; b\n", new_string:"; 1\n"}`.

| Round | Winner | Loser's result |
| --- | --- | --- |
| 1 | edit 0 (3.1s) | `SERVICE_UNAVAILABLE` "commit failed: Ledger API is temporarily unavailable"; hint "A dependency is down. Retry with backoff; this is not a problem with the request." |
| 2 | edit 1 | same |
| 3 | edit 0 | same |

No data was lost: the file holds exactly the winner's edit.

**Expected:** `commitLedgerFiles` already promises the right behavior (`backend-cluster/ledger/src/features/ledger/operations/commit-ledger-files.ts:143-235`). On a lost compare-and-swap it re-reads, re-applies the exact-text edit and commits again. Since these edits touch different lines, both should land. Only after `MAX` attempts should it answer `CONFLICT` "the ledger changed under a concurrent write; please retry". Agents running in parallel, or an agent alongside the dashboard, hit this in normal use.

**Probable cause (unverified; the host's status is only in the server log):** `isGiteaWriteConflict` (`backend-cluster/ledger/src/features/gitea/utils/gitea-error.ts:45-50`) treats only `409`, or `422` matching `/sha does not match|already exists?|not up to date/`, as a lost race. The production repository host evidently answers the losing `repoChangeFiles` with something else, likely a `5xx` from a ref-lock failure. The error then goes through `giteaWriteErrorFromCause` unretried, and backend-v2's `error-to-domain.ts:136-142` maps the `5xx` to `ServiceUnavailableError("Ledger API")`.

**Fix:**

1. Read the ledger service log line `commit ledger files` for one reproduction and note the host's status and message.
2. Add that signature (for example a `500` with "could not lock"/"failed to update ref"/"cannot lock ref") to `isGiteaWriteConflict`.
3. Add a test where the first `repoChangeFiles` rejects with that error and the retry succeeds.

Check the other writers that share `isGiteaWriteConflict` (source-slice update/delete, rename) for the same gap. Owner: `backend-cluster/ledger`. Estimate: ~45m, given log access.
