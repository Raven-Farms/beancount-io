# Ledger search accepts `order=sideways`, `limit=0` and negative ids silently, unlike its sibling catalog reads

Found by MCP QA on 2026-10-20 against `https://beancount.io` (OAuth `ledger.read`, account-wide). MCP `beancount://catalog/ledgers/search{?…}` and REST `GET /api-gateway/v1/ledgers/search` agree:

| Query | Result |
| --- | --- |
| `q=example&sort=bogus` / `mode=bogus` / `private=maybe` | `BAD_USER_INPUT` (controls) |
| `q=example&order=sideways` | `200`, default order |
| `q=example&limit=0` | `200`, every match (the cap is ignored) |
| `q=example&limit=1000` | `200` |
| `q=example&starredBy=-5` | `200`, filter ignored |

Every other list in the API bounds `limit` to `1..100` (`listLedgers`, `catalog/ledgers`, `catalog/ledgers/owned`) and refuses bad enums. An agent that typos `order=dsc` gets the default ordering with no signal.

**Root cause:** `backend-cluster/backend-v2/src/features/ledger/api/rest/v1/catalog-reads.ts:7-25`. `searchQuery` builds `page`, `limit`, `uid`, `priorityOwnerId`, `teamId` and `starredBy` from unbounded `z.coerce.number()`, and `order` from a free `z.string()`. `sort` and `mode` are only checked downstream. The MCP resource uses the same schema, and GraphQL `searchLedgers` takes the same args.

**Fix:**

- Start `searchQuery` from the shared `paginationSchema` (`page ≥ 1`, `1 ≤ limit ≤ 100`).
- Make `order` `z.enum(["asc","desc"])`, and `sort`/`mode` enums of the values the workflow accepts.
- Make the id filters positive integers.
- Mirror those constraints on GraphQL's args.
- Add one parity test for a bad `order` and `limit=0` on all three surfaces.

Owner: backend-v2. Estimate: ~25m.
