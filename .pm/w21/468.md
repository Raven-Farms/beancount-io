# Saving a file that was deleted elsewhere answers SERVICE_UNAVAILABLE ("Ledger API is temporarily unavailable"), not NOT_FOUND, so w21/378's "File Deleted" path never fires

**Severity:** moderate. The user is told to "try again in a moment", which can never succeed, and the draft's way out (Save as New File) is never offered. **Estimate:** 30 minutes. Owner: backend-v2 / ledger (with REST, GraphQL and MCP parity). A3: w21/378's fix keys on NOT_FOUND (`isLedgerGone`), assuming Gitea's 404 maps to `NotFoundError`. In production, `updateLedgerFile` on a path that no longer exists returns `SERVICE_UNAVAILABLE` / "Ledger API is temporarily unavailable" (`extensions.service: "Ledger API"`), so the app falls through to the generic hint.

Reproduced on production at `main` `c039662e6`:
- **API:** `createLedgerFile` made `qa-378.txt` on the disposable ledger, and `deleteLedgerFile` removed it. `updateLedgerFile(path: "qa-378.txt", sha: <the deleted sha>)` then returned `{"code":"SERVICE_UNAVAILABLE","service":"Ledger API"}`.
- **Native (iPhone 17e, fresh Metro at `eaa69d760`):** with the file open and edited, I deleted it through the API and tapped Save. The alert read "Failed to save — Your text is still here. Try again in a moment.", with no File Deleted dialog and no Save as New File. The draft was discarded, and the file no longer exists.

## Fix

Make an update to a missing path answer NOT_FOUND (for example, when Gitea refuses the update, check whether the path still exists before mapping the error to 5xx), identically on REST, GraphQL and MCP. As a fallback, the client could re-read the path after a 5xx on save and treat a missing file as gone.

**Acceptance:** the steps above show w21/378's File Deleted dialog, and the API returns NOT_FOUND for that update on all three surfaces.
