# A connection that drops mid-save is reported as "Nothing was saved" or "Failed to save", so a retry commits the entry twice

**Severity:** moderate (duplicate writes). **Estimate:** 45 minutes. Owner: mobile, plus backend-v2 if a request ID is added. A3: when a connection drops after the request is sent, the client sees the same `TypeError("Network request failed")` as when it is offline. `ledgerWriteFailureMessage` (`mobile/src/common/ledger-refusal.ts:85`) maps any transport failure to `ledgerWriteOffline` ("You're offline. Nothing was saved."). Budget save and delete, Open Account and the file browser use that copy. `runLedgerWrite` (`ledger-write.ts:101-110`) toasts `saveFailed` and skips the post-write refresh, so New Transaction says "Failed to save" and the screens behind it never show the entry that actually committed. `addEntries` and `bulkEntries` have no idempotency key (`createLedger` has one), so the natural retry writes the transaction or budget a second time.

Code-level at `main` `7280ccceb`. The reviewer ran both functions under `tsx` with that error. Not run natively, because it needs a connection to drop mid-request.

## Fix

Treat a transport failure on a write as unconfirmed, not as nothing saved. Refetch the affected data before offering a retry, and word the copy as "We couldn't confirm the save". Better, add a client request ID to `addEntries` and `bulkEntries`, as `createLedger` has, on REST, GraphQL and MCP for parity.

**Acceptance:** a write whose response is lost never claims "Nothing was saved", and retrying it does not create a duplicate.

## Dedupe

w21/327 covers only 5xx responses, and its acceptance keeps network failures on the offline copy. w21/044, w21/193 and w21/197 are double taps. Searched `.pm/**` for ledgerWriteOffline, isTransportFailure, "Nothing was saved", idempot, duplicate and twice.
