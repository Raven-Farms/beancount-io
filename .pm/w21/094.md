# A transaction detail screen lower in the stack keeps showing an entry that was deleted or rewritten elsewhere, with Edit and Delete that then fail

**Severity:** moderate. After a delete, Back lands on a detail screen for a transaction that no longer exists, which still looks valid and editable. **Estimate:** 1–2 hours. Owner: mobile. A3: the detail screen renders from the stashed list entry plus `getLedgerEntryContext`. That query is deliberately never evicted by `invalidateLedgerData`, so a detail left mounted under a later change never learns its entry is gone. w21/013's "not found" handling therefore never fires.

Reproduced natively on the iPhone 17e simulator (iOS 27.0) at `main` `162bce75a`, on the disposable QA ledger, which I restored byte-for-byte to `f1a0b83c`. The fixture `; qa-20261020-del` was `2026-08-30 * "QA STALEDEL" "probe"` with 0.00 USD postings to Expenses:Transport and Assets:Cash.
1. Home → QA STALEDEL (detail A).
2. Money flow → Expenses:Transport (account journal) → QA STALEDEL again (detail B).
3. On B: ⋯ → Delete → Delete. The app returns to Transport, whose journal correctly no longer lists the entry.
4. Back: detail A still shows **QA STALEDEL · $0.00 · probe · Aug 30, 2026**, with Money flow, Entry Context `main.bean:90`, and Edit and ⋯ enabled.
5. Edit (pencil): **"Failed to load transaction"** on a blank Edit Transaction sheet.

The reviewer traced the same staleness after fixing an entry through its "Open in the file editor" banner (w21/030). The edit changes the hash and the banner clears because errors refetch, but the hero and postings keep the old amounts, and Edit or Delete then fail. Not exercised natively, because the editor needs free-text typing.

## Root cause

- `mobile/src/common/apollo/invalidate-ledger.ts:89-91` deliberately leaves `getLedgerEntryContext` out of the eviction lists. Its comment says evicting after a *delete* would send "the still-mounted detail screen back for an entry that no longer exists". That assumes the deleting screen is the only mounted one.
- `mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx:322-325` runs the context query under the global `nextFetchPolicy: "cache-first"`, and `:380-385` falls back to the stash. Neither re-checks when the screen regains focus.
- `mobile/src/screens/ledger-file-editor-screen/index.tsx:448` file-scope invalidation refreshes lists, but not a mounted detail.

## Fix

On focus (`useFocusEffect`), have the detail screen refetch its own `getLedgerEntryContext` with `network-only` when the ledger has changed since it last loaded. Use a ledger-mutation counter or sha bumped by `invalidateLedgerData`. On NOT_FOUND, show w21/013's "This transaction no longer exists" state, or pop back. Keep the deleting screen's own path as it is, since it already leaves.

**Acceptance:**
- In the steps above, Back from Transport shows the not-found state, or returns to the list, instead of the deleted entry.
- After an editor fix, the detail shows the new amounts, or the not-found state if the hash changed.
- A detail whose entry didn't change does no extra network round trip on focus beyond the counter check.

## Dedupe

w21/013 added the not-found state (reached only on a cold load). w21/028, 030 and 048 cover the editor round trip without a second, still-mounted detail. Searched `.pm/**` for getLedgerEntryContext, openErrorInEditor, dismissTo and "still mounted".
