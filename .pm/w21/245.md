# Explore search finds nothing for "crypto example" or an owner name: the query goes to Gitea as one substring

**Severity:** minor-to-moderate. Explore is how people find public example ledgers, and its own comment says switching to it "widens" a search. **Estimate:** 45 minutes. Owner: ledger (backend), for REST, GraphQL and MCP parity. A3: Explore sends the typed text unchanged as `q`, and the ledger service passes it straight to Gitea's repo search. That search matches a substring of the name or description, so spaces never match the hyphenated names, and an owner matches only in the `owner/` form.

Verified against production through GraphQL `searchLedgers(q, isPrivate: false, includeDesc: true)` on 2026-10-21:

| q | results |
|---|---|
| `crypto` | 1 (open_ledger/crypto-example) |
| `crypto-example` | 1 |
| `crypto example` | **0** |
| `open_ledger/` | 50 (page full) |
| `open_ledger` | **1** (open_ledger/kroger, a description match) |
| `example` / `EXAMPLE` | 4 / 4 |

## Root cause

- `mobile/src/screens/ledger-selection/use-discovery.ts` sends `q` verbatim.
- `backend-cluster/ledger/src/api/ledgers.ts:194-215` forwards `q` to Gitea's repo search unchanged.

## Fix

In the ledger service, so every surface benefits:
- Split the query on whitespace and match every term against `owner/name` and the description (or send Gitea's comma-separated keywords and intersect the results).
- When a term matches an owner exactly, include that owner's public ledgers (look up `uid`).
- Mobile then needs no change. Add parity tests across REST, GraphQL and MCP.

**Acceptance:** `crypto example` finds `open_ledger/crypto-example`, and `open_ledger` lists that owner's public ledgers, on all three surfaces.
