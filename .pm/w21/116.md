# A "load more" page that arrives after the filter or ledger changed is appended to the new list, along with its total

**Severity:** moderate, but timing-dependent. Rows that don't match the new filter, or rows from another ledger, appear under it. Tapping a cross-ledger row opens "not found". If the new list's own fetch already landed, the leak stays until pull-to-refresh. **Estimate:** 45 minutes. Owner: mobile. A3: `loadMore` requests page N+1 with the old variables, but Apollo applies `updateQuery` to whatever the query's variables are when the response arrives. Normal query results for outdated variables are dropped; the fetchMore path has no such check.

Code-level at `main` `650ce6f72`, against Apollo 3.14.1 (`node_modules/@apollo/client/core/ObservableQuery.js:411-424`). Not exercised natively: it needs a slow network (Network Link Conditioner, about 2.5 s delay) and a filter change during "Loading more…".

## Scenario

1. With 27 transactions (page size 20), scroll to the bottom until "Loading more…" appears.
2. Within about 2 s, apply Filters → Account `Income:Salary` (3 rows).
3. The salary list then shows the 7 older Transport rides beneath the 3 salary rows, and its `total` and "No more entries" state come from the unfiltered query.

The same happens if a ledger switch lands during load-more. `mergeJournalPage` only refetches when the leaked page overlaps rows already shown.

## Root cause

- `mobile/src/screens/transactions-screen/transactions-screen.tsx:165-214`: `loadMore` uses `fetchMore` + `updateQuery` without checking that the variables it requested still match the query's current variables.
- The merchant detail screen (`merchant-detail-screen.tsx:362`) uses the same pattern.

## Fix

Capture the request's variables (or a filter and ledger generation counter) when `loadMore` starts. In `updateQuery`, return `prev` unchanged when they no longer match the current variables, or abort in-flight fetchMore calls on a variables change.

**Acceptance:** a unit test drives `updateQuery` with stale variables and expects `prev` unchanged. With a 2.5 s delay, the scenario shows only the 3 salary rows.
