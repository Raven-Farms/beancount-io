# Mixed-currency entries get the wrong headline amount: a $500 card purchase that earns miles shows "+1,500.00 MILES" in green, and one currency exchange flips sign depending on which leg carries the `@`

**Severity:** major (a debit reads as income). **Estimate:** 45–60 minutes. Owner: mobile. A2: the row amount and the detail hero are the first thing a reader sees. For entries with two currencies and no cost or price on the money side, mobile picks the currency bucket by comparing raw magnitudes across currencies (1500 miles > 500 dollars). For an exchange it picks whichever currency the `@` is *quoted in*. Both are arbitrary, so the same purchase can read as income, and the same exchange reads as an inflow or an outflow depending on how it was typed.

Environment: `main` at `63fed78a8`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0). QA account, synthetic disposable ledger `mcp-agent-eval` (restored byte-for-byte afterwards; `getLedgerErrors` stayed empty).

## Repro (observed, Home → Recent Transactions; the detail hero matches)

| entry | shows | expected |
| --- | --- | --- |
| `Liabilities:CreditCard:Visa -500.00 USD`, `Expenses:Transport 500.00 USD`, `Assets:…:Miles 1500 MILES`, `Income:…:Rewards -1500 MILES` | **+1,500.00 MILES**, green, income icon | **−$500.00** (the purchase); miles are a side benefit |
| "FX A": `Assets:Bank:Checking -100.00 USD @ 150 JPY`, `Assets:…:Jpy 15000 JPY` | **+15,000.00 JPY**, green | one consistent, neutral transfer amount |
| "FX B" (same exchange): `Assets:…:Jpy 15000 JPY @@ 100.00 USD`, `Assets:Bank:Checking -100.00 USD` | **−$100.00** | same as FX A |

The miles row also prints "1,500.00" with two decimals for an integer commodity.

## Root cause

`mobile/src/screens/transactions-screen/utils/transaction-display-utils.ts`, `selectTransactionAmount` (around lines 99-175):

- With several currency buckets on Assets/Liabilities postings and no posting quoting a cost or price, it takes the bucket with the largest `Math.abs(value)`, comparing numbers in different units (`:155-158`).
- "Money currency" means the currency some posting's price is quoted in (`moneyCurrencyOf`). For an exchange, that is whichever leg the user annotated. The chosen bucket belongs to one account, so the `mixed` guard (`accounts.size > 1`) never fires.

## Fix

Choose the headline bucket by meaning, not magnitude:

1. Prefer the ledger's operating currency, or the first `operating_currency`, when a bucket exists in it.
2. Treat a two-bucket entry whose buckets each net out against *other* Assets/Liabilities legs (an exchange between own accounts) as a transfer. Show it unsigned and neutral, like the existing same-currency transfer rule, using the operating-currency leg's size.
3. Only then fall back to the existing price/cost heuristic.

Format integer commodities at their recorded scale. Keep the `mixed` result for genuinely split trades.

**Acceptance:** the airline row reads −$500.00, and FX A and FX B read the same neutral $100.00 (or the same JPY figure, consistently). Stock trades with `{cost}` keep their current cash-side amount. Unit tests cover the three entries above plus a cost-basis buy and sell.

**Resolved 2026-10-21** — Shipped in the commit that moved this note (`mobile`). `selectTransactionAmount` now picks among currency buckets by meaning, not by magnitude:
- A trade, where a posting holds `{cost}`, keeps its cash side. That includes the existing mixed summary.
- An exchange between own accounts, where every posting is on the balance sheet and none has a cost, reads unsigned and neutral. Its operating-currency leg sizes it, or the alphabetically first currency when there is no operating currency. FX A and FX B therefore read the same $100.00.
- Any other entry shows the operating currency, then an Expenses posting's currency, then the old price and magnitude rule. The airline row reads −$500.00.

The rows and the detail hero get the operating currency from a new `useOperatingCurrency` hook. It reads the `LedgerGuard`'s cached `ledgerReadContext` (`cache-only`), so rows add no requests.

Tests in `transaction-display-utils.test.ts` cover the airline entry, FX A and FX B, and a cost-basis buy and sell. Without the fix they fail, except the trade cases, which pass both ways.

Deviation: whole-unit commodities still pad to two decimals. Letting commodity codes that are not three letters keep their recorded scale also turned the account journal's "0.00 MRMB" running balances into "0 MRMB". That would regress money-like commodities, so it was left out.

Not checked on the simulator.
