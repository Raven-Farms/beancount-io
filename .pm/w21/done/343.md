# A text file over 10 MiB still comes back as content: null on REST, GraphQL and MCP, so non-mobile clients can open it empty and overwrite it (w21/185 server half)

**Severity:** moderate. A save from any client that trusts the empty content replaces the whole file. **Estimate:** 45 minutes. Owner: ledger + backend-v2. A3: w21/185 guarded only the mobile editor. Its resolution states that the ledger service's plain file read and GraphQL still pass `content: null` for large blobs, so the dashboard and API clients get an empty document with a valid sha.

Code-level at `main` `ce639fcd9`, from w21/185's resolution. Not reproduced: it needs an 11 MB file.

## Fix

Either fetch large blobs through the raw endpoint so `content` is always populated, or return an explicit `tooLarge: true` (with no sha usable for writes) on REST, GraphQL and MCP, with parity tests. Then have the dashboard editor show a read-only notice, as mobile now does.

**Acceptance:** a request for an 11 MB file on all three surfaces either returns its content or flags it as too large, and a write based on an empty read is refused.

## Dedupe

This is a follow-up to w21/185 (done). w21/186 and w21/227 are other large-file issues. Searched `.pm/**` for "content: null", isUnreadableLargeFile and "10 MiB".

Fixed in the ledger service, the one place all three surfaces read through (backend-v2's REST, GraphQL and MCP file reads call the ledger service's `getLedgerFile` / `getLedgerFilesContent` and map the result, so none needed a change). A file past Gitea's inline limit used to come back with `content: null` and a valid sha, which clients read as an empty document. `withLargeContent` (`api/files.ts`) now fetches such a file (type file, no content, size above 0) through the raw endpoint and returns it in the usual base64 form, on both the single-file read and the batch `files-content` read; the raw fetch is the existing helper, split out of `readGiteaFileText` as `readGiteaRawBuffer` so the byte cap is enforced while streaming. Past 32 MiB the read fails with the existing size-limit error instead of returning null, so there is no empty read to write over. An inline file, an empty file and a directory are untouched. Tests (`api/__tests__/files-large.test.ts`): fills from the raw body, leaves the three untouched cases alone, refuses past the cap; the ledger suite, typecheck, lint and build are green.

Deviations: no `tooLarge` flag was added, since returning the content meets the acceptance without a contract change. Mobile's `isUnreadableLargeFile` guard (w21/185) stays as the fallback for an older server. Not exercised against a real 11 MB file or a deployed server; the mobile editor now opens such a file (up to 32 MiB) as editable text once the ledger service is deployed. The dashboard's read-only notice was not added, as the dashboard now receives the content.
