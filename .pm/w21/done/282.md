# Android: a HEIC photo from the library always fails with "Could not read receipt", though the picker already re-encoded it to JPEG

**Severity:** moderate on Android. Samsung's "High efficiency pictures" and iPhone photos synced to Google Photos are common. **Estimate:** 15 minutes. Owner: mobile. A3: w21/108's fix is iOS-only. On Android, `quality: 0.85` makes expo-image-picker re-encode the photo into a `.jpeg` cache file but still report the original `mimeType: "image/heic"` and `.heic` name. The app trusts those, uploads with `Content-Type: image/heic`, and the server (since w21/108) refuses the parse.

Code-level at `main` `c612cae39`. `shotFromLibraryResult({ assets: [{ uri: ".../ImagePicker/3f2a.jpeg", mimeType: "image/heic", fileName: "20261021_101500.heic" }] })` returns `mimeType: "image/heic"`. See `node_modules/expo-image-picker/android/.../MediaHandler.kt:50-75`.

## Root cause

`mobile/src/common/receipt-utils.ts:96, 100` (`shotFromLibraryResult`), and `use-receipt-workflow.ts:55, 69`.

## Fix

Take the type and extension from the returned file's URI extension (`.jpeg`/`.jpg` → `image/jpeg`, `.png` → `image/png`), falling back to `asset.mimeType` only when the extension says nothing. Add a unit case for the Android shape.

**Acceptance:** the shape above yields `image/jpeg` and a `.jpeg` name.

## Dedupe

The note's Android shape (`…/3f2a.jpeg` reported as `image/heic` / `20261021_101500.heic`) now yields `image/jpeg` and `20261021_101500.jpeg`; a name that already matches the file's type is kept verbatim.
