# New Transaction shows a would-break refusal only in a 2-second toast

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A2: w0/m2 made the server refuse a new entry that would break the ledger and explain why. Open Account, Add Budget and Edit Transaction keep that explanation on screen. New Transaction is the most-used write form, and it shows the explanation for two seconds, then drops it.

Environment: `main` at `ab6f2adf7`, native development build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0), light, English. Signed in as the QA account against `https://beancount.io`, on the synthetic disposable ledger `mcp-agent-eval`. That ledger has `2026-08-29 balance Assets:Cash 49.75 USD`.

## Repro

1. Home → **+** → **Enter new transaction**.
2. Set the date to **2026-08-25** and the payee to `qa-20261020-break`. Choose **Assets:Cash** as the first posting and enter `-5.00`. The second posting (Expenses:Food:Groceries) balances automatically.
3. Tap **Done**.

A "Saving…" toast appears, then an error toast reads:

> This would add an error to your ledger: Balance failed for Assets:Cash: expected 49.75 USD, got 44.75 USD (main.bean:87)

Back-to-back screenshots showed that toast for about 2 seconds (14:26:14 to 14:26:16). After that the form returns unchanged, with nothing to say why the save failed. The ledger file's sha did not change, so the refusal itself is correct. Reproduced three times. In two of those runs, screenshots taken one second apart never caught the toast at all.

## Expected / actual

- **Expected:** the form stays open and shows the refusal **inline** until the user changes the draft or saves again. That is step 2 of w0/m2/t003 ("Show the named error inline; never close the form or toast success on a refusal"). The Edit Transaction screen already does it with `saveError`.
- **Actual:** the only copy is a toast. It disappears after `DEFAULT_TOAST_DURATION` (2000 ms), whatever the message length; this one is 26 words. It can't be held or reopened, because the toast layer is `pointerEvents: "none"`.

## Root cause

- `mobile/src/screens/multi-postings-transaction/multi-postings-transaction-screen.tsx:541-562` (`handleSave`) ignores `outcome.message` when `outcome.ok` is false. The only feedback is the toast that `runLedgerWrite` → `fail()` shows (`mobile/src/common/ledger-write.ts:120-128`).
- `mobile/src/common/providers/toast-provider/toast-queue.ts:12-16`: every toast without an explicit duration lasts 2000 ms.
- Control: `mobile/src/screens/edit-transaction-screen/edit-transaction-screen.tsx:288,469` keeps `outcome.message` in state and renders it as `errorText`.

## Fix

In `handleSave`, when `outcome.ok` is false, store `outcome.message` and render it inline under the Remainder row, styled like Edit Transaction's `errorText`. Clear it when the date, payee, narration or any posting changes. Keep the toast and haptic. Optionally, give error toasts a reading-time duration (for example 2 s plus about 60 ms per character, capped near 8 s). That way the transaction-detail delete and other toast-only failures stay readable too.

**Acceptance:** repeating the repro shows the refusal text under the postings until you edit the draft, and nothing is committed. A generic failure (offline) shows its message inline the same way. A unit or component test covers a refused `addEntries` and asserts the inline message.

## Dedupe

Searched `.pm/**` (including `done/`) for toast duration, dwell, refusal and would-break. w0/m2 (done) delivered the refusal and its toast; this is the inline half of its t003 that New Transaction missed. w4/029 (done) was about toasts never appearing, not their duration. No open item covers this.

## Not verified

Android, dark mode, VoiceOver's reading of the polite live region, and the parked `add-transaction-next` screen, which also uses `useLedgerWrite`.
