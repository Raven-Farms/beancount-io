# After a ledger switch, Home's budget panel keeps showing the previous ledger's budget rows until the new reads land

**Severity:** moderate (wrong numbers under the current ledger's Home). **Estimate:** 15 minutes. Owner: mobile. A3: tabs stay mounted. On a switch to a ledger whose budgets are already cached, `useBudgetGroups` returns them at once, and the effect in `use-budget-panel.ts:74, 102` only sets `loading` and starts `network-only` reads, so `rows` still holds ledger A's rows until `setRows` (`:156`). In `budget-card.tsx:119, 184`, `showSkeleton = (groupsLoading || rowsLoading) && rows.length === 0` is false, so A's rows (for example "Groceries $420.00 / $500.00") render under B's Home for as long as B's reads take. `home-screen.tsx:277` gives `BudgetCard` no `key`.

Code-level at `main` `c8b7b6ea2`. Not run natively, because it needs budget directives in a second ledger.

## Fix

Keep the rows with their ledger, as `{ledgerId, rows}`, and treat a mismatch as `[]`, the pattern Transactions search and the file browser use. Or reset the rows when `ledgerId` changes.

**Acceptance:** switching between two budgeted ledgers never shows the other ledger's budget rows, even briefly.

## Dedupe

w21/336 (batches after cancel), 225, 165, 184 and 080 differ. Searched `.pm/**` for "budget panel", useBudgetPanel, BudgetCard and switch.

Fixed. `useBudgetPanel` now records which ledger its rows were read for (`rowsLedger`, set wherever the rows are set, including the empty case) and returns, for any other ledger, no rows, `loading: true` and no failure, so after a switch the previous ledger's rows can never render under the new Home, even for the frames before the new reads start; the skeleton shows until they land. The same-ledger path and the refresh and retry paths are unchanged. Tests (`select-budget-panel.test.ts`: the hook records the ledger with each result and masks a mismatch; both fail with the hook reverted). Deviation: a source check of the hook, which needs the native runtime. Not run natively (needs budgets in a second ledger).

Native recheck: not exercised. The stale rows lasted only the frames before the new ledger's reads started, which a 4-second tap driver and screenshots can't catch reliably, and switching ledgers would show the QA account's other ledgers, which may hold real data. It rests on the hook tests.
