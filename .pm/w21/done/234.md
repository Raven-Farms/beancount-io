# Open Account still can't constrain a new account to a commodity the ledger hasn't posted yet: an opened or declared EUR/GBP is never offered

**Severity:** minor-to-moderate. This is the first-account case that w21/085's fix leaves open. Opening your *first* EUR, GBP or stock account is exactly when there are no postings in it yet. **Estimate:** 30–45 minutes. Owner: mobile. A3: the picker offers `openAccountCurrencyChoices(operating, meta.currencies)`. The server's `currencies` is Fava's posting-ranked list (`directives-report.ts:106-152` ranks posting units and cost currencies only), so a currency named only in an `open` constraint or a `commodity` directive never appears, and the picker has no free entry.

Reproduced natively on the iPhone 17e simulator (iOS 27.0) at `main` `7e42f850e`, on the disposable QA ledger (restored byte-for-byte to `f1a0b83c`):
1. With `2026-01-01 open Assets:Bank:QaEurAcct EUR` added, `ledgerMeta.currencies` (GraphQL) is `["USD"]`. Accounts → + → Currency offers only **No currency** and **USD**.
2. With `2026-01-01 commodity GBP` added too, `currencies` is still `["USD", ...]`, without GBP.
3. Only after a posting `10.00 EUR @ 1.10 USD` does `currencies` become `["USD", "EUR"]`. The picker then lists **EUR**, which is w21/085's fix working.

## Root cause

- `mobile/src/screens/open-account-screen/open-account-screen.tsx:310` builds the choices from `meta?.currencies` only.
- `backend-cluster/ledger/src/foundation/rustledger/directives-report.ts:106-152` (`collectAttributes`) derives `currencies` from postings, faithfully to Fava.

## Fix

In mobile, extend the choices with the currencies already named in `open` constraints and `commodity` directives (both are in the account and commodity lists the app already reads). Then add a "Other…" row that accepts a typed commodity, validated with the same rule as Create Ledger (w21/107) and the backend (w21/190). Leave the server's `currencies` as it is, for Fava parity.

**Acceptance:**
- On a USD ledger with only `open … EUR` and `commodity GBP`, the picker offers USD, EUR and GBP.
- "Other…" accepts `VTI` and writes `open Assets:Broker:VTI VTI`.

## Dedupe

w21/085 (done) widened the list to commodities with postings, and its recheck found this case. w21/107 and w21/190 are currency validation. Searched `.pm/**` for openAccountCurrencyChoices, "commodity directive", "No currency" and "first EUR".

Done in part, mobile only. Added the note's second step: the currency picker now ends with an "Other…" row that opens a typed entry (`TextInputModal`), validated with Beancount's commodity grammar (`isCommodityCode`, the same rule the backend applies to posting amounts, w21/190), trimmed and upper-cased by `typedCurrencyCode`, with the reason shown under the field. A code typed there becomes the selection and joins the list for the visit (`openAccountCurrencyChoices` takes the typed codes), so opening a first EUR, GBP or `VTI` account is possible and writes `open Assets:Broker:VTI VTI`. Four new strings in all 13 locales. Tests: codes accepted and refused (`1ABC`, `-EUR`, spaces, `€`, over 24 characters), the choices ordering with typed codes, and the wiring of the row; they fail with `account-name.ts` reverted. NOT done: automatically offering currencies named only in `open` constraints and `commodity` directives. The note said both lists are already read by the app, but they are not: `LedgerAccountItem` carries no constraint currencies, `ledgerPrices` lists price pairs only, and `ledgerMeta.currencies` is posting-ranked like Fava's. Doing that needs the server to expose them (a deliberate Fava-parity decision in `collectAttributes`), which is a separate backend change; the typed entry covers the user-facing gap meanwhile.
