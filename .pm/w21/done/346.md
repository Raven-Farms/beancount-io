# Ledger-profile links and Android's broad /ledger prefix land on Home, the Files tab, or not-found

**Severity:** minor-to-moderate. **Estimate:** 20 minutes. Owner: mobile. A3: AASA claims `"/ledger/*"` (`well-known-route.ts`), so the app also receives two-segment profile links. One example is `https://beancount.io/ledger/open_ledger`, the examples profile, which is in the sitemap. The resolver returns `null` for them, and `rewrite-system-path.ts` then sends the user to `"/"`. The user silently lands on Home for whatever ledger is current, with no browser fallback. `beancount:///ledger/open_ledger` does the same.

On Android, `mobile/app.json` uses `pathPrefix: "/ledger"`. That also claims `/ledger` (the my-ledgers list), `/ledger-gallery` and `/ledger_assets/…`. The rewrite leaves those paths unchanged, so Expo Router matches `/ledger` to the Files tab (`(tabs)/ledger.tsx`) and the others to `+not-found`.

Code-level at `main` `99c937e0e`: the resolver and rewrite were run with `tsx`. Not run natively.

## Fix

For paths the resolver can't map, open the original URL in the browser with `Linking.openURL` instead of rewriting to `/`. Change the Android intent filter to `pathPrefix "/ledger/"`.

**Acceptance:** `https://beancount.io/ledger/open_ledger` and `/ledger-gallery` open in the browser, not on Home, the Files tab or not-found.

## Dedupe

Nothing on the board covers this. Searched `.pm/**` for "profile link", "pathPrefix" and "ledger-gallery".

Fixed in the app; the hosted association file is not touched. `browserFallbackUrl` (`rewrite-system-path.ts`) names the hosted https URL of a `/ledger/…` link the resolver cannot map (the profile `/ledger/open_ledger`, in https, bare-path and `beancount:///` form); `+native-intent` now opens it with `Linking.openURL` and returns null, which Expo Router ignores for a link that arrives while the app runs and treats as the default route on a cold start, instead of rewriting to Home. Mapped links, non-ledger paths and foreign hosts are unchanged (a foreign host is never opened from here). On Android the intent filter was `pathPrefix "/ledger"`, which also claimed `/ledger` (the Files tab), `/ledger-gallery` and `/ledger_assets/…` (not-found); it is now `pathPattern "/ledger/..*/..*"`, so only owner/name paths reach the app and everything else goes straight to the browser. The note proposed `pathPrefix "/ledger/"`, which would still claim the profile and would make the browser fallback re-open the app in a loop on Android, so a pattern was used instead. Tests (`rewrite-system-path.test.ts`: the fallback URL for the three forms, the unchanged cases, the native-intent wiring and the intent-filter pattern; all three fail with the fix reverted). Deviations: the iOS association file (served by backend-v2, still 404 on production, w4/blocked/001) keeps claiming `/ledger/*`, so on iOS the profile link reaches the app first and is then handed to Safari, which iOS does not send back to the app; the `app.json` change needs a new native build to take effect on Android; none of this was run on a device.
