# Pulling to refresh on Reports never re-reads the ledger's read context, so "Failed to load" or the stale banner stays after the network returns

**Severity:** low. **Estimate:** 10 minutes. Owner: mobile. A3: `reports-screen/reports-screen.tsx:92-101`: `onRefresh` awaits only `incomeRefetch()`, but the failure state and the stale banner (`:175-181`) also depend on `ledgerMeta`. Home, Accounts and account detail include `ledgerMetaRefetch()` in their pull. With no cached context, "Failed to load / Try again" survives a successful pull. With a cached context and its error kept, the stale banner stays. Code-level at `main` `966ff79aa` (selector behavior proven under `tsx`; Apollo 3.14.1 keeps the old `data` and sets `error` on a failed refetch, `useQuery.js:236-253`). Not run natively: the simulator can't cut the network here.

## Fix

Refetch the read context in Reports' pull, as the other screens do.

**Acceptance:** after the network returns, a pull clears both states. A screen test covers it.

## Dedupe

See w21/406, w21/262 and w21/390. Searched `.pm/**` for ledgerMetaRefetch together with Reports.

---

**Resolved 2026-10-22** — Reports' pull to refresh re-reads the read context (`ledgerMetaRefetch()`) with the statement and the scheduled-entry checks, as Home, Accounts and account detail do, so a pull after the network returns clears "Failed to load" and the stale banner. Case in `read-context-gate.test.ts` (`mobile`); not run natively (the simulator cannot cut the network).

Native recheck (iPhone 17e): not exercised. It needs the read context to fail and then recover (the network cut and restored), and the simulator can't cut the network here. The fix's screen test covers the refetch.
