# File editor's "File Changed → Reload" refreshes the text but keeps the old error list, so it shows a fixed error at a line that no longer exists

**Severity:** minor. **Estimate:** 15–20 minutes. Owner: mobile. A2: the editor's conflict dialog is the recovery path when a file changed remotely, for example when someone fixed the ledger on the web. Reload swaps in the new content but leaves the error strip as it was. It goes on announcing "1 error" with the old message and line number, and its jump arrow lands on an unrelated line, until the user leaves the screen.

Environment: `main` at `391e3a405`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0). QA account, synthetic disposable ledger `mcp-agent-eval` (restored byte-for-byte afterwards). The stale save was refused, so nothing from the app was written.

## Repro

1. Append a failing assertion to `main.bean` outside the app: `2026-10-10 balance Assets:Cash 1.00 USD` (line 90). `getLedgerErrors` reports it.
2. Home → bell → tap the error. The editor opens on line 90 with the strip reading **1 error**.
3. Outside the app, remove the assertion. `getLedgerErrors` is now `[]` and the file has 88 lines.
4. In the editor, add a comment line → **Save** → **File Changed: "This file was changed remotely. Discard local changes and reload?"** → **Reload**. The conflict path itself works correctly.
5. The text is now the 88-line remote file, but the strip still reads **1 error**, and expanding it shows *"Balance failed for Assets:Cash: expected 1.00 USD, got 49.75 USD — line 90"*. Its arrow jumps to empty line 88. The phantom error stays as long as the screen is open.

## Root cause

`mobile/src/screens/ledger-file-editor-screen/index.tsx:443-455`: `handleReload` calls only the file query's `refetch()` and resets the document. The strip renders `filterFileErrors(allErrors, path)` (line 629) from `useLedgerErrors(ledgerId)` (line 396). That query revalidated once on mount and then follows the cache (`nextFetchPolicy: "cache-first"`), and nothing on this path invalidates it. The save path already does the right thing: `reportNewErrors` calls `invalidateLedgerData(client, "errors")` (around line 405). The "file unavailable" Reload button (around line 721) has the same file-only refetch.

## Fix

In `handleReload`, and in the unavailable-state Reload, also refresh the errors scope (`invalidateLedgerData(client, "errors")` or a `refetch` of the errors query) alongside the file refetch, so the strip matches the reloaded text. Optionally clear the strip while the refetch is in flight.

**Acceptance:** after step 4, the strip disappears without leaving the screen. If the remote change introduces an error instead, it appears with the correct line. A test drives `handleReload` with a mocked client and asserts the errors scope is refetched.

---

**Resolved 2026-10-21** — The file editor's `handleReload` (the "File Changed → Reload" path) now calls `invalidateLedgerData(client, "errors")` before refetching the file, as the save path's `reportNewErrors` already did. That evicts the errors fields and refetches the active errors query, so the strip matches the reloaded text: it disappears when the remote change fixed the error, and shows the correct line when it introduced one. The file-unavailable Reload button refreshes the errors scope too. The note's acceptance asked for a test driving `handleReload` with a mocked client. jest-lite can't render the screen, so `reload-errors.test.ts` checks the wiring on the source instead: errors are invalidated before the refetch on the conflict path, and on the unavailable path. The scope's refetch behaviour is covered by the existing `common/apollo` tests. Reverting fails 2 cases. Native gates pass: format, lint, typecheck, `yarn test:unit` (2525 passed, 1 skipped). Not exercised on the simulator. Shipped in the commit that moved this note (`mobile`).
