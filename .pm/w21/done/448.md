# Files: tapping Back while deleting a folder's last file lands one folder too high

**Severity:** minor. **Estimate:** 10 minutes. Owner: mobile. A3: `mobile/src/screens/ledger-file-browser-screen/index.tsx:579-581` decides with the `pathStack` captured at tap time (`deleteEmptiesFolder(pathStack, sorted.length)`) but pops whatever stack is current when the delete finishes (`updatePathStack(popPathStack)`). During the delete only the delete buttons are disabled; Back and the up control are not (`:357`, `:673`). The reviewer's tsx run of the real `deleteEmptiesFolder` and `popPathStack`: tap at `["","a","a/b"]`, go up to `a` while the delete runs, then the delete finishes and the stack becomes `[""]` instead of `["","a"]`.

Code-level at `main` `1e9f0fc30`; not exercised on the device (it needs a folder fixture and a tap inside the delete's round trip).

Steps: with `a/x.bean` and `a/b/y.bean`, open `a/b`, delete `y.bean`, and tap Back at once. The browser shows the root, although `a` still exists.

## Fix

Pop only if the current top is still the folder that was emptied: `updatePathStack(prev => top(prev) === emptiedPath ? popPathStack(prev) : prev)`.

**Acceptance:** the sequence above ends in `a`. A unit case is added.

## Dedupe

w21/088 (done) added the step-up after the last file is deleted, not this race. Searched `.pm/**` for deleteEmptiesFolder, deletingPath and "last file".

Resolved. A delete that empties a folder now steps up from that folder, not from wherever the browser is when the delete finishes: it records the folder it was tapped in and `popPathStackFrom(stack, folder)` pops only if that folder is still the top. Tapping Back during the round trip, from `a/b` to `a`, now ends in `a` instead of the root. Unit cases cover both outcomes and the wiring; the wiring pin fails against the old screen. Deviation: not driven on the device (it needs a folder fixture and a tap inside the delete).
