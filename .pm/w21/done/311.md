# GraphQL getLedgerErrors drops "code" and "hint", which REST and MCP return, so mobile never shows the service's fix hints

**Severity:** minor. It also breaks the REST/GraphQL/MCP parity rule. **Estimate:** 20 minutes. Owner: backend-v2 + mobile. A3: the GraphQL error type has only `filename`, `lineno` and `message`. REST `/errors`, the MCP `errors` resource and `checkLedger` return the raw `{ message, source, code, hint }`. Examples of hints mobile never sees: `TS_PLUGIN_SKIPPED`'s "Did you mean \"fava.plugins.…\"?" and `INVALID_UTF8`'s "Re-save the file as UTF-8…".

Code-level at `main` `ba784a628`.

## Root cause

`backend-cluster/backend-v2/src/features/ledger/api/resolvers/ledger-data-resolver.query.ts:112-121` (type) and `:466-470` (mapping), against `vocabulary-handler.ts:153-158` (REST).

## Fix

Add nullable `code` and `hint` to the GraphQL type and resolver, with parity tests. Mobile then shows the hint under the message in Notifications and the editor banner.

**Acceptance:** GraphQL returns `code` and `hint` matching REST for the same ledger, and mobile renders the hint.

## Dedupe

w2/013 added both fields to the internal type behind REST but not GraphQL, and w21/188 proposes exposing `severity` only. Searched `.pm/**` for BeancountError, hint and code together with GraphQL.

Backend half fixed; the mobile half is split out as w21/424 (blocked on a deploy). GraphQL `getLedgerErrors` now returns nullable `code` and `hint`, the same values REST `/errors`, the MCP `errors` resource and `checkLedger` return (an absent or empty value is null, not an empty string), so the three surfaces agree again; the response shape for REST/MCP is unchanged, so the OpenAPI snapshot did not move. Resolver test in `ledger-data-resolver.test.ts` (fails to compile without the fields). backend-v2 typecheck, lint (knip), the full suite (373 suites, 6462 tests) and `generate-v1-openapi` are green. Not done here: mobile rendering of the hint under the message in Notifications and the editor banner. Mobile's generated client is built from the production schema, which does not yet have these fields (nor `severity` from w21/188), so a query selecting them would be rejected by the server until backend-v2 deploys; w21/424 holds that work with its unblock condition.
