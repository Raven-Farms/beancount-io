# Commit listing silently caps "limit" at 50 on REST, GraphQL and MCP, and asks Gitea for stats and file lists it throws away

**Severity:** minor-to-moderate for API and agent callers; a client that treats a short page as the end stops early. **Estimate:** 30 minutes. Owner: backend-v2. A3: the service only checks `limit >= 1` and forwards it to Gitea, which caps commit pages at 50 without saying so. The OpenAPI spec and resolver document no maximum. The same call leaves Gitea's `stat`, `verification` and `files` options at their default `true` ("disable for speedup"), then reads only sha, message, author and committer.

Code-level at `main` `2e850e737`. The 50 cap and the defaults come from Gitea 1.24's source and the generated client's documentation (`gitea-api.ts:6815-6820`). They weren't measured against the live Gitea.

## Root cause

`backend-cluster/backend-v2/src/features/gitea/commits/service/commits-service.ts:234-262` (validation and call) and `:274-290` (mapper), plus `commit-reads.ts:42-46`. `ledger-repo-service.ts:127` has the same call.

## Fix

Publish and enforce a maximum of 50 across all three surfaces (or stitch upstream pages, as w2/m34 t002 did for `listLedgers`), with parity tests. Pass `stat: false, verification: false, files: false`.

**Acceptance:** `limit=100` either errors with the documented maximum or returns 100 commits on REST, GraphQL and MCP alike, and the list call sends the three speed flags.

## Dedupe

w2/m34 t001 and t002 fixed the same cap for `listLedgers`. Searched `.pm/**` for MAX_RESPONSE_ITEMS, CommitsRangeSize, "ledgerCommits limit" and repoGetAllCommits.

Fixed, taking the "publish and enforce a maximum of 50" option. `CommitsService.listCommits` refuses `limit` above `MAX_COMMITS_PAGE_SIZE` (50) with a BAD_USER_INPUT "limit must be at most 50" before any Gitea call, so REST, GraphQL and MCP (which all go through the service) behave alike instead of silently returning 50; the maximum is published in the REST query schema (`maximum: 50` in `docs/openapi/v1.json`, regenerated) and in the GraphQL argument's description, and MCP takes it from the same schema. The list call now sends `stat: false, verification: false, files: false`, and so does `getLatestCommit`, which reads only the commit's own fields. The mobile and dashboard callers use 30. Tests: service cases (limit 51, 100, 1000 refused without a Gitea call; exactly 50 accepted with the three flags), the REST schema bound, `getLatestCommit`'s flags, and the existing exact-argument pins in `commit-parity` and `ledger-repo-service` updated for the flags (the new service cases fail with the service reverted). backend-v2 typecheck, lint (knip), the full suite (373 suites, 6468 tests) and `generate-v1-openapi` are green. Not measured against the live Gitea (the speedup is its documented behaviour).
