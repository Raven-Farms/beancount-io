# A Custom filter ending 9999-12-31 passes validation but makes the whole journal fail to load

**Severity:** low (an edge case). **Estimate:** 5 minutes. Owner: mobile. A3: the filter checks only start ≤ end. The server computes the day after the end, `10000-01-01`, rejects it, and fails with "Failed to parse date". The Custom date pickers set no `maximumDate`.

Code-level at `main` `ba784a628`. The server's `parseDateRange("2026-01-01 - 9999-12-31")`, copied and run under Node, returns `undefined`. Fava overflows the same way.

## Root cause

- `mobile/src/screens/transactions-screen/filters/select-filter-query.ts:57-62` (`isDateRangeValid`).
- `transaction-filters-screen.tsx:414-420` (no `maximumDate`).
- `backend-cluster/ledger/src/foundation/rustledger/directive-filter.ts:937-938`.

## Fix

Pass a `maximumDate` (for example 9999-12-30) to the Custom pickers, or refuse an end of 9999-12-31 in `isDateRangeValid`.

**Acceptance:** the picker can't select 9999-12-31, or Apply is disabled with a message. A unit case is added.

## Dedupe

w3/185 covers reversed ranges. Searched `.pm/**` for 9999, maximumDate and "Failed to parse date".

Fixed with both of the note's fixes. The filter sheet's date picker is capped at 9999-12-30 (`maximumDate`, from the shared `MAX_FILTER_DAY`), and `resolveDateRange` clamps a custom window's ends to that day before they are serialized, so a stored or typed 9999-12-31 can never reach the server: the query becomes `2026-01-01 - 9999-12-30` instead of failing the whole journal with "Failed to parse date". The clamp keeps Apply enabled (nothing is invalid), so no new message was needed; an ordinary or far-future window is untouched. Tests added to `filters/__tests__/select-filter-query.test.ts` (the clamp cases and the picker wiring fail with the two files reverted). Mobile gates and deadcode green. The server's own overflow in `directive-filter.ts` (another package) is not changed.
