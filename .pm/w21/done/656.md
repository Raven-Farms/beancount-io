# `option "plugin_processing_mode" "raw"` is ignored by the hosted engine: pads are applied and balance assertions enforced, unlike bean-check and `bea`

**Severity:** low. **Estimate:** 30 minutes. Owner: ledger (rustledger upstream). Compared at `main` `1ec9cb250`: bundled `@rustledger/wasm` 0.24.0 against Python Beancount 3.2.3 with beanquery 0.2.0, on the same text. With raw mode, a `pad` and a `balance`, rustledger inserts the padding (Assets:Bank 100 USD) and still raises "Balance failed" for a wrong assertion, while Beancount applies no pad and runs no balance check. The user sees padding rows and errors that `bean-check` and `bea check` don't show.

## Fix

Honour raw mode upstream, or have the ledger service warn that the option is unsupported.

**Acceptance:** raw mode matches Beancount, or a visible warning explains the difference.

## Dedupe

w5/766 is about CLI export only. Searched all of `.pm/` for plugin_processing_mode.

---

**Resolved 2026-10-22** — the ledger service now honours raw mode itself, since the bundled `@rustledger/wasm` 0.24.0 still ignores it: when the entry point's last `option "plugin_processing_mode"` is `"raw"`, the parse inserts no padding and drops the pad and balance-check errors (E2001 failed balance, E2002 past explicit tolerance, E2003 unused pad, E2004 multiple pads), while validation such as an account that was never opened still reports. BQL follows, because a ledger with a pad is queried over the materialized snapshot. Checked against the engine and Python Beancount's `bean-check` on the same six cases; the one remaining difference is that the engine has no duplicate-balance check (`Duplicate balance assertion with different amounts`), in either mode. Tests: `engine-raw-plugin-mode.test.ts` (fails without the change), `option-validation.test.ts`, and a live check in `scripts/verify-rustledger.ts` (`backend-cluster/ledger`). A ledger service deploy carries it to production.
