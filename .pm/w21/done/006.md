# After a relaunch, Transactions and Merchants show the last session's data while Home shows today's

**Severity:** major. **Estimate:** 30–60 minutes. Owner: mobile. A1/A2: the expected loop is that an agent, the CLI or the web dashboard writes to a hosted ledger and the user then opens the app. On cold start Home shows the new entries, but tapping **See all** leads to a Transactions list without them, and it stays that way until the user happens to pull to refresh.

Environment: `main` at `ab6f2adf7`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0), light, English. QA account on `https://beancount.io`, synthetic disposable ledger `mcp-agent-eval`. The temporary fixture was restored byte-for-byte (sha256 checked, clean ledger check).

## Repro

1. In the app, open Transactions and Merchants on the ledger so both are cached. The newest transaction is 2026-08-28 FARMERS MARKET, and Merchants reads "Search 10 merchants…".
2. Outside the app (web editor, API, `bea`), append three entries for a new payee `qa-20261020-gym` dated 2026-07-25, 08-25 and 09-25. The file write succeeded, and `getLedgerErrors` stayed empty.
3. Terminate and relaunch the app (`xcrun simctl terminate` / `launch`).
4. **Home → Recent Transactions** lists `qa-20261020-gym −$30.00` first, and Net Worth moved from $17,108.51 to $17,018.51. Correct.
5. **Transactions** still starts at **August 28, 2026 FARMERS MARKET**, with no `qa-20261020-gym` rows. **Merchants** still reads **"Search 10 merchants…"**, with no new payee. Both stayed that way across another relaunch and repeated tab switches.

## Root cause

- `0f4c21f19` ("persist Apollo cache for offline-tolerant cold starts") restores the whole Apollo cache from AsyncStorage before first render (`mobile/src/common/apollo/cache-persist.ts`). It moved Home, Accounts and Reports to `cache-and-network` and pinned that in `src/common/apollo/__tests__/fetch-policies.test.ts`.
- The Apollo client has no `defaultOptions`, so every query without an explicit policy is `cache-first`. With a persisted cache, that means "never ask the network on a cold start":
  - `mobile/src/screens/transactions-screen/transactions-screen.tsx:132-146`: `useGetLedgerJournalQuery`, no `fetchPolicy`.
  - `mobile/src/screens/merchants-screen/merchants-screen.tsx:158-169` (payee rollup) and `use-payee-recurrence.ts:27-34` (series): `useQueryShellQuery`, no `fetchPolicy`.
  - `mobile/src/screens/merchant-detail-screen/merchant-detail-screen.tsx:259-296`: three queries, no `fetchPolicy`.
- Control: Home's `recent-transactions-card.tsx` uses `cache-and-network`, which is why Home was current in step 4.

## Fix

Give these list and detail surfaces `cache-and-network`, matching the m34 decision for Home, Accounts and Reports. Cached rows render instantly offline and are replaced when the network answers. Keep pagination's `fetchMore` merge and pull-to-refresh semantics (spinner only for a user pull). Extend `fetch-policies.test.ts` to pin the new surfaces. Alternatively, set a client-wide `defaultOptions.watchQuery.fetchPolicy = "cache-and-network"` and keep the explicit `network-only` / `no-cache` call sites. Then any future screen is safe by default; document that choice in `mobile/AGENTS.md`.

Also fix `budget-screen/hooks/use-budget-actuals.ts`, `use-budget-groups.ts` and `home-screen/hooks/use-budget-panel.ts`, which set `cache-first` explicitly. **Observed later in the same run:** a budget added through the app (`2026-08-01 custom "budget" Expenses:Food:Groceries "monthly" 300 USD`) was then removed from the file outside the app. After a relaunch, Home's Budget card still listed **Food:Groceries $0.00 / $300.00** for a budget that no longer exists.

**Acceptance:** repeat steps 1–5. After the relaunch, Transactions lists `qa-20261020-gym` within one network round trip, Merchants counts 11 and shows the new payee, and its detail shows three transactions. Offline cold start still renders the cached lists, with the stale banner where it applies. The fetch-policy test fails if any of these surfaces reverts to a default policy.

## Dedupe

Searched `.pm/**` (including `done/`) for cache-first, persisted cache, cold start and stale. `w4/234` (open) is the same Apollo default on the **dashboard**'s BQL page (`dashboard/src/features/bql/pages/index.tsx`). It is a separate package and code path, but the same mechanism, so the two fixes should describe the policy the same way. The persistence work (w1/m34, done) deliberately covered only Home, Accounts and Reports. No item covers Transactions or Merchants.

---

**Resolved 2026-10-20** — Took the client-wide option. `APOLLO_DEFAULT_OPTIONS` (`mobile/src/common/apollo/default-options.ts`) makes every watched query `cache-and-network`, with `nextFetchPolicy: "cache-first"`: revalidate once per mount or variables change, then follow the cache. Explicit `network-only` and `no-cache` call sites keep their policies.

- Transactions, Merchants (rollup and recurrence) and merchant detail now revalidate on a cold start with no per-screen change, and so will any future screen.
- `use-budget-groups` and `use-budget-actuals` drop their explicit `cache-first`, which is what kept a removed budget on Home's card.
- Home's budget panel reads its totals `network-only`, falling back to `cache-only` offline.
- `mobile/AGENTS.md` gains "Fetch policies — revalidate the persisted cache".

Tests: `default-options.test.ts` runs a real `ApolloClient` over a restored cache. A cold-start watch renders the persisted rows and then the network's, while Apollo's bare default answers from the cache with zero requests, which is the bug. A later cache write does not refetch. `fetch-policies.test.ts` pins the client wiring, the six list/detail/budget sources (none reverts to `cache-first`) and the panel's network-first read. Mobile gates pass: format, tsc, eslint, knip, and 2375 unit tests.

Not verified on the simulator (relaunch repro, offline cold start, stale banner). `w4/234`, the same mechanism on the dashboard's BQL page, stays open there. Shipped in `c4fb798db` (`mobile`).
