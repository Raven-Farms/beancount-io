# The entries precheck ignores `inferred_tolerance_default` written the Beancount way ("USD:0.01", "*:0.005"), refusing entries bean-check accepts, and gives whole-number postings a 0.5 tolerance

**Severity:** low (API, agents). **Estimate:** 20 minutes. Owner: ledger. A3 (code-level at `main` `b6d52c1a0`; proven through the real Koa handler in a scratch jest test with only Gitea mocked): `transaction-balance.ts:66-77` (`scanInferredToleranceDefault`) accepts only a bare number, so the real syntax `"USD:0.01"` silently falls back to 0.005. Splitting -10.00 USD into three postings of 3.33 USD is then refused as `UNBALANCED` "residual 0.01 USD", though bean-check and the engine accept it. In the other direction, `halfUnit(0)` (`:47, :136`) gives integer postings a 0.5 tolerance where Beancount gives none, so "10 USD / -9.6 USD" passes the precheck and is refused later by the engine (E3001) with a different message. Mobile blocks non-zero remainders itself (`postings-utils.ts:431`).

## Fix

Parse `inferred_tolerance_default` per currency (`CUR:value` and `*:value`), and use Beancount's inferred tolerance (half the last decimal digit, zero for integers).

**Acceptance:** the 3 × 3.33 split is accepted under "USD:0.01", and 10 / -9.6 USD is refused by the precheck. Tests cover both.

## Dedupe

See w21/135 (tolerance multiplier). Searched all of `.pm/` for inferred_tolerance_default and halfUnit.

---

**Resolved 2026-10-22** — the ledger service's entries precheck (`transaction-balance.ts`) now uses Beancount's tolerance inference: `option "inferred_tolerance_default"` is read as `CURRENCY:value` and `*:value` declarations (each adds one; a later one for the same currency wins; a bare number, which both engines report as invalid, declares nothing). A posting with decimals implies half its last digit and a whole number implies nothing. A currency's tolerance is the largest implied value raised to its own default; one with none implied takes its own default, then `*`, then zero. The old 0.005 floor is gone. The 3 × 3.33 split is accepted under "USD:0.01", and 10 / −9.6 USD is refused by the precheck (UNBALANCED, residual 0.4 USD). Checked against Python Beancount 3.2.3 and the bundled `@rustledger/wasm` 0.24.0. Where they differ, the precheck follows Beancount: rustledger lets a `*` default raise an implied tolerance, so under the setup template's `"*:0.001"` a residual above the implied tolerance but within 0.001 is refused here though the hosted engine would accept it; bean-check refuses it too. Tests: `transaction-balance.test.ts` and a live check in `scripts/verify-rustledger.ts` that the precheck agrees with the real engine on eleven cases (`backend-cluster/ledger`). A ledger service deploy carries it to production.

Production recheck: awaits the ledger service deploy (with w21/532–534, 550, 569, 649–657).
