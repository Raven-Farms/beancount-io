# "Show older changes" gets stuck once 30 or more commits land while Notifications is open: each tap re-asks for page 2, and newer commits append below older ones

**Severity:** low. **Estimate:** 20 minutes. Owner: mobile. A3 (code-level at `main` `9b513aede`, proven under `tsx` with the real functions): `notifications-screen/commit-pages.ts:34-36` (`shownCommitPages`) and `notifications-screen.tsx:282-305` (`showOlder`) derive the next page from the row count. After 30 or more new commits, the server's page 2 is exactly the rows already shown, `appendCommitPage` adds nothing, and every tap asks for page 2 again. That page is full, so the button never hides. With 40 new commits, rows 31–40 are the *newest* commits, appended below older ones.

Not run natively (it needs 30 or more commits pushed during one visit).

## Fix

Page by the last shown commit (a cursor or "before sha"), or re-anchor by dropping overlap and refetching the first page when the head moved.

**Acceptance:** after a burst of 30 or more commits, Show older keeps reaching older commits in order. A unit case is added.

## Dedupe

Same button as w21/313, w21/431, w21/498 and w21/512, but a different cause (a fully duplicated page while the screen is open). Searched `.pm/**` for shownCommitPages and appendCommitPage.

**Resolved 2026-10-22** — Show older now notices a moved list: `commitPageOverlaps` tells an older page that repeats a commit already shown (new commits shift the offset pages), and the screen then reads the first page again instead of appending or re-asking page 2, so the new commits land at the top and the button no longer sticks. Unit cases cover the 30-new-commits and one-new-commit shifts and a clean older page; a source check pins the flow. Not run natively (needs 30 commits pushed during a visit).
