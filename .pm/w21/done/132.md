# A commit's FILES list shows a renamed file as two "+0 −0" files, and a created file looks the same as a deleted one

**Severity:** moderate. The Recent changes → commit screen misdescribes what a commit did. A deleted ledger file reads like an unchanged one, and a rename reads like two untouched files. **Estimate:** 1–2 hours. Owner: backend-v2, plus mobile rendering. A3: Gitea's commit `files[]` lists a rename as a removed path plus an added path, each with a status (`added`/`removed`/`modified`), while its `.diff` detects the rename. The backend drops the status (`CommitFileChange` has no status field) and looks up per-file counts by the diff's *new* path only, so old paths always get 0/0.

Verified live through read-only GraphQL against production at `main` `cf6122e14`, on `puncsky/mcp-agent-eval` (`getCommitDetails` for all 632 commits):
- `46e4d871…` ("Rename qa-20261020-a.bean → qa-20261020-c.bean"): FILES shows `qa-20261020-a.bean +0 −0` and `qa-20261020-c.bean +0 −0`. The diff has one `rename from / rename to` block.
- `b510ee34…` lists 3 file rows for a 2-file diff. The old name reads `+0 −0`.
- `13a3f1ef…` (create the empty `qa-20261020/n.bean`, from this run's w21/088 probe) and `019ea867…` (delete it) both show `qa-20261020/n.bean +0 −0`, and nothing marks the deletion.

## Where

- `backend-cluster/backend-v2/src/features/gitea/commits/service/commits-service.ts:324-336` maps `commit.files` and drops `status`, keying stats by `filename` only.
- `mobile/src/screens/commit-detail-screen/commit-detail-screen.tsx:262-280` renders the rows.

## Fix

- Add `status` (added, removed, modified, renamed) and `previousFilename` to `CommitFileChange` on REST, GraphQL and MCP together, built from the diff's `rename from/to`, `new file mode` and `deleted file mode` headers.
- Collapse a rename into one row.
- Mobile shows "Added", "Deleted" or "Renamed from …" badges.

**Acceptance:**
- `46e4d871` shows one "Renamed from qa-20261020-a.bean" row.
- `019ea867` shows the file as Deleted, and `13a3f1ef` as Added.
- Add parity tests.

## Dedupe

w3/m17 lists "renamed diff targets" as unverified only. Searched `.pm/**` for rename, "similarity index", "rename from", CommitAffectedFiles, status and "+0 −0".

**Resolution (2026-10-21):** backend-v2 `parseFileStatsFromDiff` now reads each file's extended headers (`new file mode`, `deleted file mode`, `rename from`/`rename to`) and counts `+`/`-` only inside hunks. `commitFileChanges` collapses Gitea's removed + added pair for a rename into one row, and falls back to Gitea's own status when the diff is unavailable. `CommitFileChange` gains `status` (`added`/`removed`/`modified`/`renamed`) and `previousFilename`. REST and the MCP resource return the service result, so all three surfaces carry them. The new `commit-parity.test.ts` rename case and the service tests fail with the fix reverted.

Mobile does not query the new fields yet: its codegen reads the production schema, and querying a field the deployed backend lacks would break the screen. `commitFileRows` derives the same status from the `diff` the commit screen already fetches, and shows "Added", "Deleted" or "Renamed from …" under the row and in its accessibility label (13 locales).

Not exercised natively or against `46e4d871`/`019ea867`/`13a3f1ef`; the backend half needs a backend-v2 deploy.
