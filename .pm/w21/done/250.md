# Deleting from a transaction detail after the entry changed elsewhere fails with a bare "Failed to delete transaction", and every retry fails the same way

**Severity:** moderate. Web, CLI and agent edits make this common. **Estimate:** 30 minutes. Owner: mobile. A3: w21/028 taught Edit Transaction to recognise "changed elsewhere". Delete never learned it. A NOT_FOUND (the entry's hash changed) or a CONFLICT (the slice sha moved) is reported as a generic failure, and nothing refetches the context. The stale entry stays on screen with Delete still offered, and each retry fails identically until the user leaves.

Reproduced natively on the iPhone 17e simulator (iOS 27.0) on a bundle from before w21/117, on the disposable QA ledger (restored byte-for-byte to `f1a0b83c`):
1. Seed `; qa-20261020-del` (`2026-08-30 * "QA STALEDEL" "probe"`), then open its detail from Home.
2. Change the entry's text through the API, as another client would.
3. ⋯ → Delete → Delete. The alert reads **"Failed to delete transaction / Ledger resource not found"**, and the detail still shows QA STALEDEL.

On current `main` (`6a7949ccc`), w21/117's `ledgerWriteFailureMessage` maps NOT_FOUND and CONFLICT to null, so the alert drops the raw line and reads only "Failed to delete transaction", with the same dead end. A reviewer ran the real `deleteTransaction` against backend-v2's shapes (`error-to-domain.ts:129-132`). `selectOutcomeFailure` (the edit screen's classifier) returns `{ kind: "conflict" }` for both.

## Root cause

- `mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx:389`: `describeFailure: (e) => ledgerWriteFailureMessage(e, i18n)`, with no gone or conflict branch.
- `delete-transaction.ts:36-38` shows it in an Alert; no refetch follows.

## Fix

Classify the delete error with `isEntryGone` / `isConflictError`, as `save-failure.ts` does:
- **NOT_FOUND:** show the `transactionDetailRemoved` state (w21/094) and `invalidateLedgerData(client, "entries")`.
- **CONFLICT:** refetch the entry context, then say it was modified elsewhere and offer Delete again on the fresh copy.

**Acceptance:**
- In the steps above, Delete lands on "This transaction was changed or removed…".
- A metadata-only change elsewhere followed by Delete succeeds after one refetch.
- Unit cases cover both codes.

## Dedupe

w21/117 (done) covers transport errors only, w21/197 the double fire, w21/028 the edit-only conflict, and w21/094 the stale detail after an in-app write. Searched `.pm/**` for deleteTransaction, describeFailure, "Ledger resource not found", and isEntryGone together with delete.

Fixed in mobile: Delete now recognises an entry that changed elsewhere. `classifyStaleDelete` reads a failed delete as `gone` (NOT_FOUND, since entries are addressed by a content hash that moved) or `conflict` (a moved source-slice checksum), and `deleteTransaction` calls a new `onStale` hook for either. The detail screen's hook invalidates the entries scope and refetches the entry context, so a removed entry lands on its "This transaction was changed or removed..." state (w21/094) with no extra dialog, and a changed one holds the fresh `sha256sum`, so deleting again works on the new copy. A conflict also shows a dialog (`deleteTransactionChanged`, new in all 13 locales): "This transaction was changed elsewhere. It has been reloaded; try deleting it again." Any other failure behaves as before (offline text, refusals). Tests in `delete-transaction.test.ts` cover the gone path (reload, no dialog), the conflict path (reload plus the dialog), other failures unchanged, the classifier, and the detail screen's wiring; four fail with the two files reverted. The "no raw error message" guard stays satisfied (the classifier reads the server text only to detect the checksum). Deviation: the note's "metadata-only change then Delete succeeds after one refetch" is the second Delete on the reloaded copy, not an automatic retry, and no simulator run.
