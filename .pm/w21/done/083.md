# A ledger link opened while signed in stays stashed, and replays on the next sign-in, possibly as a different account

**Severity:** moderate (wrong navigation across accounts). **Estimate:** 15–20 minutes. Owner: mobile. A3: while signed in, tap a link such as `https://beancount.io/ledger/alice/books/journal`. Transactions opens correctly. But `rewriteSystemPath` has also stored the link in the pending-app-link slot, and nothing clears it on a signed-in open. Later in the same app process:
- signing out and in again,
- an auth-error teardown and re-sign-in,
- or a different user signing in

replays it. The app jumps from Home to `alice/books` Transactions. If the new account can't read that ledger, `openAppLinkTarget` (`open-app-link.ts:47-50`) opens Safari to the old URL.

Environment: `main` at `705ec4ba4`. Code-level. The simulator's `openurl` raises an untappable system confirmation here, so a native link open can't be driven.

## Root cause

- `mobile/src/common/app-links/rewrite-system-path.ts:31` calls `setPendingAppLink(target, url)` for every resolved link, whether or not a session exists.
- `use-app-link-handler.ts:54-68` opens the target directly when signed in, and stashes only when signed out, but never clears the stash.
- The slot (`pending-app-link.ts`, on `globalThis`) is emptied only by `takePendingAppLink`. That runs on a `session` change (`use-app-link-handler.ts:91-97`) or in `oauth-sign-in-finalizer.ts:38`.

## Fix

Stash only when there is no session. Or call `clearPendingAppLink()` after a direct open, and on sign-out as part of `clearServerScopedState`.

**Acceptance:** a unit test where resolving a link with a session leaves `peekPendingAppLink()` null, and a later session change opens nothing.

## Dedupe

w4/021 (done) is Welcome shown to a signed-in user, and w21/071 is the auth-error teardown's leftover local state, which doesn't include this in-memory slot. Searched `.pm/**` for pendingAppLink and app-link replay. No item.

**Resolved 2026-10-21** — Shipped in the commit that moved this note (`mobile`). `routeIncomingAppLink` in `pending-app-link.ts` decides what happens to an incoming link. Signed out, it stashes the link for sign-in. Signed in, it clears the slot that `rewriteSystemPath` filled and returns "open now". `use-app-link-handler.ts` routes every link through it, and `clearServerScopedState` clears the slot as well, covering Log out, server change and, since w21/071, the auth-error teardown. In `pending-app-link.test.ts`, a link resolved by `rewriteSystemPath` and then routed with a session leaves `peekPendingAppLink()` null, and a later `takePendingAppLink()` finds nothing. A signed-out link still waits for sign-in. The handler and sign-out wiring check fails with those changes reverted; the behaviour tests exercise the new helper directly. A native link open can't be driven, because the simulator's `openurl` shows an untappable confirmation.
