# Merchant detail's exact-payee filter can exceed the ledger's 256-character pattern limit, so a merchant with long merged spellings fails to load its journal

**Severity:** moderate for affected merchants. **Estimate:** 20 minutes. Owner: mobile. A3: since w21/181 (`bab8acf5f`), `filter-exact-payee.ts:57-69` joins every merged spelling into one escaped alternation and adds 12 characters. The ledger service refuses patterns over `MAX_FILTER_PATTERN_LENGTH = 256` (`directive-filter.ts:64, 193-197`) with `BadUserInputError`.

Under `tsx`, a 59-character bank payee with 3 case variants and 1 trailing-space spelling produced a 259-character pattern. Two of its alternatives were identical, because the filter trims spellings that w21/093 deliberately keeps distinct. Before the change, one plain needle was sent.

Code-level at `main` `24df51bf0`. Not run natively.

## Fix

Lowercase and de-duplicate the alternatives, since the server match is case-insensitive. If the pattern still exceeds 256 characters, fall back to the plain free-text filter for the primary spelling.

**Acceptance:** that merchant's detail loads its journal.

## Dedupe

This is a follow-up to w21/181 (done). Searched `.pm/**` for MAX_FILTER_PATTERN_LENGTH, "256 char" and exactPayeeFilter.

Fixed. `exactPayeeFilter` now merges spellings that differ only in case or trailing space into one alternative (the server matches case-insensitively and `filterExactPayee` still narrows exactly on the client; the first spelling is kept), and if the anchored pattern still exceeds the ledger service's 256-character limit it returns the plain quoted text filter for the primary spelling (`toPlainSearchFilter`, what the screen sent before w21/181) instead of a pattern the server refuses, so the merchant's journal loads and the client trims the extra rows. Tests (`filter-exact-payee.test.ts`: four case and space variants collapse to one alternative; six distinct long spellings fall back to the primary spelling as text; case variants alone still use the anchored form); both new cases fail with the selector reverted, and the existing anchoring tests are unchanged. Deviation: the fallback can page rows other than the merchant's (text match), as before w21/181, so for such a merchant the 500-entry cap can again cut off its own rows; that needs a server-side payee-list filter and is not attempted here. Not run natively with that merchant.
