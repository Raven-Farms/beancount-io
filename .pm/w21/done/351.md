# A connection that drops mid-save is reported as "Nothing was saved" or "Failed to save", so a retry commits the entry twice

**Severity:** moderate (duplicate writes). **Estimate:** 45 minutes. Owner: mobile, plus backend-v2 if a request ID is added. A3: when a connection drops after the request is sent, the client sees the same `TypeError("Network request failed")` as when it is offline. `ledgerWriteFailureMessage` (`mobile/src/common/ledger-refusal.ts:85`) maps any transport failure to `ledgerWriteOffline` ("You're offline. Nothing was saved."). Budget save and delete, Open Account and the file browser use that copy. `runLedgerWrite` (`ledger-write.ts:101-110`) toasts `saveFailed` and skips the post-write refresh, so New Transaction says "Failed to save" and the screens behind it never show the entry that actually committed. `addEntries` and `bulkEntries` have no idempotency key (`createLedger` has one), so the natural retry writes the transaction or budget a second time.

Code-level at `main` `7280ccceb`. The reviewer ran both functions under `tsx` with that error. Not run natively, because it needs a connection to drop mid-request.

## Fix

Treat a transport failure on a write as unconfirmed, not as nothing saved. Refetch the affected data before offering a retry, and word the copy as "We couldn't confirm the save". Better, add a client request ID to `addEntries` and `bulkEntries`, as `createLedger` has, on REST, GraphQL and MCP for parity.

**Acceptance:** a write whose response is lost never claims "Nothing was saved", and retrying it does not create a duplicate.

## Dedupe

w21/327 covers only 5xx responses, and its acceptance keeps network failures on the offline copy. w21/044, w21/193 and w21/197 are double taps. Searched `.pm/**` for ledgerWriteOffline, isTransportFailure, "Nothing was saved", idempot, duplicate and twice.

Fixed for the copy half; the retry-safety half is split to w21/449 (blocked). `ledgerWriteFailureMessage` no longer claims "Nothing was saved" for a transport failure: only a failure raised before the request left (the token refresh failing, `OAuth refresh failed`) keeps "You're offline. Nothing was saved."; "Network request failed", "Failed to fetch" and a wrapped network error now read "The server didn't confirm the save. Check before trying again.", because a connection that drops after the request was sent looks exactly like an offline one and the write may have committed. The shared write hook (`useLedgerWrite`) now words failures through this function, so New Transaction (and every other `runLedgerWrite` caller) shows that copy instead of the generic "Failed to save" for a transport failure, a gateway 5xx or a rate limit; other errors still show the screen's own failure message. Budget save and delete, Open Account and the file browser already used this function and get the new copy. Tests: `ledger-refusal.test.ts` (offline copy only before sending; the three transport forms read unconfirmed; the hook uses the function) and the pinned delete-transaction cases updated; two of them fail with the sources reverted.

Deviations: (1) no refetch after an unconfirmed failure. Evicting and refetching while the device is genuinely offline would blank the screens that were still showing cached data (w21/350 protects only the disk copy), so the copy tells the user to check the list first. (2) The acceptance "retrying it does not create a duplicate" is not met by copy alone: `addEntries` and `bulkEntries` still have no client request ID, so a retry after a lost response can write twice. That needs a REST, GraphQL and MCP contract addition plus an idempotency store, and is filed as w21/449 and blocked. Not run natively; a mid-request drop cannot be produced on demand.
