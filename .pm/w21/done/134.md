# Same-day entries come back grouped by type instead of file order, so account-journal running balances are wrong around a same-day pad, note or price

**Severity:** moderate. Account detail on mobile (and the GraphQL, REST and MCP account journal) shows impossible running balances: a +100 salary "→ 500" and a +400 padding row "→ 400". The Entry Context "balance before/after" for same-day entries is wrong the same way. **Estimate:** 1–2 hours. Owner: ledger. A3: rustledger 0.24 orders a day's directives by kind (balance, pad, transactions, note, event, price, custom). Beancount sorts by date, then a type rank that covers only open, balance, document and close, then line number. The service takes the engine's `expandPads().directives` order as the file order, and `mergePaddingTransactions` only places each padding row after its Pad.

Verified against production through the API at `main` `67bf3f9e0` on the disposable QA ledger, which I restored byte-for-byte to `f1a0b83c`. The fixture `; qa-20261020-padord`:
- open `Assets:Qa20261020Pad USD`
- `2026-08-05 *` "QA PADSAL": +100.00 from Income:Salary
- `2026-08-05 note`
- `2026-08-05 pad … Equity:Opening-Balances`
- `2026-08-06 balance … 500.00 USD`

`getLedgerAccountJournal(account: "Assets:Qa20261020Pad")`, newest first:

| Date | Entry | Change | Running balance |
|---|---|---|---|
| 08-06 | Balance | | 500.00 |
| 08-05 | Note | | 500.00 |
| 08-05 | **Salary** | **+100.00** | **500.00** |
| 08-05 | **Padding** | **+400.00** | **400.00** |
| 08-05 | Pad | | (empty) |
| 01-01 | Open | | |

Beancount's order (newest first) is Balance 500 · Padding +400 → 500 · Pad 100 · Note 100 · Salary +100 → 100. The reviewer reproduced the same result against the real engine and Beancount 3.2.3.

## Where (`backend-cluster/ledger/src/foundation/rustledger/`)

- `engine.ts:141-150` (engine order taken as-is), plus `mergePaddingTransactions` (`:189`, called at `:621`)
- `plugins/index.ts:145-161` (`sortPluginOutput`)
- `journal-running-balance.ts:503` (accumulates in that order)
- `source-slice.ts:945` (context balances)

## Fix

Re-sort directives with Beancount's `entry_sortkey`: date, then the type rank (open 0 < balance 1 < … < document 3 < close 4, with everything else at the transaction rank), then filename and line number. Insert each padding transaction directly after its Pad. Do this once in the engine adapter, so every surface gets it.

**Acceptance:**
- The fixture's journal reads Salary +100 → 100, Note 100, Pad 100, Padding +400 → 500, Balance 500.
- Entry Context for the salary shows before 0 and after 100.
- Add a ledger unit test comparing against `bea` output.

## Dedupe

w5/730 and w5/884 are CLI bulk-trade ordering. Searched `.pm/**` for "same-day order", entry_sortkey, lineno, "pad order" and "note running balance".

**Resolution (2026-10-21):** new `rustledger/entry-sort-order.ts` `restoreEntrySortOrder` runs once in `parseLedgerFilesUncached`, on the engine's directives before plugins and before `mergePaddingTransactions`, so every surface gets it. rustledger's directives carry no source position, so each takes the next line of its `date|type` from the parsed source text, in the engine's order. The day is then sorted by Beancount's `entry_sortkey`: open < balance < everything else < document < close, then line number (Beancount uses lineno alone, not filename). A day whose directive counts disagree with the source keeps the engine's order.

Run against the real engine (`parseLedgerFilesInProcess`, local script) on the note's fixture, the account journal reads Salary +100 → 100, Note 100, Pad 100, Padding +400 → 500, Balance 500, and the salary's Entry Context is before 0 / after 100. Tests: `entry-sort-order.test.ts` and a stubbed-engine wiring case in `engine-plugins.test.ts`, which fails with the engine hook reverted.

Deviation: no `bea`/Beancount binary was available here, so the expected order comes from the note's Beancount 3.2.3 result, not a fresh comparison.
