# Explore search finds nothing for "crypto example" or an owner name: the query goes to Gitea as one substring

**Severity:** minor-to-moderate. Explore is how people find public example ledgers, and its own comment says switching to it "widens" a search. **Estimate:** 45 minutes. Owner: ledger (backend), for REST, GraphQL and MCP parity. A3: Explore sends the typed text unchanged as `q`, and the ledger service passes it straight to Gitea's repo search. That search matches a substring of the name or description, so spaces never match the hyphenated names, and an owner matches only in the `owner/` form.

Verified against production through GraphQL `searchLedgers(q, isPrivate: false, includeDesc: true)` on 2026-10-21:

| q | results |
|---|---|
| `crypto` | 1 (open_ledger/crypto-example) |
| `crypto-example` | 1 |
| `crypto example` | **0** |
| `open_ledger/` | 50 (page full) |
| `open_ledger` | **1** (open_ledger/kroger, a description match) |
| `example` / `EXAMPLE` | 4 / 4 |

## Root cause

- `mobile/src/screens/ledger-selection/use-discovery.ts` sends `q` verbatim.
- `backend-cluster/ledger/src/api/ledgers.ts:194-215` forwards `q` to Gitea's repo search unchanged.

## Fix

In the ledger service, so every surface benefits:
- Split the query on whitespace and match every term against `owner/name` and the description (or send Gitea's comma-separated keywords and intersect the results).
- When a term matches an owner exactly, include that owner's public ledgers (look up `uid`).
- Mobile then needs no change. Add parity tests across REST, GraphQL and MCP.

**Acceptance:** `crypto example` finds `open_ledger/crypto-example`, and `open_ledger` lists that owner's public ledgers, on all three surfaces.

## Dedupe

w23/019 covers argument bounds on the same endpoint. w21/244 is the drawer's local filter. Searched `.pm/**` for searchLedgers, repoSearch, owner_name and "multi-word".

Fixed in the ledger service (`GET /ledgers/search`), which REST, GraphQL and MCP all reach through backend-v2's `searchLedgers`, so all three surfaces change together without adapter edits. The query is read as words (`ledger-search.ts`): one word that names no owner goes to Gitea exactly as before; with several words, Gitea is asked about the longest (any ledger matching all words matches it), up to six pages of 50, and the rest are required in `owner/name` or the description with `-`, `_`, `/` and `.` read as breaks, then the matches are paged (`page`/`limit`) rather than Gitea's pages; a word that is a Gitea user or organization (`users/{name}`, looked up only for plausible names, and not when the caller pinned `uid`) also lists that owner's ledgers, after the name/description matches and deduplicated. Blank text is no search. So `crypto example` finds `open_ledger/crypto-example` and `open_ledger` lists the owner's ledgers (plus ledgers that merely mention it). Mobile needed no change. Tests: `ledger-search.test.ts` runs the real handler over HTTP against a fake Gitea (substring name/description search plus `uid`) for the two acceptance queries, an owner narrowed by a word, all-words, paging, single words unchanged, `uid` respected, blank query, plus the word helpers; five of the HTTP cases fail with the handler reverted. Deviations: the word search reads at most 300 candidates per source (the cap bounds a very broad word); the fake Gitea encodes the substring rule from the note, so the real Gitea was not queried here; no new REST/GraphQL/MCP parity test was added in backend-v2 because it forwards the query to this one endpoint unchanged.
