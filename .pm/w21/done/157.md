# A failed account deletion has already cancelled the paid subscription and unlinked the banks

**Severity:** moderate. If the ledger-service purge errors or times out, the deletion rolls back and the user stays signed in with their data, but their Stripe subscription is already cancelled and their Plaid links are already dead. Mobile only shows "Couldn't delete account". **Estimate:** 1 hour. Owner: backend-v2. A3: the irreversible external calls (cancel every active Stripe subscription, remove every Plaid item) run *before* the database transaction. The transaction includes the ledger service's `admin.deleteUser` Gitea purge, which throws on any non-2xx.

Code-level at `main` `f18be1458`. The ordering is certain from the code; a failure wasn't induced.

## Where (`backend-cluster/backend-v2/src/`)

- `features/auth/service/account-service.ts:317-386` (Stripe and Plaid side effects) versus `:389-401` (the transaction with `favaAdminApiClient.admin.deleteUser`)
- `backend-cluster/ledger/src/api/admin.ts:60-64` and `foundation/fava/Api.ts:3755` (throws on non-2xx)

## Fix

Purge the ledgers first, or make the purge idempotent and treat a 404 as already done. Commit the user deletion, then run the Stripe and Plaid cleanup after a successful commit, with retries or an outbox so a later failure doesn't leave a deleted user billed. Make a retried deletion succeed if the purge had already happened.

**Acceptance:**
- A unit test with `admin.deleteUser` rejecting leaves the subscription and Plaid items untouched.
- A retry after a lost purge response completes.

## Dedupe

w4/043 covers how mobile reports a failure. Searched `.pm/**` for "partial deletion", "cancel subscription" together with "account deletion", and plaid together with deleteAccount.

**Resolution (2026-10-21):** `deleteAccount` now purges the ledger user first, before cancelling Stripe subscriptions or removing Plaid items, then commits the database deletion. A failed purge therefore leaves billing, banks and rows untouched. The ledger service forwards Gitea's status, so an already-purged user (a retry after a lost response) answers 404, which counts as done, and the retry completes.

Tests: `account-service.test.ts` checks that a rejected purge calls neither `deleteSubscription` nor `removeItem` and deletes no rows, and that a 404 purge completes. `account-deletion-parity.test.ts` (REST and GraphQL) carries the new effect order, the failed-purge case and a retry-after-purge case. Its old expectations, with the purge last and inside the rollback, encoded the bug and were rewritten. Both suites fail with the change reverted.

Deviations: no post-commit outbox. A Stripe failure after a successful purge still aborts with the ledgers gone, and a retry completes. Not exercised against a real deletion.

**Production recheck 2026-10-21:** not exercised. Verifying needs a real account deletion and billing state, which the QA contract rules out. Covered by the backend-v2 service and parity tests only.
