# A posting-level `!` flag is dropped everywhere: the row, the detail screen and VoiceOver read the transaction as fully cleared

**Severity:** minor-to-moderate. A user who flags a single leg as unconfirmed (common when reconciling) gets no sign of it anywhere outside the collapsed raw source. **Estimate:** 30 minutes. Owner: mobile. A3: the payload carries `flag: "!"` on the posting, but mobile reads only the transaction's `flag`. A grep for `.flag` in `mobile/src` finds only transaction-level reads.

Reproduced natively on the iPhone 17e simulator (iOS 27.0) at `main` `562a1b8ef`, on the disposable QA ledger, which I restored to `f1a0b83c`. The fixture was `2026-08-30 * "QA PFLAG"`, with `! Expenses:Transport 8.00 USD` / `Assets:Cash -8.00 USD`.
- The Transactions row "QA PFLAG · -$8.00" has no "P" badge.
- The detail shows Money flow TO Expenses:Transport +$8.00 with no marker, and no Pending badge in the hero.

## Where

- `mobile/src/screens/transaction-detail-screen/selectors/select-transaction-detail.ts:120-141` (`selectPostingRows` ignores `p.flag`)
- `transaction-detail-screen.tsx:512` (`isPending` checks `entry.flag` only)
- `transactions-screen/entry-row/index.tsx:168`

## Fix

Show a "P" marker on flagged posting rows in Money flow, with a translated "pending" in the row's accessibility label. Show the list row's badge when the transaction *or any posting* is flagged `!`, matching the dashboard (w4/220).

**Acceptance:**
- In the fixture, the Transport posting shows the pending marker and the list row shows "P".
- VoiceOver reads "pending" on that posting.

## Dedupe

w3/330 is the CLI counterpart; w4/220 is the dashboard; w21/127 and w21/140 cover the transaction badge only. Searched `.pm/**` for "posting flag", p.flag and isPending.

**Note 2026-10-21 (from a Transactions-filter review):** the Pending filter chip matches only the transaction's own flag, as Fava does, not a `!` on a single posting. If this item's row badge starts reflecting posting-level `!`, the badge and the Pending filter will disagree. Decide both together.

**Resolution (2026-10-21):** in Money flow, `selectPostingRows` marks a posting whose own flag is `!` as `pending`, and `PostingRow` shows the amber "P" badge beside that leg's account, with ", pending" (translated) in its VoiceOver label.

Decision on the addendum: the list row's "P" badge and the Pending filter both stay on the transaction's own flag, as Fava does. The filter is server-side (`transactionSubtypes`, Fava semantics), and a badge that fired on posting flags would contradict it. So the acceptance's "list row shows P" for a posting-only flag is deliberately not met; the flag shows where the posting is. If the list badge should reflect posting flags, the filter must change with it, which is a product question for whoever owns the filter semantics.

Tests: `select-transaction-detail.test.ts` (fails with the change reverted). Not re-run natively.
