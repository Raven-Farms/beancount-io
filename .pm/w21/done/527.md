# Deleting a transaction from a detail stacked above another detail of the same entry: a quick Back still shows the deleted entry (w21/094 incomplete; w21/472 fixed only edit)

**Severity:** low. **Estimate:** 20 minutes. Owner: mobile. A3 (code-level at `main` `0b838cf02`; proven with the real `invalidateLedgerData`, `createRevisionCheck` and `ledgerRevisionVar`):
- `transaction-detail-screen.tsx:368-378` re-checks its entry only on focus, and only if `ledgerRevisionVar` moved.
- `invalidateLedgerData` bumps that revision in its `finally` (`invalidate-ledger.ts:197`), so only after every mounted query's refetch has finished.
- `runLedgerWrite` starts the invalidation and navigates back at once (`common/ledger-write.ts:127-129`).

So a Back within the refetch window (about 1–3 s with all tabs mounted) sees no change, and the later bump is never read. With one query answering in 800 ms, focus at +406 ms gave `revision=0, recheck=false`, and the invalidation settled at +807 ms with `revision=1` and no re-check.

Scenario (w21/094's fixture): Home ▸ QA STALEDEL (A) ▸ Money flow ▸ Expenses:Transport ▸ QA STALEDEL (B). On B: ⋯ ▸ Delete ▸ Delete, then tap Back immediately. A still shows the entry with Edit and ⋯ enabled, and Edit opens "Failed to load transaction".

Not run natively: driver taps take about 4 s each, so a sub-second Back can't be driven.

## Fix

Make the focus effect depend on `useReactiveVar(ledgerRevisionVar)`, or bump the revision before awaiting the refetches. Or, as w21/472 did for edit, re-read before returning.

**Acceptance:** in that scenario, A shows "This transaction was changed or removed." A test covers focus arriving before the invalidation settles.
