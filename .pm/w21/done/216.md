# Some server URLs pass validation but can never match the issuer: a Unicode domain, a trailing "?" or "#", or a trailing dot

**Severity:** minor. `https://beancount.io/?` is saved as a separate override that fails as "incompatible" and hides "Try an example". The same happens with `https://bücher.example/`, `https://host.example/beancount#` and `https://host.example./`. **Estimate:** 20 minutes. Owner: mobile. A3: validation checks that `search` and `hash` are *non-empty* rather than *present*, and doesn't convert the host to ASCII. Expo's `whatwg-url-minimum` polyfill drops punycode, so the host stays Unicode while the backend's issuer is `xn--bcher-kva.example`. The issuer comparison is a plain string compare.

Code-level at `main` `709af935d`. The reviewer ran the inputs through the app's actual URL polyfill in Node.

## Where

`mobile/src/common/server-url-validation.ts:33-59` and `mobile/src/common/oauth/discovery.ts:36-38`.

## Fix

Strip an empty `?` and `#` and a trailing dot during normalization. Convert IDN hosts to ASCII, or reject them with a clear message if no punycode support is available. Compare against the canonical form.

**Acceptance:** `https://beancount.io/?` normalizes to `https://beancount.io/` and counts as the default. An IDN host either connects or gets a clear message.

## Dedupe

w5/700 is CLI only. Searched `.pm/**` for punycode, xn--, IDN, "empty query" and "trailing dot".

Fixed in mobile: `validateServerUrl` now returns one canonical form per server. An empty `?` or `#` is dropped (a non-empty query or fragment is still rejected), so `https://beancount.io/?` is the default and `https://host.example/beancount#` is `https://host.example/beancount/`; a trailing dot on the host is dropped; and a Unicode host is written in ASCII (`asciiHost`: NFKC case-fold, then RFC 3492 punycode per label, with an own encoder because React Native's URL polyfill keeps the Unicode host while the backend's issuer is `xn--...`), so the issuer comparison in discovery matches. The host is spelled out only when it changed, which leaves IPv6 literals, ports and ASCII hosts as before. Tests: `server-url-normalization.test.ts` (empty markers, non-empty rejected, trailing dot with and without a port, eight IDN hosts checked against Node's own IDNA conversion, ASCII/IP/port untouched); they fail with the change reverted. Deviation: the encoder is exercised directly because Node's `URL` already converts hosts, so the polyfill path itself was not run on a device; IDNA2008 mapping beyond NFKC and lowercase (rare compatibility characters) is not implemented, such a host just fails discovery as before.
