# Home's budget panel never re-reads budget directives past the first 500 on pull to refresh or a return to the app (w21/397 follow-up)

**Severity:** minor (only ledgers with more than 500 budget directives). **Estimate:** 10 minutes. Owner: mobile. A3: in `mobile/src/screens/budget-screen/hooks/use-budget-groups.ts`, the effect that reads pages 2 and later depends only on `[client, ledgerId, firstPage, needsMore, attempt]` (~lines 67–98). The `refreshSignal` effect (~line 52) calls the raw `refetch()`, not `reload()`, so `attempt` never changes. When the first page comes back identical, `firstPage` keeps its identity, and the cached later pages are never re-read. The foreground refresh (w21/225) has the same gap.

Code-level at `main` `58d92cc9c`. The reviewer used a real `ApolloClient` with the app's default options and a server-shaped mock of 501 directives. Changing the oldest directive's amount on the server and calling `refetch()` gives "same object after refetch? true", with one emission, so the later pages aren't read again. Not exercised natively. The fix's own note ("a refetched first page reads them again") doesn't hold when page 1 is unchanged.

Steps: with 502 budget directives, the oldest being `2024-01-01 … Expenses:QaOldest 50.00 USD`, open Home, change that line to 60.00 elsewhere, and pull to refresh. The row still shows the 50.00-based target; the Budget page shows 60.

## Fix

Have the `refreshSignal` effect call `reload()` (which bumps `attempt`), or key the rest-page read on a refetch counter as well as `firstPage`.

**Acceptance:** after the steps, Home shows the 60.00-based target. A hook test covers refresh with an unchanged first page.

## Dedupe

Follow-up to w21/397 (done). Searched `.pm/**` for readBudgetPages and refreshSignal together with budget.

The previous pages stay attached to the first page they followed until the new ones land, so the panel does not blank meanwhile. Source-wiring tests pin the pull-to-refresh bump and the revision key and fail against the old hook.
