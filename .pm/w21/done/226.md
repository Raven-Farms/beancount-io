# Changing your username in Profile leaves the app on ledger ids that no longer exist: every card fails as FORBIDDEN, and per-ledger state is lost on the next launch

**Severity:** moderate. **Estimate:** 45 minutes. Owner: mobile, plus a backend check. A3: a ledger id is `owner/name`. Profile's username change calls `updateUsername` and then only refreshes the drawer's directory. `ledgerVar`, the Apollo cache, Recent accounts (`accountUsageVar`) and merchant recurring marks (`merchantRecurringOverridesVar`) all stay keyed by the old owner. The server renames the owner, and `ledger-access-check.ts` then throws `ForbiddenError` for every `old/…` id. `isLedgerGone` treats only `NOT_FOUND` as gone, so the guard never steps in.

Code-level at `main` `7e42f850e`, traced through mobile and backend-v2. Not exercised natively: renaming the QA account is a credential-adjacent change the QA contract rules out.

## Scenario

1. Signed in with `alice/home` selected: Settings → Profile, change the username to `alice2`, save.
2. Back on Home, pull to refresh or background and return. Every card shows "Showing cached numbers" or fails with FORBIDDEN.
3. New Transaction and edits are refused. The drawer lists `alice2/home` but doesn't mark it current.
4. On the next cold start, the splash clears the unknown selection (`splash-provider.tsx:133`) and the guard picks the alphabetically first ledger. That ledger's Recent accounts and merchant recurring marks are gone for good.

## Root cause

- `mobile/src/screens/profile/profile-screen.tsx:264-267`: `await updateUsername(...)`, then `void refreshLedgers()`.
- `mobile/src/common/graphql-error-codes.ts:29-30`: `isLedgerGone` matches `NOT_FOUND` only.
- `backend-cluster/backend-v2/src/features/ledger/utils/ledger-access-check.ts:74-84`: `getUserByUsername(oldOwner)` returns null, so the check throws `ForbiddenError("Forbidden - ledger owner does not exist")`.

## Fix

After a successful rename, rewrite `ledgerVar` and every per-ledger var key from `old/` to `new/`, then run a `file`-scope `invalidateLedgerData` (or reset the store). Separately, consider having the server return NOT_FOUND (or a redirect hint) for an owner that no longer exists, so every client's gone handling applies.

**Acceptance:**
- After a rename, Home loads the same ledger under its new id, with no FORBIDDEN.
- Recent accounts survive a relaunch.
- A unit test covers the key rewrite.

Fixed in mobile: after a successful username change, Profile now calls `renameLedgerOwner(oldUsername, newUsername)`, which rewrites the owner prefix (`alice/` to `alice2/`) in the selected ledger (`ledgerVar`), Recent accounts (`accountUsageVar`) and the merchant recurring marks (`merchantRecurringOverridesVar`), so the selection follows the renamed ledger, Home loads it under its new id without FORBIDDEN, and per-ledger state survives the next cold start instead of being dropped with the unknown selection. It then runs a `file`-scope `invalidateLedgerData` (drops everything read under the old ids and bumps the revision the budget panel listens to) before re-listing the directory. Ids under another owner (shared ledgers) and lookalike owners (`alice-co/`) are untouched (`renamedLedgerId`, `renameLedgerKeys`). Tests: `ledger-owner-rename.test.ts` covers the key rewrite and the wiring order; the wiring test fails with the Profile change reverted.
