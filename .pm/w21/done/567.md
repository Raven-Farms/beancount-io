# Server: pull requests refuse edits to *existing* files with legacy names ("aux.bean", "a:b.bean"), against w23/054's rule that only new paths are checked

**Severity:** low (MCP and REST agents). **Estimate:** 10 minutes. Owner: backend-v2. A3 (code-level at `main` `7bdc974f6`): `693b56898` (w23/054) added `assertPortableRepoPath` on every `change.path` in `gitea/pull-request/service/pull-request-service.ts:271`, *before* `:349-394` decide between update and create. The repo service correctly checks only `operation === "create"`, and w23/054's done note says existing files stay editable.

Scenario: a ledger with a legacy `aux.bean` (committed earlier, or pushed with git). `createPullRequest` with `changes: [{path: "aux.bean", content: "…"}]` returns `BAD_USER_INPUT` ("uses the Windows device name"), and no PR is opened. `updateLedgerFiles` can still edit the file. Not visible on mobile, which doesn't use PRs.

## Fix

Check portability only for paths the PR creates, after the update-or-create decision, with a parity test.

**Acceptance:** a PR updating an existing `aux.bean` succeeds, and one creating `aux.bean` is refused.

## Dedupe

None found. Searched `.pm/**` for assertPortableRepoPath together with pull-request, and "Windows device name".

**Resolved 2026-10-22** — `createPRFromPatch` checks every path for safety up front (traversal, `.git`) as before, and holds a path to the portable-name rule only when the change creates it, after reading whether the file exists on the new branch (a refusal there deletes the branch, as every later failure does); an existing `aux.bean` can be updated through a pull request, and creating it is refused. Cases in `pull-request-service.test.ts` (`backend-cluster/backend-v2`, full suite green); the service is shared by REST, GraphQL and MCP. A backend-v2 deploy carries it to production.
