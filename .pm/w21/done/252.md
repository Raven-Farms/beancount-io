# Edit Transaction in a CRLF file rewrites that entry with LF and inserts an extra blank line

**Severity:** minor. It silently rewrites the file and mixes line endings. **Estimate:** 30 minutes. Owner: ledger + mobile. A3: the server splits the file on `\n`, so the served slice keeps a `\r` on every line. CodeMirror normalises line endings and turns the trailing `\r` into a final `\n`. Edit Transaction saves `doc.toString()` unchanged, and `replaceSliceInFile` appends another `\n`. w21/062's `lineEndingOf` / `withLineEnding` is wired into the file editor only. The returned `newSha256sum` then hashes content that differs from the stored block, so a follow-up save conflicts.

Code-level at `main` `6a7949ccc`. A reviewer ran real `@codemirror/state` with verbatim copies of `splitIntoBlocks` / `replaceSliceInFile`:
- **Served slice:** `…"Produce"\r\n  Expenses:Food 12.00 USD\r\n  Assets:Cash\r`.
- **Saved:** `…\n  Assets:Cash\n`.
- **File after the save:** `…"Veg"\n  Expenses:Food…\n  Assets:Cash\n\n\r\n2026-08-31…`.

In an LF file, a user-typed trailing newline inserts a blank line the same way.

## Root cause

- `backend-cluster/ledger/src/foundation/rustledger/source-slice.ts:302` (split on `\n`) and `:750-762` (`replaceSliceInFile`).
- `backend-cluster/ledger/src/features/ledger/service/ledger-journal-service.ts:1035` (`newSha256sum`).
- `mobile/src/screens/edit-transaction-screen/edit-transaction-screen.tsx:176, 266-272`.

## Fix

- **Ledger service (preferred, covering every surface):** `replaceSliceInFile` reuses the replaced block's line ending and trims trailing newlines from the incoming slice. `newSha256sum` is computed from the block as stored.
- **Mobile:** strip `\r` and trailing newlines before seeding, and trim trailing newlines before saving.

**Acceptance:** editing the narration of an entry in a CRLF file leaves every line CRLF with no new blank line, and an immediate second save doesn't conflict. Unit tests cover CRLF and an LF file with a trailing newline.

## Dedupe

w21/062 (done) covered the file editor only, and noted the slice path wasn't checked. w21/191 covers narration `\r` in the serializer. Searched `.pm/**` for CRLF, replaceSliceInFile, lineEndingOf and edit-transaction.

Fixed in the ledger service (the note's preferred fix, which covers every surface that edits a source slice): `replaceSliceInFile` now keeps the replaced block's own line ending (CRLF if its first line ends that way) and trims trailing newlines from the incoming text before adding exactly one ending, so an edit in a CRLF file stays CRLF with no stray blank line, and a trailing newline typed into an LF file no longer inserts a blank line. The `newSha256sum` the update returns is computed from the block as stored, served the way a fresh read serves it (`normalizeSliceReplacement` + `servedSliceText`, where the split on `\n` leaves a CRLF block's last `\r`), and the line count used to resolve the new entry hash comes from the same stored text, so an immediate second save presents the checksum the server now holds and no longer conflicts. Tests in `source-slice.test.ts`: the CRLF edit (LF text with a trailing newline in, pure CRLF out, no blank line), the checksum equals the checksum of a re-split of the result, the LF-file trailing-newline case, and a mixed file using each block's own ending; the suite does not even compile with the two source files reverted. Deviations: the mobile half (stripping `\r` before seeding the editor and trimming a trailing newline before saving) was not done, since the server now normalises both and CodeMirror already normalises line endings; this intentionally departs from fava's byte-exact `update_source_slice` (which always appended one `\n`) only when the incoming text ends in newlines or the block is CRLF; an engine-level check that a full update against a CRLF ledger round-trips was not run beyond these unit-level checks.
