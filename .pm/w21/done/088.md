# Deleting the last file in a Files folder will strand the browser on "Failed to load" once w23/014's NOT_FOUND listing deploys

**Severity:** moderate, as a latent regression. The user sees the success toast and then an error screen that pull-to-refresh can't clear; the only way out is the breadcrumb ‹. **Estimate:** 30 minutes. Owner: mobile. A3: git keeps no empty folders, so deleting a folder's only file removes the folder. w23/014 (done, `a30d75423`) changed `getLedgerDirContent` to answer a missing directory with NOT_FOUND instead of `[]`. Mobile's file browser still refetches the same `dirPath` after a delete and treats that error as a load failure.

Checked natively on the iPhone 17e simulator (iOS 27.0) at `main` `d7a950d7f`, on the disposable QA ledger:
- Files → + → `qa-20261020/n` → Create file, then Back, then open `qa-20261020` and delete `n.bean`. Afterwards I confirmed the folder was gone.
- **Today** the list shows "No files · Create a ledger file here" because production still runs the pre-w23/014 listing. Through the API, `getLedgerDirContent(dirPath: "qa-20261020")` and `dirPath: "no-such-dir-xyz"` both return `[]`.
- Once `a30d75423` deploys, the same listing throws NOT_FOUND ("Directory 'qa-20261020' … not found"). The browser then renders `ListEmptyComponent` in its error form: offline icon, "Failed to load", "Pull down to try loading this folder again". Pull-to-refresh only toasts the same error (`onRefresh`).

## Root cause

- `mobile/src/screens/ledger-file-browser-screen/index.tsx:479` awaits `invalidateLedgerData(client, "file")` after the delete. That refetches the current `dirPath` query.
- `:597-608`: any query error renders "Failed to load". `:354-363` `onRefresh` re-runs the same failing query.
- `backend-cluster/backend-v2/src/features/ledger/utils/directory-listing.ts:33-39` throws `NotFoundError` for a named directory with no entries.

## Fix

After a successful delete, if the deleted entry was the folder's last row (`sorted.length === 1`), navigate to the parent `dirPath` before or instead of refetching. Separately, treat a NOT_FOUND on a non-root `dirPath` as "this folder no longer exists" and step up to the nearest existing parent, so a folder removed by another client is handled too.

**Acceptance:**
- Against a backend with `a30d75423`, deleting a folder's only file lands on the parent listing, with the folder gone and no error state.
- Deleting one of two files still refreshes in place.

## Dedupe

w21/079 is the stale sha after a delete; w4/248 is the dashboard's upload refresh. w23/014 is the server change itself and didn't touch mobile. Searched `.pm/**` for "last file", "only file", "empty folder", "empty directory", "no longer exists" and getLedgerDirContent.

**Resolved 2026-10-21** — Shipped in the commit that moved this note (`mobile`). The Files browser now steps up from a folder that no longer exists:
- After a successful delete that empties a non-root folder (`deleteEmptiesFolder`: the deleted row was its only one), it pops to the parent before refreshing, so no error state shows. Deleting one of two files still refreshes in place.
- A listing that answers NOT_FOUND below the root (`isFolderGone`) steps up to the parent too. This covers a folder removed by another client. A NOT_FOUND at the root is left to the ledger guard, and an offline error still shows "Failed to load".

`folder-gone.test.ts` covers both helpers and the browser wiring; the wiring check fails with the screen change reverted. Not checked natively against a backend running `a30d75423`, since production still returns `[]` for a missing folder.
