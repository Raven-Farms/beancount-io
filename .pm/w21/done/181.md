# Merchant detail stops after 500 text-search matches, so a merchant's older rows vanish under its own "3 transactions" header

**Severity:** minor-to-moderate. A merchant whose name is a substring of a busier one ("Ace" next to "Ace Deli", "Amazon" next to "Amazon Fresh") can show "No transactions matched this merchant exactly" under a header that counts 3. **Estimate:** 30 minutes. Owner: mobile. A3: the header and the Merchants row count by exact payee (BQL), but the rows come from a journal free-text filter on the payee, which matches payee, narration or comment as a substring, and are then narrowed to the exact payee. Auto-paging stops at `MAX_PAGES` (25 × 20 = 500 raw entries) with no "more" indicator.

Code-level at `main` `f518cd365`. A native fixture needs more than 500 entries, which is too large for the shared QA ledger.

## Scenario

"QA Ace" on 08-29, 08-30 and 08-31 (10.00 each), then 500 newer "QA Ace Deli" entries. The Merchants row reads "QA Ace · 3 transactions". The detail header reads "3 transactions · $30.00 · Aug 29 – Aug 31, 2026", and the list says "No transactions — No transactions matched this merchant exactly."

## Where

`mobile/src/screens/merchant-detail-screen/merchant-detail-screen.tsx:74, 288, 335, 414`, plus `backend-cluster/ledger/src/foundation/rustledger/directive-filter.ts:582-585` (substring match).

## Fix

Fetch rows with an exact-payee filter (a quoted, anchored payee expression, as the header's BQL uses) so paging only sees this merchant's entries. If a cap remains, show "Showing first N" with a way to load more.

**Acceptance:** the scenario lists all 3 rows. A merchant with more than 500 entries shows an explicit truncation notice.

## Dedupe

w21/093 (trailing whitespace) has a different cause, and the cap was noted earlier this run as not reproducible on the example ledger. Searched `.pm/**` for MAX_PAGES, "free-text" together with merchant, and "No transactions matched".

**Resolution (2026-10-21):** merchant detail pages its journal with `exactPayeeFilter(spellings)`: `payee:"^\s*(?:<spellings, regex-escaped>)\s*$"`, an anchored payee expression padded for trailing spaces, in place of a free-text match on the name. Longer payees and narrations ("QA Ace" among "QA Ace Deli") no longer enter the 500-entry paging, so the scenario lists all 3 rows. Checked on the ledger's real filter: it keeps "QA Ace" (and case variants, which `filterExactPayee` still narrows on the client) and drops "QA Ace Deli". Tests: `src/__tests__/filter-exact-payee.test.ts` (the wiring case fails with the screen reverted).

Deviation: a merchant with more than 500 exactly-matching entries still stops at the cap without a truncation notice. Not re-run natively.
