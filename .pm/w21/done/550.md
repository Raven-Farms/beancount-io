# Deleting a file with a stale sha returns `BAD_USER_INPUT` ("sha does not match …") on GraphQL, but `CONFLICT` on REST and MCP (w23/032 handled only 422)

**Severity:** minor (parity; mobile relies on matching the raw text). **Estimate:** 20 minutes. Owner: ledger and backend-v2. A3: GraphQL's delete (`backend-v2/src/features/ledger/workflow/ledger-workflow.ts:972-1011`) calls the ledger's single-file delete (`ledger/src/api/files.ts:358-372`). Gitea 1.24 answers a stale sha there with **400**, not 422. `ledger/src/server/error-middleware.ts:95` maps only 422 and 5xx to 409, and `backend-v2/src/foundation/fava/error-to-domain.ts:157-159` turns the 400 into `BAD_USER_INPUT`. REST (`files-handler.ts:173-197`, through `/change-files`) returns 409 `CONFLICT`, and MCP `deleteLedgerFiles` (`edit-ledger-files-tool.ts:199-207`) returns `CONFLICT`.

Production (2026-10-22, disposable ledger; probe file deleted, ledger identical to its snapshot): create `qa-20261020-parity.bean`, update it, then `deleteLedgerFile(sha: <old>)` returns `BAD_USER_INPUT` with "sha does not match [given: …, expected: …]". Mobile shows "changed elsewhere" only because w21/380 matches that text (fragile; see w21/387).

## Fix

Map the single-file delete's sha-mismatch 400 to 409 in the ledger service (or route GraphQL deletes through `/change-files`). Extend `write-conflict-parity.test.ts` to mock the single-file delete.

**Acceptance:** a stale-sha delete returns `CONFLICT` on all three surfaces, and the parity test fails without the fix.
