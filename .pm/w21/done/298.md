# A second app link that arrives while the first is opening is dropped, and the user lands on the first link's ledger

**Severity:** minor-to-moderate. **Estimate:** 20 minutes. Owner: mobile. A3: `useAppLinkHandler` ignores any link that arrives while another is in flight, and queues nothing. The second link has already cleared the pending slot, and `+native-intent` has already rewritten the route to it. The in-flight window covers the readability probe and navigator-ready wait, and with unsaved editor changes, the whole "Discard changes?" dialog, so it has no upper bound.

Code-level at `main` `10857997b`. A reviewer rendered the real hook with stubbed react-native, expo-linking and expo-router, and an 800 ms probe. Link A (`alice/books/journal`) arrived at t=87 ms and link B (`bob/taxes/journal`) at t=489 ms. Only `GetLedger alice/books` was requested, and at t=992 ms the app replaced to `/transactions` with `ledgerVar = alice/books`. B was never opened. Not driven natively: `simctl openurl` raises an alert the MCP can't accept.

## Root cause

`mobile/src/common/app-links/use-app-link-handler.ts:23, 29-30` (`handlingRef`), with `:62` (`routeIncomingAppLink`) and `open-app-link.ts:71-107`.

## Fix

Queue the latest target (last link wins), or cancel the in-flight open and restart with the newer one. Re-check the latest target before setting `ledgerVar` and replacing the route.

**Acceptance:** in the scenario above, the app ends on bob/taxes. A hook test covers it.

## Dedupe

w21/083 (stash while signed in) and w21/090 (unsaved edits on a cross-ledger link) are different causes. Searched `.pm/**` for handlingRef, "second link" and use-app-link-handler.

Fixed. `useAppLinkHandler` no longer drops a link that arrives while another is opening. The newest such link is queued (last wins) and a generation counter marks the in-flight one as superseded, so `openAppLinkTarget`'s existing `isCurrentSession()` checkpoints (after the readability probe, after the discard dialog, after the navigator-ready wait) end it as "aborted" without setting the ledger or navigating, and without opening its source URL in the browser if its probe fails; then the queued link runs. In the note's scenario (A at 87 ms, B at 489 ms, 800 ms probe) the app now ends on bob/taxes, with A never navigating; with several links queued only the newest runs. Links opened one after another behave as before. Deviation: if A is already showing the "Discard changes?" dialog when B arrives, B runs after A's dialog is answered (and may ask again), not while it is up, to avoid stacking two dialogs. Tests in `common/app-links/__tests__/second-link.test.ts` run the real hook under a minimal React (two fail with the hook reverted). Mobile gates and deadcode green; not driven with a real URL (the note's `simctl` limit).
