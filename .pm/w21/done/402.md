# A long search (over 256 characters once escaped) fails the whole Transactions list with "Failed to load transactions"

**Severity:** low. **Estimate:** 10 minutes. Owner: mobile. A3: the server refuses any filter pattern over 256 characters (`directive-filter.ts:64, 193-197`, `MAX_FILTER_PATTERN_LENGTH`). `plain-search-filter.ts:37` escapes first, so every `.`, `*`, `/` or `(` doubles in length. Under `tsx`, 129 dots give a 258-character pattern and `AdvancedFilterParseError`, and so do 257 × `x`. `transactions-screen.tsx:288` replaces the list with the error, and pull to refresh fails again until the box is cleared.

Code-level at `main` `aedab56ba`.

## Fix

Cap the escaped needle on the client, or set `maxLength` on the field. Alternatively, have the server treat an over-long pattern as no match.

**Acceptance:** pasting a 260-character memo into Search shows results or "no match", never a load failure.

## Dedupe

w21/361 is the same limit on merchant detail. Searched `.pm/**` for MAX_FILTER_PATTERN_LENGTH, "256" and "pattern exceeds".

Fixed. `toPlainSearchFilter` encodes the needle one character at a time and stops before the pattern would pass the ledger service's 256 characters, so a 260-character memo (or 130 dots, which double when escaped, or apostrophes, which grow fivefold now that they match their curly forms) is cut to the longest prefix that fits: the list shows the entries containing that prefix, or none, never "Failed to load transactions". Each character is encoded whole, so an escape is never cut in half; a text that fits is quoted exactly as before. Tests (`plain-search-filter.test.ts`: the pattern stays within 256 for plain, dotted, quote-heavy, mixed and metacharacter inputs, the cut pattern still matches the text and compiles, and a 256-character text is unchanged; two fail with the helper reverted). This helper is also Merchant detail's fallback (w21/361). Not run natively.
