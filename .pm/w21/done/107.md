# Create Ledger accepts free-text currency and "Books begin" with no check, shows raw server errors, and lets impossible dates like 2026-04-31 through

**Severity:** moderate. A typo dead-ends on Review with an English server message, and an impossible date is written into the new ledger. **Estimate:** 1 hour. Owner: mobile and backend-v2. A3: ADR021 says "An … unsupported currency, impossible date … fails the request; nothing is created." The server's date check is `DATE_PATTERN` plus `Date.parse`, and V8's `Date.parse` accepts `2026-04-31` and `2026-02-30` (verified in Node: 1777593600000, 1772409600000). The impossible date reaches `open` lines.

Code-level at `main` `cd02f5446`.

## Where

- **Mobile:** `mobile/src/screens/create-ledger-screen/create-ledger-screen.tsx:204-205` uses bare `z.string()` for `currency` and `historyStart`. The inputs are at `:569-604`, and the raw `errors.root` server text is shown at `:683-684`. The app ships `setup-currencies.json` (162 codes) but never validates against it.
- **Backend:** `backend-cluster/backend-v2/src/features/ledger/setup/build-ledger.ts:75-78`.

## Fix

- **Mobile:** use a currency picker or validation backed by `setup-currencies.json`, a date picker (the app already has one) or strict calendar validation, and localized messages for both.
- **Backend:** validate a real calendar date by round-tripping `YYYY-MM-DD` through UTC components, so REST, GraphQL and MCP all reject `2026-04-31`.

**Acceptance:**
- `US` and `2026-4-1` are rejected on step 2 with localized messages.
- `2026-04-31` is rejected by the client and by every API surface.
- Add backend unit tests for 02-30, 04-31 and 2024-02-29 (valid).

## Dedupe

w5/889 is the CLI's `0001-01-01` date; w5/878 is the CLI currency prompt; w4/134 is the dashboard date filter. Searched `.pm/**` for historyStart, "Books begin", "Unsupported operating currency", 04-31 and 02-30.

**Resolved 2026-10-21** — Shipped in the commit that moved this note (`backend-v2`, `mobile`).

**Backend:** `build-ledger.ts` now checks "Books begin" with `isCalendarDate`, which round-trips `YYYY-MM-DD` through UTC components instead of `Date.parse`. 2026-02-30, 2026-04-31 and 2025-02-29 are refused ("Invalid history start …") on every surface that builds a setup, and 2024-02-29 still builds. Unit tests in `build-ledger.test.ts` fail with the check reverted.

**Mobile:** the form schema validates currency against the shipped catalog (`isSetupCurrency`, the server's own `setup-currencies.json`) and "Books begin" as a real day or empty (`isHistoryStart`). Each field shows a localized message (new `createLedgerCurrencyInvalid` and `createLedgerHistoryStartInvalid`, 13 locales). `US` and `2026-4-1` are refused on the form step by w21/105's validate-all Next. Leaving the preset start resets an invalid currency or date to its default, so a hidden field can't hold an error. `setup-validation.test.ts` covers the validators and the field wiring, which fails with the screen change reverted.

No currency or date picker was added; the fields stay text with validation. backend-v2 typecheck, lint and 6414 tests pass. Not exercised natively.
