# The journal's account filter matches substrings, so filtering by `Assets:Cash` also returns `Assets:CashApp` (or any name containing it)

**Severity:** moderate. The Transactions filter says one account is applied while rows from other accounts appear. The same server filter backs REST, GraphQL and MCP `getLedgerJournal`. **Estimate:** 1 hour. Owner: ledger. A3: the hosted ledger service ports Fava's account filter, a case-insensitive regex substring or a whole component anywhere in the name. Mobile's picker sends an exact account name and expects that account plus its children (w21/036). The CLI already fixed the same filter with anchored matching (w5/292, w5/616); the hosted service didn't.

Verified through the API at `main` `650ce6f72` against the disposable QA ledger (read-only): `getLedgerJournal(query: {account, directiveTypes: ["Transaction"]})`
- `"Assets:Cash"` gives total 5.
- **`"Assets:Cas"` gives total 5.** No such account exists.
- `"Bank:Check"` gives total 9 (Checking's rows).
- `"Food"` and `"Expenses:Food"` both give 6.

So a ledger with `Assets:Cash` and `Assets:CashApp` gets both accounts' rows under the mobile filter "Assets:Cash". `Expenses:Transport` also matches `Expenses:TransportFees` and `Assets:Reimbursable:Expenses:Transport`.

## Root cause

- `backend-cluster/ledger/src/foundation/rustledger/directive-filter.ts:225-237` (`applyAccountFilter`) uses the helpers at `:166-174` and `:208-223`, which match a substring or regex.
- `mobile/src/screens/transactions-screen/filters/select-filter-query.ts:128-130` sends the picked name as-is.

## Fix

Port the CLI's anchored matching into `applyAccountFilter`: an exact account name matches itself and its children (`^<escaped>(:|$)`). Keep the explicit-regex behaviour only for values that look like regexes, if Fava compatibility for MCP callers matters, and document that choice. This one fix covers REST, GraphQL and MCP; mobile needs no change.

**Acceptance:**
- With `Assets:Cash` and `Assets:CashApp` fixtures, filtering by `Assets:Cash` returns only Cash rows.
- `Assets:Cas` returns 0, or is treated as a regex only by an explicit opt-in.
- Add parity tests on all three surfaces.

## Dedupe

The CLI items are w5/292, w5/616, w5/829, w5/502 and w3/379; w21/036 is the mobile picker. Searched `.pm/**` for CashApp, "prefix sibling", has_component, AccountFilter and applyAccountFilter.

**Resolved 2026-10-21** — Shipped in the commit that moved this note (`backend-cluster/ledger`). `applyAccountFilter` (`directive-filter.ts`) now anchors a plain account name: a value with no regex syntax matches that account, its children, or a whole run of components anywhere, case-insensitively as Fava does. `Assets:Cash` returns Cash and `Assets:Cash:Wallet` but not `Assets:CashApp`, and `Assets:Cas`, `Bank:Check` and `Expenses:Transport` (vs TransportFees) match nothing. `Food` still finds `Expenses:Food`. A value with regex syntax keeps Fava's unanchored search, so `^Assets:Cash` or `Food|Checking` behave as before; the 256-character pattern guard now covers both paths. The choice is documented on the function. This one filter backs REST, GraphQL and MCP journals, and mobile needs no change. `account-filter-anchored.test.ts` covers the note's cases and the pattern path, and three of its four cases fail with the change reverted. All 113 existing filter tests, Fava golden parity included, still pass. Ledger lint, typecheck, build and 1436 tests pass. Not added: per-surface parity tests in backend-v2, since the surfaces proxy this one service filter. The dashboard's filter box now gets anchored matching for plain names too.
