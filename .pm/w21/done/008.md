# An account created from a back-dated New Transaction opens today, so the transaction is refused

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A2: entering a past receipt with a new category is a normal first-week task. The app's own inline **Create** flow opens the account with today's date, then the same form refuses the transaction because that account "was not opened until" today. Mobile offers no way to fix an account's open date except the raw file editor.

Environment: `main` at `ab6f2adf7`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0), light, English, "today" = 2026-10-20. QA account on `https://beancount.io`, on the synthetic disposable ledger `mcp-agent-eval`. The created `open` was removed afterwards and the file restored byte-for-byte (sha256 checked, clean ledger check).

## Repro

1. Home → **+** → **Enter new transaction**. Set **Date** to **2026-08-25** and payee `qa-20261020-inline`.
2. Tap the second posting's account → Account Picker → search `Expenses:Qa-20261020-Snacks` → **Create "Expenses:Qa-20261020-Snacks"**.
3. Open Account appears prefilled (Expenses: / `Qa-20261020-Snacks`) with **Open date 2026-10-20**. Tap **Done**. The account is committed (`2026-10-20 open Expenses:Qa-20261020-Snacks USD`), and the form returns with it selected.
4. Enter `-7.00` on Assets:Bank:Checking and tap **Done**. Refused:

   > This would add an error to your ledger: Account Expenses:Qa-20261020-Snacks used on 2026-08-25 but not opened until 2026-10-20 (main.bean:92)

## Expected / actual

- **Expected:** when Open Account is reached from a dated entry form, its open date defaults to that form's date. The transaction then succeeds in one pass. The open date stays editable, and stays today when the form's date is in the future.
- **Actual:** the open date is always "now". The refusal (shown only as a 2-second toast, see `w21/001`) leaves the user with a committed, unusable account and no in-app path to re-date it.

## Root cause

- `mobile/src/screens/open-account-screen/push-open-account.ts:9-34`: the handoff carries only `prefill` and `prefillRoot`.
- `mobile/src/screens/open-account-screen/open-account-screen.tsx:239`: `const [date, setDate] = useState(() => new Date())`.
- `mobile/src/screens/account-picker-screen/account-picker-screen.tsx` (the Create row) calls `pushOpenAccount` without the entry's date, which the posting-picker caller in `multi-postings-transaction-screen.tsx` has in state.

## Fix

Add an optional `openDate` (`YYYY-MM-DD`) to `pushOpenAccount` and the route params. In the posting-picker path, pass the earlier of the transaction date and today, and have the account picker forward it when it pushes Open Account. In Open Account, validate the param (well-formed and not after today) and use it as the initial date. Otherwise keep `new Date()`. Accounts-tab **+** keeps today's default.

**Acceptance:** repeating the repro shows Open date **2026-08-25** in step 3, and step 4 saves. From the Accounts tab, Open Account still defaults to today. A malformed or future `openDate` param falls back to today. Unit tests cover the param validation and the picker forwarding the date.

---

**Resolved 2026-10-20** — `pushAccountPicker` takes an optional `entryDate`, and New Transaction's posting picker passes the form's date. The picker's Create row forwards it to `pushOpenAccount` as `openDate`. Open Account seeds its date with `initialOpenDate(openDate, now)`, which accepts a real `YYYY-MM-DD` on or before today and otherwise uses now. The field stays editable. Other callers pass nothing, so the Accounts tab **+**, budgets and filters keep today. Tests: `open-date.test.ts` (past, today, future, missing, malformed and impossible dates), the push helpers forwarding the date (`push-open-account.test.ts`, `push-account-picker.test.ts`), and the three-hop wiring (`create-account-open-date.test.ts`). Mobile gates pass: format, tsc, eslint, knip, and 2387 unit tests. The repro was not re-run on the simulator, and the parked `add-transaction-next` screen does not pass a date. Shipped in `d2bcf794c` (`mobile`).
