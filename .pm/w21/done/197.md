# Delete Transaction can be fired twice while the first is in flight; the repeat reports "couldn't delete" after the delete succeeded

**Severity:** minor. With no "Deleting…" feedback, a user repeats ⋯ → Delete → Delete. The first succeeds and pops the screen, and the second gets "not found" with an error haptic, toast and refusal dialog over the journal. **Estimate:** 10 minutes. Owner: mobile. A3: `handleDelete` has no in-flight check. `deleting` disables only the Edit pencil, not the ⋯ → Delete item, and the delete passes no loading message.

Code-level at `main` `7fa4c4682`.

## Where

- `mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx:337-375` (`handleDelete`), `:541-545` (the menu item) and `:562` (pencil disabled)
- `delete-transaction.ts:28-35` (no loading toast)

## Fix

Return early from `handleDelete` while `deleting`, disable the Delete menu item while it runs, and show a "Deleting…" toast.

**Acceptance:** with a 3 s delay, a second ⋯ → Delete during the first is ignored, and only "Deleted" appears.

## Dedupe

w21/079 (stale sha) and w21/094 (stale detail) are different causes. Searched `.pm/**` for "second delete", "delete twice", deleting and "Deleting…".

**Resolution (2026-10-21):** the detail screen's delete now runs through `createSingleFlight`, and `handleDelete` returns early while one is running. A second ⋯ → Delete during the first is ignored, and `deleting` (which disables the Edit pencil) covers the whole delete rather than only the mutation. The delete shows a "Deleting..." progress toast (`deleting`, 13 locales; `deleteTransaction` takes `messages.loading`), dismissed when it ends, so only "Deleted" remains. Tests: `transaction-detail-screen/__tests__/delete-transaction.test.ts` (progress toast and the single-flight wiring, failing with the screen reverted); the session-end cases now ignore the progress toast. Deviation: the menu item is guarded, not visibly disabled, since the shared menu item has no disabled state. Not exercised with a 3 s delay.
