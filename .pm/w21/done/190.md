# Mobile can't add any transaction on a ledger whose currency isn't exactly three uppercase letters (USDC, MUSD, VBTLX, A1B)

**Severity:** major for affected ledgers. Every save from New Transaction (and quick add) is refused with `postings[0].units.number "11.11 MUSD" is not a decimal number`. Crypto, fund-share and custom currencies are common in Beancount, and the public minimax ledger uses MUSD. **Estimate:** 20 minutes. Owner: backend-v2. A3: the legacy `addEntries` workflow parses the mobile amount string with `/^(-?[\d,.]+)\s+([A-Z]{3})$/`. Anything else falls back to number = the whole string and currency = "USD", which the entry service rejects.

Verified through the API at `main` `e65b694f0` against production. The GraphQL `addEntries` mutation mobile uses, with postings `Expenses:Transport "1.00 USDC"` / `Assets:Cash "-1.00 USDC"`, returned **BAD_USER_INPUT `entry 0: postings[0].units.number "1.00 USDC" is not a decimal number`**. Nothing was written; the ledger stayed at `f1a0b83c`.

## Where

- `backend-cluster/backend-v2/src/features/ledger/workflow/legacy-entry-workflow.ts:33-48` (`parsePostingAmount`)
- `ledger-entry-service.ts:309` (the refusal)

## Fix

Parse the currency with Beancount's commodity grammar (`[A-Z][A-Z0-9'._-]{0,22}[A-Z0-9]`, or a single uppercase letter), split on the last whitespace, and never default to USD silently. Return a clear error if the amount truly has no currency.

**Acceptance:**
- `"11.11 MUSD"`, `"-11.11 USDC"`, `"5.00 VBTLX"` and `"3.00 A1B"` produce the right number and currency, and the entry is written.
- Add unit tests for these, plus 3-letter codes.

## Dedupe

w3/641 and w23/043 are other amount-validation items. Searched `.pm/**` for parsePostingAmount, `[A-Z]{3}` and "legacy addEntries currency".

**Resolution (2026-10-21):** the legacy `addEntries` amount parser moved to `legacy-posting-amount.ts` (`parsePostingAmount`) and reads the currency with Beancount's commodity grammar (`[A-Z]` or `[A-Z][A-Z0-9'._-]{0,22}[A-Z0-9]`) rather than exactly three uppercase letters. `11.11 MUSD`, `-11.11 USDC`, `5.00 VBTLX`, `3.00 A1B` and `1,000.25 EUR` each give the right number and currency. An amount with no currency is now a `BAD_USER_INPUT` ("must be a number followed by a currency, like "11.11 USD""), never silently USD. The resolver test that pinned the USD fallback was rewritten to expect the refusal. Tests: `workflow/__tests__/legacy-posting-amount.test.ts` and `ledger-legacy-resolver.test.ts`; they fail with the old three-letter pattern. Mobile always sends `<amount> <currency>`, so no client change. Needs a backend-v2 deploy; not run against a live ledger.

**Production recheck (2026-10-21):** not deployed yet. Production's GraphQL `addEntries` got `Expenses:Transport "1.00 USDC"` / `Assets:Cash "-1.00 USDC"` on the disposable QA ledger and still returned `BAD_USER_INPUT entry 0: postings[0].units.number "1.00 USDC" is not a decimal number`. Nothing was written; the ledger stayed at `f1a0b83c`. Mobile's New Transaction was not exercised. Needs another check after the backend-v2 deploy.
