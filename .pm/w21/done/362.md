# The splash's late ledger check can clear a ledger the user picked after launch

**Severity:** minor (a race on slow networks). **Estimate:** 10 minutes. Owner: mobile. A3: since w21/183 (`a0248f6ee`), `splash-provider.tsx:138-142` handles a check that arrives after the deadline with `if (shouldClearLedgerSelection(late)) ledgerVar(null)`. It never checks that `ledgerVar()` is still the ledger it validated. Simulated under `tsx` with the real `settleWithin`: the splash validates `old-ledger`, the user picks `new-ledger` from the drawer or via an app link, the late NOT_FOUND arrives, and `ledgerVar` becomes `null`. LedgerGuard then falls back to the first ledger.

Code-level at `main` `24df51bf0`. Not run natively.

## Fix

`if (ledgerVar() === ledger && shouldClearLedgerSelection(late)) ledgerVar(null);`

**Acceptance:** a late NOT_FOUND for the launch ledger never clears a ledger the user has since chosen.

## Dedupe

This is a follow-up to w21/183 (done). Searched `.pm/**` for settleWithin, LEDGER_CHECK_DEADLINE, "late check" and "ledgerVar(null)".

Fixed. The splash's late-check handler now clears the selection only if `ledgerVar()` still holds the ledger it validated (`ledgerVar() === ledger && shouldClearLedgerSelection(late)`), so a late NOT_FOUND for the launch ledger no longer wipes a ledger the user picked from the drawer or an app link in the meantime. The in-window failure path is unchanged (it runs before the user can interact). Test (`settle-within.test.ts`: the guard in the handler; fails with the splash provider reverted). Deviation: a source check, not a run of the real handler with a delayed rejection. Not run natively on a slow network.
