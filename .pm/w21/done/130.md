# A starred private ledger never appears in Starred, while Yours shows its star filled (REST, GraphQL and MCP alike)

**Severity:** moderate. A user's own private, starred ledger is missing from their Starred list; if it's their only star, the tab says "No starred ledgers". **Estimate:** 1 hour. Owner: backend-v2. A3: `getUserStarredRepos` lists stars with the Gitea **admin** client and no sudo. Gitea 1.24 includes private repos in `GET /users/{u}/starred` only when the requester is that user (`private := ctx.ContextUser.ID == ctx.Doer.ID`), and the admin never is. `isStarred` on Yours uses the user's own client (`userCurrentCheckStarring`), which sees private stars, so the two disagree.

Code-level at `main` `3c20a88e0`. Not exercised natively, because starring is an account write outside the disposable-ledger authorization.

## Where

- `backend-cluster/backend-v2/src/features/gitea/user-profile/service/user-profile-service.ts:426-431`
- `ledger-workflow.ts:1725-1735` (`isStarred` via the user client)
- Mobile consumes it at `mobile/src/screens/ledger-selection/use-discovery.ts:67-82`.
- GraphQL `getUserStarredRepos`, REST `/v1/social/starred-repositories` and the MCP `userStarredRepos` resource share the service. Collaborator access to private ledgers has the same gap.

## Fix

For the caller's own list, build it with the caller's credentials, using Gitea's `userCurrentListStarred` (it includes private repos), or with sudo as the user. Keep the anonymous public-profile behaviour (public only) for other users' lists. Apply this on all three surfaces in the same change, per the parity rule.

**Acceptance:**
- Starring one's own private ledger lists it under Starred on mobile and in the API.
- Another user's public profile still omits it.
- Add parity tests.

## Dedupe

Searched `.pm/**` for "starred private", getUserStarredRepos, userListStarred, getAdminApiClient and IncludePrivate.

**Resolution (2026-10-21):** `getUserStarredRepos` takes the viewer's user id; when the viewer's own Gitea login is the requested username (case-insensitive), the list is read with their own client via `userCurrentListStarred`, which includes private stars. Anyone else's list, an anonymous read, or a failed own-client lookup keeps the admin public read. GraphQL (`ctx.userId`), REST `/v1/social/starred-repositories` (`identity.userId`) and the MCP `social/starred-repositories` resource (`identity.userId`) all pass the viewer. Tests: service cases for the own list and someone else's, and a parity case in `social-list-parity.test.ts` that fails when any one surface's pass-through is reverted. Not exercised natively (starring is an account write); collaborator access to another user's private ledger is still public-only on their profile, as intended for someone else's list.
