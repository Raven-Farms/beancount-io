# A transaction detail opened cold (from a link) shows any load failure as "No entry context data available", with no Retry

**Severity:** moderate. **Estimate:** 15 minutes. Owner: mobile. A3: with no stashed list entry (a cold entry link routed straight to `/transaction-detail`), the detail comes only from the entry-context query. The `if (!entry)` early return renders the skeleton or `journalNoData`, and only NOT_FOUND gets its own state. A SERVICE_UNAVAILABLE, INTERNAL, timeout or dropped connection reads as a permanent dead end. w21/118's Retry lives inside `EntryContext`, which renders only after this early return.

Code-level at `main` `c3ec33b97`. Not driven natively: entry links need `simctl openurl`, whose alert the MCP can't accept.

## Root cause

`mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx:518-532` (the early return), `:340` (the query) and `:457` (`isEntryGone`).

## Fix

In the `!entry` branch, when `error && !isEntryGone(error)`, render `CardLoadFailure` with `onRetry={() => refetchContext()}`.

**Acceptance:** a cold link whose context read fails shows a failure with Retry, and a NOT_FOUND still shows the removed state. A source or unit check covers both.

## Dedupe

w21/013 (NOT_FOUND), w21/118 (done; Retry when an entry exists), w21/094 and w21/253 are different paths. Searched `.pm/**` for journalNoData and "No entry context data available".

Fixed. In the transaction detail's no-entry branch (a cold link with nothing stashed), a failed entry-context read now shows `CardLoadFailure` with Retry (`refetchContext()`) instead of "No entry context data available"; the skeleton while loading and the empty text for a read that returned nothing are unchanged, and a NOT_FOUND still returns earlier into the removed state. Source checks in `transaction-detail-screen/__tests__/cold-load-failure.test.ts` (the failure case fails with the screen reverted); the retry is not driven against a real link or network. Mobile gates and deadcode green.
