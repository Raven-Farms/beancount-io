# The first entry of an included file that starts with a UTF-8 byte-order mark can be opened but never saved or deleted ("modified elsewhere" forever)

**Severity:** minor. **Estimate:** 20 minutes. Owner: ledger. A3: the load and commit paths decode the file differently. The ledger load (`file-map-loader.ts:527`, `requireUtf8: true`) uses `TextDecoder`, which strips the BOM (`gitea-file-content.ts:54`). The commit path (`commit-ledger-files.ts:111`) keeps it, and on line 0 the BOM hides the date from `DATE_PREFIX` (`source-slice.ts:134`). So the entry is never found at commit time (`ledger-journal-service.ts:158`, NotFound).

Code-level at `main` `d1ce598bc`. The reviewer ran the real decode and update path in-process: `getContext` succeeds, then update and delete both fail with `NotFoundError Entry with ID '…' not found`. Control: the same file with a comment as line 1 updates fine and keeps the BOM.

Mobile shows NOT_FOUND as "Transaction was modified elsewhere. Reload and try again." Reload discards the draft, every later save fails the same way, and Delete says "Failed to delete transaction". Python `bean-check` 3.2.3 rejects such a file outright (`Invalid token: '\ufeff2024-03-05'`), while the hosted engine accepts and lists the entry.

Not run natively, because the disposable ledger has no BOM-prefixed include.

## Fix

Decode both paths the same way and write the BOM back on save, or make the block splitter ignore a leading BOM on line 0.

**Acceptance:** with `printf '\xEF\xBB\xBF2024-03-05 * "Shop" "Groceries"\n  Expenses:Food  10 USD\n  Assets:Bank\n' > 2024.bean` included from main, the entry can be edited and deleted, and the BOM is preserved.

## Dedupe

Only CSV, CLI and dashboard file-save BOM items exist (w3/done/248, w4/done/268). Searched `.pm/**` for BOM, FEFF and "byte order mark".

Fixed in the ledger service. The commit read (`readFileOrNull` in `commit-ledger-files.ts`) kept a leading UTF-8 byte-order mark while the ledger load, which decodes with `TextDecoder`, drops it; on line 0 the mark hid the first entry's date from the block splitter, so an entry opened from the load was never found at commit time (NOT_FOUND, shown on mobile as "modified elsewhere"). The commit read now strips the mark before handing the text to the transform, so the transform sees what the load saw, and writes it back when the file had one, so the file keeps its bytes (the note's acceptance asked for the BOM to be preserved). A transform that changes nothing still sends nothing, and a file without a mark is untouched. Tests (`commit-ledger-files-bom.test.ts`: the transform sees line 0 as the entry, an edit keeps exactly one mark, a no-op writes nothing, and a markless file is unchanged; the first fails with the commit path reverted). Ledger typecheck, lint, build and the full suite (1510) are green. Deviations: the test drives `commitLedgerFiles` with a stubbed Gitea client rather than the real include chain from the note's `printf` file; it takes effect when the ledger service is deployed. The hosted engine still accepts such a file where Python `bean-check` rejects it; that mismatch is not changed here.
