# A resumed Create Ledger draft can never repeat its first create: every Create fails with a generic error for up to 24 hours (requestId reused with a changed request)

**Severity:** moderate-to-major. **Estimate:** 30 minutes. Owner: mobile (plus backend-v2 messaging). A3: the draft keeps the `requestId` but blanks `openingAmount` (`common/create-ledger-draft.ts:45, 86-87`), and a draft from an earlier day rewrites `historyStart` to today. The server compares a hash of the whole request before checking whether the first attempt finished (`backend-v2/src/features/ledger/workflow/ledger-workflow.ts:595-612`), and a different hash is a `ValidationError` ("requestId was already used with a different creation request"), which mobile classifies as `other` (`create-ledger-screen.tsx:283-287, 413`). Under `tsx`, a Personal draft with Assets:Bank 1250.00 resumed the same day gives a different hash (setup accounts gone); a next-day resume differs even after re-typing the amount.

So when the create's response is lost (flaky network, or the app killed mid-create) but the ledger was made, every later Create shows "Couldn't create the ledger. Please try again.", even after renaming, until the 24-hour TTL or a sign-out. The new ledger is never selected. This breaks w21/053's "a retried create remains idempotent".

Code-level at `main` `9bd067834`. Not driven natively, because creating ledgers is out of bounds.

## Fix

Mint a new `requestId` whenever the request differs from the one last sent, by storing a hash of the last sent request rather than the amount. Treat a "requestId was already used" refusal as a reason to mint a new id, refresh the directory, and offer the existing ledger.

**Acceptance:** a resumed draft with a changed amount creates normally, and a lost-response retry lands on the ledger that was already made.

## Dedupe

w21/053, 066, 071 and 203, w23/008 and w4/320 differ. Searched `.pm/**` for requestId, "different creation request", resume and create-ledger-draft.

Resolved on the mobile side. The Create Ledger screen now keeps a creation `requestId` only while the request stays the same: it fingerprints what it sends (without the id), stores that fingerprint in the draft (`sentFingerprint`, a short hash, never the amount), and mints a new id and window whenever a create differs from the last one sent. A resumed draft with a retyped amount or a new Books begin therefore creates normally, and the identical retry still reuses the id and stays idempotent (w21/053). A "requestId was already used with a different creation request" refusal also mints a fresh id and refreshes the directory before showing the error, so the next Create can succeed. Tests cover the fingerprint, the keep/replace rule, the refusal match, the draft round trip and the screen's wiring (the wiring pin fails against the old screen).

Deviations: the "offer the existing ledger" step is not built (the refreshed directory shows it; nothing selects it), and the backend-v2 half (a clearer refusal than a generic ValidationError) is not changed — the app now recognises the existing wording, so a wording change there would need the match updated. Not driven natively, since creating ledgers is out of bounds.

Native recheck: not exercised. Reproducing it requires tapping Create (making a ledger) and then repeating a changed create, and this run doesn't create or delete ledgers on the QA account. It rests on the fingerprint and requestId tests.

Follow-up (audit, 2026-10-22): see w21/501 and 502.
