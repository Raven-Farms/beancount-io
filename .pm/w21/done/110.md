# The first New Transaction after a relaunch pre-fills accounts from the stale persisted cache, including an account that no longer exists

**Severity:** moderate. A quick entry (amount, then Done) right after opening the app posts to whatever account the persisted cache last ranked first. That account may since have been closed, renamed or deleted, and the server then refuses the save. **Estimate:** 45 minutes. Owner: mobile. A3: the form seeds its two postings once, from `useLedgerMeta`, as soon as `assets` is non-empty and `metaLoading` is false. After a cold start, that first value comes from the cache that `apollo3-cache-persist` restored. The network refresh lands later, and the one-shot seed never revisits it.

Reproduced natively on the iPhone 17e simulator (iOS 27.0) at `main` `95a4d19ec`, on the disposable QA ledger at `f1a0b83c`.
1. During the w21/103 probe, `Assets:Bank:Qa20261020Old` was the top-ranked asset. I then removed every fixture line, so the account no longer exists. The API's `ledgerMeta.accounts` no longer lists it.
2. I relaunched the app twice and browsed Home, Accounts, Transactions and Reports.
3. Home → + → Enter new transaction showed **FROM `Assets:Bank:Qa20261020Old`** and TO `Expenses:Transport`, the stale ranking.
4. Back, then + again: **FROM `Assets:Bank:Checking`** and TO `Expenses:Food:Groceries`, the current ranking.

The same lag showed in w21/103: the launch right after the ledger change still seeded the previous ranking.

## Root cause

`mobile/src/screens/multi-postings-transaction/multi-postings-transaction-screen.tsx:537-556` seeds when `!seeded && !metaLoading && assets.length > 0` and never re-seeds. `use-ledger-meta.ts:7` uses `cache-and-network` (with the global `nextFetchPolicy: "cache-first"`), and `common/apollo/cache-persist.ts` restores the previous session's `ledgerMeta`. The first render's `assets[0]` is therefore last session's ranking. Not proven: whether `loading` is already false because another mounted `useLedgerMeta` resolved from cache first.

## Fix

While the postings are still the untouched seed (`postings` deep-equal to `initialDraft.postings`), re-seed when fresh `ledgerMeta` arrives from the network (`networkStatus === ready` after a network result). Separately, never seed an account missing from the latest `ledgerMeta.accounts`, and apply w21/103's open-account check.

**Acceptance:**
- After removing the top-ranked account and cold-starting, the first New Transaction pre-fills the current top account.
- A user who has already edited a posting is never overwritten.
- Add a unit test for the re-seed guard.

## Dedupe

w21/103 covers closed accounts in the ranking, not cache staleness. w21/045 covers the picker. Searched `.pm/**` for ledgerMeta, "persisted cache", cache-persist, "stale account" and seed together with posting.

**Seen again 2026-10-21** (`main` `7a7b0be95`): the disposable ledger was rewritten with renamed roots (`Activos:` / `Gastos:`) for a w21/073 recheck, then restored to English roots outside the app. After a relaunch, New Transaction still seeded **Activos:Bank:Checking** and **Gastos:…Groceries**, accounts that no longer existed.

**Resolved 2026-10-21** — Shipped in the commit that moved this note (`mobile`). New Transaction's seeding no longer stops after the first seed. When the ledger's ranking, the close dates or the date change, it recomputes the seed. It replaces the postings only when `shouldReseed` (`postings-utils.ts`) agrees: the current postings still match the last seed by account and typed amount (the user hasn't touched them), and the new seed differs. The persisted cache's stale ranking is therefore replaced once the network's arrives, including an account since removed or the renamed-roots case in the "seen again" note. Edited postings are never overwritten, and an unchanged seed can't loop. Tests in `postings-utils.test.ts` cover the stale → fresh reseed, an edited account or amount kept, and no-op on an unchanged seed. The wiring check fails with the screen change reverted. A cold start after removing the top-ranked account was not re-run natively.
