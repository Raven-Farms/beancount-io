# Saving an edit that keeps the entry's hash (metadata, a comment, posting order) leaves the transaction and drops you on the journal

**Severity:** minor. **Estimate:** 15 minutes. Owner: mobile. A3: `resolveSaveExit` treats a reported hash equal to the request's as an old-server echo, and exits with `router.dismiss(2)`, which pops the detail as well. The ledger service's `hashEntry` excludes `meta` and sorts postings, so ordinary metadata edits keep the hash.

Code-level at `main` `6a7949ccc`. A reviewer ran the ledger service's `hashEntry` under Node: a transaction with and without `invoice: "INV-7"` (and with postings swapped) hashes to the same value (`eaf98218…`), and `resolveSaveExit(h, h)` returns `{ kind: "journal" }`. Not driven natively, because the editor needs free-text typing.

## Root cause

- `mobile/src/screens/edit-transaction-screen/save-exit.ts:17-29`.
- `edit-transaction-screen.tsx:350-361` (`router.dismiss(2)`).
- The service only echoes the old hash on a resolve failure (`ledger-journal-service.ts:1018-1030`).

## Fix

When the hash is unchanged, go `router.back()` to the detail. Since w21/094 it refetches on focus after any write, and shows the gone state if the entry really vanished.

**Acceptance:** adding `invoice: "INV-7"` and saving returns to the same transaction's detail, which shows the metadata. A unit case covers `resolveSaveExit(h, h)`.

## Dedupe

w21/028, 030 and 048 cover the editor round trip with a changed hash. Searched `.pm/**` for resolveSaveExit, "dismiss(2)", "same hash" and metadata-only.

Fixed in mobile: `resolveSaveExit` now tells three cases apart. A new hash re-keys the detail (`detail`, as before); the SAME hash reported means the entry kept its identity (the ledger's `hashEntry` omits `meta` and sorts postings, so a metadata edit, a comment or a reordered posting does not move it), and the editor goes back to the detail it was opened from (`unchanged`, `router.back()` with a `dismiss(2)` fallback when nothing is below), which refetches on focus after the write because the ledger revision moved, so adding `invoice: "INV-7"` and saving returns to the same transaction showing it; and no hash at all (a server that predates the field) still lands on the journal. Tests: `save-exit.test.ts` pins `resolveSaveExit(h, h)` as `unchanged` and the screen's branch; both fail with the two files reverted. Deviation and risk: an older server that echoes the request's hash even when the content hash really changed is now indistinguishable from an unchanged one, so after a content edit the user would return to a detail that shows the "changed or removed" state instead of landing on the journal; that is a self-hosted-version-skew case, and the screen offers its way back. No device run (the editor needs free-text typing).

**Recheck (2026-10-21): not exercised natively.** It needs typing a metadata line into the Edit Transaction code editor (a DOM CodeMirror view), which Expo MCP taps and the clipboard-paste route cannot place reliably on this simulator.
