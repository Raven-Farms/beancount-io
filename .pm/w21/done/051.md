# New ledger's "Books begin" defaults to the UTC date, so in the evening across the Americas the ledger starts tomorrow and the first entry made today is refused

**Severity:** major (a new user's first entry fails). **Estimate:** 20–30 minutes. Owner: mobile. A1/A2: Create Ledger → **Preset** pre-fills **Books begin** with `new Date().toISOString().slice(0, 10)`, which is the UTC calendar date. From 17:00 PDT (or 16:00 EST in winter) until midnight, that is **tomorrow**. Without a known opening balance, the server opens every preset account on `historyStart` itself, so the user's first transaction dated today posts to accounts that "aren't open yet" and is refused. East of UTC, the default is yesterday in the early morning, which is harmless.

Environment: `main` at `e14b83047`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0). The host and simulator were on America/Los_Angeles at **23:47 PDT on 2026-10-20**. No ledger was created: the form was inspected and abandoned.

## Repro (observed)

1. Drawer → **+ New** → Step 1 **Preset** → **Next**.
2. Step 2 reads **Books begin: 2026-10-21**, although the device's date is 2026-10-20. (New Transaction on the same device defaults to **2026-10-20**, via `getFormatDate`, which uses local time.)

## Consequence (from the server path)

`backend-cluster/backend-v2/src/features/ledger/setup/build-ledger.ts:75-192`: `openDate = hasKnownOpening ? dayBefore(historyStart) : historyStart`. With "Decide later" (no opening amount), every account is opened on 2026-10-21. An entry dated today, the app's default, then hits the ledger's inactive-account check, and the save shows "This would add an error to your ledger: … inactive account". With a known opening amount, the opening `balance` is dated tomorrow.

## Root cause

`mobile/src/screens/create-ledger-screen/create-ledger-screen.tsx:228`: `historyStart: new Date().toISOString().slice(0, 10)`. It is the only `toISOString().slice` date in mobile `src/`. Everything else uses `getFormatDate(new Date())` (local).

## Fix

Use `getFormatDate(new Date())` for the default. Add a unit test that pins the clock to 23:30 in a UTC−7 zone and asserts the local date.

## Same form, also fix

- **Preset's description is the Review step's text.** Step 1 shows **Preset: "This is exactly what will be created. Go back to change anything."**, because the option's hint key is `createLedgerReviewDescription` (`create-ledger-screen.tsx:415-418`). On the first step there is nothing to go back to, and it doesn't say what a preset is. Give it its own key, for example "Pick a ready-made chart for what you track", in all 13 locales.
- **Opening balance can't take a decimal comma** (code-level; the simulator's hardware keyboard hides the software keypad, so this wasn't seen natively). The field uses `keyboardType="decimal-pad"` (around line 633), whose separator follows the device region: "," in de/fr/es/nl/pt/ru/sk/uk/bg/ca, with no "." key. The schema (around line 198) accepts only `/^-?\d+(\.\d+)?$/`, so `1234,56` is "invalid amount" and a fractional opening balance can't be typed there. Reuse New Transaction's `parseExactAmount` (w21/031), which accepts `1,25`.

- **Opening account block is laid out outside its card's padding** (observed). On step 2, "Opening account" and "Decide later" sit at the card's edge (`styles.label` and `styles.hint` with no `styles.row` wrapper, around lines 591-594). Each one-line account option uses `templateRow`'s `minHeight: 72`, so the four options read as widely spaced orphans. "Decide later" looks like a heading but is the default choice, and the only way back to it is re-tapping the selected account. Wrap the label and hint in a padded row, use a list-row height, and make "Decide later" a selectable option.

**Acceptance:** at 23:30 local in America/Los_Angeles, Books begin shows the local date, and a preset ledger created with "Decide later" accepts a transaction dated today. Preset's step-1 description is its own copy. `1234,56` validates and is sent as `1234.56`.

## Dedupe

Searched `.pm/**` for Books begin, historyStart, toISOString and decimal-pad. w3/m53 defined the setup contract, and w5/889 covers a `0001-01-01` overflow. Neither covers the default date. Adjacent: the dashboard's `features/ledger-list/components/ledger-form.tsx:179` uses the same `toISOString().slice(0, 10)` default and should get the same fix (separate package).

**Resolved 2026-10-21** — Create Ledger (`mobile/src/screens/create-ledger-screen/`) changes:

- **Books begin** now defaults through `defaultHistoryStart`, which is `getFormatDate`, the device's local date, like New Transaction. At 23:30 in America/Los_Angeles it reads 2026-10-20, not the UTC 2026-10-21, so preset accounts open today and the first entry dated today posts.
- **Preset** on step 1 has its own description, `createLedgerStartPresetHint` ("Pick a ready-made chart of accounts for what you track…"), translated in all 13 locales, instead of the Review step's "This is exactly what will be created…".
- **Opening balance** goes through `openingAmountValue`, which reuses New Transaction's `parseExactAmount`, for both validation and the setup payload. `1234,56` validates and is sent as `1234.56`, and junk is still refused.
- **Opening account** now sits in a padded row inside the card. "Decide later" is a selectable option listed first, the default, alongside the accounts, and the options use a 48-pt list-row height instead of 72.

`setup-presets.test.ts` covers the Los Angeles evening (asserting the old UTC construction gives the wrong day), comma and dot amounts, empty and junk input, and the Preset hint wiring. `creation-refresh.test.ts`'s module mock gained the two helpers. Reverting the screen and helpers fails 4 cases. Not covered by a test: the layout change, which was not checked on the simulator. Native gates pass: format, lint, typecheck, `yarn test:unit` (2535 passed, 1 skipped). The dashboard's `ledger-form.tsx` has the same UTC default; it is a separate package and not in this workstream. Shipped in the commit that moved this note (`mobile`).
