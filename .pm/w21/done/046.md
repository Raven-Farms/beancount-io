# Merchants merges payee case variants in the list, but the drill-down shows only one variant, so its count, total and dates disagree and the other variant's entries are unreachable

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A2: imported ledgers often spell one merchant several ways ("WHOLE FOODS" from a bank CSV, "Whole Foods" typed by hand). The Merchants list deliberately merges case variants into one row and sums their counts. Tapping that row opens a detail screen filtered to the **exact** display variant, so it reports fewer transactions, a smaller total and a different date range than the row just tapped. The minority variant's transactions don't appear anywhere in Merchants.

Environment: `main` at `71dc3c909`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0). QA account, synthetic disposable ledger `mcp-agent-eval` with three Coffee entries: `2026-10-01 "QA CAFE" 4.00`, `2026-10-02 "QA CAFE" 5.00` and `2026-10-03 "Qa Cafe" 6.00` (restored byte-for-byte afterwards).

## Repro

1. Drawer → **Merchants**. The top row reads **QA CAFE · 3 transactions · Oct 3, 2026**. There is no separate "Qa Cafe" row, and search for it returns the same merged row.
2. Tap it. The detail reads **QA CAFE · 2 transactions · $9.00 · Oct 1, 2026 – Oct 2, 2026** and lists only v1 and v2.
3. The Oct 3 **Qa Cafe** $6.00 entry, which the row counted and dated, can't be reached from Merchants.

## Root cause

- `mobile/src/screens/merchants-screen/selectors/aggregate-payees.ts:80-160` (`aggregatePayees`) keys rows by `payee.toLowerCase()`, sums `transactionCount`, widens first/last dates across variants, and keeps the majority variant as the display name. The comment says tapping "opens the shown variant".
- `merchants-screen.tsx:234-237` navigates with `params: { payee: item.merchant.payee }`, which carries only that one spelling.
- The detail screen's queries are exact: `merchant-stats.ts` `buildMerchantMetaBql`/`buildMerchantCurrencyTotalsBql` (`bqlPayeeEquals`) and `filter-exact-payee.ts` (`trim() ===`). The recurrence and series selectors on that screen inherit the same subset.

## Fix

Make the drill-down cover what the row counted. Pass every variant spelling the row merged (for example a `variants` array kept on the aggregate), and have the detail match any of them: an OR of `bqlPayeeEquals` in the BQL, and a set lookup in `filterExactPayee`. Add a lowercase compare only if the BQL dialect supports it on both engines. Keep the display-name rule. Optionally show "also appears as Qa Cafe" under the header so the merge is visible. The other option, not merging in the list, would contradict the w1 merge decision, so it isn't recommended.

**Acceptance:** with the fixture above, the detail reads 3 transactions, $15.00 and Oct 1 – Oct 3, 2026, and lists all three entries. A payee with a single spelling is unchanged. Unit tests cover the aggregate's variants and the detail filter.

## Dedupe

Searched `.pm/**` for variant, case-insensitive, merge and merchant. The merge was introduced with the w1 merchant-grouping work (`86062503c`). w4/048, w2/042 and w21/006 touch merchants, but none covers the list/detail mismatch. No open item.
