# Reports keeps a "−$0.00 · 0%" row for a category that nets to zero, and the Sankey can draw phantom nodes, because monthly amounts are summed as floats and compared with exact zero

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A2: a refunded subscription or a returned purchase leaves a category at exactly zero for the period. Reports should drop it, as it drops every zero account. Instead the category shows as **"−$0.00 · 0%"**, a signed zero next to real spending, because the per-month amounts are added as JavaScript floats (`10.10 + 20.20 − 30.30 = −3.55e-15`) and the filter tests `!== 0`. The same residue reaches the cash-flow Sankey, which uses `> 0` and `< 0` with no tolerance.

Environment: `main` at `a6af6844a`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0). QA account, synthetic disposable ledger `mcp-agent-eval` with `Expenses:Entertainment:Streaming` +10.10 (Jul 5), +20.20 (Aug 5) and −30.30 (Sep 5) against Checking (restored byte-for-byte afterwards).

## Repro (observed)

Reports → **6M** (Mar–Sep). The Expenses card lists Housing:Rent, Food, Transport and then **"Entertainment:Streaming −$0.00 · 0%"** with an empty bar. The category's net for the window is exactly 0.

## Same cause, verified by running the shipped selectors under Node

- **Phantom Sankey node:** months of Shopping 0.10 / 0.20 / −0.30 give a tree value of `5.55e-17`, and `sankey-data.ts` emits a `cash-flow → Expenses:Shopping` link of `5.55e-17`. That is a labelled node with an invisible ribbon.
- **Fake Savings or Shortfall:** income −0.30 against expenses 0.10 + 0.20 gives `savings = 5.55e-17 > 0` (`sankey-data.ts:397-405`), so a "Savings" node appears for a month that broke exactly even.

## Root cause

- `mobile/src/screens/reports-screen/selectors/select-ranged-account-tree.ts:~133`: `sums.set(account, (sums.get(account) ?? 0) + value)` accumulates floats across months.
- `mobile/src/components/account-list/select-account-list.ts:~133`: `.filter((node) => node.value !== 0 || …)` is an exact comparison.
- `mobile/src/screens/reports-screen/selectors/sankey-data.ts:238` (`toRankedNodes` `value > 0`) and `:397-405` (`savings > 0` / `< 0`) use no tolerance. The budget code already treats half a cent as zero (w4/130).

## Fix

Sum per-account amounts in exact decimal (the scaled-integer helpers from w3/m34) or round each sum to the currency's display precision before filtering. Treat `|value| < 0.005` (or half a unit of the display scale) as zero in the tree filter, the Sankey node filter and the savings/shortfall test. Never render a signed zero ("−$0.00"). In `mobile/src/common/number-utils.ts`, `signedAmount` chooses `-` from `value < 0` before rounding to `digits`. Pick the sign from the rounded value, so every formatter in the app is protected, not just Reports.

**Acceptance:** the fixture above shows no Streaming row in 6M, a month whose income equals its expenses draws neither Savings nor Shortfall, and the Sankey has no zero-width node. Unit tests feed 10.10 / 20.20 / −30.30 and 0.10 / 0.20 / −0.30 series through the tree and the Sankey.

## Dedupe

w21/039 (open) is the "0%" label for a *negative* category, a different defect (a real non-zero refund). w4/130 fixed the same round-off class for budget variance. Searched `.pm/**` for float, residue, −$0.00 and negative zero with mobile Reports. No item.

---

**Resolved 2026-10-21** — Three changes:

- `selectRangedAccountTree` strips float residue from every per-account window sum, roll-up and card total (`withoutResidue`: ten decimals, beyond any recorded scale, with -0 normalized). The 10.10 / 20.20 / −30.30 Streaming category nets to exactly 0, so the existing zero filter drops it from the breakdown.
- The cash-flow Sankey treats anything under half a cent as zero, as budget variance does (w4/130), in its depth extraction, its ranked-node filter and the Savings/Shortfall test. A break-even window draws neither, and there are no zero-width nodes.
- `signedAmount` (`common/number-utils.ts`), behind every signed money and units formatter, takes its "−" from the shown, rounded amount, so a residue can never print "−$0.00" anywhere in the app. Real negatives keep their sign, and -0.005 still rounds to -$0.01.

`float-residue.test.ts` feeds the 10.10 / 20.20 / −30.30 series through the ranged tree (only Rent remains) and a break-even 0.10 / 0.20 / −0.30 window through the tree and the Sankey (no Shopping node, no Savings or Shortfall, every link at least half a cent). It also checks residue formatting. Reverting the three files fails 3 cases. Native gates pass: format, lint, typecheck, `yarn test:unit` (2548 passed, 1 skipped). Not checked on the simulator. Shipped in the commit that moved this note (`mobile`).

**Native recheck 2026-10-21** — Passed on iPhone 17e (iOS 27.0), dev build 1.20261002.50, with Metro restarted `--clear` on `main` containing `613ce3516`.
