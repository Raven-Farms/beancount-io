# Mobile file editor silently corrupts non-UTF-8 files on save: "Café" becomes "Caf�" (mobile counterpart of w4/276)

**Severity:** major (data corruption). **Estimate:** 30–45 minutes. Owner: mobile. A2: ledgers imported from older tools or bank exports are sometimes Latin-1 or Windows-1252. w4/276 made the dashboard refuse lossy editing of files it can't decode faithfully. The mobile editor decodes every file as UTF-8, shows replacement characters without a warning, and writes them back. One unrelated edit and save permanently replaces every non-UTF-8 byte with `EF BF BD`.

Environment: `main` at `a2cab4a61`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0). QA account, synthetic disposable ledger `mcp-agent-eval`. The fixture file was created through the API and deleted afterwards. `main.bean` was untouched.

## Repro

1. Create `qa-20261020-latin1.bean` containing the bytes `; qa-20261020 Caf\xE9 latin-1 comment\n` (`é` as Latin-1 `E9`).
2. Files → open it. The editor shows **`Caf�`**. There is no warning or read-only notice, and Save is offered once anything changes.
3. Add a line `; qa added` → **Save**. The save succeeds.
4. `getLedgerFile` bytes:
   - before: `…43 61 66 **e9** 20 6c 61 74 69 6e…`
   - after: `…43 61 66 **ef bf bd** 20 6c 61 74 69 6e… 3b 20 71 61 20 61 64 64 65 64`

   The original `é` is lost. Offline, the shipped decoder round-trips `436166e90a` to `436166efbfbd0a`.

## Root cause

`mobile/src/common/ledger-file-content.ts`: `decodeLedgerFileContent` does `Buffer.from(base64).toString("utf8")`, which replaces invalid sequences with U+FFFD without failing, and `encodeLedgerFileContent` re-encodes the string as UTF-8. Nothing checks that decode→encode reproduces the original bytes.

## Fix

Mirror w4/276. After decoding, re-encode and compare with the original bytes, or decode with a fatal UTF-8 decoder. If they differ, open the file read-only with a notice ("This file isn't UTF-8 text; editing it here would change characters. Edit it on a computer.") and hide Save. Keep the existing UTF-8 BOM behaviour, which round-trips correctly. Apply the same guard anywhere else the app writes back file content it decoded.

**Acceptance:** the repro file opens read-only with the notice, and its bytes stay `…e9…`. UTF-8 files, including ones with a BOM and multibyte text, edit and save byte-exact. A unit test covers a Latin-1 byte, a valid UTF-8 multibyte string and a BOM file through decode→encode.

## Dedupe

Dashboard: w4/276 (done, "Refuse lossy text-file editing for unsupported byte encodings") and w4/278 (CSV decoding). Searched `.pm/**` for encoding, Latin-1, U+FFFD and lossy with mobile. No mobile item.

**Resolved 2026-10-21** — `isLosslessLedgerFileContent` (`mobile/src/common/ledger-file-content.ts`) decodes a base64 file as UTF-8, re-encodes it and compares bytes. The file editor runs it on the first load and on Reload. A file that doesn't round-trip, such as the repro's Latin-1 `é`, opens read-only: the editor is read-only, Save and the insert bar are hidden, and the banner reads "This file isn't UTF-8 text. Editing it here would change some of its characters, so it opens read-only. Edit it on a computer." The notice shows even beside the error banner, and the bytes are never written back. UTF-8 files, including BOM and multibyte text, edit exactly as before. The only other write of encoded content is the Files browser's new empty file, which decodes nothing. The new `ledgerEditorNotUtf8` key is translated in all 13 locales (locale parity passes). `ledger-file-content.test.ts` covers a Latin-1 byte (refused; shows the `436166efbfbd0a` it would have written), UTF-8 multibyte text and a BOM file round-tripping byte-exact, text-encoded content, and the editor's wiring at both load sites. `read-only-banner.test.ts` was updated for the new banner condition. Reverting the codec and editor fails 5 cases. Native gates pass: format, lint, typecheck, `yarn test:unit` (2499 passed, 1 skipped). Not checked on the simulator. Shipped in the commit that moved this note (`mobile`).
