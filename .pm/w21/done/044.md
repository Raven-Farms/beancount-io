# New Transaction's Done stays live while the save is in flight, so a second tap posts the entry twice

**Severity:** major (duplicate ledger writes). **Estimate:** 20–30 minutes. Owner: mobile. A2: the live add flow (Home/Transactions **+ → Enter new transaction**, and receipt capture) keeps **Done** enabled and tappable for the whole `addEntries` round trip. `handleSave` sets its only guard (`savedOutRef` / `saved`) *after* the write resolves, so every tap during the "Saving…" window sends another `addEntries`. A user who taps again because nothing seems to happen gets the same transaction written twice.

Environment: `main` at `3df1d765d`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0). QA account, synthetic disposable ledger `mcp-agent-eval` (the probe entry was removed afterwards and the ledger checked clean).

## Native evidence (in-flight window)

New Transaction with the prefilled Checking/Groceries postings and `-1.23`. Tap **Done** once, with a `simctl io screenshot` burst started at the same moment:

| t after the tap lands | screen |
| --- | --- |
| ~0 s | Done pressed |
| +0.4 s … +2.0 s | **"Saving…"** toast over the form. Done is still green/enabled, and the form and its fields stay interactive |
| +2.4 s … +3.1 s | toast gone, form still shown, Done still enabled |
| later | back on Home, one entry written |

So Done accepts input for about 3 s per save on this connection. Expo MCP taps take about 4 s each and serialize, so a second tap inside that window was **not** driven natively. The duplicate follows from the code path below.

## Root cause

`mobile/src/screens/multi-postings-transaction/multi-postings-transaction-screen.tsx`:

- `handleSave` (around line 585) returns early only on `savedOutRef.current`, which is set after `await confirmWrite(…)` resolves with `ok` (around line 626).
- `canSave = validationError === null && !saved` (line 555) ignores the pending write. The header `Pressable` (around line 661) has no `disabled` prop, only `accessibilityState`.
- `runLedgerWrite` (`src/common/ledger-write.ts`) shows a non-blocking loading toast and has no in-flight dedupe either.

Other write forms already guard this: Edit Transaction has `saveInFlightRef` (`edit-transaction-screen.tsx:222`), transaction delete disables on the mutation's `deleting`, and Add Budget and Open Account fold the mutation's `loading` into `canSubmit` and pass `disabled`. The parked `add-transaction-next-screen.tsx` has the same gap but is off every UI path.

## Fix

Add an in-flight ref that is set synchronously at the top of `handleSave`, before validation toasts and the `await`, and cleared on a non-ok outcome. Fold it into `canSave` (with `accessibilityState.busy`) and pass `disabled={!canSave}` to the header button. Mirror Edit Transaction's `saveInFlightRef` pattern so the two transaction forms match.

**Acceptance:** two `onPress` calls in the same tick, or during a held mutation, send exactly one `addEntries`. Done reads disabled/busy while saving. A failed save re-enables Done with the draft intact. A unit or render test holds the mutation promise and asserts one call after repeated presses.

## Dedupe

Searched `.pm/**` for double-tap, double-submit, duplicate save/transaction, in-flight and pending write with mobile. w1/032 and m26 disabled submit only **after** a committed save (stranded cold-link forms). w3/196 has an in-flight ref for file creation only. Dashboard w4/295 covers drafts during a pending Budget submit. No item covers concurrent New Transaction saves.

**Resolved 2026-10-21** — A new `createSingleFlight` (`mobile/src/common/single-flight.ts`) gate now wraps New Transaction's write (`multi-postings-transaction-screen.tsx`). It closes synchronously before the first `await`, so presses in the same tick or during the held `addEntries` run one write; any extra press returns without toasting or writing. It reopens when the write settles, so a failed save leaves Done live with the draft intact. Done is `disabled` while saving or after a save, and reads `busy` and disabled to VoiceOver while saving. **Deviation:** Done stays pressable on an invalid draft, because tapping it is how the form names the problem (the validation toast). So it isn't `disabled={!canSave}`; only its look and accessibility state reflect that. `single-flight.test.ts` holds the write's promise and asserts one call across a same-tick press and a press during the held write, the busy transitions, and that a rejected write reopens the gate. A source check pins the screen's wiring, because the runner can't render it; reverting the screen fails it. The parked `add-transaction-next-screen.tsx` is off every UI path and was left alone. Native gates pass: format, lint, typecheck, `yarn test:unit` (2510 passed, 1 skipped). Not driven natively with a real double tap. Shipped in the commit that moved this note (`mobile`).

**Native recheck 2026-10-21** — Passed on iPhone 17e (iOS 27.0), dev build 1.20261002.50, with Metro restarted `--clear` on `main` containing `ac1e1199a`. New Transaction with the prefilled Checking/Groceries postings and `-1.23` → one **Done** tap with a `simctl io screenshot` burst: while "Saving…" shows, **Done renders disabled (grey)**, and the ledger received exactly **one** entry (restored byte-for-byte afterwards). A true double-tap inside the window still can't be driven natively (Expo MCP taps take about 4 s and serialize), so the same-tick press relies on the shipped `createSingleFlight` unit tests.
