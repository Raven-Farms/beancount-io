# `createLedger`: REST and MCP enforce a 200-character title limit and `requestId` bounds that GraphQL doesn't, so an empty `requestId` silently disables idempotency on GraphQL

**Severity:** minor (parity rule, validation). A 201-character title is accepted by GraphQL and refused by REST and MCP. `requestId: ""` is refused by REST and MCP, but GraphQL accepts it and quietly turns idempotency off (`input.requestId && store`). **Estimate:** 20 minutes. Owner: backend-v2. A3: these limits live only in the REST Zod schema (shared by MCP), not in the setup builder or workflow that GraphQL also calls.

Code-level at `main` `afd7265e3`.

## Where (`backend-cluster/backend-v2/src/`)

- GraphQL: `…/ledger-resolver.types.ts:68` (`title?`) and `:233` (`requestId?`)
- REST: `…/lifecycle-handler.ts:29` (title max 200) and `:66` (`requestId` 1–200)
- MCP: `mcp-lifecycle.ts:21-22`
- Workflow: `ledger-workflow.ts:577`

## Fix

Move the title and `requestId` constraints into the shared builder or workflow validation, so all surfaces refuse the same inputs with the same code.

**Acceptance:** a 201-character title and `requestId: ""` are refused identically on GraphQL, REST and MCP. Add parity tests using `previewLedgerSetup`.

## Dedupe

Searched `.pm/**` for "requestId length", "setup.title", ledgerCreateInput and CreateLedgerInput.

Fixed in backend-v2: the 200-character title cap now lives in the shared setup builder (`previewLedgerSetup`, `SETUP_TITLE_MAX`), which GraphQL, REST and MCP all reach, and the `requestId` bounds (1-200, `CREATE_REQUEST_ID_MAX`) are enforced in `LedgerWorkflow.createLedger` before anything is created, so an empty `requestId` on GraphQL is a `ValidationError` instead of silently disabling idempotency. The REST/MCP Zod schema reuses the same constants. Tests: a workflow test (empty and 201-character `requestId`, 201-character title, nothing created) and a surfaces test (REST parse and builder both refuse 201, accept 200); the workflow and builder tests fail with the fix reverted. Deviation: REST and MCP still refuse these earlier, at Zod parse, so their error text differs from the workflow's; the inputs refused are now identical.
