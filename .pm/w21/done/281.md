# Receipt capture can prefill an account the ledger never opened, and the save writes it, leaving a "never opened" error

**Severity:** moderate. **Estimate:** 30 minutes. Owner: backend-v2 + mobile. A3: the server returns the model's suggested `sourceAccount` / `targetAccount` without checking them against the `openAccounts` it sent in the prompt, which only asks the model to use them "when possible". With an empty account list, the prompt's schema examples (`Expenses:Food:Groceries`, `Assets:Cash`) invite made-up names. On mobile, `isOpenOn` returns true for any account without a close date, including ones that don't exist. `validatePostings` checks only that an account is filled, and the write path appends unknown accounts as written.

Code-level at `main` `c612cae39`. Not exercised natively: a parse spends AI quota. A reviewer's Node run on a ledger holding only `Assets:Bank:Checking`, `Expenses:Dining` and a closed `Assets:OldCard`: `isOpenOn("Expenses:Food:Groceries", …)` and `isOpenOn("Assets:Cash", …)` both return `true`; only the closed account is rejected.

## Root cause

- `backend-cluster/backend-v2/src/features/llm/service/llm-service.ts:261-281` and `recommend-accounts/prompts.ts:21`.
- `mobile/src/screens/multi-postings-transaction/multi-postings-transaction-screen.tsx:553-557`.
- `mobile/src/common/account-close-dates.ts:34-35`.
- `postings-utils.ts:331`.

## Fix

- **Server (covers GraphQL, REST and MCP):** drop any suggestion not in `openAccounts`.
- **Mobile:** seed only accounts present in the ledger's list and open on the entry date, otherwise fall back to the defaults. Have `isOpenOn` (or a sibling) treat unknown accounts as not usable for postings.

**Acceptance:** a parse suggesting `Expenses:Food:Groceries` on that ledger prefills the default accounts, and the server response omits the unknown name. Unit tests cover both.

## Dedupe

w3/560 fixed the dashboard's sibling, and w21/229 (open date) and w21/103 (closed default) are related. Searched `.pm/**` for recommendAccounts, openAccounts, prefillSourceAccount, "never opened" and E1001.

Fixed on both sides. Server (backend-v2, so GraphQL, REST and MCP alike): `recommendAccounts` now drops a suggested `sourceAccount` / `targetAccount` that is not in the `openAccounts` list it was given (exact match; an empty list drops both), so the parse response omits an invented name such as `Expenses:Food:Groceries`. The response shape is unchanged, so no OpenAPI or parity change. Mobile: new `isSeedableOn` (declared by the ledger and open on the entry date) gates the receipt prefill, so an unknown suggestion falls back to the same default accounts a blank entry gets. `isSeedableOn` claims nothing when no accounts were read at all, so a failed read does not turn every account unknown. Tests: `llm/utils/__tests__/recommend-accounts.test.ts` (three cases fail with the filter reverted) and `isSeedableOn` cases in `account-close-dates.test.ts`; one source pin in `postings-utils.test.ts` updated to the new gate. Backend typecheck, lint (knip) and the full suite and mobile gates and deadcode are green. Not exercised: a real receipt parse (it spends AI quota). Left as is: a typed-in new account still writes as typed, which is the Create-account path.
