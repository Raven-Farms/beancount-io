# An entry with no cash posting reads "−6,760.00" in the list and "6,760.00" on its detail

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A2/A3: the public `open_ledger/*` ledgers are the app's shop window, and many of their entries are Income → Expenses statements with no Assets or Liabilities posting. The same entry carries a minus on Home and in Transactions, then loses it when opened.

Environment: `main` at `ab6f2adf7`, dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0), light, English. Public read-only ledger `open_ledger/adobe`, selected from Browse ledgers → Explore.

## Repro

1. Drawer → **Browse ledgers** → **Explore** → `open_ledger/adobe`.
2. Home → Recent Transactions: the first row, **Adobe Inc.** / "FY2026Q3 Income Statement", reads **`-6,760.00 MUSD`**.
3. Tap it. The detail hero reads **`6,760.00 MUSD`**, unsigned. Money flow lists `FROM Income:Revenue -6,760 MUSD` and six `TO` rows (Expenses:… and `Equity:Adjustments`), and no Assets or Liabilities posting.
4. Second instance, same ledger: the second Recent Transactions row, a generated `(Padding inserted for Balance of 203 MUSD for difference -42 MUSD)` entry dated 2026-08-27, reads **`-42.00 MUSD`** in the list and **`42.00 MUSD`** on its detail. Its only postings are `Equity:OtherComprehensiveIncome -42` → `Equity:Adjustments +42`.

## Expected / actual

- **Expected:** one entry, one headline. An entry with no balance-sheet posting has no in/out direction, so it should render unsigned and neutral in both places, just as `selectTransactionAmount` already treats a transfer between two cash accounts ("a transfer has no in/out direction at the transaction level, so the value stays zero and the amount renders unsigned").
- **Actual:** the row adds a sign and the hero doesn't. Worse, the row's sign is arbitrary: it is the sign of whichever posting is largest. A one-income → many-expenses statement reads `−`. A many-incomes → one-expense entry would read **`+` in green**, which the row code defines as "money in".

## Root cause

- `mobile/src/screens/transactions-screen/utils/transaction-display-utils.ts` (`selectTransactionAmount`, the final fallback after the cash-posting branch): with no Assets/Liabilities posting, it returns the largest posting's signed `value`.
- `mobile/src/screens/transactions-screen/entry-row/format-entry-row-amount.ts:17-21` signs every non-zero `value`. Its comment says it does so "the way the transaction detail hero adds it".
- `mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx:421-430` adds the minus only when `hasCashPosting`. `selectHeroAmount` (`select-transaction-detail.ts:53-57`) still prefixes `+` and colors green for a positive fallback value, so the hero is only half-neutral.

## Fix

Make "no balance-sheet posting" a directionless amount at the source: in `selectTransactionAmount`'s fallback, return the largest posting's magnitude with `value: 0`, as the transfer branch does. The row and the hero then both render it unsigned and neutral, and the `hasCashPosting` special case in the detail screen can go. Keep the cash-posting branch, mixed-trade handling and transfer rule unchanged.

**Acceptance:** on `open_ledger/adobe`, the Adobe Inc. FY2026Q3 Income Statement shows `6,760.00 MUSD`, unsigned and neutral, on Home, Transactions and its detail. A synthetic Income:A + Income:B → Expenses:C entry renders unsigned and neutral, not `+` green. Cash-backed entries (`-$23.50` FARMERS MARKET style) are unchanged. Unit tests in `transaction-display-utils` / `format-entry-row-amount` cover both no-cash shapes.

## Blast radius

`selectTransactionAmount` feeds `selectEntryRowAmount` (Home Recent Transactions, Transactions, account journals, merchant detail rows) and `selectHeroAmount` (transaction detail). Before changing merchant rows, check that the merchant header's signed Income/Expenses total (w2/041) and its rows still read coherently.
