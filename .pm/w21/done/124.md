# A holding bought in a non-operating currency is labelled with the wrong price basis: "at cost (no price)" when a cost-currency price exists, "priced" when only an operating-currency price exists

**Severity:** moderate. Home's Net Worth and Assets captions, the Accounts root caption and the valuation sheet tell the user to add a price that already exists. A user who follows that advice is shown a figure labelled as market value that is still at cost. **Estimate:** 1 hour. Owner: mobile. A3: the ledger values a lot at the price in its **cost currency** (`lot-inventory.ts:134-141`, `getRate(lot.currency, lot.costCurrency, date)`, else cost), with no multi-hop. Mobile decides "priced" vs "at cost, no price" by looking for a price against the **operating currency**. The m26 README writes down that assumption ("A pair matches in either direction with the operating currency").

Reproduced natively on the iPhone 17e simulator (iOS 27.0) at `main` `c26bdfe94`, on the disposable QA ledger (operating currency USD), which I restored byte-for-byte to `f1a0b83c`. The fixture `; qa-20261020-veur`:
- `commodity VEUR`, opened `Assets:Qa20261020Broker` and `Equity:Qa20261020Seed`
- `2026-08-03`: `10 VEUR {50.00 EUR}` against the seed, −500.00 EUR
- `2026-08-28 price VEUR 55.00 EUR`

Home → Net Worth caption: **"At market value · 1 at cost (no price) · 1 not in total"**. The backend has valued the lot at market (550 EUR) using the EUR price.

The reviewer ran the selector on the mirror case, with only `price VEUR 60.00 USD`. It puts VEUR in `priced` with a price date, while the backend values it at cost (500 EUR), so the warning disappears.

## Root cause

- `mobile/src/common/valuation.ts:289-316` `selectValuation` classifies holdings via the `priceDates` / `dateIndex` lookups (`:90-134`) against the operating currency.
- The backend side is `backend-cluster/ledger/src/foundation/rustledger/lot-inventory.ts:134-141`.

## Fix

Classify each holding by whether a price exists between its commodity and its **cost currency** on or before the valuation date, which is exactly the backend's rule. Holdings with no cost currency keep the current rule. Update the m26 README's wording.

**Acceptance:**
- With the fixture, the caption has no "at cost (no price)" entry, and the sheet lists VEUR as priced (Aug 28).
- With only a USD price, VEUR reads "at cost (no price)".
- Add selector unit tests for both.

## Dedupe

The m26 known follow-up is the header-vs-row figure, a different issue. Searched `.pm/**` for "cost currency", two-hop, multi-hop, atCostNoPrice and "no price".

**Resolved 2026-10-21** — Shipped in the commit that moved this note (`mobile`). `selectValuation` now classifies a converted holding the way the ledger values it (`lot-inventory.ts`): by a price against its cost currency, never hopping through another. The candidate cost currencies are those in the balance's cost map other than the holding itself; the operating currency is the fallback when there is no cost map. The latest price on or before the date across them decides, and the managed-feed match uses the same currency. The fixture (VEUR at 50 EUR, an EUR price on 28 Aug) is now priced (Aug 28) with no "at cost (no price)". With only a USD price it reads at cost, no price. A lot bought in USD behaves as before. New cases in `valuation.test.ts` fail with the change reverted, and all existing valuation tests pass. Limits: an account whose cost map mixes currencies can match a price in any of them, since per-commodity cost currencies aren't on the balance read. The m26 README in another workstream wasn't reworded. Not re-checked natively.
