# Amounts typed in Persian or Arabic-Indic digits are always refused in New Transaction

**Severity:** moderate for Persian users; the app ships an `fa` locale with right-to-left layout. **Estimate:** 15 minutes. Owner: mobile. A3: `parseExactAmount` matches only ASCII `\d` and `.` / `,`. It doesn't map U+06F0–06F9 (Persian), U+0660–0669 (Arabic-Indic), the Arabic decimal separator `٫` (U+066B) or full-width digits to ASCII first. Done shows "Use digits and one decimal point, like 1234.56".

Code-level at `main` `7e42f850e`. Run under Node, `parseExactAmount` returns `null` for `"۱۲٫۵۰"`, `"١٢٫٥٠"`, `"۱۲.۵۰"`, `"12٫50"` and `"１２.５"`. Not driven natively: whether the iOS decimal pad sends these digits depends on the active keyboard, and the simulator here has only an English hardware keyboard. Pasted text reaches the same parser.

## Root cause

`mobile/src/screens/multi-postings-transaction/postings-utils.ts:40-60`: the regexes test the raw string. The field uses `keyboardType="decimal-pad"` (`multi-postings-transaction-screen.tsx:396`).

## Fix

Before matching, map every Unicode decimal digit (`\p{Nd}`) to ASCII and `٫` to `.` (and the Arabic thousands separator `٬` to `,`). The ledger keeps ASCII amounts.

**Acceptance:** `parseExactAmount("۱۲٫۵۰")` returns `"12.50"`, and so do the Arabic-Indic and full-width forms. A unit test covers each.

## Dedupe

w21/192 is Open Account names in non-Latin scripts, and w1/done/110 the CLI's bulk import. Searched `.pm/**` for "Persian digit", Arabic-Indic, `۱` and parseExactAmount.

Fixed in mobile: `parseExactAmount` maps non-ASCII numerals to ASCII before it matches (`toAsciiNumerals`): the digits of Arabic-Indic, Persian (Extended Arabic-Indic), N'Ko, Devanagari, Bengali, Gurmukhi, Gujarati, Oriya, Tamil, Telugu, Kannada, Malayalam, Thai, Lao, Tibetan, Myanmar, Khmer, Mongolian and fullwidth forms become 0-9, the Arabic decimal separator `٫` and the fullwidth period become `.`, and the Arabic thousands separator `٬` and fullwidth comma become `,`. `۱۲٫۵۰`, `١٢٫٥٠`, `۱۲.۵۰`, `12٫50` and `１２.５` now parse as 12.50 (12.5), a sign and Arabic thousands grouping carry through (`۱٬۲۳۴٫۵۰` gives 1234.50), and the field still shows what was typed while the ledger gets ASCII. Junk in any script is still refused. Tests: three cases in `postings-utils.test.ts` (each script form, sign/grouping, refusals); two fail with the change reverted. Deviation: a table of digit-zero code points (the ones in real use) rather than every `\p{Nd}` block, because Unicode digit blocks cannot be mapped without a table; a decimal pad's actual output for a Persian keyboard was not checked on a device.

**Native recheck (2026-10-21, iPhone 17e, Metro restarted with `--clear`):** fixed. In New Transaction I pasted `۱۲٫۵۰` (Persian digits with the Arabic decimal separator) into the first posting's amount. The field keeps the typed text, the auto leg reads **−12.50**, and Done is enabled. Nothing was saved; the draft was discarded. I did not try the iOS Persian decimal pad itself.
