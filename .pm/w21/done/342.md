# If iOS kills the editor's web view process, the draft silently resets and the last shortcut is inserted again at the top of the file

**Severity:** major when it happens (silent draft loss plus an unwanted edit). Confidence is medium-low; not reproduced. **Estimate:** 45 minutes. Owner: mobile. A3: Expo reloads a DOM component when its WebContent process dies. The reloaded page gets the first render's props (the original file text), and the screen keeps no copy of the draft. After the reload, `prevInsertSeq` restarts at null, so the next props update re-applies the last `insertSpec` at position 0 (for example `2026-10-21 ` at the top). The editor's revision counter also restarts at 0 while the screen's tracker keeps the old latest revision, so every later edit is dropped as stale and Save stays enabled.

Code-level at `main` `57826d105`: `node_modules/expo/src/dom/webview-wrapper.tsx:108, 129-131, 151`, `mobile/src/components/code-editor/code-editor.tsx:258, 425-447`, and `ledger-file-editor-screen/revision-tracker.ts:41`.

## Fix

- Have `onEdit` carry the text (debounced) so the screen can re-seed the draft after a reload.
- Give `insertSpec` an epoch, or clear it once applied.
- Have the editor report its revision base on mount so the tracker can reset.

**Acceptance:** a simulated web view reload (or a component remount in a test harness) keeps the draft, inserts nothing, and keeps dirty tracking working.

## Dedupe

Searched `.pm/**` for ContentProcessDidTerminate, prevInsertSeq, insertSpec and WebContent; nothing matched.

Fixed for the file editor, from Expo's source (the note's premise checked: `webview-wrapper.tsx` reloads the web view on `onContentProcessDidTerminate` and the reloaded page gets `initialPropsRef`, the first render's props). Not reproduced on a device, since a WebContent kill cannot be triggered here. The editor now announces itself with `onReady` on mount and reports its text with `onDraft` 400 ms after the last change; the screen keeps the latest text in a small recovery object (`createEditorRecovery`, fed by load, reload, save and draft reports). The first `onReady` is the ordinary mount; a second one is a restarted web view, and the screen puts the draft back under a new epoch, restarts the revision tracker with it (so edits are no longer dropped as stale, the failure that left Save enabled with nothing tracked) and hands the editor the saved text as `savedValue`, so "unsaved" is still measured against what was last saved. The accessory bar's insert is cleared once the editor reports the edit it made, so a reload no longer applies the last shortcut again at the top of the file. Tests: the recovery rules (`editor-recovery.test.ts`: first ready is a no-op, the draft comes back, the saved baseline follows saves and reloads) and source checks of the editor and screen wiring (all four wiring cases fail with the editor and screen reverted); the real web view restart is not simulated. Not covered: Edit Transaction mounts the same editor and does not pass the new optional props, so it keeps the old behaviour after a restart (a follow-up for that screen's own document state); and up to 400 ms of typing before a kill is lost.
