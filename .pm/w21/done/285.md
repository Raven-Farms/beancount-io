# A receipt date that isn't YYYY-MM-DD goes straight into New Transaction's date

**Severity:** minor. It needs the model to break its schema, which is unenforced. **Estimate:** 15 minutes. Owner: backend-v2 + mobile. A3: the parse schema's date is a plain `z.string()` with "YYYY-MM-DD" only in its description. `receiptDate` passes any non-empty string, and the form takes it as the date.

Code-level at `main` `c612cae39`. Run under Node: `receiptDate` returns `"2026/10/21"`, `"2026-10-21T14:32:00"`, `"21/10/2026"` and `"2026-1-5"` unchanged, and `parseFormatDate` gives an Invalid Date for them (what the date picker opens on). The closed-account check then compares the strings wrongly, and the save meets the backend's `^\d{4}-\d{2}-\d{2}$` check.

## Root cause

- `backend-cluster/backend-v2/src/features/llm/utils/call-llm.ts:28-32`.
- `mobile/src/common/receipt-utils.ts:9-10`.
- `multi-postings-transaction-screen.tsx:482`.

## Fix

- **Server:** `.regex(/^\d{4}-\d{2}-\d{2}$/)` plus a calendar check, normalising common forms.
- **Mobile:** `receiptDate` falls back to today unless the value is a valid ISO date.

**Acceptance:** each input above prefills today (or the normalised date), never an invalid one. Unit cases are added.

## Dedupe

Searched `.pm/**` for receiptDate, prefillDate and "Invalid Date". w21/069 (done) is the amount precision.

Fixed on both sides. Server (backend-v2, so GraphQL, REST and MCP alike): new `normalizeReceiptDate` is applied to the parsed date in `parseReceipt`. A valid `YYYY-MM-DD` passes; `2026/10/21`, `2026.10.21`, `2026-10-21T14:32:00` and `2026-1-5` are normalised to ISO; a day-first or month-first form (`21/10/2026`), an impossible day (`2026-02-30`, `2025-02-29`) or text becomes null, which the client already maps to today. Deviation: the zod schema is left a plain string, since a regex in a strict response format can break a provider (the schema's own comment explains why), so the check is at the DTO boundary, not in the schema. Mobile: `receiptDate` falls back to today unless the value is a real ISO day, so a server that predates the change or an unnormalised value still never opens the form on an Invalid Date. Tests: `normalize-receipt-date.test.ts` (backend) and a `receiptDate` case in `receipt-utils.test.ts` (fails with the fix reverted). Backend typecheck, lint (knip) and the llm suite (parity included) and mobile gates and deadcode are green. No API shape change.
