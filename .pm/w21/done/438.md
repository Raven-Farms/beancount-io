# Ledger setup validation messages are garbled ("Validation failed for Unsupported operating currency \"XX\": setup"): ValidationError's arguments are swapped

**Severity:** minor (on REST, GraphQL and MCP, and shown raw on mobile's Review). **Estimate:** 10 minutes. Owner: backend-v2. A3: `backend-v2/src/features/ledger/setup/build-ledger.ts:37-39` calls `new ValidationError(message, "setup")`, but the constructor is `(field, reason)`. The same swap is at `ledger-workflow.ts:550, 561, 610`. Under `tsx`, the real `previewLedgerSetup` with currency "XX" returned the message `Validation failed for Unsupported operating currency "XX": setup`, with `{field: "Unsupported operating currency \"XX\"", reason: "setup"}`. Mobile shows `previewError.message` on Review (`create-ledger-screen.tsx:783`), and REST and MCP `field` is the whole sentence.

Code-level at `main` `9bd067834`.

## Fix

Use `new ValidationError("setup", message)`, and flip the workflow calls the same way (`"requestId"`, `"setup"`), with a parity test on the error shape.

**Acceptance:** that preview returns `field: "setup"` with a readable reason on all three surfaces.

## Dedupe

Only w1/037 matched (the correct order on another path). Searched `.pm/**` for "Validation failed for", "ValidationError(message" and ": setup".

Resolved. The four ledger-setup `ValidationError` calls had `(message, field)` for a `(field, reason)` constructor: `build-ledger.ts`'s `fail` and the workflow's three checks (`setup`/`template` exclusive, `requestId` length, `requestId` reused with a changed request). They now pass `("setup", message)` and `("requestId", message)`, so a bad currency reads "Validation failed for setup: Unsupported operating currency …" with `field: "setup"` and the sentence as `reason`, on REST, GraphQL and MCP alike (all three build the response from the one domain error, so no per-surface change was needed). The tests now pin the message and metadata of each of the four; they fail against the old order, and the full backend-v2 suite (6,507 tests, including the surface-parity gate) passes with no OpenAPI drift. Mobile needs nothing: its reuse detection (w21/434) matches on the text, which is unchanged. Deviation: needs a backend-v2 deploy to take effect; the three surfaces were checked through the shared error and the existing parity gate, not by calling each live.
