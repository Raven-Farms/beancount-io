# In guest mode, one failed refresh blanks the whole example ledger, though its data is still on screen

**Severity:** moderate. A guest scrolling an example on a flaky connection loses the whole visit. **Estimate:** 30 minutes. Owner: mobile. A3: the guest Apollo client reports every failed read to the guest session. Any error that isn't FORBIDDEN, UNAUTHENTICATED or NOT_FOUND counts as a "connection" failure, and one failure flags the session. From then on, every tab and pushed screen shows the full-screen "Couldn't load this example. Check your connection…". The next foreground runs `retry()`, which remounts the session, clears the cache and drops filters and the open transaction. Signed in, the same blip keeps the rows under a stale banner (w21/081).

Code-level at `main` `3443fb319`. A reviewer ran `createGuestClient` with a stubbed fetch under Node. After a successful first journal load, a failing `fetchMore` (scroll) and `refetch` (pull to refresh) each sent `connection` to the session, while the cached rows were still in the cache.

## Root cause

- `mobile/src/common/guest/guest-client.ts:21-27` (classification) and `:79-80` (report every failure).
- `mobile/src/screens/examples/example-ledger-provider.tsx:52-66, 115, 173`.

## Fix

Keep the session-wide failure for access loss ("unavailable") only. Let connection errors reach each screen's existing stale banner or per-card retry, and never flag the session when the failing query already has cached data.

**Acceptance:** with the network dropped after a load, the guest journal keeps its rows under the stale banner. A client test covers the classification.

## Dedupe

w21/084 (done) is the foreground remount, and w21/151 is signed-in offline handling. Searched `.pm/**` for guestReadFailure, GuestReadContext, guestConnectionError and "stale banner" together with guest.

Fixed. The guest client now tracks whether anything has loaded (a result with no errors) and flags the session for a connection failure only before that; losing access (FORBIDDEN, UNAUTHENTICATED, NOT_FOUND) still always does. After a first successful load, a failed scroll, pull to refresh or foreground refetch no longer replaces the example with "Couldn't load this example" or triggers the remount that dropped filters and the open transaction; the rows stay in the cache and each screen's own stale banner or per-card retry handles the error, as signed in (w21/081). A first load that never arrives still shows the full-screen retry. Deviation: "never flag when the failing query already has cached data" is implemented session-wide (anything loaded), not per query: a failed scroll's query has different variables from the cached page, so a per-query test would still blank the example. Tests in `common/guest/__tests__/guest-client.test.ts` cover connection-after-load, first-load, and access loss after an error result (the first fails with `guest-client.ts` reverted). Mobile gates and deadcode green; no device run on a flaky connection.
