# Editing the description of an entry that already has an interpolation or lot-match error is refused as "would add an error", because the old error quotes the old description

**Severity:** major for affected entries. Users can't rename or re-date a broken entry, which is exactly when they need to edit it. The API docs promise that "errors the ledger already had never block". **Estimate:** 30 minutes. Owner: ledger. A3: `newLedgerErrors` (`backend-cluster/ledger/src/features/ledger/utils/new-ledger-errors.ts:15-17`) matches old errors to new ones by exact message text plus filename. The engine's interpolation and lot-matching errors end with `(date, "narration")`, so after an edit the old error reads as a new one. It is called from `ledger-journal-service.ts:492-513`.

**Verified against production (2026-10-21, `main` `d1ce598bc`), through the GraphQL mutation mobile's Edit Transaction uses:**
1. I appended this to the disposable QA ledger:
   ```
   2026-01-01 open Expenses:QaInterp
   2026-08-30 * "QA INTERP" "Groceries"
     Expenses:QaInterp
     Assets:Cash
   ```
   `getLedgerErrors` already listed `interpolation failed: cannot infer currency for posting to account Expenses:QaInterp (2026-08-30, "Groceries")`.
2. `updateLedgerEntrySourceSlice` sent the same slice with only the narration changed to `"Groceries edited"`.
3. It returned **`VALIDATION_FAILED`: "this edit would introduce 1 new bean-check error: interpolation failed: … (2026-08-30, \"Groceries edited\")"**.

The ledger was restored to `f1a0b83c`. Mobile shows this as "This would add an error to your ledger: …". Per the reviewer, `Ambiguous lot match for … (date, "narration")` behaves the same. Controls: existing "does not balance", "never opened", "invalid currency" and balance-assertion errors don't block.

## Fix

Normalize a trailing `\s\(\d{4}-\d{2}-\d{2}, ".*"\)$` before comparing. Better, compare the errors inside the edited block's line range with the old block's errors. Add regression tests for the interpolation and lot-match messages, including a date edit.

**Acceptance:** with the fixture, a narration-only or date-only edit saves, and an edit that adds a genuinely new error is still refused.

## Dedupe

w23/034 (backend-v2 counting an existing error as new when its line shifts) and w21/m1 differ. Searched `.pm/**` for interpolation, "existing error", pre-existing, "would add an error" and newLedgerErrors.

Fixed in the ledger service. `newLedgerErrors` now compares errors with the trailing entry tag removed: the engine ends interpolation and lot-match errors with `(date, "narration")`, so a narration or date edit rewrote the message and the error the ledger already had read as new, refusing the edit. The tag (` (YYYY-MM-DD, "…")` at the end of the message) is ignored for matching only; the per-error count is kept, so a second broken entry, a different message (another account) and the same message in another file all still count as introduced, and an edit that adds a genuinely new error is still refused. Tests (`new-ledger-errors.test.ts`: narration-only and date-only edits of an interpolation error, a lot-match error with a quoted narration, and the three still-refused cases; the first two fail with the source reverted). Ledger typecheck, lint, build and the full suite (1506) are green. Deviations: (1) this is the cheaper of the note's two options; comparing errors by the edited block's line range would also catch an edit that replaces one broken entry with another of the same message, which this treats as unchanged. (2) The test uses the message text recorded in the note rather than a live engine parse (a standalone WASM probe hung here). (3) It takes effect when the ledger service is deployed; not re-run against production with the QA fixture.
