# Futures currencies like "/ESZ24" and "/6E" are refused as "not a valid currency", though both engines accept them (w23/033)

**Severity:** low (traders, API and agents; mobile when the ledger already uses one). **Estimate:** 10 minutes. Owner: ledger. A3 (code-level at `main` `c1c3be649`; the validator and rustledger 0.24 were run on the same input): `entry-tokens.ts:26` requires a leading `[A-Z]`. rustledger and Beancount 3.2.3 accept `/ESZ24` (Beancount's `lexer.l` lists `/6J` and `/NQH21` as examples). This hits posting units and prices, `open` currencies, `commodity`, `price` and custom amounts on REST, GraphQL and MCP. On mobile, New Transaction is refused whenever the ledger already uses such a commodity.

## Fix

Use Beancount's currency grammar (an optional leading `/`).

**Acceptance:** `/ESZ24` passes and `/6.3` is still refused. Tests cover both.

## Dedupe

None found (searched all of `.pm/` for "/ESZ24", futures and "not a valid currency").

---

**Resolved 2026-10-22** — the ledger service's entry validator now takes a futures currency: a `/` followed by a letter, then Beancount's currency characters, ending in a letter or digit (`/ESZ24`, `/NQH21_QNEG21C13100`), in every place it checks a currency (posting units and prices, `open`, `commodity`, `price`, custom amounts) on REST, GraphQL and MCP. `/6.3` and `/E_` are still refused. Deviation from the note: `/6E` and `/6J` stay refused. They are valid Beancount, but the bundled `@rustledger/wasm` 0.24.0 reads `1 /6E` as one sixth of the currency `E`, so accepting them would store a wrong amount; they wait on an upstream fix. Tests: `entry-tokens.test.ts` (fails without the change) and a live check in `scripts/verify-rustledger.ts` that the validator accepts a futures currency exactly when the engine reads it back as written (`backend-cluster/ledger`). A ledger service deploy carries it to production.
