# Every server-discovery mismatch is reported as "does not expose the required Beancount.io API", with no hint of the right URL

**Severity:** minor-to-moderate. On docker-mac, `http://127.0.0.1:42601/` is rejected although the health check returns OK; only `http://localhost:42601/` connects. Pasting the README's "API" URL gets the same message. **Estimate:** 30 minutes. Owner: mobile. A3: every `OAuthDiscoveryError("incompatible")` (a resource mismatch, an `authorization_servers` mismatch, 503 `oauth_not_configured`, or not a Beancount server at all) collapses into one string. The canonical URL is in the response but never shown.

Code-level at `main` `709af935d`.

## Where (`mobile/src/`)

- `common/oauth/discovery.ts:148-163`
- `common/server-url.ts:64`
- `screens/…/server-settings-screen.tsx:140`
- `app/auth/welcome/index.tsx:94` (the Welcome copy)

## Fix

Distinguish the causes. On an issuer or resource mismatch, show "This server identifies as <canonical URL>. Use that address?" with a one-tap switch. Give "not configured for sign-in" its own message.

**Acceptance:** `http://127.0.0.1:42601/` on docker-mac offers `http://localhost:42601`. A non-Beancount URL keeps the generic message.

## Dedupe

w2/029 fixed malformed-JSON classification only. Searched `.pm/**` for serverConnectionIncompatible, "issuer mismatch", authorization_servers and 127.0.0.1.

Fixed in mobile: discovery failures now carry what the user can act on. `OAuthDiscoveryError` has an optional `detail`: `not_configured` (the backend's 503 `oauth_not_configured` while its signing keys are unset) or `mismatch` with a `canonicalUrl`, taken from the server's own claim (its single authorization server, else its resource without `/v1`, else the metadata issuer) and kept only when it is a valid server URL different from the one asked about, so a hostile or malformed claim yields no address. `testServerConnection` passes the detail through. Server settings shows "This server identifies as <url>." with a "Use that address" button (`use-canonical-server`) that fills the field and re-tests that address in one tap; "not set up for sign-in yet" has its own message. Welcome's sign-in failure has the same two outcomes (`not_configured`, `mismatch`). A server that is not Beancount.io, or one that names no usable address, keeps the generic "does not expose the required Beancount.io API". Four new strings in all 13 locales. Tests: discovery (mismatch via resource and via authorization server, rejected claims, 503 not-configured, 404 and other 503 stay generic) and the sign-in runner; they fail with the discovery change reverted. Deviations: the switch is a tap on a visible address, not automatic; no simulator run against docker-mac, so the 127.0.0.1 to localhost example is covered by the equivalent HTTPS fixtures only.
