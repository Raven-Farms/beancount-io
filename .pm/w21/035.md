# Offset paging repeats a row when an entry is added between pages, and the lists append it without dedupe

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A1: with agents and the CLI writing to the same ledger, a newer entry can land while a user scrolls Transactions. The next page then starts one row earlier, and the app appends the repeated entry, so the same transaction appears twice in a row. A removal elsewhere has the mirror effect: one entry is silently skipped.

Environment: `main` at `df735980a`. API reproduction against `https://beancount.io` on the synthetic disposable ledger `mcp-agent-eval` (restored byte-for-byte). It was not driven natively, because the list rows carry no testIDs and the automation can't scroll to trigger `onEndReached`.

## Repro (API, same queries the screens send)

1. `getLedgerJournal(offset: 0, limit: 5, directiveTypes: [Transaction])` returns FARMERS MARKET, CITY BUS, WHOLE FOODS, SUSHI PLACE, **BLUE BOTTLE**.
2. Append `2026-09-10 * "qa-20261020-new"` outside the app.
3. `getLedgerJournal(offset: 5, limit: 5)` returns **BLUE BOTTLE**, TRADER JOES, LANDLORD LLC, ACME CORP, VISA. BLUE BOTTLE is on both pages.

## Root cause

- `mobile/src/screens/transactions-screen/transactions-screen.tsx:164-192`: `loadMore` asks for `offset: transactions.length`, and `updateQuery` concatenates `[...prev, ...next]` with no identity check. `keyExtractor` at line 289 is `` `${entry_hash}-${index}` ``, so React never warns about the duplicate.
- The same offset-plus-concatenate pattern is in `account-detail-screen.tsx` (around line 299) and `merchant-detail-screen.tsx` (around line 352, keyed `` `${hash}:${index}` ``).

## Fix

In each `updateQuery`, append only entries whose `entry_hash` (plus a directive key for non-transactions) isn't already present. Keep `total` from the newest response. If the response contains an entry newer than `prev[0]` (the list moved), trigger a `refetch` from offset 0 so the user sees the new entry at the top rather than missing it. Then the key extractors can use the stable hash alone. A cursor (`before: <date,hash>`) API would remove the problem at the source, but that's a backend change; note it as follow-up.

**Acceptance:** a unit test feeds page 1 and a shifted page 2 (with one overlapping entry) through each screen's merge and asserts one copy. A test with a newer entry in page 2 asserts a refetch. The existing paging tests pass.

## Dedupe

Searched `.pm/**` for offset paging, duplicate rows, fetchMore and keyExtractor. The journal-paging items (w3/m13, w3/m30, w4/235) cover filters and the first-page limit, not mid-scroll shifts. w21/024 (foreground refetch) makes this window more common but is a separate fix.
