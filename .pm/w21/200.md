# Directory listing parity: REST and MCP drop `sha`, `size` and `lastCommitSha`, which GraphQL returns and mobile relies on

**Severity:** moderate (parity rule). A REST or MCP client can't show file sizes or do a sha-guarded delete or update from a listing without reading every file first. Mobile uses `size` and sends `entry.sha` as the optimistic lock on delete. **Estimate:** 1 hour. Owner: backend-v2. A3: `LedgerRepoService.listDirContent` projects Gitea's listing down to path, name and type. GraphQL reaches the ledger service separately and returns the full `LedgerFileContent`.

Verified through the API at `main` `afd7265e3` (read-only, disposable ledger):
- REST `GET /api-gateway/v1/ledgers/puncsky/mcp-agent-eval/files` → `[{"path":"main.bean","name":"main.bean","type":"file"}, …]`
- GraphQL `getLedgerDirContent` → `{name, path, type, size: 2817, sha: "f1a0b83c…", lastCommitSha: "494b3816…"}`

The MCP `listLedgerFiles` tool returns only path and type (no name), per the reviewer's read.

## Where (`backend-cluster/backend-v2/src/`)

- GraphQL: `…/ledger-resolver.query.ts:137` → `ledger-workflow.ts:1472-1507`
- REST: `…/files-handler.ts:52` (`dirEntrySchema`) and `:93-103`
- MCP: `…/list-ledger-files-tool.ts:21, 42`
- Shared: `ledger-repo-service.ts:34` (type) and `:196` (projection)

## Fix

Carry `size`, `sha` and `lastCommitSha` (and `name` on MCP) through `listDirContent` and all three adapters, and add them to the parity contract test.

**Acceptance:** all three surfaces return the same fields for the same directory, and a parity test pins it.
