# Deleting an account leaves the user's API keys in place and still accepted for identity checks

**Severity:** moderate (privacy and security). Mobile's Delete Account promises to "permanently delete all your data", but the account's API keys survive: their rows (name, scopes, last-used time) stay stored and still resolve to an identity on endpoints that don't look up the user row. Ledger operations fail, because those do look up the user. This is the same class of gap w0/054 closed for OAuth grants. **Estimate:** 30 minutes. Owner: backend-v2.

Code-level at `main` `f18be1458`. Not exercised, because account deletion is destructive.

## Where (`backend-cluster/backend-v2/src/`)

- `features/auth/service/account-service.ts:389-401`: the deletion transaction removes Plaid items, paid customers, sessions, OAuth grants and the user, but never calls `models.apiKey.deleteByUserId`. That method exists (`features/apikeys/data/api-key-model/postgres-impl.ts:110`) and has no production caller.
- `api_keys` has no foreign key to `users`, so nothing cascades.
- API-key identity resolution (`server/api/identity.ts:391-427`) checks only that the key exists, isn't revoked and hasn't expired. It doesn't check that the user still exists.

## Fix

Delete, or revoke, the user's API keys inside the deletion transaction, and make API-key identity resolution reject keys whose user no longer exists. Add the call to the `deleteAccount` tests.

**Acceptance:**
- After `deleteAccount`, no `api_keys` rows remain for the user.
- A key from a deleted account is rejected by every surface, including token introspection, as unauthenticated.
