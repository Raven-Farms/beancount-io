# A delete that finds the entry removed elsewhere still toasts "Failed to delete transaction" over the "changed or removed" screen

**Severity:** minor. **Estimate:** 10 minutes. Owner: mobile. A3: w21/250 made Delete recognise a stale entry, but `deleteTransaction` (`transaction-detail-screen/delete-transaction.ts:61-81`) learns of it only *after* `confirmWrite` (the shared `runLedgerWrite`) has already shown its own error toast for the failed write. For the "gone" case the code comment promises "no dialog, its own screen state explains", yet the user still sees a red **"Failed to delete transaction"** toast over the "This transaction was changed or removed…" screen. That reads as if the app broke, when the entry simply moved.

**Natively confirmed (2026-10-21, iPhone 17e, `main` `e0012e396`):**
1. I seeded `2026-10-21 * "QA STALEDEL" "probe"` and opened its detail.
2. Through the API I changed the narration to "probe2", then chose ⋯ → Delete → Delete.
3. The screen showed the changed-or-removed state plus the "Failed to delete transaction" toast.

The ledger was restored to `f1a0b83c`.

## Fix

Let `runLedgerWrite` take a `classifyFailure` (or `suppressFailureToast(error)`) hook, so a stale delete skips the generic toast, and keep the conflict dialog for the "changed" case.

**Acceptance:** with the repro above, only the changed-or-removed state shows, with no error toast. A genuine failure still toasts.
