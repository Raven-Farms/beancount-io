# Saving an emptied Edit Transaction deletes the entry, skips the delete confirmation, and says "Transaction saved"

**Severity:** moderate. Clearing the editor is a destructive write. It bypasses the Delete action's "This action cannot be undone" confirmation, and the success toast misreports what happened. **Estimate:** 30 minutes. Owner: mobile, plus a backend guard. A3: an empty or whitespace-only `newContent` is treated as an ordinary slice edit. The ledger service, matching Fava's `update_source_slice`, replaces the entry's lines with `"" + "\n"`, a blank line. No new entry hash comes back, so the app shows `editSuccess` and dismisses to the journal.

Code-level at `main` `9c7878b18`. I tried it natively on the disposable ledger (fixture `; qa-20261020-empty`, removed afterwards, ledger back at `f1a0b83c`), but the simulator runs with a hardware keyboard and the edit menu offers no Select All once a word is selected, so the automation couldn't empty the editor.

## Where

- `mobile/src/screens/edit-transaction-screen/edit-transaction-screen.tsx:240-357` has no content check before `newContent: content` (`:270`).
- `backend-cluster/backend-v2/src/features/ledger/…/ledger-journal-resolver.mutation.ts:80,166` and the REST handler (`z.string()`) accept an empty string.
- `backend-cluster/ledger/src/foundation/rustledger/source-slice.ts:750-763` `replaceSliceInFile`.

## Fix

- **Client:** when `content.trim() === ""`, disable Save, or route to the existing Delete confirmation and delete path.
- **Server:** reject a whitespace-only `newContent` with BAD_USER_INPUT ("use delete"), identically on REST, GraphQL and MCP.

**Acceptance:**
- Clearing the editor and tapping Save either can't save or shows the delete confirmation.
- The API returns BAD_USER_INPUT for `newContent: "  "` on all surfaces.
- Add tests on both sides.
