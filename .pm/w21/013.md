# A transaction deleted elsewhere still opens as if it exists, with "Error: Ledger resource not found" inside it

**Severity:** minor. **Estimate:** 30–45 minutes. Owner: mobile. A1/A2: once agents, the CLI and the web dashboard write to the same ledger, an entry the app is still showing can vanish underneath it. Tapping it today renders the full transaction as if nothing happened, offers to share a link to it, and buries the real situation in a raw server message inside the Entry Context card.

Environment: `main` at `1aadc33ea` (clean worktree served by Metro), dev build `io.beancount.ios` 1.20261002.50 on iPhone 17e (iOS 27.0), English. QA account on `https://beancount.io`, synthetic disposable ledger `mcp-agent-eval`. The fixture was restored byte-for-byte (sha256 checked, clean ledger check).

## Repro

1. With the Transactions tab open, append `2026-09-25 * "qa-20261020-fresh" …` outside the app and relaunch. The row appears (as w21/006 intends).
2. Remove that entry outside the app (restore the file) and keep the app running. Visit Settings, then return to **Transactions**. The mounted list still shows the row, which is expected: it revalidates per mount, not per focus.
3. Tap the row. The detail renders **qa-20261020-fresh −$30.00**, the date and both Money flow postings. The Entry Context card reads **"Error: Ledger resource not found"** in red. **⋯** still offers **Share link** and **Copy link**, both to an entry that no longer exists. Edit and Delete are hidden.

## Expected / actual

- **Expected:** when the entry context query answers not-found for this hash, the screen says the transaction is no longer in the ledger (it was changed or removed elsewhere). It offers to go back and refresh, hides the share and copy actions, and refetches the list it came from, so the stale row disappears.
- **Actual:** the stale cached entry renders as authoritative, the only signal is `journalError: <server message>`, and link actions stay live.

## Root cause

- `mobile/src/screens/transactions-screen/entry-context/index.tsx:249-256`: any `entryError` is rendered as `` `${t("journalError")}: ${entryError.message}` ``, the raw server text, with no not-found branch.
- `mobile/src/screens/transaction-detail-screen/transaction-detail-screen.tsx` renders the hero and postings from the entry passed in from the list cache. It already fetches the context (passed down as `contextData` / `contextError`) and derives write actions from it, but it does not treat a NOT_FOUND context as "entry gone". `src/common/graphql-error-codes.ts` provides the error-code helpers.

## Fix

In the detail screen, classify the context error. On NOT_FOUND, replace the body with the existing unavailable-detail state (the one shown for a missing deep-linked entry), with copy along the lines of "This transaction was changed or removed. Go back to see the current list." Clear the header actions, and trigger a refetch of the journal queries (ledger invalidation), so Transactions and Home drop the row. Keep the raw message only for genuinely unexpected errors, and translate the fallback.

**Acceptance:** repeating the repro shows the unavailable state, with no Share or Copy link. Going back shows the list without the removed row. A transient network error still shows a retryable error, not "removed". A test covers the NOT_FOUND branch.

## Dedupe

Searched `.pm/**` (including `done/`) for "resource not found", no-longer-exists and unavailable-detail. w4/045 (Edit Transaction concurrent-edit handling) covers a stale *save*. The retained-detail items ("Keep retained transaction details bound to their original ledger", "Clear retained transaction actions when the ledger route becomes unavailable") cover ledger switches. None covers an entry removed elsewhere.
