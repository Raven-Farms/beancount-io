# Refund or return receipts are always prefilled as a purchase

**Severity:** minor-to-moderate. Scanning a return slip opens New Transaction with money leaving the payment account, and the user must notice and flip the sign. **Estimate:** 30 minutes, plus a prompt change. Owner: mobile and backend-v2. A3: the parse prompt says "The TOTAL amount paid as a negative number (expense)" with no way to express a refund. The client then applies `Math.abs` ("Receipts are expenses"), and `createPrefilledPostings` always makes the source posting negative.

Code-level at `main` `f7bcaa7de`. Seeing the model's output on a real refund image needs one `parseReceipt` call (AI quota), which wasn't run. If the model returns a positive amount anyway, the account recommender switches to income-style accounts, so the result can read as Income rather than a reversed expense.

## Where

- `mobile/src/screens/receipt-capture-screen/receipt-capture-screen.tsx:142-144, 201` (`Math.abs`)
- `mobile/src/screens/multi-postings-transaction/postings-utils.ts:180-200`
- `backend-cluster/backend-v2/src/features/llm/utils/extract-receipt-from-file/prompts.ts:9`
- `recommend-accounts/prompts.ts:15`

## Fix

Add an `isRefund` (or signed-amount) field to the parse contract, keep the sign through the client, and prefill a refund as money returning to the payment account against the original expense category.

**Acceptance:** a refund receipt prefills the payment account as positive and the expense category as negative. A normal receipt is unchanged.

**Blocked 2026-10-21** — Still wanted, and the cause is confirmed at HEAD: the parse prompt asks for the total "as a negative number (expense)" with no way to express a refund, and the client applies `Math.abs` before `createPrefilledPostings`. The fix cannot be built and verified here:
- It changes what the model is asked and what it returns. A prompt change to the receipt parser cannot be evaluated without live `parseReceipt` calls on real return slips, which spend AI quota, and a regression there would misread ordinary receipts, the common case.
- It adds a field to the parse contract (`isRefund` or a signed amount). The mobile codegen reads the production schema, so the app cannot query a field that is not deployed yet; the backend field must ship and deploy first, then the app.
- Deriving the refund from the model's current sign is not safe: the note's own caveat is that the model may return a positive amount for an ordinary receipt too.

**Unblock:** the owner approves spending AI quota on a small evaluation set (a few refund slips and a few ordinary receipts) and confirms the contract shape (`isRefund` vs signed amount). Then backend-v2 ships the prompt and field (REST/GraphQL/MCP parity as applicable), the production schema updates, and mobile follows with the prefill. Who can clear it: the repository owner.
