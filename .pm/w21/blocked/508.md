# Mobile guesses that an entry is a plugin copy from its first line; read the ledger's `generated_from` instead (split from 443)

**Severity:** low (the guess already withholds Edit and Delete on copies). **Estimate:** 30 minutes. Owner: mobile. Split from w21/443, whose server half shipped: the ledger's entry context now carries `generated_from` (the source entry's hash for a copy that `amortize_over`, `forecast` or the pad pass generated, else null) on REST, GraphQL and MCP together.

Mobile does not read it yet. Until it does, `isPluginCopy` (`transaction-detail-screen/selectors/select-plugin-copy.ts`) infers a copy by comparing the entry's day and names with the first line of the slice it was answered with. That catches amortized copies, forecast occurrences and padding, and leaves an entry it cannot read alone, but it cannot say which entry the copy came from, and an unusual first line could withhold Edit and Delete from an ordinary entry.

## Fix

Add `generated_from` to `getLedgerEntryContext.graphql`, regenerate the client against the deployed schema, and decide a copy by `generated_from !== null` (keeping the first-line check only for a server that omits the field). Offer a link to the source entry, and say why Edit and Delete are missing.

**Acceptance:** with `plugin "fava.plugins.amortize_over"` and a 12-month entry, each copy's detail names or opens its source and offers no Edit or Delete; an ordinary entry keeps both.
