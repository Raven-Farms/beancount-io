# New Transaction writes every posting in the ledger's first operating currency, with no way to choose another

**Severity:** major for anyone with more than one currency. A EUR card, a JPY cash account or a brokerage account can't be used from the phone: the save is refused, or USD is silently written into the foreign-currency account. A currency exchange can't be entered at all. **Estimate:** 2–3 hours. Owner: mobile. A3: the form takes `currencies[0]` once and stamps it on every posting. It has no currency control and no price (`@` / `@@`) field.

Native observation on the iPhone 17e simulator (iOS 27.0) at `main` `7e42f850e`: posting rows show only an amount ("0.00", "-12.50"), with no currency shown or editable anywhere in the form. The payload was proven in Node by running `buildEntryInput` on a USD-operating ledger with `2026-01-01 open Assets:Bank:EUR EUR`. Picking that account and typing −12.50 gives `[{"account":"Assets:Bank:EUR","amount":"-12.50 USD"},{"account":"Expenses:Food","amount":"12.50 USD"}]`. The engine refuses a currency outside the account's `open` constraint (code-read).

## Root cause

- `mobile/src/screens/multi-postings-transaction/multi-postings-transaction-screen.tsx:469`: `const currency = currencies.length > 0 ? currencies[0] : "USD"`.
- `:619-623` pass it to `buildEntryInput`.
- `postings-utils.ts:350-361` append `opts.currency` to every posting.

## Fix

Give each posting a currency. Default it to the account's `open` constraint when it has exactly one, else the operating currency, and show it on the row with a picker. Balance each currency separately in the remainder. When exactly two currencies are present, offer a price on one leg (`@` per unit or `@@` total) so an exchange balances. Keep the single-currency flow unchanged.

**Acceptance:**
- Picking `Assets:Bank:EUR` shows EUR on that row, and the payload carries EUR.
- A EUR→USD exchange with `@` saves and balances.
- A unit test covers `buildEntryInput` with mixed currencies.

## Dedupe

w21/085 is Open Account's currency list, w21/190 the backend's three-letter currency regex, and w21/107 Create Ledger's free-text currency. None covers posting currency in New Transaction. Searched `.pm/**` for `currencies[0]`, "posting currency", "currency picker", and "New Transaction" together with currency or EUR.

---

**Blocked 2026-10-21** — Still wanted (confirmed at HEAD: `currency = currencies[0]` is stamped on every posting by `buildEntryInput`), but it cannot be built and verified here because three of its parts need things the app does not have today:
- **Per-account currency.** The note defaults a row to its account's `open` constraint. The `ledgerMeta` read the form uses returns account names only (`accounts: string[]`) and the ledger's currency list, so no client read carries an account's constraint currencies. A per-account read has to be chosen or added first.
- **A price on a leg.** The write the form uses is the legacy `addEntries`, whose posting input is `{ account, amount: "N CCY" }` with no price (`legacy-posting-amount.ts` accepts a number and a commodity only). An exchange with `@`/`@@` needs either a price field added to that input in backend-v2 (REST/GraphQL/MCP parity applies) or a move to the typed `addLedgerEntry` mutation, whose posting input has `units` and `price`. Mobile's generated client is built from the production schema, so it can use the change only after the backend deploys.
- **Design.** A per-row currency picker, per-currency balancing in the remainder row and auto-leg, and a price entry for the two-currency case change the main transaction form. They need an owner-approved layout (and the unit tests that go with the per-currency math), and none of it can be driven on a device from this run.

No partial change was shipped: a currency picker without the account default and the price would still leave exchanges impossible, and risks the single-currency flow every user depends on.

**Unblock:** the owner picks (1) where account constraint currencies come from, (2) the price path (legacy input field vs the typed mutation) and its deploy order, and (3) the form design. Then the work splits cleanly: backend field and deploy, then mobile in one change with the `buildEntryInput` mixed-currency unit tests. Who can clear it: the repository owner.
