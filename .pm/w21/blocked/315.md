# In-app commits are signed with the Gitea username and the account's real email, not the user's name or a noreply address

**Severity:** minor (display) to moderate (privacy). On public ledgers, anyone who can read the commits sees the author's signup email. **Estimate:** 45 minutes. Owner: backend-v2 + deploy. A3:
- Signup creates the Gitea user with only username, password and email, so `full_name` stays empty, and `updateProfile` stores first and last name in Postgres only.
- In-app commits are made without an explicit author, so Gitea signs them as that user: name = username (its fallback when `full_name` is empty), email = the account email.
- Gitea's keep-email-private default is off, and `deploy/` doesn't set it.

Verified against production on 2026-10-21: on the disposable QA ledger, the five latest commits' authors all carry a real (non-noreply) email, and each author name equals that email's local part. Notifications shows that username on every row ("‹username› · Oct 21, 2026"). Addresses are deliberately not recorded here.

## Root cause

- `backend-cluster/backend-v2/src/features/auth/service/auth-service.ts:274-280` (Gitea user creation).
- `account-service.ts:286-303` (`updateProfile`).
- `backend-cluster/ledger/src/features/ledger/operations/commit-ledger-files.ts:215-218` and `ledger/src/api/entries.ts:246-253` (commits without an author).
- `commits-service.ts:278-279` returns the name and email, and `listCommits` allows anonymous reads of public ledgers.

## Fix

- Set Gitea's `full_name` from first and last name at signup and in `updateProfile` (`adminEditUser`), and backfill existing users.
- Enable Gitea's default keep-email-private in the deploy config, and pass a noreply author on in-app commits.
- Optionally drop `email` from anonymous API responses. Git history itself also carries the email, so the deploy setting is the real fix.

**Acceptance:** a new in-app commit shows the user's name and a noreply email, and anonymous `listCommits` on a public ledger exposes no real email.

**Blocked 2026-10-21** — Still wanted (the root-cause lines are unchanged at HEAD: signup creates the Gitea user with no `full_name`, `updateProfile` stores names in Postgres only, and in-app commits carry no author), but the fix that actually closes the privacy problem is a production data and configuration change that cannot be built and verified from this repository:
- **The effective fix is Gitea's per-user "keep email private" plus a noreply address.** `DEFAULT_KEEP_EMAIL_PRIVATE` in `deploy/` applies to users created after it is set; every existing user, and so every commit made from now on by them, needs the flag flipped by an admin backfill against the live Gitea. That is a production operation, and what the Gitea admin API accepts for it (and whether API-made commits then use the placeholder address) has to be checked against the deployed Gitea version, which there is no instance here to do.
- **History keeps the old address.** Commits already in public ledgers carry the real email in git itself; removing it means rewriting history, which changes every commit sha that mobile, the dashboard and users' links point at. That is a product and privacy decision, not an implementation detail.
- **The noreply scheme is a decision.** Gitea's own placeholder (`<id>+<name>@noreply.<host>`), a project-owned domain, or an explicit author on every in-app commit (touching `commit-ledger-files.ts` and `entries.ts` in the ledger service as well) each lead to different addresses in history.
- The part that is safe alone, setting `full_name` at signup and in `updateProfile` with a backfill, would fix the display name on Notifications but not the privacy exposure, and shipping it as the whole fix would make the item look done.
No partial change was shipped.

Then the code is: `full_name` at signup and profile update, the deploy setting, and the author on in-app commits, with a unit test that a new commit's author carries the name and the noreply address.
