# Deleting a file that `main.bean` includes just says "Deleted", with no warning, though the ledger then breaks (missing include) or silently loses the file's entries (glob include)

**Severity:** minor (silent data loss from balances). **Estimate:** 45 minutes. Owner: backend-v2 and mobile. A3 (code-level at `main` `b1ba52fcd`): mobile's `ledger-file-browser-screen/index.tsx:588-651` (`confirmDelete`) and `:656-667` (the dialog) say only `Delete "jan.bean"? This cannot be undone.`. The server's delete (`ledger-workflow.ts:972-1011`) checks only `assertKeepsEntryPoint`, while its rename (`:1066-1150`) finds the `include` lines and globs that point at the file and refuses or rewrites them. The file editor warns after saving ("Saved, with a new ledger error"), but delete has no such check.

Scenario: `main.bean` has `include "books/2026/jan.bean"` and `include "books/2025/*.bean"`. Deleting `jan.bean` toasts "Deleted", and a missing-include error appears only on the bell. Deleting `books/2025/a.bean` produces no error at all, and its entries drop out of every balance.

Not run natively (it needs folder fixtures; this QA run keeps file writes minimal).

## Fix

On delete, find includes that reach the file (as rename does). Warn in the dialog ("main.bean includes this file; its entries will be removed from the ledger"), or refuse an exact include, on all three surfaces.

**Acceptance:** both deletes warn before confirming, and the surfaces agree. Tests cover an exact include and a glob.

**Blocked 2026-10-22** — Still wanted, but it needs an API contract the note leaves open ("warn in the dialog, or refuse an exact include, on all three surfaces"). Delete is a plain write today on REST, GraphQL and MCP; making it check includes means choosing between (a) refusing a delete that breaks an exact `include` (a new refusal for existing clients and agents, with its own code and parity cases), (b) a dry-run or preview that reports which includes reach the file so the app can warn before it confirms (a new field or operation on three surfaces, a backend-v2 deploy before mobile can read it), or (c) a warning in the delete result, which arrives after the file is gone. A glob include cannot be refused sensibly at all, since its effect is silent loss of entries. Rename already finds these includes, so the lookup exists; the decision is what the other surfaces do with it.

**Unblock:** the owner picks (a), (b) or (c) for REST, GraphQL and MCP together (and whether a glob is warned or only an exact include refused); then it is a ledger or backend-v2 change with parity cases and a deploy, and a mobile dialog change after it. Who can clear it: the repository owner (API contract decision and deploy).
