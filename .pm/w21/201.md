# Reading a missing file returns `null` with no error on GraphQL but NOT_FOUND on REST and MCP; a directory path is BAD_USER_INPUT on REST and MCP only

**Severity:** minor-to-moderate (parity rule, failure behaviour). The same request fails differently by surface, and GraphQL also turns upstream rate-limit or unavailable errors into INTERNAL_SERVER_ERROR. **Estimate:** 1–2 hours, coordinated with mobile, which relies on the `null` (w3/201's null-result recovery). Owner: backend-v2 and mobile. A3: GraphQL uses the single-file read through the workflow, which maps a 404 or a directory result to `null`. REST and MCP use the batched `getFilesContent`.

Verified through the API at `main` `afd7265e3` (read-only):
- REST `GET …/files/nope-qa.bean` → **404** `{"code":"NOT_FOUND","message":"File with ID 'nope-qa.bean' not found"}`
- GraphQL `getLedgerFile(path: "nope-qa.bean")` → **`{"getLedgerFile": null}`** with no error

## Where (`backend-cluster/`)

- GraphQL: `backend-v2/src/…/ledger-resolver.query.ts:121` → `ledger-workflow.ts:1429-1464`, and `ledger/src/api/files.ts:76-104`
- REST: `…/files-handler.ts:127`; directories via `ledger-repo-service.ts:228`
- MCP: `read-ledger-files-tool.ts:99` (an uncoded Error classified as NOT_FOUND by message, `mcp-errors.ts:235`)

## Fix

Pick one contract: NOT_FOUND for a missing file, and BAD_USER_INPUT "is a directory" for a directory, on all three surfaces. Pass upstream error codes through. Update mobile's file editor to treat NOT_FOUND as its current null case in the same change.

**Acceptance:** a parity test covers a missing file and a directory path on all surfaces, and the mobile editor still shows "File unavailable" for a missing file.
