# Posting amounts written the user's locale way are refused in 8 of 13 languages ("1.234,56", "1 234,56", U+2212 minus), while en/zh grouping is accepted

**Severity:** minor (the amount is refused, not misread, but the error then asks for a format foreign to the language). **Estimate:** 30 minutes. Owner: mobile. A3: `parseExactAmount` (`mobile/src/screens/multi-postings-transaction/postings-utils.ts:44-60`) recognises grouping only with `,`. It has no handling for `.` grouping, space, NBSP or NNBSP grouping, the U+2212 minus, or LRM marks, and every locale's message says "…one decimal point, like 1234.56" (`en.ts:203` and the same in de, fr, pt and ru).

Code-level at `main` `73a36ae00`. In the reviewer's tsx run, each locale's own `Intl.NumberFormat(l, {minimumFractionDigits: 2})` output was fed to the parser:
- en and zh `1,234.56` parse to 1234.56;
- ca, de, nl and pt `1.234,56` return null;
- fr, ru, sk and uk `1 234,56` (narrow or no-break space) return null;
- fa negatives (LRM + U+2212) return null;
- a pasted `−12.50` with U+2212 returns null.

Not exercised on the device (pasting is limited in this run).

## Fix

Normalise first: strip U+200E and U+200F, map U+2212 to `-`, and drop spaces, NBSP and NNBSP between digit groups. Then accept `.`-grouped amounts when a `,` decimal follows (`^-?\d{1,3}(\.\d{3})+,\d+$`). Add tests over every locale's Intl output. A bare `1.234` stays the decimal 1.234, as w21/031 decided.

**Acceptance:** each locale's formatted 1234.56 and −12.50 parse correctly. Unit cases are added.
