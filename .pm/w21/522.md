# After Overwrite or Recreate, the file editor still compares against the text first loaded, so reverting the edit is never saved and Back loses it silently

**Severity:** minor (silent data divergence). **Estimate:** 30 minutes. Owner: mobile. A3 (code-level at `main` `605af3313`, proven under `tsx` with the real `@codemirror/state` and `revision-tracker`):
- `mobile/src/components/code-editor/code-editor.tsx:377`: the editor's saved-text baseline (`savedDocumentRef`) moves only when a save started by `requestSave` succeeds.
- `ledger-file-editor-screen/index.tsx:649` (`overwriteRemote`) and `:681` (`recreateFile`, the w21/378 flow): these save outside that path. They clear the screen's unsaved flag (`markRevisionsSaved`) but leave the baseline at the text first loaded.

Scenario:
1. Files ▸ `main.bean` (`2026-01-01 open Assets:Cash`). Type `2026-01-02 open Assets:Bank` and don't save.
2. Change the file elsewhere.
3. In the app: Save ▸ "File Changed" ▸ Overwrite ▸ Overwrite. Save greys, which is correct, and the server now has both lines.
4. Delete the Bank line, or undo it. The buffer now equals the *first-loaded* text, so `isDirty` is false.
5. Save stays grey, and Back leaves with no "Discard your changes?". Reopening shows the Bank line still in the file.

Not run natively: the driver can't select and delete text inside the DOM editor.

## Fix

After Overwrite or Recreate succeeds, move the editor's baseline to the saved text: route both through `requestSave`, or push a new `savedValue` through `documentSpec`.

**Acceptance:** in that scenario, step 4 turns Save back on and Back asks to discard. A test covers Overwrite and Recreate followed by a revert.
