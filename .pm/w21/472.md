# w21/388 is not fixed on the device: after a metadata edit that keeps the hash, Save returns to a detail screen without the new metadata

**Severity:** moderate (the save looks lost; w21/251's and w21/388's acceptance are still unmet). **Estimate:** 20 minutes. Owner: mobile. A3: the fix (`fc36cb097`) clears `selectedTransactionVar` so the detail screen falls back to entry context and its focus refetch. On the device, the detail screen you return to still renders the old entry, so the refetch either doesn't fire or the cached context isn't replaced.

Reproduced natively (iPhone 17e, fresh Metro `--clear` at `452b3733f`+, including `fc36cb097`). The fixture was `2026-08-30 * "QA Meta" "qa-20261020 meta probe"` on the disposable ledger, later restored to `f1a0b83c`:
1. I opened it from Transactions, tapped Edit, added `  qq: "b"` under the header (soft keyboard and accessory chips), and tapped Save.
2. The save committed: the file holds the line, and `getLedgerJournal` and `getLedgerEntryContext` for hash `52c329af…` return `meta: {qq: "b"}`.
3. The detail screen showed Money flow and Entry Context with no Details/Metadata card, unchanged after another 5 s.
4. Going Back and reopening the row showed "Metadata: qq: b".

## Fix

After a hash-keeping save, refetch entry context explicitly (or update its cache entry from the saved slice) before returning, rather than relying on the focus refetch. Check the guest stash too.

**Acceptance:** the steps above show "qq: b" on the detail screen right after Save. A screen-level test covers the return path, not only the stash clearing.
